# TODO2 (new platform build-out tasks)

The single task file. Every agent, the swarm orchestrator and the integrator read and write only this file for task state.

| Mark | Meaning |
|---|---|
| `[ ]` | Open. Nobody has taken it. |
| `[-]` | Taken. An agent is working it (`agent:` names who). |
| `[x]` | Done. Evidence and the PR or commit are on the entry. |

Rules for agents:
- Pick the first open task whose `depends` are all done. Change `[ ]` to `[-]` and add `- agent: <your name>` before you start. Keep WIP one per agent.
- When the task passes every gate, change it to `[x]`, add `- evidence:` (commands, CI run, SHA) and `- pr:` in the same change. Never mark `[x]` without evidence.
- If you stop without finishing, put the mark back to `[ ]` and remove `agent:`.
- Swarm workers do not edit this file. The orchestrator marks `[-]` when it starts a worker and the integrator marks `[x]` when it merges. A task is swarm-dispatchable when it has a `scope`.
- Entry fields: `requirements`, `depends` (task IDs), `scope` (comma-separated path prefixes), `reserved` (one database migration version), `aliases`, `agent`, `pr`, `evidence`, `details` (indented text). Specification requirement IDs come from SMARTCLINIC_V1_SPEC.md.
- Name folders and Java packages after the business domain (for example `capacity`, `events`, `patient.identity`), never after a task, story or gate ID such as `s_g5_05` or `x_01`: a task's `scope` is where its files go, so never write an ID-based path there. `scripts/check-names.py` fails the build on any new one.
- Add new stories, acceptance changes and improvement ideas here as new `[ ]` entries. Record defects in BUGS.md.
- Automatic sections: `## Repairs (automatic)` holds `FIX-<run>` repairs of a red `main`, `## Audit findings` holds the daily audit's `AUD-` tasks, and `## Issue fixes` holds `ISS-<n>` tasks made from GitHub issue #n by the issue monitor. `attempts` counts worker runs; at 3 a task waits (the issue monitor may give it one more round).

Simulated review findings are evidence of review activity, not clinical or human pilot acceptance. Real-patient approval remains a G5 gate.

## Instructions for every agent (read this first)

You are one worker on the SmartClinic V1 team. Follow these steps in order for every task. Do not skip a step because the task looks small.

1. **Read the rules before you touch code.** Read these files completely, in this order: `AGENTS.md`, `CODING_STYLE.md`, `docs/WORKFLOW.md`, `docs/SWARM.md`, `MEMORY.md`, `WORKSPACE.md`. Then read `SMARTCLINIC_V1_SPEC.md`: the sections named in your task's `requirements`, plus section 7 (architecture) and section 8 and 8.1 (security, operations, production web platform). Read every file under `docs/decisions/`. For staff web or patient app work also read `docs/design/README.md`, `docs/design/screens-and-navigation.md`, `docs/design/screen-recipe.md`, `docs/design/token-contract.md`, `docs/design/accessibility-patterns.md` and `docs/design/rtl-and-localization.md`. For database work read `db/migrations/README.md`; for API contracts read `contracts/README.md`.
2. **Load the skill for your area.** The skills are in `.opencode/skills/<name>/SKILL.md`. Always load `smartclinic-delivery`. Then load the ones that match the files you change: Java and Spring `smartclinic-senior-backend`, security and login `smartclinic-senior-spring-security`, database `smartclinic-senior-database`, build and tests `smartclinic-senior-java-build` and `smartclinic-test-engineer`, web `smartclinic-senior-react` and `smartclinic-senior-typescript`, mobile `smartclinic-senior-mobile`, shell `smartclinic-senior-shell`, Python `smartclinic-senior-python`, CI and infrastructure `smartclinic-devsecops` and `smartclinic-senior-cloud-iac`, review `smartclinic-qa-reviewer`.
3. **Stay inside the task.** Change only files under the task's `scope`. If the task needs a file outside it, stop, write the reason in your notes file (the path in your prompt) under `## Why this is not finished`, and finish without changing that file.
4. **Write the failing test first**, then the smallest change that makes it pass, then clean up. Use synthetic data only. Never commit a secret, token, password, key, real patient data or a real domain name.
5. **Names.** Name folders, packages, classes and files after what they hold (business domain), never after a task, story or gate ID. `scripts/check-names.py` fails the build on `s_g5_05`, `x_04`, `dlv_02` and similar.
6. **Run the checks yourself** before you finish: `bash scripts/worker-check.sh` for API work, `bash apps/staff-web/check.sh` for staff web, `bash apps/patient-mobile/check.sh` for the patient app, `python3 -I scripts/check-docs.py` when you edit Markdown, and for any Java or script change also `python3 -I -m unittest discover -s scripts/tests` (it fails on an unqualified Javadoc `{@link}`, an ID-style name and similar). All must pass. Paste the commands and their final lines into your notes file under `## Test evidence`, and the coverage result under `## Coverage` (AGENTS.md, Coverage rules and Swarm hand-off).
7. **Commits and pull requests.** Never add `Co-Authored-By` or `Claude-Session` lines to a commit message or pull request description.
8. **Do not edit `TODO.md`, `.github/workflows/*`, `.opencode/*`, `opencode.json`, `AGENTS.md` or `scripts/*`.** The orchestrator, the integrator and people own them, and a pull request that touches them is not merged automatically. Put a lesson for these files under `## Lessons for workers` in your notes.
9. **If something is unclear or the spec and the task disagree**, do not guess. Write the question and what you found under `## Why this is not finished` in your notes file and stop. When your prompt has findings from earlier runs, start from them.
