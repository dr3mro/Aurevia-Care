# PHARM-04 — API: pharmacy substitution proposal that the prescriber must approve (never automatic)

## Summary

Added a pharmacy substitution kernel in `com.aurevia.pharmacyflow.substitution`. Pharmacy staff propose one of the **tagged catalog alternatives** attached to the medication actually selected on the prescription, with a bounded reason (`stock`, `brand`, `formulation`), an optional note and an optional documented allergy-override reason. The prescriber sees the original and proposed catalog entries side by side with the retained allergy check, then approves with an explicit attestation — creating a new immutable **signed revision with provenance** — or declines with an optional note. Nothing changes the prescription until approval.

Safety gates added after bounded clinical/backend review: the current entry is bound to `Draft.selectedEntryId`; strength and market-approved route must be preserved; a verified allergy conflict needs an override reason; approval re-resolves the catalog and the allergy, requires an explicit prescriber attestation and fails closed if the alternative is no longer effective or a new conflict appeared. A narrow, pharmacy-authorized read port (`SubstitutionCatalog`) with a tenant-guarded JDBC adapter (`JdbcSubstitutionStore`) avoids the clinician-only `PrescriptionService.searchCatalog` boundary that would otherwise make the propose flow dead for its only authorized actor. Reuses `DrugCatalog`, `AllergyChecker`, `SpecialtyRoles`, `IfMatch`, `IdempotencyKey` and the sibling `pharmacyflow` kernel/controller pattern. Synthetic fixtures only; no dependency added; no file outside the two declared scope paths changed.

## Affected requirements

- **RX-01** — tagged catalog alternatives for prescriber review; medicine identity, catalog version and allergy findings are preserved in the side-by-side view.
- **RX-02** — prescriber attestation and explicit decision discipline; `If-Match` + `Idempotency-Key` commands; a separate signed revision, never an automatic substitution.
- Supporting: ARC-02 (tenant scope/roles/RLS), ARC-03 (`If-Match`, idempotency, 403/404/409/412/422 semantics), IAM-01 (shared role vocabulary), OPS-02 (decision provenance).

## Risk class

**Safety-critical** (prescribing). Clinical-safety and backend reviews were run, with negative and failure tests for each safety gate. No real-patient approval gate is touched.

## Review owner

Simulated `aurevia-physician-reviewer` and `aurevia-senior-backend` bounded read-only reviews; integrator's full gate. No human clinical sign-off is claimed.

## Data changes

None. No Flyway migration, backfill or schema change. The kernel holds proposals/revisions in memory exactly like the sibling `pharmacyflow/{inbox,status,clarify}` kernels; the new JDBC adapter performs read-only queries through `PrescriptionRepository` inside the existing tenant-guarded transaction, so forced RLS still confines results to the active organization. Rollback is code-only.

## Authorization boundaries and audit events

- Organization, subject and roles come only from `TenantContext` and freshly resolved `StaffRepository.activeRoles`; roles are frozen in each command. No role, tenant, prescriber or patient identity is accepted from the request body.
- `PHARMACY_STAFF` may propose and view as proposer; `CLINICIAN` may decide and view as the named prescriber, resolved from the draft. Others are denied; non-parties and wrong-tenant subjects are concealed as 404.
- The read port deliberately bypasses the clinician-only `RX_SEARCH_CATALOG`/`RX_CHECK_ALLERGIES` **action matrix** but not tenant RLS: it exposes only narrow reads over the RLS-bounded repository, is inherently read-only and never writes a prescription.
- Every write requires `Idempotency-Key`; every decision requires `If-Match`, and approval additionally requires a non-blank attestation. Stale version → 412, closed proposal → 409, invalid input → 422, wrong role → 403, invisible resource → 404.
- No durable `audit_event` row is appended here because the audit package is outside scope; sibling pharmacyflow kernels behave the same way. Durable audit of the decision is recorded as a follow-up in Findings.

## Migration and rollout considerations

No migration, so no expand/contract or rollback concern. New REST routes under `/api/v1/pharmacy/substitutions` have no callers until PHARM-06 (staff-web prescriber review) and PHARM-08 (browser journey) land. No feature flag is needed because no data is persisted.

## Clinical and architecture review

Two bounded simulated reviews were requested and their actionable findings resolved in code:

- **Physician review, HIGH — allergy check bypassed:** fixed by running `AllergyChecker.check` on the proposed entry inside `propose`, requiring an override reason on `CONFLICT`, storing the retained check on the proposal and revision, and re-checking at approval.
- **Physician review, HIGH — strength/formulation/route equivalence:** fixed by requiring identical strength value/unit and the market-approved route matching the draft route; brand/formulation changes remain possible but now require an explicit prescriber attestation on approval, carried into the signed revision.
- **Physician review, MEDIUM — stale catalog at approval:** fixed by re-resolving current and proposed entries and the tagged-alternative relationship inside `decide` and failing closed with `CATALOG_CHANGED`.
- **Physician review, MEDIUM — current entry not bound to the prescription:** fixed by resolving `Draft.selectedEntryId` through the read port and rejecting `CURRENT_ENTRY_NOT_PRESCRIBED`.
- **Backend review, HIGH — propose flow dead for pharmacy staff (clinician-only catalog action):** fixed by introducing the read-only `SubstitutionCatalog` port and `JdbcSubstitutionStore` adapter over the RLS-bounded `PrescriptionRepository`, removing all calls to clinician-gated `PrescriptionService` methods. No prescription-package file was changed.
- **Backend review, LOW — idempotency key omitted the prescription:** fixed by including `prescriptionId` in the propose key; `replayedCommandsRecordOnce` asserts two prescriptions with one key yield two proposals.
- **Backend review, LOW — pharmacy note lost on decision:** resolved by keeping the propose note on `Proposal.note`, adding a distinct `attestation` on the signed revision and preserving the override reason on the proposal through both decisions.
- **Not fixed here (documented below):** RX-02 market-entitlement re-derivation and durable audit/persistence require cross-boundary files outside scope.

No human clinical or architecture sign-off is claimed.

## Findings

- **Scope-limited durability and audit:** AGENTS.md's end-to-end list (Flyway migration with RLS, `Jdbc*` store behind a `*Store` interface, OpenAPI entry) is only partly satisfiable inside the declared scope. This story adds domain kernel, thin injected controller, HTTP-level integration tests and a read-only JDBC store behind a port; a migration and OpenAPI publication are outside the two allowed paths and owned by other tasks/workers. Matches the existing pharmacyflow siblings. No undocumented deviation was made.
- **RX-02 market entitlement not re-derived at approval:** unlike `RxService`'s clinician commands, approval checks only the generic `CLINICIAN` role because the entitlement policy is private to `RxService` and the prescription package is out of scope. A follow-up should expose a bounded entitlement check for substitution approval. Not changed here.
- **Signed revision is not applied to the transmitted prescription or persisted:** approval records an immutable in-memory revision; a cross-boundary task should persist it behind an RLS store, append an audited decision event and wire a version-checked step that applies the approved revision to the RX-02 prescription snapshot. PHARM-06/07/08 consume the API but do not require persistence.
- **Worker gate timeout (environment):** `scripts/worker-check.sh` reached the PostgreSQL integration tier and was stopped at the 285 s cap (exit 124); no check failed, and all fast constituent gates passed.
- **`opencode.json` CI-profile artifact (environment):** `S` skip-worktree flag, worktree byte-identical to `.github/opencode.ci.json`; the first `worker-check.sh` attempt reported it stale. Verified with HEAD bytes and left untouched.

## Lessons for workers

- A list-bearing record must call `List.copyOf(` **at least twice** — in the compact constructor and in an overridden accessor — or `scripts/tests/test_java_conventions.py` fails; the override also satisfies SpotBugs EI_EXPOSE_REP.
- SpotBugs' central EI_EXPOSE_REP2 exclusion matches class-role suffixes (`Service|Repository|Controller|Store|Interceptor|Guard|Appender|Configuration`), not `@Component` in general. Name a Spring adapter with a conventional role suffix (`JdbcSubstitutionStore`) instead of adding a per-file suppression.
- Check the sibling action matrices before choosing a kernel dependency: `RxService` READ allows `pharmacy_staff`, but `PrescriptionService` READ/SEARCH_CATALOG/CHECK_ALLERGIES do not. A mocked test stays green while the real flow is 403.
- `Alternative` and `AllergyCheck` live in `com.aurevia.prescription.PrescriptionContract`; `DrugCatalog`/`AllergyChecker` are in `com.aurevia.prescription`. Import them from there rather than duplicating domain types.
- Clover-style `||`/`&&` branches need a distinct test per operand: covering `freshProposed == null` does not cover the later `!stillAlternative(...)` operand; a different identity with the same id keeps both entries effective and takes that branch.
- For a cloud worker, a red pack check is the CI profile under `skip-worktree`: verify with `git ls-files -v opencode.json`, restore HEAD bytes only for the local gate and put the CI bytes back byte-for-byte; never regenerate or commit that file.
- The worker-check integration tier can exceed the five-minute cap; run `scripts/quick-check.sh`, `scripts/frontend-check.sh`, standalone SpotBugs and targeted JaCoCo instead, and leave the full gate to the integrator.
