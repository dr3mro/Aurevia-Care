# BUILD-35 — FHIR R4 mapping for orders, specimens, observations and diagnostic reports

## Summary

Added a self-contained, library-free FHIR R4 mapping layer under `com.aurevia.exchange.fhir`. It maps the existing internal records (`OrderView`, `LabAccession`, `LabObservation`, `ReportRevision`) to and from FHIR R4 JSON for ServiceRequest, Specimen, Observation and DiagnosticReport, using the Jackson 3 `JsonNode` API already on the classpath (no new dependency). Patient, accession and order identifiers are mandatory on import and a missing one is rejected with a stable 422 code instead of being guessed; the order identifier is a typed `Identifier` with a synthetic system rather than only the FHIR logical `id`. The partner profile name travels in `meta.profile` on every projection. A corrected DiagnosticReport carries a versioned `supersedes` extension linking it to the original revision, and contained Observations preserve less-than comparators, UCUM units/codes, reference ranges, abnormal flags and provenance. Specimen `quality` is a FHIR CodeableConcept array.

## Affected requirements

XCH-01 (released order → ServiceRequest), XCH-04 (result identifiers, correction lineage → DiagnosticReport), LAB-01 (accession → Specimen), LAB-02 (observation kinds, qualifiers, ranges, report states → Observation/DiagnosticReport).

## Risk class

Cross-boundary (new interoperability boundary using synthetic fixtures only). No production endpoint, tenant state, persistence or clinical approval is changed by this story.

## Data changes

## Authorization boundaries and audit events

No new authorization boundary or audit event. Every import path rejects a resource lacking the patient/accession/order identifiers before any domain projection is built; no value is inferred from unrelated fields. All fixtures use invented identifiers and contain no patient data or credentials.

## Migration and rollout considerations

## Lessons for workers

- The project uses Jackson 3 under `tools.jackson.databind`, not `com.fasterxml.jackson.databind`: build JSON with `JsonNodeFactory.instance.objectNode()`/`arrayNode()` and read with `asString()`, `asInt()`, `decimalValue()`.
- A FHIR `Code` is a CodeableConcept (`code.coding[0].code`), while `interpretation` and `dataAbsentReason` are Coding arrays. Mixing the two silently produces empty round-trip fields; a full-object `assertEquals` on the projection catches it immediately.
- Write one `fromDomain` adapter per mapper that normalizes nullable strings to `""`; then `assertEquals(source, fromFhir(toFhir(source)))` is a strict, cheap round-trip assertion that also catches dropped qualifiers and units.
- Keep the required-identifier guards in one shared helper (`FhirSupport.parseReference`): each guard becomes a branch that must be taken on both sides, so centralizing them reduces both duplication and the number of negative tests.
- A self-round-trip test cannot detect a non-conformant wire shape: both directions can agree on the same wrong FHIR type. Assert the literal FHIR shape (`quality[0].coding[0].code`, `identifier[0].system`, `valueQuantity.code`) in addition to object equality before calling a mapping done.
- In FHIR R4, `CodeableConcept` is `{coding:[{system,code}]}` while `interpretation`/`dataAbsentReason` are arrays of `Coding`; `Quantity` carries both display `unit` and UCUM `code`/`system`; business identifiers belong in typed `Identifier` entries, not only in the resource `id`.
- Before adding a defensive parse, check whether it introduces an uncovered branch: a `try/catch` around `Integer.valueOf` adds no JaCoCo branch but needs a negative test for the catch line; an extra `if` adds a branch that must be exercised on both sides.
