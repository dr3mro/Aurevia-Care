## Summary
Stale interactive `orca` claims no longer hold their scope forever. `reclaim()`
now releases an `orca` claim only when the task carries evidence written after
the claim or a matched merged pull request. Claiming a task clears prior
completion evidence, which is the freshness signal that prevents releasing a
claim an interactive worker may still be using. Other agent prefixes, live
workers, open PRs and incomplete entries are unchanged.

## Authorization boundaries and audit events
`set_task_status` clearing evidence on `taken` is the freshness contract; a
later explicit evidence write is the only positive completion signal. `reclaim`
computes matched PRs before the guard, so the merged-PR path is available to all
claim types; production callers query swarm-labelled PRs, so the merged-PR path
for an unlabelled ORCA PR is unit-only and harmless. No workflow, permission,
token or concurrency change.

## Migration and rollout considerations
Existing taken ORCA tasks that already contain old evidence remain taken until a
fresh evidence write or a matched merged PR; they are not auto-released by this
change, which is the conservative behavior.

## Findings
The merged-PR release path for an ORCA claim is unit-only because production
`reclaim` callers query swarm-labelled PRs and `pr_task_id` matches swarm branch
names or `<TASK-ID>:` titles. Keeping the path is harmless; releasing stale ORCA
entries in practice relies on fresh evidence. The plan review's other Required
gap — stale evidence surviving a claim — is fixed by clearing evidence on claim.

## Lessons for workers
Do not treat an `evidence:` field on a `[-]` task as completion unless it was
written after the claim; claiming now clears it.
