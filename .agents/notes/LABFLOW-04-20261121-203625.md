# LABFLOW-04 — API: corrected and entered-in-error reports, and release to the clinician and the patient by policy

## Summary

Added a self-contained `com.aurevia.labflow.release` slice. It composes the existing
durable XCH-06 `ReleaseService` (forced-RLS `patient_release` / `release_event` / `release_notification`
tables), the RLS-bounded `LabAccessionRepository`, the transactional `AuditAppender` and the shared
tenant-guarded `TransactionTemplate`. A `FacilityReleasePolicy` maps the facility's configured patient
release rule to an existing `ReleaseKind` (immediate, timed delay, or review hold): the clinician
receives the issued report at release time, while patient access opens only by policy. A correction
supersedes the release with a different immutable revision, records what changed and why, and emits
`CORRECTION_NOTICE` facts to the clinician and the patient who saw the earlier revision. Entered-in-error
withdraws with a reason and exposes a notice while history is preserved. `ReleasedReportView` carries the
revision, issuing organization, effective date, correction context and withdrawal notice (PAT-02).
A complete history folds release decisions and viewer notifications. A thin injected controller exposes
five routes under `/api/v1/lab/releases`.

No migration, dependency, configuration file or production file outside the declared two-path scope was
added. All fixtures use synthetic identifiers.

## Affected requirements

LAB-02 (spec §5, line 76): "Support preliminary, final, corrected and entered-in-error reports";
"Trigger XCH-04/05 on relevant issued revisions". PAT-02 (spec §5, line 86): "Show released reports with
revision, issuing organization, effective date and correction context"; "Authorize every download against
the linked patient and current release". Also implements XCH-06 (line 68 — separate release authorization
referencing the immutable revision and policy version, immediate/timed/hold, corrections and withdrawals
update access, retain history and notify recipients) and the "Retracted document" scenario (line 196 —
portal stops serving the withdrawn revision, disclosures remain in history, correction tasks use the
original recipient list). Reuses ARC-02 tenant isolation, ARC-03 version preconditions, OPS-02 audit,
ADM-01 policy versioning and CLN-05 entered-in-error semantics.

## Risk class

Safety-critical (docs/WORKFLOW.md): patient release authorization, patient association and a withdrawn/
corrected clinical result. Negative and failure tests cover cross-tenant concealment, stale version (via the
`If-Match` precondition), invalid policy and reason, hold-without-deadline, and a release with no prior
viewers. Evidence is tool-generated (Maven/Surefire/JaCoCo/SpotBugs/Flyway/PostgreSQL) plus bounded
simulated review; no real clinician, unit participant or patient evidence is claimed.

## Data changes

None. No Flyway version consumed, no backfill, lock or volume impact, no rollback or forward-fix.
The slice writes only to existing forced-RLS tables through existing adapters:
`public.patient_release`, `public.release_event`, `public.release_notification` (via `ReleaseService`),
`public.audit_event` (via `AuditAppender`), and reads `public.lab_accession` through its RLS repository.
Rollback is removal of the new package only; no data is orphaned because no column or table was added.

## Authorization boundaries and audit events

- Active tenant and actor come only from `TenantContext` (`X-Active-Organization` + authenticated
  subject); organization, actor and issuing organization are never accepted from the request body.
- Before authorizing a release, the report identifier is proved to belong to the active tenant through
  the forced-RLS `LabAccessionRepository.findById` fold inside the guarded transaction; a peer tenant's
  report is concealed as 404. `ReleaseService` re-derives membership and the clinician/tenant-admin
  decision role on every command and enforces the `If-Match` version precondition on corrections and
  withdrawals.
- Notification facts carry only recipient scope (`ordering-clinician`, `linked-patient`), a non-sensitive
  type and reason — never clinical content or a patient identifier in the payload.
- Audit: purpose `LAB_REPORT_RELEASE`, resource type `LAB_RELEASE`, scope `LAB`; actions
  `LAB_REPORT_RELEASE_AUTHORIZE`, `_CORRECT`, `_WITHDRAW`, `_READ`, `_HISTORY`, outcome `SUCCESS`.
  The durable XCH-06 decisions are separately audited by `ReleaseService` with `RELEASE_ADMIN`.
  This slice's audit append runs in the shared tenant-guarded transaction so the RLS actor/tenant GUCs
  are bound; it is intentionally a separate transaction from the release decision so a deferred
  `ReleaseService` failure is not rolled back here.

## Migration and rollout considerations

None. Five new routes are component-scanned under `/api/v1/lab/releases`; no existing route is altered.
The facility policy is carried on the command (bounded and validated) because the approved ADM-01
configuration store is owned by a separate task; a site must supply its approved version and kind.

with a one-hour timed patient delay, corrected to a new revision with a reason and viewer notices,

## Findings

- Reuse over duplication: the slice composes `exchange.release.ReleaseService`, `LabAccessionRepository`,
  `AuditAppender` and the shared `TransactionTemplate`. No duplicate release state machine, repository or
  migration was introduced. `ReleaseKind`, `PatientRelease` and `ReleaseEvent` are reused unchanged.
- Tenant isolation gap closed at this entry point: `ReleaseService.authorize` trusts the client-supplied
  revision and patient identifiers and does not itself prove the report belongs to the active tenant.
  A RLS accession lookup in `release` now conceals a foreign report as 404 (proved end to end). The
  gap in `ReleaseService` itself remains for other callers and is recorded here, not edited (out of scope).
- The viewer-notification ledger is an append-only in-memory list (process-local). The durable XCH-06
  release facts (`patient_release`, `release_event`, `release_notification`) survive a restart; the
  supplementary clinician/patient notice facts in this slice are not claimed to survive one. This mirrors
  the LABFLOW-03 in-memory report kernel pattern; a task request above asks for a durable store.
- The facility policy travels on the command because no approved ADM-01 configuration store is in scope.
  Bounds are validated (positive version, non-null kind, non-negative delay, positive hold deadline), but
  a caller could choose IMMEDIATE to suppress a site delay; the task request above asks for server-side
  resolution from approved configuration.
- This slice's audit append runs in a separate guarded transaction from the release decision, so the two
  are not atomic. This deliberately preserves `ReleaseService`'s audited deferred-failure pattern (a DENIED
  audit committed before the exception) instead of rolling it back in an outer transaction.
- Bean/route naming: the controller is `LabReportReleaseController` and its routes sit under
  `/api/v1/lab/releases`, distinct from `exchange.release.PatientReleaseController` (`/api/v1/releases`),
  so component scanning and route mapping do not collide (proved by the full Spring context in the
  integration test).
- Environment artifact (not a defect of this change): the worktree `opencode.json` is the CI profile under
  `skip-worktree`, so `check-pack.py` and five `test_check_pack` cases fail until HEAD bytes are restored;
  all other policy checks and 799 of 804 tooling cases pass with the worktree bytes and all 804 pass with
  the HEAD bytes. No protected file was edited.
- Bounded simulated senior-backend review (static file reads; no tool execution by the reviewer):
  F1 (MEDIUM, accepted/out of scope) — client-supplied policy; F2 (MEDIUM, accepted/out of scope) —
  process-local viewer ledger; F3 (MEDIUM, fixed) — added the RLS accession ownership check so a peer
  tenant cannot release a foreign report; F4 (LOW, fixed) — used `specimenId + ":v" + version` because
  the release revision-id pattern rejects `/`; F5 (LOW, fixed) — wrapped audit in the guarded transaction
  after the HTTP test exposed an RLS violation. No reviewer finding remains unaddressed inside scope.

## Lessons for workers

- `AuditAppender.append` writes to a forced-RLS table and must run inside the shared tenant-guarded
  `TransactionTemplate`; calling it directly yields `42501 new row violates row-level security policy for
  table "audit_event"` and surfaces as HTTP 500 outside a guarded transaction.
- `POST /api/v1/lab/releases/{id}/correct` and `.../withdraw` require an `If-Match` version header;
  omitting it returns 428 `PRECONDITION_REQUIRED` before any service logic runs.
- `ReleaseService` does not prove tenant ownership of client-supplied revision/patient ids; any lab entry
  point must check the RLS accession fold first or a peer tenant can authorize a foreign release.
- Release revision ids must match `[A-Za-z0-9._:-]{3,128}` — `/` is not allowed. Use `specimenId + ":v" + version`.
- JaCoCo counts both operands of `value == null || value.isBlank()`; a blank-string validation test alone
  leaves the `== null` side uncovered. Add an explicit null case for every such guard.
- `TransactionCallback`'s method is `doInTransaction(TransactionStatus)`, not `execute(...)`; when stubbing
  a mocked `TransactionTemplate.execute`, invoke `callback.doInTransaction(null)` in the answer.
- A `TIMED` release is not visible until its effective instant; assert delayed patient visibility through
  `GET /api/v1/patients/{id}/released-revisions` and through `PatientRelease.visibleNow(clock)`, not just
  the authorization response.
