# READY-41 — Durable authorization decision ledger (OPS-02)

## Summary

`CommandAuthorization.DecisionSink` now has a production implementation:
`JdbcDecisionSink` writes allow and deny decisions to the append-only V65
`authorization_decision` table through the caller's tenant-guarded transaction.
`AuthorizationDecisionConfiguration` exposes it as the single production
`DecisionSink` bean; unit tests keep `InMemoryDecisionSink` by construction.
A failed ledger write never authorizes a command: the sink throws
`DecisionAuditException` carrying a denial with reason `AUDIT_UNAVAILABLE`.
No route, OpenAPI entry or generated client changed. All identifiers and codes
in tests are synthetic; no patient data, request body or credential is stored.

## Data changes

New additive migration `db/migrations/V65__authorization_decisions.sql` creates
`public.authorization_decision`: `id uuid` primary key with `gen_random_uuid()`,
`organization_id uuid` referencing `organization`, `subject`, `action`,
`resource_type`, `decision text CHECK (decision IN ('allow','deny'))`,
`reason_code`, `correlation_id` and `decided_at timestamptz DEFAULT now()`.
Every code column has an explicit database length CHECK matching the Java
bounds (subject 256, action 128, resource_type 128, reason code 64, correlation
128). The table has ENABLE and FORCE ROW LEVEL SECURITY with
`tenant_isolation` USING/WITH CHECK `organization_id = public.app_org()`;
reject-mutation triggers cover UPDATE, DELETE and TRUNCATE for every role,
including the owner. `aurevia_app` receives SELECT and INSERT only. No
existing migration was edited; no backfill, no lock or volume impact on
existing rows; rollback drops the new table.

## Authorization boundaries and audit events

`JdbcDecisionSink` checks the bound `TenantContext` before SQL: absent context,
blank/null organization and a decision from another tenant all fail closed.
The insert names `organization_id` explicitly and runs inside the caller's
tenant-guarded transaction, so the ledger row commits or rolls back with the
command. Client-derived command identifiers are stripped of control characters
and truncated independently of `CommandAuthorization`, whose non-UNKNOWN paths
pass the raw value; subject, action, reason code and correlation are bounded as
well. `rolesUsed` is never persisted, and there is no free-text, body or
patient column. The OPS-02 reason `AUDIT_UNAVAILABLE` lives on the in-memory
denial carried by `DecisionAuditException`: when the ledger is down no row can
be written. The HTTP contract is deliberately unchanged (500
`DECISION_NOT_RECORDED`), so no new audit event or error code is published.

## Migration and rollout considerations

V65 is additive and can be deployed before the application: an instance
starting before the migration simply fails closed on its first ledger write.
No feature flag, no data migration, no client rollout ordering. The V65
description is a business-domain name; the reserved version is used once.

## Production entry point and integration test

Production bean: `AuthorizationDecisionConfiguration.authorizationDecisionSink`
supplies `JdbcDecisionSink` behind `CommandAuthorization.DecisionSink`. The
gate itself still has no HTTP caller today; AUTH-WIRE-01 owns that interceptor
and depends on this story, so no route is claimed here and no OpenAPI or client
change is needed. `AuthorizationDecisionLedgerTest` autowires the bean, asserts
`instanceof JdbcDecisionSink`, writes inside `TransactionTemplate` (so the
guarded GUC is bound), and reads rows back through a second PostgreSQL
connection. It also drives `CommandAuthorization.synthetic(...)` through the
durable bean, proving gate → sink → table, and asserts a rolled-back decision
leaves no row.

## Findings

- **Environment conflict (tool evidence).** The owner directive in
  `.opencode/config/MEMORY.md` forbids Git commands and Git-using scripts; the
  story text asks for `git merge --no-edit origin/main`, a local commit and
  `bash scripts/worker-check.sh`. `scripts/worker-check.sh` dispatches
  `scripts/worker_gate.py` (Git calls at lines 84, 103, 108, 272, 275, 403),
  and `scripts/quick-check.sh` dispatches `check-constraints.py` and
  `check-names.py`, which invoke Git. The authoritative no-Git directive wins;
  no Git command or commit was run here and no tracker/protected file was
  edited. The integrator owns the full gate, merge and task marks.
- **Brief gap.** The brief lists the missing V65 file as a path needing
  confirmation; it is the file this story creates under the reserved version
  V65. The brief also restricts skills to `aurevia-delivery`, while
  `tasks/_head.md` step 2 names domain skills; recorded above.
- **Reachability (reviewer + tool).** `CommandAuthorization` has no HTTP caller
  yet. `tasks/00094000-AUTH-WIRE-01.md` is `[-]` with `depends: READY-41` and
  already owns the single interceptor that will call the gate for every POST;
  this story deliberately stops at the durable bean. No task-request needed.
- **AUDIT_UNAVAILABLE semantics (reviewer).** When the ledger is unavailable no
  row can be written, so the reason is carried by the in-memory denial on
  `DecisionAuditException`; the public HTTP error remains 500
  `DECISION_NOT_RECORDED`. A future worker should know that unauthenticated
  decisions carry `organizationId=""` and no `TenantContext`, so this sink
  fails closed as `AUDIT_UNAVAILABLE` rather than 401; AUTH-WIRE-01 must supply
  a tenant-less audit path or skip ledger writes for that case.
- **Command identifier mapping (reviewer decision).** V65 has no `command_id`
  column, so the bounded command identifier is stored in `resource_type` and
  the catalog action key in `action`. Only codes are persisted; `rolesUsed`,
  bodies and patient fields are not.
- **Reviewer optional findings adopted (reviewer + tool).** The sink strips
  Unicode control/format and line/paragraph separator categories (`Cc`, `Cf`,
  `Zl`, `Zp` — the last added at the coverage auditor's Optional request), not
  just ASCII `Cntrl`, and truncates on a code-point boundary so a surrogate
  pair is never split; `DecisionAuditException`'s Javadoc no longer claims a
  live consumer. All were re-tested and re-counted in the coverage batch above.
- **Hand-off to AUTH-WIRE-01 (reviewer).** Besides the tenant-less audit path
  for unauthenticated decisions, the interceptor must commit denial evidence
  on a path that is not rolled back: because this sink joins the caller's
  transaction, a deny followed by an interceptor rollback leaves no row
  (`rolledBackDecisionLeavesNoRow` documents the atomicity trade-off).
- **No production code outside scope changed.** `CommandAuthorization`,
  `InMemoryDecisionSink`, `scripts/wiring-baseline.json`, trackers and
  workflows are byte-unmodified.

## Lessons for workers

- When the owner's durable no-Git directive conflicts with a story's Git steps,
  stop at the directive, run the Git-free equivalents of every gate stage and
  record the exact conflict and tool evidence in the notes; do not re-diagnose
  the same blocked artifact on another pass.
- A durable audit sink must join the caller's tenant-guarded transaction; a
  self-managed transaction breaks state/audit atomicity and hides the real
  isolation boundary.
- Bound client-derived audit values at the sink, not only at the gate: the
  non-UNKNOWN authorization paths pass the raw command identifier to the sink.
- A bean without an HTTP caller can still be the correct slice when the backlog
  already assigns the caller to a dependent task; check `depends` before filing
  a task-request.
