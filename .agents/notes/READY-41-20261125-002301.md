# READY-41 · Durable authorization decision ledger (OPS-02)

## Summary

Implement the durable OPS-02 authorization decision ledger: migration V65, a JDBC
`DecisionSink` with a production Spring bean, and fail-closed sink-failure behavior.
Synthetic tenants and subjects only; no patient data or credentials in any fixture.

isolation and fail-closed authorization audit.

- **Sink-failure behavior:** the `ApiException` code becomes `AUDIT_UNAVAILABLE`
  (500). No `Decision` object with that reason code is ever constructed because
  `sink.record()` throws; the `Decision.reasonCode` Javadoc is therefore left
  unchanged. The single existing assertion of `DECISION_NOT_RECORDED` in
  `CommandAuthorizationTest` is changed intentionally because behavior changed on
  purpose, not to make a test pass.
- **Second fix pass:** a review found that the first length CHECKs rejected values
  the gate itself emits, so `action` and `correlation_id` now permit length 0 as
  bounded sentinels (unresolved command, absent correlation); all text columns stay
  length-bounded. A new integration case drives `authorize()` through the production
  bean for unknown (422), malformed (422), null-correlation (allow) and denied (403)
  commands and asserts the persisted rows and codes. Class and `Decision` Javadoc
  were corrected to match the 401-before-sink behavior. No threshold or check was
  weakened: the relaxed bounds describe legitimate domain values, while the fixed
  reason codes keep client text out of the ledger.
- **Fix pass after code review:** tenant-less identities now raise the defined 401
  before any sink call, so a durable sink's tenant precondition cannot mask the
  authentication outcome; `UNAUTHENTICATED` was removed from the `Decision` reason
  codes and the now-unreachable null-identity path and `auditableCommandId()` were
  deleted. Unknown/malformed commands record only the fixed `UNKNOWN_COMMAND` /
  `INVALID_COMMAND` code, so no client-supplied identifier reaches the ledger.
  V65 now also bounds every text column length, and the integration test asserts
  TRUNCATE rejection and that a forged cross-tenant INSERT fails specifically with
  `row-level security`. Two existing test methods were updated because behavior
  changed on purpose (401 before recording; fixed reason code instead of attempted
  identifier); neither was weakened.
- **Mismatch for the follow-up owner:** `AUTH-WIRE-01` step 4 asks for a decision
  row for every case including sink failure. A throwing sink cannot persist a deny
  row; the agreed behavior here is 500 `AUDIT_UNAVAILABLE` with no row. This is
  flagged for that task's owner; workers do not edit `tasks/`.
- **Unauthenticated path:** `JdbcDecisionSink` explicitly rejects a decision whose
  organization id is null or blank instead of relying on a PostgreSQL cast error.
  Production callers must invoke the sink inside the tenant-guarded transaction so
  `app.current_org` is bound (`TenantGuardTransactionManager`).

## Findings

- **Cross-story mismatch for AUTH-WIRE-01 owner:** step 4 of `tasks/00094000-AUTH-WIRE-01.md` asks for a decision row for every case including sink failure. A throwing sink cannot persist a deny row; the agreed behavior delivered here is 500 `AUDIT_UNAVAILABLE` with no row. Flagged for that task's owner; workers do not edit `tasks/`.
- **No HTTP caller in this story:** the production `DecisionSink` bean is reachable from Spring and proved against PostgreSQL, but `CommandAuthorization` still has no request-time caller. AUTH-WIRE-01 owns that wiring; READY-41 does not claim the full entry-point-to-test definition of done.
- **OWASP image limit:** no cached NVD database in this worker; exact error recorded above.
- A test-first integration fixture initially failed with `new row violates row-level security policy for table "organization"`; fixed by binding `app.current_org` before seeding each synthetic organization, matching the existing integration-test pattern.
- An initial `Instant` parameter failed with `Can't infer the SQL type to use for an instance of java.time.Instant`; fixed by binding `Timestamp.from(...)` and asserting that parameter in the unit test.
- **Carry-forward for AUTH-WIRE-01:** the new integration case catches `ApiException` *inside* the guarded transaction so the deny row commits. A real request-time interceptor must preserve that commit semantics for denials (for example a separate transaction boundary for the sink write), or durable denial audit is lost once the gate is wired. Also reconcile that task's "row for sink failure" expectation with the agreed 500 `AUDIT_UNAVAILABLE` / no-row behavior.
- **No commit was made:** the owner's durable no-Git directive forbids commits, merges and Git-backed scripts in this worker. All scoped changes are in the working tree for the trusted integrator to publish.
- `InMemoryDecisionSink`'s Javadoc was updated in the same change because it claimed durable audit still lived with the owning services' audit appender, which this story supersedes.

## Lessons for workers

- Bind `app.current_org` before inserting seed rows into any tenant-owned table, including `organization`; Flyway applies first but the seed connection is still subject to forced RLS.
- PostgreSQL via Spring `NamedParameterJdbcTemplate` needs `java.sql.Timestamp` for an `Instant` decision time; a raw `Instant` parameter fails before the INSERT reaches RLS.
- With a durable sink, "fail closed with an audit reason" means the `ApiException` code `AUDIT_UNAVAILABLE`; no `Decision` object with that reason is constructed, so do not advertise it in the `Decision` record's Javadoc.
