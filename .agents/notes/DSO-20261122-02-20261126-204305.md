## Summary

The `synthetic-auth` profile now fails application startup unless `AUREVIA_ALLOW_SYNTHETIC_AUTH=true` is explicitly supplied. The permit-all filter chain is unchanged once opted in; the OIDC resource-server chain, its blank issuer/audience checks and its audience validator are untouched. This closes the threat-model gap that let a deployed image inherit header-only identity by profile configuration drift.

## Affected requirements

IAM-01 (authentication boundary / synthetic-auth test-only guarantee), WEB-03 (OIDC resource-server boundary). No new requirement IDs were introduced; `docs/security/threat-model.md:40` and `:100` record the gap this change closes.

No route, role, permission, tenant check or audit event was added or changed. The guard removes an unsafe *startup* configuration: without the opt-in no filter chain exists and no request is served. ## Migration and rollout considerations

Deployments that intentionally use the test profile must set `AUREVIA_ALLOW_SYNTHETIC_AUTH=true` explicitly; all others fail closed. The published `:latest` image currently defaults to `synthetic-auth` and therefore needs the person-owned image change recorded in the task-requests block before its smoke loop can pass. Production must use the `production` profile and must never supply the opt-in.

## Lessons for workers

- When a startup guard is activated by a profile, count every `@ActiveProfiles` / `spring.profiles.active` site in the whole test tree before coding: a "three runners" plan missed seven in-scope `@SpringBootTest` suites and 210 out-of-scope ones.
- A one-file test-classpath profile property source is the smallest fix for a fail-closed profile guard, but it belongs to whoever owns the test-resource scope; raise a task-request instead of editing it from a Java-only scope.
- For a "200 without a token" assertion under synthetic-auth, still send `X-Synthetic-Subject` and a valid `X-Active-Organization`: `TenantContextInterceptor` otherwise returns 401/422 and the test fails for the wrong reason.
- In this cloud image `python3 -I -m unittest discover -s scripts/tests` reports three stale `opencode.json` pack failures (skip-worktree CI profile) and one background-process reap failure. Confirm once, record the command and final line, run the other policy stages individually, never regenerate the protected generated file, and hand the pack drift to the trusted integrator rather than treating it as an allowed exemption (AGENTS.md/task 01323000).
- `scripts/worker-check.sh` runs every integration suite; use the individual policy scripts plus targeted `-Dtest=...` batches instead, and leave the full gate to the integrator.
