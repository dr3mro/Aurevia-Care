# FIX-44919572318 — Repair main: Agent swarm failed

## Summary

**Classification: external GitHub Actions credentials/permission failure in the trusted
integration step, not a repository defect. No repository file was changed.**

Run [44919572318](https://github.com/dr3mro/Aurevia-Care/actions/runs/44919572318) (push of
`9aa95073df86725eca6a122b1bf02ac3c781ea82`, 2026-11-21T15:30Z) failed only in
`Swarm integrator / Integrate the ready batch / Merge each PR, gate, then push once`. That step
ran for three seconds (15:59:22–15:59:25Z) and exited 1. The watchdog issue #387, written from
the **full** failed log, classified it `credentials`: at that commit the classifier requires a
`CREDENTIALS` match plus either an auth-named failed step or a precise auth error (Bad
credentials / Resource not accessible / Requires authentication / permission denied / HTTP
401-403 / expired-invalid token), and excludes test-only steps. Here the step name is inert, so
the precise auth string from the full log is the deciding signal. The stored tail in the task is
PostgreSQL service-container noise and contains no code error, so it cannot be used to infer a
repository defect.

The failing step is a trusted wrapper that calls
`python3 -I scripts/swarm.py integrate-batch --queue "$QUEUE" --gate "$GATE"`. Its first action
for a queued PR is a `gh pr view` inside `is_repair`. A synthetic bad-credential response makes
that command exit 1 in under a second with `CalledProcessError`, reproducing the observed
three-second failure shape. No repository edit can repair a runner token or secret: the correct
action under the story rule ("When it is a transient or runner problem, say so ... and change
nothing") is this classification note only.

This is **not** a claim that the problem is proven fixed. The next green run (44929256479) had an
empty queue and **skipped** `Integrate the ready batch`, so it never re-exercised the failing
path; the same is true of the current green runs inspected. If the failure recurs with a non-empty
queue, a person must check the health/scopes of `SWARM_TOKEN` (or the job token) rather than
assign another code repair.

## Findings

1. **The task's stored log tail is not the failure.** `repair_task()` captures only the last 150
   lines of `gh run view --log-failed`; for this job those lines are PostgreSQL container
   shutdown noise. Running the failed commit's `classify_failure` on that tail returns
   `unknown`, while the watchdog's full-log verdict was `credentials`. A repair worker reading
   only the tail cannot diagnose an auth error. Path: `scripts/swarm.py` (`repair_task`). Do not
   edit that script from a repair PR (protected file); route a log-capture improvement to the
   daily notes/triage.
2. **Fast failure is consistent with the first `gh` call, not with the merge gate.** Steps 1–7
   succeeded and step 8 lasted three seconds; `integrate-batch` reaches `gh pr view` in
   `is_repair` before any merge or gate subprocess. `gh()` does not retry `Bad credentials`.
   Path: `scripts/swarm.py` (`gh`, `is_repair`, `integrate_prepare`).
3. **No repository change to blame.** Between `9aa9507` and the next green head `799770f` there
   is no change to integrator token wiring. The maintainer's label change and the issue's
   "next run is green" comment indicate an external secret/permission condition at that time.
4. **Recovery is unproven, not disproved.** The following green runs skipped the integration job
   because the queue was empty. Classify this as "external auth failure, no repo defect"; do not
   close a recurrence as code-fixed. Next step for a person: verify `SWARM_TOKEN` validity and
   scopes (or the job token permissions) and re-run a wave with a non-empty queue.
5. **Worker-environment noise recorded once**: six `test_check_pack` failures from the
   skip-worktree CI profile; not a defect of this pass and not to be "fixed" by regenerating or
   committing `.opencode/opencode.json`.

## Lessons for workers

- Before coding a `FIX-<run>` repair, read the run's job/step metadata and the watchdog issue:
  the repair task body keeps only the log tail, which can be pure service-container noise.
  A three-second trusted-step failure points at auth/setup, not at the application gate.
- A watchdog class of `credentials` is strong evidence: the classifier requires a precise auth
  string in the full log and excludes test steps. Treat it as an owner/secret issue, not a code
  defect, and do not change workflow or script files from a repair PR.
- "Next run green" is not proof when the failing job was skipped for an empty queue. Record that
  distinction explicitly instead of claiming the problem is resolved.
- In cloud workers, `git ls-files -v .opencode/opencode.json` returning `S` and the worktree file
  matching `.opencode/opencode.ci.json` explains `test_check_pack` failures; never regenerate or
  commit that file from a worker.
