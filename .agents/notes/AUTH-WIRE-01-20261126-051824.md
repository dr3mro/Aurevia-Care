## Requirement mapping

- OPS-02: the gate must produce an append-only decision for each gated command through the delivered
  `DecisionSink`, including denial and sink-failure paths.
- ARC-04: a single interceptor resolves the handler to one catalog command and applies one decision
  algorithm to every analogous POST transition rather than duplicating policy in controllers.
- Acceptance mapping: allowed command → decision row and handler runs; forbidden role/tenant → 403
  and deny row; unknown command → deny row (fail closed); sink failure → deny, never an allow;
  tenant isolation → a decision row is visible only in its own tenant.
- Deliberate scope boundary: the interceptor registers on `CommandCatalog.paths()` (24 POST
  templates). The other ~224 POST handlers keep their existing service-level authorization; they
  cannot be catalogued here because the generated contract/client artifacts are outside scope.
  The unknown-command deny is proven by registering the same interceptor without a path
  restriction (effectively `/**`) in the standalone HTTP harness. This is recorded
  as a finding and a task request, not presented as complete fail-closed coverage of every POST route.

## Findings

1. Catalog coverage boundary. `CommandCatalog.synthetic()` has 24 POST entries and only about 13 match live handlers; 227 of 248 `@PostMapping` handlers have no entry. This change registers the gate on `catalog.paths()` only, so those 227 POSTs keep their existing service-level authorization and are not recorded by the new interceptor. Expanding the catalog changes generated contract/client artifacts outside this task's scope and needs an owner decision; requested below.
2. No command identity exists on the wire. The matched Spring route template is the only server-authoritative identifier; the generated client's `command` field is transport metadata and was deliberately not trusted.
3. Deny statuses are the gate's native contract, not a uniform 403: 401 `UNAUTHENTICATED`, 422 `UNKNOWN_COMMAND`, 403 `FORBIDDEN` for membership/policy denial, 403/500 `AUDIT_UNAVAILABLE` or 500 `DECISION_NOT_RECORDED` for sink failure. The story's "403 on deny" is satisfied by every policy-denied command; translating 422/500 to 403 would mask which decision was made.
4. Tenantless `UNAUTHENTICATED` requests have no durable row by design (`JdbcDecisionSink.java:100-106`, forced RLS cannot own such a row). The standalone test asserts the recorded in-memory deny; the real-sink test asserts no allow row.
5. Out-of-scope observations (not changed here): the correlation id is generated twice (`CorrelationIdFilter` and `TenantContextInterceptor`), but the gate correctly uses the tenant context value; idempotency replay performs a second `ReplayAuthorization` check after the gate recorded ALLOWED, so a revoked caller can receive 404 with no new deny decision.
6. `bash scripts/worker-check.sh` and `bash scripts/python-coverage.sh` fail only on the documented stale `opencode.json` CI-runtime profile in this worker image; see Test evidence. No protected file was edited to work around it.

the owning services on catalogued POST routes. It swallowed application-level DENIED

replay filter could conceal them with 404, and ran on the static-resource fallback handler
for catalog-shaped paths with no controller, turning a native 404 into 422 UNKNOWN_COMMAND.

### Repair (production, in scope)

`CommandAuthorizationInterceptor.preHandle` now:

1. Returns immediately for non-POST requests and for handlers that are not a Spring
   `HandlerMethod`, so resource/view fallbacks keep their native 404.
2. Still asks `CommandAuthorization.authorize` for every resolved catalog command, so each
   allow and deny is appended to the V65 ledger through the injected `DecisionSink` before
   any response.
3. Swallows only a recorded `FORBIDDEN` for a resolved command: the owning service re-checks
   membership, role/action, object tenancy and preconditions and writes its own application
   audit and error body (ARC-04). `UNKNOWN_COMMAND` (422), `UNAUTHENTICATED` (401) and sink
   failures (`AUDIT_UNAVAILABLE`, `DECISION_NOT_RECORDED`) still fail closed by rethrowing,
   because no owning service can enforce those cases.

No service became ungated: every live catalog path maps to a controller whose service
re-authorizes (`FacilityService:188-196`, `SpecialtyAuthorizationFlowTest` attestation path,
`IdempotencyFilter:56-122` replay path). No threshold, exclusion, suppression or skipped

### Repair findings

1. Deliberate breadth of the swallowed deny. The gate uses one machine-readable HTTP code
   (`FORBIDDEN`) for `COMMAND_FORBIDDEN`, `MEMBERSHIP_INACTIVE`, `MEMBERSHIP_UNAVAILABLE` and
   `POLICY_UNAVAILABLE`. Restricting the swallow to `COMMAND_FORBIDDEN` alone would make a

   so all four are intentionally left to the owning service. Every live catalog route
   re-checks membership and its owning action policy in a tenant transaction. Next worker:
   if a future catalog entry's service omits that re-check, carry the recorded reason code
   on the denial and make infrastructure/wiring reasons fail closed at the gate.
