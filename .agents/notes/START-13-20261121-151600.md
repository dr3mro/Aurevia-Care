# START-13 — Docs: partner integration guide for the exchange API

## Summary

Added `docs/reference/partner-api-guide.md`: a laboratory/imaging partner
integration guide built only from the committed contract and running code. It
covers authentication (OIDC bearer token; synthetic subject is test-only),
tenant selection (`X-Active-Organization` validated against token `orgs`), all
order/result/critical states and the commands that move them, idempotency and
retry rules, the exact error body and status codes, what a partner may and may
not rely on, one fully synthetic worked example, and an entry-point-to-test
trace. Documented-vs-enforced gaps are explicit and tagged `PLANNED:` with open
task ids. No other file was changed; `docs/reference/index.md` was not touched
(START-18 owns that link).

## Findings

- The catalog-generated contract documents `Idempotency-Key` and `X-Api-Version`
  on protected POST commands, but the exchange controllers parse `If-Match`
  only; the shipped `InMemoryIdempotencyLedger` is a synthetic reference no
  exchange controller uses. Documented as a `PLANNED: READY-42` gap rather than
  claiming header-based replay safety.
- Specification WEB-04 requires request header/body size caps and an exact-origin
  CORS allowlist. Neither is present in `apps/api/src/main` or `application.yml`,
  although `TODO.md` marks `READY-04` as `[x]`. The guide marks these as
  `PLANNED: SPEC-WEB-04-C03` and `PLANNED: SPEC-WEB-04-C04`. Integrator note:
  reconcile the tracker mark with the missing code; this worker did not edit
  TODO.md.
- XCH-05 ordering: `CriticalResultService.verify` returns `409 OWNER_REQUIRED`
  unless `assign` (owner + due time) already ran, so the guide's command sequence
  is `assign → verify → ...`, not the reverse. Corrected during the draft after
  reading the service.
- Senior Integrations reviewer finding: the generated contract advertises
  `/api/v1/orders/{id}/accept` and `/api/v1/critical/{id}/acknowledge`, but the
  deployed controller paths are `/api/v1/xch03/orders/{id}/accept` and
  `/api/v1/critical-results/{id}/acknowledge`. The guide now names the controller
  paths as authoritative and warns about the drift (reviewer evidence).
- Senior Integrations reviewer finding: `ResultRoutingService.listReconciliation`
  is read-only — no route moves an entry from `open` to `resolved`. The guide no
  longer implies that transition and marks operator resolution
  `PLANNED: BUILD-08` (reviewer evidence).

## Lessons for workers

- When writing an API guide, distinguish what the generated OpenAPI catalog
  *documents* from what the controllers actually *parse*; its own README says it
  does not prove route wiring or gate invocation.
- Verify command ordering against the service's state guards (`requireState`,
  `requireVersion`) rather than inferring it from the controller's method order;
  the XCH-05 assign-before-verify rule was easy to state backwards.
- `check-docs.py` skips `.agent/` notes but checks every other Markdown file:
  keep example UUIDs, codes and relative links synthetic and resolvable, and use
  only requirement IDs defined in the specification.
