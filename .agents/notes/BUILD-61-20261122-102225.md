## Summary

Added one real-PostgreSQL acceptance suite for gates G0 and G1 in the scoped
package `apps/api/src/test/java/com/aurevia/acceptance/platform`.
Seven integration tests reuse two synthetic tenants that share identical local
identifiers (facility code `MAIN`, MRN `MRN-SHARED@CLINIC`, file name
`shared-scan.pdf`, delivery key `ORDER-CODE-SHARED`, export object alias
`shared-export-object`) and prove: API/search/file/worker/export isolation and
fail-closed context; next-request revocation; one winner for competing bookings;
stale-draft rejection against a signed note; all-or-nothing consolidation.
No production code, migration, dependency or threshold was changed.

## Findings

1. **Export HTTP entry point is broken under a real database (defect, not faked).**
   `GET /api/v1/tenant/exports/{jobId}` returned 500 for a valid active
   `tenant_admin` on a real PostgreSQL instance. Stack evidence:
   `TenantExportService.authorize(TenantExportService.java:189)` →
   `AuditAppender.append` → `PSQLException: new row violates row-level security
   policy for table "audit_event"`. Root cause: `TenantExportService` does not
   inject or use the tenant-guarded `TransactionTemplate` (unlike
   `FacilityService`, `ConsolidationService` and ~100 other services), so
   `ExportPermissionGuard` reads `has_active_membership`/`active_roles` and the
   DENIED audit append run with no `app.current_org`/`app.actor` GUCs; forced
   RLS hides every row, `mayExport` returns false, and the denial audit insert
   fails. The same gap affects `start` and `expire`. Fix belongs in
   `apps/api/src/main/java/com/aurevia/tenant/export/TenantExportService.java`
   (wrap authorize + store + audit in the guarded `TransactionTemplate`) via a
   separate story; it is outside this task's test-only scope. The acceptance
   test therefore proves export isolation at the durable `export_job` RLS and
   private object-store layers, and does not claim the HTTP path as proven.
2. **Pre-existing Git conflict markers outside scope.** Three committed files at
   HEAD contain literal conflict markers inside Javadoc comments:
   `apps/api/src/main/java/com/aurevia/exchange/hl7/Hl7ParseException.java`
   (lines 6/10), `Hl7Parser.java` (14/18) and `Hl7Segment.java` (10/14), each
   referencing `origin/swarm/BUILD-37-469`. They were present in HEAD before
   this task and are outside the scoped path; they do not break javac because
   they sit inside Javadoc, but `git grep -nE '^(<<<<<<<|>>>>>>>) '` is not clean.
   The integrator or the owning BUILD-37 follow-up must resolve them.
3. Fixture detail: `consolidation_dependency` is append-only and the blocker
   fold keys on `(patient_id, kind, reference)`. Resolving a blocker therefore
   requires appending a second row with the *same* reference and `resolved =
   true`, not an UPDATE. The first test run used an UPDATE and a new reference;
   both were corrected after observing the real failure.

### Specialist review disposition (test-engineer, simulated, tool-verified)

A bounded `aurevia-test-engineer` review of commit `c21605c8` returned six
findings. Disposition after the fix pass (all seven tests re-run green):

1. HIGH, tautological CLN-05 assertion — fixed. The sign response field was
   compared to itself. It now asserts the checksum is non-empty, equals SHA-256
   of the original draft content, and equals the value read back from the
   append-only revision view (`staleDraftCannotOverwriteSignedNote`).
2. MEDIUM/HIGH, booking concurrency proof — partly fixed. An unexpected
   response status now fails with its status and body instead of incrementing
   neither counter. The two threads still rendezvous on a `CyclicBarrier`
   before calling `book()`; guaranteeing simultaneous database transactions
   would need a request-side instrument outside this test-only scope, so the
   durable `count(*)` assertion remains the consistency proof.
3. HIGH, G0 exports not proven at HTTP — open, recorded above as a production
   defect. The test's Javadoc explicitly limits its evidence to the RLS and
   object-store layers; no HTTP download claim is made.
4. MEDIUM, revocation requirement mislabel — fixed. Relabelled IAM-02 (not
   IAM-04) in the test and class Javadoc. The G0 clauses "prior invitations and
   protected releases" are not exercised by this suite; the test Javadoc says
   so explicitly and those remain a separate G3 access-path evidence gap.
5. LOW, export count assertions order/data dependent — fixed. Both counts are
   now filtered by the seeded job id.
6. LOW, file-content isolation asserted on status only — fixed. The owner's
   `/content` response bytes are now asserted equal to the synthetic original.

## Lessons for workers

- Before writing a "revoked subject keeps access" assertion, check the action
  policy: `clinician` cannot read facilities in the G0 policy, so use an
  `admin-*` subject that already proved 200 in the same fixture.
- Append-only tables cannot be "resolved" with UPDATE. Read the fold query
  (`DISTINCT ON (patient_id, kind, reference)`) before seeding a resolution row;
  the reference must match the blocker's.
- A 500 on a real-DB HTTP test is often a missing `TransactionTemplate`, not a
  bad fixture. Confirm by reading the service constructor and the RLS policy
  before changing the test; record the production defect instead of faking a
  pass.

## Why this is not finished

Gate G0's export criterion is only partly evidenced by this change. The HTTP
export download path returns 500 on a real database (Finding 1) because
`TenantExportService` omits the tenant-guarded transaction, so its permission
and audit writes run without tenant GUCs. I did not fake this: the committed
test proves export isolation at the `export_job` RLS and object-store layers
with two tenants sharing an identical local object alias, and the HTTP-level
owner-read/cross-tenant-404 assertions were removed rather than asserted
against broken behavior. Exact next step: a separate in-scope story fixes
`TenantExportService` to use the injected `TransactionTemplate` around
`authorize`, store calls and audit appends (mirroring `FacilityService`), then
re-add the HTTP manifest-download isolation assertions to this suite. The
pre-existing HL7 conflict markers (Finding 2) must be resolved by their owner
or the integrator; this worker did not touch files outside its scope. A second,
narrower gap recorded by the specialist review: the G0 revocation sentence also
names prior invitations and protected releases, which are patient-access paths
outside this suite's staff-deactivation fixture; a separate story must add that
evidence, and the test Javadoc no longer overclaims it.
