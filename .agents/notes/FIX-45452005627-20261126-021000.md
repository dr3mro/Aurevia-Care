## Findings

- Two Spring configurations from opposite merge sides both defined `authorizationDecisionSink`, so the application context could not start. Kept `AuthorizationConfiguration` (`PROPAGATION_REQUIRES_NEW`) because the rollback-survival integration case requires it; removed the untested duplicate.
- Deleted `AuthorizationDecisionLedgerIntegrationTest`, a losing-side suite that queried a nonexistent `command_id` column, expected lowercase `resource_type`, a NULL-tenant row and an unlisted `PROBE` reason. `AuthorizationDecisionLedgerTest` supersedes it with 12 real-PostgreSQL cases.
- Restored `resource_type text NOT NULL DEFAULT 'COMMAND' CHECK (resource_type = 'COMMAND')`; the losing migration side allowed arbitrary client-supplied discriminators. The boundary test now asserts a client-supplied `CLIENT_COMMAND` is rejected.
- The ledger IT had an order-dependent count: an earlier default-timestamp case commits a second empty-correlation row. Assertions are now scoped to the specific action and correlation (`countAllowWithMissingCorrelation`, `assertLedgerDecision` filtered by action).
- `scripts/check-docs.py` now passes `env=child_environment(read_only=True)` to `git check-ignore`, with a regression asserting `GIT_DIR` is stripped; `python3 -I` needs the scripts path on `sys.path` for this import.
- A concurrent session committed the staged authorization files as `2b0e541a` and pushed an unrelated tracker commit `5263939e`; both were reconciled with a fast-forward before this push.

## Lessons for workers

- A source-level conflict-marker scan must cover all production trees, not just the file named in the failing log: Java compile and Spring context failures surfaced behind the first TypeDoc error.
- When two merge sides implement the same bean or integration suite, compare their invariants to the tests before choosing a side; a "clean" file can still contradict the retained schema.
- `python3 -I` needs an explicit `sys.path` insertion in a script that imports a sibling module.
