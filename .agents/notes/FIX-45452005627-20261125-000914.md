## Findings

- The CI red was a flaky assertion, not a frontend build or contract failure. The delivery gate's
  `docs`, `java-verify` and `verify` jobs were skipped only because the `frontend` job failed in
  the dependent chain; no gate configuration change is needed.
- Reproducing the exact CI failure by repeating the full suite locally did not succeed (four
  green runs); a deterministic deferred-effect mock reproduced the identical assertion failure,
  which is enough evidence for the timing diagnosis. The mock test was temporary and deleted.
- The worker prompt asked for `git merge --no-edit origin/main` and a local commit, but the
  durable owner directive forbids Git commands and Git-using scripts in this environment, and
  AGENTS.md assigns publication to the trusted integrator. No Git command was run; the fix is in
  the working tree for the integrator to publish. This is a prompt/rules mismatch, not a story
  defect.

## Lessons for workers

- An assertion on a callback invoked from a passive React effect must wait for the callback with
  `waitFor`; observing the rendered state view does not prove the effect has flushed under CI
  load. Keep the same equality assertion so a double notification is still caught.
- A prior worker note with the same file, line and failure message is valid diagnosis evidence;
  a green local run does not disprove a load-dependent flake.
