# DSO-20261122-03 — Scheduled audit-chain verification (stopped: out-of-scope prerequisite)

## Summary

Investigated whether a scheduled verifier can call the existing `audit_verify_chain(uuid)`
for each active tenant and append an operator-queryable `AUDIT_CHAIN_VERIFY`
SUCCESS/FAILURE outcome to the existing append-only `audit_event` table, closing the
OPS-02 "schedule automated audit-chain verification with an alert on failure" gap in
`docs/security/threat-model.md:44` and `:52`.

**Outcome: stopped before writing code.** Four independent read-only specialists found
no authoritative in-scope source of cross-tenant organization ids. The design's
verification-and-append half is sound, but a scheduler cannot obtain the tenant ids
without a new migration or a privileged role outside this task's declared scope. Per the
brief's Risk 1 and the plan-reviewer's first Required gap, the correct action is a
task-request and stop, not a fabricated tenant list or an RLS bypass.

## Findings

**Critical — the story is not implementable inside the declared scope.** Four
independent read-only specialists (context-optimizer, senior-backend,
senior-spring-security, plan-reviewer) reached the same NO-GO after targeted reads.
There is no authoritative in-scope source of active organization ids for a scheduler.

- `db/migrations/V2__rls_roles_policies.sql:6-8,13-22`: `public.app_org()` reads only
  `app.current_org` (NULL when unbound), and `organization` has `ENABLE` + `FORCE RLS`
  with `USING/WITH CHECK organization_id = public.app_org()`. `aurevia_app` is
  `NOBYPASSRLS` (`db/migrations/README.md:3`, `db/check.sh:22-25,93-94`). A `SELECT` on
  `organization` therefore returns zero rows on a scheduler thread.
- `TenantGuardTransactionManager.java:35-48` fails closed before any SQL when
  `TenantContext.current()` is null and binds exactly one org per transaction; the
  guarded datasource cannot discover the ids it needs before opening a transaction.
- Every candidate was checked and rejected: the shared app datasource, a request-token
  `orgs` claim (`ClaimsTenantResolver`, `AuthenticatedPrincipal` — no principal on a
  scheduler thread, and only the subject's entitled tenants), all config properties and
  the full `config/` package, `tenant.export`/`tenant.importing`, the pure `RetentionJob`
  domain kernel, and every DB fold granted to `aurevia_app`. Repo-wide grep found no
  `ActiveTenantSource`, no `@Scheduled`, no `@EnableScheduling`, no BYPASSRLS role and no
  `SECURITY DEFINER` tenant-list function.
- A hard-coded or config-property tenant list is not authoritative, goes stale on
  onboarding/offboarding and is expressly forbidden by the brief; an `InMemory*` bean
  would also trip `check-wiring.py` and would not be durable. `SET row_security = off`,
  a BYPASSRLS role and a cross-tenant `SECURITY DEFINER` enumerator were explicitly
  rejected by senior-spring-security as ARC-02 violations requiring out-of-scope work.
- The brief is self-contradictory: its routing block and Risk 1 state that no in-scope
  cross-tenant enumeration exists and instruct a task-request + stop, while its plan
  sketch adds `ActiveTenantSource.java` as if the source already existed. The blocker
  statements are authoritative and were followed.
- The task wording "enumerates active tenant ids through the existing tenant boundary"
  is misleading: the tenant boundary is the blocker, not the source of ids.
- The remainder of the design is sound once a source exists: bind a synthetic
  `TenantContext(id, system subject, "AUDIT_REVIEW", correlation)` per tenant, call
  `audit_verify_chain(CAST(:id AS uuid))` in a guarded transaction, append
  `AUDIT_CHAIN_VERIFY` SUCCESS/FAILURE via `AuditRepository.appendAudit` in a **fresh**
  guarded transaction when verification throws (the first transaction is aborted), clear
  the context in `finally`, and continue the loop. Define empty chain as SUCCESS and any
  `ok=false` row as FAILURE. Gate the verifier with `@ConditionalOnProperty` so live
  scheduling cannot destabilise other `RANDOM_PORT` integration tests.
- `docs/reference/modules/api-audit.md` currently states the audit package has "no
  scheduled job". Once a verifier is added, that developer reference needs an update;
  it is outside this task's scope and is noted for the next worker.

**Resolved wiring entries:** none. `python3 -I scripts/check-wiring.py` exited 0 at the

**No production code was written.** A verifier whose tenant source cannot be supplied in

## Lessons for workers

- Read the brief's risk block as authoritative when its plan sketch contradicts it; a
  planned interface is not an existing production data source.
- When a security boundary is described as "the existing tenant boundary", verify that
  the boundary is a source of ids before designing a loop over them — FORCE RLS on the
  one table that holds them makes the boundary the blocker.
- A scheduled job has no request principal and no request thread context; enumerate the
  inputs before designing the per-tenant transaction and correlation id.
- Do not run `worker-check.sh` for a stopped story: it runs the entire integration suite,
  which the brief forbids for a worker. Run only targeted commands for what changed.
