# FU-1778-01 — Authoritative cross-tenant active-organization enumerator for scheduled jobs

## Summary

Adds one authoritative, identifier-only source of active organizations for scheduled jobs that have no `TenantContext` or `app.current_org` GUC. `V101__active_tenant_enumerator.sql` adds an explicit `organization.active` flag (default true), an owner-only permissive RLS policy for the NOBYPASSRLS migration role, and a narrow `SECURITY DEFINER` function `public.active_organization_ids()` owned by `aurevia_migrate` with `search_path = pg_catalog`, `REVOKE ALL FROM PUBLIC` and `GRANT EXECUTE` to `aurevia_app` only. `ActiveTenantSource` and `JdbcActiveTenantSource` in `com.aurevia.tenant` call only that function. No HTTP route, OpenAPI change, client regeneration, BYPASSRLS grant, hard-coded tenant list or table-grant widening.

## Affected requirements

IAM-01, ARC-02, OPS-02, OPS-06. The task file assigns no explicit requirement ID; these are the requirements governing tenant isolation, role separation and cross-tenant job behavior (PROJECT_V1_SPEC.md §7 ARC-02 and §8 OPS-02/OPS-06).

## Data changes

`V101__active_tenant_enumerator.sql` (reserved version for this story; no V1/V2 edit):

- `ALTER TABLE public.organization ADD COLUMN active boolean NOT NULL DEFAULT true` plus a column comment. Existing tenants become active; no row rewrite or backfill.
- `CREATE POLICY active_organization_enumerator ON public.organization TO aurevia_migrate USING (true)`. Forced RLS also binds the NOBYPASSRLS owner; permissive policies OR together, so this lets the definer see all rows while `aurevia_app` keeps only V2's `tenant_isolation` policy. The policy is not GUC-gated: `CREATE FUNCTION ... SET app.*` is rejected for the migration role (see Findings).
- `public.active_organization_ids()` — `RETURNS TABLE (organization_id uuid)`, `LANGUAGE sql STABLE SECURITY DEFINER SET search_path = pg_catalog`, body `SELECT o.organization_id FROM public.organization AS o WHERE o.active ORDER BY o.organization_id`. The flag is the single authoritative active filter; the function returns identifiers only.
- `ALTER FUNCTION ... OWNER TO aurevia_migrate`, `REVOKE ALL ... FROM PUBLIC`, `GRANT EXECUTE ... TO aurevia_app`.
- Header declares `Change: expand`, purpose, invariants, lock/volume and recovery. Disabling the capability is `REVOKE EXECUTE FROM aurevia_app`; a future removal needs a `Change: contract` migration with `Requires-expand: V101`.

## Authorization boundaries and audit events

The runtime role can execute the narrow function but cannot read another tenant's `organization` row directly (0 rows with no GUC, 1 row with a GUC in the integration test), cannot INSERT/UPDATE/DELETE `organization` (SQLSTATE 42501), is not a member of the definer role and has `rolbypassrls = false`. The migration role alone has the owner-only permissive policy. No audit event or clinical record is created or changed; the function exposes no patient, staff or display-name data.

## Findings

- Both named specialists were consulted before coding. Initial senior-spring-security report was `VERDICT: NO-GO` with a Critical: a `SECURITY DEFINER` owned by a NOBYPASSRLS role under FORCE RLS should see no rows. This is fused with the senior-database proposal (`VERDICT: GO`): additive permissive policies OR together, so an owner-only policy makes the definer's effective predicate true. The rebuttal was proven on real PostgreSQL before coding: with two active and one inactive synthetic org, `aurevia_app` with no GUC got both active ids from the function and 0 rows from a direct SELECT; with `app.current_org=ORG_B` the function still returned both ids and the direct SELECT returned 1. `proacl` showed `{aurevia_migrate=X/aurevia_migrate,aurevia_app=X/aurevia_migrate}` (no PUBLIC). senior-spring-security then withdrew the Critical and returned `VERDICT: GO`.
- senior-database's GUC-gated variant of the policy could not be implemented: `CREATE FUNCTION ... SET app.enumerate_active_orgs='on'` fails with `permission denied to set parameter "app.enumerate_active_orgs"` for the NOBYPASSRLS/NOCREATEROLE migration role (tool evidence from psql). The simple owner-only policy is used instead; it keeps the required owner, adds no BYPASSRLS and requires no out-of-band role.
- "Active" is the explicit `organization.active` flag, not an active-membership fold. A fold would skip a newly provisioned organization with no staff and would let one live membership mark a frozen tenant active. The integration test seeds an expired/deactivated-membership-free active org and an inactive org to prove the flag decides.
- No task request is needed for the eventual consumer: task `00073776-FU-1778-02.md` (DSO-20261122-03 re-scope) already covers the scheduled `AuditChainVerifier`. No fake caller, controller or hard-coded list was added; `check-wiring.py` does not flag names ending in `*Source`.
- The unit test cannot use `@SpringBootTest` without a second datasource configuration; the real Spring bean is not in scope here because FU-1778-02 owns wiring. The primitive is proven end to end with the real JDBC template over a real PostgreSQL connection in `ActiveTenantIntegrationTest`.
- Tooling note: the full Python suite and `quick-check.sh` fail on pre-existing `opencode.json` CI-profile drift and a process-reaping timing test; no script or generated config was changed by this story (see Test evidence).

## Lessons for workers

- Before designing a `SECURITY DEFINER` escape from FORCE RLS, probe the exact role/policy behavior on real PostgreSQL: the owner-only permissive policy works, but a function-level custom-GUC `SET` is rejected for a non-superuser migration role.
- `pg_policies` exposes role names in `roles` (`name[]`), not `polroles`; and a `proacl` assertion must not use the substring `=X/`, which also appears inside `aurevia_app=X/`. Use `aclexplode` with `grantee = 0` for PUBLIC grants.
- Spring-injected collaborators trigger SpotBugs EI_EXPOSE_REP2 unless the class name matches the central exclusion suffixes; injecting the operations interface `NamedParameterJdbcOperations` keeps the design clean without a suppression.
- Do not call `CREATE TEMP FUNCTION`; use a temporary schema and grant USAGE/EXECUTE for the hostile-search-path test.
