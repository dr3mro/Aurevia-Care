# READY-41 · Durable authorization decision ledger (OPS-02)

## Summary

READY-40 is `[x]`, so the prerequisite is satisfied. `CommandAuthorization` already
produces an OPS-02 `Decision` for every allow and deny, but production supplied no
durable `DecisionSink`. This change adds the V65 append-only ledger, a PostgreSQL
sink, and the production bean. There is deliberately no new controller or HTTP
route: the owning caller is `AUTH-WIRE-01` (depends on READY-41).

## Affected requirements

- OPS-02 — audit authorization decisions with actor, action, bounded resource id,
  correlation id, outcome and reason; append-only with restricted access; a
  failed audit write denies the command.
- ARC-04 — idempotent, auditable command transitions; the decision is recorded
  before the caller is answered.

## Risk class

Cross-boundary and safety-critical: new Flyway table with RLS, a Spring bean and
an authorization fail-closed path. Clinical safety review is not required
because no patient data, order or prescription is touched; DevSecOps and
coverage reviews are required and were run.

## Data changes

New `db/migrations/V65__authorization_decisions.sql` (reserved version V65,
`-- Change: expand`, additive only). One table `public.authorization_decision`:
`id uuid` PK with `gen_random_uuid()`; nullable `organization_id uuid` FK to
`public.organization`; bounded `command_id`; `subject`, `action`, constant
`resource_type='command'`, `decision` CHECK (`allow`/`deny`), `reason_code`,
`correlation_id`, `decided_at` from the server clock. ENABLE and FORCE RLS with
a policy keyed to `public.app_org()`; a `NULL` organization branch admits only
tenant-less unauthenticated evidence, never a cross-tenant row. UPDATE, DELETE
and TRUNCATE are neither granted nor possible for the owner: V17's
`reject_immutable_mutation()` triggers cover all roles. `aurevia_app` receives
SELECT and INSERT only. No backfill, no lock on an existing table, no contract
change; forward fix is a later additive migration if a column is ever retired.
No patient data is stored.

## Authorization boundaries and audit events

The server-derived `Decision.organizationId()` selects the row's tenant and the
shared guarded `TransactionTemplate` binds `app.current_org` before the insert,
so forced RLS enforces the same boundary. `subject` and `correlationId` are
server-derived; `commandId` is bounded upstream by
`CommandAuthorization.auditableCommandId()` and the column CHECK. A blank/absent
organization (unauthenticated decision) is stored as a tenant-less row. `rolesUsed()`
is intentionally not persisted: it is not one of the OPS-02 evidence fields and
would be unbounded free text. No existing audit event is changed.

## Migration and rollout considerations

Additive migration; Flyway applies V65 in version order. Verified by a real
PostgreSQL migration in the integration test (63 migrations applied) and by
`python3 -I scripts/check-migrations.py --require-baseline`. The app role has no
write path beyond INSERT; no `flyway repair` is needed for a fresh environment.
Rollback is a contract migration in a later version, not a change to V65.

## Findings

- Unauthenticated calls with **no** `TenantContext` would make the guarded
  transaction manager throw before the insert, so the sink returns 500
  `AUDIT_UNAVAILABLE` instead of 401. The integration test binds a tenant (as
  the HTTP interceptor does) and proves 401 there; AUTH-WIRE-01 must keep its
  interceptor's 401 path ahead of the gate for unauthenticated requests. The
  behavior is still fail-closed either way.
- The `OR organization_id IS NULL` policy branch makes tenant-less evidence
  readable under any tenant context. It contains only server-derived subject,
  bounded reason/command codes and correlation id; QA/privacy should confirm
  this satisfies OPS-02 "restricted access" when the ledger is enabled.
- Transaction propagation for AUTH-WIRE-01: the sink deliberately shares the
  caller's `REQUIRED` transaction so the decision and business effect commit
  together. If the future interceptor writes a deny inside an outer transaction
  that rolls back, the deny row rolls back too. AUTH-WIRE-01 must either call
  the gate outside that rollback boundary or use a `REQUIRES_NEW` guarded
  template. This is a hand-off, not a change to this story's caller-owned
  transaction contract.
- Only `command_id` has a SQL length bound. `subject`, `action`, `reason_code`
  and `correlation_id` are server-controlled or fixed codes upstream; a
  compromised app session could still write long values. Adding CHECKs is a
  defense-in-depth follow-up, not an acceptance gap for this story.
- Known reachability debt, not fixed here: no production code calls
  `CommandAuthorization` yet. READY-41 supplies the durable bean;
  `AUTH-WIRE-01` (tasks/00094000-AUTH-WIRE-01.md, `depends: READY-41`) owns the
  interceptor that will call the gate. `docs/decisions/0003-persistence-of-in-memory-stores.md:39`
  records this as a production-enablement gate. This story is therefore not
  end-to-end enabled in production until AUTH-WIRE-01 lands.
- SpotBugs EI_EXPOSE_REP2 on the two injected Spring templates could not be
  handled by the central role-suffix exclusion because this class is a `Sink`,
  and `@SuppressFBWarnings` is forbidden. Narrow private functional interfaces
  keep the collaborators injected via the constructor without exposing the
  mutable templates as fields.
- Test correction during development: the first integration run queried tenant B
  with the app session still bound to tenant A; the test now switches the GUC
  before reading B. No production behavior changed for that correction.
- Durable-directive conflict: the worker brief asked for `git merge` and a
  commit; the higher-priority durable directive in `.opencode/config/MEMORY.md`
  (2026-11-24, "do not run Git-using scripts or tests", line 7) forbids Git
  commands and Git-using scripts/tests. No Git command, push, tag or `gh` call
  was made; the harness integrator owns publication. `worker_gate.py` inside
  `worker-check.sh` uses only read-only Git, but the directive is unconditional.

## Lessons for workers

- A `DecisionSink` implementation named `JdbcDecisionSink` does not match the
  SpotBugs central exclusion's role suffixes (`Service|Repository|Controller|
  Store|Interceptor|Guard|Appender|Configuration`). Design its fields to hold
  narrow immutable collaborators from the start instead of adding a suppression.
- An integration test that reads two tenants on one JDBC session must change
  `app.current_org` between reads; `SET` is session-scoped, not per statement.
- For unauthenticated decisions the authorization record has no organization;
  a nullable tenant column plus an `OR organization_id IS NULL` RLS branch
  preserves 401 instead of turning the denial into an audit failure.
- The MEMORY.md no-Git directive outranks the auto-generated worker brief; run
  the non-Git parts of the gate individually and say so in the notes.
