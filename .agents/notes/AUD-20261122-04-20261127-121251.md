# AUD-20261122-04 — Audit in-transaction prescription denials with DENIED rows

## Summary

Make every refused sensitive prescription action leave a durable `DENIED` audit row (actor, purpose, scope, outcome) inside the tenant-guarded transaction, so a failed clinical action is provable across RX-01 draft and RX-02 transmission and not only on `authorize` denials.

## Affected requirements

OPS-02 (audit includes actor, purpose, scope, timestamp, action, resource ID, correlation ID and outcome), IAM-06 (business purpose, role, facility and user for sensitive actions). Requirement text read from `.opencode/config/PROJECT_V1_SPEC.md` lines 32 and 135.

## Risk class

Safety-critical (prescribing, authorization boundary, audit accountability). Synthetic fixtures only; no real patient data or credentials.

## Review owner

Senior backend (Java/Spring transaction boundary), with devsecops on audit semantics and coverage auditor on the catch branch.

## Data changes

None. No migration, table, RLS policy, route, OpenAPI/client, Idempotency-Key or paging change. Reuses existing `audit_event` and its V3/V98 trigger-derived `actor_id`.

## Authorization boundaries and audit events

Denied commands inside `transactions.execute` now append exactly one `DENIED` row with `action`/`purpose` from the existing action constant and `scope` from the existing service `SCOPE` constant. Actor remains trigger-derived from the transaction-local `app.actor`; no caller-supplied actor. `authorize()` DENIED and `conflict()` CONFLICT paths are unchanged, so no double row is written. Concealed cross-tenant 404s are recorded as one DENIED row in the CALLER's tenant only; the HTTP response stays 404 and no row appears in the resource owner's tenant, so the audit is not an existence oracle.

## Migration and rollout considerations

None; no schema or contract change.

- Brief says "add one test method" per flow test; test engineering required three extra negative cases (authorize double-row, concealed-404 outcome, CONFLICT-not-DENIED) plus a policy denial. I honored the one-new-method-per-file shape and folded those cases into the new methods, and added DENIED assertions to the existing cross-tenant test without changing any existing assertion there.
- The generic worker prompt says to run `scripts/check.sh` at the end, while the brief and AGENTS.md explicitly forbid a swarm worker from running it (it delegates to full `mvn verify`). I followed the brief and did not run it.
- Existing assertion changed because behavior changed on purpose (CODING_STYLE.md coverage rule 7): `apps/api/src/test/java/com/aurevia/prescription/clauses/RecordActualChannelTest.java:232` (`refusesTheWrongPrescriber`) asserted `verify(audit, never()).append(..., "DENIED")` for a wrong prescriber. That encodes the old rollback-and-no-audit behavior which this story deliberately reverses; it was not a weakening and no production code was changed to satisfy it. The assertion now requires exactly one `DENIED` append with purpose `RX_TRANSMIT`, resource type `PRESCRIPTION`, scope `PRESCRIPTION_TRANSMISSION` and the prescription id, while `verifyNoWrites()` still proves no domain write. The file is outside the task's literal scope and belongs to completed task `00547000-SPEC-RX-02-C03` (already `[x]`), so no worker can collide with it; the change is included here because the canonical `mvn verify` runs this unit test and would otherwise be red. Code review required this fix rather than a follow-up task. No `## task-requests` block is needed.
- Optional code-review suggestion not taken: the clause prose in `docs/spec/clauses/prescription/record-actual-channel.md:26` ("negatives assert ... no write") is now incomplete for this one case, but that path is outside the declared scope and no documentation file was edited by this worker.
- Design fusion: devsecops initially returned NO-GO, preferring outcome-typed auditing (CONFLICT for 412/409, NOT_FOUND for 404) and a second transaction. The story's acceptance criteria explicitly require DENIED for 403/412/409 and an append inside the same transaction, and the brief explicitly forbids a status-code conditional to avoid an uncoverable branch, so those objections are recorded as an accepted contract for this story rather than a defect. Senior backend enumerated every ApiException throw site: all precede the first row mutation, which the catch comments document. Purpose=action and workflow scope are explicitly asserted by the acceptance criteria; facility/role columns do not exist in `audit_event` and adding them would need an out-of-scope migration, so IAM-06's purpose-only portion is satisfied here and the role/facility gap is recorded as pre-existing and outside this story.

## Lessons for workers
