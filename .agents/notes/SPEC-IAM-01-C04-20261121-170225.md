## Findings

- **Gap (the reason for the disabled test):** facility scope exists as data but not as an authorization boundary. `staff_invitation.facility_id` (V70) is not inserted into `membership` by `accept_staff_invitation`; `membership`/`role_assignment` have no facility column or association table; `ActionPolicy`, `WorklistPolicy`, `CheckInService.authorize`, `EmergencyAccessService.active` and `SupportAccessService` check membership and role only. A reception user can therefore read any facility's worklist in its active organization. Full build-out needs a tenant-owned forced-RLS persistence migration, propagation in the invitation-accept function, and enforcement in every facility-aware trust boundary — roughly two implementation tasks plus one task to enable these tests.
- **Environment artifact (not a defect):** `git ls-files -v opencode.json` reports `S` (skip-worktree); the worktree file is the CI profile and differs from `git show HEAD:opencode.json` (local profile). That makes `scripts/check-pack.py` and the three `test_check_pack` cases fail locally with "opencode.json is stale". Documented in MEMORY.md (OPS-CW-003-01 / IMP-01) and the 2026-11-19 reconciled notes; `opencode.json` is maintainer-owned and was not regenerated. No tracker files were modified by the tooling test run (`git status` shows only the two intended new files).

## Lessons for workers

- When a clause is a recorded attribute rather than an enforced decision, trace the value from persistence through the `authorize()`/policy call; a column on an invitation or grant is not evidence that access was narrowed.
- The worktree `opencode.json` under `skip-worktree` is the CI profile; `check-pack.py` failures there are measurement artifacts, never a reason to regenerate the committed file.
- For a test-only clause-evidence story, prove compilation with a targeted `-Dtest=...` run and use the fast tier (`-Pno-security,fast test`) for regression; reserve full `verify`/integration for the integrator.
