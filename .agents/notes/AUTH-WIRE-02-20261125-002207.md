# AUTH-WIRE-02 — build-failing parity check between POST handlers and the command catalog

## Summary

Delivered a **test-only** parity evaluator in `apps/api/src/test/java/com/aurevia/authz/CommandRouteParityCheck.java`
and its red/green proof in `apps/api/src/test/java/com/aurevia/authz/CommandRouteParityTest.java`.
It reuses `com.aurevia.it.contract.OpenApiRouteCoverage` for route normalisation and two-way difference,
filters discovered handlers to POST, applies a reasoned allow-list, and names both handlers without a
catalog entry and catalog entries without a handler. No file under `src/main/java` changed.

The live `RequestMappingHandlerMapping` assertion is **not** included: prerequisite AUTH-WIRE-01 is still
open and the current catalog/handler sets cannot be in parity (see `## Why this is not finished`). The
task stays unfinished; the orchestrator must not mark it `[x]`.

## Findings

- **Plan review (NO-GO) was addressed before coding continued.** Required gaps: my first note claimed
  zero catalog/handler overlap (wrong); it duplicated `OpenApiRouteCoverage` instead of reusing it;
  the allow-list semantics were under-specified; and the scope statement incorrectly said
  `CommandCatalog.java` was out of scope. All four are corrected here and in the code: the evaluator
  is test-side and reuses `OpenApiRouteCoverage`, allow-list keys are normalised and unused entries are
  defined as harmless, and the catalog is in scope but owned by the still-open AUTH-WIRE-01 step 1.
  No catalog-side POST filter exists: `CommandDefinition` accepts only POST, so that branch cannot occur.
- **Verified gap (tool evidence, not reviewer evidence).** Source inspection of 76 `@RestController`
  classes: 248 `@PostMapping` occurrences / 246 distinct source route templates;
  `CommandCatalog.synthetic()` declares 24 distinct routes. After normalising `{variable}` names,
  13 catalog routes match a live handler, 11 catalog entries have no handler, and 233 distinct live
  POST routes have no catalog entry. A strict discovery assertion therefore fails against the
  untouched baseline; a narrowed "catalog-only" gate would weaken the acceptance criterion.
- The brief dispatched this story while `tasks/00094000-AUTH-WIRE-01.md` is still `[-]` and
  `CommandAuthorization` has no production caller (it appears only inside `com.aurevia.api.authorization`
  and tests). The story and the brief both say to await that prerequisite.
- **Post-code reviews (first pass, NO-GO) were addressed where the change permits.** Code and security
  reviewers asked that the evaluator be shared rather than private to one test class: it was extracted
  to `CommandRouteParityCheck.java`, its allow-list reasons must now be one line, and the unexplained
  set is sorted for deterministic messages. Coverage and review evidence that was still "Pending"
  when those read-only agents sampled the note is filled in above. The remaining NO-GO item is the
  open prerequisite and the missing live Spring-discovery assertion, recorded below.
- Git commands were not run because of the durable owner directive; therefore no commit exists for
  this work and `worker-check.sh` was not run. An authorised integrator must run it and commit the
  scoped files; this is a hard prerequisite for calling the story done.

## Lessons for workers

- Verify catalog-to-handler overlap with a corrected normalisation before claiming a parity gate is
  green; an early script compared `/api/v1/...` with `api/v1/...` and reported a false zero overlap.
- `OpenApiRouteCoverage` already owns route normalisation, sorted reports and two-way difference;
  extend or reuse it instead of writing a parallel `Route` type.
- A production class called only by tests is dead production code. A build gate can live entirely in
  test source and still fail the build.
- The durable directive in `.opencode/config/MEMORY.md` forbids Git-using commands and scripts, so
  `worker-check.sh` (which calls `worker_gate.py` with `origin/main`) cannot be run by this worker.

## Why this is not finished

Acceptance criterion 1 (discover every `@PostMapping` via Spring `RequestMappingHandlerMapping` and
compare it with the catalog) is not implemented as a passing gate. Prerequisite AUTH-WIRE-01 is open:
its production interceptor is absent and step 1 (catalog entries for live command handlers) is undone.
With 11 catalog entries lacking handlers and 233 distinct live POST routes lacking catalog entries,
the assertion cannot be green. Fixing it needs either ~233 new catalog entries — owned by swarm-1's
AUTH-WIRE-01 step 1 and forcing OpenAPI/client regeneration, which is outside this story — or ~233
reasoned allow-list entries, which breaks the "short allow-list; unexplained entry is a defect" rule.
No skip, suppression or weakened gate was added to hide this.

Next step: finish AUTH-WIRE-01, then replace the helper's hand-supplied route set with the set from
`RequestMappingHandlerMapping` in a `@SpringBootTest(webEnvironment = MOCK)` and assert
`report.passed()`. The reusable `CommandRouteParityCheck` and its 13 tests are ready for that wiring.
