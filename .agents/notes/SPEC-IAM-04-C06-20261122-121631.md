# SPEC-IAM-04-C06 — Lock both records during commit (API test)

## Summary

Adds a synthetic-data API/SQL integration test that proves IAM-04 clause 6 —
`Lock both records during commit` — against the existing implementation, plus the
clause evidence document. No production code, existing test, contract or
migration was changed. The clause is already built, so no test is `@Disabled`.

Discovery (step 1 of the task) found the clause implemented here:

- `apps/api/src/main/java/com/aurevia/patient/consolidation/ConsolidationService.java`
  — `consolidate(...)` and `correct(...)` call `repository.lockPair(survivorId, duplicateId)`
  and refuse with 409 `both patient records must be locked` unless both rows are
  locked; the pair is locked before versions are read and the association, event
  and audit are appended in one tenant-guarded transaction.
- `.../consolidation/DuplicateRepository.java` — `lockPair(...)`, the SQL boundary.
- `db/migrations/V9__duplicate_review_consolidation.sql` —
  `public.lock_patient_pair(uuid, uuid)`: ordered advisory lock plus
  `SELECT ... FOR UPDATE` on both `patient_record` rows, `SECURITY DEFINER`,
  forced RLS, execute granted only to `aurevia_app`.
- `.../consolidation/ConsolidationController.java` —
  `POST /api/v1/duplicate-reviews/{reviewId}/consolidate` (and `/correct`).
- Contract entry: the duplicate-review routes are documented in `contracts/openapi.yaml`.
- Neighbouring suites reused for style/fixtures:
  `apps/api/src/test/java/com/aurevia/it/patientidentity/ConsolidationIsolationTest.java`
  and `.../authz/clauses/WriteChecksCurrentScopeTest.java`.

## Test evidence

New test class:
`apps/api/src/test/java/com/aurevia/patient/clauses/LockRecordsDuringCommitTest.java`
(`@Tag("integration")`, `RANDOM_PORT`, `synthetic-auth`, isolated database
`aurevia_patient_lock_it`, Flyway from `filesystem:../../db/migrations`,
synthetic users `reviewer-a`/`approver-a`/`reception-a`, two synthetic duplicate
patients per test). Five tests, named after behavior:

1. `pairLockHoldsExclusiveRowLocksOnBothRecordsUntilTransactionEnds` —
   `lock_patient_pair` returns 2; a second transaction gets SQLSTATE 55P03 on
   `FOR UPDATE NOWAIT` for each row while the first is open; both rows are
   lockable after rollback.
2. `consolidationCommitsBothAppendsAtomicallyUnderThePairLock` —
   `POST /api/v1/duplicate-reviews/{id}/consolidate` returns 200; one association
   and one consolidation are appended and chart visibility moves to the survivor.
3. `consolidationRefusesToCommitWhenThePairLockCannotClaimTwoRecords` — a
   malformed review naming one patient as both sides (seeded directly, because
   `open` rejects it) returns 409 `both patient records must be locked` and
   appends nothing.
4. `pairLockReportsOneLockedRecordForAMissingPatient` — SQL pair lock returns 1
   when one id does not exist, so it cannot satisfy the two-record precondition.
5. `staleVersionIsRefusedBeforeTheLockedCommitAppendsAnything` — stale `If-Match`
   returns 412 and appends nothing.

## Lessons for workers

- `scripts/check.sh` calls `apps/api/check.sh`, which runs every integration
  suite plus JaCoCo and takes over ten minutes. For a single clause test, run
  `mvn -q -B -f apps/api/pom.xml -Pno-security -Dtest=<Class> test` and the
  individual policy steps of `check.sh`; leave the full gate to the integrator.
- `FOR UPDATE NOWAIT` fails deterministically with SQLSTATE 55P03, so a lock
  proof needs no `sleep`, thread race or timing assertion — hold the lock on a
  second JDBC connection and assert the state code.
- A malformed review that the public command rejects (survivor == duplicate)
  can be seeded directly with SQL to exercise the `lockPair != 2` guard
  deterministically; it is refused with 409 instead of merging a chart into
  itself. This is a stronger, in-scope negative than a timing-based race test.
