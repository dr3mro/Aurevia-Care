## Lessons for workers

- When writing a clause evidence note under `docs/spec/clauses/product/`, the repo root is four `../` levels up; verify every relative link with a small regex script before running `python3 -I scripts/check-docs.py`, because the gate only reports the first-level symptom ("broken link") and a wrong depth is easy to introduce.
- Do not stop at the feature screens: read the page container (`patientPages.tsx`) and navigator (`RootNavigator.tsx`) too — the placeholder command wiring that decides whether a clause is truly built is documented there, not in the screens' tests.
- `check-docs.py` derives allowed requirement IDs from the spec's table rows and `**ID ·` bold leads only; IDs written as `- **PAT-01** …` are not recognized. Avoid unrecognized IDs in notes until a maintainer widens the detector.
- For evidence notes, distinguish "code exists and is unit-tested" from "entry point reaches it end to end" and from "human/partner/G5 evidence is held". The clause note must say who supplies the latter; a passing Jest/mvn run never substitutes for it.
