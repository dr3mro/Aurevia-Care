# BUILD-62 — Gate G2 acceptance tests

## Summary

Added four synthetic acceptance/integration test classes under
`apps/api/src/test/java/com/aurevia/acceptance/exchange` covering every
G2 acceptance scenario in PROJECT_V1_SPEC.md section 9. Each test drives the
real domain service (SpecimenRejectionService, ResultRoutingService,
CriticalResultService) with mocked persistence boundaries and a fixed clock, so
the assertions exercise production logic through its normal entry points. No
production code was added or changed. All data is synthetic (invented UUIDs,
subject keys, accession numbers and notes); no patient data or credential is
used.

## Affected requirements

XCH-04, XCH-05, LAB-01, G2 (and LAB-02 / XCH-06 where the scenario depends on
revision/version binding). XCH-06 is not independently proven here: patient
release is asserted only as "does not acknowledge a critical result" (XCH-05);
release authorization/hold behaviour is covered by its own slice's tests.

## Risk class

Safety-critical (G2 critical-result escalation and result reconciliation). This
change is test-only, so it changes no runtime behaviour; the tests add negative
and failure-path assertions for the safety-critical flows.

## Review owner

Senior Java and Spring Boot; Test Engineer; Laboratory User (simulated); QA
reviewer for evidence. No clinical or human pilot feedback is represented —
these are synthetic acceptance tests only.

## Data changes

None. No migration, no reserved version used, no Flyway/DDL touched.

## Findings

- The four G2 scenarios are fully implementable with existing production code;
  no missing behaviour was found for LAB-01, XCH-04 or XCH-05.
- `CriticalActions.RELEASE` requires the `tenant_admin` role. The first draft of
  the critical-result test used only `lab_verifier` + `clinician` and failed at
  the release step; the synthetic actor now carries all three roles so the test
  can show that a patient release never satisfies clinical acknowledgment.
- XCH-06 is exercised only indirectly (release is a fact that does not
  acknowledge). Its authorization/hold/withdraw behaviour is not re-proven here.
- Pre-existing, unrelated worker artifact: `check-pack.py`/`gen-opencode.py
  --check` report a stale `opencode.json` in this worker's worktree because the
  file is skip-worktree and holds the CI profile. HEAD is documented green in
  MEMORY.md; no protected file was modified.

## Lessons for workers

- When a service's action matrix separates roles (e.g. `CriticalActions.RELEASE`
  is `tenant_admin`-only), give the synthetic test actor every role the scenario
  needs or the first run fails with a misleading "missing permission" error.
- In this worker image `opencode.json` is skip-worktree with the CI profile, so
  `scripts/check.sh`/`quick-check.sh` can fail at `check-pack` for reasons
  unrelated to the change. Verify with `git ls-files -v opencode.json` and
  `git status`, run the remaining gates individually, and never edit the
  protected file.
- Follow the existing `acceptance/` convention: real domain service + mocked
  repository + fixed clock + synthetic fixtures, with the requirement IDs written
  both in the class Javadoc and inline on each test method.
