# Agent swarm

Up to 10 OpenCode workers run in parallel on GitHub-hosted runners. An orchestrator splits tasks from [TODO.md](../TODO.md), each worker commits to its own branch, and an integrator merges only what passes the full check. A failed run on `main` becomes a repair task in `TODO.md`, planned before everything else. One scheduler (`swarm.yml`) plans, works, integrates and starts the next wave inside a single run; waves may overlap up to 20 workers. Everything is event driven, so nothing runs while there is no work.

## Flow

| Step | Workflow | What happens |
|---|---|---|
| 1. Split | `swarm.yml` (plan) | Reads TODO.md. Picks `[ ]` tasks that have a `scope`, whose `depends` are all `[x]` and whose scopes do not overlap each other, `[-]` tasks or open swarm PRs. Marks up to 10 picked tasks `[-]` with `agent: swarm-<slot>` in one commit to `main`, and frees stale claims first: a `[-]` swarm task with no open PR, or with a PR labelled `needs-human`, goes back to `[ ]` (or to `[x]` if a person merged its PR). Repairs and fix requests go first. One task per slot. |
| 2. Work | `swarm.yml` (worker) | Starts the slot's prepared image, checks out the repository, runs the agent on branch `swarm/<ID>-<run>` with a cooperative 175-minute deadline (185-minute job cap, 10 minutes for bundling), runs the fast gate `scripts/quick-check.sh`, packs the commits and exits. The container is discarded and the `next` job starts a fresh wave. A failed or PR-less worker releases its claim back to `[ ]`; the trusted publish job does this because workers hold no token. |
| 3. Publish | `swarm.yml` (publish) | A separate trusted job pushes the branch and opens the pull request. The worker never holds a GitHub token. |
| 4. Integrate | `swarm-integrator.yml` (called by `swarm.yml` after the workers) | One job for the whole ready batch: merges each PR into local `main` one at a time, runs the full gate `scripts/check.sh` after each (with a PostgreSQL service, JaCoCo, OWASP and cached NVD), then commits and pushes once. A PR over 15 changed files is labelled `needs-human` to be split into one story per PR. No model is used. |
| 6. Return | `swarm-integrator.yml` | On a conflict or failing full gate the PR gets `needs-fix` with the log tail and goes back to the pool; its merge is rolled back so the rest of the batch proceeds. After 3 attempts it gets `needs-human`, and the planner returns the claim to `[ ]`. |
| 7. Repair | `swarm.yml` (plan job), `fix-pr-gate.yml` | A failed run on `main` is appended to `TODO.md` as `FIX-<run>` (scope `*`, so nothing else runs meanwhile) by `swarm.py add-repair-task --latest` at the start of every plan (at worst the hourly schedule), with no separate watchdog run: one open repair at a time, three per day, then an issue. `fix-pr-gate.yml`: only an open `FIX-` PR labeled `autofix` triggers this workflow, on `pull_request` events (`opened`, `synchronize`, `reopened`, `labeled`). It runs the full gate and dispatches the integrator when green, or `swarm.py fail()` when red. There is no failed-run trigger and no cron: a repair exists only when a fix PR is available. |
| 8. Continue | `swarm.yml` (loop) | After the integrator of a wave, the next wave starts (never while one is already waiting) if `TODO.md` still has ready `[ ]` tasks. An hourly schedule restarts the loop if it stalls. It stops when nothing is left to do. |

**Continuous loop.** Start it once (run **Agent swarm**, or push a change to `TODO.md`). It then repeats wave, publish, integrate, next wave until every task is `[x]`. A task a worker has taken 3 times without finishing keeps `attempts: 3` in `TODO.md` and waits for a person, and the monthly minute cap in `budget-gate` (10000 minutes, about five full 10-worker waves) still applies, so the loop cannot run away.

**Repair gate.** While main is red the full gate fails every pull request on classes other repair tasks still have to fix, so repairs (`FIX-` and `DLV-` PRs) merge through `scripts/repair-gate.sh` instead: the quick gate, the PostgreSQL integration tier judged by `scripts/worker_gate.py` on the classes the task names (PostgreSQL is mandatory there), `db/check.sh` and the developer reference. OWASP, SpotBugs and JaCoCo run in Delivery right after the merge; a red result becomes the next repair task. Ordinary PRs keep the full gate.

**Two-tier checks.** The worker runs `scripts/worker-check.sh` (the quick gate plus the PostgreSQL integration suites and `db/check.sh`; the agent image carries PostgreSQL 17 and `start-postgres` starts it; `scripts/worker_gate.py` only fails an ordinary task on integration suites related to its change, so red suites already on `main` do not turn every PR into a draft, while `FIX-` and `DLV-` repair tasks are strict) for fast feedback, and the trusted integrator runs the full `scripts/check.sh` on each merge result with a PostgreSQL service and cached NVD data, so SpotBugs, OWASP, JaCoCo and DB policy failures cannot reach `main`. Delivery re-verifies the merged commit on main. The expensive checks run once per batch, not once per worker.

**Batching.** The integrator sets up Java/Maven once, merges every ready PR in one job, pushes once, and Delivery verifies the pushed commit on main. Publish is one job for all slots rather than a matrix; the worker keeps no GitHub token and only the trusted publish job holds one.

## Prepared images

`agent-image.yml` builds a base image once (OpenCode V2 CLI, Git, gh, JDK 21, Maven, the project's Maven dependencies). `swarm-images.yml` adds one small layer per slot, `ghcr.io/<owner>/<repo>-agent-<n>`, that bakes that slot's OpenCode model and config from `.github/swarm/slots.json`. Each slot uses its own free account through the secret `OPENCODE_API_KEY_<n>`. Credentials are never baked into an image. Edit `slots.json` to give a slot a different model or extra OpenCode settings, and the image rebuilds.

**Reusable build, never per-task.** Images are built only when their own inputs change (the agent Dockerfile, `slots.json` or the image workflows), on the monthly refresh, or by manual dispatch. `swarm.yml` contains no build step: a worker only pulls its slot's `:latest` image, so running N tasks does not rebuild anything. Because a slot image layers on the base `:latest` tag, `swarm.yml` checks image health before planning a wave: while `agent-image` or `swarm-images` is running, or the last slot build is not green, it starts no workers (avoiding a stale-image race such as a V1 CLI after the base moved to V2). A successful `Swarm slot images` run re-triggers `swarm.yml`, so a wave skipped during a rebuild still picks up its task. To verify a CLI change reached workers, rebuild the base image, wait for slot images, then start a wave.

## Setup

1. Push the branch, merge it, then run **Agent image** once. **Swarm slot images** follows automatically.
2. For each slot you use, save the repository secret `OPENCODE_API_KEY_<n>` from that slot's own OpenCode account. If a slot-specific secret is absent, the worker falls back to `OPENCODE_API_KEY`; if neither secret exists, the task goes back to `[ ]`.
3. Settings, Actions, General: allow Actions to create pull requests.
4. `main` must allow the orchestrator and the integrator to push (the orchestrator pushes the `[-]` marks in TODO.md). Either exempt the integrator from the branch rule, or save a fine-grained token with contents, pull requests and actions write as the secret `SWARM_TOKEN`. A `SWARM_TOKEN` also lets pull requests and merges trigger the Delivery workflow and the next wave.
5. Edit TODO.md and push to `main`, or run **Agent swarm** manually.

## Rules the swarm enforces

- Workers follow AGENTS.md, CODING_STYLE.md, the specification and the `.opencode` specialists, stay inside their `Scope`, and use only their `Reserved` migration version.
- Workers do not edit shared trackers. The orchestrator marks a task `[-]` when it starts a worker, and the integrator marks it `[x]` with `pr:` and `evidence:` and writes `docs/swarm/<ID>.md` after each merge, one at a time, so TODO.md never conflicts. A worker that fails or publishes nothing releases its claim back to `[ ]` in the trusted publish job; the planner also frees claims whose PR is closed, unmerged or labelled `needs-human`.
- Repair pull requests (`FIX-`, label `autofix`) are merged by the integrator like other swarm work, including changes to `.opencode/`, `scripts/` and the other protected files, as long as the full gate passes. `.github/workflows/*` is the exception: the App token cannot push it, so such a worker bundle is blocked by `publish()`. Ordinary story pull requests touching protected files still wait for a person.
- A story pull request that changes `.github/`, `.opencode/`, `scripts/`, `opencode.json`, AGENTS.md, Dockerfile, compose or any `check.sh` is never merged automatically. It is labeled `needs-human`. Repair pull requests (`FIX-`, label `autofix`) are the exception: the integrator merges them after the full gate even when they change those files, except `.github/workflows/*`, which the App token cannot push. All merges still require the full gate, and shared trackers stay integrator-only.
- One worker per task, up to ten tasks per wave. A pull request touching more than 15 files is labelled `needs-human` and must be split into smaller stories before it can merge.
- GitHub Actions has no `workflows` permissions scope; the `GITHUB_TOKEN` (a GitHub App token) cannot push `.github/workflows/*`. `publish()` detects workflow-file changes in a worker bundle, releases the claim and skips the push instead of crashing the remaining slots. With `SWARM_TOKEN` configured (with workflow scope), the publish job sets `SWARM_WORKFLOW_PUSH` and workflow-file changes are pushed normally; without it, the change is blocked and released. Ordinary story PRs touching those files still get `needs-human` from `guard()`.
- The integrator merges exactly the commit it tested and refuses if the branch moved; it re-runs the full gate on the merge result.
- A rate limit, timeout or failure ends that worker. There are no retries inside a run.
- Use synthetic data only. Free models are not suitable for real patient data. Check each provider's terms before running several free accounts.

## Not verified yet

Written and unit tested (scripts/tests) but never run on GitHub: the image builds, the container jobs, per-slot secrets, OpenCode reading the baked slot config and auth file, pushing to protected `main`, and the integrator check timing. Start the first wave with `workers=1` (a manual dispatch input); waves default to 10 workers, and each worker publishes its own pull request when it finishes.

**Budget gate.** `swarm.py budget-gate` pauses waves near an estimated monthly runner-minute cap (default 10000). It is off for public repositories, where standard GitHub-hosted runners are free; it was pausing a free swarm. The plan job has `issues: write`, so a pause opens an issue instead of failing silently.
