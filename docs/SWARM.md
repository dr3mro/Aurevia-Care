# Agent swarm

OpenCode story workers run in waves on GitHub-hosted runners; `SWARM_MAX_WORKERS_PER_WAVE` sets the per-wave cap (default all 20, hard ceiling 20) and `SWARM_MAX_WAVE_COUNT` sets how many waves may run at once (default 3, clamped 1..20). The global ledger still caps workers at 20. An orchestrator splits tasks from the [task files](../tasks/), each worker commits to its own branch, and an integrator merges only what passes the full check. A failed run on `main` becomes a repair task in `tasks/`, planned before everything else. One scheduler (`swarm.yml`) plans, works, integrates and starts the next wave inside a single run; waves are admitted by the trusted wave-count gate and each wave offers at most the configured number of story workers. The dispatch order is red-`main` repairs, PR fixes and debugger work, verified PR merges, backlog tasks, then optional scheduled daily agents. PR fixes take worker slots first. A ready merge is handed to the serialized integrator before backlog dispatch, and spare workers can run eligible tasks while it merges. The configured wave can fill up to twenty worker slots using the ten configured accounts twice. Capacity refills as workers finish and remains subject to budget, image readiness, dependencies and scope locks. While the latest definitive Delivery result on `main` is a failure, only automatic `FIX-<run>` and designated `DLV-` repairs get new worker, debugger, or integration slots. Cancelled and skipped runs leave the last verdict in place, even when they fill the recent-run listing. A failed Delivery is the sole candidate for creating a new automatic repair until Delivery passes. A queued or open repair for a known non-Delivery workflow waits and does not block the Delivery repair. Ordinary taken scopes do not block a repair, but incomplete tasks always reserve their scope, including against repairs and force overrides. Already-running workers can finish. Ordinary scheduling resumes when Delivery is green. A worker that ends starts the next wave at once when there is room, so a free slot is not idle until the slowest worker of its wave finishes. Everything is event driven, so nothing runs while there is no work.

## Flow

| Step | Workflow | What happens |
|---|---|---|
| 1. Plan | `swarm.yml` (plan) | Reads `tasks/`. Picks `[ ]` tasks that have a `scope`, whose `depends` are all `[x]`, whose `attempts` are below 5 and whose scopes do not overlap each other, `[-]` tasks, `[!]` incomplete tasks or open swarm PRs. Repairs and fix requests go first. Marks up to the effective per-wave cap of picked tasks `[-]` with `agent: swarm-<slot>` in one commit to `main` (one worker by default; up to 20 when `SWARM_MAX_TASK=true`), and frees stale claims first: a `[-]` swarm task with no open PR, or with a PR labelled `needs-human`, goes back to `[ ]` for another attempt (or to `[x]` if a person merged its PR). It comments "received" on the task's issue, if it has one. |
| 2. Work | `swarm-worker.yml` (work) | Starts the slot's prepared image with no write token. Reads the earlier findings about the task from its issues (read-only token, before the agent runs). Runs the agent on `swarm/<ID>-<run>` in up to four segments (45, 45, 45 and 40 minutes); between segments it merges `main` into the branch. Then `scripts/worker-check.sh`, then `scripts/coverage-check.sh` for the areas the task touched: a coverage failure goes back to the agent with the report, at most twice. A last merge with `main` lets the agent fix conflicts, up to 5 attempts. The commits are bundled and the container is discarded (300-minute job cap). |
| 3. Validate and publish | `swarm-worker.yml` (validate, publish) | A tokenless validation job gates the candidate bundle, then a trusted job on a fresh runner, one per worker, pushes only the validated commit and opens the pull request with the worker's notes as its body; a worker that did not finish gets a draft with "Why it failed" and the end of its check log. It writes the hand-off: an issue that the next worker reads, or for an `ISS-<n>` task a comment on issue #n with the worker's findings. A failed or PR-less worker releases a still-taken claim back to `[ ]` for another attempt; incomplete tasks are never automatically reopened. When work is held without a retry, the orchestrator marks it `[!]` with the reason and next action in `details:`. |
| 4. Integrate | `swarm-integrator.yml` (called by `swarm.yml` after the workers) | A tokenless validate job merges each PR into local `main` one at a time and runs `scripts/integrator-gate.sh` (the full `scripts/check.sh` with PostgreSQL, JaCoCo, OWASP and cached NVD, plus the developer reference) after each ordinary PR — repairs use `scripts/repair-gate.sh` instead. A trusted publish job on a fresh runner re-checks the exact validated bundle and PR heads, then commits and pushes once. No model is used. An `ISS-<n>` task's issue closes when its PR merges. |
| 5. Resolve | `swarm-integrator.yml` (resolve) | A PR that conflicts with `main` goes to an agent that merges `main` into the branch and fixes the conflicts (no token; a trusted job pushes the result), up to 5 times per PR. |
| 6. Return | `swarm-integrator.yml` | A failing gate labels the PR `needs-fix` with the log tail and its merge is rolled back so the rest of the batch proceeds; a fix worker takes it in the next wave. It goes to the [debugger](#debugger) (`needs-debug`) first, not to a blind fix; a person is asked only after three rounds of debugger and fix. A PR over 50 changed files gets `needs-human`; so does a story PR that changes protected files, and its issue is labelled `needs-review` (a person approves it; no worker is sent) — unless the [`SWARM_ALLOW_PROTECTED` kill switch](#kill-switch) is on, in which case it merges after the full gate and opens a `protected-change` oversight issue instead. Each of those opens an issue with the cause. |
| 7. Repair | `swarm.yml` (plan job), `fix-pr-gate.yml` | A failed run on `main` is appended to `tasks/` as `FIX-<run>` (scope `*`, so nothing else runs meanwhile) by `swarm.py add-repair-task --latest` at the start of every plan: one open repair at a time, three per day, then an issue. `fix-pr-gate.yml` runs only for a `FIX-` PR or one labelled `autofix`: one job runs the full gate on the PR's code with no write token, and a second job on a fresh runner, using the scripts from `main`, dispatches the integrator when green or calls `swarm.py fail()` when red. |
| 8. Continue | `swarm.yml` (loop) | After the integrator of a wave, the next wave starts (never while one is already waiting) if `tasks/` still has ready `[ ]` tasks. An hourly schedule (minute 7) restarts the loop if it stalls. It stops when nothing is left to do. |

**Continuous loop.** Start it once (run **Agent swarm**, or push a change to `tasks/`). It then repeats wave, publish, integrate, next wave while eligible `[ ]` tasks remain. `[!]` incomplete tasks stay visible but are not dispatched and do not satisfy dependencies. A task a worker has taken 5 times without finishing keeps `attempts: 5`; the daily issue monitor gives it one more round, at most twice, before it waits for a person. The monthly minute cap in `budget-gate` still applies to private repositories.

**Merge conflicts.** Fix workers and the integrator resolver use the [merge conflict skill](../.opencode/skills/aurevia-merge-conflict/SKILL.md). The runner reads it from the fetched base so older branches can resolve incoming changes without already containing the skill.

**Repair gate.** While main is red the full gate fails every pull request on classes other repair tasks still have to fix, so repairs (`FIX-` and `DLV-` PRs) merge through `scripts/repair-gate.sh` instead: the quick gate, the PostgreSQL integration tier judged by `scripts/worker_gate.py` on the classes the task names (PostgreSQL is mandatory there), `db/check.sh` and the developer reference. OWASP, SpotBugs and JaCoCo run in Delivery right after the merge; a red result becomes the next repair task. Ordinary PRs keep the full gate.

**Worker preflight.** Before launching the first implementation segment, the work job checks Java wiring, installs each present frontend app from its lockfile with development dependencies, and runs its typecheck. Any failure stops the job at preflight.

**Wiring baseline.** The trusted integrator validates each merge candidate against
its first-parent baseline using the checker loaded from main. It rejects candidate
baseline edits or new findings. Resolved exemptions are removed in the merge
commit before the normal or repair gate runs. A failed check rolls back the
candidate and its baseline cleanup together.

Maintainers can refresh the wiring baseline from a stable checkout by running
`python3 -I scripts/check-wiring.py && python3 -I scripts/check-wiring.py --write-baseline`.
The first command rejects new wiring violations before the second rewrites the
file. Review the diff for removals, then verify with
`python3 -I scripts/check-wiring.py --fail-on-stale`.

**Three check stages.** The worker runs `scripts/worker-check.sh` (the quick gate plus the PostgreSQL integration suites and `db/check.sh`; the agent image carries PostgreSQL 17 and `start-postgres` starts it; `scripts/worker_gate.py` only fails an ordinary task on integration suites related to its change, so red suites already on `main` do not turn every PR into a draft, while `FIX-` and `DLV-` repair tasks are strict) for fast feedback. A tokenless validation job re-checks the candidate bundle in `swarm-worker.yml`. The trusted integrator then runs the full `scripts/integrator-gate.sh` (`scripts/check.sh` plus the developer reference) on each ordinary PR's merge result with a PostgreSQL service and cached NVD data, so SpotBugs, OWASP, JaCoCo and DB policy failures cannot reach `main`; its own publish job re-checks the exact bundle SHA before writing. Repairs use `scripts/repair-gate.sh` at merge time and Delivery runs OWASP, SpotBugs and JaCoCo on `main` right after the push (see **Repair gate** above). Delivery re-verifies the merged commit on main. The expensive checks run once per batch, not once per worker.

**Batching.** The integrator sets up Java/Maven once, merges every ready PR in one job, pushes once, and Delivery verifies the pushed commit on main. Each worker has its own publish job, so a PR opens as soon as its worker ends; the worker keeps no GitHub token and only the trusted publish job holds one. The validated manifest and bundle travel in a flat `validated-batch` artifact (only the `validated` directory); stacked-branch records travel separately in `stack-plan`, because upload-artifact nests paths under their common ancestor when more than one path is uploaded. The publish job checks for `validated/manifest.json` and `validated/main.bundle` before invoking `integrate-publish`, so a layout regression fails with a named error instead of a `FileNotFoundError`.

## Labels

The swarm drives its fix/debug/repair loops with GitHub labels. They are defined in `scripts/swarm.py` (`LABELS` and `ISSUE_LABELS`) and created by `ensure-labels`.

### Pull request labels

| Label | Applied when | What it triggers | Removed when |
|---|---|---|---|
| `swarm` | A swarm worker opens the PR | Marks it as swarm-owned; the integrator and PR flow only act on `swarm` PRs | PR merged/closed |
| `autofix` | A repair worker opens the `FIX-`/`DLV-` PR for a red main; the watchdog dispatches the wave | `fix-pr-gate.yml` runs the full gate on it; the integrator fast-tracks a green result | PR merged/closed |
| `needs-fix` | Integration failed (gate red, or conflict after retries) | A fix worker is dispatched with fresh attempts | Worker fixes and pushes |
| `needs-human` | Three fix attempts exhausted, or a protected/unknown cause | The swarm stops; a person must decide | A person intervenes |
| `needs-debug` | A failing fix needs root-cause analysis | `swarm-debugger.yml` runs a debugger agent | Debugger publishes its report and adds a `debug-N` label |
| `fix-1` / `fix-2` / `fix-3` | Each fix-worker attempt | Attempt counter; after `fix-3` the next failure goes to `needs-human` | Reset on re-dispatch |
| `debug-1` / `debug-2` / `debug-3` | Each debugger round | Round counter; after `debug-3` one more failure goes to `needs-human` | Reset on re-dispatch |

### Issue labels

| Label | Applied when | What it triggers | Removed when |
|---|---|---|---|
| `swarm-issue` | The swarm opens or updates an issue | Flags it for the issue monitor | Issue closed |
| `ci-failure` | A Delivery or scheduled workflow fails | The monitor classifies the cause; may open a repair task or `needs-human` | Issue closed |
| `stalled` | No wave is running while work waits | The watchdog starts a wave | A wave starts |
| `needs-review` | The PR works as designed but needs approval | A person approves/merges | Person approves |
| `worker-handoff` | A worker stopped mid-task | The next worker reads its notes and continues | Task done |
| `swarm-review` | The six-hourly review has suggestions | A person decides on task order/workflow changes | Person decides |
| `protected-change` | A protected file merged under `SWARM_ALLOW_PROTECTED` | Oversight audit trail only | Never (permanent record) |

### Typical flows

- **Red PR:** `needs-fix` + `fix-N` → fix worker → repeat; after 3 → `needs-human`, or `needs-debug` → `debug-N` → fix → repeat.
- **Red main:** watchdog dispatches a wave → plan creates a `FIX-<run>` task → repair worker opens an `autofix` `FIX-` PR → fix-pr-gate → green → integrator; red → back to workers.
- **Issues:** `ci-failure` / `worker-handoff` / `swarm-issue` → monitor triage → task or `needs-human`.

Task state itself uses marks in `tasks/*.md` (`[ ]` open, `[-]` taken, `[!]` incomplete, `[x]` done), not GitHub labels. `[!]` is not done or dispatchable, does not satisfy `depends`, and keeps its `scope:` reserved until explicitly reopened or completed; its `details:` records the reason and next action.

## Priority

PO selection and SM allocation read the same red-state repair evidence: an open `FIX-<run>`/`DLV-` task with an attached failing job, head SHA, run link and bounded log tail is listed in `tasks=` before backlog work, and the SM allocates it first within the wave cap. PO candidates and SM allocations stay agent output only; agents never create or claim tasks — the trusted repair step, watchdog and planner own that.

Each task may carry `priority: high|normal|low`. Without it a task is **high** when its title contains `(HIGH PRIORITY` and **low** when its id starts with `QAD-`, `DSO-` or `AUD-` (the daily QA, DevSecOps and audit findings); everything else is normal. Inside the backlog lane the task file breaks ties in high, normal and low priority. The PR fix and merge lanes are handled first. Low-priority backlog tasks use spare slots. Scheduled audit, QA, DevSecOps, notes and strategist agents wait for a later scheduled run if higher-priority work is ready or currently using all slots. `aurevia monitor` shows the queue in this order with `H` and `L` markers.

## Forcing a task

To start one task now, run **Agent swarm** by hand (Actions, Run workflow) and put its id in `task` (for example `FIX-INSTANT-OPENAPI`), or run `gh workflow run swarm.yml --ref main -f task=<ID>`. The `now=true` input is reserved and currently inert: a dispatch still queues behind the running wave for this branch. The plan job puts that task first and ignores its attempt limit and the "pull request waiting for a fix" gate, but cannot bypass the one-wave-per-branch group. It still refuses a task that is not open, has no scope, has unmet `depends`, or whose scope overlaps a running or incomplete task.

## Issues and hand-off

Every problem the swarm cannot solve in the moment becomes a GitHub issue, written only by trusted jobs (workers never hold a token). Each issue carries hidden markers (`swarm-fingerprint`, `swarm-task`, `swarm-pr`, `swarm-workflow`), so the same cause updates one issue instead of opening many. Only issues by the repository's own automation or by an owner, member or collaborator are read.

| Issue | Opened by | Label | Closed when |
|---|---|---|---|
| A workflow run failed | `swarm-watchdog.yml`, when Delivery, Agent swarm, the slot images, the daily audit, the issue monitor or the daily notes finish red (a transient runner error is retried once first) | `ci-failure` (plus `needs-human` for a credential or quota problem) | the next run of that workflow is green |
| A red `main` | `swarm-watchdog.yml`, when a Delivery run on `main` fails for a code reason | a repair task and a wave started at once, instead of waiting for the next plan or the watchdog | the next Delivery run is green |
| The swarm stalled | the watchdog every 15 minutes: it starts a wave itself once none has run for 30 minutes while work is waiting (the hourly schedule is often delayed or dropped); the issue opens only when no wave has appeared after 60 minutes | `stalled`, `needs-human` | waves run again |
| A worker stopped before finishing | the publish job, with the worker's own "Why this is not finished" and its check log | `worker-handoff`, `agent-fixable` | the task is done or its PR is merged or closed |
| A pull request will not merge by itself | the integrator: fix attempts used up, too many files, or protected files (the last only while the kill switch is off) | `needs-human` or `needs-review` | the PR is merged or closed |
| Protected files merged with the kill switch on | `guard()` / `report_protected_merge()` in `scripts/swarm.py`; one issue per PR revision | `protected-change` (non-blocking; no `needs-human`/`needs-review`) | the owner reads and closes the issue; see [Kill switch](#kill-switch) |
| A problem found in the day's notes | the daily notes job | `agent-fixable` | its `ISS-<n>` task merges |

A worker reads the open issues about its task (and for an `ISS-<n>` task, issue #n) before it starts, as untrusted notes, and continues from them. Set the repository variable `SWARM_ISSUES` to `off` to stop all issue writing and the issue monitor.

## Debugger

The first stop for a failing pull request, and the only one before a person: worker, debugger, fix, then again up to three times (labels `debug-1` to `debug-3` count the rounds). A pull request goes to `swarm-debugger.yml` (label `needs-debug`) when integration fails, or when a fix worker ends with `failed` and pushes nothing. The workflow starts at once and again hourly as a safety net, and takes the oldest waiting pull request, one at a time.

1. **Debug** (agent, no GitHub token, up to 130 minutes; up to four pull requests at once, the oldest first, each on its own slot 3, 6, 7 or 8 so a queue of failures does not wait for one debugger at a time). The branch is merged with `main`, then the agent works on the whole project: it reads the whole history of the pull request, oldest step first (the first worker's notes, every integrator failure with its log, every earlier debugger report and what each fix worker did; the newest steps whole, older ones shortened to fit), plus earlier findings on the task's issues, runs every test suite fastest first, runs each failing test again on a clean worktree of `main` to separate the branch's bug from failures already there, and finds the root cause. It does not change the repository. It writes `.agent/debug-report.md` with `Root cause found: yes|no`, the failing commands, the root cause with file and line, a numbered fix plan, the failures that were already there and what it ruled out.
2. **Send it on** (trusted job). A report with `Root cause found: yes` and a Fix plan is posted on the pull request, which gets `debug-<round>` and `needs-fix`, and a wave starts. From round 2 the debugger is told that the earlier fix did not work. The fix worker reads the report from the pull request comments.
3. **A person, last.** If the debugger found no cause, wrote no report twice in the same round (a run with no report at all is retried once first, since that is a runner or model failure and not a finding), or the fix after round 3 fails integration, the pull request gets `needs-human` and an issue explains why. The daily issue monitor can give a stuck one fresh rounds.

## Issue monitor

`swarm-issue-monitor.yml` hands open `agent-fixable` issues to workers.

- **Hourly** (minute 37): issues open for more than an hour that no worker was ever assigned.
- **Daily at 2:00 AM New York time** (06:00 UTC in summer, 07:00 UTC in winter; each cron runs only in its own season): issues with no activity for 24 hours.

For each issue (at most 3 per run): an issue with no task goes to a read-only **triage worker**, which writes a title, a scope and a plan. A trusted job validates them like audit findings (bounded text, safe relative scope, never workflow, script or agent files) and adds task `ISS-<n>` as a file in `tasks/` (at most 5 open). An issue whose PR is a draft or labelled `needs-fix`/`needs-human` sends that PR back to the fix workers with fresh attempts; a healthy PR waiting for the integrator is left alone. An issue whose task is waiting gets a wave; a task with its attempts used up gets one more round (daily only). An issue whose task is done or whose PR merged is closed. Every action is a comment on the issue. After two such requeues, or when triage cannot find a safe scope, the issue gets `needs-human`. Label your own issue `swarm-issue` and `agent-fixable` to hand it to the swarm.

## Daily notes and audit

- **Daily notes** (`daily-notes.yml`, 05:10 UTC, after midnight in New York all year): a read-only worker reconciles the notes of each finished day under `.agents/notes/` into one file, `.agents/reports/<YYYY-MM-DD>.md` (summary, completed work, findings, open problems, lessons for workers). The originals go into `.agents/notes/archive/<YYYY-MM-DD>.zip` and are removed; only the newest daily file stays in `.agents/notes/`, older ones move to the archive, and notes that arrive late are appended to their day. A notes file that another document names (a task's "read first", a decision record) stays where it is. One night reads at most about 100 KB of notes; the rest follow the next night as late notes. When the worker produces nothing usable, the job fails and the watchdog opens an issue, and the originals wait for the next run. Up to 3 new problems become `agent-fixable` issues. Edits the worker proposes to `AGENTS.md`, `.opencode/*.md` or `docs/*.md` go out as a draft pull request `notes/rules-<day>` labelled `needs-review`, after the docs check passes; a person merges it. Set `SWARM_NOTES` to `off` to stop it.
- **Strategist** (`swarm-strategist.yml`, every six hours at :23): a read-only worker (slot 4) reviews the code base, the task files and the state of the swarm (open pull requests, recent runs) and writes at most 5 new tasks, task-order changes and workflow optimizations. A trusted job adds the valid new tasks like audit findings (same checks and the same cap of 25 open `AUD-` tasks) and opens or updates one `swarm-review` issue with the order and workflow suggestions. Those are suggestions only: nothing about order or workflows is applied automatically.
- **PR flow** (`swarm-pr-flow.yml`, when a Delivery run finishes and every 20 minutes): trusted code, no LLM, so it is fast. For every open swarm pull request it does the next step at once instead of waiting for the next integration run or the hourly wave: a failed Delivery goes to the debugger, a draft nobody took goes to a fix worker (and a wave starts), missing Delivery evidence waits for or re-runs an exact pull-request run, an approval-stuck Delivery waits, a passed Delivery wakes the integrator now, a due debugger or fix wave is started if none is queued or running, and a pull request green for 90 minutes that has not merged opens one issue for a person. For failed Delivery, the router fetches the failed-job log for the exact tested head. It attaches the SHA, run link, tool and bounded identifiers to the PR history read by the next worker. Straightforward test or compile failures enter one shared fix wave per pass, subject to existing capacity and retry limits. Ambiguous or repeated failures go through the debugger. While main is red this flow acts only on repair pull requests.
- **Issue flow** (`swarm-issue-monitor.yml`, mode `now`): a new, reopened or labeled issue, and every 10 minutes after that, hands an issue no worker has had to triage or a fix worker once it is five minutes old (it used to wait an hour). Issues the watchdog opens do not fire the issue event, which is why the 10-minute schedule exists.
- **Daily QA review** (`daily-qa.yml`, 08:43 UTC, slot 3) and **Daily DevSecOps review** (`daily-devsecops.yml`, 09:29 UTC, slot 5): a read-only agent (the QA reviewer, or the DevSecOps engineer) reviews the repository with a focus that rotates by weekday (QA: requirement traceability, failure paths, contracts, user journeys, test-suite health, data; DevSecOps: supply chain, workflow security, containers and infrastructure, secrets and PHI, runtime configuration, operability) and writes one JSON file: at most 5 tasks, 5 suggestions for agents, skills and prompts, and 10 workflow suggestions. A trusted job (`swarm.py daily-publish`) adds the valid tasks like audit findings (same checks, ids `QAD-<date>-NN` and `DSO-<date>-NN`, and a cap of 25 open tasks per role) and opens or updates one issue per role with the suggestions. Nothing about agents or workflows is applied automatically; a person decides. Run one by hand with *Run workflow* and a focus.
- **Daily audit** (`daily-audit.yml`, 07:17 UTC): a read-only worker audits the repository with a focus that rotates by weekday (security, tests and coverage, spec drift, production readiness, frontends, code health, a broad sweep) and writes at most 10 findings. A trusted job adds the valid ones as `AUD-` tasks under `## Audit findings`, and adds none while 25 audit tasks are still open. Run it by hand with a `focus` to audit something specific.

Agent text that lands on `main` (tasks/ entries, the daily note) is passed through the same link, requirement-ID and secret checks Delivery runs, so it cannot turn `main` red.

## Two independent verification gates

Two native GitHub checks guard a protected merge, and they answer different questions:

- **`Delivery gate`** (`.github/workflows/delivery.yml`) verifies the *code*: policy, script tests, frontend, Java/database and docs must all succeed. `scripts/check-delivery-gate.py` fails closed on a missing, failed, cancelled or unjustifiably skipped job. The workflow has no path filters on any trigger, so a documentation-only PR or push still reports the check. It is already required by the `PROTECT` ruleset. The integrator accepts only `pull_request` runs for the exact head SHA; it never dispatches Delivery on a mutable PR branch, and missing/skipped evidence has no documentation-only exception.
- **`Swarm gate`** (`.github/workflows/swarm-gate.yml`) verifies the *swarm contract*: PR classification (worker, integration, reconciliation, manual or malformed automation), task existence and eligibility, evidence schema, protected-file/workflow/coverage-config restrictions, tested-revision lineage, and integration-manifest ancestry. A worker note names one `Tested revision: <40-hex>`; the gate uses the read-only compare API to prove that commit is the merge base of the current head, so an ancestor or the head itself passes while a diverged, missing, malformed or cross-revision claim fails closed. Exact head currency is a separate `tested_revision` check against the live `headRefOid`. `scripts/swarm_gate.py` is pure and checked out from the protected base revision, so a worker PR cannot edit the verifier that judges it; worker notes are inspected for shape and revision claims, never treated as proof of a passing check. A newly taken task has no `evidence:` field on the base because `set_task_status()` writes it only when the integrator marks the task done; for a worker PR whose task is still `[ ]` or `[-]`, `task_evidence` is satisfied when the base task record has evidence **or** the newest worker note contains all required sections plus a canonical command, and the check reason names the source that satisfied it. Done tasks, reconciliation and integration keep the base-only rule. Ancestry is a metadata-consistency contract, not proof of what was tested: a note can be replayed in a later PR whose head still contains that commit.

**Trust model.** The gate workflow checks out the base revision for the verifier and a second checkout of the tested revision for the manifest only. It runs with `contents: read` and `pull-requests: read`; it never pushes or merges. Ancestry evidence comes from `gh api` in that read-only job with the repository pinned to `GITHUB_REPOSITORY`; the note supplies only a validated query token, and no code from the tested checkout is executed. Cross-repository heads, API errors and ambiguous revision fields fail closed. `revision_binding` is `not_applicable` to `merge_group` events, which keep their manifest and local ancestry proof. Manual pull requests get repository-wide checks and receive `not_applicable` for swarm-specific checks; a PR with an automation signal it cannot parse fails closed.

**Rollout.** Stage A ships the Swarm gate as a *non-required* check while `Delivery gate` stays required; the owner validates it on a docs-only PR, a code PR, a manual PR, an integration PR and a deliberately failing case. Stage B asks the owner to add `Swarm gate` to the `PROTECT` ruleset's required checks (keep `Delivery gate`), disable bypass for automation and keep force pushes off. Rollback is to remove `Swarm gate` from the required checks; the workflow can remain. This implementation does not change branch protection or grant any bypass.

## Prepared images

The worker image installs Debian's `python3-yaml` and checks the import with `python3 -I` during the build. The hosted Delivery tooling, fix-PR validation and integrator jobs use `.github/actions/setup-tooling-python` before running the same script tests. For local runs, `python3 -I -c 'import yaml'` verifies that PyYAML is available to the interpreter used by the gates.

### Direct model environment

Every production `opencode run` receives the exact model name from the required `SWARM_MODEL` environment variable through the single wrapper in `scripts/agent-run.sh`. The agent workflows export:

```yaml
SWARM_MODEL: ${{ vars.SWARM_MODEL || 'opencode-go/hy4-flash-free' }}
```

There is no secondary model variable, force flag, model registry, role/phase ranking or failover. A missing or empty `SWARM_MODEL` is a configuration error before OpenCode starts. A rate limit, timeout or implementation failure is terminal; the wrapper never invokes a second model.

Slot images carry only shared OpenCode settings. `.opencode/config/slots.json` must not contain a `model` key at any depth; `load_slots` rejects direct or nested model selection so the runtime environment remains the only model input.

Configure:


### Two independent gates

Two separate native checks report on every revision; neither substitutes for the other:

- **`Delivery gate`** (from `delivery.yml`) is the existing comprehensive CI verdict. It fails closed when any mandatory job is missing, failed, cancelled or unjustifiably skipped (`scripts/check-delivery-gate.py`). There are no path filters on any trigger, so a documentation-only PR or push still reports the check; branch protection never waits forever for a verdict that cannot be created.
- **`Swarm gate`** (from `swarm-gate.yml`) is the trusted swarm-contract verdict. It classifies each PR (worker, integration, reconciliation, ordinary human, or malformed automation), verifies the task exists and is eligible on the protected base, checks that evidence has the required shape, rejects worker edits to gates/workflows/coverage/trackers, and proves the note's tested revision is in the head ancestry through the trusted compare API while checking the live `headRefOid` separately. For merge groups it reads the integration manifest from the tested tree and proves each recorded worker head is an ancestor of that tree. Worker-authored notes are supporting metadata only: they cannot mark a check passed or not-applicable. The verifier runs from `scripts/swarm_gate.py` checked out at the protected base revision, so a worker PR cannot edit the code that judges it. Ordinary human PRs get applicable repository-wide policy checks with swarm-specific checks reported as not applicable; malformed automation fails closed. `SWARM_GATE_REQUIRED_CHECKS` (optional repository variable, comma-separated check names) adds objective GitHub check conclusions that must be `success` or `neutral` for worker PRs.

**Rollout.** `Swarm gate` is deployed first as a non-required check so its verdicts can be validated on worker, integration, reconciliation and ordinary PRs, plus a merge-group revision. Only after that validation should the repository owner add `Swarm gate` to the required status checks alongside — never instead of — `Delivery gate`. The gate workflow is read-only (`contents: read`, `pull-requests: read`) and never pushes or merges; GitHub remains the authority for protected merges.

`pr-rebase.yml` refreshes a new pull request onto `main` on open so its gate runs against the current base. That rebase rewrites commit SHAs, so a worker note's canonical `Tested revision:` no longer names an ancestor of the new head: after any rebase or rebuild, rebind that single line to the final head and observe a fresh Delivery verdict before the Swarm gate can prove ancestry. `dependabot-auto-merge.yml` merges low-risk dependency updates. `release-app-image.yml` publishes the tagged application image only when the tag points to a green default-branch commit; tags are restricted by the `PROTECT-TAGS` ruleset.

`agent-image.yml` builds a base image once (OpenCode V2 CLI, Git, gh, JDK 21, Maven, the project's Maven dependencies). `swarm-images.yml` adds one small layer per slot, `ghcr.io/<owner>/<repo>-agent-<n>`, that bakes only the shared OpenCode settings (and any extra slot config) from `.opencode/config/slots.json`; no model is baked into any slot image. Each slot uses its own free account through the secret `OPENCODE_API_KEY_<n>`. Credentials are never baked into an image. Edit `slots.json` to add or remove a slot or to change OpenCode settings and the slot images rebuild; the workflow supplies the model through `SWARM_MODEL` at run time.

**Reusable build, never per-task.** Images are built only when their own inputs change (the agent Dockerfile, `slots.json` or the image workflows), on the monthly refresh, or by manual dispatch. A change to `slots.json` — now slot entries and settings only, never a model — still rebuilds the slot images and is the signal that workers must pick up the new baked config. `swarm.yml` contains no build step: a worker only pulls its slot's `:latest` image, so running N tasks does not rebuild anything. Because a slot image layers on the base `:latest` tag, `swarm.yml` checks image health before planning a wave: while `agent-image` or `swarm-images` is running, or the last slot build is not green, it starts no workers (avoiding a stale-image race such as a V1 CLI after the base moved to V2). A successful `Swarm slot images` run re-triggers `swarm.yml`, so a wave skipped during a rebuild still picks up its task. To verify a CLI change reached workers, rebuild the base image, wait for slot images, then start a wave.

## Setup

1. Push the branch, merge it, then run **Agent image** once. **Swarm slot images** follows automatically.
2. For each slot you use, save the repository secret `OPENCODE_API_KEY_<n>` from that slot's own OpenCode account. If a slot-specific secret is absent, the worker falls back to `OPENCODE_API_KEY`; if neither secret exists, the task goes back to `[ ]`.
3. Settings, Actions, General: allow Actions to create pull requests.
4. `main` must allow the orchestrator and the integrator to push (the orchestrator pushes the `[-]` marks to `tasks/` files). Either exempt the integrator from the branch rule, or save a fine-grained token with contents, pull requests, actions and workflows write as the secret `SWARM_TOKEN`. A `SWARM_TOKEN` also lets pull requests and merges trigger the Delivery workflow and the next wave. Issues, comments and labels always use each job's built-in token (`GH_ISSUES_TOKEN`), and the issue monitor and daily notes jobs use only the built-in token, so `SWARM_TOKEN` needs no issues scope. When it expires, pushes fail and the watchdog opens a `needs-human` issue with the built-in token.
5. Optional repository variables: `SWARM_ISSUES=off` stops all issue writing and the issue monitor; `SWARM_NOTES=off` stops the daily notes job; `SWARM_ALLOW_PROTECTED=1` lets protected-file pull requests merge automatically after the full gate, with an oversight issue — see [Kill switch](#kill-switch). Boolean variables use canonical lowercase tokens: `1/true/yes/on` enable and `0/false/no/off` disable; case and padding are normalised, and any other value falls back to the documented default. The shared `swarm-flags.yml` job resolves the five workflow-gated booleans (`SWARM_ENABLED`, `SWARM_MAX_TASK`, `SWARM_LLM_SELECTION`, `SWARM_ISSUES`, `SWARM_NOTES`) and the two numeric caps (`SWARM_MAX_WORKERS_PER_WAVE`, `SWARM_MAX_WAVE_COUNT`) once with `scripts/swarm_flags.py`; workflows gate on its canonical outputs instead of comparing raw values, because GitHub expressions cannot trim or case-fold. Integers are clamped, padded digits are accepted, and non-integers fail closed to one worker or one wave. `SWARM_SINGLE_TASK` is retired and ignored. `SWARM_ALLOW_PROTECTED` stays a Python-only switch with the same token set. The Python commands read the same tokens and defaults, so a padded or mixed-case value cannot satisfy one side and bypass the other.
6. Edit a task file under `tasks/` and push to `main`, or run **Agent swarm** manually.

## Rules the swarm enforces

- Workers follow AGENTS.md, CODING_STYLE.md, the specification and the `.opencode` specialists, stay inside their `Scope`, and use only their `Reserved` migration version. `scope` is both the planner's collision map and a worker commitment under tasks/ rule 3: if a story's steps seem to need a file outside `scope` (for example a `web/` controller, an `it/` test or a regenerated client), stop and add a `task-requests` block to your notes instead of making an undocumented "transparent deviation"; parallel workers own those files.
- Workers do not edit shared trackers. The orchestrator marks a task `[-]` when it starts a worker, holds unfinished work as `[!]`, and the integrator marks it `[x]` with `pr:` and `evidence:` and writes `docs/swarm/<ID>.md` after each merge, one at a time, so task files never conflict. A worker that fails or publishes nothing releases a still-taken claim back to `[ ]` for another attempt in the trusted publish job; incomplete tasks are never automatically reopened. The planner also frees claims whose PR is closed, unmerged or labelled `needs-human`. Holding work without a retry uses `[!]`, with reason and next action in `details:`.
- Repair pull requests (`FIX-`/`DLV-`, label `autofix`) are merged by the integrator like other swarm work, including changes to `.opencode/`, `scripts/` and the other protected files, as long as the repair gate (`scripts/repair-gate.sh`) passes; Delivery re-runs the full checks after the merge. Gate-config files (the merge gate's own configuration) still stop a repair unless the kill switch is on. `.github/workflows/*` is the exception: the App token cannot push it, so such a worker bundle is blocked by `publish()`. Ordinary story pull requests touching protected files still wait for a person unless the kill switch is on.
- A story pull request that changes `.github/`, `.opencode/`, `scripts/`, `.opencode/opencode.json`, AGENTS.md, Dockerfile, `compose.yaml`, `apps/api/pom.xml`, a gate-config file or any `check.sh` (root or module) is never merged automatically. It is labeled `needs-human` and an issue labelled `needs-review` says why. Workers therefore put lessons for these files in their notes; the daily notes job proposes them as a reviewed pull request. The [`SWARM_ALLOW_PROTECTED` kill switch](#kill-switch) is the only exception for a story PR. Repair pull requests (`FIX-`/`DLV-`, label `autofix`) are the other exception: the integrator merges them after the repair gate even when they change those files (gate-config files still stop a repair unless the kill switch is on), except `.github/workflows/*`, which the App token cannot push. Every merge still passes its gate — the full `scripts/check.sh` for a story, `scripts/repair-gate.sh` for a repair — and Delivery re-verifies the pushed commit on `main`; shared trackers stay integrator-only.
- One worker per task, up to the configured story workers per wave (hard ceiling 20) and up to the configured concurrent waves. A pull request touching more than 50 files is labelled `needs-human` and must be split into smaller stories before it can merge.
- GitHub Actions has no `workflows` permissions scope; the `GITHUB_TOKEN` (a GitHub App token) cannot push `.github/workflows/*`. `publish()` detects workflow-file changes in a worker bundle, releases the claim and skips the push instead of crashing the remaining slots. With `SWARM_TOKEN` configured (with workflow scope), the publish job sets `SWARM_WORKFLOW_PUSH` and workflow-file changes are pushed normally; without it, the change is blocked and released. Ordinary story PRs touching those files still get `needs-human` from `guard()` unless the kill switch is on.
- The integrator merges exactly the commit it tested and refuses if the branch moved; it re-runs the applicable gate on the merge result (full `scripts/check.sh` for a story, `scripts/repair-gate.sh` for a repair).
- A rate limit, timeout or failure ends that worker. Inside a run the only retries are bounded: two coverage repairs, five conflict fixes when merging `main`. The next attempt comes from a later wave (5 per task), the fix workers (3 per PR) or the issue monitor (2 requeues per issue).
- Every agent step runs without a write token. Anything an agent produces (a branch bundle, findings, a triage plan, a reconciled note) is checked and published by a separate trusted job that runs the scripts from `main`.
- Use synthetic data only. Free models are not suitable for real patient data. Check each provider's terms before running several free accounts.

## Single-task lifecycle

When `SWARM_MAX_TASK=false` (the default), the swarm runs one task at a time:

1. `select` job: OpenCode with `aurevia-product-owner` picks one eligible task (LLM); falls back to deterministic planning if it produces nothing.
2. `plan` job: claims the task `[-]`, emits a one-worker matrix. LLM selection runs only when `SWARM_LLM_SELECTION` holds an enable token (`1/true/yes/on`); the canonical value is `true`. The `select` and `plan` jobs read the canonical flags from the `flags` job, so a padded enable token still reaches both the shell gate and the Python planner.
3. Worker: decomposes the task into ordered steps, runs `aurevia-plan-reviewer` before coding, implements step by step, then runs code-reviewer, coverage-auditor, devsecops and qa-reviewer, recording each `VERDICT: GO` under `## Review verdicts`.
4. Integrator merges; loop job waits for Delivery green on the merged SHA before planning the next task.
5. If the task is not done (taken or open PR), no next task is planned; the task stays active through debug/fix loops until green or `needs-human`.

## Kill switch

`SWARM_ENABLED` is a repository **variable** (not a secret) that pauses the swarm: when set to the canonical disable token `0`, `false`, `no` or `off`, the plan job exits with an empty matrix, `continue_swarm`, `top_up`, `pr_flow` and the issue monitor do nothing, and no new wave starts. Case and padding are normalised, so `False` pauses too. Workers that are already running finish and publish. Delete the variable or set it to `1`/`true`/`yes`/`on` to resume. It never weakens a gate.

`SWARM_MAX_TASK` is a repository **variable** (default `false`) that selects the wave mode. Off means one wave with one worker: no slot refill, and no next task while a task is taken or has an open pull request. On means the planner may use `SWARM_MAX_WORKERS_PER_WAVE` workers and up to `SWARM_MAX_WAVE_COUNT` concurrent waves, subject to the global 20-worker ledger. The wave count comes from one checked Actions API snapshot that excludes the calling run; an API or shape error emits `capacity_unavailable` and plans nothing. Branch state is never used to count waves.

`SWARM_MAX_WORKERS_PER_WAVE` defaults to all 20 workers when unset, is clamped to 1..20, and fails closed to 1 on an unparseable value. `SWARM_MAX_WAVE_COUNT` defaults to 3, is clamped to 1..20, and fails closed to 1. The operator's configured values are still bound by slots, budget, eligible tasks and the global ledger.

### Features, allocation and the work trail

A feature is a range of related tasks sharing a task-ID prefix, for example `SMSG-*` or `PRINT-*`. The `select` job runs the `product-owner` agent after reading the spec, task marks (`[x]` done, `[-]` taken, `[!]` incomplete, `[ ]` open), BUGS, decisions and targeted source under `apps/`, `db/` and `contracts/`; it emits up to two comma-separated feature prefixes, preferring different features, and candidate task ids from them. When only one feature has an eligible gap, it emits that one prefix with up to two tasks. The `allocate` job runs the `scrum-master` agent over the same evidence and picks at most the effective worker count of open tasks with disjoint `scope:` paths, preferring different feature prefixes and falling back to one task when no second eligible task exists. Both agents use the context-optimizer method: implemented, partial, planned and unknown work are separated before choosing. Their output is only a priority hint; the trusted planner re-checks dependencies, attempts, in-flight PRs, live claims and scope overlap before granting a claim. Only `[ ]` is eligible; `[!]` neither satisfies dependencies nor releases its scope.

Every stage appends its instruction and outputs to `.agent/work-trail.jsonl` inside the worker bundle: PO selection, SM allocation, the task-advisor brief, worker implementation, reviews and conflict resolution. Text is JSON-encoded and command markers are quoted before it reaches a log. The integrator reads the trail from each branch so it knows what every worker was told and produced.

### Integration into stacked pull requests

Workers publish scoped bundles, not pull requests. The integration workspace combines all bundles on top of `main`, resolves conflicts with the `aurevia-merge-conflict` skill and domain specialists, and runs the full gate on the combined tree. It then builds one stacked branch per worker, each based on the previous branch, and runs the full `integrator-gate.sh` on each branch SHA; the plan and gate results are published as artifacts. Any bundle that fails after integration is dropped with a fixed reason and requeued in a later wave. No force-push is used. Opening one pull request per stacked branch is **planned, not implemented**: the trusted publish path still merges the validated batch into `main` through the existing per-PR flow. This gap is recorded in task `01321000` and needs an owner decision before it is claimed as done.

`SWARM_ALLOW_PROTECTED` is a repository **variable** (not a secret) that lifts only the "never merge protected files automatically" rule in `scripts/swarm.py guard()`. Set it to `1` (also accepted: `true`, `yes`, `on`, case-insensitive) to turn it on; turn it off by deleting the variable or setting it to `0` (`false`, `no` or empty also work). An on/off change needs no code change or redeploy.

With the switch on, a pull request that touches protected files is **not** labelled `needs-human` and is not held for a person. The PR gets a comment naming the skipped files, and the integrator merges it after the full gate. What the switch does **not** relax:

- the full `scripts/check.sh` gate still runs on the merge result (a repair still uses `scripts/repair-gate.sh`), and Delivery still re-verifies the pushed commit on `main`;
- the shared-tracker rule still fails a PR that edits a task in `tasks/` or `tasks/`, `MEMORY.md`, `WORKSPACE.md`, `BUGS.md`, `PROJECT.md` or `docs/swarm/*`;
- the 50-file limit still sends a larger PR to `needs-human`;
- the branch must still match what was tested, and `.github/workflows/*` pushes still need `SWARM_TOKEN` with workflow scope (`SWARM_WORKFLOW_PUSH`) — the switch does not grant that permission.

Repairs already bypass the protected-file rule without the switch; the switch additionally lifts the gate-config check that would otherwise still block a repair. Module `check.sh` files are protected either way.

**Oversight issue.** For each PR revision that changes protected files (one issue per PR and head commit), a trusted job opens an issue labelled `protected-change`. It lists the protected files and their diffs, the PR link, the task id and the revision. It carries **no** `needs-human` or `needs-review` label, nothing waits for it, and it does not block the merge. A person reads it when convenient and closes it; if something is wrong, revert the merge or turn the switch off. Set `SWARM_ISSUES=off` to stop all issue writing, including these.

## Task files

Tasks live one per file in `tasks/<sequence>-<ID>.md`, so two writers only conflict when they touch the same task. `tasks/` is no longer stored in git: it is a local copy that git ignores, rebuilt from `tasks/` whenever the swarm reads or writes the tasks, or by `python3 scripts/taskstore.py view`. Workers, `scripts/check.sh` readers and people get it that way; the GitHub monitor reads the files directly. The sequence number keeps the old order; a new task gets a number between its neighbours and nothing else is renamed. Finished tasks are archived under `tasks/done/` and still satisfy `depends`.

- **Adding or editing a task by hand.** Edit or add the file in `tasks/` (keep the `- [ ] ID · title` line first). Edits to the local `tasks/` are lost the next time it is rebuilt.
- **Conflicts.** A pull request that touches `tasks/` or `tasks/` is not the source of truth: the integrator keeps main's version of those files and goes on merging.
- **Waves.** `swarm.yml` starts on a push that changes `tasks/**`.
- **Code.** `scripts/taskstore.py` (split, join, write, view, archive) and the `todo_read`, `todo_write`, `todo_paths` helpers in `scripts/swarm.py`. Without `tasks/.sharded` everything still works on a plain `tasks/`.

## Tasks requested by agents

A worker cannot edit `tasks/`. If its work needs a task that does not exist, it adds a fenced block named `task-requests` to its notes file: a JSON list of `{"title", "details", "scope", "depends"}`. When the worker's pull request merges, the integrator checks each request like an audit finding (title length, safe `scope` paths that are not protected files, `depends` on existing tasks, no duplicate title) and adds the valid ones as `FU-<pull request>-<n>` right after the worker's own task, so they are picked up soon after it. At most 3 per task and 30 open at once; the merge comment lists what was added. Anything invalid is ignored without failing the merge.
