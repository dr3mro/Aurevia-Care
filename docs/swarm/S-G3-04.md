## Defects found and fixed (test-first: red then green)

1. **S-G3-04-A1 (OPS-02, audit fidelity)** — `CareUnitDirectoryService.verifiedCharts` hard-coded `MessagingActions.UNIT_LIST` in its denial audit, so a no-verified-chart denial during `connect`, `listConnections` or `revoke` was recorded against the wrong action. Fixed by passing the attempted action from each caller. Red: `expected: <CONNECTION_CREATE> but was: <UNIT_LIST>`; green after fix.
2. **S-G3-04-A2 (OPS-02, missing audit)** — `requireActiveConnection` threw a bare `403` ApiException with no audit record, so a denied protected connection use (wrong unit, unlinked chart, revoked connection, stale membership) left no evidence. Fixed by routing through `authorize` and `deny` under a new bounded `CONNECTION_USE` action (patient self-service only). Red: `NoSuchElement` (no DENIED audit); green after fix.
3. **S-G3-04-A3 (MSG-01, tenant scoping)** — the mobile synthetic client's `listEligibleUnits` used all fixture units, so a cross-tenant unit with a matching relationship could appear in the patient directory even though `connect` rejects it. Fixed by constraining the listing to the active organization before applying eligibility. Red: expected `[]`, received the foreign unit; green after fix.
4. **S-G3-04-A4 (ARC-07, wrong-context reuse)** — the mobile client's idempotency lookup matched on patient/unit/reference but ignored context, so a connect with a different verified context silently returned the existing connection. Fixed by including context in the lookup; a mismatch now falls through to relationship validation and is denied. Red: `Expected: false, Received: true`; green after fix.

**Decision:** preserved the server's deliberate `409 CONFLICT` for reusing the same source reference under a different context (`connectAfterRevocationOrWithADifferentContextConflicts`); the mobile client now denies rather than returning the wrong connection. No API contract change, no schema change, no new dependency.
