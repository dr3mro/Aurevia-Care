## Defect found (safety-critical — patient identity / permission)

Both bounded reviewers (Senior Spring Security & OIDC; Software Architect) independently confirmed the same gap in `PatientAccessService`: role authorization (`authorize`) and token subject binding (`requireToken`) were the only gates on the three patient self-service commands. Each command loaded the account by a **caller-supplied `accountId`** via `requireAccount`, which checks tenant only — it never compared `account.subject()` to `actor.subject()`.

| Command | Exploit before fix |
|---|---|
| `recover` | patientA redeems their own valid recovery code against a same-tenant peer's `accountId` (synthetic fixtures share one fact digest) → resets/activates the peer account and consumes A's code. |
| `sensitiveChange` | patientA uses their own step-up token against a peer's `accountId` → unlinks the peer's chart or overwrites the peer's recovery contact. |
| `checkChartAccess` | patientA reads the chart-link/lock decision of any same-tenant account by passing its `accountId` (no token at all). |

This violated PRD-03 self-access and IAM-01 domain authorization; an unlink is a denial-of-access/clinical-safety hazard and a lockout reset defeats the account-lockout control. No controller compensates — the service is the sole entry point in this slice. Existing tests missed it because the only peer patient fixture lived in a different organization (tenant 404), not in the same tenant.

## Fix (smallest coherent change)

- Added private `requireOwnedAccount(actor, accountId)` in `PatientAccessService`: load the tenant-scoped account, then if `actor.subject()` != `account.subject()`, append `ACCESS_DENIED` with detail `not_owner` and throw 404 `NOT_FOUND` (ARC-04 concealment — a 403 would confirm the account exists).
- Swapped `requireAccount` → `requireOwnedAccount` at the three patient-command call sites: `recover`, `sensitiveChange`, `checkChartAccess`.
- Left staff commands (`issueRecovery`, `unlock`, `changeStaffContact`, `accountView`) on `requireAccount`: they legitimately act on another subject's account and must not be blocked.
- No public record, enum, request type, store interface, OpenAPI contract or state-model change. AccessToken remains subject-bound; once the account is owned by the actor and the token is bound to the actor's subject, token and account resolve to the same patient (reviewers agreed no accountId field is needed for this fix).
