# AUD-20261120-01 — Return HTTP 201 from patient registration and catalog entry creation

## Summary

`contracts/openapi/generated/openapi.yaml` declares `'201'` for `registerPatient` (POST `/api/v1/patients`) and `defineCatalogEntry` (POST `/api/v1/catalogs/{family}/entries`), but `PatientController.register` and `CatalogController.define` returned `ResponseEntity.ok(...)` (HTTP 200) with no `Location` header. Both now use `ResponseEntity.created(...)`, matching the convention already used by `StaffController`, `FacilityController`, `ConfigurationController` and `AppointmentController`. Tests that asserted 200 for these two POSTs were changed to assert 201, and the two primary HTTP tests now assert the `Location` header. No OpenAPI file, other controller, migration or shared tracker was changed.

## Affected requirements

- ARC-03 — versioned REST API and explicit command semantics; the OpenAPI contract is authoritative for the success status of these POST commands.
- IAM-03 — patient registration (POST `/api/v1/patients`).
- ADM-01 — tenant catalog entry definition (POST `/api/v1/catalogs/{family}/entries`).

Acceptance mapping:

| Acceptance criterion | Evidence |

| Both POSTs answer 201, not 200 | `PatientRegistrationTest` (6 tests) and `CatalogIsolationTest` (3 tests), red then green |
| Both POSTs carry a `Location` header | Assertions in `PatientRegistrationTest.registerAndReadPatient` and `CatalogIsolationTest.approvalMakesCatalogEntryEffective` |
| No test expects 200 for these POSTs | `grep` of status assertions near the two paths: none remain |
| Unrelated endpoints unchanged | Only the two controller `register`/`define` methods and their tests differ; `approve` and the GET endpoints still answer 200 |
| Contract unchanged | No file under `contracts/` was modified |
| Worker gate green | `bash scripts/worker-check.sh` (see Test evidence) |
