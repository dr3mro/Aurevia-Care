## Purpose

Section 9 of `SMARTCLINIC_V1_SPEC.md` (G3 — patient and operations) lists the required evidence for patient report access, generic notifications, withdrawn releases and messaging across both mobile platforms. This note maps each criterion named in the gate task to a merged test, document or story that exists on `main` today and records its status. It prepares evidence for a person to accept; it never records acceptance. Acceptance of G3 is a human Product Owner decision, and the clinical and privacy sign-offs that gate real use stay human decisions (G5). A merged test proves an engineering behaviour, not that a person has accepted it.

Only evidence merged on `main` is linked. A design document, a simulated UAT script, an open task title or a naming claim alone is not treated as proof of a behaviour. Where a domain-level acceptance test is backed by an HTTP-level and/or mobile test, all are named so a reviewer can trace the entry point.

Requirement scope: PAT-01 supplies the generic-notification, detail-after-authentication and device-revocation rules; PAT-02/PAT-03 and XCH-06 supply authorized revisions and terminal withdrawal; MSG-01–07 supply connection-scoped messaging, uploads, instructions, separate facts, generic dispatch, service governance and revocation.

## Entry point to test trace

- **Authorized revisions.** HTTP `GET /api/v1/patient/reports` and `GET /api/v1/patient/reports/{id}/download` (`ReleasedReportControllerHttpTest`, `PatientReleaseIsolationTest`). `ReleasedReportService` re-derives the verified patient link on every action and filters held, future-dated, withdrawn and foreign-chart revisions; the mobile `report-core.test.ts` drives an exact-revision download authorization through the client, including the withdrawn and foreign-patient negatives.
- **Generic notifications.** HTTP `GET /api/v1/patient-flow/notices/{kind}` (`PatientFlowPresentationControllerHttpTest.notificationTextIsReachableOverHttp`) and the appointment status-change flow (`PatientAppointmentControllerHttpTest`). `GenericPushNotice` / `buildPushPayload` carry fixed text; detail is fetched only after authentication (`features/notifications/payload.test.ts`).
- **Withdrawn releases.** HTTP release/withdraw routes and patient-visible revision routes (`PatientReleaseIsolationTest.withdrawalStopsAccessRetainsHistoryAndNotifies`, `withdrawnRevisionCannotBeReauthorized`). Withdrawal is a terminal release state; the fact history and prior-recipient notification are retained while access returns 410.
- **Messaging.** HTTP `POST /api/v1/patient/attachments` (multipart scan/publish/download, `AttachmentControllerHttpTest`), `POST /api/v1/patient/instructions/{id}/acknowledge` and fact routes (`InstructionFactControllerHttpTest`), connection/conversation commands (`PatientConversationAcceptanceTest` over `ConversationService` with a JDBC store behind it), and `GET /api/v1/patient-flow/presentation` for both platform profiles (`PatientFlowPresentationControllerHttpTest`). On mobile the same flows are exercised through the shared clients in `features/units`, `features/attachments`, `features/instructions`, `features/acknowledgments` and `features/governance`.

## Open items (not evidence gaps, not acceptance)

1. **Human acceptance of G3 remains open.** No Product Owner, clinical or privacy sign-off is recorded in this note or anywhere on `main`. A person must accept G3 using this evidence; a worker cannot. `GATE-PACK-G3` (tasks/, "Gate G3 … evidence pack for the Product Owner to accept") is the open task that prepares the signable pack; the decision itself is a human Product Owner action that no worker task can close.
2. **Per-clause gate tasks remain open.** `SPEC-G3-01`, `SPEC-G3-02`, `SPEC-G3-03`, `SPEC-G3-04` and `SPEC-G3-05` are `[ ]` in tasks/; their `docs/spec/clauses/gates/` notes and `gates/clauses` test classes do not exist on `main`. They are still-open formal artifacts, not evidence gaps: the merged BUILD-63 acceptance tests, HTTP tests and mobile tests above already prove each behaviour. `GATE-PACK-G3` depends on all five. Closing them is a separate clause-note task, not a reason to mark a criterion open here.
3. **Native-device verification is not claimed.** The evidence proves the shared React Native code and both declared platform profiles (iOS/Android configuration and platform-aware presentation), but no on-device iOS/Android or native screen-reader run exists on `main`. That verification is a G5 human action, owned by `S-G5-12` and prepared by `GATE-PACK-G5`, not a G3 evidence gap and not something a worker can record.
4. **Open mobile-app defects narrow end-to-end readiness.** `BUGS.md` records `QA-SOURCE-01` (PAT-01, High: Confirm on an eligible appointment has a no-op handler) and `QA-SOURCE-02` (PAT-02, High: Download on a released report has a no-op handler and a mismatched HTTP method in the standalone client), both from static review with synthetic scenarios and both "open, regression pending". They do not negate the server-side authorization and non-disclosure behaviour proved above, but they are unresolved UI defects in the patient surface; each needs its own triage, regression test and retest before this gate can be signed.
5. **Delivery contract debt is tracked separately.** `BUGS.md` `DELIVERY-1491` (ARC-03, ARC-04, WEB-05) records instant-messaging operations published before pagination/mutation-header support and routes absent from the baseline; the local repair removed premature entries and tracks the remaining route debt. It concerns OpenAPI/staff-client parity rather than the patient-messaging behaviours above, but it remains an open delivery finding.
6. **This note is evidence, not a verdict.** It does not say "Ready for acceptance" or "Not ready"; that verdict belongs to the signable pack and the human decision described above.
