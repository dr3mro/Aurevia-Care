## Purpose

Section 9 of `SMARTCLINIC_V1_SPEC.md` (G4 — specialty and finance) lists the required evidence for radiology, physical therapy, pharmacy and self-pay. This note maps each of the five evidence sentences named in the gate task to a merged test, document or story that exists on `main` today and records its status. It prepares evidence for a person to accept; it never records acceptance. Acceptance of G4 is a human Product Owner decision, and the clinical and privacy sign-offs that gate real use stay human decisions (G5). A merged test proves an engineering behaviour, not that a person has accepted it.

Only evidence merged on `main` is linked. A design document, a simulated UAT script, an open task title or a naming claim alone is not treated as proof of a behaviour. Where a domain-level acceptance test is backed by an HTTP-level and/or durable-store integration test, all are named so a reviewer can trace the entry point. All five rows below are led by the BUILD-64 acceptance tests (PR #494, squash merge commit `206fff6b7b51591e774e54b9f28adfc02c2eecaf`, merged into `main`); each cited class, method and negative case was read directly.

Requirement scope: RAD-01 supplies the study-link verification, signed interpretation and addendum rules; PT-01 supplies referral acceptance, signed notes and approved-summary/return-acknowledgment rules; RX-02 supplies stable submission IDs and partner-status verification before an ambiguous retry; FIN-01 supplies fixed-precision entries, reference deduplication and numbered receipts, with immutable linked ledger entries and balance rules.

## Entry point to test trace

- **Wrong-patient study.** Domain entry `ImagingService.associateStudy(AssociateStudyCommand)` (`RadiologyWrongPatientStudyRefusedAcceptanceTest`); HTTP `POST /api/v1/radiology/worklist/orders/{orderId}/studies` (`WorklistControllerHttpTest.linking_a_study_for_the_wrong_patient_is_refused_over_http`) and `POST /api/v1/imaging/orders/{orderId}/studies` plus `GET /api/v1/imaging/orders/study-link-reviews` and `POST /api/v1/imaging/orders/study-link-reviews/resolve` (`ImagingControllerHttpTest.mismatchQueuesAReviewAndReLinkAfterReviewThroughHttp`). `ImagingService` verifies patient, accession, role, version and tenant before setting a Study Instance UID; a mismatch queues an OPEN link review, mutates nothing and never emits `STUDY_ASSOCIATED`.
- **Addendum to referrer.** Domain entry `ImagingService.addAddendum(AddendumCommand)` (`RadiologyAddendumReachesReferrerAcceptanceTest`); HTTP `POST /api/v1/radiology/reports`, addendum publication, `GET /api/v1/radiology/reports/events`, `GET /api/v1/radiology/reports/addenda/open`, `POST /api/v1/radiology/reports/{orderId}/addenda` and `POST /api/v1/radiology/reports/{id}/addenda/{version}/acknowledge` (`ReportControllerHttpTest.addendum_notifies_the_referrer_and_acknowledgment_closes_it_over_http`). A signed addendum appends `ADDENDUM_LINKED` then `REFERRER_NOTIFIED` addressed to the verified referrer and opens an addendum the referrer can read and acknowledge; an invalid addendum appends neither.
- **Therapy discharge.** Domain entry `TherapyService.acceptReferral`, `recordNote`, `signNote`, `sendSummary` and `acknowledgeReturn` against the injected store (`TherapyDischargeAcceptanceTest`); HTTP referral accept and episode read at `POST /api/v1/therapy/episodes` and `GET /api/v1/therapy/episodes/{episodeId}` (`TherapyControllerHttpTest`); JDBC/persistence path `JdbcTherapyStore` with `TherapyEpisodeFlowTest.signsDischargeTransitionsEpisodeAndSendsApprovedSummaryWithReturnAcknowledgment` and `JdbcTherapyStoreIntegrationTest.signedNoteIsImmutableAndDischargeClosesTheReferral`. "Referral closure" in this domain is the episode reaching `DISCHARGED` after a signed discharge note; there is no separate referral-status entity or closure endpoint. The signed note is immutable and tenant-scoped in the database.
- **Ambiguous prescription.** Domain entry `RxService.transmit`, `verifyPartnerStatus` and `retry` (`PharmacyAmbiguousTransmissionAcceptanceTest`); HTTP create/attest/transmit/verify/retry on `POST /api/v1/prescriptions/{id}/transmit`, `POST /api/v1/prescriptions/{id}/verify-partner-status` and `POST /api/v1/prescriptions/{id}/retry` (`RxTransmissionFlowTest.ambiguousRetryIsBlockedUntilPartnerStatusIsVerifiedAbsent`, `RxHttpSecurityTest.allowedSubjectReachesSuccessStatusOnEveryRoute`). The stable submission id is inserted once; a partner status must be verified absent before a retry is issued, and a present status returns the prescription to SUBMITTED with no second logical send.
- **Finance replay.** Domain entry `FinanceService.postEntry` with its `FinanceRepository.findByReference` digest replay check (`FinanceLedgerReplayAcceptanceTest`, `FinanceService`/`FinanceRepository`); HTTP invoice create/issue/payments/refunds at `POST /api/v1/finance/invoices/{id}/payments` and `/refunds` and `GET /api/v1/finance/reconciliation` (`FinanceFlowTest.refundReestablishesIssuedStateAndReplayIsANoOp`, `aReusedReferenceWithADifferentPayloadIsRejected`, `FinanceHttpSecurityTest.allowedSubjectReachesSuccessStatusOnEveryRoute`). A recorded reference is idempotent by digest; a reused reference with a different payload is a 409 conflict and never posts money twice. Finance roles see amounts, not clinical narrative.
