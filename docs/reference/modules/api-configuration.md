# Module guide: Tenant configuration (`com.aurevia.configuration`)

The `configuration` package owns versioned tenant configuration: append-only drafts, separately named approvals, effective-dated reads and immutable history for administrative and clinical or market policies. It owns the invariants and the single SQL boundary for them, so a policy change is always a new version with an actor-derived author, a named approver and a correlated audit event, never an update of an existing row ([ConfigurationService.java](../../../apps/api/src/main/java/com/aurevia/configuration/ConfigurationService.java), [ConfigurationRepository.java](../../../apps/api/src/main/java/com/aurevia/configuration/ConfigurationRepository.java)).

Primary requirement: ADM-01 — tenant admins configure facilities, referral partner directory, scheduling policies, templates, catalogs, coverage rosters, critical-result escalation rules and patient release policies, while clinical and market policies require named approval, effective dates, audit and version history. Supporting requirements are ARC-02, IAM-01 and OPS-02; the V5 migration header also records OPS-06 ([PROJECT_V1_SPEC.md](../../../.opencode/config/PROJECT_V1_SPEC.md), [V5__tenant_configuration.sql](../../../db/migrations/V5__tenant_configuration.sql)).

## Entry points

The HTTP adapter lives in `com.aurevia.web`, not in this package. The package itself declares no `@RestController`, no scheduled job and no event handler. The authoritative HTTP contract declares all four routes with their request and response schemas ([openapi.yaml](../../../contracts/openapi.yaml)); the generated command-oriented document declares only the two POST commands and is described below. The end-to-end route trace is recorded in the [maintainer guide](../maintainer.md). Every `CONFIG_*` action is decided by `ActionPolicy` from active membership and role assignment re-read inside the command transaction; `tenant_admin` allows all four actions and `reception` denies them ([ActionPolicy.java](../../../apps/api/src/main/java/com/aurevia/authz/ActionPolicy.java), [ConfigurationActionPolicyTest.java](../../../apps/api/src/test/java/com/aurevia/authz/ConfigurationActionPolicyTest.java)). Client-supplied authority fields are inert.

The generated command-oriented contract declares 201, 401, 403, 422, 428 and 500 for both POST operations; the 404 and 409 outcomes above are service-level results asserted by the HTTP tests, not declared entries in that document ([generated/openapi.yaml](../../../contracts/openapi/generated/openapi.yaml)).

`ConfigEntry` is the shared projection for a draft, an approval or an effective value; `ConfigHistory` freezes its entry list so an append-only trail cannot be mutated in memory ([ConfigEntry.java](../../../apps/api/src/main/java/com/aurevia/configuration/ConfigEntry.java), [ConfigHistory.java](../../../apps/api/src/main/java/com/aurevia/configuration/ConfigHistory.java)). The controller's `CreateRequest` and `ApproveRequest` records carry only key, value, effectiveFrom and note; organization, version, author and approver are never accepted from the client ([ConfigurationController.java](../../../apps/api/src/main/java/com/aurevia/web/ConfigurationController.java)).

## Tables it reads and writes

All statements run inside the tenant-guarded transaction, and V5 applies `ENABLE` plus `FORCE ROW LEVEL SECURITY` with `USING`/`WITH CHECK organization_id = app_org()` to both configuration tables; `app_org()` is defined in V2, whose header records that the separate migration and non-bypass runtime roles are provisioned out-of-band; the `NOBYPASSRLS` role creation is performed by the database check script ([V5__tenant_configuration.sql](../../../db/migrations/V5__tenant_configuration.sql), [V2__rls_roles_policies.sql](../../../db/migrations/V2__rls_roles_policies.sql), [db/check.sh](../../../db/check.sh), [TenantGuardTransactionManager.java](../../../apps/api/src/main/java/com/aurevia/tenant/TenantGuardTransactionManager.java)).

| Table / schema object | Relationship | Source |

V5 also defines `BEFORE UPDATE OR DELETE` and `BEFORE TRUNCATE` triggers on both tables using `reject_immutable_mutation()` (defined in V4). On the tables the runtime role receives only `SELECT` and `INSERT`, with `UPDATE`, `DELETE` and `TRUNCATE` revoked; the two SQL functions are separately granted `EXECUTE` ([V5__tenant_configuration.sql](../../../db/migrations/V5__tenant_configuration.sql), [V4__staff_lifecycle.sql](../../../db/migrations/V4__staff_lifecycle.sql)). The `db/check.sh` apply-and-assert gate exercises the forced RLS, actor-derived fields, version sequencing, approval uniqueness, the fold and the immutability triggers directly ([db/check.sh](../../../db/check.sh)).

## Events published or consumed

**None.** No class in the package publishes or consumes a domain event: there is no `@EventListener`, message sender or outbox call in its sources. `appendAudit` writes an append-only audit row synchronously inside the caller's transaction; it is an audit fact, not a durable event. Durable event delivery belongs to the separate `events` package and its X-02 contract ([ConfigurationRepository.java](../../../apps/api/src/main/java/com/aurevia/configuration/ConfigurationRepository.java), [contracts/events/README.md](../../../contracts/events/README.md)).

## Things to know

- **A draft is never effective on its own.** `get` reads `effective_config`, which joins `config_approval` and requires `effective_from <= now()`. An approved version with a future window returns 404 until the instant passes; ordering is by effective window, creation time and id, not by version number ([V5__tenant_configuration.sql](../../../db/migrations/V5__tenant_configuration.sql), [ConfigurationIsolationTest.java](../../../apps/api/src/test/java/com/aurevia/it/ConfigurationIsolationTest.java)).
- **Actor identity is database-owned.** V5 `BEFORE INSERT` triggers set `created_by` and `approved_by` from `app.actor`; a forged `approvedBy` in the approval body is inert. The service additionally refuses an approver whose subject has no `user_identity` row (403) before inserting anything ([V5__tenant_configuration.sql](../../../db/migrations/V5__tenant_configuration.sql), [ConfigurationService.java](../../../apps/api/src/main/java/com/aurevia/configuration/ConfigurationService.java)).
- **Everything is append-only.** V5 rejects `UPDATE`, `DELETE` and `TRUNCATE` on both tables; a change is a new version. `ConfigHistory` also freezes its list in memory, so callers cannot mutate the returned trail ([V5__tenant_configuration.sql](../../../db/migrations/V5__tenant_configuration.sql), [ConfigHistory.java](../../../apps/api/src/main/java/com/aurevia/configuration/ConfigHistory.java)).
- **Version allocation is serialized in the database.** `next_config_version` takes a transaction-scoped advisory lock keyed by organization and key, and fails closed if the tenant context is unset; a racing duplicate insert is caught as `DuplicateKeyException` and returned as 409 `CONFLICT` with a `CONFLICT` audit row ([V5__tenant_configuration.sql](../../../db/migrations/V5__tenant_configuration.sql), [ConfigurationService.java](../../../apps/api/src/main/java/com/aurevia/configuration/ConfigurationService.java)).
- **Authorization and concealment are deliberate.** Membership and roles are re-derived from database folds on every command, so deactivation denies the next request. A foreign-tenant key or an unknown version is concealed with 404 after actor authorization, while a valid actor in the wrong organization gets 403; denials are committed as `DENIED` audit rows in the same transaction ([ConfigurationService.java](../../../apps/api/src/main/java/com/aurevia/configuration/ConfigurationService.java), [ConfigurationIsolationTest.java](../../../apps/api/src/test/java/com/aurevia/it/ConfigurationIsolationTest.java)).
- **Null and blank `effectiveFrom` differ.** A missing value defaults to `Instant.now()`, but a blank or unparseable string is 422 `INVALID_EFFECTIVE_FROM`; keys must match `[a-z][A-Za-z0-9._:-]{2,63}` (3–64 characters starting lowercase) and values must be 1–4000 characters ([ConfigurationService.java](../../../apps/api/src/main/java/com/aurevia/configuration/ConfigurationService.java), [ConfigurationServiceTest.java](../../../apps/api/src/test/java/com/aurevia/configuration/ConfigurationServiceTest.java)).
- **The returned `approvedAt` is a service instant.** The approval projection uses `Instant.now()` from the service, while the persisted `approved_at` is the V5 database default; the stored and returned strings can differ slightly ([ConfigurationService.java](../../../apps/api/src/main/java/com/aurevia/configuration/ConfigurationService.java), [V5__tenant_configuration.sql](../../../db/migrations/V5__tenant_configuration.sql)).
- **The command-generated contract covers only the two POST commands.** `CommandCatalog` emits [generated/openapi.yaml](../../../contracts/openapi/generated/openapi.yaml) and [generated/client.ts](../../../contracts/openapi/generated/client.ts) with just `createConfiguration` and `approveConfiguration`; those `GET` read and history routes have no entry in the command catalog or its client. Separately, the staff-web types generated from the authoritative [contracts/openapi.yaml](../../../contracts/openapi.yaml) include all four routes, with `getEffectiveConfiguration` and `getConfigurationHistory` ([openapi.d.ts](../../../apps/staff-web/src/api/generated/openapi.d.ts), [contracts/openapi/README.md](../../../contracts/openapi/README.md)).
- **Audit is synchronous and tenant-bound.** `appendAudit` writes `actor_id = NULL` and relies on the V3 trigger to resolve the actor from `app.actor`; purpose `CONFIG_ADMIN` and scope `CONFIG` are constants on the repository, and the correlation id is echoed from `TenantContext` ([ConfigurationRepository.java](../../../apps/api/src/main/java/com/aurevia/configuration/ConfigurationRepository.java), [V3__audit_chain.sql](../../../db/migrations/V3__audit_chain.sql)).
