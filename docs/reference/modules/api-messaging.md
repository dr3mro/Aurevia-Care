# Module guide: patient messaging API (`com.aurevia.messaging`)

The `messaging` package is the server-side backbone for patient-to-care-unit communication: it publishes the verified care-unit directory and connection grants (MSG-01), then scopes conversations, attachments, typed instructions, acknowledgment facts, service profiles, governance and released reports to one verified patient, one recipient unit and one active tenant connection. It also hosts the patient-flow presentation and G3 gate-evidence slices. Protected commands derive organization and subject from the request context, and where a role gate applies they re-derive active membership and role on every call, rather than trusting client-supplied identity ([CareUnitDirectoryService.java](../../../apps/api/src/main/java/com/aurevia/messaging/units/CareUnitDirectoryService.java), [ConversationService.java](../../../apps/api/src/main/java/com/aurevia/messaging/conversations/ConversationService.java), [MessagingGovernanceService.java](../../../apps/api/src/main/java/com/aurevia/messaging/governance/MessagingGovernanceService.java)).

Primary requirement: MSG-01 (eligible units and verified, connection-scoped relationships). The package also implements MSG-02 through MSG-07, and the code states additional boundary requirements ARC-01 through ARC-07, IAM-01, IAM-02, IAM-05, OPS-02, WEB-04 and XCH-06 on individual classes ([PROJECT_V1_SPEC.md](../../../.opencode/config/PROJECT_V1_SPEC.md), [contracts/openapi.yaml](../../../contracts/openapi.yaml)).

## Entry points

Twelve `@RestController` classes expose 71 HTTP routes under `/api/v1`. There are **no scheduled jobs, no Spring event listeners and no durable outbox publisher** in this package: a tool search for `@Scheduled`, `@EventListener`, `publishEvent` and `delivery_outbox` across its sources returned no matches. Commands that are not HTTP routes are named in the tables and in [Things to know](#things-to-know).

In the caller column, **patient** means the `patient` role with a verified chart in the active tenant, **staff role** means one of `reception`, `clinical_assistant`, `clinician`, `lab_collector`, `lab_verifier`, `radiology_staff`, `radiology_interpreter`, `pt_clinician`, `pharmacy_staff`, and **unit staff** further narrows that set to the unit's category (`reception`/`clinical_assistant`/`clinician` for clinic, `lab_collector`/`lab_verifier` for lab, `radiology_staff`/`radiology_interpreter` for radiology, `pt_clinician` for therapy, `pharmacy_staff` for pharmacy) ([ConversationActions.java](../../../apps/api/src/main/java/com/aurevia/messaging/conversations/ConversationActions.java)). Roles are re-derived from active membership on every request; a role key alone never crosses a tenant, unit or connection boundary.

## Things to know

- **A directory listing is not an authorization.** `eligibleUnits` and `connect` require an independently verified chart and an active, unconsumed, unexpired relationship tying that exact patient to that exact unit; a role such as `tenant_admin` may list units but cannot connect as a patient, and both reads still require a verified chart ([CareUnitDirectoryService.java](../../../apps/api/src/main/java/com/aurevia/messaging/units/CareUnitDirectoryService.java)). A repeated verified reference returns the original connection, and a single-use invitation is consumed only on the first successful connection.
- **No cross-unit conversations.** `ConversationActions.allowsUnit` narrows a staff role to its unit category, so a cross-unit assignment or transfer is impossible; `tenant_admin` may read the work queue but holds no work-item write action, and `privacy_auditor` holds no messaging action at all ([ConversationActions.java](../../../apps/api/src/main/java/com/aurevia/messaging/conversations/ConversationActions.java)).
- **Four instruction facts stay separate.** A view never acknowledges, an acknowledgment confirms receipt of one exact revision, and a generic dispatch fact carries only the key `NEW_INSTRUCTION` and no clinical content; requested acknowledgments need a due instant for overdue routing ([InstructionFactService.java](../../../apps/api/src/main/java/com/aurevia/messaging/acknowledgment/InstructionFactService.java)).
- **Not every domain command has a route.** `AttachmentService.publish`, `remove`, `fileIntoChart`, `view`, `events` and `inbox` are used by tests but are not exposed by `AttachmentController`, which binds only upload, scan and download; `MessagingGovernanceService.applyRetention` has no route either ([AttachmentService.java](../../../apps/api/src/main/java/com/aurevia/messaging/attachments/AttachmentService.java), [AttachmentController.java](../../../apps/api/src/main/java/com/aurevia/messaging/attachments/AttachmentController.java), [MessagingGovernanceService.java](../../../apps/api/src/main/java/com/aurevia/messaging/governance/MessagingGovernanceService.java)).
- **The appointments slice is synthetic and is recorded wiring debt.** Its service has no Spring stereotype and no persistence adapter: the controller constructor builds `SyntheticPatientAppointmentPorts` and a service in production. `scripts/wiring-baseline.json` lists `PatientAppointmentController` under `controller-builds` and the `DeviceTokenStore` and `PatientAppointmentStore` ports under `store-without-durable`; durable adapters and wiring are follow-on work ([PatientAppointmentController.java](../../../apps/api/src/main/java/com/aurevia/messaging/appointments/PatientAppointmentController.java), [PatientAppointmentService.java](../../../apps/api/src/main/java/com/aurevia/messaging/appointments/PatientAppointmentService.java), [wiring-baseline.json](../../../scripts/wiring-baseline.json)).
- **One in-memory store lives in production source.** `InMemoryPatientAccessStore` is in `src/main` and is used by tests and acceptance fixtures; the production `PatientAccessService` is backed by the `@Repository` `JdbcPatientAccessStore`. The in-memory class is listed under `inmemory-in-main` in the wiring baseline ([InMemoryPatientAccessStore.java](../../../apps/api/src/main/java/com/aurevia/messaging/enrollment/InMemoryPatientAccessStore.java), [JdbcPatientAccessStore.java](../../../apps/api/src/main/java/com/aurevia/messaging/enrollment/JdbcPatientAccessStore.java), [wiring-baseline.json](../../../scripts/wiring-baseline.json)).
- **Report authorization is not single-transaction.** Each store read opens its own tenant-guarded transaction, so a withdrawal or correction committed between two reads can change an in-flight download; sequential withdrawal stops the next download ([ReleasedReportService.java](../../../apps/api/src/main/java/com/aurevia/messaging/reports/ReleasedReportService.java)).
- **Two slices sit here by convention, not by patient-messaging domain.** `flows` serves server-authored patient presentation (locale, RTL, platform wording, approved notice text) and `evidence` evaluates synthetic restore, downtime, load and accessibility fixtures for the G3 gate; the evidence ledger is rebuilt on every call and is not a database table ([PatientFlowPresentationService.java](../../../apps/api/src/main/java/com/aurevia/messaging/flows/PatientFlowPresentationService.java), [GateEvidenceService.java](../../../apps/api/src/main/java/com/aurevia/messaging/evidence/GateEvidenceService.java)).
- **Denials are facts.** The owning services append a non-sensitive audit fact for both success and denial of a bounded action, including concealment as 404 for foreign tenants and unavailable resources; the audit trail itself is a privileged read ([CareUnitDirectoryService.java](../../../apps/api/src/main/java/com/aurevia/messaging/units/CareUnitDirectoryService.java), [MessagingGovernanceService.java](../../../apps/api/src/main/java/com/aurevia/messaging/governance/MessagingGovernanceService.java)).
