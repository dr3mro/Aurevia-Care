# Module guide: Laboratory (`com.aurevia.lab`)

The `lab` package owns the specimen lifecycle for laboratory medicine: it accessions a requisition under an issuer-scoped unique number, records specimen type, site, collector and collection/receipt time with patient and accession matching at both touchpoints, and preserves rejection, notification and linked recollection as immutable history. Its `lab.result` subpackage holds the LAB-02 domain kernel that captures numeric, qualified numeric, text and coded observations, verifies and issues append-only report revisions against versioned approved site policies, and emits XCH-04/05 trigger facts ([LabAccessionService.java](../../../apps/api/src/main/java/com/aurevia/lab/accession/LabAccessionService.java), [LabResultService.java](../../../apps/api/src/main/java/com/aurevia/lab/result/LabResultService.java)).

Primary requirements: LAB-01 (specimen accession) and LAB-02 (observations, verification states and issued revisions), with tenant, audit and immutability duties from ARC-01, ARC-02, ARC-03 and OPS-02, issuer/code boundary from IAM-03 and comparability from XCH-07 ([PROJECT_V1_SPEC.md](../../../.opencode/config/PROJECT_V1_SPEC.md)).

## Entry points

The package declares one `@RestController` (accession) and no scheduled jobs and no event handlers. The `lab.result` package exposes library commands only: its HTTP entry point is `LabResultEntryController` in the separate `labflow.results` package, so a result request reaches this kernel through `ResultEntryService`. The "caller" column names the duty that may invoke each entry point. Membership and roles are re-derived from the active tenant in `LabAccessionService.authorize` and `ResultEntryService.authorize`, never accepted from an HTTP request body; `LabActionPolicy` and `LabRules` define the role-to-action mapping, while the internal library commands carry server-populated role sets ([LabAccessionController.java](../../../apps/api/src/main/java/com/aurevia/lab/accession/LabAccessionController.java), [LabAccessionService.java](../../../apps/api/src/main/java/com/aurevia/lab/accession/LabAccessionService.java), [ResultEntryService.java](../../../apps/api/src/main/java/com/aurevia/labflow/results/ResultEntryService.java)).

## Events published or consumed

The accession side writes an immutable **history ledger**, not a durable domain event: `lab_accession_event` records each `accessioned`, `collected`, `received`, `rejected` or `recollected` step inside the state-changing transaction. It consumes no external event ([LabAccessionRepository.java](../../../apps/api/src/main/java/com/aurevia/lab/accession/LabAccessionRepository.java), [V26__laboratory_accession.sql](../../../db/migrations/V26__laboratory_accession.sql)).

The result kernel produces **in-memory `TriggerEvent` facts** of four types — `RESULT_ISSUED` and `RESULT_CORRECTED` route an issued revision to a named owner and coverage queue (XCH-04), `CRITICAL_RESULT` escalates each critical finding with owner, due time and backstop (XCH-05), and `RESULT_WITHDRAWN` withdraws future access to an entered-in-error revision. Each fact has a deterministic `dedupKey` and name-based `eventId` for a future outbox. This package does not deliver them to a partner or satisfy a clinical acknowledgment; `labflow.results.ResultEntryService` separately registers the XCH-05 critical-result workflow, and the X-02 durable outbox belongs to the `events` package. The result kernel consumes no events ([TriggerEvent.java](../../../apps/api/src/main/java/com/aurevia/lab/result/TriggerEvent.java), [LabResultService.java](../../../apps/api/src/main/java/com/aurevia/lab/result/LabResultService.java), [contracts/events/README.md](../../../contracts/events/README.md)).

## Things to know

- **The result kernel is not wired to HTTP, persistence or an outbox here.** `LabResultService` is a `final` class constructed by `ResultConfiguration` with an **empty** `LabPolicyCatalog`, so it has no implicit reference range or critical threshold: an empty catalog preserves the abnormal flag supplied at the boundary. Its revision and event ledgers are process-local `HashMap`s, so data does not survive a restart; `labflow.results` persists the durable workflow state separately ([LabResultService.java](../../../apps/api/src/main/java/com/aurevia/lab/result/LabResultService.java), [ResultConfiguration.java](../../../apps/api/src/main/java/com/aurevia/labflow/results/ResultConfiguration.java)).
- **`comparable` and `events` have no production caller.** `LabResultService.comparable` and `LabResultService.events` are the only public kernel methods not called by `ResultEntryService`; tests exercise them as the read surface for XCH-07 comparability and pending XCH-04/05 trigger delivery ([LabResultService.java](../../../apps/api/src/main/java/com/aurevia/lab/result/LabResultService.java)).
- **The source order is a reference, not an aggregate.** A specimen carries only a bounded `sourceOrderRef` string; this package never creates an order record and grants no general chart access through it ([LabAccession.java](../../../apps/api/src/main/java/com/aurevia/lab/accession/LabAccession.java)).
- **Collection and verification are separate duties.** `LabActionPolicy` hard-codes `lab_collector` (accession, read, collect) and `lab_verifier` (read, receive, reject, recollect), and `LabRules` mirrors that split for the result kernel; site-configurable privileges are a later concern. `ResultEntryService` additionally prevents an enterer from self-verifying ([LabActionPolicy.java](../../../apps/api/src/main/java/com/aurevia/lab/accession/LabActionPolicy.java), [LabRules.java](../../../apps/api/src/main/java/com/aurevia/lab/result/LabRules.java)).
- **Two state machines are enforced twice.** `AccessionState` and `VerificationState` define legal edges in Java, and V26's `guard_lab_accession_update` trigger mirrors the accession edges in SQL so a stray update cannot walk a specimen backwards or skip a stage. A rejection never deletes the original specimen; recollection is only legal from `REJECTED` and the recollected row is terminal ([AccessionState.java](../../../apps/api/src/main/java/com/aurevia/lab/accession/AccessionState.java), [LabTypes.java](../../../apps/api/src/main/java/com/aurevia/lab/result/LabTypes.java), [V26__laboratory_accession.sql](../../../db/migrations/V26__laboratory_accession.sql)).
- **Verification is not patient release or clinician acknowledgment.** Only `FINAL` and `CORRECTED` revisions route to an owner; release of information and acknowledgment belong to the exchange and messaging packages ([LabTypes.java](../../../apps/api/src/main/java/com/aurevia/lab/result/LabTypes.java)).
- **A qualifier or a different unit is never guessed.** `LabRules.comparable` joins results only for present exact numeric observations of one test identity with matching units, or a documented, versioned, one-way conversion from `LabConversionCatalog`; unknown, absent, qualified and qualitative values stay visible but unjoined ([LabRules.java](../../../apps/api/src/main/java/com/aurevia/lab/result/LabRules.java), [LabUnitConversion.java](../../../apps/api/src/main/java/com/aurevia/lab/result/LabUnitConversion.java)).
- **The list read reuses the single-record permission.** `list` authorizes with `ACCESSION_READ` and resource id `ALL`, so anyone who may read one accession may page the tenant's accessions; its opaque cursor must be a canonical `<createdAt>:<id>` or the service returns 422 before querying ([LabAccessionService.java](../../../apps/api/src/main/java/com/aurevia/lab/accession/LabAccessionService.java)).
