# Module guide: Exchange (`com.aurevia.exchange`)

The `exchange` package implements the cross-organization clinical data-exchange slices of the API: an authorized sender releases an order as an immutable snapshot with a bounded disclosure and a receiver work item, and the receiver answers through a versioned response workflow. It also owns inbound result routing and reconciliation, critical-result escalation, patient release decisions, observation trending, and the synthetic FHIR R4/HL7 v2 partner conformance fixtures, together with the HTTP adapters, command services, state machines, JDBC stores and wire mappers for XCH-01 through XCH-07 ([OrderController.java](../../../apps/api/src/main/java/com/aurevia/exchange/order/OrderController.java), [ExchangeStateMachine.java](../../../apps/api/src/main/java/com/aurevia/exchange/task/ExchangeStateMachine.java), [PartnerReportProcessor.java](../../../apps/api/src/main/java/com/aurevia/exchange/conformance/PartnerReportProcessor.java)).

Primary requirement: XCH-01 — an order carries the local patient and encounter, order code, priority, clinical question, destination, source actor and responsible clinician/work queue; the sending organization authorizes the specific payload, recipient, purpose and duration; the released content is snapshotted and stamped; and the receiver sees an exchange-specific work item with a locally verified patient association, with no general chart access ([PROJECT_V1_SPEC.md](../../../.opencode/config/PROJECT_V1_SPEC.md), [OrderService.java](../../../apps/api/src/main/java/com/aurevia/exchange/order/OrderService.java)). Sibling slices XCH-02 to XCH-07 add the three-channel task state machine, recipient responses, result routing, critical results, patient release and trending; the arc and operations rules are ARC-01 to ARC-05, IAM-01, IAM-06, PRD-06, WEB-04 and OPS-02 ([PROJECT_V1_SPEC.md](../../../.opencode/config/PROJECT_V1_SPEC.md)).

## Entry points

All HTTP routes are thin adapters under `/api/v1`; tenant context is derived by the request interceptor and the adapters only parse the body, `If-Match` and query parameters before delegating to an injected service ([OrderController.java](../../../apps/api/src/main/java/com/aurevia/exchange/order/OrderController.java), [CriticalResultController.java](../../../apps/api/src/main/java/com/aurevia/exchange/critical/CriticalResultController.java)). Roles below are re-derived from active membership inside each guarded transaction, never accepted from the client; a denied request is audited before it is returned ([OrderService.java](../../../apps/api/src/main/java/com/aurevia/exchange/order/OrderService.java)). This package declares **no scheduled job and no event handler**: there is no `@Scheduled`, no `@EventListener` and no `ApplicationEventPublisher` in its sources. ## Events published or consumed

No class in this package publishes or consumes a durable domain event through the separate delivery outbox: there is no `@EventListener`, no `ApplicationEventPublisher` and no call into the `events` package, whose synthetic contract and reserved migration are owned elsewhere ([contracts/events/README.md](../../../contracts/events/README.md)). Instead each slice writes its own append-only ledger and notification table in the same tenant-guarded transaction as the state change, and appends a structured `audit_event` with identifiers only, never the inbound clinical payload ([ExchangeTaskService.java](../../../apps/api/src/main/java/com/aurevia/exchange/task/ExchangeTaskService.java), [ResultRoutingService.java](../../../apps/api/src/main/java/com/aurevia/exchange/result/ResultRoutingService.java)).

## Things to know

- **The conformance fixtures are synthetic and not wired into a running controller.** `ConformanceLedger`, `PartnerReportProcessor`, the wire adapters and `ConformanceFixtures` are plain classes with no Spring component annotation and no database; they model receiver rules (dedup, stale revision holding, bounded retry, dead-letter and review reopening) for fixtures and unit tests only ([ConformanceLedger.java](../../../apps/api/src/main/java/com/aurevia/exchange/conformance/ConformanceLedger.java), [PartnerReportProcessor.java](../../../apps/api/src/main/java/com/aurevia/exchange/conformance/PartnerReportProcessor.java)).
- **The HL7 duplicate ledger is process-local.** `Hl7Exchange` keeps consumed control ids in a `ConcurrentHashMap`-backed set, so a restart loses it; a corrected retry of a rejected message is accepted because only a message that produced a command consumes its id ([Hl7Exchange.java](../../../apps/api/src/main/java/com/aurevia/exchange/hl7/Hl7Exchange.java)). Durable replay protection belongs to the exchange store.
- **One reconciliation decision is held in memory and its queue status cannot advance.** `ReconciliationService` keeps decisions in a `ConcurrentHashMap` and rejects a second resolution, but migration V22 grants the runtime role only SELECT and INSERT on `xch04_reconciliation`; setting durable status needs a follow-up storage story with a bounded UPDATE grant. The read endpoint only keys by tenant and entry id and performs no role check, unlike the resolve command ([ReconciliationService.java](../../../apps/api/src/main/java/com/aurevia/exchange/result/ReconciliationService.java), [V22__result_routing.sql](../../../db/migrations/V22__result_routing.sql)).
- **A delivery receipt can never close a clinical task.** XCH-02 keeps workflow, transmission and clinical review in three independent channels; the transmission branch copies the clinical channel unchanged, the V20 update guard allows exactly one channel to change per command, and clinical review is clinician-only ([ExchangeStateMachine.java](../../../apps/api/src/main/java/com/aurevia/exchange/task/ExchangeStateMachine.java), [V20__exchange_task_states.sql](../../../db/migrations/V20__exchange_task_states.sql)).
- **Sharing an order grants no general chart access.** The receiver gets only the exchange projection and must bind a locally verified patient by MRN and issuer with attestation; mismatches are a 403 and inaccessible rows are concealed as 404 ([WorkItemView.java](../../../apps/api/src/main/java/com/aurevia/exchange/order/WorkItemView.java), [OrderService.java](../../../apps/api/src/main/java/com/aurevia/exchange/order/OrderService.java)).
- **Clinical acknowledgment is deliberately narrow.** In XCH-05 a verifier cannot acknowledge, a clinician acknowledgment needs a prior verbatim read-back, and neither a delivery fact nor a patient release satisfies it; escalation channels come from effective configuration, including a site-approved backup channel and recipient ([CriticalResultService.java](../../../apps/api/src/main/java/com/aurevia/exchange/critical/CriticalResultService.java), [CriticalActions.java](../../../apps/api/src/main/java/com/aurevia/exchange/critical/CriticalActions.java)).
- **Immutable clinical history is appended, never rewritten.** XCH-04 corrections add a new revision and an unreviewed task while preserving the acknowledged prior revision and attestation, and a retry with the same key but a divergent payload returns 409; XCH-06 withdrawal and correction supersede rather than erase ([ResultRoutingService.java](../../../apps/api/src/main/java/com/aurevia/exchange/result/ResultRoutingService.java), [ReleaseService.java](../../../apps/api/src/main/java/com/aurevia/exchange/release/ReleaseService.java)).
- **Missing trend policy reveals data rather than hiding it.** When no comparability rule is established the analyzer returns every observation in the visible exclusion list with a reason, and qualified or non-numeric values stay visible but are never compared; it produces no clinical interpretation ([TrendAnalyzer.java](../../../apps/api/src/main/java/com/aurevia/exchange/trend/TrendAnalyzer.java), [TrendService.java](../../../apps/api/src/main/java/com/aurevia/exchange/trend/TrendService.java)).
- **Action policies are local to each slice.** XCH-02, XCH-03, XCH-04, XCH-05, XCH-06 and XCH-07 each own a bounded policy rather than widening the shared action policy; consolidating them is follow-on work once the exchange module settles ([ExchangeActionPolicy.java](../../../apps/api/src/main/java/com/aurevia/exchange/task/ExchangeActionPolicy.java), [ExchangeResponseActionPolicy.java](../../../apps/api/src/main/java/com/aurevia/exchange/response/ExchangeResponseActionPolicy.java)).
- **Tests for five subpackages live outside the package test tree.** The critical, release, task, response and trend production packages have no dedicated test folder under `com.aurevia.exchange`; their unit, HTTP and isolation tests are under `com.aurevia.it.exchangeresult`, `it.exchangerelease`, `it.exchangetask`, `it.exchangetrend` and `it.exchange` ([CriticalResultControllerHttpTest.java](../../../apps/api/src/test/java/com/aurevia/it/exchangeresult/CriticalResultControllerHttpTest.java), [ExchangeTaskIsolationTest.java](../../../apps/api/src/test/java/com/aurevia/it/exchangetask/ExchangeTaskIsolationTest.java)).
