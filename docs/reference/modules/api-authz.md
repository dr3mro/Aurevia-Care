# Module guide: authorization (`com.aurevia.authz`)

The `authz` package is the authorization and sensitive-access boundary of the API: it owns the bounded role/action matrices, the append-only role-change history, the time-limited emergency and platform-support access controls, and the specialty permission and human-attestation routes. Each protected operation re-reads membership, roles, site approval and facility scope inside a tenant-guarded transaction, derives the actor and organization from the authenticated context, and records an append-only OPS-02 audit row on success and on authorization denial ([AccessController.java](../../../apps/api/src/main/java/com/aurevia/authz/access/AccessController.java), [RoleHistoryService.java](../../../apps/api/src/main/java/com/aurevia/authz/history/RoleHistoryService.java), [SpecialtyAttestationService.java](../../../apps/api/src/main/java/com/aurevia/authz/specialty/SpecialtyAttestationService.java)).

Primary requirement IAM-01: deny access without active membership, the required action permission and domain authorization, with facility scope further narrowing access; the tenant is the organization ([PROJECT_V1_SPEC.md](../../../.opencode/config/PROJECT_V1_SPEC.md)). IAM-02 supplies the role-change ledger, IAM-06 the break-glass and support controls, PRD-06 the human clinical attestation, OPS-02 the durable audit and ARC-02 the isolation rule; the generated X-04 command contract binds one specialty action to this package ([contracts/openapi/README.md](../../../contracts/openapi/README.md), [maintainer.md](../maintainer.md)).

## Entry points

The package declares three `@RestController` families and no scheduled job and no event handler. Its remaining entry points are library calls made by other packages and by its own services. The "who" column names the role, re-derived server-side on each request, that may invoke each route; a role value in a request body or JSON command never grants authority. All routes appear in the staff API contract ([openapi.yaml](../../../contracts/openapi.yaml)); only the specialty attestation command is additionally cataloged for the generated client ([manifest.json](../../../contracts/openapi/generated/manifest.json), [client.ts](../../../contracts/openapi/generated/client.ts)).

## Events published or consumed

**None.** No class in `com.aurevia.authz` publishes or consumes a domain event; there is no `@EventListener`, message sender or outbox call in its sources. Audit rows are synchronous appends in the caller's transaction, and `AccessDecision` is a returned outcome, not a durable event. Durable event delivery is the separate `events` package and its V55 outbox ([EmergencyAccessService.java](../../../apps/api/src/main/java/com/aurevia/authz/access/EmergencyAccessService.java), [SpecialtyAttestationService.java](../../../apps/api/src/main/java/com/aurevia/authz/specialty/SpecialtyAttestationService.java), [V55__durable_event_outbox.sql](../../../db/migrations/V55__durable_event_outbox.sql)).

## Things to know

- **Only one authz route is cataloged in the generated command contract.** The catalog binds `attestClinicalDecision` to `SPECIALTY_ATTEST` and `SpecialtyActions`; the access and role-history routes are in the hand-authored staff OpenAPI document but not in the generated catalog. No production route calls `CommandAuthorization` yet: every authz route enforces authorization directly in its own service against fresh database folds, so the catalog ↔ client drift gate proves nothing about those routes ([manifest.json](../../../contracts/openapi/generated/manifest.json), [CommandCatalog.java](../../../apps/api/src/main/java/com/aurevia/api/authorization/CommandCatalog.java), [contracts/openapi/README.md](../../../contracts/openapi/README.md)).
- **Authorization denials are committed before they are thrown.** The services record a DENIED audit row inside the guarded transaction and carry the exception out in an `AtomicReference` or `Sink`, so the audit survives; the client receives a machine-readable error. Input-validation and not-found failures can still throw directly without an audit append ([EmergencyAccessService.java](../../../apps/api/src/main/java/com/aurevia/authz/access/EmergencyAccessService.java), [SpecialtyAttestationService.java](../../../apps/api/src/main/java/com/aurevia/authz/specialty/SpecialtyAttestationService.java)).
- **Separation of duties is enforced twice.** The service checks the reviewer or approver role and the SQL guards reject self-review and self-approval (`subject <> reviewer`, `subject <> approver`); V11 and V88 add equivalent check constraints, so bypassing the service still cannot create the row ([AccessRepository.java](../../../apps/api/src/main/java/com/aurevia/authz/access/AccessRepository.java), [V11__emergency_and_support_access.sql](../../../db/migrations/V11__emergency_and_support_access.sql), [V88__access_review.sql](../../../db/migrations/V88__access_review.sql)).
- **Emergency access is gated and non-stacking.** A grant needs an approved `access.emergency.enabled` configuration entry, a facility in the active organization and scope, and no unexpired unrevoked grant for the subject; the alert and the privacy-auditor review row are opened in the same transaction as the grant ([EmergencyAccessService.java](../../../apps/api/src/main/java/com/aurevia/authz/access/EmergencyAccessService.java), [V5__tenant_configuration.sql](../../../db/migrations/V5__tenant_configuration.sql)).
- **Facility scope is a database fold with deliberate exceptions.** A member with recorded facility assignments is confined to them, a member without assignments keeps organization-wide behaviour, and `tenant_admin` and `privacy_auditor` are exempt; the repository only maps that answer and never invents a scope ([V93__membership_facility_scope.sql](../../../db/migrations/V93__membership_facility_scope.sql), [AccessRepository.java](../../../apps/api/src/main/java/com/aurevia/authz/access/AccessRepository.java)).
- **History is append-only in memory as well as in storage.** `RoleHistory` freezes its change list on construction and on access; V71 and V46 reject update, delete and truncate for every role, including the migration owner ([RoleHistory.java](../../../apps/api/src/main/java/com/aurevia/authz/history/RoleHistory.java), [V71__role_change_history.sql](../../../db/migrations/V71__role_change_history.sql), [V46__specialty_attestation.sql](../../../db/migrations/V46__specialty_attestation.sql)).
- **The clinical decision is derived, never supplied.** A specialty attestation stores the `DIAGNOSIS`, `TREATMENT` or `RELEASE` class derived by `SpecialtyActions.decisionFor` from the attested action; the client cannot send a decision, and PRD-06 remains a human act ([SpecialtyActions.java](../../../apps/api/src/main/java/com/aurevia/authz/specialty/SpecialtyActions.java), [SpecialtyDecision.java](../../../apps/api/src/main/java/com/aurevia/authz/specialty/SpecialtyDecision.java)).
- **A legacy review body is still accepted.** `ReviewRequest` has a one-argument constructor so a `{"note": ...}` JSON body without `outcome` deserializes and is closed as `recorded`; an unknown explicit outcome is refused before any database work ([AccessContracts.java](../../../apps/api/src/main/java/com/aurevia/authz/access/AccessContracts.java), [AccessRules.java](../../../apps/api/src/main/java/com/aurevia/authz/access/AccessRules.java)).
- **Reads and writes are concealed rather than explained.** A foreign-tenant or unknown subject returns 404 on the role-history route, and a cross-tenant grant or incident is invisible under forced RLS; repeated role and membership folds make a revocation effective on the very next protected request ([RoleHistoryService.java](../../../apps/api/src/main/java/com/aurevia/authz/history/RoleHistoryService.java), [V2__rls_roles_policies.sql](../../../db/migrations/V2__rls_roles_policies.sql)).
