# Running the agent team in GitHub Actions

The agent team runs as the swarm: OpenCode workers on GitHub-hosted runners, coordinated only through `tasks/`, pull requests and GitHub issues. [SWARM.md](SWARM.md) describes the whole flow; this page covers the image, the setup and the safeguards. The earlier issue-label team workflow (`story` label, `/oc` comments) has been retired.

## Files

- `.github/agent-image/Dockerfile` and `.github/workflows/agent-image.yml` build `ghcr.io/<owner>/<repo>-agent:latest` when the Dockerfile changes, monthly, or on demand; `swarm-images.yml` adds one layer per slot.
- `swarm.yml`, `swarm-worker.yml` and `swarm-integrator.yml` plan, work, publish and integrate. `fix-pr-gate.yml` validates repair pull requests.
- `swarm-watchdog.yml`, `swarm-pr-flow.yml`, `swarm-issue-monitor.yml`, `daily-notes.yml`, `daily-audit.yml`, `daily-qa.yml` and `daily-devsecops.yml` keep it running without a person: failure and stall issues, issue hand-off to workers, the daily notes, the daily audit and the daily QA and DevSecOps reviews.
- `pr-rebase.yml` refreshes a newly opened pull request onto `main` before its gate runs. `dependabot-auto-merge.yml` merges low-risk Dependabot updates. `release-app-image.yml` publishes the application image from an authorized version tag after the green-main check; `delivery.yml` publishes the bootstrap image and GitHub release.
- `scripts/agent-run.sh` holds the agent steps and `scripts/swarm.py` the trusted logic; both are unit tested with fake `opencode` and `gh` under `scripts/tests`.
- `.opencode/opencode.ci.json` is the unattended permission profile, generated by `scripts/gen-opencode.py`.

## Setup

Follow the setup in [SWARM.md](SWARM.md#setup): run **Agent image** once, save `OPENCODE_API_KEY_<n>` per slot (or one `OPENCODE_API_KEY`), allow Actions to create pull requests, and save `SWARM_TOKEN`. The optional repository variable `SWARM_ALLOW_PROTECTED=1` is a kill switch that lets protected-file pull requests merge after the full gate with a non-blocking `protected-change` oversight issue ([Kill switch](SWARM.md#kill-switch)); leave it unset to keep the default person-review rule. Free models change and some retain prompts, so check each model's privacy note and use synthetic data only.

## What runs when

| Schedule (UTC) | Workflow |
|---|---|
| Every hour at :07 | `swarm.yml` safety-net wave, when work is waiting and no wave runs |
| Every 15 minutes, and when a watched workflow finishes | `swarm-watchdog.yml`: failure and stall issues, closing finished ones, and starting a wave when none has run for 30 minutes while work waits |
| 05:10 daily | `daily-notes.yml`: reconcile yesterday's worker notes |
| 06:00 (summer) or 07:00 (winter) daily | `swarm-issue-monitor.yml`: 2:00 AM New York pass over issues with no progress for 24 hours |
| Every 20 minutes, and when Delivery finishes | `swarm-pr-flow.yml`: moves every open swarm pull request to its next step (debugger, fix worker, Delivery re-run, integrator) |
| Every 10 minutes, and on every new, reopened or labeled issue | `swarm-issue-monitor.yml` (mode now): hands unassigned issues to a worker after five minutes |
| 07:17 daily | `daily-audit.yml` |
| 08:43 daily | `daily-qa.yml`: QA review, tasks and suggestions for agents and workflows |
| 09:29 daily | `daily-devsecops.yml`: DevSecOps review, tasks and suggestions |
| Every 6 hours at :23 | `swarm-strategist.yml`: suggests tasks, task order and workflow changes |
| 47 past every hour | `swarm-debugger.yml` (safety net; normally dispatched at the first failure; up to four pull requests debugged side by side) |
| 04:17 on the 1st | `agent-image.yml` refresh |

Everything else is event driven: a push to `tasks/`, a finished wave, a pull request event or a manual dispatch.

## Safeguards

- Agent steps have no write token. Pushing, pull request creation, labels and issues happen in separate trusted jobs that run the scripts from `main`. The agent profile denies `gh`, `git push`, `git tag`, `curl`, `wget`, `ssh` and `docker`.
- Issues and comments are read only when written by the repository's automation or by an owner, member or collaborator; their text reaches agents as untrusted notes.
- Reviewers and the triage, audit and notes workers run read-only. Anything they write is validated before it lands: bounded text, safe scopes, no workflow, script or agent files, and the docs and secret checks Delivery runs. The `SWARM_ALLOW_PROTECTED` repository variable is the only exception to the protected-file rule: with it on, a protected-file pull request merges after the full gate and opens a non-blocking `protected-change` oversight issue ([Kill switch](SWARM.md#kill-switch)); the full gate, tracker rule and file-count limit remain.
- `Delivery gate` is a required check on `main` under the `PROTECT` ruleset. The integrator's direct push is separately authorized; the required check is never removed to accommodate it.
- Use synthetic data only. Free models are not suitable for real patient data.
