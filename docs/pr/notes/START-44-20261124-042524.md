## Findings

- **Brief incomplete, not wrong in substance.** The worker brief listed no specialists and named only the `delivery` skill, while the story and AGENTS.md require the plan→code/coverage/security loop and the backend skill's standalone SpotBugs command. I followed AGENTS.md and the story, loaded `aurevia-senior-backend`, and recorded the discrepancy here as instructed by the prompt.
- **Scope-file provenance.** The task flagged `AuditNegativePathsTest.java` as "absent in this snapshot … need confirmation as planned paths or stale references". I confirmed it is a genuinely new file: `git status --short` shows `??`, `git log --oneline -1 -- <path>` is empty and `git cat-file -e HEAD:<path>` fails. The plan reviewer initially read the file I had just created and asked for this check; it is resolved.
- **Derived error code.** `parseFilter` builds `INVALID_` + `name.toUpperCase(Locale.ROOT)`; for `resourceType` this is `INVALID_RESOURCETYPE` (no underscore). The test asserts that exact code.
- **Audit append field.** `AuditService` records the **action** filter as the appended event's resourceId (`actionFilter == null ? "ALL" : actionFilter`), not the resource-type filter. My first red run caught an incorrect `"FACILITY"` expectation; the assertion now expects `ALL`.
- **Story criteria not applicable to this package.** A stale-version check (no version or optimistic-lock field on an append-only audit event), an idempotency-key replay (a read query has no idempotency key or ledger), and a by-identifier cross-tenant `NOT_FOUND` lookup (the API exposes a cursor page, not a by-id GET) have no corresponding behavior in `audit`. I did not fabricate tests or a failing test for them. The related real behavior — cross-tenant rows concealed under forced RLS — is already asserted by `AuditQueryTest.tenantAdminReadsOnlyItsOwnAuditTrail` (`seed-b` absent from the ORG_A response).
- **No real bug found.** I found no case where another tenant's audit record is readable through this API, so no failing test was added and the pull request stays green.
- **Tooling false positives.** The Python tooling failures and the `worker-check.sh` stop were reproduced on a tree with my two files removed, and are the documented skip-worktree/sandbox artifacts; no gate was weakened to make them pass.

## Lessons for workers

- Derive error codes from the production expression before asserting them: `"resourceType".toUpperCase(Locale.ROOT)` yields `RESOURCETYPE`, so the code is `INVALID_RESOURCETYPE`.
- Read the append arguments at the call site: `AuditService` stamps the action filter as the audit event's resourceId, not the resource-type filter; a plausible-looking guess fails the red run.
- When a task marks its scope path "absent or stale", prove provenance with `git status`, `git log -1 -- <path>` and `git cat-file -e HEAD:<path>` before creating the file, so a genuinely new file is not mistaken for an overwrite.
- Before attributing a failing generic tooling suite to your change, reproduce it with your new files moved aside; the cloud image's skip-worktree `opencode.json` and sandbox fixtures fail on the baseline too.
- A mocked repository returning an empty list cannot prove row-level-security concealment. Name empty-result tests after the contract they assert and cite the real-PostgreSQL integration test for tenant isolation.
