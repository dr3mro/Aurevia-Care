# READY-43 — Production profile that cannot start in an unsafe state (WEB-01, WEB-05)

## Summary

Added a hardened `production` Spring profile and a startup fail-closed check. A production process now refuses to start if it also enables `synthetic-auth`, if `AUREVIA_DB_PASSWORD` is blank, or if the datasource URL contains neither `sslmode=require` nor `verify-full`. Failure messages never include the password. Scoped to the four paths declared by the story; synthetic fixtures only; no migration, contract or tracker changes.

## Affected requirements

- **WEB-01** — TLS/edge transport: production profile honours forwarded headers from the TLS-terminating edge and rejects a non-TLS datasource URL.
- **WEB-05** — Lifecycle: graceful shutdown with a 30-second drain, Tomcat connection timeout and bounded request-body swallow, and fail-closed startup when required configuration is absent.
- **ARC-01** — Listed by the story; no domain-key or data-model change in this scope.

## Risk class

Cross-boundary / defensive security (configuration plus startup validation). No patient data, no signed data, no cross-organization sharing, no prescribing or critical results.

## Review owner

Senior Spring Security and Senior Java/Spring Boot (both simulated bounded reviews, see Findings). Integrator owns the full gate and database/integration tests.

## Data changes

None. No Flyway migration, backfill, lock or volume impact; no rollback/forward-fix needed. Configuration is read from the environment at startup; unsetting `SPRING_PROFILES_ACTIVE=production` reverts to the base profile.

## Authorization boundaries and audit events

None. The change adds no request handling and no audit events. It prevents an unsafe process from starting; it does not alter tenant, role or patient-link scope.

## Migration and rollout considerations

No migration. Deploy with `SPRING_PROFILES_ACTIVE=production`, a TLS datasource URL, a non-blank `AUREVIA_DB_PASSWORD` and OIDC settings. The process fails before the context completes if any invariant is violated. Rollout is a configuration change; rollback is removal of the profile variable. Forwarded headers are trusted from the TLS-terminating edge — the deployment must prevent direct callers from injecting `X-Forwarded-*`.

## Findings

- **Initial gate failures were mine and fixed:** the first test fixtures used a literal `jdbc:postgresql` URL, which `test_fast_tier.py` misclassified as a PostgreSQL test requiring `@Tag("integration")`; and `PASSWORD = "..."` tripped `check-secrets.py`. Fixed by using a synthetic JDBC scheme (`jdbc:synthetic`) in the unit fixture and a `// synthetic-ok` marker on the same line as the fixed non-credential fixture. Both gates now pass.
- **Simulated security/backend finding — substring match is not a URL parse (Medium):** a URL such as `?sslmode=disable&note=sslmode=require` would pass. **Not changed:** the story explicitly defines the gate as "the datasource URL does not contain `sslmode=require` or `verify-full`"; a stricter parser would deviate from the stated acceptance criteria and add uncovered branches. Recorded as an owner risk-acceptance / follow-up item.
- **Simulated security finding — `sslmode=require` does not authenticate the server (Medium policy):** it encrypts without certificate/hostname verification. The story explicitly accepts either token; `verify-full` is preferable. Owner risk acceptance needed for production use of `require`.
- **Simulated backend finding — `@PostConstruct` ordering (Medium):** the reviewer claimed the connector can bind before validation. The story mandates a `@Component` active under `production`, so an `EnvironmentPostProcessor` would not satisfy it. A `@PostConstruct` throw aborts `finishBeanFactoryInitialization`, so `finishRefresh()` (web-server start) never runs and the context fails to start. Javadoc wording was tightened to claim only context-start failure.
- **Simulated backend finding — password bound from the env var rather than `spring.datasource.password` (Low):** the story explicitly names `AUREVIA_DB_PASSWORD`, and `application.yml` already maps that variable to the datasource password. Kept as specified.
- **Simulated backend/security finding — forwarded headers trusted without a proxy allowlist (Low):** `server.forward-headers-strategy: framework` is explicitly required by the story. Documented the edge-trust assumption in `apps/api/README.md`; deployment-level allowlist is out of scope.
- **Optional, not adopted:** the test-engineer suggested parameterising the password-leak assertion over all three failure paths. The messages are compile-time constants and the three exact-message assertions already prove no interpolation.

## Lessons for workers

- A literal `jdbc:postgresql` anywhere in a test file trips `test_fast_tier.py`'s DB-test tag rule even without `@SpringBootTest`; use a synthetic driver scheme for pure unit fixtures.
- `check-secrets.py` flags `PASSWORD = "<8+ non-space chars>"`; add the documented `// synthetic-ok` marker **on the same line** for a fixed non-credential fixture.
- `ApplicationContextRunner.withPropertyValues("spring.profiles.active=...")` activates `@Profile` beans; an exception from `@PostConstruct` is captured in `context.getStartupFailure()` with the `IllegalStateException` in the cause chain.
- `YamlPropertySourceLoader` parses bare numerics as `Integer`; assert with `String.valueOf(...)`.
- In a cloud worker, `git ls-files -v opencode.json` showing `S` means the worktree holds the CI profile; `check-pack.py`/`gen-opencode.py --check` failures there are measurement artifacts — verify with `git show HEAD:opencode.json` and never regenerate or commit that file.
- When a reviewer proposes stronger semantics than the story's literal acceptance criteria, record the conflict as a risk-acceptance finding rather than silently deviating; the integrator and owner own the trade-off.
