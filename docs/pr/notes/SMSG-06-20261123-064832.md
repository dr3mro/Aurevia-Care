## Plan (before coding)

New business-domain package `com.aurevia.staffmsg.directory`:

1. `DirectoryPolicy` (pure): `allowsCrossFacility(boolean)` returns the tenant flag;
   `requireSameOrganization(actorOrg, targetOrg)` throws `ApiException(403,
   CROSS_ORGANIZATION_MESSAGING_DISABLED, ...)` unless the two tenant ids are equal
   (null-safe, fail closed). Cross-org stays refused because SMSG-01 is unapproved.
2. `DirectoryContract`: immutable view records with `from(...)` mappers reused from
   existing domain types — `FacilityEntry` <- `Facility`, `UnitEntry` <- `CareUnit`,
   `StaffEntry` (staff + facility code) <- `StaffMember` plus the browsed facility;
   `FacilityDirectory` and `StaffDirectory` wrappers.
3. `StaffDirectoryService` (`@Service`): injects `StaffRepository`, `FacilityRepository`,
   `TransactionTemplate`. `facilities()` and `staff(facilityCode)` read only inside
   `transactions.execute`, derive the org from `TenantContext.current()` (fail closed 403
   when unbound), resolve the facility by tenant-local code (404 when absent), and hide
   staff with empty roles or non-active status.
4. `CrossFacilityMessagingGuard` (`@Component`, injectable for future instant/mail callers):
   injects `DirectoryPolicy`, `AccessRepository`, `StaffDirectoryService`, `ActiveStaffGuard`
   and `TransactionTemplate`. `requireCrossFacilityAllowed(facilityCode)` first requires a
   bound `TenantContext` (403 when absent), then inside one `transactions.execute` re-checks
   actor membership + at least one active role, resolves the destination facility through
   the tenant-scoped service and asserts same-organization from that DB-derived record.
   The V93 `is_facility_out_of_scope(subject, code)` fold then decides whether a cross-facility
   decision is needed: only for an out-of-assignment destination does the guard require the
   approved tenant flag (`AccessRules.isEnabled(access.effectiveConfig(key))`, missing config
   is false), refusing with `CROSS_FACILITY_MESSAGING_DISABLED` when it is absent. No org,
   role or facility identity comes from a request field; the destination org is DB-derived.
5. HTTP-level test through a thin adapter in the mirrored test package, service injected by
   constructor (production `@RestController` deliberately deferred — see "Brief correction").

Revised after plan/security review:

- `ActiveStaffGuard` (`@Component`, in-package): single rule "active membership AND at least
  one active role", injected into both the service and the guard, so it is defined once.
- `DirectoryPolicy.requireSameOrganization` semantics: **both arguments must be non-null**;
  a null on either side fails closed with the same 403. Implemented as
  `actor == null || target == null || !actor.equals(target)`.
- Guard calls `policy.allowsCrossFacility(AccessRules.isEnabled(effectiveConfig(key)))` so the

  `check-wiring.py`'s `unreferenced-service` rule stays clean without a production controller

  only uses `findFacility`.

The brief asks for a production thin `@RestController` plus an HTTP-level test but also
forbids editing `contracts/`. These conflict: `apps/api/src/test/java/com/aurevia/it/contract/OpenApiRouteParityTest.java#everyControllerRouteIsDocumentedOrBaselined`

`OpenApiRouteCoverage.Report.passed()`); `scripts/worker-check.sh:51` runs that suite, and the
baseline run of `-Dtest=OpenApiRouteParityTest -Dgroups=integration test` exited 0. Both
contract files are outside this task's scope, so a production controller would make a required
gate red. Per the brief ("if the brief is wrong or incomplete, say so in the notes and carry
on from the story and AGENTS.md"), the HTTP-level test uses a thin nested `@RestController`
adapter in the mirrored test package (the established `SecurityFilterChainHttpTest` pattern;
`/api/v1/probe` is also absent from `contracts/` and parity still passes). The production
controller, its OpenAPI entry and the regenerated client are requested in `task-requests`.

### Security design fixes (spring-security review, before coding)

- Added actor membership + active-role re-check in the guard; the V93 fold alone returns
  `false` (in scope) for a subject with no membership and exempts oversight roles, so it is
  not an authorization check.
- Wrapped the config read and the fold in the guard's own `TransactionTemplate.execute`;
  without a bound `app.current_org` RLS hides the rows and the negated fold would allow.
- Destination organization is derived from the tenant-scoped `Facility` record rather than
  a caller-supplied string; a foreign facility is invisible under RLS and fails closed.
- Read the policy flag with `AccessRepository.effectiveConfig(key)` +
  `AccessRules.isEnabled`, not `ConfigurationService.get(key)` (whose `CONFIG_READ`
  permission is admin-only and which appends its own audit). Denial audit is deferred with
  the rest of the guard-to-service wiring; recorded under Findings.

## Findings

- **Brief correction:** the brief requires a production thin controller and an HTTP test but
  forbids `contracts/`. `OpenApiRouteParityTest#everyControllerRouteIsDocumentedOrBaselined`
  (run by `worker-check.sh:51`) fails on any new live Spring route absent from
  `contracts/openapi.yaml` / `missing-routes.txt`, so a production controller would make a
  required gate red from a worker that cannot edit those files. Used a test-local nested
  adapter for the HTTP-level proof and requested the production controller, OpenAPI entry and
  regenerated client as a merge-blocking task below. No in-Tenant end-to-end send is claimed.
- No migration, table, RLS policy, dependency, workflow, script, tracker or `.opencode` file
  was changed. All fixtures are synthetic subjects and documented-pattern UUIDs; no PHI,
  credential or real identifier appears in code, tests, logs or notes.
- Guard-to-service wiring and denial audit are deferred: until a follow-up calls the guard
  from the instant/mail send paths, no production request reaches the cross-organization
  refusal or the cross-facility allow decision. This is a declared merge-blocking task, not
  a claim of done end to end.
- `MessagingStore` has no list-by-facility method, so a live units listing is not built;
  `UnitEntry.from(CareUnit)` is supplied and tested for the follow-up story.
- The V93 fold also returns false for legacy members with no facility assignment and for
  `tenant_admin` / `privacy_auditor`, so those actors cross facilities without the tenant
  flag. That follows the app-wide IAM-01 scope rule; an absolute tenant-wide switch would
  need a different scope primitive outside this story's scope.
- `facilities()` and `staff(facilityCode)` are tenant-scoped by forced RLS and gated by
  active staff, but they do not apply the V93 facility-scope fold: a facility-assigned actor
  can browse staff at a facility they cannot message. Enforcement is at send time in the
  guard; confirm this read-vs-send distinction matches MSG-02 intent in the wiring story.
- The story's premise is stale: `docs/decisions/staff-messaging/README.md` marks staff
  messaging *proposed, not approved*, and SMSG-01's cross-organization connection is disabled;
  the implementation therefore fails closed on every cross-organization attempt, as directed.
- `openapi.json`/`opencode.json` skip-worktree and git/gh sandbox test failures are
  environmental; confirm once, do not regenerate protected files on a later pass.

## Lessons for workers

- Before adding a controller in a worker, check `OpenApiRouteParityTest` and the scope: a live
  `@RestController` mapping without a same-story OpenAPI entry fails the integration gate.
  A nested test-only `@RestController` gives an HTTP-level proof without registering a route.
- `check-wiring.py` flags any `*Service` with no other `src/main` caller; give a new service a
  real production caller (here the guard calls `StaffDirectoryService.findFacility`) instead
  of adding a baseline entry.
- SpotBugs' central `EI_EXPOSE_REP2` exclusion only covers role suffixes
  (`Service|Repository|Controller|Store|Interceptor|Guard|...`); name a Spring collaborator
  holder with one of those suffixes, because the exclude file is outside a worker's scope.
- The V93 facility-scope fold is not an authorization check: it returns false for a subject
  with no membership and exempts oversight roles. Pair it with an explicit active-membership
  and active-role gate, and always run the reads inside the tenant-guarded `TransactionTemplate`.
- Mockito in this image cannot mock `final` classes; leave injectable collaborators non-final.
