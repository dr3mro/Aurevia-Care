# ORDER-04 — API: order status to result, with cancel and amend rules

## Summary

Added a pure Java domain kernel in `com.aurevia.orderentry.status` that exposes exactly
one status per clinical order (`draft`, `placed`, `delivered`, `accepted`, `collected_or_scheduled`,
`resulted`, `cancelled`) with an append-only fact trail. Cancel requires a reason: before partner
acceptance it moves the order straight to `cancelled`; after acceptance it records a cancel request
to the partner and keeps the status until the partner responds (confirm → cancelled, deny → unchanged).
Amend creates a linked new revision and emits a partner-notification fact. Linking a result moves the
order to `resulted` and projects the result back onto the status, reusing the existing
`exchange.result.ResultModel.ResultKind`; a critical link only marks the separate XCH-05 workflow and
never advances verification or acknowledgement here. Workflow milestones are ranked and cannot go
backwards. All commands take the active tenant, subject and fresh roles (clinician ordering privilege).
Synthetic identifiers only; no new dependency and no file outside `scope`.

Specialists were consulted through their loaded `SKILL.md` guidance (advisory); no separate subagent
delegation was available in this swarm-worker run. Applied senior-backend rules (final class, no
`*Service`/`InMemory*` name, immutable records, SpotBugs clean), test-engineer rules (every branch
mapped to a test, deterministic clock) and the physician-reviewer critical-result checklist (critical
acknowledgement stays in XCH-05 — simulated review, no human sign-off).

## Affected requirements

LAB-01, LAB-02, RAD-01, XCH-03 (result link also reuses the XCH-04 disposition type; critical
handoff references XCH-05 without changing it).

## Risk class

Cross-boundary clinical order workflow (docs/WORKFLOW.md). Cancel-after-acceptance and critical-result
linking touch partner and clinical-safety boundaries; negative/failure tests are included, but the
review is simulated only — there is no real clinician or unit pilot acceptance in this story.

## Review owner

senior-backend (domain kernel), test-engineer (test matrix), physician-reviewer (critical-result
safety). Loaded as advisory skills above.

## Data changes

No migration, backfill or lock/volume impact: the task scope allows only the `orderentry/status`
main and test packages. The kernel keeps its projections in memory exactly as the predecessor kernels
`OrderPlacementService` and `OrderDeliveryCoordinator` do; the integrator/Delivery wire persistence,
HTTP and OpenAPI in a later slice. No schema or table was added, so there is no RLS/FORCE RLS change.

## Authorization boundaries and audit events

Every mutating command calls `requireScope` (active org from context, authenticated subject, fresh
`clinician` role) and keys all state by organization + opaque order id using a unit separator, so one
tenant cannot observe another. Event facts carry only opaque ids, a non-sensitive reason/detail and
server timestamps — no PHI, credentials or clinical payload. The append-only status trail is a domain
fact ledger; durable audit-event wiring is deferred with the rest of the persistence slice.

## Migration and rollout considerations

None in scope. No feature flag or schema needed; new packages are additive and unreferenced by other
main classes, so there is no rollout or rollback impact until the wiring story consumes the kernel.

## Clinical and architecture review

Physician-reviewer guidance (simulated): a critical result is linked as a fact and flagged, but no
verification, escalation, read-back, acknowledgement or patient release is performed here — those stay
in XCH-05. Delivery/patient release is not treated as clinical acknowledgement. Reused the existing
`ResultKind` disposition rather than inventing a second critical vocabulary. Architecturally the
cancel request after acceptance is a pending fact on the same status (not an eighth status), which
keeps the required seven-status vocabulary while still requiring recipient response per XCH-03.
No real clinician or unit pilot acceptance was available; this is simulated review only.

## Findings

1. Scope: this story owns only the `orderentry/status` main/test packages. As with ORDER-01..03, the
   domain kernel has no migration, `Jdbc*` store, controller, HTTP integration test or OpenAPI entry;
   those are intentionally deferred to the integration story. `scripts/check-wiring.py` reports no new
   finding because the class is a plain final kernel (not `*Service` and not `InMemory*`). Delivery must
   wire it before calling the end-to-end acceptance met.
2. Pre-existing environment artifact (not caused by this change): `check-pack.py` exits 1 with
   `opencode.json is stale` and the 5 `test_check_pack` cases fail. MEMORY.md OPS-CW-003-01 records that
   cloud workers see the CI `opencode.json` under `skip-worktree`; this is a measurement artifact, not
   HEAD truth. No agent config or `opencode.json` was edited here.
3. `scripts/python-coverage.sh` warns that `coverage` is not installed in this image; its only failures
   are the same `test_check_pack` cases. Python-tooling coverage could not be measured here.
4. Initial JaCoCo run showed `OrderStatus.rank()` and `StatusEventKind.wire()` at 0% because the kernel
   reads the backing fields directly from inside the same class and the compiler inlines that access;
   a direct accessor assertion was added to reach 100% (no production change).

## Lessons for workers

- When an enum has a private field plus a public accessor, calls from inside the same class compile to
  a direct field read and leave the accessor uncovered — add a direct accessor assertion (or call the
  accessor in production) before claiming 100% JaCoCo.
- In cloud workers, treat `check-pack.py` / `test_check_pack` failures as the documented skip-worktree
  CI-profile artifact; verify with `git show HEAD:opencode.json` rather than editing agent config.
- A test helper that advances an order must use the view's own order id; hard-coding one order id makes
  multi-order tests advance the wrong aggregate and fail with a misleading "cannot go backwards".
