## Findings

- `docs/SWARM.md` was internally inconsistent and stale against code: it said 15 changed files in the Flow table (line 14) but 30 in the Rules section; code enforces `MAX_PR_FILES = 30` (`scripts/swarm.py:27`, guard at `:2298`). Task attempts were documented as 3, code is `MAX_ATTEMPTS = 5` (`:29`, `:1486`).
- Repairs (`FIX-`/`DLV-`/autofix) were documented as passing the "full gate"; `gate_for()` (`:2366-2378`) and `integrate_batch()` (`:2429-2435`) run `scripts/repair-gate.sh` for them, with OWASP/SpotBugs/JaCoCo running in Delivery after the merge. Ordinary PRs use `scripts/integrator-gate.sh`. SWARM.md lines 12, 20, 22, 77–79 and 82 now distinguish the two.
- No document mentioned `SWARM_ALLOW_PROTECTED`. With it on (`"1"/"true"/"yes"/"on"`, case-insensitive — `protected_override()` at `:2258-2264`), `guard()` (`:2267-2307`) skips the protected-file block and `report_protected_merge()` (`:2233-2255`) opens one `protected-change` oversight issue per PR revision. The switch does **not** relax the full gate, the shared-tracker rule, the 30-file limit, branch-tip verification or the `SWARM_TOKEN` workflow-push requirement. It also lifts the gate-config check that otherwise still blocks a repair. Repairs already bypass `PROTECTED` without the switch (`:2275-2276`).
- Verified correct and left unchanged: worker caps (10 per wave, 20 across waves), four 45/45/45/40-minute segments and 300-minute job cap, two coverage repairs, five conflict fixes, `MAX_FIX = 3`, `MAX_REQUEUES = 2`, 3 issues/run and 5 open tasks, audit 10/25, PostgreSQL 17 in the agent image, all TEAM-ACTIONS schedule rows against workflow `cron:`, and every label name. Module `check.sh` files are protected (`PROTECTED` at `:57-59`; `scripts/tests/test_swarm.py:1017-1024`) — the stale comment at `scripts/swarm.py:47-50` says otherwise but code/tests are authoritative and scripts are out of scope.
- Defect (not fixed here, out of scope): `scripts/swarm.py:47-50` comment contradicts `PROTECTED:58` and the tests. Maintainer-owned; recorded for a future docs/comment pass.

## Lessons for workers

- For a docs-only reconciliation, read the code constants and the call sites, not just names: several stale numbers in these two docs were plausible (3 vs 5, 15 vs 30) and only the source lines settled them.
- When a specialist review reports findings, re-read the exact lines: it caught three absolute claims ("full gate", "never merged automatically") that a constant-only diff would have missed.
- In a swarm worker, `check-pack.py` failures and `test_check_pack` failures mean the worktree CI profile (`skip-worktree opencode.json`), not a stale committed file. Verify with `git show HEAD:opencode.json` vs `render(ci=False)` before touching anything.
