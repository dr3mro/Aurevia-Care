## Findings

1. **V59 is double-booked** (verified above); this is the sole reason the task is unfinished.
2. **`AUD-20261120-11` was closed without applying its expected fix.** Its own notes say the fix is outside a worker's scope and belongs to the tracker owner; TODO.md was not corrected. A future dispatch will keep hitting this collision.
3. **Design decision needed — `updateProfile` vs append-only.** `ServiceProfileStore.updateProfile` is documented as "Replace a draft with its approved, immutable copy" and `ServiceProfileService.approve` reuses the same `id` and `version`, changing `status` DRAFT→APPROVED and stamping approver fields (`ServiceProfileService.java:174-203`). The in-memory adapter is a plain `put`. A JDBC adapter therefore needs an UPDATE path (guarded so only DRAFT→APPROVED and only approval fields change), or a separate approval-fact table plus a read-time fold — the latter would require changing `ServiceProfileService`, which is outside READY-35's scope. The story's "append-only facts get no UPDATE grant" should be read as applying to the audit and work-fact tables, not the profile version row; confirm with the architect.
4. **Design decision needed — cross-aggregate reads.** Four interface methods (`hasActiveMembership`, `activeRoles`, `unitExists`, `hasConnectedChart`, `isUnitAssigned`) refer to facts owned elsewhere. Durable tables already exist for `membership`, `role_assignment`, `patient_link` / `account_chart_link` and `conversation`; there is no `care_unit` table until READY-35's sibling READY-36 (V60) and no obvious unit-assignment table. A V59-only adapter must either read those existing tables (preferred, no duplication) or create tenant-local projections; duplicating membership/connection state would violate ARC-01/ARC-02 and risk divergence. Confirm the boundary with the architect, especially because READY-36 will add care units in the next migration.
5. **Seeding methods are not on the interface.** `InMemoryServiceProfileStore` exposes `addMember`, `addUnit`, `linkPatient`, `addConnection`, `assignUnit` and `addProfile` (lines 39-72) used by unit tests to arrange state. A JDBC store cannot expose those as production API; the integration test will need SQL fixtures or a test-only seeding helper inside the test scope.
6. **Value shapes need JSONB.** `ServiceProfile` carries nested lists (`ServiceHours.windows` with `DayOfWeek`/`LocalTime`, `topics`, `urgentInstructions`, `backupCoverage`); `WorkItemFact` and `MessagingAudit` are also records. Plan JSONB columns plus a `RowMapper` and a deterministic ordering (`ORDER BY seq`/`created_at`) so `auditEvents`, `workItems`, `versions` and `effectiveProfile` keep the in-memory semantics. `effectiveProfile` must select APPROVED rows with `effective_from <= at` and the **highest version**, and `latestVersion` must return 0 on an empty result.
7. **The AUD-20261120-04 row-level-security gate named in step 6 does not exist** in `scripts/`, `docs/` or `.github/`; nothing to run. `db/check.sh` remains the runtime RLS assertion gate.
8. Pre-existing red checks listed in `## Test evidence` (opencode CI profile under skip-worktree; missing `yaml` module). They are not caused by this task and are not fixable inside its scope.

- Before writing any migration in a swarm story, run `git ls-files db/migrations/ | grep 'V<n>__'` and `python3 -I scripts/check-migrations.py --require-baseline`. A "reserved version" in a TODO entry can be stale after a merged repair; the migrations directory is the authority.
- A previous audit (`AUD-20261120-11`) already found this exact collision and its note was merged. When a prompt's findings say an owner fix is expected "before dispatch", check that the fix actually landed before building on the old value.
- Reproduce a migration-gate failure against a **temporary copy** under `/tmp/opencode` and call `check_migrations.check(root, ...)` directly (the script is hyphen-named, so import it with `importlib.util`). That keeps the working tree clean and still gives real tool evidence.
