## Findings

- Self-access enforcement is substantially implemented: verified-link checks on appointments, released reports, conversations, attachments and enrollment; object-level tests deny a patient acting on a peer's account; durable chart-link tables exist in V10, V33, V83 and V84 with forced RLS.
- Gap 1: patient self-service controller routes are absent from `contracts/openapi/generated/openapi.yaml`, `client.ts` and `manifest.json`; the contract is generated from `CommandCatalog.java` by `CommandClientGenerator.java`.
- Gap 2: `PatientAppointmentController`'s production constructor wires `SyntheticPatientAppointmentPorts` and `VerifiedPatientLink`'s Javadoc states no verified-link table exists for that slice, so appointment/device self-access is process-local, not durable. `scripts/wiring-baseline.json` grandfathers this self-building controller, so a green wiring check is not evidence of proper wiring.
- Gap 3: `ReleasedReportService.InMemoryAuditSink` is an `@Component`, so report access allow/deny decisions are not durably auditable across a restart.
- Gap 4: no approved manual-process or site human evidence is in the repository (the counterpart clause owns that document).
- Independent QA reviewer (read-only, simulated) confirmed the enforcement files and the no-proxy observation and refined the note: V10 and V33 also store verified chart links (Gap 2 wording corrected), `PatientReleasedRevisionsController` is another patient route missing from OpenAPI (Gap 1), and the in-memory audit sink became the new Gap 3. The task count is therefore three code tasks plus one site/human evidence item.
- Reviewer caveat: the keyword search cannot prove absence of a proxy mode absolutely and there is no positive patient-app test asserting self-only; the `How to verify` grep is labelled as a keyword check and recommends a dedicated regression test.
- Inverse client gap observed, out of scope for this note: `apps/patient-mobile/src/features/reports/reportClient.ts` targets `/api/v1/released-reports`, which has no controller in `src/main`; production `apps/patient-mobile/src/app/providers.ts` uses `/api/v1/patient/reports`.
- Tooling surprise: `scripts/check-docs.py` treats PAT-01/PAT-02/PAT-03 as undefined because the spec writes them as `- **PAT-01** ...` rather than `**PAT-01 · ...`; citing those IDs in a checked Markdown file would fail the docs gate. The note therefore describes them by feature name and keeps requirement IDs in this (skipped) notes file.

## Lessons for workers

- Before citing a requirement ID in a checked Markdown file, confirm `scripts/check-docs.py` recognizes it: only `| ID |` table rows and `**ID ·` bold leads count as defined. PAT-0x is not recognized; use feature prose there and keep IDs in `docs/pr/notes/`.
- For an evidence note, read the whole requirement (outcome + boundary), then trace each half to code, migration, test and generated contract separately; a controller that exists but is missing from OpenAPI is a real gap, not evidence of end-to-end delivery.
