## Findings

- Scope survey (tool evidence): the clause is implemented by
  `com.aurevia.messaging.governance` — `MessagingGovernanceController` routes
  `POST /legal-holds`, `GET /retention/{resourceId}`, `POST /exports`; `MessagingGovernanceService`
  methods `placeHold`, `retentionDecision`, `applyRetention`, `createExport`; plus
  `MessagingGovernanceInputs`, `MessagingGovernanceActions`, `MessagingAuditContract` and the
  `InMemoryMessagingGovernanceStore` / Jdbc store pair. No route under `web` adds retention
  application.
- Real gap (tool evidence, `docs/security/threat-model.md:62`): `applyRetention` is a dry-run that
  returns eligible identifiers and an audit fact. It has no HTTP route, no scheduled/worker caller
  and performs no deletion; the threat model already records `GAP: Implement and test a scheduled
  retention job that respects legal holds and records deletion evidence` (OPS-07). The clause doc
  therefore records `Partly proven` and names the missing execution path. No `@Disabled` test is
  added: `scripts/check-constraints.py` rejects every newly added disabled test and
  `scripts/worker-check.sh` runs that check, so a new skipped test would fail a required gate; the
  missing implementation is outside this no-production-code task and is already tracked.
- Pre-existing, out-of-scope conflict markers were found in committed Javadoc of three HL7 files
  (`exchange/hl7/Hl7ParseException.java:6,10`, `Hl7Parser.java:14,18`, `Hl7Segment.java:10,14`)

## Lessons for workers

- When a clause's API surface exists but its execution path is tracked as a separate OPS gap,
  prove the HTTP surface with active tests and record the execution gap in the clause doc; do not
  add a new `@Disabled` test, because the quality gate rejects it.
- Keep the wrong-tenant assertion on a resource that exists only in the owning organization and
  give the caller active membership in the other organization, otherwise the response is 403
  rather than the intended 404 concealment.
