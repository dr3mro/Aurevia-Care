# WFAUDIT-04 — First release must not fail for a missing local architecture tag

## Summary

Produced a proposed workflow patch (document only) at `docs/operations/workflow-changes/first-release-architecture-tag.md`. Root cause: delivery.yml's `release` job loads the smoke-tested image as `aurevia:test` but never creates the `$image-$arch` local tag; on a first release `imagetools inspect` correctly fails and `docker push "$child"` then fails because no local tag with that reference exists. A second defect blocks re-runs: `.Id` equality compares a freshly rebuilt image with the previously published one and fails because rebuilds get a new image-config `created` time. The proposed patch adds the missing `docker tag`, replaces `.Id` with stable version/revision label checks, fails closed on ambiguous existence, validates the RepoDigest, and adds no `:latest` tag. No workflow file was changed; no release was created or tagged.

**Evidence sources:** executed tool commands (file reads, stubbed dry run, diff/apply checks, policy checks) and a simulated `aurevia-github-workflow` specialist review (subagent `ses_e0141bb84ffeR4WWT7dT2icc4P`). **No simulated-user and no human/clinical evidence.** No patient data, credentials or real domain names in any note or fixture.

- **WEB-11** — build once and promote the same signed artifact; never overwrite a version tag with different content; keep `:latest` off pre-release versions.

## Findings

1. **Blocking (fixed by the proposal):** delivery.yml release loop never creates `$image-$arch` locally; first release fails at `docker push`. Confirmed by file reads and dry-run A; independently confirmed by the GitHub Workflow specialist (tool reads, no commands run).
2. **Blocking (fixed by the proposal):** `.Id` equality fails on re-run after a rebuild; provenance labels are the correct identity. Confirmed by dry-run A2 and by the specialist's read of `scripts/verify.sh` and `Dockerfile` (no `SOURCE_DATE_EPOCH` pin).
3. **Overwrite risk (mitigated for children):** `imagetools inspect` failure was treated as tag absence; the patch cross-checks with the fail-closed branch (scenario F). The parent-manifest guard at original line 209 still conflates absent with transient error; recorded as a residual risk in the document for a follow-up.
4. **RepoDigest assumption (fixed):** empty digest now fails closed (scenario E).
5. **`release-app-image.yml` is already correct:** it tags before pushing (lines 60–61) and gates `:latest` on `VERSION == *-*` (line 86); its unconditional `imagetools create` can overwrite its own separate `-app` manifest but that is out of scope.
6. **Environment artifact (not a defect):** `opencode.json` under skip-worktree makes `check-pack.py` and three tooling tests red locally. Confirmed with `git ls-files -v` and a HEAD-vs-worktree hash comparison. Left untouched.

## Lessons for workers

- A `docker push <name:tag>` needs the *local reference*, not just identical bits under another tag; `docker load` of a `docker save` tar restores only the saved tag. Trace tag creation explicitly in release jobs.
- Image `.Id` is not a stable release identity across rebuilds: the image config `created` timestamp changes. Use immutable build-arg labels (version, revision) for provenance checks instead.
- When a dry-run harness models a shell step, avoid running the function in an `if ( … )` wrapper: `set -e` is suppressed inside function calls used as a condition. Capture the exit status from a standalone subshell, and persist stub state across scenarios (a `declare -p` state file reloaded with `declare -g` avoids function-local shadowing).
- In a cloud worker, `git ls-files -v opencode.json` showing `S` means check-pack/test_check_pack failures are CI-profile artifacts, not change defects; record the hashes and leave the file alone.
- Producing a proposed workflow patch: take the diff from a scratch copy, `git apply --check` it against a pristine copy, then extract it back from the document and check byte-for-byte equality, so the embedded diff is provably applicable.
