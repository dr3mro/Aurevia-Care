# START-45 — API: negative-path and tenant-isolation tests for the package `authz`

## Summary

Test-only story. One new class, `apps/api/src/test/java/com/aurevia/authz/AuthzNegativePathsTest.java`
(package `com.aurevia.authz`), consolidates negative-path and tenant-isolation assertions for
the authorization domain with synthetic fixtures. No production code, existing test, contract
or migration is changed. Five tests: input refused before SQL, wrong role denied and audited,
foreign identifier concealed as not found with no second effect, invalid version precondition
stopping the command, and a repeated command refused with a conflict.

## Affected requirements

- IAM-01 — deny access without active membership, required action permission and domain
  authorization; every write checks the current scope. Asserted by the wrong-role,
  foreign-identifier and repeated-command scenarios.
- ARC-02 — tenant context derived from authentication, application-level action and object
  policy, fail closed on missing context or an invisible identifier. Asserted by the generic
  `NOT_FOUND` and `DENIED` outcomes and the absence of a foreign record mutation.

## Risk class

Cross-boundary (authorization and tenant-isolation evidence), test-only. No data change.

## Findings

1. **Idempotency-Key in authz is correlation-only, not deduplicating.** `contracts/openapi.yaml`
   declares the optional `RetryKey` header (`Idempotency-Key`, lines 10109-10114, "the owning service
   applies replay safety where the command supports it") on `POST /api/v1/access/emergency`,
   the emergency review route and `POST /api/v1/specialty/attestations`. No authz service reads
   that header or replays a stored outcome; the implemented deduplication is in `events`/`web`.
   Asserting "same key returns the original outcome" in this package would invent behaviour, so
   the repeated-command test asserts the real safety property instead: an active grant makes a
   second grant `409 CONFLICT` with no insert.
2. **No stale-version compare-and-set in authz.** `SpecialtyAttestationRepository.insert` is a
   plain insert, and V46 only checks `attested_revision > 0`; `IfMatch.parse` rejects absent,
   blank, non-numeric and non-positive preconditions (428/422) but does not compare against a
   stored version. The stale-version acceptance sub-item is therefore evidenced in the existing
   `com.aurevia.authz.clauses` tests (`RoleClinicianTest.staleDraftVersionOnSignIsRefused`,
   `RoleClinicalAssistantTest.handoffRefusesStaleVersion`, both `412 STALE_VERSION`), while this
   class covers the authz precondition boundary that does exist.
3. **Worker-image artifacts, not change defects** (tool evidence, recorded once): the
   `opencode.json` skip-worktree CI profile and the 13 failures / 4 errors in the Python tooling
   suite use generated or temporary fixtures and are unrelated to the Java test file. No
   protected file was changed to make a gate pass.
4. No real bug was found in the surveyed authz paths; the PR is green.
5. These are service/controller tests against a mocked RLS repository. They prove
   fail-closed behavior, generic not-found answers and the absence of a foreign-record
   mutation; they are not database-level RLS proof. Forced RLS is evidenced by the
   integration suites named in the survey (`EmergencyAccessReviewIntegrationTest`,
   `RoleHistoryIntegrationTest`, `SpecialtyAuthorizationFlowTest`).
6. Reviewers noted that most scenarios overlap existing assertions outside this package;
   the additive assertions are listed in the coverage-delta table above, especially the
   in-package `If-Match` precondition cases.

## Why this is not finished

The new test class itself is complete and green. Two acceptance sub-items cannot be asserted
in this package without inventing behaviour, so they are recorded here and left to an owner:

- `Idempotency-Key` replay: `AccessController` and `SpecialtyController` declare no
  `@RequestHeader("Idempotency-Key")` parameter and no authz service consults a dedupe store.
  The header is correlation-only per `contracts/openapi.yaml:10109-10114`. Claiming that a replay
  returns the original outcome would require production code, which this story forbids.
  Exact runtime call not executed: the change is test-only and the PR must stay green.
- Stale version: `SpecialtyAttestationRepository.insert` is a plain insert and V46 only checks
  `attested_revision > 0`; there is no stored-version compare in authz. The `412 STALE_VERSION`
  behaviour already has evidence in `com.aurevia.authz.clauses` (see Findings item 2).

## Lessons for workers

- Before writing a generic "negative paths" test, survey `it/<domain>` as well as the package's
  own test tree: in this repository many clause and HTTP tests for `authz` live under
  `com.aurevia.it.authz`, so the "uncovered" list shrinks sharply.
- A header declared in OpenAPI is not proof of a service behaviour. Check the implementation:
  `Idempotency-Key` is correlation-only on the authz routes, and a dedup assertion would fail.
- In cloud workers, confirm `git ls-files -v .opencode/opencode.json` before treating a
  `check-pack` stale error as a change defect; never regenerate that protected file.
- A foreign-identifier 404 still writes DENIED/NOT_FOUND audit rows. Assert "no domain row
  inserted or mutated" rather than "no repository interaction" for that path.
