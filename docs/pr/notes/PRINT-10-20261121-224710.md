# PRINT-10 — Browser test: print a prescription, lab order and chart summary in English and Arabic

## Summary

Adds a synthetic Playwright journey under `apps/staff-web/e2e/print` that drives the three exported print buttons through their real providers, stubs only the `/api/v1/**` boundary, and reads the print audit back through that stub. One prescription patient copy, one lab requisition sheet and one chart summary are printed in English and again in Arabic (right-to-left). Draft sources are refused, a reason is required before every print, and the PDF is produced by the browser (`page.pdf()`), so no printer is contacted.

No production source was changed. The print buttons are exported by `src/features/print` but are not yet mounted on the owning screens (PRINT-08 explicitly left mounting to those screen owners), so a dev-only harness is used, mirroring the existing `e2e/radflow/referrer-harness.html` pattern.

## Affected requirements

- WEB-09 — resilient screens: the preview, reason-required alert and state words are asserted in both locales.
- RX-02 — sign then print the patient copy; the approved channel and attestation gate the button.
- LAB-01 — place the lab order then print its issuer-scoped requisition sheet.
- Related (not claimed by this story): WEB-10 is the specification clause for end-to-end browser verification in English and Arabic.

## Risk class

Cross-boundary (test-only). It exercises the staff web against a stubbed protected printing/audit boundary; no clinical data, migration or production code is touched. A clinical/negative-path review is relevant because prescription printing is RX-02 safety behaviour, but the change adds no clinical decision logic.

## Data changes

None. No migration, backfill, schema, lock or volume impact; no reserved migration version used. No patient identifier, credential or real domain appears in the files, logs or this note.

## Authorization boundaries and audit events

The harness sends each confirmed print to `POST /api/v1/printing/audit` through the real transport with the write CSRF cookie; the stub records one sanitized row per print (kind, coded reason, handout language, action/copy/sheet count/printable). The test asserts those rows are absent for drafts and for a reason-less Print, and present with the exact reason and language after confirmation. Sign/place commands go through the same stub. The real server remains authoritative for permission and state; this browser test does not weaken or replace it. No audit entry carries handout content.

## Migration and rollout considerations

None. The harness HTML is served by the Vite dev server only and is not a production entry point; it is excluded from the production build (which uses the root `index.html`).

## Findings

- The print buttons are not mounted on any routed prescription, order or chart screen (PRINT-08 deliberately left that to the screen owners). A durable browser test of the real screens is therefore blocked until those mounts exist; this harness is the in-scope substitute. Next worker: when a screen mounts the buttons, add a harness-free variant of this journey against that route.
- Pre-existing, out-of-scope defect on `main`: committed conflict markers remain in `apps/api/src/main/java/com/aurevia/exchange/hl7/Hl7ParseException.java`, `Hl7Parser.java` and `Hl7Segment.java` (`git grep -nE '^(<<<<<<<|>>>>>>>) '`). Present at HEAD before this story; not touched here because `apps/api` is outside the `apps/staff-web/e2e/print` scope. Report to the integrator/owner.
- Environment only, not a code change: Playwright Chromium and its apt dependencies were absent locally and were installed to run the journey. CI already provisions the browser; no repository file was changed.

## Lessons for workers

- Read the owning feature README before writing a browser test: `apps/staff-web/src/features/print/README.md` states the buttons are unmounted, which dictates a dev harness. The `e2e/radflow/referrer-harness.html/.tsx` pair is the reusable pattern.
- Assertions on a Node-side Playwright stub array race with the browser `fetch`; wrap them in `expect.poll(...)` rather than a synchronous `expect` immediately after a click.
- `apps/staff-web/tsconfig.json` includes only `src`, `tests` and `vite.config.ts`, so `npm run typecheck` silently skips `e2e/**`. Run an explicit strict `tsc` over new harness/spec files and `eslint e2e/...` yourself; `check.sh` only lints them.
- Reuse existing domain predicates (`canPrintPreview`) in a harness instead of restating a boolean, so no untested branch is introduced even in test scaffolding.
