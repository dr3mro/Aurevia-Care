## Findings

Senior-backend and test-engineer confirmed that under `synthetic-auth` `TenantContextInterceptor` binds the context from headers and never calls the resolver; the membership half is enforced in `FacilityService.authorize`. The clause document states this accurately and cites `ClaimsTenantResolverTest` as the separate JWT/OAuth claim proof.

Fixed by appending an active event at `now() - interval '2 days'` and a revoked event at `now() - interval '1 day'`, attaching the tenant_admin grant to the revoked event, and setting `app.actor`/`app.current_org` before the inserts. ## Lessons for workers

- "Deactivate a membership" means appending a `status='revoked'` event: `V1` CHECK allows only `active`/`revoked`, and `V4` forbids UPDATE/DELETE. Give the events explicit past `valid_from` values so `current_membership()`'s `DISTINCT ON` fold is deterministic, attach the role grant to the current event, and assert the fold in the fixture so a 403 cannot be misattributed to a missing role.
- Under `@ActiveProfiles("synthetic-auth")` the HTTP path never calls `ClaimsTenantResolver`; do not claim it as exercised evidence. Cite the resolver's own unit test for the claim half.
- `scripts/worker-check.sh` runs **all** integration suites; a swarm worker must run its individual stages instead and leave the umbrella gate to the integrator.
- Assert error `code` and `message` from `ApiErrorHandler` (`code`, `message`, `correlationId`), not only the HTTP status, and assert the peer tenant's data is absent on denial.
