# SMSG-07 — API: staff-message attachments (MSG-03, CLN-07)

## Summary

Added a self-contained staff-message attachment slice under
`apps/api/src/main/java/com/aurevia/staffmsg/attachments`: a value
contract that reuses the document domain's three media types and the
staff-messaging `ScanState`, a bounded role/action matrix, pure input validation
that delegates to the shared `UploadValidation`, a tenant-scoped store port with a
durable JDBC implementation, a domain service and a thin HTTP controller.

Upload binds the file to the uploader and a chosen conversation or mail draft,
refuses anything but PDF/JPEG/PNG, enforces a configured size and count limit,
computes the checksum from the original bytes and places them in the private
object store with a `PENDING` scan state. A failed scan moves the file to
`QUARANTINED`; the sender sees the scanner detail and the send step refuses such
a file. `pending()` lists unsent files; `send()` requires explicit confirmation,
names every pending file and its recipients, and validates the whole batch before
mutating any member. Download authorizes per recipient, verifies the stored bytes
against the checksum and appends an audit fact. No payload bytes or object URLs
enter an audit. Originals and checksums are preserved.

Synthetic data only. No new dependency. No file outside the declared scope was
changed.

## Affected requirements

- CLN-07 — original bytes and checksum retained for later chart association.

## Data changes

No new table and no migration. The slice persists through schema already created
by V91 (`staff_attachment_link`, forced RLS), the existing document metadata and
event tables (`document_artifact`, `document_event`) and the existing private
object-store port. No backfill, no lock or volume impact beyond ordinary inserts
and updates on those tables, no new retention obligation and no forward-fix.

## Authorization boundaries and audit events

- Tenant: every store method takes the active organization explicitly; all reads
  and writes run in the tenant-guarded transaction.
- Roles: senders may upload/send/download/read; `security_scanner` alone may scan;
  `privacy_auditor` and `tenant_admin` may read views and audit trails.
- Ownership: only the uploader may send a file, and only to its bound draft.
- Recipients: download is allowed only for a recipient of the published message.
- Audit: `UPLOADED`, `SCANNED_CLEAN`, `SCANNED_QUARANTINED`, `SENT`, `DOWNLOADED`
  and `ACCESS_DENIED` facts are appended as mapped `document_event` rows, carrying
  subject, outcome and a bounded non-sensitive detail. No bytes, file names in
  denial details, or object URLs are logged.

## Migration and rollout considerations

None. The JDBC store's `message_id` link value is the draft identifier until send
and the published message identifier afterwards; in a real database the draft
selector must reference an existing `staff_message` row because the V91 column
carries a foreign key. Synthetic fixtures use an in-memory store that does not
enforce that key.

## Coverage repair (attempt 1 of 2)

The coverage gate reported `Failed to execute goal ... Could not collect
dependencies ... spring-boot-starter-oauth2-client:pom:4.1.2 (present, but
unavailable) ... HTTP Status: 429`. This was a dependency-resolution failure,
not an uncovered line or branch: the gate's plain `mvn` hit Maven Central rate
limiting before any test or JaCoCo check ran. All evidence in this section is
from executed tool commands (no reviewer, simulated user or human participant).

Two environment repairs were required to let the gate run at all (both outside
the repository, not committed):

1. Wrote `$HOME/.m2/settings.xml` with the Google Maven Central mirror so any
   download avoids the rate-limited central endpoint.
2. `MAVEN_OPTS=-Dmaven.repo.local=/opt/m2`; the cached artifacts were tracked to
   the original worker's temp mirror id (`_remote.repositories`) and one stale
   `.pom.lastUpdated` recorded the 429, so plain `mvn` considered them
   "unavailable" and retried central. Deleted all `_remote.repositories` and
   `*.lastUpdated` files under `/opt/m2`; `mvn -Pno-security dependency:resolve`
   then exited 0.

With dependencies resolving, the full gate surfaced the genuine defect:
`Tests run: 3909, Errors: 626` — every error an ApplicationContext load failure
whose root cause was `No qualifying bean of type
'...staffmsg.attachments.StaffAttachmentLimits' available`. `StaffAttachmentLimits`
is a plain record that was never registered as a Spring bean, so
`StaffAttachmentService` (a `@Service`) could not be constructed in the real app
context. The original `StaffAttachmentControllerHttpTest` used
`MockMvcBuilders.standaloneSetup` with a hand-built service, which bypassed DI
and masked the defect from the targeted suite.

Fix (scoped, committed): registered the bean via
`StaffAttachmentConfiguration.staffAttachmentLimits()` (default bounds) and added
`JdbcStaffAttachmentStoreTest.configurationProvidesTheLimitsBeanRequiredByTheService`,
which invokes the bean method and asserts both default values. The new method has
no branches; its single line and method are covered by that test. The full app
context's existing integration tests are the entry-point proof that the service
now wires and the attachment routes load.

## Findings

1. `scripts/check-pack.py` and `python3 -I scripts/gen-opencode.py --check` both
   report `opencode.json is stale`. `git status` and `git diff -- opencode.json`
   show no change by this worker; this is the pre-existing environment artifact
   recorded in MEMORY.md (OPS-CW-003-01). I did not edit the file (out of scope).
2. `bash scripts/python-coverage.sh` exits 1 with
   `{"violations": [{"file": "TODO.md", "rule": "tracker"}]}`. The worker
   environment sets `STORY_BODY`/`SWARM=1`, so `worker_gate.candidate_from_env`
   treats the orchestrator's tracker commit in `origin/main...HEAD` as a worker
   edit. No tracker file was touched by this worker. All other policy gates pass.
3. Maven Central returned HTTP 429; dependency resolution succeeded through the
   Google Maven Central mirror via a temporary settings file that is NOT part of
   the commit.
4. Full `mvn verify` / `apps/api/check.sh` and `scripts/check.sh` were not run:
   the execution request forbids commands that run every integration test and a
   full verify. The integrator and Delivery must run the full gate and 100%
   bundle check. Targeted tests and JaCoCo report were run instead.
5. No OpenAPI entry or regenerated client was added: `contracts/` is outside this
   story's scope. A task request is included below.
6. `ScanState.QUARANTINED` in the staff-messaging contract means "scanner found a
   threat", not "awaiting scan" (as in the documents domain). It is reused with
   that meaning; `PENDING` is the awaiting-scan state.
7. The JDBC store's original bytes are held through the injected `ObjectStorePort`
   bean; the default `FileSystemObjectStore` adapter is process-scoped for its
   metadata index. A managed object-store adapter must replace that bean in a
   deployed profile for durable originals (documented on the configuration class).

## Lessons for workers

- Maven Central can rate-limit (HTTP 429) in this worker image; the Google mirror
  at `maven-central.storage-download.googleapis.com/maven2/` resolves the same
  coordinates. Keep the settings file untracked and delete it before committing.
- Before reporting `opencode.json` or `python-coverage.sh` failures, check
  `git status`/`git diff` and the `SWARM`/`STORY_BODY` environment: in this worker
  those two failures are pre-existing environment artifacts, not your change.
- `ScanState.QUARANTINED` means a failed scan in `staffmsg.model`; do not map it
  to the documents domain's "in quarantine / awaiting scan" meaning.
- When a JDBC store must persist metadata without a new migration, composing the
  existing document metadata/event tables and object-store port keeps the change
  inside a narrow scope and avoids an unreviewed schema change.
