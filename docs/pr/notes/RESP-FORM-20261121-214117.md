# RESP-FORM — Staff web: responsive `Form` component

## Summary

Made the staff-web `Form` responsive without changing its behaviour, text, API or
exported names. `Form.tsx` now reads `useBreakpoint()`, stacks every field in a
single column on compact viewports, and uses the shared `grid-2` two-column grid
from the medium breakpoint only when the form has more than six *real* fields
(counted recursively so layout wrappers are traversed and summaries/prose are
not counted). The
submit action sits in a `.touch`-classed wrapper with a sticky, logical-property
footer on phones and a reserved `scroll-padding-block-end` so it cannot cover a
focused field. No stylesheet was edited and no field is hidden. A new jsdom test
file mocks `matchMedia` for compact/medium/expanded and asserts structure,
labels, roles, keyboard order, the no-hidden-field rule and the RTL case.

## Affected requirements

- **WEB-07** — supported clients / responsive staff web: three bands (compact,
  medium, expanded), single column on phones, two columns from 768 px, no hidden
  fields, no horizontal scroll, coarse-pointer targets, safe-area insets.
- **UX-01** — Arabic/RTL, logical properties, WCAG 2.2 AA form patterns
  (error summary at top, focus not obscured, 200% zoom, wrapping long text).

Note: decision `0004-responsive-staff-web.md` supersedes the 768 px floor in the
WEB-07 spec text; this change follows the decision (render down to 320 px).

## Findings

- **Fixed in this pass — field counting was wrong for real callers:** both
  reviewers showed `Children.count(children)` miscounts because
  `RegisterPatientForm.tsx` wraps six `FormField`s in one `<div>` (count 1) and
  `ScheduleForm.tsx` passes a `<p>` plus a raw `<select>` beside its fields.
  `countFields` now traverses wrappers/fragments, counts `FormField` and native
  field controls, and ignores prose/summaries; three new tests cover each case.
- **Hand-off to RESP-FORMFIELD — inputs do not actually use 16 px text:** the
  existing `.field { font-size: 16px }` rule in `responsive.css` is never applied;
  `FormField.tsx` renders its `<input>` with inline styles but no font size, so
  iOS zoom-on-focus can still occur. `Form.tsx` does not render the inputs and
  cannot fix this within its scope. RESP-FORMFIELD already lists "inputs use
  16 px text" in its details and owns `FormField.tsx`; route this there.
- **Hand-off to RESP-FORMFIELD / RESP-SHELL / RESP-STYLESHEET — focus reservation
  is not effective in a real browser:** `scroll-padding-block-end` is set on the
  form, which is `display: grid` with no `overflow` and therefore not the scroll
  container; the `scroll-margin-block-end` companion rule sits on `.field`,
  which is currently unapplied (item above). Neither `AppShell` nor the root
  stylesheet sets scroll padding on the real scroll container, so WCAG 2.4.11
  "focus not obscured" by the sticky bar is unverified here. The reservation is
  also undersized: 32 px vs a sticky bar of ~44 px target + 16 px padding.
  Needs the scroll container fixed in the shell/theme and `.field` applied to
  inputs, then proved in the Playwright phone project. No task-request is added
  because RESP-FORMFIELD, RESP-SHELL and RESP-STYLESHEET already own those files.
- **Pre-existing `gen:api:check` failure (not this change):** the committed
  `contracts/openapi.yaml` is ahead of `apps/staff-web/src/api/generated/openapi.d.ts`.
  Verified with a non-mutating temp generation and diff: the contract (changed
  by commit `f85d4adb`, `PRINT-02: add print endpoints, permissions and sanitized audit trail (#539)`)
  adds `/api/v1/printing/handouts`, `/api/v1/printing/handouts/download`,
  `PrintReason` and `HandoutKind` that the committed generated client lacks.
  My working tree contains only the two scoped files, so this is repository
  state on `main`, not a regression from RESP-FORM. I did not regenerate or
  hand-edit the generated client (out of scope; generated files are never
  hand-edited).
- **Environment:** staff-web `node_modules` was absent on first run; `npm ci`
  was required before the local Vitest/Vite binaries could run.
- **Pixel-level limits are intentional:** jsdom cannot measure 44 px targets,
  paint the sticky ring or evaluate `@media`; the stylesheet and coarse-pointer
  rules are covered by `tests/theme/responsiveStylesheet.test.ts` and the
  painted checks belong to the Playwright tasks, per the story.

## Lessons for workers

- Do not edit `responsive.css` for a form-specific need that the stylesheet
  lacks. This story needed a sticky action bar and a scroll-space reservation;
  there is no `.form`, `.form__fields`, `.form__actions` or `.form__scroll`
  class in `apps/staff-web/src/theme/responsive.css` even though
  `docs/design/responsive-layout.md` section 8 shows those selectors. I used
  logical inline styles (`position: sticky`, `inset-block-end`, `padding-inline`,
  `scroll-padding-block-end`) and recorded the missing classes here instead.
  A future styled-components story should add those classes to the stylesheet
  (with token fallbacks) and let components use them.
- `Button` hard-codes `minHeight: 32px` and accepts no `className`, so the
  `.touch` class was placed on a grid wrapper around it; the button stretches
  to the wrapper's coarse-pointer floor. If a future story lets `Button` accept
  a class, apply `.touch` directly to the button instead.
- `bash apps/staff-web/check.sh` runs `gen:api:check` first and stops there on a
  stale generated client. To validate a scoped UI change while that pre-existing
  drift exists, run the remaining steps individually (`typecheck`, `lint`,
  `build`, `check-bundle-size.mjs`, `test:coverage`) and record the drift rather
  than editing generated or contract files outside your scope.
