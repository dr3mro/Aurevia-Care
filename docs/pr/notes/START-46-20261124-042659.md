## Lessons for workers

- Drive negative-path proofs through the real HTTP controller when the story says "API": status plus JSON error code catches a behavior that only exists in a domain kernel. But stub authorization on the repository the service actually reads — `CatalogService` and `ConfigurationService` each query their own membership fold, so one shared unused stub silently turns a 404 into a 403.
- A tenant-concealment test must seed the record for the owner and make the repository answer depend on `TenantContext.current().organizationId()`; an unconditional `Optional.empty()` proves nothing about isolation.
- When a story's negative-path checklist names a behavior the scoped API does not implement, keep the pull request green and write the exact call and the owning task in `## Why this is not finished` instead of adding a failing or tautological test.
- Do not run `scripts/check.sh`, `apps/api/check.sh` or `scripts/worker-check.sh` as a worker: they exceed the time budget and own the full gate. Targeted `-Dtest=...` plus standalone SpotBugs and the policy scripts cover the scoped change.

## Why this is not finished

The in-scope change is complete and green (10 new tests, 36 catalog tests, SpotBugs and policy scripts all pass). One acceptance bullet cannot be fully proven with today's code, and this section records it rather than hiding it:

- **"a repeated request with the same idempotency key"** is not implemented by the catalog API. `POST /api/v1/catalogs/diagnosis/entries` with header `Idempotency-Key: catalog-retry-key` called twice with the same body allocates versions 1 then 2 (`repeatedRequestsWithOneKeyAppendVersionsRatherThanReplaying` asserts `$.version` 1 and 2); `CatalogController` reads no idempotency header and there is no dedup ledger in the catalog path. A true tenant-scoped replay with first-message-wins is owned by the open task `READY-42` (durable idempotency ledger / `IdempotencyFilter`), blocked on `READY-41`. No production change was in scope here, so no failing test was added.
- **"a stale version"** is proven only as far as the API supports: `approve` with version 0 returns 422 `INVALID_VERSION`, an unknown version returns 404 `NOT_FOUND`, and an already-approved version returns 409 `CONFLICT`. `CatalogController` has no `If-Match`/412 precondition; `IfMatch.parse` exists but no catalog route calls it. A catalog-specific version precondition is requested below.
