## Findings

1. **No implementation gap.** CLN-02 clause 1 is built; `CheckInService.verify`/`checkIn` and `WorklistPolicy` implement the rule and `ClinicController` exposes both HTTP routes. The clause doc status is therefore `Proven by tests` and `Gap: None`. No `@Disabled` test was needed.
2. **Known worker-environment false positive (OPS-CW-003-01), not a defect of this change.** `python3 -I scripts/check-pack.py` fails with `opencode.json is stale: run scripts/gen-opencode.py`, and the same artifact causes 6 `test_check_pack` failures in `python3 -I -m unittest discover -s scripts/tests`. Evidence: `git ls-files -v opencode.json` returns `S` (skip-worktree), `git diff --stat opencode.json` is empty, and `git show HEAD:opencode.json` hashes differently from the worktree file. The worktree file is the CI runtime profile installed by `agent-run.sh`; the committed HEAD profile is the correct generated local profile. AGENTS.md classifies this as an environmental false positive and assigns the full gate to the integrator. Per instruction, it was confirmed once and not re-diagnosed or edited.
3. The targeted Maven test emitted Mockito self-attachment / dynamic-agent warnings on JDK 27; these are the documented local-toolchain warnings (the project pins `--release 21` and a subclass-maker workaround) and did not affect the result.
4. Specialist review (read-only file reading; no commands executed) found no blockers or majors and three minor items, all resolved in-scope:
   - The two `never().insertVerification(...)` denial assertions used `anyString()` for the `alternateCode`/`alternateReason` arguments. Mockito's `anyString()` excludes `null`, but those fields are `null` for `two_identifiers`, so a denied-path regression that stored null alternates could have passed. Changed both to `nullable(String.class)`; the strict positive `eq(null)` assertions remain.
   - The clause doc did not mention the existing real-PostgreSQL HTTP proof. Added `it.schedulingcheckin.CheckInWorklistIntegrationTest` to the Evidence and Neighbours sections and stated explicitly that this new class is service-level, clause-focused evidence.
   - Audit-scope matchers used `anyString()` and the verify→check-in link relied on a manual `hasVerification` stub. Tightened all audit matchers to `eq("CHECK_IN_WORKLIST")` and commented that the stub models the committed verification row, with a pointer to the integration test for the real causal chain.

## Lessons for workers

- For clause-proof stories on already-implemented behaviour, the test is green on first run; that is correct. Record it as proof (status `Proven by tests`) rather than inventing a red state by changing production code.
- Reuse the exact fixtures and inline `TransactionTemplate` callback from `it.schedulingcheckin.CheckInServiceTest` for any new scheduling/checkin test; it avoids a database and keeps denial-audit assertions deterministic.
- In this worker image, `check-pack.py` and the `test_check_pack` unit failures are the OPS-CW-003-01 skip-worktree artifact. Check `git ls-files -v opencode.json` once, run the other policy stages individually, and never regenerate or commit the protected `opencode.json` to "fix" it.
- Mockito `anyString()` does not match `null`. When asserting `never()` on a call whose optional trailing arguments are legitimately null on the happy path, use `nullable(String.class)`/`any()` or the `never()` assertion is vacuous for the null case.
- Before writing a clause doc, grep the neighbouring `it/` package for an existing HTTP integration test; name it explicitly so the doc does not imply there is no end-to-end proof even when this task only adds service-level evidence.
