# PHARM-06 — Staff web: prescriber view of pharmacy status, clarification replies and substitution approval

## Summary

Added a `prescriberstatus` feature under `apps/staff-web/src/features/prescriberstatus` exporting three presentational components: `PharmacyStatusTimeline`, `ClarificationReply` and `SubstitutionReview`. The timeline renders one row per status fact (submitted, delivery confirmed, clarification, accepted/rejected, dispensing, plus a generic fallback) with dispensing evidence kept on the dispensing row. Clarification replies send an answer body and/or an amended revision with `If-Match` and a fresh `Idempotency-Key`; an answered thread is read-only and links the revision. Substitution review shows original and proposed catalog entries side by side; approval requires an explicit attestation and surfaces the signed revision returned by the API, while decline keeps the original and creates no revision. Reuses `StatusViewResponse`/`StatusEventResponse` from `features/pharmacyinbox` and the same unpublished-route descriptor pattern; no new npm dependency; no file outside the granted scope changed. Synthetic fixtures only.

## Clinical and architecture review

The UI never fabricates a revision or a decision: approval/decline and clarification answers call the real PHARM-04/PHARM-03 endpoints with version and idempotency preconditions, and the returned projection is what the component renders. Attestation is required client-side for a clear error but the server remains authoritative (PHARM-04 re-validates catalog, allergy and attestation). The timeline keeps acceptance and dispensing distinct, matching RX-02. A bounded simulated React plan was applied; no human clinical sign-off or real-patient approval is claimed.

2. **`features/prescriptions` absent** (tool `find`): the task's "read features/prescriptions" step refers to a folder that does not exist in `apps/staff-web` (it exists only in `apps/patient-mobile`); `features/pharmacyinbox` plus the backend contracts were used as authoritative.
3. **Pre-existing committed conflict markers** (tool `git grep`): `apps/api/src/main/java/com/aurevia/exchange/hl7/{Hl7ParseException,Hl7Parser,Hl7Segment}.java` contain `<<<<<<< HEAD` / `>>>>>>> origin/swarm/BUILD-37-469` markers in committed files on a clean tree. Outside this scope; not touched. Owner: the exchange/HL7 module or integrator.
4. **Known `opencode.json` CI-profile artifact** (tool): `check-pack.py` and five `test_check_pack.py` tests fail at clean HEAD because the worktree file is the CI profile under `skip-worktree` (`S`, no diff, identical to `.github/opencode.ci.json`). Not caused by this change; protected file not edited.
5. **Duplicated descriptor helpers** (tool read): `pharmacyinbox/api.ts` keeps its `pharmacyDescriptor`/`commandMeta` private, so the same ~10 lines are repeated locally; centralizing them in `src/api/client.ts` would touch a shared file outside scope. Improvement idea for a future tooling story, not a defect in this slice.

## Lessons for workers

- In jsdom, a section `aria-label` that equals a `FormField` label makes `getByLabelText` find two elements; give the section a distinct label (e.g. the action name), not the field label.
- `getByText` on a string that appears both in a thread entry and in the answer summary fails with "multiple elements"; assert on a `data-testid` run instead.
- When passing `locale` as a prop, the RTL test still needs `I18nProvider` in the wrapper because the document `dir` is mirrored by that provider, not by the component.
- Read `coverage/coverage-summary.json` for exact per-file counters; the compact Vite coverage table truncates directory names and omits zero-error files, so a scoped run can look empty while every touched file is at 100%.
- `scripts/check.sh` transitively runs the full `mvn verify`; in a worker, run its bounded policy constituents and the module `check.sh` instead, and say why in the notes.
