# TRACK-04 — API integration tests: prescribe→pharmacy and order→released result

## Summary

Added synthetic, two-tenant HTTP integration tests for the whole care loops, under the
single allowed scope `apps/api/src/test/java/com/aurevia/journey/loop`:

- `PrescriptionJourneyLoopTest` — prescribe (create + attest), route (transmit + confirm
  delivery), pharmacy accept, dispense.
- `LaboratoryJourneyLoopTest` — authorized exchange order, collect (accession + matched
  specimen), result, verify, release, corrected report + corrected release.
- `ImagingJourneyLoopTest` — RAD-01 imaging order: worklist receive, schedule/link study,
  signed report, addendum + referrer acknowledgment.
- `LoopSupport` — shared synthetic DB seeding, HTTP client, journey-projector helpers.

After every step, facts observed in real HTTP responses are normalized to
`JourneyEvent` records and projected with the existing pure read model
`JourneyTimeline.view(...)`, asserting the exact complete/pending pattern and the next
expected step. The two tenants' fact collections are deliberately mixed before projection;
a disjoint time band per tenant (tenant B earlier) makes a missing tenant filter visible
through the projector's earliest-wins rule. Cross-tenant HTTP reads are asserted to return
404. No production file, dependency, migration or threshold was changed.

## Authorization boundaries and audit events

Every HTTP request carries only synthetic headers (`X-Synthetic-Subject`,
`X-Active-Organization`) plus the command-specific `If-Match` / `Idempotency-Key`. Roles
are seeded per tenant (clinician, pharmacy_staff, lab_collector, lab_verifier,
radiology_staff, radiology_interpreter, reception, tenant_admin); verification uses a
different subject from result entry so `SELF_VERIFICATION` is not triggered. Asserted
boundaries: cross-tenant reads of the peer's prescription, order, lab result, release and
imaging worklist/report all return 404; a subject without membership in the peer tenant
returns 403; identical local identifiers in both tenants resolve to each tenant's own
row. No audit event was added or changed by this change; existing audit events emitted by
the exercised endpoints are not asserted beyond their HTTP effects.

## Findings

1. `V19__exchange_orders.sql` enforces `CHECK (organization_id <> destination_org)`, so an
   exchange order cannot be routed to its own tenant. The lab loop therefore seeds
   cross-tenant authorizations (A→B, B→A); the intentional bounded work item in the peer
   tenant is not treated as a leak. The peer order row is still invisible via
   `GET /api/v1/orders/{id}` (404).
2. `exchange_authorization.destination_org` has an FK to `organization`; seeding grants
   must happen after both organizations are inserted.
3. The journey read model has no HTTP endpoint and keeps the earliest event per step, so
   "timeline changes after every action" is not literally possible: verify and correct
   do not move an already-complete step. The tests assert HTTP state transitions plus an
   explicit unchanged-timeline assertion rather than inventing new steps.
4. The release history action for a correction is `RELEASE_CORRECT`, while the
   `TIMED`/`PT1H` variant of the existing release suite records `CORRECTION_NOTICE`; the
   assertion matches the actual command path used here.
5. `GET /api/v1/releases/{id}` returns the durable `PatientRelease` projection (no
   `patientVisibleNow`); that flag is on the `POST /api/v1/lab/releases`
   `ReleasedReportView` response.
6. The worktree `opencode.json` CI-profile artifact made the first `quick-check.sh` red;
   see Test evidence item 6 and the "Lessons" note below. No file was regenerated or
   committed.
7. No production defect was found. No defect was added to BUGS.md because every issue was
   a fixture/expectation correction inside this change.

## Lessons for workers

- Before writing the seed, read the check constraints and FKs of the migration that owns
  the table (`V19__exchange_orders.sql`): a self-destination fails a `CHECK`, and a
  destination grant fails an FK until both organizations exist.
- A `JourneyTimeline` step keeps the earliest fact; to prove tenant isolation, give the
  two tenants disjoint time bands with the peer *earlier*, so a missing org filter makes
  the peer event win and the assertion fails.
- Reusing `JourneyTimeline` from an integration test needs one stable `itemId` across all
  facts of an item; set the accession `sourceOrderRef` to the exchange order id and use
  that id for every projected fact.
- `scripts/tests/test_fast_tier.py` requires `@Tag("integration")` on every test-tree Java
  file containing `jdbc:postgresql`, including a shared fixture class with no `@Test`.
- In a cloud worker, a stale `opencode.json` under `skip-worktree` is the CI profile, not a
  HEAD problem: restore `git show HEAD:opencode.json` for the gate, then put the CI bytes
  back byte-for-byte. Never regenerate or commit it.
