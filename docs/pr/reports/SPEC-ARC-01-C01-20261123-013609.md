Swarm hand-off notes and pull request description. Worker branch `swarm/SPEC-ARC-01-C01-1080`.

## Summary

Proof by a real-PostgreSQL integration test that tenant-owned records carry an
organization ID and an opaque (UUID) ID, plus the clause evidence document.
Two new files only; no production, migration, contract, script or configuration

`com.aurevia.tenant.TenantContext` / `TenantGuardTransactionManager`.

## Findings

- **Scope of the proof (tool + reviewer evidence).** The four asserted tables are the
  foundational tenant-owned records of `V1__tenant_schema.sql`. A read-only survey
  found later feature migrations with deliberately different keys — e.g.
  `V84__report_release_store.sql` `report_chart_link` has no `id`,
  `report_release_revision.id` is `text`, and `V80__template_store.sql`
  `template_audit_event.event_id` is a `bigint` identity. The test and doc
  therefore do **not** claim catalog-wide conformance; a separate audit is
  requested below. This did not block this scoped story, so no `@Disabled` gap
  test was added (the constraint gate rejects one).
- **Overlap with sibling C02.** `crossTenantForeignKeyIsRefused` exercises the
  composite FK, which is also the subject of sibling task SPEC-ARC-01-C02. It is
  kept here because the senior-developer brief explicitly requires two negative
  methods and the assertion is limited to clause 1 (an opaque id cannot be
  referenced without its organization). The integrator should avoid counting it
  as C02's acceptance evidence.
- **Fixture gap found and fixed (tool evidence).** The first targeted run failed
  with HTTP 403 `missing action permission` because `seed(...)` created a
  membership but no `role_assignment`; adding `tenant_admin` in the fixture made
  the suite green. No production code changed.
- **Cloud-worker false positive (tool evidence).** `bash scripts/worker-check.sh`
  and 6 of 1187 Python tooling tests fail only on `check-pack` because
  `opencode.json` is the CI runtime profile installed under `skip-worktree`
  (`git ls-files -v` = `S`). Recorded once; remaining stages were run
  individually and pass. The generated file was not touched.
- **Pre-existing defect in `HEAD`, not introduced here (tool evidence).** Three
  tracked production files already contain unresolved merge-conflict markers in
  their Javadoc in the committed base: `apps/api/src/main/java/com/aurevia/exchange/hl7/Hl7ParseException.java:6,10`,
  `Hl7Parser.java:14,18` and `Hl7Segment.java:10,14` (verified with
  `git show HEAD:<path>` and `git grep -nE '^(<<<<<<<|>>>>>>>) '`). They sit inside
  `/** ... */` blocks, so compilation and the 100% coverage gate are unaffected,
  but the developer reference renders the markers. Out of this story's scope;
  a cleanup task is requested below.

## Lessons for workers

- Copy the **whole** neighbour `seed(...)` — organization, `user_identity`,
  `membership` **and** `role_assignment`. Omitting the role yields a 403
  `missing action permission` at the HTTP entry point, not a 404 or a tenant error.
- Assert the SQLState (`23503` FK, `23502` NOT NULL) and a message fragment, not
  just `assertThrows`: a policy (42501) or privilege error would otherwise be a
  false green for a constraint test.
- When probing a NOT NULL column under FORCE RLS, use a superuser connection for
  that one insert and comment why: otherwise RLS `WITH CHECK` can replace the
  expected 23502 with a policy error. Use the NOBYPASSRLS migrate role with a
  matching `app.current_org` for the composite-FK probe so RLS cannot mask it.
- Do not generalise a four-table V1 schema proof into a catalog-wide claim;
  later feature modules intentionally use named or non-UUID keys, and that
  belongs in a separate conformance task.
