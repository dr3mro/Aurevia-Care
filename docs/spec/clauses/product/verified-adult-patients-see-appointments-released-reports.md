## Clause

Verified adult patients can see appointments and released reports, obtain copies, manage notification preferences, and securely exchange messages, files and instructions with connected care units.

## Status

Partly built

## Gap

The clause is not verifiable end to end from the repository today. Missing parts, with the files that would change:

1. **Patient command wiring.** `placeholderAction` handlers in `apps/patient-mobile/src/app/patientPages.tsx` must be replaced with the existing domain commands and the API client, plus an account/preferences page; `providers.ts` and the affected screen tests would change. One code task.
2. **Notification preferences.** Only device-token register/revoke/invalid exists (`apps/api/.../messaging/appointments/PatientAppointmentController.java`, `apps/patient-mobile/src/features/notifications/*`). There is no per-topic/channel preference, quiet-hours or opt-in state, no endpoint and no UI. A preference model, store/service, route, screen and tests are needed (new files under the relevant `messaging` / notifications domains and their tests). One code task.
3. **Verified-adult eligibility.** Date of birth is stored and validated (`apps/api/.../patient/PatientService.java`) and identity proofing exists (`apps/api/.../patient/identity/*`), but no age/Adult eligibility rule or dependent/proxy exclusion is enforced in code. That rule and its negative tests belong in the patient-identity/enrollment domains. One code task.
4. **Synthetic production ports and service-profile persistence.** `SyntheticPatientAppointmentPorts` supplies the patient appointment, verified-link and device stores from `src/main`, and `InMemoryServiceProfileStore` is the `@Repository` production bean with process-local authorization state (AUD-20261121-01). Both need tenant-owned forced-RLS migrations, `Jdbc*` implementations behind their interfaces, removal of the in-memory beans from `src/main` and HTTP-level integration tests. One code/database task.
5. **Real push delivery and connected units.** The `PushGateway` implementation always returns `DELIVERED` and no partner care-unit connection is configured or verified. An APNs/FCM adapter, cloud configuration and a partner unit connection require a cloud account and a partner, plus DevSecOps/system-design review. One infrastructure/partner task.
6. **Public contract.** Patient self-service endpoints are absent from `contracts/openapi.yaml`, `contracts/openapi/generated/*` and the generated client. Those artifacts and their checks would change. One contract task.
7. **Human and partner evidence.** Identity-proofing procedure approval, per-unit eligibility/inbox/after-hours verification, G5 signed site acceptance and real-patient acceptance are not in the repository. These cannot be created by a code change: the site clinical lead and privacy owner, the participating care-unit operators, the Product Owner and the clinical lead must supply them, linked from `docs/operations/production-readiness/launch-checklist.md`. One human/partner-gated task.

That is **seven separate tasks** (six code/contract/infrastructure slices and one human/partner-gated evidence task). Clause 2 (self-access only) and clause 3 (staff manual process) are separate tasks and are not assessed here.

Focused human checks: confirm `apps/patient-mobile/src/app/patientPages.tsx` and `RootNavigator.tsx` still pass `placeholderAction` to command handlers (gap 1); confirm `dispatchNotice`/`commandForSession` still have no production caller (gap 2); confirm `grep -r "implements ServiceProfileStore" apps/api/src/main/java` still returns only `InMemoryServiceProfileStore` and `SyntheticPatientAppointmentPorts` still lives under `src/main` (gap 4); search `contracts/openapi.yaml` and `contracts/openapi/generated/manifest.json` for `/api/v1/patient/` (gap 6); confirm the `PushGateway` implementation still returns `DELIVERED` unconditionally (gap 5). Each should be shown absent/closed once the corresponding task is done.

Before G5 a site must produce, and link from `docs/operations/production-readiness/launch-checklist.md`: the signed site acceptance matrix and G5 acceptance record with no unresolved patient-safety, tenant-isolation, record-integrity or critical-escalation defect; the approved identity-proofing and re-verification procedure for adult self-access; per-participating-unit verification of eligibility rules, inbox ownership, after-hours guidance and backup coverage; evidence that generic notifications reveal no clinical content on a real device; and a real-patient acceptance record for appointments, released-report copies, notification preferences and secure messaging with connected units. These are supplied by the site clinical lead and privacy owner, the participating care-unit operators, and the Product Owner/clinical lead — not by repository code or simulated review.
