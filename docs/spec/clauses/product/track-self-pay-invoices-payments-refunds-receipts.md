# PRD-04 clause 1 — evidence note

## Clause

Track self-pay invoices, payments, refunds and receipts.

## Status

Partly built

## Evidence

The API and persistence slice for all four facts exists in the repository and is covered by unit and HTTP/PostgreSQL tests. The staff-web journey and the G4 acceptance evidence for the product outcome are not present, so the clause is not fully built or fully verified at product level.

- The requirement and its boundary ("No claims adjudication, payer integrations, card data storage or accounting ledger") are defined in [PROJECT_V1_SPEC.md](../../../../.opencode/config/PROJECT_V1_SPEC.md), section 1, row PRD-04.
- Domain types: [FinanceContract.java](../../../../apps/api/src/main/java/com/aurevia/finance/FinanceContract.java) defines `Invoice`, `InvoiceItem`, the `InvoiceState` lifecycle (draft, issued, partially paid, paid, void), `EntryType` (payment, refund, credit), the append-only `LedgerEntry` with `receiptNo`, the combined `View`, and daily `Reconciliation` totals.
- Behaviour: [FinanceService.java](../../../../apps/api/src/main/java/com/aurevia/finance/FinanceService.java) creates, issues, posts payments/credits/refunds, voids, lists, reads and reconciles invoices. Money is integer minor units in one currency per invoice; balances are recomputed under a row lock with version preconditions, replay deduplication by durable reference, independent approver checks and an audit append on each command.
- HTTP entry point: [FinanceController.java](../../../../apps/api/src/main/java/com/aurevia/finance/FinanceController.java) serves `POST /api/v1/finance/invoices`, `GET /api/v1/finance/invoices`, `GET /api/v1/finance/invoices/{id}`, `POST .../issue`, `POST .../payments`, `POST .../credits`, `POST .../refunds`, `POST .../void` and `GET /api/v1/finance/reconciliation`.
- Persistence and invariants: [V45__finance.sql](../../../../db/migrations/V45__finance.sql) creates `finance_invoice`, `finance_invoice_item`, `finance_ledger_entry` and `finance_receipt_counter`, inherits forced row-level security from V2, enforces the balance identity, one currency per entry, append-only ledger and item rows, replay-unique references and gap-free per-tenant receipt numbers. [FinanceRepository.java](../../../../apps/api/src/main/java/com/aurevia/finance/FinanceRepository.java) is the SQL boundary and runs inside the tenant-guarded transaction.
- Authorization: [FinanceActions.java](../../../../apps/api/src/main/java/com/aurevia/finance/FinanceActions.java) holds the bounded action matrix; [CommandCatalog.java](../../../../apps/api/src/main/java/com/aurevia/api/authorization/CommandCatalog.java) and [CommandAuthorization.java](../../../../apps/api/src/main/java/com/aurevia/api/authorization/CommandAuthorization.java) register the `FinanceActions` policy.
- Tests present: [FinanceLedgerTest.java](../../../../apps/api/src/test/java/com/aurevia/finance/FinanceLedgerTest.java), [InvoiceListServiceTest.java](../../../../apps/api/src/test/java/com/aurevia/finance/InvoiceListServiceTest.java), [InvoiceListControllerTest.java](../../../../apps/api/src/test/java/com/aurevia/finance/InvoiceListControllerTest.java), [FinanceContractTest.java](../../../../apps/api/src/test/java/com/aurevia/it/finance/FinanceContractTest.java), [FinanceServiceTest.java](../../../../apps/api/src/test/java/com/aurevia/it/finance/FinanceServiceTest.java), [FinanceFlowTest.java](../../../../apps/api/src/test/java/com/aurevia/it/finance/FinanceFlowTest.java) (including `fullLifecyclePostsItemizedPaymentsAndNumberedReceipts`, `refundReestablishesIssuedStateAndReplayIsANoOp`, `reversalsRequireReasonAndAnIndependentApprover`), [FinanceHttpSecurityTest.java](../../../../apps/api/src/test/java/com/aurevia/it/finance/FinanceHttpSecurityTest.java) and [InvoiceListIntegrationTest.java](../../../../apps/api/src/test/java/com/aurevia/it/finance/InvoiceListIntegrationTest.java).
- Contract and generated clients: [openapi.yaml](../../../../contracts/openapi.yaml) documents `GET /api/v1/finance/invoices` and the Invoice, InvoiceItem, LedgerEntry, InvoiceView and InvoicePage schemas; the generated [client.ts](../../../../contracts/openapi/generated/client.ts), [manifest.json](../../../../contracts/openapi/generated/manifest.json), [openapi.yaml](../../../../contracts/openapi/generated/openapi.yaml) and staff-web [openapi.d.ts](../../../../apps/staff-web/src/api/generated/openapi.d.ts) are checked in.
- Recorded verification in the repository: [BUILD-13.md](../../../swarm/BUILD-13.md) records PR #295, targeted test commands that ended `EXIT:0`, and JaCoCo with zero missed lines or branches on every finance class. - Traceability discrepancy found during this survey: `CommandCatalog.issueInvoice` uses the path `/api/v1/invoices`, while `FinanceController.create` serves `/api/v1/finance/invoices`. [CommandClientGenerator.java](../../../../apps/api/src/main/java/com/aurevia/api/authorization/CommandClientGenerator.java) generates the command client from that path, so the checked-in generated client and manifest advertise a create route that the controller does not serve. Runtime authorization is performed independently by `FinanceService`, and the HTTP tests exercise the real controller route, so this is a generated-contract mismatch rather than a proven authorization failure. Files that would change: `CommandCatalog.java` plus the regenerated client and manifest. One task.
