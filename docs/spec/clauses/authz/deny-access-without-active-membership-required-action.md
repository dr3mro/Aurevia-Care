# IAM-01 clause 3 — API test evidence

## Clause

Deny access without active membership, the required action permission and domain authorization for the resource.

## Status

Proven by tests

## Evidence

Test class: `com.aurevia.authz.clauses.DenyAccessWithoutActiveMembershipRequiredActionTest`
(path: `apps/api/src/test/java/com/aurevia/authz/clauses/DenyAccessWithoutActiveMembershipRequiredActionTest.java`).
All four tests are active (none are disabled) and pass with synthetic data only.

- `allowsWhenMembershipActionPermissionAndOwningDomainPolicyHold` — positive proof. Active
  membership, a permitted role and the owning domain policy together produce an allowed
  `Decision` (`reasonCode=ALLOWED`) for the `STAFF_INVITE` action of `inviteStaff`, and the
  decision is recorded once in the synthetic decision sink.
- `deniesWhenActiveMembershipIsMissingEvenForAnOtherwiseQualifiedRole` — negative proof.
  A `tenant_admin` whose membership is inactive is refused with HTTP 403 `FORBIDDEN`
  ("no active membership") and the recorded reason `MEMBERSHIP_INACTIVE`.
- `deniesWhenActiveRolesLackTheRequiredActionPermission` — negative proof. A `reception`
  role with active membership lacks the tenant-admin-only `STAFF_INVITE` permission and is
  refused with HTTP 403 `FORBIDDEN` and recorded reason `COMMAND_FORBIDDEN`.
- `deniesWhenOnlyANonOwningDomainPolicyWouldAllowTheAction` — negative proof of domain
  authorization. With a command bound to owning policy `OWNING`, a colliding action that a
  different policy (`OTHER`) allows does not widen access: only the owning policy is
  consulted and the command is denied (`reasonCode=COMMAND_FORBIDDEN`).

Production classes exercised through the normal server-side command entry point
(`CommandAuthorization.authorize`):

- `com.aurevia.api.authorization.CommandAuthorization` — the IAM-01 server-side
  authorization gate; re-resolves membership and roles on every call, checks active
  membership, consults only the owning policy via `permits`, denies closed with stable
  reason codes and records every decision.
- `com.aurevia.api.authorization.CommandCatalog` and `CommandDefinition` — bind
  each protected command to one action and exactly one owning domain policy, so another
  policy cannot widen a resource's decision.
- `com.aurevia.authz.ActionPolicy` — the owning policy for the `STAFF_INVITE`
  action used in the positive and role-denial tests (`tenant_admin` allowed, `reception`
  denied).
- `com.aurevia.api.authorization.InMemoryDecisionSink` — synthetic decision
  ledger used to assert that allow and deny outcomes are recorded before the caller is
  answered.

Neighbouring implementations observed in the source survey (not changed by this task):
`com.aurevia.staff.StaffService`, `StaffInvitationService`,
`messaging.governance.MessagingGovernanceService`, `messaging.service.ServiceProfileService`,
`clinical.notes.ClinicalNoteService` and `messaging.instructions.InstructionService` each
perform the same active-membership plus action-permission check in their owning service;
`InstructionService` additionally verifies care-unit assignment and active patient-unit
connection for object-level domain authorization. Controllers in `com.aurevia.web`
delegate these decisions to the owning services; the relevant Flyway migrations are under
`db/migrations` and the protected-command contract is generated by
`api.authorization.CommandClientGenerator` from `CommandCatalog`.

## Gap

None.

The IAM-01 clause-3 rule is built and proven by active tests at the command gate and by the
owning services. This task added proof only; it did not change production code, an existing
test, the OpenAPI contract or a migration. Object-level narrowing (for example facility
scope or care-unit assignment) remains the responsibility of the owning service and is
described in the specification as an additional constraint ("Facility scope may further
narrow access"), not as part of this clause's minimum rule.
