# 0003. Persistence of in-memory stores

- Status: proposed
- Date: 2026-11-20
- Requirement IDs: ARC-01, ARC-02, OPS-02

## Context

The API currently has many in-memory adapters behind persistence ports. The adapters wired into production embed the active organization in every key, so two tenants with identical local identifiers stay isolated in memory, but the data exists only in a process and disappears on restart. The test-only `InMemoryDecisionSink` is the exception: it holds a plain process-local list with no organization key. In the `Who injects` column, "injector" means a `private final <Interface>` field in `apps/api/src/main/java`; "not @Service" means the injecting class has no Spring stereotype and is constructed directly, so it has no production HTTP entry point.

## Decision

Replace the stores in three ordered groups. Each store gets its own story, its own adapter and its own migration version; no single change replaces several stores.

1. **Spring beans that already have tables.** Replace `InMemoryDeliveryStore` with a JDBC adapter over the existing V55 tables (`delivery_outbox`, `delivery_dead_letter`, `delivery_receipt`, `delivery_replay`, `delivery_link`, `delivery_audit`), remove `@Repository` from the in-memory class and keep it for unit tests only. No new migration. This is already tracked as AUD-20261120-06 and establishes the pattern: tenant-scoped parameterized SQL, forced row-level security, an atomic state, audit and outbox commit, and a real HTTP entry point. Do this first because it is the only bean whose tables already exist.
2. **Spring beans that need a new migration.** `InMemoryServiceProfileStore` (proposed V59), `InMemoryMessagingStore` (V60), `InMemoryFlowPolicyStore` (V61), `InMemoryMessagingGovernanceStore` (V62), `InMemoryInstructionFactStore` (V63) and `InstructionStore.InMemory` (V64). Each is a `@Repository` behind a `@Service`, so restart loses live state today. Give each store one reserved version from V59 upward, claim that version on its TODO entry before coding, and create tenant-owned tables with forced RLS, the non-owner runtime role, durable uniqueness where the port requires it and append-only audit consistent with ARC-01, ARC-02 and OPS-02. `PatientFlowPresentationService` has no controller reference in main, so its story must also confirm the entry point with AUD-20261119-03.
3. **Stores nobody injects, or injected only by code with no production entry point.** `IdempotencyLedger.InMemoryIdempotencyLedger` has zero injectors in main: remove it or mark it an orphan for AUD-20261119-03. The plain classes `InMemoryTemplateStore`, `InMemoryDecisionSink`, `InMemoryDocumentStore`, `InMemoryAttachmentStore`, `InMemoryPatientAccessStore`, `InMemoryReportReleaseStore` and `InMemoryTherapyStore` are injected only by non-Spring classes with no controller (`TemplateService`, `CommandAuthorization`, `PdfBindingService`, `DocumentGuard`, `QuarantineService`, `AttachmentService`, `PatientAccessService`, `ReleasedReportService`, `TherapyService`). Resolve these with AUD-20261119-03 — expose an entry point and then give the store a migration, or honestly mark the workflow pending — instead of adding migrations to code no request can reach. `InMemoryPatientAccessStore` can reuse `patient_account` and `account_invitation` (V10), and `InMemoryReportReleaseStore` can reuse `patient_link` (V33) and `patient_release`, `release_event`, `release_notification` (V24) when those workflows become reachable.

The security-relevant stores are not excused by group 3: authorization decisions and idempotency/replay state must become durable before production even if their current adapters are only reachable from tests. `CommandAuthorization` currently receives its `DecisionSink` from a synthetic test factory and has no production sink; the owning authorization and API-contract stories must name a durable decision sink (OPS-02) and a transactional replay ledger (ARC-03, ARC-04) as a production-enablement gate, not a follow-on cleanup.

## Alternatives considered

- **Replace every in-memory store in one change** — rejected: it cannot be reviewed or verified as one green slice, and it obscures which store owns which invariant. Ordering by "bean with a table" first, then "bean needing a table", then "no production caller" keeps each change traceable to a test.
- **Keep the in-memory stores and periodically flush snapshots to PostgreSQL** — rejected: a periodic flush is not atomic with the domain commit, so state, audit and outbox can diverge on process loss, contrary to ARC-02 and ARC-05. The replacement must commit state and audit in the same transaction.
- **One shared migration for all stores, or one migration version per group** — rejected: each store owns its schema and reserved version. A shared migration couples independent stories and defeats expand/contract review under OPS-06. Use V59 and up, one per store, claimed in tasks/ before use.
- **Defer the decision ledger and idempotency ledger because nothing production-facing injects them** — rejected: OPS-02 durable authorization audit and ARC-03/ARC-04 replay protection are required before real-patient use, so they are named explicitly in Consequences and carry a production-enablement gate even though their current adapters are test-only.

## Consequences and evidence

- Restart loses data for every `@Repository` in the table: `InMemoryDeliveryStore`, `InMemoryServiceProfileStore`, `InMemoryMessagingStore`, `InMemoryFlowPolicyStore`, `InMemoryMessagingGovernanceStore`, `InMemoryInstructionFactStore` and `InstructionStore.InMemory` are all process-local, so committed state is not durable today. Six of their seven `@Service` callers have an HTTP controller; `PatientFlowPresentationService` is the exception (Decision group 2).
- `InMemoryDecisionSink` and `IdempotencyLedger` are security-relevant: audit decisions and replay protection must be durable before production (OPS-02, ARC-03, ARC-04), even though today their only adapters are used by tests and neither is a Spring bean.
- The non-annotated stores also lose data on restart, but they are not production beans: their injecting classes have no Spring stereotype and no controller, so they are orphans to resolve with AUD-20261119-03 rather than production gaps with a live entry point.
