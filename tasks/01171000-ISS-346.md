    What is wrong: db/check.sh applied Flyway migrations by expanding the raw shell glob db/migrations/V*.sql. A bare glob expands lexically, so once versions reached two digits (V10, V11, ... V90) they sort before V1..V9 and psql applies V10__patient_identity_proofing.sql before V1__tenant_schema.sql creates public.organization, failing with `psql:.../V10__patient_identity_proofing.sql:17: ERROR: relation "public.organization" does not exist`. The migrations themselves are sound: the Flyway-backed integration test applies the same files in correct version order. Evidence: db/check.sh:31-37 (migration apply loop); db/migrations/V1__tenant_schema.sql (creates public.organization); db/migrations/V10__patient_identity_proofing.sql (references it at ~line 17); 43 migration files exist through V90, so double-digit ordering is always exercised; .github/actions/java-verify/action.yml:41 runs `bash db/check.sh`, so this is the database check in CI (confirm it there; do not edit workflow files). Fix: in db/check.sh feed the migration list to the psql apply loop in numeric Flyway version order using GNU `sort -V` (for example `printf '%s\n' db/migrations/V*.sql | sort -V`, or `find db/migrations -name 'V*.sql' | sort -V`), preserving ON_ERROR_STOP, the migrate role and the ephemeral database; leave the migration SQL unchanged.
