# TODO

The single task file. Every agent, the swarm orchestrator and the integrator read and write only this file for task state.

| Mark | Meaning |
|---|---|
| `[ ]` | Open. Nobody has taken it. |
| `[-]` | Taken. An agent is working it (`agent:` names who). |
| `[x]` | Done. Evidence and the PR or commit are on the entry. |

Rules for agents:
- Pick the first open task whose `depends` are all done. Change `[ ]` to `[-]` and add `- agent: <your name>` before you start. Keep WIP one per agent.
- When the task passes every gate, change it to `[x]`, add `- evidence:` (commands, CI run, SHA) and `- pr:` in the same change. Never mark `[x]` without evidence.
- If you stop without finishing, put the mark back to `[ ]` and remove `agent:`.
- Swarm workers do not edit this file. The orchestrator marks `[-]` when it starts a worker and the integrator marks `[x]` when it merges. A task is swarm-dispatchable when it has a `scope`.
- Entry fields: `requirements`, `depends` (task IDs), `scope` (comma-separated path prefixes), `reserved` (one database migration version), `aliases`, `agent`, `pr`, `evidence`, `details` (indented text). Specification requirement IDs come from SMARTCLINIC_V1_SPEC.md.
- Name folders and Java packages after the business domain (for example `capacity`, `events`, `patient.identity`), never after a task, story or gate ID such as `s_g5_05` or `x_01`: a task's `scope` is where its files go, so never write an ID-based path there. `scripts/check-names.py` fails the build on any new one.
- Add new stories, acceptance changes and improvement ideas here as new `[ ]` entries. Record defects in BUGS.md.
- Automatic sections: `## Repairs (automatic)` holds `FIX-<run>` repairs of a red `main`, `## Audit findings` holds the daily audit's `AUD-` tasks, and `## Issue fixes` holds `ISS-<n>` tasks made from GitHub issue #n by the issue monitor. `attempts` counts worker runs; at 3 a task waits (the issue monitor may give it one more round).

Simulated review findings are evidence of review activity, not clinical or human pilot acceptance. Real-patient approval remains a G5 gate.

## One-week execution plan (1 wave per hour)

Created 2026-11-19T08:55Z from the open entries above. Horizon: 7 days × 24 hours = 168 hourly wave slots. This plan uses 7 implementation waves; the remaining 161 hourly slots are buffer for `needs-fix` retries, fix PRs, gate re-runs and human approvals.

Cadence and limits:

- One wave is launched per hour at minute 7 (`swarm.yml` schedule `cron: '7 * * * *'`). Because the `agent-swarm` concurrency group queues (`cancel-in-progress: false`, `queue: max`), a wave starts when the previous one finishes.
- Up to 10 workers per wave, one task per worker. Each task targets 50 minutes or less so a wave fits its hour; the 175-minute agent timeout is a hard cap, not a target.
- A wave takes a task only after its `depends` are `[x]`; gate entries wait for their phase tasks to merge.
- S-G0-04 is blocked (search, files, workers and exports surfaces do not exist yet) and is not scheduled.
- Gate entries (S-G1-09, S-G2-11, S-G3-13, S-G4-07, S-G5-12) prepare evidence only. Product Owner, clinical and privacy acceptance are human decisions; a worker cannot satisfy them.
- G5 production enablement additionally needs signed site configuration and real partner contracts. The swarm can only produce synthetic evidence.
