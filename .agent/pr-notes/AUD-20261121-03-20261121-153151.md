# AUD-20261121-03 — Rename G3EvidenceService to a business-domain class name

## Summary

Renamed the forbidden requirement-ID class `G3EvidenceService` to the business-domain name `GateEvidenceService` (matching the sibling `GateEvidenceController` and the `/api/v1/gate-evidence` route). Used `git mv` so history follows. Updated the class/constructor declarations, the controller's `{@link}`, field type and constructor parameter, and every test reference. No behavior, route, fixture or contract changed.

Because the wiring baseline is keyed by file path, keeping the original per-file `@SuppressFBWarnings` on the renamed file produced a **new** `fb-suppression` finding and failed `check-wiring.py`. As the story explicitly authorizes ("or move it to the central exclusion as the Java skill requires"), the justification is preserved as a comment and the suppression was moved to a narrow, commented `EI_EXPOSE_REP` match in `apps/api/spotbugs-exclude.xml`. The per-file annotation is gone; `check-wiring.py` and SpotBugs are both green.

## Findings

1. **Path-keyed wiring baseline creates a new finding on rename (resolved).** `scripts/check-wiring.py` keys `fb-suppression` and `requirement-id-name` by file path, so renaming the file makes the grandfathered suppression a new finding. The story named this exact tension and authorized centralizing the exclusion. Resolved by removing the per-file annotation and adding a narrow commented match in `apps/api/spotbugs-exclude.xml`. The two old baseline lines for `G3EvidenceService.java` are now stale and print notes only; `scripts/wiring-baseline.json` was deliberately left unchanged (`scripts/` is maintainer-owned).
2. **Scope note for the integrator.** `apps/api/spotbugs-exclude.xml` is outside the two declared scope directories, but the story's own expected fix explicitly authorized "move it to the central exclusion as the Java skill requires" and only forbade editing `scripts/` and the shared trackers. No other file outside the two scope directories was changed. If the integrator prefers strict two-directory scope, the equivalent in-scope alternative is to make `ledger()` return a defensive `EvidenceLedger` copy and drop the exclusion entirely; I did not do that because it changes accessor semantics beyond a rename.
3. **Environment artifact (not a defect of this change).** `check-pack.py` and three `test_check_pack` tests fail because the worktree `opencode.json` is the CI profile placed under `skip-worktree`; HEAD holds the correct local profile. This matches MEMORY.md OPS-CW-003-01/IMP-01. I did not regenerate or modify `opencode.json`. `scripts/check.sh` therefore stops at that policy check before reaching module gates.
4. **Kept "G3" in Javadoc prose** (e.g. "G3 gate-evidence report"). CODING_STYLE.md permits requirement IDs in Javadoc; only class/package/table names are forbidden. `test_java_conventions` is green.
5. **Bounded specialist review (simulated/static, no commands run by the reviewer).** The `smartclinic-senior-java-build` review confirmed: the central exclusion is correctly wired (`apps/api/pom.xml:151`) and maximally narrow (Bug + exact Class + exact Method + comment); no forbidden name, check-names or check-wiring regression; coverage/TDD trace intact; SpotBugs was run after compilation as the skill requires. It raised **no blocking findings**. Low-impact, integrator-owned follow-up: delete the two now-stale `G3EvidenceService.java` lines in `scripts/wiring-baseline.json` (`fb-suppression` line 10, `requirement-id-name` line 33) — the baseline "may only shrink", and workers may not edit `scripts/`. Optional separate story: make `ledger()` return a defensive copy and delete the exclusion.

## Lessons for workers

- A path-keyed wiring baseline means renaming a grandfathered file turns its suppression into a NEW finding: run `check-wiring.py` immediately after any `git mv`, before declaring a rename green.
- The Java build skill's rule is load-bearing here: never leave a per-file `@SuppressFBWarnings`; move the justification to a narrow, commented `apps/api/spotbugs-exclude.xml` match (compile first, then `spotbugs:check` — a bare check is vacuously green without class files).
- For a rename TDD trace, point the existing tests at the new name first (compile-time RED), then `git mv` and rename the declarations (GREEN); Maven compiles all test sources even with `-Dtest`, so a clean `testCompile` also proves no dangling references elsewhere.
- In a swarm worker, a red `check-pack.py` / `test_check_pack` with `git ls-files -v opencode.json` showing `S` is the known CI-profile artifact, not something to "fix" by regenerating the config.
