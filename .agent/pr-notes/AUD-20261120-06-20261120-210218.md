# AUD-20261120-06 — Replace the in-memory delivery outbox store with a PostgreSQL-backed store

## Summary

`InMemoryDeliveryStore` was the only `@Repository` implementing `DeliveryStore`, so all
ARC-05 outbox events, receipts, dead letters, replays, links and audit facts disappeared on
restart and were invisible to other API instances. This change adds
`events/JdbcDeliveryStore` as a `@Repository` over the existing V55 tables with fully
parameterized SQL, moves the synthetic in-memory adapter into test sources with no Spring
annotation, and adds unit and real-PostgreSQL acceptance tests. The production `DeliveryStore`
bean is now the JDBC adapter (proved by `JdbcDeliveryStoreIntegrationTest.productionBeanIsTheJdbcStore`).
No controller, domain-service signature, contract or migration changed.

Entry-point-to-test trace: `POST /api/v1/delivery/events` → `DeliveryController.publish` →
`DurableEventService.publish` → `JdbcDeliveryStore.byIdempotencyKey` /
`JdbcDeliveryStore.publishAtomically` → `delivery_outbox` + `delivery_audit` (V55) →
`JdbcDeliveryStoreIntegrationTest.storesAndReadsBackAnEventWithItsAuditFact` /
`reStoresTheSameEventIdWithoutCreatingASecondEffect`. Transmission and dead-letter paths run
through `/sent`, `/failed`, `/retry`, `/dead-letter`, `/dead-letters/review` and are asserted by
the same integration class.

## Data changes

No new migration and no schema edit. The adapter writes the existing V55 tables
`delivery_outbox`, `delivery_receipt`, `delivery_dead_letter`, `delivery_replay`,
`delivery_link`, `delivery_audit`; it also reads `exchange_order` (V19) and `patient_record`
(V7) for identifier confirmation. `db/check.sh` still applies and verifies V1–V58.

## Authorization boundaries and audit events

Tenant isolation is unchanged: every statement runs inside the tenant-guarded
`TransactionTemplate`, so `TenantGuardTransactionManager.doBegin` binds `app.current_org`,
`app.actor`, `app.purpose` and `app.correlation_id` before any SQL. Reads add no manual
organization predicate; forced RLS confines them. Inserts pass `organization_id` explicitly
(CAST to uuid), matching `PatientRepository`; the V55 triggers derive `actor_subject` from
`app.actor`. No audit action, permission or role changed. No patient data is stored by the new
adapter: only opaque ids, server instants, wire keys and a payload digest.

## Migration and rollout considerations

V55 already exists and is `Change: expand`, so the adapter is a pure code replacement. Rollback
is a redeploy of the previous artifact; no data backfill or forward-fix is needed. `InMemoryDeliveryStore`
remains available as a test fixture but is no longer a production bean.

## Findings

1. The delivery service has no transaction boundary of its own (unlike every other module in
   `apps/api`). The adapter therefore opens one tenant-guarded `TransactionTemplate` transaction per
   store operation, which makes the HTTP endpoints work against V55's forced RLS and actor triggers
   without changing the service. The atomic outbox+audit commit required by `DeliveryStore` is kept
   inside `publishAtomically`. A future story may move the transaction boundary to the service for
   whole-command atomicity; that is out of scope here and does not reduce current safety (the V55
   unique constraint still prevents a second downstream effect under a race).
2. PostgreSQL `timestamptz` stores microseconds, while Java `Instant.now()` carries nanoseconds. A
   receipt returned from the database can therefore differ in sub-microsecond digits from the first
   in-memory response. The integration test asserts the immutable `receiptId` and outcome, not the
   textual timestamp, to avoid a false failure. This is expected behavior of any JDBC adapter and
   is not a clinical data change.
3. The worker gate `bash scripts/worker-check.sh` is red in this environment for pre-existing
   reasons documented under Test evidence (CI-profile `opencode.json` under skip-worktree; 5+12
   Python tooling failures reproduced at clean HEAD, including missing PyYAML). No file outside the
   task scope was edited to work around these; the original worktree file was restored.
4. During implementation two self-inflicted defects were found and fixed before the final green run:
   text-block concatenation produced `SELECTorganization_id` / `RETURNINGorganization_id` (SQL
   syntax error, caught by the integration test), and pgjdbc could not infer a type for
   `java.time.Instant` (caught by the integration test; instants are now converted to UTC
   `OffsetDateTime`). Both now have passing end-to-end assertions.

## Lessons for workers

- When adding SQL to a Java text block, never end the fragment with `SELECT`/`RETURNING` and
  concatenate a column constant on the next line — incidental trailing whitespace is stripped and
  the tokens fuse. Use `"SELECT " + COLUMNS + "FROM ..."` with explicit spaces.
- pgjdbc 42.7.x cannot bind `java.time.Instant` without an explicit SQL type; pass
  `OffsetDateTime.ofInstant(instant, ZoneOffset.UTC)` (or a `Timestamp`) instead.
- In this repository a Java `DeliveryStore`-style domain service may have no `TransactionTemplate`:
  a JDBC adapter behind it must open the guarded transaction itself or every read is silently empty
  under forced RLS and every insert fails the actor trigger.
- In a worker container the worktree `opencode.json` is the CI profile under `skip-worktree`;
  `check-pack.py`/`gen-opencode.py --check` judge that file, not HEAD truth. Temporarily restoring
  `git show HEAD:opencode.json` (then putting the CI profile back) separates a real staleness from
  the known false positive.
- A failing integration test is the fastest way to find SQL and JDBC type errors that unit mocks
  cannot reveal; run the new `@Tag("integration")` class directly before the full gate.
