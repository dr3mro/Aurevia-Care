## Lessons for workers

- When a task lists several verification methods in parentheses, map each one to a concrete step in the runbook. A general rule plus per-item observations is safer than assuming one item owns the method.
- Describe integrator issues from the source function bodies, not from intuition: an approval-gated Delivery run requests a fresh run without opening a `pr-stuck` issue, while a failed fix worker does open one that is keyed by pull request and updated rather than reopened.
- Keep a person-supplied-input boundary explicit. A classifier that accepts a log argument does not read GitHub issues, so a runbook must say the person copies the diagnosis before classifying it.
- Do not put angle-bracket placeholder tokens in the Test evidence or Coverage sections of a worker notes file: the candidate gate applies its placeholder regex to exactly those two sections. Describe placeholders in prose instead.
- A GitHub verification runbook that ticks a box, writes verified or fills a result cell defeats its own purpose. Keep the header, boxes, table and Approval in the nothing-verified state until a person runs it on GitHub; a scratch red proof is a deterministic local check, never GitHub evidence.
- `scripts/check-docs.py` applies its structural rules to `docs/operations/` as well as most of the tree; run it after every edit to that directory and demonstrate the red case first with a deterministic check on the unmodified file.
- Copy observable strings verbatim from the emitting code, including punctuation: the held-pull-request issue title carries a hash prefix, and a person comparing a real issue against a runbook that omits it will look for the wrong title. A scratch verifier should assert the exact string, not just a substring.
