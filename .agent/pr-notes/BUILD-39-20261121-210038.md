# BUILD-39 — Object storage port with a local filesystem adapter

## Summary

Added a storage-only port under `com.aurevia.smartclinic.documents.storage` with a local filesystem adapter for development and tests. An object is placed in private quarantine, promoted only against the checksum a clean scan verified, read back only when its immutable version and checksum match the bytes on disk, deleted during cleanup, and expired when a promoted export disappears. Keys are namespaced by tenant and built from an opaque random alias, so no patient identifier or patient-derived value enters a key. No dependency, controller, migration or file outside the two declared `storage` scope directories was changed. Production S3 binding remains BUILD-40.

## Affected requirements

ARC-06 (unique object keys, verified object version, quarantine, mediated-download-ready object bytes, protected payloads out of logs/URLs). Supporting tenant/patient invariants from ARC-01/ARC-02 are enforced in the key shape and isolation tests; authorization, verdicts and audit facts remain in the existing `documents` domain services.

## Risk class

Cross-boundary (new storage port in the documents domain) with tenant/patient safety relevance. Negative and failure tests cover cross-tenant isolation, tampering, quarantine non-disclosure, version and checksum rejection, and fail-closed I/O. No clinical sign-off is claimed; this is infrastructure with no HTTP entry point in this story.

## Review owner

Simulated `smartclinic-senior-backend` review (subagent, review-only). Its four findings were addressed or explicitly accepted with rationale (see Findings). No human, clinical or simulated-user evidence was used. Evidence provenance for all checks below is executed tool commands plus one simulated reviewer; no patient data or credentials were used.

## Data changes

None. No Flyway migration, backfill, lock or volume impact. The filesystem adapter writes synthetic test bytes under a `@TempDir`; its metadata index is process-scoped and its Javadoc states it is development/test only, with the managed durable adapter supplied by BUILD-40.

## Authorization boundaries and audit events

Keys are tenant-scoped via `ObjectKey.tenantId()` and carry no patient data; the port takes no role/patient context by design (patient binding stays in the domain store). A per-test read with another tenant's key is rejected. No audit events are added here — `DocumentGuard`/`QuarantineService` continue to own fact recording above this boundary.

## Migration and rollout considerations

None in this story. Rollout/deployment of the production object-store binding is BUILD-40 and a later integration story; this adapter is not a production bean.

## Lessons for workers

- `scripts/check-wiring.py` fails any new `interface *Store` without a `Jdbc*` implementation. Name a pure hexagonal port `*StorePort` (or provide a Jdbc impl) from the start, or the policy gate fails after the code is written.
- In a cloud worker, a stale-`opencode.json` pack failure is usually the CI profile under `skip-worktree`. Confirm with `git ls-files -v`, `cmp` against `.github/opencode.ci.json` and `git show HEAD:opencode.json`; run local gates with HEAD bytes under a restore trap and never regenerate or commit the file.
- To keep a checked-exception catch at 100% JaCoCo, parameterize the cause (here the digest algorithm name) and test the failure path directly instead of adding an unreachable guard, pragma or suppression.
- SpotBugs `NP_NULL_ON_SOME_PATH_FROM_RETURN_VALUE` on `Path.getParent()` is best fixed by constructing the parent from `root` plus key components, not by a `requireNonNull` guard that can never fire.
- Re-deriving a checksum from the bytes actually read is what makes a method named `getVerified` fail closed; comparing only a stored label is a keyed lookup, not verification.
