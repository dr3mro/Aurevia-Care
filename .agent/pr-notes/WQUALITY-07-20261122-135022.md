## Lessons for workers

- When a story names four verification scenarios for "each change", apply them where the code actually has that behaviour (WQUALITY-01/02 read Delivery state) and, for offline gates, mark the scenario not applicable with an equivalent control — do not invent a stale-Delivery test for a classifier that reads no Delivery state.
- A checklist for already-merged changes must say "confirm the commit is on `main`", not "apply the patch"; the sibling `github-verification-checklist.md` uses apply blocks because it tracks proposed workflow patches, but these six tasks are merged scripts.
- `check-docs.py` validates relative links and requirement IDs plus structural rules (balanced fences, heading jumps, table pipe counts, token patterns, unclosed comments). Run it after the final edit, not only after the first draft.
- Check `git grep -nE '^(<<<<<<<|>>>>>>>) '` after merging `origin/main`, but distinguish committed content from an unresolved merge with `git status`/`git ls-files -u` before treating markers as work to fix; these HL7 markers are pre-existing and out of scope.
