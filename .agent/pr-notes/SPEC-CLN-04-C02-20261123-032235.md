## Lessons for workers

- Before adding a `@Disabled("GAP: …")` to a new test in this repo, run
  `python3 -I scripts/check-constraints.py --base origin/main --require-base` first: the gate
  postdates the older clause PRs and rejects every added Java `@Disabled`. Old disabled tests are
  grandfathered and are not proof that a new one will pass.
- For evidence-only API tasks with no endpoint, an active domain-level test keeps the "Partly proven"
  claim honest; make the disabled HTTP tests the would-prove part and say explicitly which production
  classes were executed versus only surveyed.
- Seed the reception actor in **both** tenants before inserting any patient: V7's actor trigger
  ("patient registration requires an authenticated user of the active tenant") otherwise fails the
  ORG_B seed. Read the Surefire XML for authoritative `tests/errors/skipped/failures`, not the exit code.
- A "complete but disabled" test must still be enablement-ready: seed the tenant template version a
  governance-only migration cannot write, give each test a distinct id against an append-only store,
  send `Idempotency-Key` on command POSTs, and assert the error code the service really returns rather
  than a validation detail it never puts in the HTTP body. A disabled test is not exempt from review.
- Prove a fixture's silent SQL step with a row-count assertion in `@BeforeAll`; `INSERT … SELECT` from
  an empty view succeeds while seeding nothing, which would make an enabled test fail much later.
