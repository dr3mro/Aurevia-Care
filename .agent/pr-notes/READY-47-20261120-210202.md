## Summary

Adds an authenticated JSON transport and an OS-backed session token store to the patient app, with no login screen. Every request reads the current credential, uses an opaque correlation id, enforces a 15-second abort deadline and converts failures into a closed set of typed errors. The credential is written only to `expo-secure-store` under the key `session`; no new dependency was added.

## Affected requirements

| ID | How this change serves it |
|---|---|
| PAT-01 | Patient app can call protected appointment/notification endpoints over HTTPS with a bearer credential, correct `Accept-Language` and generic error metadata; the token is read per request so revocation takes effect on the next action. |
| ARC-03 | Versioned `/api/v1` paths are passed by the caller; every call carries a fresh `X-Correlation-Id`, machine-readable error `code` is preserved, conflict codes 409/412 are distinguished, and a missing credential fails closed before any request is sent. |

## Risk class

Cross-boundary: a new client API boundary and OS credential storage. It does not decide clinical meaning, sign data, share across organisations, link patients, prescribe or acknowledge critical results, so the specification's clinical/architecture sign-offs are not a rollout gate for this slice. The READY-48 consumer is responsible for mapping `unauthenticated` to session expiry and clearing the token.

## Review owner

Senior React Native and Expo specialist (simulated read-only review) and Senior TypeScript conventions. No human review claimed.

## Data changes

None. No migration, schema, backfill or server state. The only persisted item is the synthetic session credential in the OS keychain/keystore under `session`.

## Authorization boundaries and audit events

The credential is read immediately before each request and is never stored in application state, AsyncStorage or a clinical cache. A missing or blank credential produces `unauthenticated` without a fetch. No server-side audit event is added or changed; the client sends the correlation id the server uses for its audit record.

## Migration and rollout considerations

None. The transport is not yet wired into any screen (READY-48 does that), so it has no production entry point in this slice. `requireAuthentication` is deliberately false until PKCE and IdP details are approved (launch checklist READY-46).

## Findings

1. `jest.config.ts` in this module collects only `<rootDir>/src/**/*.test.ts(x)` (plus three root-level files). The story also allowed `apps/patient-mobile/tests/api`, but a test there would never run and would not count toward coverage. Tests were therefore placed in `src/api`, which is inside the declared scope. No jest configuration was changed.
2. `src/features/reports/credentials.ts` already contains `SecureCredentialStore` with the same three SecureStore operations under a different key (`aurevia.patient.session`) and a `read/save/clear` interface. The story mandates the key `session` and the function names `saveToken`/`loadToken`/`clearToken`, and that file is outside this task's scope, so the new `src/api/tokenStore.ts` is a deliberate, reviewable duplicate of the storage seam rather than an edit to existing behaviour. READY-48 should wrap the new transport to satisfy the existing `ReportTransport`/`TokenStore` ports and may consolidate the two stores in a later, in-scope story.
3. `Accept-Language` is configured once at transport creation (default `'en'`). When READY-48 wires Arabic screens it must create the transport with `language: 'ar'`; a per-call locale override would be a separate story if the app switches locale at runtime.
4. No login screen was added. PKCE and the OIDC client registration need the identity provider details owned by a person (launch checklist READY-46); this story only supplies the transport and credential storage those screens will use.
5. Paths passed to `get/post/put` are joined to the origin with exactly one slash, so both `/api/v1/x` and `api/v1/x` work (regression test added). Callers still supply versioned paths; the transport does not build resource URLs itself.
6. `get<T>` returns parsed JSON as `T` without runtime validation, matching staff-web's pattern. Feature clients must keep validating untrusted payloads at their own boundary, as `reportClient.ts` already does; a transport-level validator would be a separate API decision.
7. A non-JSON or empty success body (for example 204) rejects during parsing and is classified as `network`. V1 protected routes return JSON, so this is documented rather than special-cased; if a JSON-less command is introduced it needs its own handling.
8. `saveToken` does not reject a blank token; the transport already fails closed on a blank credential with `unauthenticated`, so no request is sent with one.

## Lessons for workers

- In `apps/patient-mobile`, put tests under `src/**` — the Jest `testMatch` ignores a new `tests/` directory, so an otherwise correct test there would silently not run and would leave the new production file uncovered.
- `@jest/globals` must be imported explicitly before `jest.fn`/`jest.mock`/`jest.spyOn` in this module or `tsc --noEmit` fails; bare `describe`/`it`/`expect` are fine without it.
- The canonical gate is `bash apps/patient-mobile/check.sh`; it runs `npm ci` again, so a focused `npx jest src/api` is the fast inner loop and the full check is the final gate.
- `globalThis.__DEV__` is set by the `jest-expo` preset; tests can flip it with `Object.defineProperty` and must restore it afterwards to avoid leaking development-only URL acceptance into other suites.
- Put credential reads, body serialisation and timer/controller creation inside the same guarded `try` as the fetch; otherwise a storage or serialisation failure escapes as an untyped error and the module's typed-error contract is false. Test the rejecting-provider path explicitly.
- Check `error instanceof TransportError` before `signal.aborted` in an abort-aware catch, or a stalled typed error response can be silently re-labelled as a timeout.
