## Summary

Added `JdbcTherapyStore`, a tenant-guarded Spring JDBC adapter behind the existing
`TherapyStore` port. It persists episodes, evaluations, problems, baseline
measurements with units, goals, versioned outcome scales with units, readings,
interventions, session/progress/discharge notes with signatures, summaries, return
acknowledgments and the append-only audit trail. `TherapyService` is now a Spring
`@Service` that receives the store by injection; `TherapyController` receives the
service by injection and no longer constructs collaborators. The synthetic
`InMemoryTherapyStore` moved from `src/main` to `src/test` (same package, so all
existing test fixtures still compile). The reserved **V85** migration fills the
two storage gaps that V77 did not cover: evaluation problem text and an atomic,
durable scale-version counter. All fixtures are synthetic.

## Affected requirements

- **PT-01** — episodes, evaluation, problems, baseline measurements with units,

## Data changes

New `db/migrations/V85__therapy_store.sql`, `Change: expand`, additive only:
- `therapy_evaluation_problem` — tenant-owned append-only text of an evaluation's
  problem list (the one `Evaluation` field V77 had no table for). Enabled + forced
  RLS, `tenant_isolation` policy with `WITH CHECK`, explicit grants/revokes and
  UPDATE/DELETE/TRUNCATE rejection triggers.
- `therapy_scale_sequence` — per-tenant `(organization_id, key)` counter; versions
  are allocated by one atomic `INSERT … ON CONFLICT DO UPDATE … RETURNING`, so two
  concurrent definers cannot receive the same version. Enabled + forced RLS, the
  same policy, grants/revokes; intentionally mutable (a counter).

No destructive DDL, no backfill, no change to an existing migration. Row volume is
a handful of small rows per episode. Rollback/forward-fix: a later additive
migration can drop these two tables; no existing data depends on them.

## Authorization boundaries and audit events

Tenant comes only from `TenantContext`, bound to `app.current_org()` by the
tenant-guarded transaction after it opens; every statement also filters/writes
`organization_id` explicitly so the policy's `WITH CHECK` fails a mismatch.
Authorization roles stay in `TherapyService` (unchanged). Audit facts remain the
append-only `therapy_audit_event` rows written by the service; the JDBC adapter
appends them in the same guarded transaction as the domain write. The signed-note
UPDATE is restricted to `signed = false`, so re-saving an aggregate can never
rewrite a signed note and V77's `guard_therapy_signed_note` trigger is never fired
on an already-signed row.

## Migration and rollout considerations

V85 is the reserved version and is applied by Flyway in numeric order after V84.
`db/check.sh` applies it and verifies RLS, policies and role separation. No
production table is altered, so rollout needs no backfill or lock-heavy step.
Immutability and cross-tenant rejection are enforced by database triggers and RLS,
not by application grants alone.

## Findings

- **Pre-existing, not caused by this change:** `python3 -I -m unittest discover -s scripts/tests -q` reports 3 failures, all in `test_check_pack.py` (`opencode.json is stale`). The worktree `opencode.json` carries Git's skip-worktree flag and is the CI profile copied by `agent-run.sh`; this is the already-documented false positive in `MEMORY.md` (OPS-CW-003-01) and the delivery skill. `opencode.json` is protected and was not touched.
- V77 already creates all 11 therapy tables; V85 adds only the two genuinely missing pieces (evaluation-problem storage and an atomic durable version counter) rather than duplicating schema. The reserved-version gap for V85 was unfilled before this change and is now filled.
- Specialist review (simulated) recommended the established V5 `next_config_version` function as an alternative to a counter table; the counter table was chosen because it makes allocation atomic per call without requiring allocate and save to share one transaction. A second recommendation to remove `final` from the Spring beans was applied after the integration test exposed a CGLIB proxy failure.
- **Out of scope, for the integrator/owner:** `contracts/openapi.yaml` still describes `POST /api/v1/therapy/referrals/{id}/accept`, while the live controller serves `POST /api/v1/therapy/episodes` and `GET /api/v1/therapy/episodes/{id}`. This pre-existing drift predates BUILD-31 and cannot be changed inside this story's paths; the OpenAPI entry and regenerated client need a separate owner decision.
- `scripts/wiring-baseline.json` now has three stale lines (controller-builds, inmemory-in-main, store-without-durable for therapy). `check-wiring.py` exits 0 with notes only; the baseline is owned by the integrator and was not edited.
- No decision or evidence is missing for the story itself.

## Lessons for workers

- Read the reserved migration of the predecessor story first: V77 already owned the therapy tables, so the real V85 deliverable was the two fields V77 could not persist (`Evaluation.problems`) and durable atomic version allocation — not a duplicate schema.
- A Spring bean reached by an AOP advisor cannot be `final`: the integration context failed with `Cannot subclass final class JdbcTherapyStore` until `final` was removed from the store and service. Run one real-`@SpringBootTest` integration test before claiming wiring is done; mocked unit tests cannot catch this.
- When stubbing one mocked `NamedParameterJdbcTemplate` for many differently-shaped queries, give each SQL a unique table/alias fragment and stub with `contains(...)`; also remember `SqlParameterSource.getValue` throws for an absent key, so guard with `hasValue(...)`.
- Treat `scripts/check.sh`/`apps/api/check.sh` as forbidden in worker mode: they call `mvn verify` (all integration tests). Run the targeted test classes, `jacoco:report`, `db/check.sh`, SpotBugs and the policy scripts individually instead.
- In a cloud worker, `check-pack.py`/`gen-opencode.py`/`test_check_pack.py` staleness of `opencode.json` is the known skip-worktree CI-profile artifact, not a defect in the diff.
