# SPEC-XCH-07-C01 — XCH-07 clause 1 API evidence

## Summary

Added a standalone HTTP-level integration test and a clause evidence document proving XCH-07
clause 1: numeric observations enter a patient's trend only after test identity, source unit and
an effective comparability rule are established; every non-comparable result stays visible with a
closed exclusion reason and is never plotted. Test first, then documentation; no production code,
contract, migration or existing test was changed.

## Affected requirements

XCH-07 (first sentence only). Clause 2 (display fields) and clause 3 (qualifiers/qualitative
results) are deliberately left to their own stories and are covered here only where an exclusion
must retain its original fields.

## Risk class

Routine — test and documentation only. The evidence crosses the HTTP → service → analyzer → RLS
SQL boundary, but no runtime behavior, schema or contract changes.

## Lessons for workers

- A POST that returns `ComparabilityRule.version` and a GET that returns `TrendView.ruleVersion` are
  different JSON fields; capture the POST version and compare it with the GET ruleVersion, and use
  distinct test codes when rules are tenant-wide so JUnit method order cannot change the version.
- A rule-less negative test must post at least one observation; otherwise "every exclusion has the
  reason" passes vacuously on an empty list.
- For an evidence-only clause test with no production change, a genuine red run can be produced in a
  throwaway worktree by mutating one production gate, running the targeted suite, capturing the
  failing assertion and removing the worktree — the delivered tree stays production-clean.
- `-Pno-security,fast -Dgroups=integration` is a false green; use `-Pno-security -Dgroups=integration`
  and read the Surefire `tests=` count. A bare `spotbugs:check` is vacuous; compile first.
- `scripts/worker-check.sh` runs every integration test; a swarm worker should run its constituent
  stages individually and leave the full gate to the integrator.
