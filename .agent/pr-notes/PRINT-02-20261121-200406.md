# PRINT-02 — API: print endpoints, permissions and the print audit trail

## Summary

Added a thin HTTP surface over the PRINT-01 handout service in the new
`com.aurevia.printing.web` package. `POST /api/v1/printing/handouts`
renders one immutable, versioned handout; `POST /api/v1/printing/handouts/download`
re-checks permission, verifies the requested version and returns the deterministic
PDF bytes. Identity is rebuilt from `TenantContext` plus the current
`StaffRepository.activeRoles` inside a tenant-guarded transaction — no role,
facility or patient identifier is read from the request. A default-deny
`PrintPolicy` maps active roles to handout kinds, checks the facility of the
record and conceals a foreign tenant as 404. A closed three-value reason list is
required. Every print, reprint, download and refusal writes exactly one sanitized
OPS-02 fact through `PrintAuditTrail` → `PrintAuditAppender` → `AuditAppender`,
carrying identifiers, reason, action, facility and server time and no content.
`contracts/openapi.yaml` gained both paths, their schemas and the error responses.
No dependency, migration, table or file outside the declared scope was changed.

## Authorization boundaries and audit events

- Tenant: the record's organization must equal the derived actor's organization;
  a mismatch is concealed as `404 NOT_FOUND` (UAT step 16, ARC-02), not a tenant
  conflict. The internal `HandoutService` `403 WRONG_TENANT` remains as defence
  in depth for non-HTTP callers.
- Role: `clinician` may print every kind; `lab_collector`/`lab_verifier` only a
  lab order; `radiology_staff`/`radiology_interpreter` only an imaging order;
  reception, clinical assistant, PT, pharmacy, finance, tenant admin and privacy
  auditor are denied. Roles come only from `StaffRepository.activeRoles`.
- Facility: the facility of the record (`HandoutSource.facility`) is checked via
  `FacilityRepository.findByCode` in the active tenant; no caller preference or
  client-supplied facility selector is used. See Findings for the precise limit
  of this check.
- Reason: closed list `give_to_patient`, `referral`, `patient_request`; missing,
  blank or unknown is rejected with `422 INVALID_REASON` before any render.
- Audit: `purpose = reason`, `action = HANDOUT_PRINT|HANDOUT_REPRINT|HANDOUT_DOWNLOAD`,
  `resourceType = HANDOUT`, `scope = record facility`,
  `resourceId = kind:handoutId:v<version>:r<sourceRevision>`, `outcome =
  SUCCESS|DENIED`; `actor_id` is derived by the V3 trigger from the transaction
  local `app.actor` set by `TenantGuardTransactionManager`. The audit entry value
  type has no field for clinical content, patient name/identifier, filename, URL
  or object key. Denials are appended inside the transaction and thrown after it
  so the row survives.

## Findings

1. **Client-supplied source snapshot (P1, out of scope).** `HandoutService`
   takes `state`, `attested`, `printChannel`, `patientId`, clinical lines and
   checksum from `HandoutSource`; the only current producer of that value is the
   HTTP request body. A caller with a print role could therefore describe a
   draft as signed or inject content. No authoritative loader exists for the
   five kinds, and adding one would touch prescription/orders/chart/report
   packages outside this scope. Not fixed here — task-request 1. The permission
   and audit facts are still correct for a truthfully supplied source, and
   `HandoutPolicy` still checks the domain state vocabularies.
2. **Facility check is existence-only (P1, out of scope).**
   `FacilityRepository.findByCode` proves the record's facility exists in the
   active tenant; it does not prove the caller is assigned to that facility or
   has a care relationship to the patient. The model exposes no per-subject
   facility or care-relationship reader. The endpoint uses the record's facility
   (never a caller header) and denies an unknown facility, but UAT steps 15
   (Facility B) and 16 (care relationship) are not fully enforceable in scope.
   Not silently presented as a fully enforced scope — task-request 2.
3. **No durability / audit read model (P2, out of scope).** Reprint labeling uses
   a process-local marker; `HandoutService` uses `LocalHandoutArchive`. After a
   restart a re-render keeps the deterministic version but `producedAt`/
   `producedBy` change. No Flyway/RLS/JDBC store could be added inside scope —
   task-request 3.
4. **Generated staff client not regenerated (P2).** `contracts/openapi.yaml` is
   the authoritative staff contract, so it was edited directly. The derived
   `apps/staff-web/src/api/generated/openapi.d.ts` is outside scope and was not
   regenerated. No local or CI gate in `worker-check.sh`/`frontend-check.sh`
   runs `gen:api:check`; the integrator may regenerate with the pinned tool
   (`cd apps/staff-web && npm run gen:api`). The X-04 generated artifacts under
   `contracts/openapi/generated/` were not touched — they come from
   `CommandCatalog.java`, a different pipeline.
5. **Reserved Idempotency-Key header.** Both new POST operations declare
   `Idempotency-Key` to satisfy `OpenApiContractRulesTest`; the controller does
   not yet deduplicate on it. This mirrors the existing `IdempotencyKeyOptional`
   reserved-header convention in the contract; durable replay safety belongs to
   the durable print-record follow-up (task-request 3).
6. **Wrong-tenant status choice.** The HTTP boundary returns `404 NOT_FOUND` for
   a foreign-tenant record (concealment per ARC-02 and UAT step 16); the reused
   `HandoutService` still returns `403 WRONG_TENANT` to non-HTTP callers.
7. **Environment-only red gates.** `quick-check.sh` and `python-coverage.sh`
   fail as described in Test evidence because the worktree `opencode.json` is the
   CI profile under `skip-worktree` and the Python `coverage` package is absent.
   Both were reproduced independently of this change; no protected file was
   edited or regenerated.

## Lessons for workers

- Standalone MockMvc must register `.setControllerAdvice(new ApiErrorHandler())`
  or `ApiException` never becomes a 403/404/409/422 response; the assertion then
  fails with an unhandled exception instead of the documented status.
- Keep *every* audit append inside the `TransactionTemplate`; throwing from
  inside rolls the DENIED row back. Record the fact, capture the failure in a
  `Sink`/`AtomicReference`, return from the callback, then throw after commit.
- When refactoring for transaction correctness, re-run JaCoCo immediately: the
  new `result == null` early return in `download` initially left one branch
  uncovered and needed an explicit forbidden-role download test.
- SpotBugs excludes `EI_EXPOSE_REP2` only for class names ending in
  `Service|Repository|Controller|Store|Interceptor|Guard|Appender|Configuration`.
  Name a new injected audit writer with an allowed suffix instead of adding a
  `@SuppressFBWarnings` (which `check-wiring.py` rejects).
- `ResourcelessTransactionManager` is not on this classpath; the existing
  `PassthroughTransactionManager implements PlatformTransactionManager` pattern
  (returning `SimpleTransactionStatus`) is the DB-less unit-test equivalent.
- Before believing a `check-pack`/`test_check_pack` failure, run
  `git ls-files -v opencode.json`; `S` means the CI profile is active under
  `skip-worktree` and the worktree check is not HEAD truth.
- New OpenAPI POST operations need tags, a shared-`Error` body for documented
  4xx responses, and an `Idempotency-Key` parameter or
  `OpenApiContractRulesTest` fails; descriptions must avoid person-name and
  patient-identifier-shaped prose (`OpenApiErrorRulesTest`).
