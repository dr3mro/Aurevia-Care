# LABFLOW-10 — Browser journey and operations guide for the laboratory workflow

## Summary

Added a Playwright browser journey for the synthetic laboratory workflow and the
plain-language operations guide it documents. The journey opens the real
staff-web routes (`/lab/accessions`, `/lab/results/entry`, `/lab/release`,
`/lab/turnaround-board`) with three independent browser contexts standing in for
two laboratory users and a clinician, collects a matched specimen, rejects and
recollects a second specimen, enters and independently verifies observations,
reads the released report and what the patient can see, records a correction and
a withdrawal, and checks the turnaround board and partner-outage route. A
deterministic in-browser harness serves only `/api/v1/lab/**` and records every
command; no live patient, partner, credential or database is used. The guide
`docs/operations/lab-workflow/README.md` states the steps, the outage route and
the correction rules in plain language. No dependency was added and no file
outside the declared scope was changed.

Files added (all inside scope):
- `apps/staff-web/e2e/labflow/synthetic-lab-api.ts`
- `apps/staff-web/e2e/labflow/lab-journey.spec.ts`
- `docs/operations/lab-workflow/README.md`

## Affected requirements

| Requirement | Acceptance in this story | Where it is covered |
|---|---|---|
| LAB-01 | Issuer-scoped accession matched at the bedside; rejection retains reason and notification; recollection creates a linked specimen under one order | Journey steps 1–5; safety test "mismatched patient identifier blocks collection" and "empty rejection reason blocks the reject command" |
| LAB-02 | Enter and independently verify observations; release; corrected and entered-in-error states with a reason; per-audience release status | Journey steps 6–9; safety test "withdrawal removes a report from clinician and patient view" |
| WEB-09 | Blocked actions keep typed work and stay disabled; explicit state text; worded (not colour-only) overdue/outage cues; status announced in `role="status"` regions | Every `expect(...).toBeDisabled()/toContainText()`; turnaround-board step; correction/withdrawal reason guards |

Acceptance criterion 1 ("write the journey with two lab users and a clinician; check what the clinician and patient see after each step") is met by the three contexts and by asserting both `release-status-clinician` and `release-status-patient` after release, correction and withdrawal. Criterion 2 (the guide with steps, outage route and correction rules) is met by the new README.

## Risk class

Routine for the change itself: test-only files plus an operations document, no
production, contract, database, identity or clinical-policy code changed. The
workflow *described* is safety-relevant (patient identity match, rejection,
result verification and release), so the journey deliberately includes negative
assertions for the identity mismatch, the empty rejection reason and the
entered-in-error withdrawal. All evidence is synthetic and simulated; no real
clinician, laboratory user or patient participated and none is claimed.

## Findings

- Pre-existing, out-of-scope gate defect: `apps/staff-web/check.sh` step 1
  `npm run gen:api:check` fails because the committed `contracts/openapi.yaml`
  gained printing-handout paths that the committed
  `apps/staff-web/src/api/generated/openapi.d.ts` does not contain. Verified by
  empty `git diff HEAD` for both files. Fixing it requires regenerating a file
  outside this story's scope, so it was not touched. The integrator/owning
  contract worker should run `npm run gen:api` in `apps/staff-web` and commit the
  regenerated client.
- Product limitation observed while writing the journey: the collection desk has
  no recollect button, and the result-entry/release screens are presentational
  with synthetic fixtures (no shared server state across the role contexts). The
  journey therefore drives recollect through the intercepted browser endpoint
  and represents the two lab users via separate contexts plus the on-screen
  distinct subjects. This is stated in the guide; wiring a recollect control and
  cross-context server state belongs to feature/API stories, not this test-and-
  guide story. No task request is raised because no existing task is needed to
  complete *this* story.
- No new defect in the touched area was found; all in-scope checks are green.

## Lessons for workers

- The staff-web Playwright config starts Vite itself; a browser binary alone is
  not enough on a bare runner — `playwright install-deps chromium` supplies the
  OS libraries, otherwise Chromium exits 127 on `libglib-2.0.so.0`.
- A successful lab command reloads the accession list and clears the local
  identity drafts, so any follow-up action (for example printing the label) must
  re-complete the bedside check first.
- The e2e files are excluded from the module tsconfig, so `npm run typecheck`
  does not check them. Run a targeted `tsc` with the repo's strict flags; with
  `exactOptionalPropertyTypes`, build `browser.newContext` options conditionally
  instead of passing `baseURL: string | undefined`.
- Check `gen:api:check` first when a staff-web gate is unexpectedly red; a
  committed contract/generated-client drift can fail `check.sh` before any of
  your own steps run, and the owning file is usually outside a worker's scope.
