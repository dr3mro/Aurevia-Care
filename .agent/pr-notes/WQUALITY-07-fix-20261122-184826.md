## Lessons for workers

- In a cloud worker, `git ls-files -v opencode.json` showing `S` explains `check-pack.py` and `test_check_pack` failures; verify with `git show HEAD:opencode.json` and never regenerate or commit that file. Do not re-diagnose it on a later pass (OPS-CW-003-01).
- A swarm PR that edits `scripts/` is never auto-merged, so a debugger report urging out-of-scope test fixes must be recorded as a finding, not followed: it would block the task. Check the task file's `scope:` line and the delivery skill's protected-file list before editing anything outside the named document.
- For a documentation-only change, `python3 -I scripts/check-docs.py` plus `check-secrets.py` and the 31 `test_check_docs.py` tests are the applicable gates; a green docs gate does not make the repository-wide unit suite green when pre-existing out-of-scope tests fail.
- Before treating a red full suite as your own regression, locate the failing files and check them with `git show origin/main:<file>`; if they are owned by other tasks and outside your `scope`, record the command, error and exact next step under Findings instead of editing protected files.
- A checklist about CI must derive required checks from the branch-protection gate job and each job's `if`/matrix conditions, not from the list of jobs that appear in a run; confirm which workflow actually publishes a digest before telling a person to record one.
- When a reviewer raises Optional factual slips, verify each against the source before editing, apply in-scope corrections, and re-run the applicable gates after the final edit.
