## Summary

BUILD-15 closes the MSG-05 acceptance gap for "acknowledging an old revision does not satisfy a new one."

Survey first: the MSG-05 implementation this story describes is **already present in the baseline** (committed by `d2f5bf1b` READY-39 / `0ff238d4` S-G3-08). `messaging/acknowledgment` already records publication, notification dispatch, first in-app view and explicit acknowledgment as four separate immutable facts (`InstructionFacts.FactType`), binds each acknowledgment to an exact `revision` with a stale-revision guard in `InstructionFactService.acknowledge`, routes overdue requested acknowledgments to the owning unit (`overdueFollowUps`), and keeps a receipt-only scope (`AcknowledgmentScope.RECEIPT`). The existing test `acknowledgmentBindsToTheExactPublishedRevision` proves "ack old rev 1 → 409 STALE_REVISION; ack current rev 2 → success."

What was **not** locked down was the complementary, more precise acceptance scenario: a receipt recorded while revision 1 *is current*, followed by publication of revision 2 — proving the revision-1 receipt does not satisfy revision 2 and does not suppress revision 2's overdue follow-up. This change adds exactly those two regression tests (test-first), using synthetic identifiers only. No production code was added or modified; the smallest change that closes the story's acceptance evidence is a test-only addition.

## Findings

- The MSG-05 production slice and most acceptance tests already existed on the base branch before this task (history: READY-39, S-G3-08). This task did not need any new production code; adding any would have duplicated an existing, well-tested domain and risked the 100% JaCoCo gate.
- Existing test `acknowledgmentBindsToTheExactPublishedRevision` covers the "ack a stale revision after a newer one exists" direction. The opposite direction — "ack while current, then publish newer, old ack does not carry over" — was the missing acceptance evidence and is now covered by the two new tests (all identifiers synthetic, no patient data).
- Environmental (not a defect of this change): `opencode.json` is flagged `S` (skip-worktree) in this cloud worker and holds the CI profile, which differs from the committed HEAD file. `check-pack.py` and the five `test_check_pack` tests therefore report it stale. Proven against the committed file: `committed HEAD opencode.json == generator output: True`, `check-pack on tree with committed file: []`. The committed file is authoritative for the integrator.
- `scripts/check-wiring.py` emits a pre-existing note that `messaging/evidence/G3EvidenceService.java` is fixed and should be removed from `scripts/wiring-baseline.json` (the rename already happened in AUD-20261121-03). Exit 0; `scripts/` is maintainer-owned and outside this task's scope, so no change was made.

## Lessons for workers

- In a cloud worker, before treating a `check-pack.py` / `test_check_pack.py` "opencode.json is stale" failure as your defect, run `git ls-files -v opencode.json`. Flag `S` means the worktree holds the CI profile copied by `agent-run.sh`; judge the committed file with `git show HEAD:opencode.json` and the generator, and record the artifact in notes instead of editing the file (it is maintainer-owned and outside task scope).
- When a story maps onto an already-implemented feature, survey the domain first and add only the precise missing acceptance test. Do not manufacture production changes to look busy — they endanger the 100% coverage gate and duplicate existing code.
