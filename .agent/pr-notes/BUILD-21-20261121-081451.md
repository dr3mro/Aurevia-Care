# BUILD-21 — Patient app: enrollment, recovery and account lockout screens

## Summary

Completes PAT-03 acceptance for the patient app's pre-authentication account screens.
The enrollment (invitation entry), recovery, lockout, step-up re-authentication and
support-request screens already existed under
`apps/patient-mobile/src/features/enrollment`; the missing acceptance artifact was a
proof that **no screen reveals whether a record exists**.

The concrete defect found and fixed: `EnrollmentScreen` and `RecoveryScreen` rendered
distinct messages for `expired`, `reused`, `locked` and `error`, so an observer could
infer a code/account's state (enumeration). Both screens now render one generic
failure line for every failed status; the detailed reason stays server-side.
`mapInvitationError` was reduced to a single generic failure for the same reason.
All work is inside the declared scope; no dependency, tracker, protected file or
out-of-scope source was changed. All identifiers in code and tests are synthetic.

## Findings

1. **Out-of-scope wiring gap (needs an owner).** `apps/patient-mobile/src/app/RootNavigator.tsx`
   never renders `StepUpPrompt`, and `app/providers.ts` has no step-up string provider.
   The prompt and its tests exist, but no sensitive change in the running app reaches a
   sign-in-again prompt; the server-side assertion comment documents the required
   enforcement. Both files are outside `scope`, so nothing was changed. Evidence:
   senior-mobile reviewer static read + this agent's grep; no runtime user test.
2. **Dead shared string fields.** `EnrollmentStrings`/`RecoveryStrings` still declare
   `expired`/`reused`/`locked` and `providers.ts` still supplies them in English and
   Arabic, but the screens no longer render them. Removing the fields requires editing
   `app/providers.ts` (out of scope); left in place deliberately to keep the build
   green. Recommend removal in the same follow-up as finding 1.
3. **`mapInvitationError` has no production caller** (pre-existing; only tests call it).
   It is now generic and consistent with the UI. A future caller must map its single
   `enrollment.invalid` key to a localized string; no other key is returned.
4. **Lockout disclosure boundary.** `LockoutScreen` still shows "Access is locked"
   plus a countdown. Non-disclosure relies on the parent not routing a generic
   enrollment failure to it; the parent is out of scope, so this was verified at the
   component level only (`privacy.test.tsx`).
5. **Tooling artifact.** `scripts/check.sh` fails only on the known skip-worktree
   `opencode.json` staleness (see Test evidence). Not caused by this change; protected
   file untouched.
6. **Intentional test rewrites.** The `mapInvitationError` cases in `model.test.ts`
   and the four state cases in each of `screens.test.tsx`'s enrollment and recovery
   suites were rewritten because behavior deliberately changed to generic failures.
   No test was weakened to hide a failure; the new assertions are stricter (one
   indistinguishable message). Per AGENTS.md rule 7, recorded here explicitly.
7. No dependency was added; none of the existing packages could be avoided because
   no new capability was introduced.

## Lessons for workers

- Before changing a feature's exported TypeScript interfaces, grep for consumers
  outside the scope. Here `app/providers.ts` and `app/RootNavigator.tsx` own the
  en/ar label contract, so the interface had to stay unchanged.
- In this patient-mobile setup `render(...)` is awaited and queries must use the
  `screen` global. Several renders in one test with manual `cleanup()` made `screen`
  miss mounted nodes; one render per `it.each` case is reliable.
- A `scripts/check.sh` "opencode.json is stale" result in a cloud worker is usually
  the CI profile copied under `skip-worktree`. Verify with `git ls-files -v` and
  `git show HEAD:opencode.json` and report it, rather than regenerating a protected
  file outside your scope.
- "No screen reveals whether a record exists" is testable as "every failure renders
  the same fixed message and no record-shaped marker appears"; write that as an
  explicit acceptance test rather than relying on per-state message tests.
