# SPEC-IAM-04-C03 — API proof: a second authorized reviewer approves consolidation

## Summary

IAM-04 clause 3 ("A second authorized reviewer approves consolidation.") is already
implemented in the repository. This task adds a focused, active (non-disabled) Java test
that proves the rule through the normal service entry point, plus the required clause
evidence document. Positive proof shows a different, authorized reviewer approving a ticket
and both reviewers retained as provenance; negative proofs show refusal of the opener,
an unauthorized role, and a subject without active membership. Synthetic fixtures only.

No production code, existing test, contract, migration, tracker or workflow was changed.

Entry-point-to-test trace:
`POST /api/v1/duplicate-reviews/{reviewId}/consolidate`
(`com.aurevia.smartclinic.patient.consolidation.ConsolidationController.consolidate`,
which receives `ConsolidationService` by injection)
→ `ConsolidationService.consolidate` re-authorizes the approver, compares the acting
subject with `DuplicateReview.openedBySubject`, locks the pair and appends the event
→ `DuplicatePolicy.allows(APPROVE, role)` bounds the action to `tenant_admin` /
`privacy_auditor`
→ `SecondAuthorizedReviewerApprovesConsolidationTest` drives that service method with a
real policy and a synchronous `TransactionTemplate`, mocking only the repository boundary.
The HTTP-level and real-PostgreSQL proof already exists in
`it/patientidentity/ConsolidationIsolationTest` and is run by the integrator's database gate.

## Lessons for workers

- Clause-proof tasks are green by design when the rule is already implemented: the
  "failing test first" step cannot be produced without changing production code, which is
  out of scope. State that explicitly instead of inventing a red run.
- Confirm the `opencode.json` "stale" failure once with `git ls-files -v opencode.json` and
  a comparison of `git show HEAD:opencode.json` to the generator render, then run every
  later gate stage individually; do not regenerate the protected file or re-diagnose it.
- For a mocked-repository proof, assert the *absence* of the side effect as well as the
  status code (no pair lock, no association/event append, DENIED audit) — that is what
  distinguishes a refused authorization from a failed precondition.
