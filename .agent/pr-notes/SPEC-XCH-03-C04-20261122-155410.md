# SPEC-XCH-03-C04 — XCH-03 clause 4 (API test)

## Summary

Added one focused, active API-level proof of XCH-03 clause 4, "Revocation blocks
future sender-hosted retrieval and records downstream notification", and its
clause evidence document. The clause is already fully implemented in production;
this change adds proof only. No production code, existing test, OpenAPI contract
or Flyway migration was changed, no dependency was added and no test was skipped
or disabled.

Source survey (task step 1) located the clause in:
`apps/api/src/main/java/com/aurevia/smartclinic/exchange/response/ExchangeResponseController.java`
(routes `POST /{id}/revoke`, `GET /{id}/retrieve`, `GET /{id}` under
`/api/v1/xch03/orders`), `ExchangeResponseService.java` (`revoke` inserts the
notification and writes `REVOKED`; `retrieve` re-checks `REVOKED` on every call
and raises 410; `run` enforces the version compare-and-set; `authorize`
re-derives membership and roles), `ExchangeResponseActionPolicy.java`
(`REVOKE_ROLES = {clinician, tenant_admin}`), `ExchangeResponseInputs.java`
(revoke-field validation), `ExchangeState.java` (terminal `REVOKED`),
`ExchangeResponseCommands.java` (`RevokeRequest`, `Notification`, `OrderView`)
and `db/migrations/V21__xch03_order_response.sql` (`xch03_notification` with
`UNIQUE (organization_id, event_id)`, ENABLE/FORCE RLS via `xch03_app_org()`,
actor and append-only triggers). An existing broader positive proof is
`it/exchangetask/ExchangeResponseExchangeTest.revocationBlocksRetrievalAndRecordsDownstreamNotification`;
the new class adds a dedicated-DB clause proof with three refuting negatives.

## Findings

1. **Known worker-environment false positive (not a change defect).**
   `bash scripts/quick-check.sh` and `bash scripts/worker-check.sh` stop at
   `check-pack: opencode.json is stale: run scripts/gen-opencode.py`. Verified once:
   `git ls-files -v opencode.json` → `S opencode.json` (CI profile installed under
   `skip-worktree`); worktree `opencode.json` is byte-identical to
   `.github/opencode.ci.json`; HEAD holds the local profile; `git diff HEAD --
   opencode.json` is empty. The six `test_check_pack` failures in
   `python3 -I -m unittest discover -s scripts/tests -q` and the
   `scripts/python-coverage.sh` failure are the same artifact. No protected file
   was regenerated or committed; the integrator owns these gates.
2. **Whole-repository integration suite not run by this worker.** `worker-check.sh`
   fast-fails at finding 1 before reaching `-Dgroups=integration`. Running every
   integration test (>10 minutes) is forbidden for a swarm worker. The targeted
   integration class for the touched area passed with four active methods, and
   `db/check.sh` passed; the integrator and Delivery run the full gate.
3. **OpenAPI contract gap (separate task, out of scope).** The XCH-03 order routes
   including `POST /api/v1/xch03/orders/{}/revoke` and
   `GET /api/v1/xch03/orders/{}/retrieve` are not in `contracts/openapi.yaml`;
   they are baselined in `contracts/openapi/missing-routes.txt` (lines 349 and
   121). The clause doc states this accurately. The contract is protected and was
   not edited.
4. **Pre-existing committed conflict markers (not caused by this work).**
   `git grep -nE '^(<<<<<<<|>>>>>>>) '` finds markers committed in HEAD in
   `apps/api/src/main/java/com/aurevia/smartclinic/exchange/hl7/Hl7ParseException.java`,
   `Hl7Parser.java` and `Hl7Segment.java` (inside Javadoc, so the build still
   compiles). They are production files outside this task's scope and were left
   untouched.
5. **Sibling concurrency risk.** Tasks SPEC-XCH-03-C03 and C05 write other clause
   tests into the same new `exchange/clauses` and `docs/spec/clauses/exchange`
   directories. This test uses the unique database name
   `smartclinic_xch03_revoke_clause_it` to avoid colliding with their fixtures.

## Lessons for workers

- For a dedicated-DB clause test copied from a neighbouring integration test,
  choose a new database name and use it consistently in the `@SpringBootTest`
  property, the URL constant and both `DROP DATABASE ... WITH (FORCE)` calls;
  sibling workers may copy the neighbour's name into the same directory.
- A cross-tenant negative only proves RLS concealment if the actor is a valid
  member with the required role in its own tenant and sends its own
  `X-Active-Organization`; otherwise the 404 could be an authorization artifact.
- In a wrong-role negative, send the current `If-Match` version so the 403 is
  unambiguously caused by the role rather than by the precondition check that
  runs later.
- In a cloud worker, `opencode.json` under `skip-worktree` is the CI profile, not
  HEAD truth. Confirm once with `git ls-files -v`, `cmp` with
  `.github/opencode.ci.json` and `git show HEAD:opencode.json`, then run the
  remaining gate stages individually and do not regenerate or commit that file.
  Re-diagnosing it on a later pass wastes a run.
