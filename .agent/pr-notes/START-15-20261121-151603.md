# START-15 — Docs: personal data inventory (what is stored, where, how long)

## Summary

Added `docs/security/data-inventory.md`: an engineering inventory, for a privacy
officer to review (explicitly **not legal advice**), of every table in the
database that holds personal or clinical data. For each table it records, in
plain words, the data kind, the role keys that can read it (taken from the
authorization code), whether the table is append-only, whether it is covered by
tenant export (OPS-07) and by retention, and the audit events that record access.
The newest migration covered (**V90**, `V90__onboarding_import.sql`) is stated at
the top. Where export or retention is not implemented, the cells read `NOT YET:`
with a suggested task title (`TASK-EXPORT`, `TASK-RETENTION`, defined in a
legend). No code, migrations, dependencies or shared indexes were changed.

## Lessons for workers

- For a migration-derived inventory, extract `CREATE TABLE` column lists and
  the `GRANT ... UPDATE` / `no_update_delete` trigger sets programmatically
  first; full SQL dumps are too large to read linearly and raw glob order is
  lexical (V10 before V1) — sort by numeric version.
- Append-only is best derived from the absence of an `UPDATE` grant (all tables
  also revoke `DELETE`/`TRUNCATE`), not from trigger-name heuristics alone,
  which conflate RLS arrays with immutability arrays.
- Distinguish "declared field" from "implemented control": a `retention_policy`
  column is not a retention job. Say `NOT YET:` rather than implying coverage.
- Use inline code paths instead of Markdown links in new docs pages so
  `scripts/check-docs.py` cannot report broken links to files other workers
  have not created yet.
- `python3 -I scripts/check-docs.py` skips `.agent/` and `docs/archive/`, so this
  notes file cannot turn the docs gate red; verify the actual page instead.
