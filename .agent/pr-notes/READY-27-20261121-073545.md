# READY-27 — Results: /results inbox and /results/critical queue

## Summary

Added the staff-web results feature under `apps/staff-web/src/features/results`. `/results` shows the XCH-04 reconciliation queue (open/resolved filter) and a result-review panel that opens one immutable revision by opaque ID and acknowledges it with the observed `If-Match` version. `/results/critical` shows the XCH-05 operational report ordered by due time, with a 30-second countdown (interval cleared on unmount), explicit OVERDUE text, roster-gap/failed-notification sections, and a single-result detail panel offering acknowledge, assign, escalate (reason required) and read-back commands. Both pages implement the seven WEB-09 states, en/ar messages, RTL layout and tenant remounting. Synthetic data only; no new dependency.

## Affected requirements

XCH-04 (result routing, reconciliation, acknowledgment), XCH-05 (critical verification, owner, due time, escalation, read-back, acknowledgment). Supporting: ARC-03 (cursor/version semantics), WEB-08/WEB-09 (chunk budget, resilient screens), UX-01 (en/ar, RTL), ADM-02/OPS-05 (operational queue view).

## Risk class

Safety-critical (critical-result queue and clinical acknowledgment) per `docs/WORKFLOW.md`. Mitigations: negative and failure tests for every command, `409/412` conflict state that keeps typed input, version precondition sent from the displayed revision, overdue marked with text and colour, and no display of acknowledgement as "done". No clinical or human participant was involved; all review evidence is tool output or simulated specialist review. Real site sign-off remains a G5 gate.

## Review owner

Senior React and Vite (implementation/stack), Senior TypeScript (strict types and API boundary), Senior Spring Boot / Integrations (server contract read only, unchanged). Clinical safety reviewer is a separate G5 human gate and was not available here.

## Data changes

None. No migration, backfill, schema change or rollback/forward-fix. Read-only UI over existing XCH-04/XCH-05 endpoints.

## Authorization boundaries and audit events

The active organization is sent on every request through `buildRequestDescriptor` (`X-Active-Organization`); switching organization remounts both pages so no prior tenant's rows persist. Every state-changing command carries `If-Match` from the version observed on screen. Authorization, verification, escalation and acknowledgment decisions remain server-side in `CriticalResultService`/`ResultRoutingService`; no new audit event is introduced. No patient identifier is placed in a URL, page title, log or browser storage; the opaque result/critical ID is the only path parameter, and patient ID appears only inside the authenticated table body.

## Migration and rollout considerations

None. Route chunks stay within WEB-08 (final gzip: `ResultsInboxPage` 1.85 kB, `CriticalQueuePage` 2.54 kB; budget 250 kB). Feature routes self-register via `features/results/routes.ts`; the shared route registry and navigation were not edited.

## Findings

- **No result-list endpoint exists.** The server exposes `GET /xch04/reconciliations` (bounded 200, status filter, no cursor) and `GET /xch04/results/{id}`, but no list of final reports needing review. The inbox therefore surfaces unmatched/conflicting reports from the reconciliation queue and provides an explicit opaque-ID lookup for one result revision and its acknowledge action. "Cursor paging if the API offers it" is not implemented because the API does not offer a cursor; this is stated in the UI code comment and here rather than faked.
- **Shared route-registry fixtures updated outside scope.** Adding `features/results/routes.ts` changes `createRoutes(false)`, so the hardcoded expectations in `apps/staff-web/src/app/routes.test.tsx` and `apps/staff-web/tests/app/AppShell.test.tsx` had to gain `/results` and `/results/critical`. This follows the precedent recorded in `.agent/pr-notes/READY-23-20261121-024004.md` (READY-21/22/23 updated the same registry). No other file outside `apps/staff-web/src/features/results` was changed; `app/routes.tsx`, `app/navigation.ts`, trackers, scripts and workflows are untouched.
- **Escalate form maps the required reason to the API's non-sensitive `detail` field** and prefills channel/recipient from `escalationTarget` (backup when overdue, primary otherwise). Outcome is fixed to `delivered`; a failed delivery is recorded by the server workflow, not fabricated by the UI.
- **Arabic countdown** uses `Intl.RelativeTimeFormat` with `numberingSystem: 'latn'` (a documented TS 5.7 lib gap cast) so digits never mix with Latin identifiers. The TS cast is localized to `domain.ts` and has no `any` or `@ts-ignore`.
- **Review resolutions (simulated reviewers, not human/clinical evidence).** `smartclinic-senior-react` raised four issues; `smartclinic-senior-typescript` found no high-impact type/wire defects and confirmed field-for-field parity with the Java view records and correct `If-Match` propagation. All four React findings were fixed and retested:
  1. Overdue rows had text but no colour → the OVERDUE badge now uses inverted theme tokens (`foreground` background, `background` text) in `CriticalQueuePage.tsx`; asserted in the due-time test.
  2. Conflict Compare/Reload/Copy buttons were inert → both pages now render `ConflictState` directly with working callbacks (compare panel, version reload, clipboard copy) instead of the noop `StateView` path; each callback and the no-clipboard branch are tested.
  3. Escalation always sent `outcome: 'delivered'` and `systemDown: false` → the form now has an outcome selector and a system-down checkbox, threaded through `escalateCritical` into the request body; `domain.ts:outcomeFrom` avoids a cast at the call site; both values are asserted in API and page tests.
  4. The event trail reused "No failed notifications reported." as its empty label → added a dedicated `noEvents` en/ar message and tested an empty trail.
- **Evidence provenance:** commands and coverage numbers came from executed tools. Specialist findings above come from simulated reviewers, not a clinician, QA participant or simulated patient user.

## Lessons for workers

- The generated OpenAPI client does not declare the exchange paths; follow the admin feature's established pattern (build headers from a declared path, then override `url`) instead of adding a client dependency.
- Any new `features/*/routes.ts` also changes the exact expected arrays in `src/app/routes.test.tsx` and `tests/app/AppShell.test.tsx`; update both minimally or the staff-web gate fails even though the feature tests pass.
- With per-file 100% v8 coverage, an unexercised default such as `result.ownerSubject ?? ''` is a failed branch: test the null side explicitly rather than adding an exclusion.
- `StateView.forTransportError` gives a conflict state with **noop** Compare/Reload/Copy buttons; screens that need WEB-09's working conflict actions must render `ConflictState` directly (see `features/chart/NotePage.tsx`).
- If an API command accepts an outcome or a system-down flag, expose it in the form; hard-coding the happy value silently records a failed escalation as delivered.
