# SMSG-05 — API: email-like staff messages

## Summary

Added a staff-to-staff mail API under `com.aurevia.staffmsg.mail`: versioned drafts with
stale-write rejection, send with explicit recipient confirmation and no blind copy, reply, reply all,
forward that keeps attachment links, per-person inbox/sent/archive folders, flags, and threads grouped
by normalized subject and a shared reference. Recipients may be people, a role in a facility or a unit
mailbox; a role is expanded to its current holders at send time inside the tenant-guarded transaction
and the concrete subjects are frozen on the published message. All fixtures are synthetic. No file outside the declared scope was changed and
no dependency was added.

Implementation follows the repository's existing domain-kernel pattern (as in `pharmacyflow.clarify`):
a domain service behind a thin injected controller, with deterministic in-process state. The six
staff-messaging tables and their forced RLS policies already exist in `db/migrations/V91__staff_messaging.sql`
(SMSG-02), so no migration was added or reserved for this story.

## Risk class

Cross-boundary (new public REST surface, new role-lookup boundary through `StaffRepository`). No patient
data, prescribing, signed records or cross-organization sharing is involved, so clinical sign-off is not
required for this slice.

## Review owner

Senior Java and Spring Boot (skill loaded and applied). A bounded read-only review was completed by the
`orevia-senior-backend` specialist: it found one production-blocking role-lookup defect and five
smaller gaps; all six were addressed and re-verified (see Findings). Reviewer evidence is a specialist
report, not a tool result; no human clinical or staff-participant review was claimed.

## Data changes

None. No migration, backfill, lock or volume impact. The value types are shaped after the existing V91
tables but this slice does not read or write them; the production constructor resolves role holders from
the already-authorized staff projection inside a `TransactionTemplate`. Kernel state is process-local,
so durability across restart and a `Jdbc*` store are follow-ups (see task-requests and Findings).

## Authorization boundaries and audit events

Active organization and actor are read only from `TenantContext` in the controller; no command accepts
them from a request body. Drafts and messages are concealed with `404` outside the owner/participant set
and across tenants. Role expansion reads active staff through `StaffRepository.query` inside a
`TransactionTemplate` bound to `TenantGuardTransactionManager`, so forced RLS sees `app.current_org`.
No new audit events were added; audit, search and legal hold belong to SMSG-09. There is deliberately no
blind-copy kind in `RecipientKind` and any `bcc` field on compose **or** draft save is rejected with
`422 BLIND_COPY_NOT_ALLOWED`.

## Migration and rollout considerations

No migration or configuration change. The controller is registered under `/api/v1/staff/mail` and uses the
normal authentication chain; no feature flag is introduced. No production deployment was performed.

## Findings

1. **Durable persistence / OpenAPI publication are outside this story's scope.** The kernel keeps drafts,
   messages and folders in process memory; the V91 tables exist but no `Jdbc*` adapter writes them in this
   slice, and `contracts/openapi` is outside the declared scope. These are real follow-ups, not claimed
   as done here (task-requests below). The implementation mirrors other merged slices such as
   `pharmacyflow.clarify`, which use the same kernel shape.
2. **Facility-scoped role resolution is not yet enforced.** `RecipientDirectory.holders` receives the
   facility and the draft/message records it, but the current `StaffRepository` staff projection has no
   facility field, so `StaffRecipientDirectory` expands a role across active holders in the tenant. The
   interface supports facility-scoped resolvers; tightening this needs a staff-directory change (SMSG-06).
3. **No audit events for open/send/forward/move** in this slice; SMSG-09 owns mail governance.
4. **`opencode.json` gate artifact (environment, not a change defect).** The worktree file is under
   `skip-worktree` (`git ls-files -v` → `S`) and equals `.github/opencode.ci.json`, while `HEAD:opencode.json`
   is the local profile. `python3 -I scripts/check-pack.py` therefore reports
   `opencode.json is stale: run scripts/gen-opencode.py`, and five `test_check_pack` cases fail in the full
   `scripts/tests` suite. I confirmed the artifact with `cmp`, ran `quick-check.sh` with the HEAD bytes
   restored, then restored the original CI-profile bytes. The file was not regenerated or committed.
5. No other defects were found by the executed checks.

### Specialist review outcome (reviewer evidence)

A bounded read-only `orevia-senior-backend` review reported six findings. The reviewer ran no builds
and observed no test, coverage or HTTP evidence; the source-based findings were evaluated and re-verified
with the tool commands in Test evidence:

1. **HIGH — role lookup outside the tenant-guarded transaction.** `StaffRecipientDirectory` called
   `StaffRepository.query` in auto-commit, so forced RLS would see no `app.current_org` and role recipients
   would silently expand to nobody in production while mocked tests passed. **Fixed**: the directory now
   executes the lookup through the shared `TransactionTemplate` bound to `TenantGuardTransactionManager`;
   `MailService`'s production constructor injects it, and both the directory and production-constructor
   tests drive the callback through a mocked template.
2. **HIGH — process-local state / no `Jdbc*` store.** Confirmed; retained as the first follow-up task and
   explicitly not claimed as done. The `MailContract` Javadoc was corrected to say these are in-memory
   values shaped after the V91 tables, not projections of them.
3. **MEDIUM — flags global while `MailView` looked viewer-scoped.** The V91 schema stores `flags` on message
   metadata, so message-level semantics were kept; `MailView` Javadoc now states that folders are
   per-participant and flags are shared, and `flagsAreSharedMessageMetadataWhileFoldersStayPerPerson`
   asserts the behavior.
4. **LOW — `confirmationMatches` Javadoc contradicted duplicate handling.** Reworded to say order and
   duplicates are ignored; the existing test already asserts that behavior.
5. **LOW — save silently discarded `bcc`.** `SaveDraftCommand` now carries `bcc`; `saveDraft` rejects a
   non-empty value with `422 BLIND_COPY_NOT_ALLOWED`, and `savingADraftCannotIntroduceABlindCopy` covers it.
   The draft's facility stays immutable on save by design.
6. **LOW — thread grouping used only the reference.** `listThreads` now groups on a composite normalized
   subject + reference key; `independentMessagesNeedBothSubjectAndReferenceToShareAThread` covers the
   case where the reference differs.

## Lessons for workers

- Java records with `List` fields are checked twice: SpotBugs needs `List.copyOf` in the compact constructor
  **and** an overridden defensive accessor, and `test_java_conventions.py` counts literal `List.copyOf(`
  occurrences in the file (wrapping it in a shared helper does not satisfy that check). Keep at least two
  literal calls in every file that declares a list-bearing record.
- A nullable confirmation list is the convenient place for those literal calls: use
  `value == null ? null : List.copyOf(value)` in the constructor and accessor, and cover both sides with a
  test that omits the field and a test that supplies it.
- In a cloud/swarm worker, `opencode.json` is the CI profile under `skip-worktree`; check-pack and five
  `test_check_pack` cases fail for that reason. Restore `HEAD:opencode.json` only for the local gate, put the
  CI bytes back immediately, and never regenerate or commit the file. Record the artifact in Findings.
- When a scope forbids migrations, OpenAPI files and cross-package edits, the accepted repo pattern is a
  domain kernel with a thin controller; state the durability/contract follow-ups explicitly instead of
  claiming end-to-end completeness.
- `TenantContext` is a `ThreadLocal`; clear it in `@AfterEach` of standalone MockMvc tests so a failed
  `preHandle` cannot leak a context into the next test.
- Read-only repository lookups still need the tenant-guarded `TransactionTemplate`: RLS GUCs are set only
  in `TenantGuardTransactionManager.doBegin`, so a direct `jdbc.query` runs with no tenant and returns
  nothing under forced RLS. Mocked repository tests cannot reveal this; trace every query to a transaction.
