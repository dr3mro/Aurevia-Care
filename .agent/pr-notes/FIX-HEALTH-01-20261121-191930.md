# FIX-HEALTH-01 — unauthenticated health probes in the OIDC chain

## Summary

`GET /health/live` and `GET /health/ready` now need no token under every production profile. The exact two GET paths are permitted in both production filter chains: the stateless OIDC resource-server chain (`SecurityConfiguration.oidcSecurityFilterChain`, order 2) and the browser/staff-web chain (`StaffWebLoginConfiguration.staffWebSecurityFilterChain`, order 1). The browser chain is the one that actually receives a health probe in production, because a probe carries no `Authorization: Bearer` header and therefore matches the `securityMatcher = !isBearerRequest` order-1 chain first. Neither a `/health/**` wildcard nor any change under `/api/v1/**` was introduced. HTTP tests cover both chains with a local stub JWT decoder and a synthetic in-memory JDBC probe; no real issuer, database or patient data is used.

## Affected requirements

WEB-05 (PROJECT_V1_SPEC.md line 153: health routes are the only routes outside `/api/v1`, need no authentication and return no patient or tenant data). Related: WEB-02, WEB-03 (two-chain OIDC/browser security boundaries).

Acceptance mapping:
1. Permit exactly the two health GETs before `anyRequest().authenticated()` — done in both chains; no wildcard; API prefix untouched.
2. Non-synthetic HTTP test with a test JWT decoder: unauthenticated GET of each probe returns 200, an unauthenticated `/api/v1/` GET still returns 401 — `SecurityFilterChainHttpTest` (OIDC chain) and `HealthChainHttpTest` (full chain set).
3. Existing synthetic-auth tests kept passing — `SecurityConfigurationTest`, `BrowserSessionHttpTest`, `HealthControllerTest`, `HealthReadyIntegrationTest` (integration, existing test DB setup, unchanged).
4. `bash scripts/worker-check.sh` run; see Test evidence.

## Risk class

Cross-boundary (authentication configuration spanning the browser and bearer chains). Bounded security review by `orevia-senior-spring-security` (static source review, no code changes). No clinical/patient data is exposed: the controller returns only `UP`/`DOWN` and readiness runs `SELECT 1` with no diagnostics.

## Findings

- The task description attributed the defect only to the OIDC chain. In production the `@Order(1)` browser chain also intercepts unauthenticated health GETs (no bearer header) and would redirect them to OIDC login (302), so fixing only the OIDC chain would not have worked. Both chains were changed and both are tested. Evidence: pre-fix red run (302 with full chain set) and the Spring Security specialist's static review.
- In standalone MockMvc, `addInterceptors(...)` applies the interceptor to every path; production registers `TenantContextInterceptor` with `addPathPatterns("/api/v1/**")`. Using `addMappedInterceptors(new String[] {"/api/v1/**"}, ...)` in the two test helpers made the tests faithful and removed a false 401 on the health routes.
- Adjacent, out of scope: WEB-05 says readiness means "database reachable and migrations current", but `HealthController.ready()` only runs `SELECT 1`. No task in `tasks/` covers this; recorded for the integrator/owner rather than changed here.
- Environment only (not change defects): worktree `opencode.json` is the CI profile under `skip-worktree`; no repository config file was regenerated or committed. No OWASP/NVD run locally (no key); the integrator runs the full gate.

## Lessons for workers

- When both OIDC and staff-web chains are active, an unauthenticated probe reaches `@Order(1)` first. Permit the exact paths in both chains (or use a dedicated higher-priority chain), and prove it with a test that adds the full `springSecurityFilterChain` FilterChainProxy rather than only one chain's filters.
- Mirror production interceptor path patterns in standalone MockMvc with `addMappedInterceptors`; a bare `addInterceptors` runs on health paths too and produces misleading 401s.
- Spring Security 7.1.2 `requestMatchers(HttpMethod, String...)` builds `PathPatternRequestMatcher` matchers directly and needs no handler introspection; if a permit rule appears not to fire, check for an earlier application exception before rewriting the matcher.
- `worker_gate.py` requires non-empty `Test evidence` and `Coverage` headings in this notes file before `worker-check.sh` can pass; write the notes before the final gate run. Avoid literal angle-bracket tokens inside those two sections.
