# BUILD-41 (fix pass) — publish the three tenant-export routes in the route-parity baseline

## Summary

Fix pass for BUILD-41 / PR #621. The integrator's `mvn verify` failed solely on
`OpenApiRouteParityTest.everyControllerRouteIsDocumentedOrBaselined`: the three
tenant-export controller routes added by `e32bcae3` were neither documented in
`contracts/openapi.yaml` nor carried in the shrinking baseline. This change adds
the three routes, in normalized and sorted form, to
`contracts/openapi/missing-routes.txt` — the repository's designed mechanism for
contract documentation that is deliberately deferred to a tracked follow-up.

changed. The failing gate is green; the full contract documentation remains a
follow-up task (requested below and already requested by the first worker).

## Findings

- Root cause: `ExportController` registers three mappings that the authoritative
  contract does not document. The baseline is consumed by `OpenApiRouteCoverage`
  with path variables normalized to `{}`, so the correct baseline entries are
  `GET /api/v1/tenant/exports/{}`, `POST /api/v1/tenant/exports` and
  `POST /api/v1/tenant/exports/{}/expire`. All three were added in sorted order.
- The primary (DOD-complete) fix would document the three operations in
  `contracts/openapi.yaml` (with an `ExportResult` schema and shared 403/404/409/410
  error responses) and regenerate `apps/staff-web/src/api/generated/openapi.d.ts`.
  That was not done here: the `openapi-typescript` CLI and `node_modules` are absent
  in this worker, so the client cannot be regenerated offline, and the work is a
  separate, wider-scope task that the first worker already requested. Editing the
  contract without regenerating the client would break `gen:api:check`.
- Scope note: `contracts/` is outside the original BUILD-41 scope
  (`apps/api/.../tenant/export`, its tests and `V89`). The baseline addition is the
  minimal repository-designed mechanism to unblock the gate; full contract
  publication is deliberately left to the follow-up task.
- No ghost routes, stale-baseline entries or other failing checks were observed.
- Pre-existing/environmental: the `check-pack.py` staleness is the documented
  skip-worktree CI-profile artifact, unrelated to this change.
- Observation only (not fixed, out of scope): three unrelated files under
  `apps/api/src/main/java/com/aurevia/exchange/hl7/`
  (`Hl7ParseException.java`, `Hl7Parser.java`, `Hl7Segment.java`) contain literal
  `<<<<<<< HEAD` / `>>>>>>> origin/swarm/BUILD-37-469` lines inside Javadoc comments
  in committed `HEAD`. They are harmless to compilation (inside `/** */`) and
  `check-docs.py` passes; they belong to BUILD-37 and were left untouched here.

## Lessons for workers

- When a new controller mapping lands, register it in `contracts/openapi.yaml` or in
  `contracts/openapi/missing-routes.txt` in the same change. Deferring it only through
  a `task-requests` block leaves the integrator's `OpenApiRouteParityTest` red and
  blocks the merge — the baseline is the mechanism that keeps the gate green while
  documentation is pending.
- Baseline path variables must be normalized to `{}` and the file kept sorted; the
  parity test parses `METHOD /path` lines and normalizes both sides before comparing.
- In this cloud worker `opencode.json` is a skip-worktree CI profile: `check-pack.py`
  and five `test_check_pack` cases report staleness regardless of the change. Verify
  with `git show HEAD:opencode.json` and do not regenerate the protected file.
