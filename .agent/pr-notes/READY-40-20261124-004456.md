# READY-40 — Persist patient instructions in PostgreSQL (V64) instead of memory

## Summary

Replaced the process-local `InstructionStore.InMemory` bean with a PostgreSQL-backed
`JdbcInstructionStore` (new migration V64). MSG-04 templates, revisions and facts now
survive a restart and remain tenant-isolated. The nested `InMemory` class is kept for
fast unit tests but is no longer a Spring bean, so production wiring resolves the JDBC
adapter. No route, OpenAPI entry or generated client changed.

## Repair attempt 1 — coverage gate failure (resolved)

**Root cause (tool evidence).** The integrity gate's full Maven test run failed with
`Tests run: 6047, Failures: 0, Errors: 6, Skipped: 4`. All 6 errors were Spring
context-load failures in `messaging/clauses/ExposeCommandsConnectSendAssignResolveAcknowledgeTest`:
`NoSuchBeanDefinitionException: No qualifying bean of type ...InstructionStore$InMemory`.
READY-40 removed `@Repository` from the nested `InstructionStore.InMemory` class, but this
pre-existing ARC-07 clause test still `@Autowired` that exact bean type (former line 87).
This was a test-wiring failure, not an uncovered production line or branch — no threshold
was lowered and no exclusion was added.

**Fix (test-only).** Converted `ExposeCommandsConnectSendAssignResolveAcknowledgeTest` to
drive the production `JdbcInstructionStore` instead of the removed in-memory bean:
- removed the `@Autowired InstructionStore.InMemory instructionStore` field and the
  `InstructionStore`, `Autowired` and `List` imports;
- removed the per-test `seedMember`/`seedUnitStaff`/`linkPatientChart` seeding — roles,
  chart links and unit assignment are already seeded authoritatively in `prepare()`
  (V4 `active_roles` fold, V10 chart links, V63 `instruction_fact_unit_assignment`);
- removed the `seedConnection()` helper and its three calls — `connectionActive` reads
  V60 `patient_unit_connection`, which the HTTP `connect()` command writes through the
  production `JdbcMessagingStore.insertConnection`;
- updated the class Javadoc to name `JdbcInstructionStore` as the production bean.

No production Java, migration, contract or configuration file changed in this repair.

## Data changes

New additive migration `db/migrations/V64__patient_instructions.sql` creates three tables:
`instruction_template`, `instruction_revision`, `instruction_fact`. Each has
`organization_id NOT NULL REFERENCES public.organization`, a primary key including the
organization, `created_at timestamptz NOT NULL DEFAULT now()`, `ENABLE` + `FORCE ROW LEVEL
SECURITY`, a `tenant_isolation` policy with `USING/WITH CHECK (organization_id =
public.app_org())`, and explicit GRANT/REVOKE to `smartclinic_app`. Facts are append-only:
SELECT/INSERT only, UPDATE/DELETE/TRUNCATE revoked, and `reject_immutable_mutation()`
triggers cover every role including the migration owner. Revisions carry only a narrow
UPDATE for state/links; template reapproval uses an unbranched `ON CONFLICT DO UPDATE` to
match the port's put semantics. No backfill, no lock/volume impact on existing rows;
rollback is dropping the three tables. Roles, verified charts, patient-unit connections
and staff-unit assignment are read from the authoritative V4/V10/V60/V63 folds — no
second copy. No existing migration, contract, workflow, script or tracker file was edited.

## Authorization boundaries and audit events

`JdbcInstructionStore.organization()` derives the organization from `TenantContext.current()`
and throws `ApiException(403, "FORBIDDEN", "no active tenant context")` before any SQL when
the context or its organization is missing. Every statement also names `organization_id`
explicitly and runs in the tenant-guarded `TransactionTemplate`; forced RLS is a second
barrier. Staff reads remain bound to unit assignment over an active patient connection
(ARC-02). `instruction_fact` is an append-only domain trail with restricted grants and
reject-mutation triggers. No new central `audit_event` events were added: the pre-existing
MSG-04 flow had none, and adding `AuditAppender` to `InstructionService` would change its
constructor, breaking 7 out-of-scope clause tests. This OPS-02 dimension is explicitly
deferred with a `task-requests` entry below.

## Migration and rollout considerations

V64 is additive and safe to deploy with the application: the new adapter is the only
`InstructionStore` bean once `@Repository` is removed from `InMemory`. Any API instance
starting before the migration is applied will fail its first instruction query rather
than silently write to memory. No route or client rollout ordering change.

## Production entry point and integration test

`InstructionController` (POST/GET `/api/v1/patient-instructions`) → injected
`InstructionService` → injected `JdbcInstructionStore` → V64 tables. The HTTP path is
exercised by `JdbcInstructionStoreIntegrationTest.httpEntryPointPersistsThroughTheJdbcStoreAndIsolatesTenants`
(`@SpringBootTest(RANDOM_PORT)`, `@Tag("integration")`, synthetic-auth headers), which
POSTs a send, GETs the thread back with its SENT/DISPATCHED facts, asserts a cross-tenant
GET returns 404, POSTs a withdraw and asserts the persisted WITHDRAWN state through the
store. The direct-store tests bind `TenantContext` explicitly as
`JdbcDeliveryStoreIntegrationTest` does.

   adding `AuditAppender` requires changing `InstructionService`'s constructor, whose 8

## Lessons for workers

- When a nested in-memory `@Repository` is replaced, grep for `@Autowired <Outer>.<Nested>`
  across the whole test tree before removing the annotation — a single out-of-scope Spring
  slice can pin the bean even when every unit test uses `new`.
- Seed authoritative folds with the same subject that the HTTP headers will use; the
  `patient_record` trigger rejects an actor that is not a seeded user of the active org.
- In this repository enums serialize to their Java names (`COLLECTION`, `SENT`) in HTTP
  JSON, not the lowercase wire keys used by the domain `wire()` methods.
- A direct `queryForObject(..., Integer.class)` wrapped in `Objects.requireNonNull` avoids
  an uncoverable null branch while still proving the count is present.
- When a durable adapter replaces an in-memory Spring bean, an `@Autowired` test pinned to
  the nested fake fails the *whole* Maven run at context load (not just coverage). Fix the
  test by seeding the authoritative folds in `prepare()` and letting the production store
  read them; simply deleting the seed calls is safe only when the HTTP command already
  writes the fold (here, the connect POST writes `patient_unit_connection`).
