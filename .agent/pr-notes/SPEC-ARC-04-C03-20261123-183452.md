## Findings

- The brief cites `messaging/clauses/CommitPublicationAuditQueueUpdateNotificationOutboxTest.java:376-446`

  shows that range contains audit *counting* helpers and a `work_item_event` trigger keyed to a
  conversation id. The correlation-id-keyed audit trigger pattern is in
  `events/clauses/CommitStateAuditOutboxRecordAtomicallyApplicableTest.java:222-245` on `delivery_audit`.
  I adapted that pattern to `audit_event` and kept the prompt's scope paths. This is a brief
  inaccuracy, not a stale scope path; recorded here for the next worker.
- The brief names `docs/archive/pr-notes/2026-11-20.md` as the newest daily lesson source; a newer
  reconciled note `.agent/pr-notes/2026-11-21.md` also exists and was consulted.
- ARC-04 also requires an `Idempotency-Key`; the current accept route has no such header. That is a
  separate clause/C01-C02 concern, out of scope for this clause-3 proof. No gap is claimed here
  because this document proves only the commit-together clause.
- Reviewer Optional findings resolved before the final run: devsecops noted that a new PostgreSQL
  function grants `EXECUTE` to `PUBLIC` by default, so I added `REVOKE EXECUTE ... FROM PUBLIC` in the
  test-only trigger setup. code-reviewer asked that the injected 500 be tied to this request and that
  the peer-tenant case check the peer's tenant too, so I added an `X-Correlation-Id` header assertion
  on the failed response and an `ORG_B` audit-count assertion. After those three edits the targeted
  test is still 7/7 green, SpotBugs 0, constraints 0 and Java conventions OK. I did not assert the
  injected message in the 500 body: Spring's default error body does not expose it, and a non-firing
  trigger would make the same command return 200, so the status plus rollback assertions already
  prove the injection fired.
- Test-engineer's Required gap (closed): the original seven tests could pass if the audit fact were
  committed in a separate transaction. `auditFactRollsBackWhenOrderCommitFails` now adds a deferred
  constraint trigger on `xch03_order` that raises at the outer commit, after `audit.append` has run.
  Its `auditSuccessCount(marker) == 0` assertion fails if the audit fact survives in its own
  transaction. The doc's "reusing the fixture" wording was corrected to "following the fixture
  pattern" because the class copies rather than shares the neighbour's setup.

## Lessons for workers

- For a clause that is already implemented, "tests first" means writing a complete active proof and
  demonstrating fault detection, not leaving a red test or adding `@Disabled`. A one-assertion probe
  that is temporarily inverted, observed to fail, then restored byte-identically is honest red
  evidence and does not change the delivered file.
- The spec's literal route can be an authorization-mapping string rather than a controller path.
  Always confirm the `@RequestMapping` prefix on the controller before calling an HTTP route in a
  test; here the real route is `/api/v1/xch03/orders/{id}/accept`.
- `xch03_order` has both `version` (the optimistic-lock field) and `revision` (the content revision).
  Seeding only `revision` leaves `version` at its default 1; assert against `version` after a command.
- A correlation-id-keyed audit trigger must `GRANT EXECUTE ON FUNCTION ... TO aurevia_app`, because
  the trigger runs as the application database role. Use a plain `RAISE EXCEPTION` (SQLSTATE P0001):
  a class-23 constraint violation is translated by `SqlFailureTranslator` into a 404/409 instead of
  the 500 that proves an unhandled write failure.
