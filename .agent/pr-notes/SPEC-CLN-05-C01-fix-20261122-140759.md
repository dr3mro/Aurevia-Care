## Lessons for workers

- After the orchestrator merges `origin/main` into a long-lived swarm branch,
  re-run test compilation before trusting earlier green results: a production
  record can gain a constructor component in a sibling story and break an
  unrelated test's `testCompile`. `git merge-base --is-ancestor <suspect> origin/main`
  and `git diff origin/main HEAD -- <file>` quickly distinguish a base-branch
  regression from a story defect.
- When a local `ExportRecord`/similar test fixture must gain a new component, add
  a small synthetic helper and pass it to every call site, then run that suite
  directly to prove no assertion was weakened.
- The `field(json, key)` helper in the clinical-note integration tests returns
  the four-character string `"null"` for a JSON null; assert that literal.
- Give each clause suite its own database name (for example
  `smartclinic_cln05_c1_it`) so parallel clause workers do not drop each other's
  data.
- A test-only change has no new production branches: the honest coverage
  statement is that no production file changed, with a targeted JaCoCo run over
  the exercised classes as the worker-area evidence and full `mvn verify` left
  to the integrator.
- In a cloud worker, `check-pack`/`test_check_pack` staleness with
  `git ls-files -v opencode.json` → `S` is an environment artifact; record it once
  and run the remaining gates individually.
