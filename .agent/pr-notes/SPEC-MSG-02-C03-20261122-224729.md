# SPEC-MSG-02-C03 — MSG-02 clause 3 API test

## Summary

Test-only clause evidence for MSG-02: "Every new inbound patient message creates
or reopens a work item." Adds one synthetic HTTP-level clause test class and one
clause-evidence document. No production code, migration, contract, dependency or
existing test changes. The clause is **Proven by tests**: a patient open appends
a `CREATED` work fact and queues the conversation for staff; a reply to a
`resolved` thread appends `REOPENED`; a reply on an already-open thread returns
the single work item to `awaiting_staff` without a false second work fact.

MSG-02 (clause 3). Supporting evidence only for ARC-02/ARC-04 (tenant isolation and

## Findings

- Work-item semantics: one work item per conversation. `work_item_event` is a
  transition ledger (`CREATED` on open, `REOPENED` only from `RESOLVED`);
  `conversation_message` is the per-message ledger. An intermediate reply keeps
  the existing item active via `updateState` and appends no work fact — emitting
  `REOPENED` there would falsely record a resolution. Agreed with the plan
  reviewer and test engineer; recorded in the clause doc. No `@Disabled` GAP
  test was added because the implemented behavior is faithful to the clause.
- Survey observation: `ConversationService.open` writes the conversation and its
  `CREATED` fact but no `conversation_message` row; the first inbound content is
  the conversation's `topic`. The create half is therefore proven at the
  work-item-state level, not by a first message row. Changing that would need a
  separate production task; nothing was changed here.
- Contract debt (out of scope): the conversation routes are baselined in
  `contracts/openapi/missing-routes.txt` lines 26-28 and 163-169 with no OpenAPI
  operation. Recorded in the clause doc's Evidence, not edited.
- No red/green phase exists for this PR: no production line changed, so the new
  tests are acceptance evidence against the existing implementation rather than
  a regression fix. Each test asserts an observable outcome, so a behavioral
  regression would fail it.
- Pre-existing on `HEAD` and out of scope: `git grep '^(<<<<<<<|>>>>>>>) '`
  finds unresolved conflict markers inside Javadoc comments in three
  `apps/api/src/main/java/com/aurevia/exchange/hl7/` files
  (`Hl7ParseException`, `Hl7Parser`, `Hl7Segment`). They compile and are
  untouched by this PR; they will render as stray text in the developer
  reference and need a separate owner.

## Lessons for workers

- In a cloud worker, `git ls-files -v opencode.json` showing `S` explains the
  `check-pack.py` / `test_check_pack` / `python-coverage.sh` failures: verify the
  committed `HEAD` profile against the generator render and the runtime profile
  with `--check-runtime`, then record it once and do not regenerate that file.
- For test-only clause work under `apps/api`, capture generated identifiers from
  a Mockito `ArgumentCaptor` on the repository write rather than parsing the JSON
  response: this module's test classpath has no Jackson databind.
- Before declaring a GAP for a "per message" clause, check whether the domain has
  a per-message ledger distinct from the work-item transition ledger, and read
  the requirement's own next sentence. Adding `@Disabled("GAP: ...")` to a
  correct behavior would fail `check-constraints.py`.
