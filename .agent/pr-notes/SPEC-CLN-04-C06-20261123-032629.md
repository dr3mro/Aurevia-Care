# SPEC-CLN-04-C06 — Spec CLN-04 clause 6 (API test): clinical governance approves field dictionaries and requiredness

## Summary

Test-only + documentation-only evidence story. Added one HTTP integration test class and one clause note proving which half of CLN-04 clause 6 is actually built. The reachable path versions a field dictionary carrying `REQUIRED`/`OPTIONAL` definitions and preserves a distinct named approval in the effective version and history; the approver can only be `tenant_admin`. The `clinical_governance` actor named by the clause exists in `clinical.templates.TemplateService` but has no HTTP controller, so a complete test for that half is recorded verbatim in the clause note for a follow-up task. No production code, migration, contract or existing test was changed. Synthetic fixtures only.

**Deviation from the story text, recorded deliberately:** story step 3 and the advisor brief asked for that complete test to be added to the Java class as `@Disabled("GAP: ...")`. `scripts/check-constraints.py:56` rejects every newly added Java `@Disabled`, and `docs/WORKFLOW.md` makes that a hard `quality-gate.sh` failure; scripts are out of worker scope. The code-reviewer ruled the added marker a Required gate violation, so the method is preserved in the doc (exempt from that checker) rather than as a skipped test. All gates now pass. This keeps the story's intent — a complete, ready-to-enable proof of the missing behaviour — without weakening a quality gate.

## Findings

- **Governance-role gap (the point of the story).** `authz.ActionPolicy:43-84` grants `CONFIG_APPROVE` only to `tenant_admin`; there is no `clinical_governance` role. `clinical.templates.TemplateService:39,410-411` has the `CLINICAL_GOVERNANCE` constant and approval authorization, and `validate` at `:290-313` enforces requiredness, but no controller calls it. `contracts/openapi.yaml` publishes no governance/template approval route. The clause note records this as `Partly proven` and explicitly refuses the false "Proven by tests" claim.
- **Enabling detail.** `DurableVersionStore.approve` calls `configurations.history(...)` before approving, so the follow-up must grant `CONFIG_HISTORY` as well as `CONFIG_APPROVE` to the governance role; otherwise the enabled test would fail with 403 for a different reason.
- **Fixture facts for the next worker.** Dictionary keys are capped at 32 characters by `VersionStore.KEY` (`[a-z][a-z0-9_]{1,31}`); longer keys return 422. `Approval.approver` is a `user_identity` UUID resolved by `ConfigurationService.approve`, not the synthetic subject; the test captures the seeded id as a fixture and asserts it against the HTTP body.
- **Gate conflict resolved without a suppressed test.** An added `@Disabled("GAP: ...")` was first written per the story, went red on `check-constraints.py`, and was removed on the code-reviewer's Required finding; the complete method now lives in the doc. All gates pass and no quality gate was weakened.
- **Environment artifacts (recorded once, not re-diagnosed).** Worktree `opencode.json` is the CI profile under `skip-worktree` (`S`); this explains the six `test_check_pack` failures and the `quick-check.sh`/`python-coverage.sh` exits above. OWASP/NVD and the full JaCoCo gate stay with the integrator.
- **Out-of-scope observation (not changed).** `git grep -nE '^(<<<<<<<|>>>>>>>) '` reports conflict-marker lines inside Javadoc in `apps/api/src/main/java/com/aurevia/smartclinic/exchange/hl7/Hl7ParseException.java`, `Hl7Parser.java` and `Hl7Segment.java`. `git show HEAD:<file>` confirms they are already committed in `HEAD` (no worktree diff), so they predate this story; these files are outside its scope and were left untouched. They compile because they sit in comments, but the owner should clean them up.

## Lessons for workers

- Check `scripts/check-constraints.py` before adding a story-mandated `@Disabled`: it rejects every new Java `@Disabled` with no exemption, and `docs/WORKFLOW.md` makes that a hard gate. Record a complete unbuilt test verbatim in the clause doc instead, and say in the notes why the story text was not followed literally.
- Dictionary keys pass through `VersionStore.KEY` (2–32 lowercase chars/digits/underscore) before `ConfigurationService.validateKey` (3–64); a long descriptive key fails with 422.
- `Approval.approver` in the catalog HTTP body is a user UUID, not the subject from `X-Synthetic-Subject`; capture the seeded `user_identity.id` during fixture setup and compare with that.
- `DurableVersionStore.approve` reads history before it approves, so any new approving role needs both `CONFIG_HISTORY` and `CONFIG_APPROVE`.
