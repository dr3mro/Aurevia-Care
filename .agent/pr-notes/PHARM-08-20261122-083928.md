# PHARM-08 — Browser test and guide: prescribe, route, pharmacy accepts, clarifies, substitutes and dispenses

## Summary

Adds one synthetic Chromium journey across two browser roles (prescriber and
pharmacy) that drives the real staff-web pharmacy screens and the real typed API
clients through prescribe/route → clarification question → prescriber answer →
substitution proposal → prescriber approval → pharmacy acceptance → dispensing
evidence. Both roles share one in-memory, append-only pharmacy store behind a
stubbed `/api/v1/pharmacy/**` boundary. A dev-only harness mounts the exported
prescriber status components, which are not routed in the portal yet. Adds an
operations guide in plain language with a status glossary and an
entry-point-to-test trace. No application source, dependency, schema, contract,
tracker or workflow file was changed.

## Lessons for workers

- Playwright needs OS libraries as well as the browser binary in a fresh worker:
  `npx playwright install chromium` alone fails with
  `libglib-2.0.so.0: cannot open shared object file`; `npx playwright
  install-deps chromium` repaired the environment. Both are environment-only
  and add no repository dependency.
- The staff-web module `check.sh` excludes `e2e/**` from Vitest and the module
  tsconfig `include`; a green module gate does not typecheck or run the browser
  tests. Run `npm run e2e` and an explicit strict `tsc` over the new e2e files
  as well, and paste the typecheck final lines into the notes.
- In a cloud worker, a stale `opencode.json` pack check is usually the CI
  profile under `skip-worktree`. Confirm with `git ls-files -v`, compare with
  `.github/opencode.ci.json` and `git show HEAD:opencode.json`; never regenerate
  or commit that generated file.
- Shared state for a two-role browser journey belongs in the Node test process,
  not in a page: install a route handler on each context's page that closes over
  one store, so a command from one role is genuinely visible to the other.
- `getByText` on a question string can match both the timeline detail and the
  thread entry; scope the assertion to a `data-testid` to avoid a strict-mode
  violation.
