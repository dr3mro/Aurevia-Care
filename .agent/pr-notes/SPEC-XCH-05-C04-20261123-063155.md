# SPEC-XCH-05-C04 — XCH-05 clause 4 (API test)

## Summary

Add a dedicated HTTP-level integration test proving that delivering a critical
notification and recording a patient release never satisfy clinician
acknowledgment, plus a clause document recording the evidence. The clause is
already implemented; this is test-and-documentation only. No production code,
existing test, migration, contract or dependency is changed.

## Affected requirements

XCH-05 (spec sentence: "Delivery and patient release do not satisfy clinician
acknowledgment." — SMARTCLINIC_V1_SPEC.md line 67).

## Risk class

Cross-boundary (real PostgreSQL, tenant isolation, role guards and an append-only
audit ledger are exercised through the HTTP entry point). All fixtures are
synthetic; no PHI, credentials or real identifiers.

## Data changes

None. No migration is added or changed. A fresh synthetic database
`smartclinic_critical_ack_it` is created and dropped by the test, migrated from
the existing `db/migrations` (Flyway `filesystem:../../db/migrations`). The
existing V23 `critical_result` / `critical_result_event` tables already carry
RLS, FORCE RLS, tenant policies and append-only triggers; no schema change.

Asserted, not changed: ACKNOWLEDGE is clinician-only, RELEASE is tenant_admin-only,
cross-tenant reads are concealed (404), and the ACKNOWLEDGED / PATIENT_RELEASED
facts are separate append-only events. No audit or policy code is modified.

Tests (HTTP level, real PostgreSQL, synthetic fixtures cloned from
`CriticalResultFlowTest`):

- `deliveryAndReleaseLeaveResultAwaitingUntilClinicianAcknowledges` (positive):
  register(readBack=true) → assign → verify → escalate(outcome=delivered) → release.
  Assert every call's status (201 create, 200 for the four commands). After
  DELIVERY alone: assert an `escalation_attempt` event with outcome `delivered`
  exists at revision 3 AND the `acknowledged` event count is zero. After RELEASE:
  assert a `patient_released` event exists at revision 3 AND the `acknowledged`
  event count is STILL zero; state `awaiting_ack`, version 3 unchanged. Only then
  readBack → acknowledge as `clinician-1111`: 200, state `acknowledged`, version 4,
  EXACTLY ONE `acknowledged` event at revision 3 with the clinician's actor id, and
  exactly one `CRITICAL_ACKNOWLEDGE` audit event. Splitting the assertions after
  each fact prevents a vacuous green and localises a regression to one half.
- `deliveryWithoutReadBackCannotAcknowledge` (negative): register with
  `readBack=true`; delivered attempt but no read-back → acknowledge 409 with
  `/code == "READ_BACK_REQUIRED"` (not merely any 409), state `awaiting_ack`,
  version 3, zero `acknowledged` events.
- `patientReleaseWithoutDeliveryCannotAcknowledge` (negative): register → assign →
  verify → RELEASE only (no delivered attempt); assert state `awaiting_ack`, zero
  `acknowledged` events, then acknowledge → 409 `NO_DELIVERED_ATTEMPT`. This
  directly proves a release is not a substitute for the clinical chain.
- `clinicianAcknowledgmentRequiresClinicianRole` (negative): on an
  acknowledgment-ready result, `admin-1111` (tenant_admin) acknowledge → 403
  `/code == "FORBIDDEN"` with no ACK event; `clinician-1111` release → 403
  (RELEASE is tenant_admin only).
- `anotherTenantCannotAcknowledge` (negative): set the ORG_A result up to the
  acknowledgment-ready state (delivered + read-back at revision 3); `clinician-2222`
  with the ORG_B header acknowledge on it → 404 (authorize passes for an active
  ORG_B clinician; RLS makes the ORG_A row invisible), ORG_A result unchanged with
  zero ACK events. Using `clinician-1111`+ORG_B would give 403, not 404.
- `staleVersionAcknowledgmentIsRefused` (negative): acknowledgment-ready ORG_A
  result; If-Match 1 against version 3 → 412 `/code == "STALE_VERSION"`, no
  state/version/event mutation.

## Findings

- The clause is already built and proven by
  `CriticalResultFlowTest.deliveryAndPatientReleaseNeverAcknowledge`; no
  `@Disabled` GAP test, production edit or migration was needed. The new class
  adds an explicit no-`acknowledged`-event assertion after EACH fact, event
  revision/actor bindings, an audit-count assertion and the negative matrix.
- Plan review initially returned NO-GO because a no-throw HTTP helper could hide
  a 4xx/5xx from `escalate`/`release`, making the positive test vacuous. Fixed by
  asserting every call's status and the presence of both facts before asserting
  their absence; re-review returned GO.
- Test-design review returned NO-GO until the proof rested on event counts rather
  than state alone, error codes were asserted, a release-alone negative test was
  added and a distinct DB name was used. All applied; re-review returned GO.
- Corrected a reviewer claim with evidence: `patient_released.actorId` is NOT
  null. V23's `set_critical_event_actor_from_actor()` trigger derives `actor_id`
  from `app.actor` (bound by `TenantGuardTransactionManager` from
  `X-Synthetic-Subject`); the null fields in `CriticalResultService.release` are
  `recipient` and `channel`. The test does not assert a null actor.
- Known worker-image artifacts recorded above (skip-worktree `opencode.json`,
  missing Python `coverage` module). No protected file was edited.
- Evidence provenance: tool evidence (executed Maven/Shell/Python commands and
  Surefire XML) plus simulated/static specialist reviews. No human, clinical or
  real-patient evidence is claimed; all fixtures are synthetic.

## Lessons for workers

- A no-throw HTTP helper (`onStatus(status -> true, ...)`) means every command
  must have its status asserted, or a test that only checks the final state can
  pass green after a hidden 4xx/5xx. Prove the fact happened, then prove the
  forbidden consequence did NOT happen.
- For an "X is a separate event" clause, assert the absence of the event itself
  (count all matching events by type at every revision), not merely the absence
  of a state change — a stray event can coexist with an unchanged state.
- Clone a fresh-database integration fixture with its OWN database name: an
  identical `@SpringBootTest` datasource URL reuses the cached Spring context
  and Hikari pool that a sibling test's `@AfterAll` drops.
- `worker-check.sh` runs every integration suite (line 51). A swarm worker under
  a timeout should run its individual stages plus the targeted `-Dtest=` run and
  leave the full suite to the integrator; record that decomposition in notes.
- When a reviewer cites a fact about production behavior, verify it against the
  migration/trigger and the transaction manager before adopting it; a wrong
  assertion (here, `actorId == null`) would have failed the green test.
