# RADFLOW-01 · API: performing-site worklist and handoff (received, scheduled, performed, reported)

Task: RADFLOW-01 · Story requirement: RAD-01 · Branch: `swarm/RADFLOW-01-453` · Commit: local HEAD of that branch after the review fixes (not pushed; no `gh` or tag)

## Summary

Added a bounded RAD-01 performing-site worklist kernel and thin HTTP adapter under
`com.aurevia.radflow.worklist`. An order advances forward only through
`RECEIVED → SCHEDULED → PERFORMED → REPORTED`; scheduling records the accession and
approved modality; linking the external study reuses the radiology patient-and-accession
check and refuses a wrong-patient or wrong-accession link without changing the order.
A successful link marks the study performed and emits a distinct `HANDOFF_RECORDED`
fact for the reporting stage. The worklist, the order-detail read and the fact
list are scoped by both active tenant and performing site, so a second site in
the same tenant cannot see another site's order or patient identifiers. All fixtures are synthetic. No migration (none reserved in this
task) and no files outside the two scoped paths were changed.

## Authorization boundaries and audit events

Organization, actor and active roles always come from `TenantContext` and freshly
resolved `StaffRepository.activeRoles` inside the tenant-guarded `TransactionTemplate`;
none is taken from a command body. The performing site is an explicit scope on
every read, fact list and command: `requireSite` refuses a command whose site
differs from the order's site, `readForSite` denies a cross-site detail read with
403, and `eventsForSite` filters facts carrying patient and accession identifiers.
Production wiring must bind the site to verified staff membership in a later
integration story (no facility directory or reserved migration is in scope).
Receiving and scheduling require reception or radiology
staff; linking requires radiology staff; reporting requires an interpreter or
radiology staff. Emitted facts (identifiers only, no clinical narrative, no image
pixels): `ORDER_RECEIVED`, `ORDER_SCHEDULED`, `STUDY_PERFORMED`, `HANDOFF_RECORDED`,
`ORDER_REPORTED`, `STUDY_LINK_REFUSED`. A wrong-patient link records a refused-link
fact and leaves the order revision untouched.

## Findings

1. `scripts/check-pack.py`, `scripts/python-coverage.sh` and three `test_check_pack`
   tests fail on the documented cloud-worker skip-worktree `opencode.json`
   artifact (flag `S` from `git ls-files -v`; worktree file is the CI profile and
   differs from `git show HEAD:opencode.json`). No protected file was edited. The
   integrator runs these on the merged HEAD profile.
2. The performing site is an explicit command/query scope in this kernel. A
   role/tenant check is applied on every command, but a production integration
   must bind the site to verified staff membership (facility directory is out of
   scope and no reserved migration exists). This is recorded as a rollout
   limitation, mirroring BUILD-11's "domain-kernel-complete, not releasable"
   status.
3. No OpenAPI entry or regenerated client is included (`contracts/` is outside
   scope); the HTTP routes are covered by MockMvc tests.
4. Deleted the unreachable `STUDY_NOT_LINKED` guard in `report()` (see Coverage).
5. Two bounded background reviews (Senior Java/Spring Boot and Test Engineer,
   **simulated reviewer** evidence) requested site isolation on the detail read
   and a null-timestamp fix. Both were fixed before the final commit:
   - `GET /orders/{id}` now requires `?site=` and calls `readForSite`, which denies
     a cross-site read with 403 (HTTP and domain tests added). `GET /events`
     likewise requires `?site=` and calls `eventsForSite`, because facts carry
     patient and accession identifiers that must not cross a site boundary.
   - `parseInstant` now treats null and blank input as 422 `INVALID_SCHEDULE`
     rather than letting `Instant.parse(null)` produce a 500; malformed, null and
     blank inputs are all asserted over HTTP.
6. Hand-off semantics were clarified: `HANDOFF_RECORDED` is the performing-site
   to reporting-stage handoff emitted when the study is performed, with the
   referrer as destination; `ORDER_REPORTED` records the final status and no
   longer claims a second referrer handoff.
7. Advisory, not fixed in this slice: detail and mutation endpoints still return
   the full `WorklistOrder` rather than the minimal `WorklistEntry`; the package
   is `radflow.worklist` because the story scope mandates that path even though
   `radiology.worklist` would mirror the domain package; the in-memory maps are
   not synchronized and the kernel is not durable (BUILD-11 precedent). Recorded
   for the persistence/integration follow-up.
8. No defect was found in existing code; nothing was added to BUGS.md (owned by
   the orchestrator).

## Lessons for workers

- Read the whole radiology kernel before designing a RAD slice: `RadTypes` and
  `RadRules` are the reusable domain vocabulary; duplicating them would drift.
- JaCoCo at 100% still hides an unreachable guard — read the per-line XML
  (`mi`/`mb`) and delete code no input can reach instead of writing a vacuous test.
- The cloud `opencode.json` is a skip-worktree CI profile: a local `check-pack`
  failure there is a measurement artifact. Confirm with `git ls-files -v` and
  `git show HEAD:opencode.json`, note it, and never edit the protected file.
- Write the failing test through the HTTP controller before the kernel: it made
  the required entry-point-to-test trace explicit and caught the timestamp
  boundary early.
