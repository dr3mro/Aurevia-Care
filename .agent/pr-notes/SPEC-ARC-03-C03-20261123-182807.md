## Summary

ARC-03 clause 3 evidence: the five explicit POST command families (sign, correct,
acknowledge, release, exchange) are registered in `CommandCatalog.synthetic()` with
method POST, an unregistered command fails closed with `422 UNKNOWN_COMMAND`, and the
`correct`/`release` families are proven end to end through their real controllers
with state read-back and unchanged-state refusals. Five catalog paths across four
families have no live controller; that gap is asserted with an enabled 404 test and
documented with the live alternative routes. No production code, contract, migration or tracker changed.

Evidence provenance: executed tool commands (Surefire XML, SpotBugs, policy scripts)
and simulated read-only specialist reviews. No human, clinical or real-patient
participant was involved; all fixtures are synthetic.

## Findings

- **Brief/story conflict, resolved gate-compliantly.** The story asked for full tests
  of unbuilt behavior marked `@Disabled("GAP: ...")`. I verified with a throwaway probe
  that `python3 -I scripts/check-constraints.py` fails on ANY added Java `@Disabled`,
  which also fails `quick-check.sh`, `worker-check.sh`, `check.sh`, `quality-gate.sh`
  and delivery CI; the four existing GAP-disabled tests predate that rule. AGENTS.md
  also forbids skipped tests. No `@Disabled` test was added. Instead an enabled test
  asserts that the five unwired catalog paths return 404 and the evidence doc records
  the live alternatives. This keeps the PR green without a fabricated HTTP proof.
- **Catalog-vs-route drift.** Only `correctRelease` has a controller at its catalog
  path; sign, acknowledge, `authorizeRelease` and exchange catalog paths return 404.
  `CommandClientGenerator` publishes those catalog paths into the OpenAPI contract and
  generated client, so generated functions for them currently target 404. The live
  routes are named in the doc `## Gap`. Five bounded tasks would close it (one per
  family plus production gate wiring). Out of scope here.
- **Authorization gate is inert in production.** `CommandAuthorization.authorize`
  has no production caller and no durable decision sink; catalog registration alone
  does not enforce authorization at runtime. Recorded in the doc `## Gap`, not fixed.
- **New convention.** `web.clauses` and `docs/spec/clauses/web/` are new package/doc
  folders; existing clause evidence is grouped by spec domain (for example
  `messaging.clauses`). The story mandates these two paths, so they were used as
  given; a future realignment could move them to an `api.clauses` domain folder.
- **Env artifact, already recorded.** `test_check_pack` failures come from the
  skip-worktree CI `opencode.json` profile, not from this change; see `## Test evidence`.
- **Review fixes applied.** DevSecOps first answered NO-GO because the other-tenant
  404 command response body was discarded, so tenant leakage on the command path was
  not proven; the test now captures that entity and asserts the body contains neither
  the ORG_A revision id nor the release id, in addition to the read-back checks.
  Code review noted that the phantom catalog paths are published in
  `contracts/openapi/generated/openapi.yaml` (not authoritative `contracts/openapi.yaml`);
  the doc now says so. Code review also noted the 404 probe omitted `rejectOrder`;
  the probe now covers all five catalog paths. Coverage review's one Optional note
  (`CommandDefinition` rejects non-POST) is accurate per `CommandDefinition.java:48-50`
  and already covered by `CommandAuthorizationTest`; no duplicate test was added.

## Lessons for workers

- Before adding `@Disabled("GAP: ...")` to a clause test, run
  `python3 -I scripts/check-constraints.py`: the Java rule now rejects it outright,
  so a test-enforced 404 assertion plus an evidence-doc Gap is the compliant way to
  record an unwired route.
- For a release/withdrawal/correction HTTP proof, reuse
  `PatientReleaseControllerHttpTest` and
  `HandleCorrectedWithdrawnReleasesUpdatingCurrentAccessTest`: authorize with a
  `clinician`, correct/withdraw with the same clinician, and use `reception` for the
  403 case. The revision id is a synthetic string; no report-revision seed is needed.
- Spring 6.2 names status 422 `UNPROCESSABLE_CONTENT`, not `UNPROCESSABLE_ENTITY`;
  assert the numeric 422 to stay version-independent.
