# PHARM-05 — Staff web: pharmacy inbox and detail

## Summary

Added the pharmacy worklist and prescription detail screens under
`apps/staff-web/src/features/pharmacyinbox` only. The inbox shows a status filter,
cursor pagination ("Load more") and a compact table; the detail shows one clear
card with medication, dose, quantity, dosing instructions and prescriber, the
accept/reject/clarify/record-dispensing actions, a status-history trail and
separate Accepted and Dispensed flags. Reject and clarify require a non-blank
reason; dispensing evidence is entered on its own step and never implies
acceptance. A 409/412 keeps every typed field. Routes are exported from
`features/pharmacyinbox/routes.ts` for the application's feature glob; shared
registration is deliberately left to a person or later task.

Entry-point-to-test trace:

- `/pharmacy` → `routes.ts` lazy `PharmacyInboxPage` → `useApi` →
  `api.listPrescriptions` → `buildRequestDescriptor` + `send` →
  `PharmacyInboxPage.test.tsx` ("renders the routed prescription…", "resolves the
  exported inbox route through its normal lazy entry point").
- `/pharmacy/:id` → `routes.ts` lazy `PharmacyItemPage` → `getPrescription` +
  `getPharmacyStatus` → the four command functions in `api.ts` →
  `PharmacyItemPage.test.tsx` ("accepts with the status version…", "requires a
  reason before rejecting…", "keeps dispensing evidence in a separate step…").

All data is synthetic (`SYN-PATIENT-001`, `synthetic.prescriber`, etc.). No
dependency was added and no file outside the scope was changed.

## Affected requirements

- RX-02: pharmacy inbox of explicitly routed items; accept, reject with reason,
  clarification, dispensing evidence kept as a distinct fact; submission ID and
  prescriber shown; status history.
- WEB-09: loading, empty, error (correlation ID), timeout/offline (retry
  control), forbidden, conflict (compare/reload/copy, typed text preserved) and
  session-expired states, plus a beforeunload guard for unsaved command text.

Wire field names come from the PHARM-01/PHARM-02 API projections
(`pharmacyflow/inbox/PharmacyInboxContract.java`,
`pharmacyflow/status/PharmacyStatusContract.java` and `PharmacyStatusController.java`);
the generated client does not yet publish these paths, so `api.ts` borrows a real
contract path for the shared tenant/correlation/version/idempotency headers and
substitutes only the URL, as the scheduling and duplicates features do.

## Clinical and architecture review

No signed clinical data is created or changed by the UI itself; commands are
sent to the PHARM-01/02 API, which is authoritative for tenant, role, version,
idempotency and append-only facts. The pharmacy card intentionally omits chart
content. Acceptance and dispensing evidence are shown as independent flags and
entered through separate steps. No human clinical approval was obtained or
claimed; all review here is synthetic/engineering only.

## Findings

- The story said to read `features/prescriptions`, but no such folder exists in
  this checkout (nor does any other pharmacy/orders staff-web feature). I reused
  the canonical `features/scheduling` and `features/duplicates` patterns and the
  PHARM-01/PHARM-02 Java contracts instead. No file was created outside scope.
- The routed inbox projection has no `instructions` field. The card's
  Instructions value is composed from the real `strength`, `route` and
  `frequency` fields by `dosingInstructions()` rather than inventing a wire
  field.
- `tests/messageParity.test.ts` (outside scope) discovers every
  `src/**/messages.ts` and compares it with a hard-coded registry. Naming the
  feature bundle `messages.ts` broke that global test, so the bilingual
  dictionary and its parity test live in `labels.ts` / `labels.test.ts` inside
  the feature. Functionality and parity are preserved; no out-of-scope file was
  touched. If the owner prefers the canonical filename, register the new bundle
  in that test first (task request below).
- `StateView.forTransportError` renders the shared `ErrorState` with an inert
  Retry button for offline/timeout; this is existing behaviour in every
  staff-web feature and cannot be changed inside this scope.
- Pre-existing gate blocker (not introduced here): `contracts/openapi.yaml`
  contains `order-entry` paths that `apps/staff-web/src/api/generated/openapi.d.ts`
  does not, so `npm run gen:api:check` fails at HEAD. Verified by generating to
  `/tmp/openapi-generated.d.ts` and diffing; `git status` shows only this
  feature's untracked folder. The generated file is outside scope.
- Pre-existing environment artifact: `bash scripts/check.sh` stops at
  `check-pack` because the cloud worker's `opencode.json` is the CI profile
  under `skip-worktree`; MEMORY.md records this as a measurement artifact, not
  HEAD truth.

## Lessons for workers

- Before adding `src/**/messages.ts`, run the global message-parity registry
  test: it hard-codes every bundle path and will fail on a new canonical name.
- Feature `routes.ts` files need an explicit test that renders the lazy
  component; importing the module alone leaves the lazy loader uncovered.
- With `exactOptionalPropertyTypes`, spread `{ ...(cond ? { error: text } : {}) }`
  into `FormField` instead of passing `error={undefined}`.
- A success message held in a component that remounts after a refetch is lost;
  keep it in the page that owns the reload token.
