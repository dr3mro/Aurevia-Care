# SPEC-CLN-03-C03 — Record clinical author separately from data entry actor

## Summary

Test-only clause evidence for CLN-03 clause 3 on branch `swarm/SPEC-CLN-03-C03-989`.
The clause is already implemented in the hardened `chart.record` slice, so no
production code, migration, contract or existing test was changed. Added one
HTTP-level integration test class with six named behaviours (two positive, four
negative/refusal) and one clause evidence document. All fixtures are synthetic.

## Findings

- The clause is implemented in two slices: `chart.record` (`ChartService`,
  `ChartRepository`, `ChartEntry`, `RecordEntryCommand`, `ChartController`,
  `ChartActionPolicy`, V13) and `clinical.notes` (`ClinicalNoteService`,
  `ClinicalNoteRevision`, `RevisionInput`, `NoteRepository`, V15). The new test
  proves the chart slice through the surviving HTTP entry point; the note slice
  has its own suite. No controller or migration outside those two slices stores
  the author/actor pair.
- In `chart.record` a recorder may only claim authorship for their own subject;
  a distinct author/actor pair can therefore arise only when a clinician verifies
  an entry whose author was left open. That is the rule exercised by the positive
  test, not a gap in the implementation.
- Pre-existing, out of scope: the committed OpenAPI contract contains no
  `/api/v1/chart/records` path and no `clinicalAuthor`/`dataEntryActor` fields.
  This predates the story and is not changed here; it is recorded for the owner
  of contract coverage.
- Environment-only gate failures: the `opencode.json` CI profile under
  `skip-worktree` (OPS-CW-003-01) stops `scripts/check.sh` at `check-pack`, and
  the same artifact plus missing `coverage` makes `scripts/python-coverage.sh`
  fail on six `test_check_pack` cases. Both were confirmed once with evidence and
  are not change defects.
- Simulated test-engineer review (session `ses_dfc9f1f35ffepwCFmUrOkBnkj5`,
  read-only, no files edited) confirmed the positive test proves distinct

## Lessons for workers

- Spring 6 names HTTP 422 `HttpStatus.UNPROCESSABLE_CONTENT` here; neighbouring
  chart tests assert the numeric value (`getStatusCode().value()`). Use the
  numeric assertion for 422 responses.
- Give an HTTP/database clause test its own database name and drop it in
  `@AfterAll`; other chart suites use different fixed names and would collide.
- Direct SQL reads of `chart_entry` need `SET app.current_org` even as the
  migration owner, because V13 applies FORCE ROW LEVEL SECURITY to the owner too.
- To prove "author separately from data-entry actor" in `chart.record`, record
  with an assistant, omit the author, then verify as a clinician and assert all
  three columns (`clinical_author`, `data_entry_actor`, `verified_by`); asserting
  only the response body would not prove persistence.
- Do not re-diagnose the worker-image `opencode.json` artifact: confirm with
  `git ls-files -v`, compare with `.github/opencode.ci.json` and `git show HEAD:`,
  restore the bytes, then run the remaining gate stages individually.
- When `git grep` finds conflict markers, check `git show HEAD:<path>` before
  blaming the merge: markers inside Javadoc comments can be committed and still
  compile. Report them as a pre-existing defect instead of editing out-of-scope
  production files.
