# BUILD-46 — Staff web: radiology orders, scheduling, study link and interpretation

## Summary

Added the `apps/staff-web/src/features/radiology` feature (RAD-01, WEB-09): an
imaging-order list with cursor paging, a schedule step capturing accession and
modality, a study-link step that verifies patient **and** accession before any
write, a signed interpretation whose original is immutable, and addenda that are
carried into the referrer view. A wrong-patient (or wrong-accession) link renders
a precise mismatch alert and issues no POST. Every screen exposes the WEB-09
loading, empty, error (correlation ID), offline/timeout, forbidden, stale-conflict
and session-expired states via the shared `StateViews`; conflict keeps typed work
and a working **Reload the order** action refetches an authoritative version.

Entry point → test trace: `features/radiology/routes.ts` lazily exposes
`/imaging/orders` → `OrdersPage.tsx` → `listImagingOrders` (`api.ts`) →
`send` (`api/transport.ts`); `/imaging/orders/:id` → `OrderDetailPage.tsx` →
`getImagingOrder` / `scheduleImagingOrder` / `linkStudy` /
`signInterpretationReport` / `addAddendum` → `OrderDetailScreen.tsx`.
`OrdersPage.test.tsx` and `OrderDetailPage.test.tsx` mock `send` and render those
pages through the real providers, asserting URLs, tenant headers, `If-Match`,
idempotency keys and the rendered states. `domain.test.ts` and `screens.test.tsx`
cover the pure rules and every presentational branch.

## Findings

- **Out-of-scope shared route-registry tests (blocker, integrator-owned).**
  `src/features/radiology/routes.ts` registers `/imaging/orders` and
  `/imaging/orders/:id`; the app's `import.meta.glob` self-registers them, so the
  exact-list assertions in `src/app/routes.test.tsx:20` and
  `tests/app/AppShell.test.tsx:130` now fail. READY-25's hand-off note records
  the identical cross-worker situation and states the integrator reconciles
  these arrays. I did **not** edit those out-of-scope files (AGENTS.md rule 3 and
  the worker brief). Exact next step: insert `'/imaging/orders'` and
  `'/imaging/orders/:id'` after `'/schedule/book'` in both expected arrays (two
  lines per file) — then `bash apps/staff-web/check.sh` is green with
  `Test Files 64 passed (64)` and coverage 100% on every file.
- **WEB-09 retry/copy actions on the shared state views are inert.** `StateView`
  accepts no callbacks (out of scope); this feature supplies its own working
  reload action after a command error. Compare/Copy and retry from the load-error
  view remain a shared-component follow-up (same as READY-25 F2).
- **Idempotency-Key reuse across manual retries is not implemented.** Each API
  call mints a fresh `crypto.randomUUID()` per user action (matching the
  sibling clients); key reuse on retry of the same action needs page-level key
  ownership plus the shared `StateView` callbacks, deferred with the point above.
- **Imaging routes are not in the generated contract yet.** `api.ts` borrows a
  published path for headers and substitutes the URL, exactly like
  `features/patients` and `features/scheduling`. The wire types are feature-owned
  and should be reconciled when the imaging API is added to `contracts/openapi.yaml`.
- No production defect was observed in the tool evidence; no BUGS.md entry is
  warranted for in-scope behavior.

## Lessons for workers

- With the self-registering `import.meta.glob` router, adding any
  `features/<name>/routes.ts` breaks the two hard-coded route-registry expected
  arrays; the owning worker cannot fix them inside a feature-only scope. Prefer
  letting the integrator/BUILD-52 reconcile them, and say so explicitly in notes.
- A multi-step workflow must fold the API-returned `version` back into local
  state after every command or the next `If-Match` is stale — one write per test
  hides this; add a two-writes-in-one-mount regression.
- A defensive enum guard (`isModality`) is cheap and keeps invalid values off the
  wire, but every new validation branch needs both a refuse and an accept test.
