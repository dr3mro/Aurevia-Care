## Summary

Adds the two WEB-05 unauthenticated health routes to the staff API: `GET /health/live` (process-local, never touches the database) and `GET /health/ready` (a `SELECT 1` probe through the injected `JdbcTemplate`). Readiness reduces any `DataAccessException` to HTTP 503 with a status-only body, so connection strings, host names, versions and exception text cannot leak. No Actuator dependency, no routes registered with `TenantContextInterceptor`, no build or version data.

## Data changes

None. No Flyway migration, no backfill, no schema or data changes. `GET /health/ready` issues a read-only `SELECT 1` using the already auto-configured `JdbcTemplate` and the existing runtime role; no new table or permission is introduced. The integration test creates and drops its own synthetic database `smartclinic_health_it`, matching the pattern of the other integration suites.

## Authorization boundaries and audit events

The routes are deliberately outside `/api/v1/**`, the only prefix registered with `TenantContextInterceptor` (`addPathPatterns("/api/v1/**")`). No tenant context, login header or correlation header is read or required, and no audit event is emitted: health probes are operational, not clinical actions. The status body is a constant and carries no identifier, version, host or diagnostic detail.

## Migration and rollout considerations

No migration or rollout impact. The new controller is picked up by existing component scanning and needs no configuration property. `HealthController` stores the Spring-managed singleton `JdbcTemplate`; the constructor carries the project's standard `@SuppressFBWarnings(EI_EXPOSE_REP2, "Spring-managed singleton collaborator")` annotation used by other injected collaborators.

## Findings

- Decision (scope): the story's `scope` lists only the `web` main and test paths, so `HealthReadyIntegrationTest` was placed in `apps/api/src/test/java/com/aurevia/smartclinic/web/` with `@Tag("integration")` and a distinct synthetic database, while copying the setup used by suites under `it/`. This keeps every changed file inside the declared scope. No `it/` path was touched.
- Decision: readiness follows the story exactly (`SELECT 1` = database reachable). WEB-05 also mentions "migrations current"; verifying Flyway state is a separate, larger probe and was not added, per the story's explicit instruction.
- Finding for a follow-up (not fixed here, outside scope): the non-synthetic OIDC `SecurityFilterChain` in `web/SecurityConfiguration.java` uses `anyRequest().authenticated()`, so under production profiles `/health/**` would require a bearer token. WEB-05 says these routes need no authentication. Fixing it means editing `SecurityConfiguration.java`, which is outside this story's scope; a follow-up should permit `/health/live` and `/health/ready` in that chain while leaving `/api/v1/**` protected.
- Environment: the worktree `opencode.json` is the CI profile under `skip-worktree`; `check-pack.py` reported it stale until the committed HEAD profile was temporarily restored for the local gate and the CI profile was put back afterwards. No tracked change to `opencode.json` was made. This is the already-documented OPS-CW-003-01 measurement artifact.
- No defects in the new code were found. Synthetic fixtures only; no patient data, credentials or real host names were used.

## Lessons for workers

- In a cloud worker, `check-pack.py` staleness can be the CI-profile `skip-worktree` artifact, not a real stale file: confirm with `git ls-files -v opencode.json` and `cmp opencode.json .github/opencode.ci.json`, then run the local gate with `git show HEAD:opencode.json` restored and put the CI profile back.
- `scripts/check-secrets.py` matches a variable literally named `secret` assigned a quoted string of 8+ characters, even in a test fixture. Name negative-test strings `probeMessage` or similar.
- SpotBugs `EI_EXPOSE_REP2` fires on a Spring-injected `JdbcTemplate` field; use the project's established constructor annotation (`@SuppressFBWarnings(value = "EI_EXPOSE_REP2", justification = "Spring-managed singleton collaborator")`) rather than weakening the analysis.
- When running SpotBugs alone with `-DskipTests`, JaCoCo will fail because the exec data is empty; that is expected, not a coverage regression. Re-run the full `verify` for coverage.
- Check the task's `scope` before placing an integration test: a `@Tag("integration")` test tagged correctly can live in the `web` test package, so a distinct synthetic database does not require touching `it/`.
