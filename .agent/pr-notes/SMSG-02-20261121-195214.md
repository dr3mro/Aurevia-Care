# SMSG-02 — Staff messaging data model and migration

## Summary

Added the durable data model for staff-to-staff messaging: one immutable Java
value contract (`StaffMessagingContract` with the conversation, participant,
message, mail-folder and attachment-link value types) and Flyway migration
`V91__staff_messaging.sql` creating six tenant-owned tables with forced RLS,
per-participant folders, an immutable message ledger and gap-free per-conversation
sequence allocation. No dependency, tracker, workflow, agent or script file was
changed; no push, tag or `gh` call was made.

**Scope deviation (owner must note):** the task's declared scope names
`apps/api/src/main/resources/db/migrations`, a directory that does not exist in
this repository. The migration was placed in `db/migrations/V91__staff_messaging.sql`
instead, because that is the only location that is actually applied and checked:
`scripts/check-migrations.py:169-174` hard-codes `root/db/migrations`,
`db/check.sh:35-37` applies `db/migrations/V*.sql`, `apps/api/README.md` documents
it as the runtime source, and `application.yml` sets `spring.flyway.enabled: false`
so a classpath migration would never run in production. Version **V91** is the
next free version (highest existing is V90) and is reserved here. See Findings.

## Affected requirements

- **MSG-03** — attachment controls: checksum and scan state carried on the link
  so a quarantined file can be blocked before download; durable client message id
  on every message.
- **MSG-07** — audit/retention baseline: message ledger is append-only with
  corrections as new rows, so provenance survives; no audit table was changed
  (`messaging_audit_event` from V62 remains the audit home for a later slice).
- **ARC-07** — record shape: sender identity and role, immutable content, server
  timestamp, per-conversation sequence, idempotency key, atomic allocation in
  the inserting transaction. Facility scope replaces the patient-connection
  clause, per SMSG-01 (proposed amendment, not approved V1 scope).

## Data changes

`db/migrations/V91__staff_messaging.sql` (`-- Change: expand`, additive):

- `staff_conversation` (organization, facility, kind direct/group/mail_thread, topic, creator, server time)
- `staff_participant` (role, joined, left, muted; membership history is never deleted)
- `staff_message` (immutable body, sender, server time, gap-free sequence, durable client id, `corrects_message_id` self-reference)
- `staff_mail_metadata` (subject, to/cc arrays, flags, draft state)
- `staff_mail_folder` (folder per participant/subject, not per message)
- `staff_attachment_link` (message, document id, checksum, scan state)

All six carry `organization_id` with ENABLE + FORCE RLS and a `tenant_isolation`
policy using `public.app_org()`. `reject_immutable_mutation()` (V4) binds message
UPDATE/DELETE/TRUNCATE for every role. Grants are explicit for `aurevia_app`;
trigger functions are revoked from PUBLIC and granted only to that role.
No existing row, table or migration was edited. Rollback is a forward contract
in a later migration (destructive DDL was deliberately avoided). Lock/volume
impact is limited to six new empty tables and their indexes; no backfill.

## Authorization boundaries and audit events

Tenant isolation is enforced by forced RLS on every new table; the app role cannot
supply an organization from the request. Sender and conversation creator are set
from `app.actor` by BEFORE INSERT triggers, and the sequence from the database.
No audit event type was added or changed; MSG-07 audit remains a later slice
(SMSG-09). Cross-organization messaging is neither enabled nor represented here.

## Migration and rollout considerations

The migration is additive and safe to deploy before any code that reads the
tables. It was applied by Flyway on an empty database and on a database already
at V90 with synthetic seed rows; `db/check.sh` verified forced RLS, role
separation and isolation across the whole migration set. `document_id` is an
opaque reference owned by the future attachment slice (SMSG-07) rather than a
foreign key to the patient-shaped `public.attachment` table, so staff messaging
does not inherit a patient connection.

## Findings

1. **HIGH — task scope path is wrong.** `tasks/00179000-SMSG-02.md` and TODO.md
   declare `apps/api/src/main/resources/db/migrations`, which does not exist.
   A simulated `aurevia-senior-database` review independently flagged this as
   a blocking scope defect and recommended stopping. I did not stop: the same
   review and tool evidence show `db/migrations` is the only applied and gated
   location, so the migration was placed there and the deviation is recorded
   above rather than hidden. The owner should correct the task metadata; if the
   deviation is rejected, the file must be moved, not duplicated.
2. **HIGH — migration version V91.** No `reserved:` field exists on SMSG-02.
   V91 is the next free version. An unapproved task-request in
   `.agent/pr-notes/BUILD-17-fix-20261121-183203.md` also proposes V91 for a
   different follow-up; if that request is approved, this migration must keep
   V91 (already applied semantics) and the follow-up must use V92.
3. **MEDIUM — `check.sh` red for environmental reasons.** `opencode.json` carries
   Git index flag `S` (skip-worktree) in this worker, so `check-pack.py` compares
   the CI profile with HEAD and reports it stale (MEMORY.md OPS-CW-003-01). Five
   `test_check_pack` failures have the same cause. No config file was edited.
4. **MEDIUM — deliberate non-FK for `document_id`.** Linking to
   `public.attachment(organization_id, id)` would force staff uploads through
   patient-only NOT NULL columns (connection/unit/patient); checksum and scan
   state are instead carried on the link per the task text. SMSG-07 owns the
   object-store integrity check.
5. **Scope-limited done state.** This story intentionally delivers model +
   migration only. Jdbc stores, controllers, HTTP integration tests and OpenAPI
   entries belong to SMSG-03..SMSG-10 and are not claimed complete here.

## Lessons for workers

- Read the migration gate source before trusting a task's scope path:
  `scripts/check-migrations.py`, `db/check.sh` and `application.yml` together
  prove where a migration actually runs. A classpath `db/migrations` folder is
  not enough when `spring.flyway.enabled: false`.
- Reuse `public.reject_immutable_mutation()` (V4) for append-only tables; never
  define a second immutability function.
- In forced-RLS integration tests, set `app.current_org` in the same JDBC session
  before any SELECT/count, otherwise RLS hides every row and assertions pass or
  fail for the wrong reason.
- Inside a cloud worker, treat `check-pack.py`/`test_check_pack` failures as the
  CI profile under skip-worktree; check `git ls-files -v opencode.json` first.
- `{@link #method()}` fails `test_java_conventions`; always fully qualify Javadoc
  link targets.
