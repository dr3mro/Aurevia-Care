# SPEC-LAB-01-C01 — LAB-01 clause 1 API acceptance test

## Summary

Adds a focused, real-PostgreSQL API acceptance test proving LAB-01 clause 1,
"Accession a requisition with an issuer-scoped unique ID", plus a clause-evidence
document. The clause is already fully built in production; this change adds only
proof. No production code, existing test, contract, migration or tracker is edited.
The test uses a dedicated database, two synthetic tenants (each with its own
synthetic patient), the synthetic-auth profile and Flyway from
`filesystem:../../db/migrations`, following the fixtures of
`it/lab/SpecimenAccessionIsolationTest`.

## Affected requirements

LAB-01 (clause 1). Supporting invariants exercised: ARC-01 (issuer-scoped key),
ARC-02 (forced RLS tenant isolation), ARC-03 (machine-readable errors), IAM-01
(bounded role policy), OPS-02 (audit on each accession outcome).

Acceptance mapping:

- Positive rule proof → `labCollectorAccessionsRequisitionWithIssuerScopedNumber`
  (201, issuer-scoped number/issuer in response and durable row, peer tenant cannot see it).
- Issuer-scoped uniqueness → `duplicateNumberForSameIssuerIsRefusedButAnotherIssuerMayReuseIt`
  (same issuer + number 409 `CONFLICT`; different issuer 201).
- Tenant-scoped uniqueness and concealment → `peerTenantMayReuseNumberAndCannotReadFirstAccession`
  (peer tenant 201 with its own patient; cross-tenant GET 404; DB row hidden under RLS).
- Role denial → `roleWithoutAccessionPermissionIsRefused`
  (reception and lab_verifier both 403 `FORBIDDEN`).
- Input fail-closed → `malformedIssuerAndNumberAreRefused`
  (422 `INVALID_ISSUER` and `INVALID_ACCESSION`).

## Risk class

Cross-boundary (API + database + tenant/role policy) but test-only: the proof
exercises tenant isolation and role denial, so DevSecOps and coverage reviews
apply; no production boundary is changed.

## Review owner

Senior Java and Spring Boot; Tester; DevSecOps (isolation/role negatives).

## Data changes

None. No migration, backfill, lock or volume impact. The test drops and recreates

drops it in `@AfterAll`; all rows are synthetic.

## Authorization boundaries and audit events

The test asserts that `ACCESSION_CREATE` is allowed only for `lab_collector` and
that `reception` and `lab_verifier` are denied (403). It asserts cross-tenant
concealment (404) under forced RLS. It does not add or change any audit event;
it exercises the existing `LAB_ACCESSION_CREATE` audit path in
`LabAccessionService.accession`.

## Migration and rollout considerations

None. No production deployment, no contract change, no OpenAPI/client regen.
`POST /api/v1/lab/accessions` remains baselined in
`contracts/openapi/missing-routes.txt` — a separate contract story, out of scope.

## Lessons for workers

- When reusing `SpecimenAccessionIsolationTest` fixtures, copy the pattern but use a
  dedicated database and globally distinct accession numbers/MRNs per test: the
  shared DB has no per-test reset, so reused values cause order-dependent 409s.
- `worker-check.sh` runs every module's integration suite and can exceed the 5-minute
  foreground command budget (it moved to the background and completed green here).
  Run the targeted `-Dtest=... -Dgroups=integration` suite plus the individual
  policy/SpotBugs/docs commands for fast bounded feedback, and let the integrator run
  the full gate. If worker-check has run, re-run the targeted test last so the
  class-specific Surefire XML artifact it deletes at line 48 is present for review.
- The 5-6 `test_check_pack.py` failures in a cloud worker are the CI-profile false
  positive: confirm `git ls-files -v opencode.json` → `S`, compare
  `git show HEAD:opencode.json` with the generator render, record the command and
  final line, and do not regenerate or edit the protected file.
