# SPEC-IAM-01-C06 — IAM-01 clause 6 API test

## Summary

Added a focused HTTP-level integration test that proves IAM-01 clause 6, "Every write checks current scope." A facility create succeeds only when the actor has active membership and the write permission in the organization selected for the current request; it is refused (403) with no row created for an actor from another tenant, a revoked membership, and an active member lacking the write permission. Added the clause evidence document. No production code, contract, migration or existing test was changed.

## Findings

The clause is **built, not a GAP**, so no `@Disabled` test was needed. Where it is implemented today (discovery result for story step 1):

- `apps/api/src/main/java/com/aurevia/web/TenantContextInterceptor.java` — binds the current scope from `X-Active-Organization` plus the authenticated subject; never infers it from the request body or a resource ID.
- `apps/api/src/main/java/com/aurevia/tenant/TenantContext.java` — immutable request-scoped tenant identity.
- `apps/api/src/main/java/com/aurevia/web/FacilityController.java` — thin `POST /api/v1/facilities` entry point; `CreateRequest` deliberately has no organization field.
- `apps/api/src/main/java/com/aurevia/tenancy/FacilityService.java` — `create(...)` calls `authorize("FACILITY_WRITE")` inside the tenant-guarded transaction, re-reading membership and roles on every write.
- `apps/api/src/main/java/com/aurevia/tenancy/FacilityRepository.java` — RLS-bounded store; `db/migrations` supplies per-tenant RLS/FORCE RLS.
- `apps/api/src/main/java/com/aurevia/authz/ActionPolicy.java` — action/role decision.
- The same current-scope re-check also exists in `staff/StaffService`, `staff/StaffInvitationService`, `configuration/ConfigurationService`, other domain `*Service.authorize(...)` methods and the central command gate `api/authorization/CommandAuthorization.java`; those are exercised by their own suites (`StaffServiceTest`, `StaffInvitationServiceTest`, `ConfigurationServiceTest`, `CommandAuthorizationTest`) and were not duplicated here.

Bounded specialist review (Senior Spring Security and OIDC, simulated/synthetic, 2026-11-21): confirmed "Proven by tests" is accurate and no `@Disabled` GAP is warranted; the three negatives are genuine current-scope checks (other-tenant RLS concealment, revoked membership re-resolution, role re-check), not input validation; no blocking defect for the full gate. Non-blocking feedback applied: the test Javadoc was tightened so it no longer claims to prove request-context cleanup (covered by `FacilityIsolationTest`) or audit of denials (this write path does not use the `CommandAuthorization` decision sink; the clause does not require it).

## Lessons for workers

- A cloud worker's worktree `opencode.json` is the CI profile under skip-worktree; `check-pack.py` and `test_check_pack` going red there is a measurement artifact. Confirm with `git ls-files -v opencode.json` and `git show HEAD:opencode.json` instead of editing the file.
- Do not run `scripts/check.sh` (it calls full `mvn verify`) in a worker: run `mvn ... -Pno-security,fast test`, the targeted `-Dtest=Class` integration run, SpotBugs and the policy checks separately.
- For a parallel-worker clause test, give the integration class its own synthetic database name (`aurevia_scope_it`) so concurrent workers do not drop each other's DB in `@BeforeAll`.
- Prove "current scope" with an actor who is privileged in a *different* tenant and with a revoked membership in the current tenant; these distinguish scope re-checks from input validation.
