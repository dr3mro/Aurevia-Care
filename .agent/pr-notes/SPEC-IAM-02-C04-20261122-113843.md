# SPEC-IAM-02-C04 — API calls using expired or removed membership fail closed

## Summary

Added one real-PostgreSQL acceptance test class and one clause-evidence document proving
IAM-02 clause 4. No production code, existing test, contract or migration was changed.
Four active tests (no `@Disabled`) cover: an active tenant_admin succeeds; an expired
membership (`valid_to` in the past) is refused on the next read and write; a membership
removed through the real deactivation endpoint is refused on the next read and write; and
membership in another organization does not authorize a call against the selected one.
All fixtures are synthetic.

Defects/surprises and next-worker notes:

- The `CommandAuthorization` gate is not wired into production controllers (known debt
  from AUD-20261120-14: referenced only from `api/authorization` and tests). This clause is
  nevertheless enforced today by the owning services' `hasActiveMembership`/`activeRoles`
  calls, which the new tests exercise over HTTP; wiring the gate is a separate cross-boundary
  story and is not in this task's scope.
- Expiry (`valid_to`) is a database-level state: there is no API to expire a membership, so
  `expired-a` is seeded with explicit `valid_from`/`valid_to` SQL in `@BeforeAll`, while
  "removed" is produced through the real deactivation API. Both are synthetic.
- The test database name is unique to this story (`smartclinic_iam02_clause4_it`) to avoid
  collisions with concurrently running workers' databases.
- A bounded simulated Spring Security review (`smartclinic-senior-spring-security`, static
  reading only, no builds executed) returned **no blocking findings** and confirmed the
  status "Proven by tests" is justified. Its three low-severity hardening findings were
  applied: F1 — after each refused write, an active admin reads the would-be facility code
  and gets 404, proving no tenant row was created; F2 — the cross-tenant denial now also
  asserts the "no active membership" message; F3 — the clause doc records the write-side
  check, so `## Gap: None` is accurate. F4 (single-run fresh-DB assumption) is mitigated by
  the unique database name and `DROP ... WITH (FORCE)` in `@BeforeAll`; F5 (environment
  sensitivity of `SMARTCLINIC_PG_ADMIN` / port 5432) matches the neighbouring tests and
  the worker image. The test class was re-run after these edits: 4/4 green, 0 skipped.
- The six Python `test_check_pack` failures and the two wrapper-check failures are the
  documented cloud-worker `opencode.json` skip-worktree artifact (OPS-CW-003-01), confirmed
  once with tool evidence; they are not caused by this change and no protected file was
  touched.

## Lessons for workers

- To prove IAM-02 clause 4 deterministically, seed one synthetic member per state in an
  isolated database (active, expired by `valid_to`, removed via the real deactivation API,
  other-tenant), then call the same protected route with each subject; assert both the 403
  and that no tenant data is echoed.
- A quick red probe is to flip the expected status of the negative test to 200 for one run:
  the failure message `expected: <200 OK> but was: <403 FORBIDDEN>` proves the test would
  catch a fail-open. Restore the file and re-run green before committing.
- The membership fold lives in PostgreSQL (`V4` SQL functions), not in Java: assert
  `public.has_active_membership(subject)` as an extra fixture check so a green API denial
  cannot be caused by a wrong fixture.
- In a cloud worker, `check-pack`/`test_check_pack` staleness is the CI profile under
  `skip-worktree`; verify with `git ls-files -v opencode.json` and `git show HEAD:opencode.json`,
  record once, run the remaining gate stages individually and never regenerate that file.
