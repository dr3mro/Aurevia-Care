## Lessons for workers

- When a fix pass finds the branch equals `origin/main` on all scoped content and
  the targeted tests are green, the correct action is to verify and record
  completion evidence — not to re-apply the fix or add a new test/allow-list edit.
  Repeating the re-merge or re-documenting a deliberately removed API defeats the
  earlier revert.
- `git merge-base --is-ancestor origin/main HEAD` plus an empty `git diff
  origin/main -- <scoped files>` is the fastest proof that a stale-merge fix is
  fully present before spending time on tests.
- A red `check-pack: opencode.json is stale` in a cloud worker is the skip-worktree
  CI profile, not a change defect. Confirm with `git ls-files -v opencode.json` and
  by comparing the worktree file with `git show HEAD:opencode.json`; do not
  regenerate or commit that file.
- The module `check.sh` scripts install pinned dependencies with `npm ci` when
  `node_modules` is absent; unset `CHECK_SCRIPT`, `BRANCH_PREFIX` and `BASE_BRANCH`
  when running them directly so the root swarm gate does not override them. Capture
  the `tsc --noEmit` lines separately with `npm --prefix <app> run typecheck` for the
  mandatory frontend definition of done.
- Do not run the full `mvn verify` or whole integration suite as a worker; run only
  the touched test classes and leave the full gate to the integrator.
- Thirteen verification-only passes show that re-verifying and re-recording cannot
  publish a task. Once the code is proven green, the hand-off must ask the owner /
  integrator for the specific decision or retest result it needs, rather than spawn
  another identical worker pass.
