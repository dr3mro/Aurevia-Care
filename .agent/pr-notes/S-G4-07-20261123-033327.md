## Lessons for workers

- Before writing a gate evidence note, grep the exact method names you intend to cite directly from the test files. A method-name shorthand that "looks right" can drift from the real name; a wrong name in a Proven row is a reviewer finding.
- Reuse an existing gate note (g2/g3) as the structure: evidence-source/scope bullets, Purpose, Synthetic fixtures, Evidence matrix, Entry point to test trace, Reproduction, "Open items (not evidence gaps, not acceptance)", Related evidence. The "evidence, not a verdict" framing is the core rule for G-gate documentation tasks.
- For a docs-only task, `python3 -I scripts/check-docs.py`, `check-names.py` and `check-secrets.py` are the canonical gates; run them after the final edit, not before. `check-docs.py` rglob-scans every Markdown file and validates relative links, heading/table structure and spec-defined requirement IDs, so cite only IDs that exist in `SMARTCLINIC_V1_SPEC.md`.
- Context-optimizer and code-reviewer subagents cannot run git themselves; the primary agent must confirm merge commits and SHAs with tool commands and record them as tool evidence.
