# RESP-DESIGN — Design guide: responsive layout patterns for the staff web

## Summary

Added `docs/design/responsive-layout.md`, a documentation-only layout contract for
the staff web from 320 px upward, following decision 0004. It defines the three
breakpoints, the page grid and 1200 px reading cap, navigation per breakpoint, a
nine-row component pattern matrix (phone/tablet/desktop), touch target and
spacing rules, safe-area insets, on-screen keyboard behaviour, orientation
change with preserved work (WEB-09), pointer versus touch, right-to-left
behaviour, zoom and text-spacing, and a per-rule verification matrix naming the
jsdom, Playwright project and axe method. Every CSS example uses logical
properties only. No code, token, configuration, dependency or trackers changed.
No patient data, credentials or real identifiers appear; examples use synthetic
`SYN-0001` and `SYN-FAC-01`.

Entry point to evidence trace: story item 1 (read sources) → doc section 1 and
the links; item 2 (write the guide) → doc sections 2 to 13, with section 13
mapping each rule R1 to R13 to jsdom / Playwright project / axe; item 3 (logical
properties and check-docs) → section 1 plus the commands below.

## Affected requirements

- WEB-07 — supported clients; width is a layout input, no data-free page below

## Findings

- A bounded simulated `aurevia-ux-reviewer` review (tool/simulated-reviewer
  evidence, no human or clinical participant) checked the document against all
  cited sources, the SPEC requirement text and every CSS block. It returned two
  findings, both resolved in this change before commit:
  - F1 (medium): the guide called 200 percent zoom "1.4.10" and omitted the
    400 percent reflow level required by `docs/design/accessibility-patterns.md`
    and the WCAG criterion, while decision 0004 names 200 percent. Fixed in
    sections 3 and 12 and rule R12: 200 percent text scaling is 1.4.4, 320 px
    reflow and 400 percent zoom is 1.4.10, both are tested, and the divergence
    from the 200 percent figure in decision 0004 is disclosed explicitly.
  - F2 (low): two component styles held raw pixel values while section 1 said
    raw pixels appear only in breakpoints or viewport definitions. Fixed by
    declaring `--layout-reading-max` and `--layout-drawer-inline-size` once at
    the shell boundary, using `var()` in the component styles, and amending the
    convention to name layout constants as an allowed location.
  - No other findings: all acceptance items present, no physical CSS property
    in any of the 9 CSS blocks, no accessibility-approval overclaim.
- Source conflict, faithfully recorded and not resolved here: WEB-07 in
  `PROJECT_V1_SPEC.md` and section 1 of `docs/design/screens-and-navigation.md`
  still state the 1280/768 px floors and the sub-768 px "use a larger screen"
  notice with no data. Decision 0004 is `Proposed` and says a person must amend
  the specification. The guide follows the decision and flags the conflict in
  its introduction; the swarm may not edit the spec. This needs an owner
  decision before code implements the compact layout (no code is in this scope).
- The Playwright project matrix (phone, tablet, desktop, en and ar) is a design
  requirement, not implemented here. The current `apps/staff-web/e2e/playwright.config.ts`
  has one `chromium` project. Adding the projects belongs to a separate
  implementation story with its own tests and 100 percent coverage.
- `check-pack.py` stale-config result is an environment artifact (details under
  Test evidence), not a defect of this change.
- All other policy checks listed above are green; no patient data or credential
  was introduced.

## Lessons for workers

- For a docs-only responsive-layout story, the required step 6 gate is
  `python3 -I scripts/check-docs.py`; run the fast policy checks alongside it,
  but do not run `scripts/check.sh` from a worker because `apps/api/check.sh`
  expands to full `mvn verify` and the prompt forbids it.
- When a CSS example must be direction-safe, `env(safe-area-inset-*)` names are
  platform values, not properties: map them once into direction-aware layout
  custom properties, then use only logical padding in components. A strict
  "logical properties only" check should scan fenced blocks, not prose that
  names the forbidden physical equivalents.
- Before treating `check-pack.py`'s "opencode.json is stale" as a finding, check
  `git ls-files -v opencode.json` (look for `S`) and compare the worktree file
  with `.github/opencode.ci.json` and `git show HEAD:opencode.json`. In cloud
  workers the CI profile sits there under skip-worktree; never regenerate or
  commit that file from a swarm worker.
- A design guide that follows a proposed decision against an unamended spec
  must say so explicitly; a document cannot silently amend WEB-07.
