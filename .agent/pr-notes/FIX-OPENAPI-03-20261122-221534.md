## Findings

1. All 37 routes were taken from `contracts/openapi/missing-routes.txt` and
   matched to their controllers. The context-optimizer confirmation found no
   missed route and no wrongly absorbed route: all FIX-OPENAPI-02/-04 finance,
   pharmacy, prescription and health routes remain in the baseline. The advisor
   brief said tag `staff-messaging`; the contract actually reuses existing
   per-family tags (`conversations`, `staff-instant-messaging`, `staff-mail`,
   `scheduling-administration`, `audit`) and those were reused instead — no new
   tag and no rename.
2. `OpenApiPaginationRulesTest` pins an exact list-GET set and cannot be edited
   from this scope. New GET responses are declared as non-`Page` object views;
   the final contract has zero inline `type: array` or `$ref ...Page` new GETs.
3. Every new write declares an Idempotency-Key-family header. New generic
   `RetryKey` (`required: false`) is used where the controller does not bind a
   key, and the existing required `IdempotencyKey` where it does, so the rules
   are satisfied without claiming a meaningless required header.
4. No top-level `security:` block exists in the staff contract; the existing
   convention (required `X-Active-Organization` parameter + 401/403 on every
   operation) is followed. Adding a `security:` block would change the shared
   convention outside this story.
5. **Derived mirror changed deliberately (outside the four listed scope
   prefixes):** `OpenApiContractDriftTest` fails when
   `apps/api/src/main/resources/contract/openapi.yaml` differs by a byte from
   `contracts/openapi.yaml`. The packaged copy was refreshed from the in-scope
   contract; it contains no independent logic and has precedent in earlier
   notes. No other file outside scope was changed.
6. **`worker-check.sh` and Python tooling:** both stop at
   `check-pack: opencode.json is stale` with `git ls-files -v opencode.json` =
   `S` (OPS-CW-003-01). The committed `opencode.json` is correct; the individual
   policy scripts were run directly and all exit 0. The integrator runs the
   full gate against the committed profile.
7. **PR size:** the earlier PR #901 was flagged (7493 lines, >5000 auto-merge).
   This branch keeps only the in-scope contract data plus the derived mirror;
   the remaining ~7.2k changed lines are inherent to documenting 37 operations
   and regenerating the client. Deciding manual merge versus splitting remains
   with the integrator/human; no out-of-scope route was absorbed to inflate it.
8. Pre-existing conflict markers remain in committed `exchange/hl7` Java files
   on `origin/main`; they were neither introduced nor touched here.
9. **Code-review fix (applied):** `POST /api/v1/scheduling/resources/{code}/availability`
   documented `409 StateConflict` and `412 StaleVersion`, but
   `SchedulingAdminService.addAvailability` (lines 133-160) only throws 403, 404
   and 422, takes no `If-Match`, and `resource_availability` has no unique
   constraint. Both statuses were unreachable and were removed from
   `contracts/openapi.yaml` and the packaged mirror (openapi.yaml:1527-1536); the
   client was regenerated. All 50 targeted tests, `gen:api:check` and the drift
   guard re-run green after the fix.
10. **Code-review finding retracted with evidence:** the reviewer initially asked
    for a `428` on `POST /api/v1/staff/instant/{conversationId}/messages` because
    `IdempotencyKey.parse` throws 428. The instant path does not call `parse`:
    `InstantMessagingService.send` (line 176) calls `requireKey` (lines 317-322),
    which throws invalid → `new ApiException(422, "INVALID_INPUT", ...)` (lines
    331-333). 422 is already documented at openapi.yaml:1110; adding 428 would be
    an invented status. DevSecOps independently confirmed 422 (instant) versus
    428 (mail send via `IdempotencyKey.parse`). Reviewer retracted the finding and
    returned GO.
11. **Optional review notes (no action):** a top-level `security:` block is absent
    across all 69 operations (pre-existing), so `checkSecurityResponses` never
    fires; the nine new list GETs use `*List` wrapper schemas to stay outside the
    pinned list-GET set; the reused required `IdempotencyKey` component says
    "placement"/"order" and the shared `ConfirmationNeeded` 428 description says
    "recipient confirmation" on mail send. Each is a pre-existing convention or
    documentation-accuracy nit outside this data-only scope; no threshold or
    exclusion was changed.

## Lessons for workers

- Refresh the packaged `apps/api/src/main/resources/contract/openapi.yaml`
  whenever `contracts/openapi.yaml` changes; the drift guard is byte-exact and
  the API serves the packaged copy.
- Run `npm ci` in `apps/staff-web` before `gen:api:check` in a fresh worker;
  otherwise the generator reports `dependencies missing`.
- The staff contract reuses per-family tags; do not follow an advisor brief that
  names a single blanket tag when the file already has domain tags.
- `OpenApiPaginationRulesTest` pins the exact list-GET operation-id set and
  `OpenApiContractRulesTest` pins an operation-id allowlist; use non-`Page`
  object response views for new GETs and give every new operation a tag and an
  Idempotency-Key-family header.
- A `check-pack` failure reading `opencode.json is stale` with `git ls-files -v`
  = `S` is OPS-CW-003-01 in cloud workers; verify once, record the command and
  final line, run the remaining stages individually, and never regenerate or
  commit that file.
- Whole-contract data-driven gates already prove per-operation contract
  properties; a per-operation test would duplicate them without new behavior.
