## Summary

CLN-07's association side already stored the upload SHA-256 (V17 trigger over the retained bytes), kept rotation as a presentation column, and voided with a mandatory reason plus an append-only history guarded by an immutability trigger. The missing guarantee was **re-verifying the checksum on download**. This change adds a verified-download path: a V75 PostgreSQL function recomputes `sha256(content)` from the exact retained bytes and compares it with the stored digest before returning any byte; a repository call, an audited domain command and a thin controller endpoint expose it. A mismatch is refused with 409 `CHECKSUM_MISMATCH`. Tests prove tampered bytes are detected, a void keeps the original bytes and history, and another tenant cannot read the association.

## Data changes

New `db/migrations/V75__build_06.sql` (reserved version V75, `-- Change: expand`) creates **one function and no table**: `public.document_association_verified_content(uuid) RETURNS bytea`. It is additive and changes no existing row. It runs as the invoker (`SECURITY INVOKER` default), so forced RLS on `document_association` (V17) bounds it to `public.app_org()`; a foreign or absent row returns NULL. `EXECUTE` is revoked from `PUBLIC` and granted only to `smartclinic_app`. No existing migration was edited; no backfill; negligible lock/volume impact. Flyway applied it in both integration runs: `Successfully applied 33 migrations to schema "public", now at version v75`.

## Authorization boundaries and audit events

The new command re-derives membership and the document action matrix through the existing `DocumentService.authorize` (`DOCUMENT_READ`) on every call; a denial is audited (`DENIED`) before the exception leaves the transaction. A successful verified download appends `DOCUMENT_READ` / `DOCUMENT_CONTENT` with outcome `SUCCESS`; a missing association or missing content appends `NOT_FOUND`; a checksum mismatch appends `TAMPERED` and surfaces as 409 `CHECKSUM_MISMATCH`. No payload, file name or URL is logged. Tenant context comes only from `TenantContext`/`X-Active-Organization`, never from the request body. Void continues to require `DOCUMENT_VOID` and a bounded, trimmed reason and to append a `void` history event.

## Migration and rollout considerations

V75 sorts after V17 (which owns `document_association`, its forced-RLS policy, the insert-time digest trigger and the void guard) and is applied as a normal Flyway step; the function depends only on that table and built-in `sha256(bytea)`. Deploy is additive: existing rows already carry a DB-derived digest, so no dual-write or backfill is needed and the new endpoint is available immediately. Rollback is a later contract migration that drops the function (pointing at V75 as its `Requires-expand`), per `docs/decisions/0002`. `scripts/check-migrations.py --require-baseline` and `db/check.sh` both pass with V75 present.

## Findings

1. **Environment artifact (not a defect from this change):** `opencode.json` is flagged `S` (skip-worktree) in this worker checkout, so `check-pack.py`, `gen-opencode.py --check`, the three `test_check_pack` unit tests and therefore `scripts/worker-check.sh` judge the CI profile copied under skip-worktree, not the committed local profile. This is the documented dispatch-3 finding in `MEMORY.md` and the READY-37 note. `git show HEAD:opencode.json` was not modified by this story and `git status` shows no change to it. No regeneration was attempted (out of scope and would be wrong). The integrator's trusted gate uses the committed file.
2. **Out-of-scope contract update:** the new `GET /api/v1/documents/associations/{id}/content` endpoint is a public contract change. `contracts/documents/document-artifacts.md` and the OpenAPI entry live outside this story's `scope` and were deliberately not edited; the integrator/owner should add the endpoint to those documents. The controller Javadoc was updated in-scope.
3. **Full HTTP `@SpringBootTest` for the new endpoint:** the repository convention places those in `apps/api/src/test/java/com/aurevia/smartclinic/it/documents`, outside this worker's scope. A direct controller binding test (`DocumentContentControllerTest`) and a real-PostgreSQL function test (`DocumentDigestIntegrationTest`) are provided within scope; the integrator may add a SpringBootTest version when it owns that path.

## Lessons for workers

- A story whose `scope` names a migration file with a build id (e.g. `V75__build_06.sql`) is safe for `check-names.py` — that gate checks folders/packages/classes, not migration filenames — but still give the SQL function a business-domain name.
- When the digest is DB-derived, prove read-side verification with a real database: disable row triggers as superuser (`SET session_replication_role = replica`) to simulate storage-layer tampering, then assert the verifying function raises the intended SQLSTATE. A mocked exception only proves the service mapping, not the SQL guard.
- `scripts/worker-check.sh` in a cloud worker fails at `check-pack` because `opencode.json` is under skip-worktree; run its later stages individually (SpotBugs, `db/check.sh`, Java conventions, targeted JaCoCo) and record the artifact rather than regenerating the file.
