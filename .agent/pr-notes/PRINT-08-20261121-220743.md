# PRINT-08 — Staff web: register the Print buttons on the prescription, order and chart screens

## Summary

Registered the three existing reusable print buttons behind one public barrel and documented where each owning screen mounts them. Created `apps/staff-web/src/features/print/index.ts`, which exports exactly `PrintPrescriptionButton`, `PrintOrderButton` and `PrintChartButton` and nothing else; `apps/staff-web/src/features/print/routes.ts`, which honours the feature-route contract with an empty route list (printing owns no screens); tests for both; and `apps/staff-web/src/features/print/README.md` with the exact import and JSX placement line for each button. No screen, prescription, radiology or chart feature was edited — the owning screen mounts its own button and performs the protected print call and audit. No dependency added, no generated file touched, synthetic data only.

Requirement note: the story names WEB-09, which in `PROJECT_V1_SPEC.md:157` is the resilient-screens requirement; the print-button behaviour itself was delivered by PRINT-05/06/07 under RX-02/CLN-03/CLN-05. This story is the single-barrel registration of those three components, so WEB-09 is recorded as the task's declared requirement and the barrel keeps the preview/resilience behaviour those components already implement. No requirement ID was changed.

## Findings

1. **Pre-existing generated-client drift blocks the module check.** `bash apps/staff-web/check.sh` stops at `gen:api:check`; `contracts/openapi.yaml` contains printing endpoints that `src/api/generated/openapi.d.ts` does not. Fixing it requires committing a generated file outside this task's scope; it is recorded here and in PRINT-07's notes rather than attempted.
2. **Deliberate minimal barrel.** Prop types are intentionally *not* re-exported: "the three components and nothing else" is the acceptance criterion, so screens needing a prop type import it from the button's sub-module (documented in the README).
3. **No screen mounts a button in this scope.** The prescription/order/chart screens belong to other features; this task provides the single import path and exact placement lines only. A follow-up task owns the wiring (task-requests below).

4. **Simulated senior-react review — no actionable findings.** Verified the barrel is exactly the three named components, that the empty `routes` array is safe against the real `FeatureRouteModule` glob contract (`app/routes.tsx:37-40`, `collectFeatureRoutes:55-74`), that every README prop/snapshot field matches the real button signatures, and that both new files are single re-export/assignment statements with no branches. Its one cosmetic nit (`PrintableOrder[]` → `readonly PrintableOrder[]`) was fixed. The reviewer was static/read-only and did not re-run commands; it relied on the tool evidence recorded above.

## Lessons for workers

- For a re-export-only barrel, `Object.keys(module).sort()` in a Vitest test is the direct way to prove "exports X and nothing else"; each value is then asserted to be a function (a component).
- An empty feature `routes.ts` (`export const routes: AppRoute[] = []`) is picked up by the `import.meta.glob('../features/*/routes.ts')` registry but claims no path, so it neither breaks the route tests nor shadows a screen.
- A frontend-only worker can prove its slice green even when `bash apps/staff-web/check.sh` is red at `gen:api:check` from another story: run typecheck, lint, build, bundle and `test:coverage` individually and record the read-only regeneration diff.
