## Findings

- Confirmed environment false positive (tool evidence): `git ls-files -v opencode.json` prints
  `S opencode.json` (skip-worktree); the worktree file is the CI runtime profile whose hash
  differs from `git show HEAD:opencode.json`, so `check-pack.py`, `python-coverage.sh`,
  `python3 -I -m unittest discover -s scripts/tests` (6 `test_check_pack` failures,
  final line `FAILED (failures=6)`) and `worker-check.sh` all report `opencode.json is stale`.
  Confirmed once; no protected file was regenerated or committed. The integrator owns the full
  gate.
- The first red run showed that PostgreSQL renders `timestamptz` as
  `2026-11-19 10:15:30+00`. The tests now parse the wire value back into an `Instant` and also
  assert that the GET read-back value equals the command response value; this proves the
  submitted instant was recorded without depending on a literal string form.
- Spring's `HttpStatusCode` for 422 renders as `UNPROCESSABLE_CONTENT`, so negative assertions
  compare numeric status values rather than enum identity.
- Adjacent debt (out of scope, not a clause gap): collect/receive are baselined in
  `contracts/openapi/missing-routes.txt`; `SpecimenAccessionIsolationTest` and
  `IssuerCodeBoundaryTest` already cover related paths on `main`. Documented in Evidence,

## Lessons for workers

- For an HTTP proof of a `timestamptz` field, parse the returned wire value back into an
  `Instant` and compare it to the submitted instant; PostgreSQL's `::text` form is not the
  ISO-8601 literal you posted. Also compare command response to GET read-back to prove the
  round-trip.
- In this Spring version compare `response.getStatusCode().value()` to an int for 422:
  `HttpStatus.UNPROCESSABLE_ENTITY` does not equal the returned `UNPROCESSABLE_CONTENT`
  status object.
- A test-only clause story still needs the three post-code review verdicts; the plan reviewer
  caught the timestamp wire form before the red run.
