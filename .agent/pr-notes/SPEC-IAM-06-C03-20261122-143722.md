# SPEC-IAM-06-C03 — It cannot unlock other organizations' data

## Summary

Adds a focused real-PostgreSQL clause-proof test for IAM-06 clause 3 and the clause evidence
document. Emergency access is already built and enforces own-organization scoping; the test
proves the rule is met and proves two refusal paths (foreign active organization and
cross-tenant review). No production code, existing test, contract or migration is changed.

## Affected requirements

IAM-06 (clause 3).

## Risk class

Routine — test and documentation only; no production code, contract, migration or dependency
changed. The behaviour proven is a tenant-isolation/authorization boundary, so the evidence
was gathered with the cross-boundary gate (HTTP entry point, forced RLS, migration) in mind.

## Review owner

orevia-senior-backend, orevia-senior-spring-security (authorization boundary) and
orevia-qa-reviewer (independent evidence). No clinical reviewer needed: synthetic
fixtures only, no real patient or human feedback.

## Data changes

None. No migration, backfill, lock or volume impact, rollback or forward-fix. The test drops

`@AfterAll`, using the existing `orevia_migrate` / `orevia_app` roles.

## Authorization boundaries and audit events

No audit event or authorization rule was added or changed. The test exercises the existing

against active membership inside the guarded transaction; the grant is stored with
`organization_id = active organization`; forced RLS hides it from other organizations. No
PHI, credential or real identifier appears in the fixtures.

`V11__emergency_and_support_access.sql` and `V88__access_review.sql`, both with forced RLS).

## Lessons for workers

- In this cloud worker, a red `test_check_pack.py` about a stale `opencode.json` is the
  skip-worktree CI-profile false positive: confirm with `git ls-files -v opencode.json` (`S`)
  and `git show HEAD:opencode.json`, then run the other gate stages individually. Do not edit
  or regenerate `opencode.json`.
- `worker-check.sh`, `check.sh`, `coverage-check.sh` and `apps/api/check.sh` all escalate to
  the full integration/`mvn verify` gate; for a scoped worker run, use
  `mvn -Pno-security -Dgroups=integration -Dtest=ClassName test` plus the individual policy
  scripts instead, and leave the full gate to the integrator.
- For an integration clause test, give each grant-creating test a distinct synthetic subject:
  the emergency service refuses a second unexpired grant for the same subject with 409, so
  reusing a subject makes order-dependent failures.
