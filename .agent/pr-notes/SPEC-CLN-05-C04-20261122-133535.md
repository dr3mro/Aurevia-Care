# SPEC-CLN-05-C04 — Signed revisions cannot be edited (API test)

## Summary

Added an HTTP-level acceptance test proving CLN-05 clause 4 ("Signed revisions
cannot be edited") against the existing implementation, plus the clause evidence
document. No production code, contract, migration or existing test was changed.

Discovery step 1: the clause is **not** implemented in the `chart.record` package
named in the task (that package owns CLN-03 record/verify/read and has no signing
lifecycle). It is implemented in `com.aurevia.clinical.notes`:
`ClinicalNoteController` (`PUT /api/v1/clinical-notes/{id}` → `edit`),
`ClinicalNoteService.updateDraft` → `requireEditable` (409 `IMMUTABLE_REVISION`),
`NoteState.editable()` (only `DRAFT` / `AMENDMENT_DRAFT` are editable),
`NoteRepository` and the append-only revision ledger in `db/migrations`.
Neighbours found: `com.aurevia.it.clinical.ClinicalNoteRevisionIntegrationTest`
(whole CLN-05 flow), `clinical.templates`, `clinical.queues`, and the contract
under `contracts/openapi` (clinical-notes routes).

The clause is built, so the test is enabled (not `@Disabled`) and green; there is
no GAP and no production change.

## Findings

- The task's scope names the `chart` package for the test, but CLN-05 is owned by
  `com.aurevia.clinical.notes`; the test therefore exercises that
  package through its real HTTP entry point while living in the requested
  `chart.clauses` test package. A future reader should look in `clinical.notes`,
  not `chart.record`, for the signing lifecycle.
- The new test's DB (`orevia_signedrev_it`) is distinct from the existing
  CLN-05 integration test's DB (`orevia_cln05_it`) so parallel workers do
  not collide.
- The clause was already covered in part by
  `ClinicalNoteRevisionIntegrationTest.signedRevisionsCannotBeEditedOrReSigned`;
  this story adds a dedicated clause test with wrong-role, other-tenant and
  stale-version negatives and read-back assertions of unchanged signed content.
- Pre-existing, out-of-scope observation (tool): `git grep -nE '^(<<<<<<<|>>>>>>>) '`
  finds conflict markers inside Javadoc comments in three tracked HEAD files
  (`exchange/hl7/Hl7ParseException.java`, `Hl7Parser.java`, `Hl7Segment.java`,
  from `origin/swarm/BUILD-37-469`). They are clean in git status (committed in
  HEAD), do not break compilation (comment text only), and `check-docs.py`,
  `check-names.py` and `check-wiring.py` are green. Left untouched because they

## Lessons for workers

- Before writing a clause test, grep the spec ID in `apps/api/src/main/java`: the
  package named in a task's prose may own a different requirement (here `chart`
  owns CLN-03; `clinical.notes` owns CLN-05). The scope path is still mandatory.
- For an integration test that must stay green on `main`, copy the neighbouring
  test's PostgreSQL bootstrap exactly (roles, unique DB name, Flyway location
  `filesystem:../../db/migrations`, synthetic subjects) and assert the read-back,
  not only the refusal status.
- In a cloud worker, `git ls-files -v opencode.json` showing `S` explains all
  `test_check_pack` failures; confirm once and do not regenerate the config.
- Do not run `worker-check.sh`/`check.sh` in a swarm worker: they run every
  integration test and `mvn verify` and time out; run the targeted `-Dtest=...`
  suite plus individual policy scripts and leave the full gate to the integrator.
