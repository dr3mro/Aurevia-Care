# S-G5-01 — Market policy pack, hosting region, jurisdiction and data handling map

## Summary

Updated `docs/launch/policy-pack.md` (the only file changed; scope `docs/launch`).
The page was already a decision-for-approval pack but lacked the explicit per-section
owner/evidence/status view the task requires and a concrete data handling map. Added:

1. **Policy pack sections — owner, evidence and status** — a matrix covering every
   topic the specification assigns to OPS-01 (hosting region, applicable law,
   jurisdiction-specific requirements and owners, retention by record class, legal
   hold authority, patient release, incident notification, supplier obligations,
   prescribing constraints, conditional U.S./HIPAA risk analysis) and PRD-05
   (one market per deployment, pilot scope, data handling map). Each row carries an
   accountable owner role drawn from specification section 10, an evidence location
   (signed artifact, evidence-checklist item, or the repository path where the
   repository can hold it), and a status from the required set (`approved`, `open`,
   `blocked`). A legend defines the terms. No row is `approved` and no market,
   region, contract, credential, date or real approval value was invented.
2. **Data handling map — template for owner completion** — an 11-row data-class
   map using synthetic fixture names from `docs/security/data-inventory.md`. Every
   location, processor and retention value is an "owner to enter" open item; real
   regions, processor names, contract references and retention periods are
   deliberately absent. Owner roles and status are recorded per row, and the
   cross-border transfer, out-of-region access and retention clock fields are named
   as open items for the owner.
3. Corrected a stale status sentence: the PRD-05 clause notes now exist in
   `docs/spec/clauses` (linked), while the OPS-01 clause notes remain open tasks.

The document states throughout that it is a decision pack for people; it records no
approval and makes no legal determination.

## Lessons for workers

- `python3 -I scripts/check-docs.py` enforces heading-level jumps, GFM table cell
  parity, relative-link resolution and specification requirement IDs. Count the
  unescaped pipes in every new table row, and only use IDs defined in the spec.
- A check-pack "stale opencode.json" result in a cloud worker is usually the
  CI-profile `skip-worktree` artifact: confirm with `git ls-files -v`,
  `cmp` against `git show HEAD:opencode.json` and `.github/opencode.ci.json` before
  regenerating anything, and never edit that protected file.
- When a pack must "record no approval", an explicit status legend plus per-row
  placeholder cells ("owner to enter", "to be named") keeps the document useful
  without inventing a market, region, contract or retention value.
- Check conflict markers with `git show HEAD:<file>` before treating them as
  something a merge just introduced; committed markers outside `scope` are not this
  worker's to fix.
