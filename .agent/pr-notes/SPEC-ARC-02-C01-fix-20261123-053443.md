## Test evidence

Evidence source: **executed tool commands** (Vitest, TypeScript, ESLint, Vite, bundle-size gate, v8 coverage) plus read-only reviewer verdicts. No simulated-user or human-participant evidence was available or claimed. Synthetic fixtures only.

Root cause (verified by reading `FacilitiesPage.tsx`, `PageSink.tsx`, `useApi.ts`, `ApiPage.tsx`): `FacilitiesList` renders the `<table>` (with its header cells) in the same commit in which `useApi` flips to `ready`. The data rows come from `accumulated` state, which is appended one commit later by `PageSink`'s `useEffect`. The original test awaited only `findByRole('table')` and then read the row synchronously, so under CI load it could observe an empty `<tbody>` while the headers were present. Debugger tool evidence: `Test Files 1 failed | 205 passed`, `Tests 1 failed | 2541 passed`, one failing `it.each` breakpoint with `<tbody />`; the same file passed in isolation and the full check was green in three of four runs (pre-existing flake from commit `a075fa01`, not a branch regression).

Fix: the `it.each` rendering test now awaits `within(table).findByRole('rowheader', { name: 'MAIN' })` before reading the two cells; column-header assertions stay synchronous because those `<th>` elements commit with the table. A new regression case defers the transport with `new Promise((resolve) => setTimeout(() => resolve(facilityPage()), 0))` (plain functions; this file uses Vitest `vi`, so no `jest` import and no `vi.useFakeTimers`, which would hang the timer) and awaits the row plus both cells. This mirrors the established pattern at `apps/staff-web/src/features/admin/FacilitiesPage.test.tsx:132`.

Entry-point-to-test trace: `FacilitiesPage` → `FacilitiesContent` → `FacilitiesList` → `ApiPage`/`useApi` (commits table) → `PageSink` (appends rows) → `<table>`/`<tbody>`; the responsive test drives that path for each breakpoint and for the deferred response.

Red-first note: a deterministic local red could not be produced. I first wrote the new deferred-transport case with the original synchronous row read and ran it 5 times: `1 passed | 16 skipped` on every run. I then ran the full unfixed suite three times: `Test Files 206 passed (206)`, `Tests 2543 passed (2543)` each time. This confirms the debugger's finding that the failure is CI-load-dependent rather than reproducible in a small local run. The fix removes the timing dependency by construction: the row and its cells render in the same commit, so waiting for the row cannot observe the empty tbody.

## Findings

- The failure is a genuine flake in pre-existing code (introduced by commit `a075fa01`, before this branch), confirmed by the debugger on a clean `origin/main` worktree. It was not caused by the original SPEC-ARC-02-C01 commit.
- I did **not** adopt the plan reviewer's Optional suggestion to assert an empty tbody immediately after the table await (`queryByRole(...).toBeNull()`). That intermediate state is itself timing-dependent — React's `act`/`waitFor` wrapper can flush the append effect before the assertion — so adding it would risk reintroducing the same class of flake this fix removes. The regression test asserts the user-visible end state instead.
- I did **not** make the debugger's Optional component hardening (`useRef` guard around the `reloadToken` reset in `FacilitiesPage.tsx`). The debugger marked it conditional on the regression case still flaking; 6 targeted and 2 full-suite runs were green without it. Touching production code would also require new branch coverage for no proven defect.
- Pre-existing and untouched: unresolved conflict markers inside Javadoc in `apps/api/src/main/java/com/aurevia/exchange/hl7/Hl7ParseException.java`, `Hl7Parser.java` and `Hl7Segment.java` exist on clean `origin/main`; they compile and are outside this fix's scope.
- Local worker limitations were not re-diagnosed: the `opencode.json` skip-worktree profile artifact (OPS-CW-003-01), OWASP NVD access without a key, and Python tooling without PyYAML are documented in AGENTS.md/earlier notes and are unrelated to this test-only fix. I did not run the full `mvn verify` or any all-integration-suite command.

## Lessons for workers

- When a table renders headers in one commit and rows in a later effect, wait for a row (or another row-scoped role) before reading its cells; `findByRole('table')` only proves the headers committed.
- Prefer an end-state assertion in a regression test over asserting a transient intermediate DOM state; the latter can become its own flake under `act`/`waitFor` effect flushing.
- A CI-only flake may not reproduce locally even under the full suite. Record the attempted red commands and their results honestly instead of claiming a red that was not observed, and make the fix race-free by construction.
