# QA-SOURCE-01 — fix/verification pass (Confirm appointments from the signed-in patient app)

## Summary

Continuation of PR #724 / issue #725. The first worker's run stopped before a clean hand-off; the code change was already committed on this branch as `4837bf1e Wire versioned appointment confirmation in the patient app`. This pass re-verified the whole slice end to end and then fixed two defects a bounded senior-mobile review raised, both within the story's declared scope:

1. **Second-row Confirm was silently dropped.** The in-flight guard used one global slot while the screen disabled only the one pending row. Pressing Confirm on another eligible row produced no request and no feedback. All confirm controls are now disabled while any command is in flight.
2. **A lost confirmation reply could never be reconciled.** If the server committed but its HTTP reply was lost, the retry reused the old version; the server had advanced and returned `422 NOT_CONFIRMABLE`, which the client treated as a generic retryable failure, leaving the row never shown as confirmed. That code now triggers the same reload path as a stale version, so the screen reflects server truth.

`bash apps/patient-mobile/check.sh` is green (typecheck, lint, Jest 1146 tests, 100% coverage on every touched file), the policy checks that apply to a patient-mobile-only change are green, and the developer-reference build is green. The only red local check is `check-pack` on the known cloud-worker `opencode.json` skip-worktree CI-profile artifact (recorded in MEMORY.md / BUGS OPS-CW-003-01), not a change defect. This note is the durable hand-off.

Previously delivered behavior (re-verified here): the installed `AppointmentListPage` no longer passes `placeholderAction` to Confirm. The read row's server `version` is carried into the display model, a typed client issues the versioned `POST /api/v1/patient/appointments/{appointmentId}/confirm` with `{ patientId, expectedVersion }`, and the server-returned `confirmedAt` instant is rendered in the facility zone. A 409/412 reloads the list, a 401 calls `onSessionExpired`, other failures leave the row retryable, and a synchronous slot guard plus a disabled control prevent duplicate submission while a command is in flight. All data is synthetic.

## Clinical and architecture review

- Eligibility stays server-owned; the client never enables confirmation for a non-confirmable or already-confirmed row (`deriveConfirmation` unchanged).
- Optimistic concurrency is preserved: the exact read version is sent as `expectedVersion`; a 412/409 is a reload, never a success.
- Lost-reply reconciliation: `PatientAppointmentService.confirm` commits (`store.confirm`) before returning, and checks `!current.confirmable()` (now confirmed) before the version check, so a retry after a lost reply would otherwise loop on `422 NOT_CONFIRMABLE` (`PatientAppointmentService.java:84-93`, `PatientAppointment.java:36`). The client now treats that stable code as a reload trigger, using the server's `code` field already extracted by `transport.ts:181-210`; response text is never surfaced.
- The recorded instant is the server's `confirmedAt`, formatted with the existing facility-zone formatter; the device clock is not used.
- Simulated patient walkthrough: rendered the installed page, pressed Confirm on a synthetic `booked`/`confirmationEnabled` row, observed the versioned request and server timestamp; injected stale, server-failure and 401 responses via rendered tests.
- No real clinical sign-off, pilot participant or production deployment was involved.

## Lessons for workers

- A "fix" pass on a task whose code is already green should verify, not rewrite: re-run the module `check.sh` (typecheck + lint + 100% Jest), confirm the acceptance tests actually assert the required outcomes, and write the fix-named notes file so the clean hand-off exists.
- Never run `scripts/check.sh` from a worker: it fans out to `apps/api/check.sh` (full `mvn verify`). Run its policy scripts individually plus the touched module's `check.sh`.
- In a cloud worker, a red `check-pack` is almost always the CI `opencode.json` under `skip-worktree`. Verify with `git ls-files -v`, `sha256sum` against `.github/opencode.ci.json`, and `git show HEAD:opencode.json`; never regenerate or edit that protected file.
- When the UI disables a control first, a duplicate-submission guard cannot be reached through the rendered view; test it by invoking the presentational callback twice inside one `act` with the screen mocked at the boundary. That keeps the safety guard and satisfies 100% branch coverage.
- A server "stale version" may be a 412 distinct from an already-confirmed 422; map the transport `conflict` kind to reload and keep other `validation` kinds retryable. When a server commits before its reply is lost, the retry hits `422 NOT_CONFIRMABLE` before the version check — reload on that stable `code` to reconcile rather than retrying into a loop.
- A global in-flight guard must be reflected in the UI globally: if one command blocks all claims, disable every confirm control while it is pending, not just the row being acted on. Test with two eligible rows, not two presses on one.
- Specialist reviews on an already-green slice can still surface real defects: give each finding impact/evidence/fix scrutiny, write RED tests for the ones you accept, and record deferred ones explicitly in the notes instead of silently dropping them.
