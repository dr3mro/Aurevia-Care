## Test design (branch-to-test map)

Fixture: class-unique real PostgreSQL database `orevia_override_reason_it`,
created from `filesystem:../../db/migrations`, dropped in `@AfterAll`. Two tenants
`ORG_A=11111111-...` and `ORG_B=22222222-...`, each with a `clinician-<suffix>` member
and one synthetic patient `MRN-1`. Catalog `AMOX500` (substance `AMOX-SUB`, group
`BETA_LACTAM`, approved v1) and `CIPRO` (substance `CIPRO-SUB`, approved v1). `ORG_A`
has a verified `verified_list` assessment naming `AMOX-SUB`; selecting `AMOX500` is a
verified `CONFLICT` and requires a documented override.

| Production branch / rule | Test method | Assertion |
|---|---|---|
| `PrescriptionService.selectMedication`: `overrideReason != null` → `insertOverride(reason, snapshot)`; author from V43 `app.actor` trigger | `documentedOverrideKeepsReasonAuthorAndMatchedSnapshot` | POST select (If-Match 1, reason, spoofed `authorSubject`) → 200; GET `/override/reason`, `/override/authorSubject == clinician-1111`, `/override/matchedSnapshot` contains `catalog=AMOX500:1;allergy=verified_list;outcome=conflict;findings=exact_match:AMOX-SUB:BETA_LACTAM`; JDBC row `override_reason`, `author_subject`, `matched_snapshot`, `draft_version=1`. |
| `CONFLICT && overrideReason == null` → 409 `ALLERGY_OVERRIDE_REQUIRED` | `verifiedConflictWithoutReasonIsRefused` | 409 + code; JDBC count of override rows = 0. |
| `PrescriptionInputs.optionalText`: blank → null → 409; length > 1000 → 422 `INVALID_OVERRIDEREASON` | `blankAndOverlongReasonsAreRefused` | blank reason → 409 + `ALLERGY_OVERRIDE_REQUIRED`; reason `"x".repeat(1001)` → 422 + `INVALID_OVERRIDEREASON`; no rows. |
| `PrescriptionService.requireVersion` stale version → 412 `STALE_VERSION` before any override insert | `staleVersionCannotAttachAnOverride` | If-Match 9 against version 1 → 412 + code; no rows. |
| V43 RLS/FORCE RLS on `prescription_override` | `peerTenantCannotReadTheOverride` | ORG_B clinician GET ORG_A draft → 404; JDBC query under ORG_B → 0 rows. |
| V43 append-only trigger on UPDATE/DELETE | `overrideRowIsAppendOnly` | UPDATE and DELETE each throw with message containing `append-only`; row unchanged via GET. |

No production branch is introduced by this change, so JaCoCo coverage of production
code is unchanged; the proof is the HTTP/JDBC assertions above plus the existing
suite. No `@Disabled`, skip, exclusion or threshold change is used.

## Lessons for workers

- Neighbouring HTTP fixtures' seed helpers are `private static` and their database
  names are shared; re-implement the setup locally with a class-unique database name
  and drop it in `@AfterAll` so parallel workers never collide.
- When the clause is already implemented, write the complete test against the real
  behavior and mark the doc "Proven by tests" only after every assertion passes.
  Never relax or skip a failing assertion to get green; story step 3's `@Disabled`
  applies only when the behavior genuinely does not exist.
- To prove an author is database-derived, send an extra unknown JSON field and assert
  the authenticated subject — but say in the test comment and clause doc that default
  Jackson silently ignores unknown fields, or a reviewer may read it as overriding a
  real component.
- In a cloud worker, `worker-check.sh` stops at `check-pack.py` with the CI profile
  installed under `skip-worktree`. Confirm once (`git ls-files -v`, compare worktree
  with `.github/opencode.ci.json`, `git show HEAD:opencode.json`), then run the later
  stages individually and never regenerate or commit `opencode.json`.
- `python-coverage.sh` exits 1 with `coverage is not installed` in this image even when
  no `scripts/*.py` changed; record it as an environment limit, not a change defect.
- Committed conflict markers inside `/** ... */` Javadoc blocks at HEAD do not break
  javac; record them as pre-existing and out of scope rather than editing production
  files outside the task scope.
