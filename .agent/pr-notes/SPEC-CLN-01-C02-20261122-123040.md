# SPEC-CLN-01-C02 — Prevent overlap for protected resources transactionally (API test)

## Summary

Adds an API-level proof of CLN-01 clause 2. A new integration test drives `POST /api/v1/appointments`
on real PostgreSQL with synthetic fixtures and shows that two commands claiming the same protected
clinician or room slot cannot both commit: exactly one wins, the loser gets `409 SLOT_CONFLICT` and
no row is written. A companion clause-evidence document records the status, the exercised production
classes and the (empty) gap. No production code, existing test, contract or migration was changed.

## Affected requirements

- CLN-01, clause 2: "Prevent overlap for protected resources transactionally."

## Risk class

Routine (test and clause-evidence documentation only; no production behavior changed). The clause
itself is safety-relevant scheduling behavior, so the proof runs through the real HTTP entry point
against PostgreSQL, but this change cannot alter clinical behavior.

## Review owner

Senior Java and Spring Boot (backend) for the test; Senior Java Build and Test Tooling for the
SpotBugs and unit gates; QA for independent evidence review.

None. One throwaway database `orevia_overlap_clause_it` is created by `@BeforeAll`, migrated

## Authorization boundaries and audit events

`scripts/check.sh` was intentionally NOT run: it invokes `apps/api/check.sh` = `mvn -q -B verify`,

SpotBugs, targeted integration test) were run above instead.

The three tests and what they prove:

- `twoConcurrentBookingsOfOneProtectedSlotLeaveExactlyOneCommittedAppointment` — positive: two
  simultaneous HTTP attempts on one slot produce exactly one 201 and one 409, and exactly one
  committed row remains at that slot. Fault detection: without the advisory lock/exclusion
  constraint both attempts would return 201 and the row count would be two.
- `anOverlappingBookingOfTheSameProtectedClinicianIsRefusedAndWritesNothing` — negative: a seeded
  committed `DR-A`/`ROOM-1` slot at 14:00Z makes a 14:15Z single booking fail with 409
  `SLOT_CONFLICT` and leaves the count unchanged. A single booking has no application pre-check, so
  this exercises the database constraint inside the transaction.
- `anOverlappingBookingOfTheSameProtectedRoomIsRefusedEvenForADifferentClinician` — negative: the
  committed slot uses `DR-B`/`ROOM-1`, the attempt uses `DR-A`/`ROOM-1`; only the room overlaps, and
  the room exclusion constraint still refuses it with 409 and no write.

## Lessons for workers

- In a cloud/swarm worker, `opencode.json` in the worktree is the CI runtime profile under
  `skip-worktree`. Treat `scripts/check-pack.py` / `test_check_pack` "stale" failures as an
  environment artifact and confirm with `git ls-files -v opencode.json` plus
  `git show HEAD:opencode.json`; never regenerate or edit the protected file as a worker.
- `scripts/check.sh` runs the full `mvn verify` through `apps/api/check.sh`. For a scoped worker run,
  use a targeted `mvn -Dtest=...` (add `-Dgroups=integration` for tagged PostgreSQL tests) and run
  the policy stages individually; reserve the full gate for the integrator.
- For a DB-backed clause proof, give the test its own database name and distinct fixture dates so
  parallel integration classes cannot make one test's committed slot clash with another's.
