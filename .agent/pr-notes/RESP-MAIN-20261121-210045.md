# RESP-MAIN — Staff web: load the responsive stylesheet at start-up

## Summary

The staff-web Vite entry point now imports `./theme/responsive.css` so the
responsive base stylesheet is emitted and linked in the production bundle. The
browser-support decision is no longer computed once at module load: a small
`renderEntry` function computes it from `isSupportedBrowser(navigator.userAgent,
window.innerWidth)` and is registered for both `resize` and `orientationchange`.
Because RESP-SUPPORT lowered the floor to 320 px, a tablet rotating through
intermediate widths stays supported and the mounted application is not swapped
for the plain unsupported notice on a transient width. Unsupported clients still
receive only `ThemeProvider > I18nProvider > UnsupportedBrowserPage`, with no
`App` and therefore no clinical data (WEB-07).

Scope honoured: only `apps/staff-web/src/main.tsx` and
`apps/staff-web/tests/main.test.tsx` were changed. No dependency was added and
no production file outside the two scoped paths was touched.

## Affected requirements

- WEB-07 — supported clients and the plain unsupported-browser message with no data.
- UX-01 — WCAG 2.2 AA responsive staff web (decision 0004 sets the 320 px floor).

Decision: `docs/decisions/0004-responsive-staff-web.md`. WEB-07 in
`PROJECT_V1_SPEC.md` still states the old 1280/768 px floors and needs a
person to amend it; the swarm may not edit the specification.

3. **Bounded `aurevia-senior-react` review (read-only, session
   `ses_e0010bb2effej5P3ZCCyB0OFB8`):** no high or medium findings. It confirmed
   the transient-width claim (both tablet orientations are ≥ 320, so the support
   decision is identical on every rotation event and React reconciles the stable
   `StrictMode → App` tree rather than remounting), full branch coverage and no
   TypeScript or no-data regression. Two LOW findings:
   - LOW/implemented: the no-data tree was asserted only at initial mount. Added
     `keeps the plain notice and no app when an unsupported client resizes or
     rotates`, which fires both captured handlers with `UNSUPPORTED_UA` and
     re-asserts no `App`. Target tests went 7 → 8 and the full suite 1271 → 1272.
   - LOW/not adopted: cache the last support result and call `root.render` only
     when it changes, to avoid repeated reconciliation during a rotation drag.
     Not adopted: the change is intentionally minimal, re-evaluating on every
     event is the specified behaviour, the same element type/position means React
     preserves mounted state, and a cache would add an extra branch (with its own
     coverage test) for no acceptance benefit. A supported tablet never crosses
     the floor, so the churn is bounded to rapid user-driven desktop resizes.
   Reviewer findings are *inferred* (read-only role, no execute tool); all
   execution evidence above is observed tool output from the primary agent. No
   human, clinical or patient evidence was used.

## Lessons for workers

- In a worker, a red `gen:api:check` (step 1 of `apps/staff-web/check.sh`) can be
  committed contract drift from an API story, not your change. Verify with
  `git show HEAD:contracts/openapi.yaml` and a generation to a temp file, then
  run the remaining check steps individually instead of editing the
  out-of-scope generated client.
- To test entry-point event listeners under `vi.resetModules()`, spy on
  `window.addEventListener` and capture the handlers per test, then invoke the
  captured handler directly. Real `window.dispatchEvent` also reaches stale
  handlers registered by earlier module instances and corrupts call counts.
- The new 320 px floor is what makes resize/orientation re-evaluation safe:
  a tablet's rotation never dips below it, so no debounce timer is needed and
  no transient width can swap the app for the unsupported notice.
