# LABFLOW-03 — API: result entry and verification (numeric, qualified, text, coded) with ranges, flags and verifier

## Summary

Added a self-contained `labflow/results` slice that captures the four LAB-02 observation kinds
(numeric, qualified numeric, text, coded) with units, method and instrument source, derives
abnormal (`low`/`high`) and `critical` flags from the approved site bounds carried on the command,
and verifies a report only from an authenticated subject different from the enterer. Verification
repeats the patient/accession label match, checks specimen, patient and observations, issues a
`final` revision through the existing `lab.result` kernel, and calls the durable XCH-05
`CriticalResultService.register` once per critical finding. `corrected` and `entered_in_error`
append linked revisions that preserve history. A thin injected controller exposes five routes under
`/api/v1/lab/results`. No new table, migration, dependency or production file outside the declared
scope was added.

## Affected requirements

LAB-02 (spec §5): capture numeric, qualified, text and coded observations with units, range,
method, abnormal flags, instrument/source and verifier; preliminary/final/corrected/entered-in-error
reports; verification checks specimen, patient and observations; versioned approved ranges and
critical policies; trigger XCH-04/05 on issued revisions. Clause mapping: SPEC-LAB-02-C01 (four
kinds), C02 (units, method, instrument, flags), C03 (verification checks and verifier), C04/C05
(revisions) — these clause-test tasks remain owned by their own workers and were not edited.
Also touches XCH-05 (critical registration), ARC-01/ARC-02 (tenant-owned identifiers and isolation),
ARC-03 (version preconditions), OPS-02 (audit) and reuses LAB-01 accession/patient matching.

## Risk class

Safety-critical (docs/WORKFLOW.md): patient identity, result interpretation flags, duty segregation
and a critical-result workflow. Negative and failure tests cover wrong patient, wrong tenant, stale
version, wrong state, self-verification, inactive membership, wrong role, malformed inputs and
non-matching critical bounds. Evidence is tool-generated plus one bounded simulated reviewer;
no real clinician, unit participant or patient evidence is claimed.

## Data changes

None. No reserved migration version consumed, no backfill, lock, volume impact, rollback or
forward-fix. The slice writes only to existing forced-RLS tables through existing adapters:
`public.lab_accession` (read-only here), `public.patient_record` (read via `PatientRepository` in the
existing accession flow), `public.critical_result` / `critical_result_event` via
`CriticalResultService.register`, and `public.audit_event` via `AuditAppender`. Report revisions
live in the pre-existing `lab.result` kernel (see `## Findings`).

## Authorization boundaries and audit events

- Active tenant comes only from `TenantContext` (`X-Active-Organization`); organization, actor,
  verifier and roles are never accepted from a request body. Every command runs in thetenant-guarded
  `TransactionTemplate` under forced RLS; a peer tenant's specimen is concealed as 404.
- Roles are re-derived on every command from `LabAccessionRepository`: `lab_collector` may enter,
  `lab_verifier` may verify/correct/withdraw, both may read. Inactive membership or a wrong role
  returns 403 and appends a `DENIED` audit row.
- The verifier is `TenantContext.subject()`. It is compared with the **first** immutable revision's
  `actor` (the original enterer), not the current revision's actor, so a verifier may later correct
  their own issued report but the enterer can never verify or correct it.
- Purpose `LAB_RESULT_ENTRY`, resourceType `LAB_REPORT`, scope `LAB`. Actions `LAB_RESULT_ENTER`,
  `LAB_RESULT_VERIFY`, `LAB_RESULT_CORRECT`, `LAB_RESULT_ERROR`, `LAB_RESULT_READ`; outcomes
  `SUCCESS`, `DENIED`, `NOT_FOUND`, `MISMATCH`, `CONFLICT`. A refused label match appends `MISMATCH`
  and throws after commit (failure-reference pattern) so the audit survives. No patient identifier or
  observation value is placed in an audit row.
- Critical findings call `CriticalResultService.register`, which enforces its own XCH-05 membership,
  `lab_verifier` action policy and patient existence check before a durable insert.

## Migration and rollout considerations

No data change and no migration. The new controller is component-scanned and adds five routes under
`/api/v1/lab/results`; it does not alter an existing route. It was renamed `LabResultEntryController`
because `exchange.result.ResultController` already owns the `resultController` bean name in the same
application context. OpenAPI entry/client regeneration is out of this worker's declared scope
(`contracts/`); a task request is recorded below. Full `mvn verify`, OWASP, the complete integration
tier and SHA-linked CI belong to the integrator and Delivery.

## Clinical and architecture review

No signed data, cross-organization sharing, prescribing or patient release is added. Patient identity
is matched to the stored accession before any write; verification compares identities before issuing
a final revision; the critical alert is registered as a separate XCH-05 fact and never treated as a
clinician acknowledgment. A `critical` flag is derived only from an approved bound supplied on the
command, never from a qualifier or qualitative value; qualified and qualitative results stay visible
but are not numerically evaluated. The real-PG test asserts the workflow row count (0 → 1), which is
durable independently of the in-memory report kernel. Real clinical/unit acceptance remains a G5 gate.

## Findings

- The existing `lab.result.LabResultService` kernel stores revisions and trigger events in
  `HashMap`s and is exposed here by `ResultConfiguration` as an injected bean. This reuses the
  authoritative domain rules (state machine, revision append, comparator eligibility) and keeps the
  story inside its two-path scope, but report revisions themselves are process-local: a restart
  loses the report ledger, while the critical-result row and the accession/audit rows are durable.
  The worker did not add a Jdbc store or migration because `db/migrations` is outside the declared
  scope. AUD-20261121-07 already owns "wire or delete the LAB-02 report-verification kernel" with a
  `db/migrations` scope; that task (or its successor) must supply durable report storage and a
  restart-survival HTTP test. No new duplicate store was introduced.
- The site range and critical bounds are carried on the entry command because no approved lab-policy
  configuration table exists in `db/migrations` and `configs/` is out of scope. They are bounded and
  validated, and `LabPolicyCatalog` still supplies the versioned flag/comparison semantics. A future
  configuration story should load them from approved effective-dated ADM-01 configuration rather
  than trusting a client; the `LabObservation` Javadoc's "never hard-coded" rule is respected here
  because the thresholds are not constants in code.
- Bean name collision: a controller named `ResultController` conflicts with
  `exchange.result.ResultController` in component scanning. Named this one `LabResultEntryController`
  after the business operation; no existing route or bean was changed.
- `ResultEntryService` was made non-final so the standalone MockMvc test can mock it with the
  repository's Mockito subclass maker; the constructor performs no validation, so SpotBugs
  CT_CONSTRUCTOR_THROW does not apply.
- SpotBugs found and the worker fixed two findings at their cause: `DCN_NULLPOINTER_EXCEPTION` from
  catching `NullPointerException` in `enumValue` (now `Objects.requireNonNullElse(value, "")`), and
  `ES_COMPARING_PARAMETER_STRING_WITH_EQ` on `action == ERROR` (now `ERROR.equals(action)`).
- The `opencode.json` pack-check false positive recurred: `git ls-files -v opencode.json` → `S`; the
  worktree file is the CI profile copied under `skip-worktree`. The worker ran the pack check and all
  803 tooling tests with `git show HEAD:opencode.json` bytes temporarily restored, then restored the
  CI bytes byte-for-byte. No protected file is modified.
- Bounded senior-backend clinical-safety review (simulated reviewer, static reads only; the reviewer
  did not execute tests). Dispositions:
  - **F1 BLOCKER — singleton in-memory kernel is not a durable store (accepted, out of scope, release
    gate).** Accurate: the report ledger is process-local and non-transactional, so a restart or a
    second replica loses or diverges it. `db/migrations` is outside this worker's two-path scope and
    AUD-20261121-07 already owns the sanctioned fix (tenant-owned JDBC store + RLS, or delete the
    kernel). This worker did **not** create a duplicate store. The overstated "reads and writes run
    under forced RLS" Javadoc was **fixed** to describe the real mechanism (RLS for accession/audit,
    organization-keyed kernel for reports). This worker does not claim release readiness until that
    task lands; the durable XCH-05 row and HTTP behaviour are nonetheless proven.
  - **F2 HIGH — client-supplied bounds can suppress or fabricate criticality (accepted, out of scope,
    release gate).** Accurate: no approved effective-dated catalog exists in `db/migrations` and the
    bounded site values travel on the command. A caller could widen bounds to hide a critical value.
    Server-side resolution from an approved ADM-01 catalog is requested below; the classification
    rule itself (`LabPolicyCatalog.ReferenceRange.flag`, `CriticalPolicy.isCritical`) is reused
    unchanged.
  - **F3 HIGH — correction duplicated the XCH-05 alert (fixed in this pass).** Registration now runs
    only on first verification (`if (VERIFY.equals(action))`); a correction no longer inserts a
    second alert. Added a unit assertion and a real-PG assertion that `criticalCount` stays 1 across
    `POST .../correct`. Re-running a verification is rejected as a stale version, so it cannot create
    a duplicate either. A future XCH-05 story should add source-level idempotency and addendum
    semantics for a correction that changes a non-critical result into a critical one.
  - **F4 MEDIUM — failed registration can leave an inconsistent report (accepted, consequence of F1).**
    The kernel append is in-memory and non-transactional while the alert and audit are JDBC. Fully
    fixing this needs the durable store from F1, which is out of scope; recorded as a release gate.
  - **F5 MEDIUM — `readBackRequired` hard-coded `false` (accepted, out of scope).** The XCH-05 policy
    setting is not exposed by any scoped type; the literal is deliberate and documented here so a
    policy story can derive it from approved configuration and cover the true case.
  - **F6 MEDIUM — segregation enforced only in the service; withdrawal exempt (accepted with
    rationale).** The kernel is shared, but production reaches it only through this injected service.
    Entered-in-error is an attributed, append-only withdrawal rather than a verification, so the
    enterer/withdrawer may be the same subject; the prior revision and its verifier are preserved and
    the action is audited. Enforcing the invariant in the kernel itself is deferred to F1's owner.
  - **F7 LOW — misleading RLS documentation (fixed).** Javadoc corrected as described in F1.
  - Reviewer observation (not blocking): text, coded and qualified results can never receive an
    abnormal/critical flag. This matches the existing `LabTypes` design and XCH-07 comparability
    rules and was left unchanged.
  - Reviewer confirmed sound: wrong-patient mismatch audit, membership/role denial audit,
    self-verification conflict, thin injected controller and defensive copies.
- Evidence provenance: tool commands for all test/coverage/lint results; simulated reviewer for the
  review; no simulated-user or human participant evidence.

## Lessons for workers

- Check controller **bean names**, not only file paths: two `ResultController` classes in different
  packages fail Spring component scanning with `ConflictingBeanDefinitionException`. Name controllers
  after the business operation when a generic name is already taken.
- `scripts/tests/test_java_conventions.py` requires **two** `List.copyOf(` calls in every `public record`
  whose header contains `List<` (one in the compact constructor, one in the overridden accessor).
  A shared `freeze(...)` helper does not satisfy that gate.
- With the Mockito **subclass** maker, a `final` service cannot be mocked in standalone MockMvc tests;
  keep the service non-final when its constructor does not validate, or build a real service with
  mocked boundaries.
- `LabInputs.id`/`patientId` require canonical UUIDs, and `LabActionPolicy` has no result actions —
  reuse `LabRules.COLLECTOR`/`VERIFIER` and `Set.copyOf(repository.activeRoles(...))` for role checks.
- Entry uses `expectedVersion` of the **accession after collection** (version 2), not the version read
  before collection; the integration fixture must collect first and then submit version 2.
- Segregation must compare the verifier with the **first** revision's actor. A verified report's own
  `actor` is the verifier, so comparing with the current revision would wrongly block corrections.
- When a String switch/ternary is on a method parameter, SpotBugs reports
  `ES_COMPARING_PARAMETER_STRING_WITH_EQ`; use `CONSTANT.equals(parameter)` from the start.
- Do not catch `NullPointerException` for validation — normalise with `Objects.requireNonNullElse`
  and catch `IllegalArgumentException`, which also keeps JaCoCo branches coverable.
