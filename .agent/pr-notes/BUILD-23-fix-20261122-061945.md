## Findings

1. **Decisive — green PR is unmergeable because `needs-fix` is never cleared (real, reproduced from source and GitHub state).** `scripts/swarm.py:publish()` (2011–2107) posts `Worker N pushed a fix … The integrator will retest.` and calls `gh pr ready` when checks pass, but never removes `needs-fix`. `plan_integration()` (2569) and `pr_flow()` (3009) both exclude `needs-fix` PRs; `delivery_gate()` (2529) and `release()` (1983) never clear it. Only `send_to_debugger()` (2925) and the final `needs-human` path (2424) remove it. Therefore Delivery can be green on four consecutive heads while the integrator's `Integrate the ready batch` stays skipped and every 10 minutes pr_flow dispatches another fix wave. No worker code change can break this loop; the tracker, workflow and `scripts/` are maintainer-owned. Fix belongs to the swarm automation owner.
2. **The BUILD-23 code fix itself is complete and correct.** Byte equality, single non-stale baseline line, all targeted gates green, 100% JaCoCo, both frontend checks green, and Delivery green on four fix SHAs. Earlier "re-run in-scope tests and call the rest pre-existing" passes were right about the code but did not look at why a green PR was not merging.
3. **Declared-scope conflict remains (real, tracker issue, not a code defect).** The inherited fix touched `contracts/openapi/missing-routes.txt`, outside BUILD-23's declared scope (`.../web`, `.../web` tests, packaged contract copy). A strict `worker_gate.py` rerun with `STORY_BODY` scope would flag it as `scope`. The integrator's own gate (`check.sh` + `docs.sh`) does not invoke `worker_gate.py`, so this did not cause the CI failures. Owner decision: extend the declared scope to that baseline, or document the route in `contracts/openapi.yaml`, regenerate `apps/staff-web/src/api/generated/openapi.d.ts` and remove the baseline line (FIX-OPENAPI series).
4. **CI-profile `opencode.json` artifact (environment, not a defect).** In cloud workers the worktree file is the CI profile under `skip-worktree`; policy results there are not HEAD truth. No file was regenerated or committed.
5. **Full `scripts/check.sh` / `mvn verify` deliberately not run** (worker time limit, >10 minutes); Delivery is green on the current fix heads. Frontend checks, targeted Java suite, standalone parity, JaCoCo and the cheap policy checks were run green instead.

## Lessons for workers

- When a green fix PR is repeatedly returned, stop after one diagnosis and query the REST API: `pulls/{n}` labels, `commits/{head}/check-runs`, and the integrator run's jobs. A `needs-fix`/`needs-human`/`needs-debug` label excludes the PR from `plan_integration` regardless of green checks; "the integrator will retest" is then false.
- Re-applying an already-committed fix and recording another verification-only note does not move a green PR; it only adds a commit to the loop. Diagnose the hand-off mechanism before writing a third identical note.
- Treat a scope violation in an inherited fix as a real hand-off finding too: a strict worker-gate rerun can reject a PR whose CI is green.
- Reset `apps/api/target/jacoco.exec` before the coverage batch and include `BrowserSessionHttpTest`; accumulated exec data can overstate a targeted run.
- The frontend definition of done is mandatory even on a data-only backend pass: run both `check.sh` scripts, paste the `tsc --noEmit` final lines, treat any `error TS…` as a hard stop.
