## Summary

Added a read-only pharmacy prescription inbox (RX-02, XCH-01): a chart-free projection of prescriptions **explicitly routed** to the reading pharmacy, newest first, with an exact status filter and tenant-bound cursor paging. Access requires active membership, the `pharmacy_staff` role and an approved per-subject pharmacy assignment; every request re-derives those facts from authoritative database folds inside the tenant-guarded transaction. HTTP entry points: `GET /api/v1/pharmacy/inbox` (list) and `GET /api/v1/pharmacy/inbox/{id}` (detail). Cross-pharmacy and unrouted items are invisible; cross-tenant rows are confined by forced RLS. All fixtures are synthetic.

## Affected requirements

RX-02 (routed prescription events/status), XCH-01 (exchange-specific work item, no general chart access), ARC-02 (tenant isolation), ARC-03 (cursor paging, concealment), OPS-02 (durable audit).

## Risk class

Cross-boundary / safety-critical: prescription routing, tenant and per-pharmacy isolation, no chart access.

## Review owner

Simulated specialist review: `orevia-senior-backend` (bounded implementation plan) and `orevia-senior-spring-security` (authorization design). Both were advisory, ran no commands and edited no files. No human clinician or unit participant; real clinical acceptance remains a G5 gate.

## Data changes

None. No migration, backfill, new table, new dependency or lock/volume impact. Reuses existing tenant-owned, forced-RLS `rx02_prescription` (V44/V59), `effective_config` (V5), membership/role folds (V1/V4) and the append-only `audit_event` (V3). Rollback is a plain application deployment; no schema forward-fix needed.

## Authorization boundaries and audit events

Tenant derived from `X-Active-Organization` via `TenantContext`; active membership, `pharmacy_staff` role and the subject's approved `pharmacy.inbox.assignment.<subject>` config value are re-read on **every** request (including paged requests). Missing/invalid assignment fails closed with 403. The SQL always applies `destination_pharmacy = :assignedPharmacy` (NULL destinations cannot match) and relies on forced RLS for tenant scope. OPS-02 audit: `PHARMACY_INBOX_READ` / `PHARMACY_INBOX` / `PRESCRIPTION`, resourceId = assigned pharmacy for lists or prescription id for details; `DENIED` events are committed through a failure sink, `SUCCESS` on reads. No patient data, medication, pharmacy value or cursor token is written to audit or logs.

## Migration and rollout considerations

No schema change. **OpenAPI entry and regenerated client were not added**: `contracts/openapi.yaml` is outside the declared scope (the existing `/api/v1/prescriptions` routes are not documented there either). Integrator must decide whether to register these two routes in a separate scoped task. The existing database has no `(destination_pharmacy, created_at, id)` index; a future migration may add one for inbox read performance (no correctness impact at pilot volume).

## Findings

- **Decision (RX-02/XCH-01):** a pharmacy staff subject is bound to exactly one pharmacy by an approved `effective_config` value at key `pharmacy.inbox.assignment.<subject>` (mirrors the existing `rx02.entitlement.<subject>` pattern). The pharmacy is never taken from request parameters; absent, unapproved or malformed assignments deny access. Only `rx02_prescription` columns are projected; `rx02_event.detail`, chart entries, allergies, diagnoses and demographics are never read.
- **Defect outside scope (security reviewer, simulated):** `GET /api/v1/prescriptions/{id}` (`RxService.get` / `RxActions.READ`) still permits `pharmacy_staff` and returns any prescription in the tenant with its full event trail, because `RxRepository.find` has no `destination_pharmacy` predicate. That legacy route can bypass this inbox's per-pharmacy scoping. Fixing it requires editing `prescription/rx`, outside PHARM-01's scope; no failing test was added for it. Integrator should open a scoped task (or remove `pharmacy_staff` from `RxActions.READ` once PHARM-02/03 define the pharmacy read contract).
- **Out-of-scope gate:** OpenAPI entry and regenerated client (`contracts/openapi.yaml`) cannot be added under this task's scope; flagged for the integrator.
- **Out-of-scope trust boundary:** `destination_pharmacy` is prescriber-supplied bounded text on `rx02_prescription`; the assignment value and stored destination must use the same approved pharmacy-key representation operationally, otherwise mis-keyed rows silently vanish (fail-closed but wrong). No change made here.
- **Performance follow-up:** no index exists on `(destination_pharmacy, created_at, id)`; a future migration should add one if the inbox grows. No migration was reserved or used in this task.
- **Environment:** the three Python pack-test failures, the stale `opencode.json` report and missing `coverage` package are worker-image artifacts (skip-worktree CI profile), not regressions; no protected file was edited.

## Lessons for workers

- Reuse `PageRequest`/`Cursor` for ARC-03 paging instead of a hand-rolled `createdAt:id` token: the existing type is tenant-bound and rejects foreign cursors generically.
- Mocked service tests alone leave the repository and controller at 0% JaCoCo; one real-PostgreSQL HTTP test class with two page shapes covers every SQL predicate branch and the entry point. Run the unit and HTTP test classes together in one `jacoco:report` invocation to read all touched files at 100%.
- In this image `opencode.json` is a skip-worktree CI profile, so pack-test failures are measurement artifacts. Confirm with `git ls-files -v opencode.json` and never regenerate it from a worker.
- Spring Boot 6 names HTTP 422 `HttpStatusCode`/`UNPROCESSABLE_CONTENT`; assert `.getStatusCode().value() == 422` to stay portable.
- When seeding synthetic clinical rows directly, insert `organization` before `user_identity`, membership status is `revoked` (not `deactivated`), and `patient_record.id` must be explicit if prescriptions reference a fixed patient UUID.
