## Summary

Replaced the process-local `@Repository` `InMemoryInstructionFactStore` with a
PostgreSQL adapter behind the unchanged `InstructionFactStore` interface.
`V63__instruction_facts.sql` adds nine tenant-owned tables (instruction revision,
publication, generic dispatch, first view, receipt acknowledgment, state-bearing
follow-up, idempotency digest, non-sensitive audit ledger and a staff-to-unit
assignment reference), each with `organization_id`, `created_at`, forced row-level
security, a `public.app_org()` policy and explicit grants. Append-only facts have
no UPDATE grant and reject-mutation triggers; the follow-up holds the sole UPDATE
grant for its resolution transition. `JdbcInstructionFactStore` implements all 24
interface methods through the tenant-guarded `TransactionTemplate` with
parameterized SQL, reusing the authoritative V4 membership/role folds, V10 chart
fold and V60 connection table. The in-memory adapter lost `@Repository` and moved
to `src/test` with the same package, so the existing unit tests compile unchanged
and Spring sees exactly one store bean.

## Data changes

`V63__instruction_facts.sql` is additive (`-- Change: expand`) and uses only the
reserved version V63. Nine empty tables; no backfill, no edit to any existing
migration. Lock/volume impact is negligible. Migration order is after V62 and
before V70 under both `sort -V` and Flyway numeric order, so `organization`,
`public.app_org()` and `public.reject_immutable_mutation()` exist first; Flyway
reported `Successfully applied 44 migrations ... now at version v90`. The tagged
test creates and drops its own `orevia_instruction_facts_it` database.

## Authorization boundaries and audit events

Every adapter method runs inside the shared tenant-guarded `TransactionTemplate`,
which binds `app.current_org` and `app.actor` transaction-locally before SQL.
Reads name the active organization explicitly and rely on forced RLS; writes carry
the method's `organizationId` so `WITH CHECK` fails closed on mismatch. No
authorization decision changed: `InstructionFactService` still re-checks
membership, roles, verified chart and connection on every request, now against
authoritative durable sources instead of process memory. No audit event type was
added or changed; `appendAudit` persists the same `AuditFact` the in-memory store
held.

**Staff-to-unit assignment decision (ARC-01/ARC-02):** no authoritative durable
staff-to-unit mapping exists in the current schema (`V4` holds membership and
role keys, `V60` holds patient-unit connections, neither maps a staff subject to
a unit). To preserve the in-memory semantics without inventing a second copy of
role or membership state, V63 adds `instruction_fact_unit_assignment` as a
SELECT/INSERT reference for an authorized setup path, following the
`messaging_resource` precedent in V62. Like the in-memory store, no production
path currently seeds it; that pre-existing gap is recorded under Findings.

## Migration and rollout considerations

`instruction_fact_follow_up` is the only state-bearing table: resolution is an
UPDATE of `state`, `resolved_by`, `resolved_at` and `reason` on one routed row, so
it holds the UPDATE grant. All other tables are immutable (`ON CONFLICT DO
NOTHING` writes, INSERT-only grants and reject-mutation triggers). No production
writer seeds `instruction_fact_unit_assignment`; an authorized setup path must do
so before owning-unit staff actions can pass object authorization. Forward/
rollback: a later contract removing a table must point at this `Change: expand`
per `docs/decisions/0002`.

## Findings

1. **`bash scripts/worker-check.sh` and the full tooling test suite are red on a
   known false positive, not a defect of this change** (tool): `check-pack`
   reports a stale `opencode.json`. Verified `git ls-files -v opencode.json` →
   `S` (skip-worktree), `git diff HEAD -- opencode.json` empty and
   `cmp opencode.json .github/opencode.ci.json` → identical: the committed profile
   is unchanged and the worktree holds the CI profile. This is OPS-CW-003-01,
   already documented in `MEMORY.md` and the READY-38 notes. The protected file
   was not edited; all later gates were run individually and are green.
2. **No production seeding path for staff-to-unit assignment** (tool + decision):
   `instruction_fact_unit_assignment` is INSERT/SELECT-only and no production
   writer exists, just as the in-memory store had no production `assignStaffUnit`
   caller. Owning-unit authorization via `isStaffAssignedToUnit` therefore fails
   closed until an authorized setup path seeds the reference. Recorded here for
   the owning product story; no behavior was silently stubbed.
3. **Non-UUID local ids** (tool): the JDBC adapter casts instruction and unit ids
   to `uuid`, so the synthetic "missing" sentinel used by the in-memory unit tests
   is not a valid store key. The integration test uses a UUID-shaped
   `MISSING_ID`; production commands already validate ids with
   `InstructionFactInputs.uuid`. No semantic change for valid inputs.
4. **Shared append-only database makes whole-list assertions order-dependent**
   (tool): the first run failed on a whole-list emptiness assertion because an
   earlier test's immutable instruction rows remained. Fixed with id-targeted
   `anyMatch`/`noneMatch` assertions; no threshold, exclusion or skip was added.
5. **The superseded-revision assertion was initially wrong** (tool): after
   storing revision 2, revision 2 is the *latest* candidate, so acknowledging
   revision 1 could not clear it. The test now proves the latest-revision filter
   explicitly (revision 2 is the candidate, then acknowledging it clears it).
6. **`scripts/check.sh` was intentionally not run** (tool): it invokes
   `apps/api/check.sh` = `mvn verify` with every integration test and OWASP, which
   the worker instructions forbid, and would fail at the same `check-pack`
   artifact. Every other stage was run individually and is green above.
7. **Non-blocking reviewer observations** (simulated reviewer, no action taken):
   the dispatch and audit ledgers have no index on `instruction_id`, so
   `dispatches()`/`allFacts()` filters sequence-scan as they grow — this mirrors
   the V60/V62 precedent and is a future capacity concern; and timestamptz
   stores microsecond precision, so a production instant with sub-microsecond
   nanoseconds would round-trip truncated (harmless for the current domain).
   Both reviewers explicitly approved the change with no actionable finding.

## Lessons for workers

- Prove per-class 100% coverage with the targeted tagged test plus
  `mvn -Pno-security jacoco:report` and read `jacoco.xml`; do not run the
  ten-minute full verify as a worker.
- `worker-check.sh` fails at `check-pack` in cloud workers because the CI
  `opencode.json` sits under `skip-worktree`. Confirm with `git ls-files -v`,
  an empty `git diff HEAD -- opencode.json` and `cmp` against the CI profile,
  then run the later stages individually. Do not edit the protected file.
- When replacing a seeded in-memory fake, move it to `src/test` with the **same**
  package so existing tests compile unchanged, and remove `@Repository` in the
  same commit as the new bean to avoid `NoUniqueBeanDefinitionException`.
- Integration tests sharing one database must use id-targeted, order-independent
  assertions (`anyMatch`, `contains`, `indexOf`) because append-only seed rows
  cannot be deleted.
- Reuse authoritative folds for membership, roles, verified charts and
  connections; only project a fact into the new migration when no authoritative
  durable source exists, and document why.
