## Lessons for workers

- Before writing a checklist that names exact log lines, open each source document's "How to verify on GitHub" section and quote its log lines verbatim; do not paraphrase a proving line, because a person greps for it.
- `check-docs.py` flags a literal HTML open marker anywhere in a living Markdown file, including inside inline code used as an example. Describe the marker by name instead of writing it.
- In a documentation-only hand-off, verify every claimed workflow and job name against `.github/workflows/*.yml` and every provenance claim (PR number and merge commit) with `git log`; the source notes can be stale about numbering.
- Script changes scoped to `scripts/` cannot be requested through a `task-requests` block (the validator rejects script scopes); record such gaps as findings for a person or as an audit finding instead.
- A source patch document can itself be stale about how a workflow is triggered. Check `workflow_dispatch` versus `workflow_call` in the workflow file before calling a run by hand, and distinguish a job id from its matrix display name and from text a step writes to an artifact rather than stdout.
