# SPEC-XCH-01-C02 — XCH-01 clause 2 API test

## Summary

Added an HTTP-level acceptance test and its clause evidence document proving that a
sending organization may disclose an order only when the payload (order code),
recipient, purpose and duration match an approved authorization. The clause is
already built, so this is proof-only: no production code, existing test, contract
or migration was changed.

## Affected requirements

XCH-01 — sentence under test: "The sending organization authorizes the specific
payload, recipient, purpose and duration." (SMARTCLINIC_V1_SPEC.md line 63).

Acceptance mapping:

| Clause term | HTTP test |
|---|---|
| payload / order code | `orderCodeOutsideTheGrantIsRefused` |
| recipient | `recipientOutsideTheGrantIsRefused` |
| purpose | `unapprovedPurposeIsRefused` |
| duration maximum | `durationAboveTheGrantedMaximumIsRefused` |
| duration window | `disclosureOutlivingTheGrantWindowIsRefused` |
| validity window: expired | `expiredGrantIsRefused` |
| validity window: revocation | `inactiveGrantIsRefused` |
| validity window: not yet effective | `grantNotYetEffectiveIsRefused` |
| tenant scope of the grant | `grantOwnedByAnotherTenantIsRefused` |
| role boundary | `clinicianRoleIsRequiredToDisclose` |
| rule met | `matchingPayloadRecipientPurposeAndDurationArePermitted` |

Branch-to-test mapping for `OrderService.checkGrant` (production file unchanged, lines 403-423):

| Branch / OR term | Test that takes the failing side |
|---|---|
| `grant == null` | `grantOwnedByAnotherTenantIsRefused` (RLS hides ORG_C grant from ORG_A) |
| `!grant.active()` | `inactiveGrantIsRefused` |
| `grant.effectiveFrom().isAfter(now)` | `grantNotYetEffectiveIsRefused` |
| `expiresAt != null && !expiresAt.isAfter(now)` | `expiredGrantIsRefused` |
| `expiresAt != null && disclosureExpiresAt.isAfter(expiresAt)` | `disclosureOutlivingTheGrantWindowIsRefused` |
| `!grant.orderCode().equals(orderCode)` | `orderCodeOutsideTheGrantIsRefused` |
| `!grant.destinationOrg().equals(destination)` | `recipientOutsideTheGrantIsRefused` |
| `!grant.purpose().equals(purpose)` | `unapprovedPurposeIsRefused` |
| `duration > grant.maxDurationMinutes()` | `durationAboveTheGrantedMaximumIsRefused` |
| pass side (all terms false) | `matchingPayloadRecipientPurposeAndDurationArePermitted` |
| `deny()` membership/role side | `clinicianRoleIsRequiredToDisclose` (403 `FORBIDDEN`) |

Every negative test captures order and disclosure counts before the request and asserts they are unchanged afterwards, so a denial that still wrote a row fails. The positive test asserts an increase of exactly one in each table and that the disclosure row carries the approved recipient, purpose and duration.

Branches already covered by pre-existing tests and therefore not re-created here:
the two `expiresAt() != null` FALSE sides of `checkGrant` are unreachable over HTTP
because V19 declares `expires_at timestamptz NOT NULL`; they are covered deterministically
by `it.exchange.order.OrderAuthorizationWindowTest.aDurationAboveTheAuthorizedMaximumIsRejectedEvenWithoutAGrantExpiry`
and `it.exchangeorder.OrderServiceTest.acceptsAnAuthorizationWithoutAnExpiry`, both of
which build an `AuthorizationView` with a null expiry. The `deny()` membership side is
covered by `it.exchangeorder.OrderServiceTest.deniesWhenThereIsNoActiveMembership`; the
new HTTP class deliberately asserts only the role side, so the clause proof stays scoped.

## Findings

- The brief stated that `POST /api/v1/orders` is in `contracts/openapi.yaml:401`.
  That path entry documents only GET; both `POST /api/v1/orders` (line 251) and
  `POST /api/v1/exchange/authorizations` (line 206) are actually listed in
  `contracts/openapi/missing-routes.txt`. This is a pre-existing route-parity gap,
  outside the task scope; the contract was not edited. No task request is needed
  because route documentation is already owned by the route-parity baseline.
- `OrderView` has no `purpose` component, so the brief's suggested response echo of
  `purpose` is not available. The positive test instead asserts purpose from the
  `exchange_disclosure` ledger row, which is the durable record of the approved
  purpose. No production change was made to accommodate the test.
- The plan reviewer suggested splitting the expired and inactive subcases into two
  test methods, adding a not-yet-effective case, and using an ORG_C actor for the
  foreign grant. All were adopted; the final class has 11 tests.
- The `opencode.json` skip-worktree failure is an environment artifact, not a
  defect of this change (details in Test evidence item 8).
- Pre-existing branch defect observed while checking for conflict markers, not
  touched here (outside scope): `de6c97b8` already contains committed
  `<<<<<<< HEAD` / `>>>>>>> origin/swarm/BUILD-37-469` markers inside Javadoc of
  `apps/api/src/main/java/com/aurevia/smartclinic/exchange/hl7/Hl7Parser.java:14-18`,
  `Hl7ParseException.java:6-10` and `Hl7Segment.java:10-14`. They compile because
  they sit in comments, but they should be resolved by an owner of those files.
  No task request is filed: the integrator's conflict-resolution job owns merges.

## Lessons for workers

- When copying a real-PostgreSQL harness into a clause test, give each denial its
  own seeded grant so one HTTP test isolates one `checkGrant` term, and assert
  count-before/after rather than absolute zero: earlier tests in the same class
  legitimately leave committed rows.
- A grant seeded for a foreign tenant must set `app.actor` to a user of that tenant,
  or the V19 `created_by` trigger raises 42501; an expired grant needs
  `effective_from` strictly before `expires_at` to satisfy the V19 CHECK.
- Check the response record's actual components before asserting echoed fields;
  assert content that is absent from the view (such as purpose) from its durable
  ledger row instead of adding production getters for a test.
- In a cloud worker, confirm `git ls-files -v opencode.json` = `S` once when check-pack
  fails, run the remaining gate stages individually, and never regenerate the file.
