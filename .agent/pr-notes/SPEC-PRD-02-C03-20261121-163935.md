## Findings

- Status chosen: **Partly built**. The code that separates delivery evidence from verification evidence is built and synthetically verified (`CriticalContract`, `CriticalResultService`, `CriticalResultController`, `ImagingService.recordCriticalCommunication`, `RxContract`, `RxService`, `RxActions`, `LabTypes`), and the OPS-05 `critical_contacts` runbook explicitly requires attempts, recipient, deadline, read-back and confirmed receipt as separate events. However, no real site manual-workflow artifact exists in the repository, and the human/partner portion is Not built (rule 3) — hence not "Built and verified".
- The strongest direct evidence for the clause is `docs/operations/recovery/operational-runbooks.md` `critical_contacts`, plus `CriticalResultFlowTest.deliveryAndPatientReleaseNeverAcknowledge` and `RxTransmissionFlowTest`'s dispensing-vs-acceptance assertion.
- Gap: three separate tasks — (1) a fail-closed manual-workflow evidence schema that validates delivery fields separately from verification fields; (2) explicit RX-02 printable-handover and XCH-05 backup-contact evidence fields with HTTP-level tests; (3) a human/partner task for the approved ADM-01 channel policy, a real downtime drill and the G5 signed acceptance record.
- No GitHub Actions run ID is claimed: `gh` was not called and no run log was fetched, so `delivery.yml` is cited only as a file, not as a workflow run.
- `infra/recovery/recovery_evidence.py` checks `verification.before_pilot` / `quarterly_cadence` and runbook topic membership, but does not validate delivery-versus-verification fields inside a filled artifact — recorded as a gap, not asserted as built.

## Lessons for workers

- For a spec-clause evidence note, distinguish three things explicitly: code that implements the clause, synthetic tests that verify it, and real site/human evidence. A clause whose satisfaction is a human/partner artifact is Not built in the repository even when adjacent code is green; use "Partly built" when both exist and say who supplies the rest.
- Link only files verified to exist from the note's own directory (`docs/spec/clauses/product/` → `../../../../` for repo root, `../../../` for `docs/`). `python3 -I scripts/check-docs.py` checks every relative link and every requirement-ID mention, so count path levels before writing.
- Do not claim a CI/workflow run as evidence without a fetched run ID. A workflow file is not a workflow run.
- `scripts/check.sh` calls `apps/api/check.sh` (full Maven verify, database integration, >10 minutes). For a Markdown-only task, the task-specific `python3 -I scripts/check-docs.py` is the correct gate; do not run the full chain to "be safe".
