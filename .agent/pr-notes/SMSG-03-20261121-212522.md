# SMSG-03 — API: instant conversations inside a facility

## Summary

Added the instant staff-chat slice under `com.aurevia.staffmsg.instant`:
a wire contract of immutable records, a persistence interface backed by a JDBC
store over the existing V91 staff-messaging tables, a domain service that
re-checks tenant/facility/active-role authorization on every command and read,
and a thin REST controller with an entry point for every command. There are no
new dependencies, no migration edits and no changes outside the two scoped
packages. No push, tag or `gh` call was made.

The four required behaviors are proven end to end on real PostgreSQL: a retried
`Idempotency-Key` returns the first message and stores one row; a removed member
keeps history up to their leave instant but cannot read later messages or send;
unread counts are per subject; and a wrong facility (403) or wrong tenant
(concealed as 404 / RLS-filtered) is refused.

Reuse: `StaffConversation`, `StaffParticipant` (including `isActiveAt`),
`StaffMessage` and both enums from
`com.aurevia.staffmsg.model.StaffMessagingContract` (SMSG-02) rather
than a second messaging vocabulary. V91's `UNIQUE(org, conversation,
client_message_id)`, actor/sequence triggers, immutability triggers and forced
RLS are the authoritative backstops; the service's key lookup is the fast path.

## Affected requirements

- **MSG-02** — open/find a direct conversation, create a group, add/remove
  participants, send, read state and unread counts; work-queue-shaped inbox via
  `GET /unread` and `GET /conversations`.
- **ARC-07** — immutable message content, server timestamp, gap-free
  conversation sequence, sender identity/role from the guarded actor, durable
  client message id for retry deduplication, authorization by membership and
  active role, atomic publication through the store's transaction.

## Risk class

Cross-boundary (API + persistence + authorization). No patient data, real
identifier or credential is used or stored; all fixtures are synthetic
(`nurse-a`, `nurse-b`, UUIDs from the documented pattern). Staff-to-staff
messaging remains proposed scope (SMSG-01); this story does not amend the
specification or enable cross-organization messaging.

## Data changes

None. V91 already owns `staff_conversation`, `staff_participant`,
`staff_message`, `staff_mail_metadata`, `staff_mail_folder` and
`staff_attachment_link` with forced RLS and the append-only ledger. This slice
only inserts/selects those tables and updates `staff_participant.left_at`; it
adds no column, table, index, backfill or migration version. Read cursors are a
process-local projection in the store (see Findings); no clinical record is
kept in memory.

## Authorization boundaries and audit events

Tenant comes only from `TenantContext.current()`, which the request
interceptor derives from authentication plus `X-Active-Organization`; it is
never taken from a body or resource id. Every service command re-checks
`public.has_active_membership(subject)` and `public.active_roles(subject)` via
the store, and compares the conversation's facility with the caller's facility
argument. A former member is refused on send and on `markRead`, and reads are
bounded by their `left_at`. Cross-organization access yields 404/empty via
forced RLS. No audit event type was added or changed; MSG-07 audit remains
SMSG-09. The controller passes the `Idempotency-Key` header to the service,
never a client-supplied sender or organization.

## Migration and rollout considerations

No migration to deploy. The endpoints are additive and safe to enable after
V91; the existing grants already allow the app role the INSERT/SELECT/UPDATE
used here. Read cursors restart empty on a process restart, so unread counts
reset to "everything after zero" until a client marks read again — a documented
limitation, not data loss in the immutable ledger. Rollout needs no lock or
backfill.

## Findings

1. **Scope-limited done state (owner must note).** The engineering bar's full
   "done" checklist cannot be satisfied inside the two allowed packages:
   (a) V91 has no durable per-participant read cursor, so `markRead` state is a
   process-local `ConcurrentHashMap` in `JdbcInstantConversationStore` and
   unread counts reset on restart; (b) the base schema has no staff-to-facility
   assignment table or fold, so "same facility" is enforced as active staff
   tenure plus conversation membership and a facility-id match, not an
   independent facility assignment; (c) the OpenAPI contract entry and
   regenerated client are outside scope. All in-scope acceptance tests pass.
   Three follow-up tasks are requested below; nothing outside scope was edited.
2. **Conversation value order trap.** `StaffMessagingContract.StaffConversation`
   is `(organizationId, facilityId, id, ...)`, not `(organizationId, id,
   facilityId, ...)`. The first JDBC row mapper swapped those two fields and
   produced a foreign-key violation on participant insert; fixed in
   `JdbcInstantConversationStore.mapConversation`. Any later mapper must copy
   the record's declared component order.
3. **PostgreSQL untyped parameter.** `? IS NULL` in a named-parameter query
   cannot infer a type; the visibility filter uses
   `CAST(:notAfter AS timestamptz) IS NULL OR sent_at < CAST(:notAfter AS timestamptz)`
   instead. Keep this form for nullable time bounds.
4. **Fixed clock in integration tests.** A leave instant equal to a message's
   server timestamp hides the "before leave" message because the visibility
   cut-off is strict (`sent_at < left_at`). The removed-member test advances the
   service clock by five seconds before `removeParticipant`.
5. **MEDIUM — `check.sh` red for environmental reasons.** `opencode.json` is
   under `skip-worktree` in this worker (`S` flag), so `check-pack.py` compares
   the CI profile with HEAD and reports it stale (OPS-CW-003-01). Not a change
   defect; no config file was edited.

## Lessons for workers

- Copy component order from the record declaration, not from the SQL
  `RETURNING` list; add a round-trip assertion (write then read by id) before
  building on a new row mapper.
- Bind nullable JDBC time parameters with an explicit `CAST(? AS timestamptz)`
  on both sides of `IS NULL`, or PostgreSQL rejects the statement as bad SQL
  grammar.
- Use a fresh database per integration test when a "find or open" method reuses
  existing rows; otherwise earlier tests leak state into later ones.
- Reuse `public.has_active_membership` and `public.active_roles` instead of
  projecting a second authorization copy; `Boolean.TRUE.equals(...)` on
  `queryForObject` denies on a null result and avoids unboxing findings.
- Inside a cloud worker, treat `check-pack.py` failures as the CI profile under
  skip-worktree; check `git ls-files -v opencode.json` first.

## Why this is not finished

The in-scope implementation and every gate available to a worker are complete
and green. The story cannot be called fully done under AGENTS.md's end-to-end
checklist without changes outside its scope, so the remaining work is handed
off rather than hidden:

- Durable read cursors need a tenant-owned `staff_message_read_cursor`
  migration (RLS + FORCE RLS) and a `Jdbc*` implementation of `markRead`/
  `readSequence`; until then unread state is process-local.
- A staff-to-facility assignment table/fold is needed to prove "same facility"
  independently of conversation membership.
- The OpenAPI contract entry and regenerated client for the nine new routes are
  owned by `contracts/openapi` and the client module.
- The full `mvn verify` / `scripts/check.sh` and database gate remain
  integrator-owned; no full integration suite was run here by design.
