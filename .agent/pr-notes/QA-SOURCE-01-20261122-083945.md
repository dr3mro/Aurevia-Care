# QA-SOURCE-01 — Confirm appointments from the signed-in patient app

## Summary

The installed `AppointmentListPage` passed `placeholderAction` as `onConfirm`, so pressing Confirm issued no request. Confirm is now wired end to end: the read row's server `version` is carried into the display model, a typed client issues the versioned `POST /api/v1/patient/appointments/{appointmentId}/confirm` with `{ patientId, expectedVersion }`, and the server-returned `confirmedAt` instant is rendered in the facility zone. Stale versions reload the list, a 401 ends the session, other failures leave the row retryable, and the control is disabled plus synchronously guarded while a command is in flight. All data is synthetic.

## Affected requirements

- **PAT-01** — list appointments with facility zone/status, allow confirmation where enabled, record the timestamp.
- Supporting evidence boundary: `PatientAppointmentController.java` (`POST /{appointmentId}/confirm`, `ConfirmRequest(patientId, expectedVersion)`), `PatientAppointment.java` (`version`, `confirmedAt`), `PatientAppointmentControllerHttpTest.java` (412 `STALE_VERSION`, 200 `version:2`/`confirmedAt`). The server was **not** changed.

## Risk class

Cross-boundary (patient UI → authenticated transport → existing server command). No clinical decision or new authority is introduced in the client; enablement and eligibility remain server-owned (`deriveConfirmation`).

## Review owner

Senior React Native and Expo / Senior TypeScript / Test Engineer (skills loaded). Simulated patient walkthrough executed through rendered tests; no human clinical or real-patient acceptance was performed or claimed.

## Data changes

None. No Flyway migration, table, backfill or schema change. `version` was already present in the server projection and in existing synthetic GET payloads; it is now parsed and carried by the client. Rollback is a client-only revert.

## Authorization boundaries and audit events

- Confirm is only reachable for a row the patient endpoint returned; `patientId` comes from the signed-in page props, never the response body, and is echoed with the exact version read.
- The transport supplies the bearer credential and correlation id on every request. A 401 invokes the existing `onSessionExpired` handler (credential clearing stays in the owning shell).
- No new audit event: the server's existing `PatientAppointmentService` audit path owns the record.

## Migration and rollout considerations

None. No data migration, no lock or volume impact. Client rolls out with the existing app release; an older client keeps the placeholder no-op until this change ships.

## Clinical and architecture review

- The eligibility decision stays server-owned; the client never enables confirmation for a non-confirmable or already-confirmed row (`deriveConfirmation` unchanged).
- Optimistic concurrency is preserved: the exact read version is sent as `expectedVersion`, and a 412 is treated as stale (reload), never as a success.
- The recorded instant is the server's `confirmedAt`, formatted with the existing facility-zone formatter; the device clock is not used.
- Simulated patient walkthrough: rendered installed page, pressed Confirm on a synthetic `booked`/`confirmationEnabled` row and observed the versioned request and server timestamp; injected stale, server failure and 401 responses.
- No real clinical sign-off, pilot participant or production deployment was involved.

## Findings

1. **Pre-existing committed conflict markers (out of scope).** `git grep -nE '^(<<<<<<<|>>>>>>>) '` reports markers in `apps/api/src/main/java/com/aurevia/smartclinic/exchange/hl7/{Hl7ParseException,Hl7Parser,Hl7Segment}.java`. They are present in `HEAD` and the worktree is clean; `git merge --no-edit origin/main` reported "Already up to date", so they are pre-existing repository debt, not introduced here. Those files are outside this task's scope and were left untouched.
2. **`scripts/check.sh` stops at a known cloud-worker artifact.** `bash scripts/check.sh` → `EXIT=1`, output `check-pack: opencode.json is stale: run scripts/gen-opencode.py`. Evidence: `git ls-files -v opencode.json` → `S` (skip-worktree); `sha256sum opencode.json` equals `.github/opencode.ci.json` and differs from `git show HEAD:opencode.json`. This is the CI profile copied into the worker as recorded in MEMORY.md (OPS-CW-003-01), not drift caused by this change; `opencode.json` is a protected file and was not edited. The remaining checks were run individually and all passed (see Test evidence).
3. **Pre-existing lint warnings.** `npx eslint . --max-warnings=0` reports 4 warnings in two untouched test files; 0 errors. No touched file emits a warning.
4. Existing raw appointment fixtures already contained `version`, so tightening the trust boundary to require an integer version did not break other screens.

## Lessons for workers

- In a cloud worker, `opencode.json` is the CI profile under `skip-worktree`; a `check-pack` staleness failure there is a measurement artifact. Verify with `git show HEAD:opencode.json` and `sha256sum`, run the other policy checks individually, and never regenerate or edit that protected file from a story worker.
- When a defensive guard is unreachable through the rendered UI (the control is disabled first), test it by mocking the presentational boundary and invoking its callback twice in one `act`. That keeps the safety guard, satisfies 100% branch coverage and avoids a flaky timing test.
- React's `useCallback` dependency lint will reject a `reloadCount` used only as a trigger. Remount the resource with `key={reloadCount}` instead of listing it as a dependency: the reload is explicit and the lint stays clean.
- A server's "stale version" may be a 412 distinct from an "already confirmed" 422; map the transport's `conflict` kind to reload and let `validation`/other kinds stay retryable.
