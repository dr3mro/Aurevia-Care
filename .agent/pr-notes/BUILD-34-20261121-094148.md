# BUILD-34 — Emergency and support access: time limit, alert, review and closure

## Summary

The IAM-06 production slice already existed in `com.aurevia.authz.access`
(V11 tables, qualified-clinician and site-approval gates, 1–60 minute expiry, reason
validation, `EMERGENCY_ALERT` audit, default-deny platform support with a separately
approved incident, forced RLS and composite facility FK). This story closes the two
missing rules: **the privacy-auditor alert and an OPEN review are now durable rows
created with the grant**, and **a review is closed with an explicit, validated
outcome**. `SupportAccessService` needed no change — its off-by-default incident
procedure is already implemented and covered.

Files changed (all inside the declared scope):

- `apps/api/src/main/java/com/aurevia/authz/access/AccessContracts.java` —
  `ReviewRequest` gains a second component `outcome` plus the backward-compatible
  one-argument constructor.
- `.../AccessRules.java` — `DEFAULT_REVIEW_OUTCOME`, bounded outcome set,
  `isReviewOutcome` and `validateReviewOutcome`.
- `.../AccessRepository.java` — `openReview(...)` and `closeReview(...)` SQL boundary
  with named parameters and tenant-bound inserts.
- `.../EmergencyAccessService.java` — grant opens the privacy-auditor review and
  emits `EMERGENCY_REVIEW_OPEN`; review resolves/defaults and validates the outcome
  and closes the review row in the same transaction.
- `db/migrations/V88__access_review.sql` (new, reserved version only) —
  `public.emergency_access_review` with ENABLE + FORCE RLS, tenant policy, composite
  tenant FK, `UNIQUE(org, grant_id)`, self-review prohibition and a CHECK that a
  closed review always has outcome, reviewer, note and closure time.
- Four new test classes under
  `apps/api/src/test/java/com/aurevia/authz/access/` (unit, SQL-boundary,
  rules/Jackson and a real-PostgreSQL HTTP integration suite).

No dependency, generated file, tracker or out-of-scope source was changed. Synthetic
identifiers and reasons only; no patient data, credentials or real domains.

## Affected requirements

- **IAM-06** (primary): qualified clinician, own organization, reason, short expiry,
  immediate privacy-auditor alert, independent review closed with an outcome,
  no cross-tenant unlock; platform support off by default behind an approved incident.
- Supporting: **ARC-02** (forced RLS and composite tenant FK on the new table),
  **OPS-02** (purpose/scope/actor audit facts appended in the same transactions).

## Data changes

V88 adds one table, `public.emergency_access_review`, to the existing V11 grant
tables. No existing column is altered: no backfill, no lock on existing data, one
bounded INSERT per grant and one bounded UPDATE per review. Rollback/forward-fix is
a plain DROP of the new table, policy and index (declared in the migration header).
The composite foreign key `(organization_id, grant_id)` prevents an Org A grant from
acquiring an Org B review even when local identifiers collide.

## Authorization boundaries and audit events

Organization, subject, role and time are taken only from `TenantContext` and the
injected `Clock`; the request body carries only facility, reason, note and outcome.
Existing `EMERGENCY_GRANT`, `EMERGENCY_ALERT`, `EMERGENCY_ACTIVE_CHECK`,
`EMERGENCY_REVOKE` and `EMERGENCY_REVIEW` audit facts are unchanged. Added:
`EMERGENCY_REVIEW_OPEN` with purpose `EMERGENCY_ACCESS`, scope
`privacy_auditor:<facility>`, resource type `EMERGENCY_ACCESS_REVIEW`, outcome
`SUCCESS`. The closed review row carries an independent `reviewer` that the database
forbids from equalling the grantee.

## Migration and rollout considerations

`-- Change: expand`, requirement IDs in the header, ENABLE + FORCE ROW LEVEL
SECURITY, a `tenant_isolation` policy using `public.app_org()`, explicit
`GRANT SELECT, INSERT, UPDATE` / `REVOKE DELETE, TRUNCATE` to `aurevia_app`, and
an index on `(organization_id, status, opened_at DESC)`. Applied by Flyway in both
the HTTP integration suite and `db/check.sh`; no new table is left outside forced
RLS. Outcome text is bounded by SQL CHECK and Java validation with the same set.

## Clinical and architecture review

No human clinical, privacy-officer or patient review was available; none is claimed.
Three read-only specialist design reviews were requested and received before
implementation: Senior Database proposed the RLS/CHECK/FK schema shape and flagged
the direct-SQL-insert compatibility trap; Senior Backend proposed the additive
constructor/ignored-return design and the creator-ambiguity risk; Test Engineer
proposed the acceptance matrix and the mutable-clock "next request" test. All three
explicitly ran no commands, so their findings are simulated-review evidence, while
the results above are executed-tool evidence. The design converged on a single
service-managed review table plus a server-defaulted outcome, preserving every
out-of-scope call site.

## Findings

1. The existing V11 slice already satisfied most of IAM-06; this story adds only the
   missing durable alert/open-review and outcome closure. `SupportAccessService` is
   intentionally unchanged.
2. V88 applies cleanly under Flyway in both the new HTTP integration suite and
   `db/check.sh`. The cross-tenant test proves forced RLS hides another tenant's
   review rows and that a foreign auditor receives 404 rather than a review.
3. `closeReview`'s zero-row result is deliberately ignored: the preceding
   `reviewGrant` UPDATE is authoritative, existing mocks do not stub the new method,
   and legacy direct-SQL grants have no review row. The SQL `status = 'open'` guard
   and the V88 CHECK make a second closure harmless.
4. Out of scope and left untouched: `contracts/openapi*` has no `/api/v1/access`
   entry (pre-existing), so the new `outcome` property is not documented in the
   generated client. Needs a separate cross-boundary story with a regenerated client.
5. `db/check.sh` was not extended (outside scope); V88 policy/constraint evidence
   comes from the new in-scope integration suite, which the integrator will re-run.
6. The three `test_check_pack` failures are the documented skip-worktree CI-profile
   artifact, not a regression from this change (verified against the committed file).
   For the same reason `scripts/worker-check.sh` and `scripts/check.sh` were not run
   end to end in this worker (they both invoke `check-pack.py`, and `worker-check.sh`
   additionally runs every integration suite). Their applicable parts were run
   individually above; the integrator runs the full gate on the merged SHA.

## Lessons for workers

- In a cloud worker, check `git ls-files -v opencode.json` before treating
  `check-pack.py` or `test_check_pack` failures as real; compare
  `git show HEAD:opencode.json` with the generator render instead.
- "One active grant per subject" means integration tests must use a distinct
  synthetic clinician per grant case, or revoke between cases.
- Spring 6 maps 422 to `HttpStatus.UNPROCESSABLE_CONTENT`; assert `.value() == 422`
  for compatibility.
- When adding a component to a record used by out-of-scope tests, keep the old
  constructor as an auxiliary one; Jackson 3 still selects the canonical record
  constructor (proved by both JSON-shape tests here).
- To prove 100% JaCoCo on `AccessRepository`, include the existing DB suite in the
  targeted `-Dtest` list — mock-only runs leave its SQL methods uncovered.
