## Lessons for workers

- A "Repair main" story quoting only the `if: always()` artifact-upload tail has not
  identified the failure. Reproduce the job's real run steps locally
  (`apps/api/check.sh` = tests + JaCoCo + OWASP + SpotBugs, then `db/check.sh`) and capture
  the first failing step and its final line before classifying.
- Before writing a fix, check whether a post-failure main commit already repaired it.
  `git log --oneline <failed-sha>..origin/main` and `git show --stat <candidate>` turn a
  duplicate-fix (and a unique-constraint violation) into a documentation-only outcome.
- For a Java integration failure, use `mvn -Pno-security -Dgroups=integration
  -Dtest=<Class> test` with `SMARTCLINIC_PG_ADMIN=postgres`. Never add `fast`:
  `-Pno-security,fast -Dgroups=integration` excludes integration tests and gives a false
  green. A bare `spotbugs:check` is vacuously green; compile first.
- When a service validates drafted values against an approved config fold, an HTTP proof
  test must seed the fold (entry + approval, tenant-scoped) in its own scratch DB, once.
  `UseSiteSApprovedUrgentDowntimeChannelsTest.seedPolicy` is the canonical pattern; the
  seeded codes must match the test's own request literals.
- A test-only fixture fix has no new production coverage obligation; do not claim a
  targeted `jacoco:report` proves the bundle. Record that the authoritative BUNDLE 1.00
  JaCoCo gate belongs to the integrator's full `verify`.
- In a cloud worker, `git ls-files -v opencode.json` showing `S` explains
  `check-pack.py`/`test_check_pack` failures: verify with `git show HEAD:opencode.json`
  and never regenerate or commit that file. Do not re-diagnose it on a later pass.
- Do not leave a temporary reproduction worktree inside the repository when running
  `check-docs.py`: it scans duplicate Markdown files under the worktree and reports false
  table/fence errors. Remove the worktree and rerun.
