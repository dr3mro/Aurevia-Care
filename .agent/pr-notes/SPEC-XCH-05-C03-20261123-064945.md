## Lessons for workers

- For a mock-based clause proof, apply per-test overrides (inactive backup
  recipient, restricted role) only *after* the setup helper drives the row to the
  target state; overriding before it makes the setup's own `assign` fail with a
  roster gap or missing permission.
- To prove a two-operand guard, call it twice: once with both operands wrong and
  once with the first correct but the second wrong, then assert the same stable
  code and the absence of the success fact.
- In a cloud worker, `git ls-files -v opencode.json` → `S` plus a stale
  `check-pack` failure is the documented OPS-CW-003-01 artifact: confirm once,
  run the remaining gate stages individually and never regenerate that file.
- Match the gate's exact shellcheck file set before reporting a shell-lint
  failure; scanning all tracked `*.sh` surfaces unrelated info-level findings
  outside the gate.

## Coverage repair pass (attempt 1 of 2)

The coverage gate (`bash scripts/coverage-check.sh origin/main`) failed even
though this story changed no production code, because that gate runs the full
`mvn -Pno-security verify` and four tests were red. All four were pre-existing
stale fixtures in the messaging domain, unrelated to XCH-05:

- `EnabledUnitPublishServiceHoursResponseTargetsTest`:
  `publishIsRefusedWithoutTopicsOrUrgentInstructions:170` expected
  `INVALID_TOPICS` but was `UNAPPROVED_CHANNEL`;
  `enabledUnitPublishesHoursTargetsTopicsAndUrgentInstructions:92` and
  `publishIsRefusedWithStaleVersion:140` threw
  `ApiException: urgentChannel is not an approved site channel`.
- `RequireNamedQueueOwnerBackupCoverageOverdueTest`:
  `httpPublishRefusesBlankOwnerAndMissingBackup:203` expected
  `INVALID_QUEUEOWNER` but was `UNAPPROVED_CHANNEL`.

Root cause (tool evidence: `git log -- <path>`): commit `9cc63a1f`
(SPEC-MSG-06-C06) added `ServiceProfileService.requireApprovedChannel`, so
`publish` now refuses urgent/downtime codes absent from the site-approved
config fold (`store.approvedChannels`). The two older test classes
(`7e5df1c0`, `7957450a`) predate that change and never seeded their channel
codes as approved, so validation failed closed before their assertions ran.

Deterministic fix (test fixtures only; no production code, migration, contract,
threshold or exclusion changed): in each `@BeforeEach` seed the exact channel
codes the fixture publishes via `InMemoryServiceProfileStore.seedApprovedChannels`
under the two policy keys production reads:

- `EnabledUnitPublishServiceHoursResponseTargetsTest.setUp`:
  `msg06.approved_urgent_channels` = `urgent-channel`,
  `msg06.approved_downtime_channels` = `downtime-channel`.
- `RequireNamedQueueOwnerBackupCoverageOverdueTest.setUp`:
  `msg06.approved_urgent_channels` = `urgent-phone`,
  `msg06.approved_downtime_channels` = `downtime-phone`.

This restores each test to its intended assertion under the legitimate,
now-enforced channel-approval behaviour; no test was weakened, skipped or
rewritten to hide a failure.
