## Summary

Replaced the process-local `@Repository` `InMemoryMessagingStore` with a
PostgreSQL adapter. Added `db/migrations/V60__care_units.sql` with four
tenant-owned tables (`care_unit`, `eligible_relationship`,
`patient_unit_connection`, `messaging_audit`), each with forced row-level
security, a `public.app_org()` policy and explicit grants; the audit ledger is
also protected by append-only triggers. `JdbcMessagingStore` implements every
`MessagingStore` method through a tenant-guarded `TransactionTemplate` and
parameterised SQL only, reusing the authoritative membership, role, chart-link
and patient folds instead of duplicating their state. `InMemoryMessagingStore`
lost its `@Repository` and moved to test scope; two existing Spring tests that
autowired the concrete class now supply it as a `@Primary` test bean so they
keep their deterministic fixtures while production uses the JDBC adapter.

## Data changes

`V60__care_units.sql` is additive (`-- Change: expand`) and creates four tables:

- `care_unit` — `(organization_id, id)` key, `facility_id`, `name`, `topics
  text[]`, `active`, `unit_key`, `created_at`. Append-only: no UPDATE grant.
- `eligible_relationship` — `(organization_id, id)` key, patient/unit ids,
  bounded `context`, `reference`, `active`, `consumed`, `expires_at`,
  `created_at`. Narrow UPDATE grant for the single-use consumption transition.
- `patient_unit_connection` — `(organization_id, id)` key plus
  `UNIQUE (organization_id, patient_id, unit_id, context_reference)`, bounded
  `context`/`state`, verifier, instants, `created_at`. Narrow UPDATE grant for
  revocation.
- `messaging_audit` — `(organization_id, id)` key, database-owned `seq` and
  `id`, non-sensitive fact fields, `occurred_at`, `created_at`; no UPDATE grant
  and `reject_immutable_mutation()` triggers for UPDATE, DELETE and TRUNCATE.

Every table carries `organization_id NOT NULL REFERENCES public.organization`,
`created_at timestamptz NOT NULL DEFAULT now()`, `ENABLE` + `FORCE ROW LEVEL
SECURITY`, a `tenant_isolation` policy with both `USING` and `WITH CHECK`, and
explicit grants to `smartclinic_app`. No existing migration was edited; no
backfill, lock or volume impact beyond four empty tables. Forward/rollback:
Flyway version 60 is new; a contract later removing a table must point at an
earlier `Change: expand` per `docs/decisions/0002`.

## Authorization boundaries and audit events

Every adapter method runs inside the shared tenant-guarded
`TransactionTemplate`, so `app.current_org()`, `app.actor`, `app.purpose` and
`app.correlation_id` are bound transaction-locally before any SQL. Reads carry
no manual organization predicate; forced RLS confines them. Inserts write the
method's `organizationId` so `WITH CHECK` fails closed on a mismatch —
`auditFactsAreImmutableAndCrossTenantWritesFailClosed` proves both a rejected
cross-tenant write and the append-only trigger. The adapter changes no
authorization decision: `CareUnitDirectoryService` still re-derives membership,
role and verified chart on every request. No audit event type was added or
changed; `MessagingAudit` facts are stored durably with the same fields and
insertion order as before.

## Migration and rollout considerations

V60 was free: `git ls-files db/migrations/ | grep V60__` returned nothing and
the migration gate passed, unlike READY-35's stale V59 reservation. The
migration is applied last under both `sort -V` (`db/check.sh`) and Flyway's
numeric order, so `organization`, `app_org()` and `reject_immutable_mutation()`
already exist; no out-of-order guard is needed. The production bean change is
immediate on deploy: the new adapter reads pre-existing folds, so no data
migration or dual-write is required. The tagged test creates and drops its own
`smartclinic_messaging_store_it` database.

   green. READY-35's V59 collision did not recur, so no version blocker exists

2. **AUD-20261120-04 does not exist**: `grep -rln` over `scripts`, `docs` and

   and was run green.
3. **Two Spring tests autowired the concrete in-memory class**:
   `ConversationFlowTest` and `ConversationHttpSecurityTest` call
   `addMember`/`linkPatient`/`addUnit`/`insertConnection` on an autowired
   `InMemoryMessagingStore`. Removing `@Repository` would have broken them.
   Both now declare a nested `@TestConfiguration` with a `@Primary`

   passed in the full verify (8 and 31 tests respectively).
4. **Defects found: none introduced.** One test initially wrote tenant B's
   audit while bound as tenant A and RLS correctly rejected it
   (`new row violates row-level security policy`); the test was corrected to
   bind the owning tenant, and that behavior is now asserted explicitly in
   `auditFactsAreImmutableAndCrossTenantWritesFailClosed`.
5. **Design decisions (recorded here, no owner decision outstanding):**
   - Membership, roles, verified charts and patient existence are read from the
     authoritative folds/tables rather than a V60 projection, so deactivation
     and unlink remain immediate (ARC-01, CODING_STYLE reuse).
   - `consumeRelationship` and `revokeConnection` are single idempotent UPDATEs
     with no pre-check Java branch, matching the in-memory no-op-when-absent
     semantics and keeping branch coverage honest.
   - `eligible_relationship` and `patient_unit_connection` receive narrow UPDATE
     grants for their state transitions; `care_unit` and `messaging_audit` are
     append-only, with triggers on the audit ledger for every role.
6. **Pre-existing red checks** (`check-pack` skip-worktree artifact and the
   missing `yaml` Python module) are unchanged by this work and are not
   fixable inside this scope.

## Lessons for workers

- When replacing a `@Repository` in-memory store, grep **tests** as well as
  main code for autowiring of the concrete class: `@SpringBootTest` tests can
  depend on the bean even though production only injects the interface. A
  nested `@TestConfiguration` with a `@Primary` bean keeps those tests green.
- Forced RLS with `WITH CHECK` fails closed on a cross-tenant write even when
  the `organization_id` comes from a domain record. In integration tests, bind
  `TenantContext` to the tenant that owns each row you write.
- JaCoCo counts a lambda passed to `orElseThrow` as a separate method. A
  defensive throw that cannot fire after `ON CONFLICT DO NOTHING` must be
  deleted (`orElseThrow()` no-arg), not "covered" by a contrived test.
- `worker-check.sh` can stop at `check-pack` on the known CI-profile/
  skip-worktree artifact. Run the later stages individually and record both
  results rather than editing `opencode.json` (which is protected and stale by
  design inside a worker).
