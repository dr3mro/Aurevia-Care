# SPEC-ARC-07-C04 — API test evidence for ARC-07 clause 4

## Summary

Add one focused API test class and one clause document proving that ARC-07's
authorization rule is enforced: a patient reaches messaging only through a
verified active connection, and staff reach it only through active membership,
a permitted action role and eligibility for the recipient unit. Test-only
change: no production code, contract, migration or dependency changes.

## Affected requirements

ARC-07 (Patient communication), clause 4: "Authorize patient access through the
connection and staff access through membership, unit assignment and role."

## Risk class

Safety-critical (authorization boundary). Evidence is from an automated test
and read-only reviewers only; no real clinician or patient feedback was used.

## Review owner

orevia-senior-backend (domain-service authorization); read-only reviews by
orevia-plan-reviewer, orevia-code-reviewer, orevia-coverage-auditor
and orevia-devsecops.

## Data changes

None. No migration, backfill, lock or volume impact, rollback or forward fix.
All fixtures are synthetic and tenant-scoped.

## Authorization boundaries and audit events

The tests drive the domain services with an explicit `TenantContext`. Patient
access is proved through `CareUnitDirectoryService.requireActive` (exact active
connection, owning chart, tenant directory unit) called by
`ConversationService.open`; staff access through `ConversationService.authorize`
(active membership + action role) and `ConversationActions.allowsUnit` (role
eligible for the conversation's recipient unit). No audit behavior is changed;
the tests assert existing audit outcomes where visible.

## Findings

- The rule is built, not a gap: patient access is enforced by
  `CareUnitDirectoryService.requireActive` through `ConversationService.open`, and staff access by
  `ConversationService.authorize` plus `ConversationActions.allowsUnit` and `requireAccess`. Status
  is therefore "Proven by tests" with `## Gap: None`.
- "Unit assignment" in this implementation is the bounded role-to-unit capability matrix
  (`ConversationActions.allowsUnit`) together with the recipient unit stored on the conversation;
  there is no separate per-subject unit-assignment row. The clause doc states this explicitly rather
  than claiming an unimplemented table.
- `worker-check.sh`, `python-coverage.sh` and six `test_check_pack` cases are red only because the
  worktree `opencode.json` is the CI runtime profile under `skip-worktree`. Read-only verification
  showed the committed `HEAD:opencode.json` matches the generator (`True`) while the worktree copy
  does not (`False`); no file was regenerated. The remaining stages were run individually and pass.
- `bash scripts/frontend-check.sh` exited 1 on its first attempt and 0 on a clean rerun with no
  frontend file changed by this story; treat the first result as transient.
- Pre-existing, unrelated to this story: `origin/main` contains conflict markers inside Javadoc in
  `apps/api/src/main/java/com/aurevia/exchange/hl7/Hl7ParseException.java`,
  `Hl7Parser.java` and `Hl7Segment.java`. They are inside comments, so compilation is unaffected,
  and they are out of this story's scope; they were reported, not edited.
- Review findings addressed: an initial `@SuppressWarnings("unchecked")` was removed in favor of a
  typed `invocation.getArgument(0)`; the connection audit assertion now requires exactly one
  matching event; the clause doc now states accurately that `tenant_admin` is refused at the
  action gate before the unit check and that `ConversationController` lives in the conversations
  package.

## Lessons for workers

- Audit denials from `CareUnitDirectoryService` go to `MessagingStore.appendAudit` (visible via
  `InMemoryMessagingStore.auditEvents`), while `ConversationService` gate denials go to its injected
  `AuditAppender` mock; unit-mismatch and invalid-input guards throw inside the transaction work
  and append no audit at all. Assert the right channel or the test fails for the wrong reason.
- `scripts/check-constraints.py` rejects any new `@SuppressWarnings`, even on a test-only helper;
  use a typed `invocation.getArgument(0)` instead of a raw unchecked cast in the synchronous
  `TransactionTemplate` stub.
- To prove "server-derived, not request-body" deterministically, stub the verifier boundary with
  values deliberately different from the request; with the real directory every successful value
  necessarily equals the request, so that test alone cannot distinguish propagation from echo.
