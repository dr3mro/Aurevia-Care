# SPEC-ARC-07-C04 — API test evidence for ARC-07 clause 4

## Summary

Add one focused API test class and one clause document proving that ARC-07's
authorization rule is enforced: a patient reaches messaging only through a
verified active connection, and staff reach it only through active membership,
a permitted action role and eligibility for the recipient unit. Test-only
change: no production code, contract, migration or dependency changes.

## Affected requirements

ARC-07 (Patient communication), clause 4: "Authorize patient access through the
connection and staff access through membership, unit assignment and role."

## Risk class

Safety-critical (authorization boundary). Evidence is from an automated test
and read-only reviewers only; no real clinician or patient feedback was used.

## Review owner

smartclinic-senior-backend (domain-service authorization); read-only reviews by
smartclinic-plan-reviewer, smartclinic-code-reviewer, smartclinic-coverage-auditor
and smartclinic-devsecops.

## Data changes

None. No migration, backfill, lock or volume impact, rollback or forward fix.
All fixtures are synthetic and tenant-scoped.

## Authorization boundaries and audit events

The tests drive the domain services with an explicit `TenantContext`. Patient
access is proved through `CareUnitDirectoryService.requireActive` (exact active
connection, owning chart, tenant directory unit) called by
`ConversationService.open`; staff access through `ConversationService.authorize`
(active membership + action role) and `ConversationActions.allowsUnit` (role
eligible for the conversation's recipient unit). No audit behavior is changed;
the tests assert existing audit outcomes where visible.

## Migration and rollout considerations

None. Test and documentation files only.

## Coverage

This diff is test-only: zero `src/main` hunks, so there are no new production
lines or branches for JaCoCo to cover. The targeted command above runs 15 active
tests with 0 skipped; the full JaCoCo 100% gate stays with the integrator and
Delivery (a swarm worker must not run the full `mvn verify`). The meaningful
evidence is fault detection — each named branch below has an asserting test that
would fail if the guard were removed.

| Authorization branch | Test that takes it |
|---|---|
| Patient success derives patient/connection/unit from the verifier, not the request | `patientOpenPersistsServerDerivedIdentitiesFromTheVerifiedConnection` (verifier stub returns different values; `insertConversation` asserts those values) |
| Patient success with the real connection verifier and directory unit | `patientOpenThroughAnActiveConnectionPersistsTheDirectoryDerivedIdentities` |
| Connection revoked (403 `FORBIDDEN`, connection audit `DENIED`) | `patientOpenDeniesARevokedConnection` |
| Connection owned by another chart (404 `NOT_FOUND`, audit `NOT_FOUND`) | `patientOpenDeniesAnotherPatientsConnection` |
| Unknown connection (404 `NOT_FOUND`, audit `NOT_FOUND`) | `patientOpenDeniesAnUnknownConnection` |
| Connection for another unit / directory-derived unit mismatch (403) | `patientOpenDeniesAConnectionForAnotherUnit` |
| Unbounded unit key (422 `INVALID_UNITKEY`, no lookup or audit) | `patientOpenRejectsAnUnboundedUnitKeyBeforeAnyLookup` |
| Patient naming another subject (404 before existence lookup) | `patientOpenConcealsAnotherSubjectWithoutProbingExistence` |
| Staff eligible role + unit success (state `AWAITING_PATIENT`, SUCCESS audit, no connection use) | `staffOpenAllowsAnEligibleRoleInItsUnit` |
| Inactive membership (403, DENIED audit, no role or patient lookup) | `staffOpenDeniesInactiveMembership` |
| Role missing the open permission (403, DENIED audit) | `staffOpenDeniesARoleWithoutTheOpenPermission` |
| Staff role not eligible for the unit (403, no write, no SUCCESS audit) | `staffOpenForAnUnassignedUnitIsDenied` |
| Wrong role for a work item (403, DENIED audit) and cross-unit work item (403, no write) | `staffWorkItemDeniesWrongRoleAndCrossUnit` |
| Object-level patient concealment on an existing thread | `getConcealsAnotherPatientsThreadFromThePatient` |
| Object-level staff unit mismatch on an existing thread | `getDeniesStaffOfAnIneligibleUnitOnAnExistingThread` |
