The clause is fully built. The positive test drives the real `/api/v1/clinical-notes`
entry point against PostgreSQL and proves the complete lifecycle: an original draft is

## Findings

1. **Package/domain split (intentional, per task scope).** The test class sits under
   `chart/clauses` as a clause-evidence test, but the behaviour it proves is owned by
   the `clinical.notes` domain (`ClinicalNoteController`, `ClinicalNoteService`,
   `NoteState`, `NoteRepository`, V15). The clause doc states both explicitly. No
   `chart.record` code was touched.
2. **Private helpers in the neighbouring reference test.** `ClinicalNoteRevisionIntegrationTest`'s
   `seed`/`request`/`createBody`/`field`/`sha256` helpers are all `private`, so the new
   class defines its own local copies (the established pattern in the sibling clause
   tests) instead of calling across classes or widening visibility in an existing test.
   The plan reviewer recorded this as a Required gap; it was fixed before coding and
   the re-review was GO.
3. **Known worker-image artifacts** (`opencode.json` skip-worktree `check-pack` failures,
   missing Python `coverage`, offline OWASP/NVD): recorded once above with evidence; no
   protected file was edited.
4. **Pre-existing committed conflict markers (not introduced, out of scope, left untouched).**
   `git grep -nE '^(<<<<<<<|>>>>>>>) '` finds markers inside Javadoc comments in
   `exchange/hl7/Hl7ParseException.java`, `Hl7Parser.java` and `Hl7Segment.java`; they are

## Lessons for workers

- For an evidence-only clause test, the helpers in the neighbouring integration test are
  `private`: define local private copies in your own class and never widen visibility in
  an existing test, which is outside the scope.
- Use a database name unique to your task (here `smartclinic_cln05_c01_it`, not the
  reference `smartclinic_cln05_it`) because parallel workers share the PostgreSQL server;
  set `app.current_org`/`app.actor` for each seed and migrate from `filesystem:../../db/migrations`.
- `mvn -Pno-security,fast -Dgroups=integration` does **not** run integration tests because
  the `fast` profile's `excludedGroups=integration` wins. Use `-Pno-security -Dgroups=integration`
  and read the Surefire XML for the authoritative counts. A bare `spotbugs:check` is
  vacuously green; compile first (`-DskipTests compile spotbugs:check`).
- A `check-pack` / `opencode.json is stale` failure inside a cloud worker is almost always
  the CI profile under skip-worktree (OPS-CW-003-01). Prove it with `git ls-files -v` +
  `git diff --stat`, record it, run the remaining stages individually, and never edit or
  regenerate `opencode.json` as a worker.
