# BUILD-64 — Gate G4 acceptance tests: radiology, therapy, pharmacy and finance

`apps/api/src/test/java/com/aurevia/acceptance/specialty`. Each class exercises a

## Findings

1. **RAD-01 "reaches the referrer" is a domain fact, not a delivery.** `ImagingService`
   emits `REFERRER_NOTIFIED` with `destination = referrer` but no outbox, publisher or
   referrer inbox exists (src/main grep). The acceptance test proves the fact and its
   ordering; actual delivery is not implemented.
2. **No HTTP endpoints for RAD sign/addendum or PT evaluation/note/sign/summary/ack.**
   `ImagingController` exposes intake/read/study-link only; `TherapyController` exposes
   accept/read only. These acceptance tests are necessarily service-level, matching the
   existing `acceptance/patient` pattern.
3. **RAD and Rx/PT in-memory state.** `ImagingService`, `WorklistService` and the Rx/Finance
   repositories are in-memory or JDBC-bound with no durable store for the imaging kernel;
   AUD-20261121-05 already tracks the RAD persistence defect in TODO.md. Out of BUILD-64 scope.
4. **PT "referral closure" has no separate entity or endpoint.** Closure is modelled as
   `EpisodeState.DISCHARGED` after signing a `DISCHARGE` note; there is no `closeReferral`
   method, referral status entity or closure route. The test also proves the approved
   summary and referrer return acknowledgment.
5. **RX-02 database deduplication is not exercised by this fast suite.** Unique constraints,
   `ON CONFLICT DO NOTHING`, append-only triggers and immutable submission id are covered by
   `it/prescription/RxTransmissionFlowTest` (`@Tag("integration")`, PostgreSQL), outside this
   package's scope. The new test proves service-level single-send deduplication.
6. **FIN-01 has no ledger-fold rebuild API.** "Reproduce balances on replay" is proven as
   command-replay idempotency by reference digest; deriving balances from stored entries after
   the fact is not a callable capability.
7. **Test-only fixture boundary.** `FinanceRepository` is a concrete class and the only
   finance fake (`FinanceLedgerTest.LedgerFakeRepository`) is private in another package, so
   the finance test carries a small local subclass fixture; `RxRepository` is likewise
   concrete, so the RX test uses a state-holding Mockito mock.
8. **QA review resolutions (non-blocking).** The simulated QA reviewer found no blocking
   issue. Addressed in scope: test-method-level requirement-ID comments added; the therapy
   reconstruction assertion is now described as "state lives in the store, not the service
   instance" (restart durability is the JDBC integration test's job); numbered receipts are
   asserted (`receiptNo` 1 then 2); and the finance fake now returns 0 on a version mismatch
   instead of always 1. The RX test documents that its `verify(...)` interactions, not the
   mock-written state atoms, are the "no duplicate send" proof; stale-version/retry-limit
   enforcement stays with `RxServiceTest` / `RxTransmissionFlowTest`. The remaining QA notes
   (RAD delivery outbox, PT referral entity, owner decisions for PROJECT.md/MEMORY) are
   recorded above and in "Why this is not finished" because they require production or
   tracker changes outside this test-only scope.

## Lessons for workers

- The `acceptance/*` convention here is service-level with in-memory/mock fixtures and
  requirement IDs in Javadoc; it is not MockMvc or `@SpringBootTest`. Check for an HTTP
  route before promising one — sign/addendum and PT note commands have none.
- For a concrete repository with no fake, a `Mockito` mock whose mutator `Answer`s update a
  small in-test state holder (version/state/submission id) gives deterministic returned
  aggregates without a real DB; verify the mutator call counts instead of asserting on a
  stub that proves nothing.
- A database-free subclass of a concrete `Jdbc*` repository must call `super(null)` and
  override every method the service actually calls (including `loadForUpdate`,
  `findByReference` and `nextReceiptNo`), otherwise replay/balance paths silently break.
- In a cloud worker, a red `check-pack.py` is the CI `opencode.json` under `skip-worktree`:
  restore `git show HEAD:opencode.json` bytes, run the gate, restore the CI bytes with `cmp`
  verification; never regenerate or commit that file.
- `scripts/quick-check.sh` is the safe fast gate; `scripts/check.sh`, `worker-check.sh` and
  `coverage-check.sh` run the full verify / all integration tests and belong to the integrator
  under this story's time-budget rule.
- Make a hand-written repository fake enforce the same preconditions as the real one (for
  example return 0 from `updateInvoice` on a version mismatch). A fake that always succeeds
  cannot detect a service that skips its version check, which makes an idempotency test
  circular. Assert the side effects that the acceptance criterion actually names (receipt
  numbers, call counts), not only the returned DTO.

## Why this is not finished

The requested acceptance **tests are written and green** (10/10). Full end-to-end G4
acceptance cannot be claimed from a test-only change because the following production
behaviors are missing or unproven inside this scope; each needs a separate owner story:

- RAD-01: no persistent imaging store with RLS/FORCE RLS, no injected service (the production
  controller builds `new ImagingService(...)`), no HTTP sign/addendum route and no outbox to
  actually deliver a referrer notification. Tracked as AUD-20261121-05 in TODO.md. Next step:
  persist imaging state behind a `JdbcImagingStore`, inject the service, add the sign/addendum
  routes and an outbox, then add an HTTP-level integration test.
- PT-01: no separate referral entity or closure endpoint; "closed referral" is only the
  episode state transition. Next step (owner decision): add a referral resource with an
  explicit CLOSED state and closure route, then extend this acceptance test.
- RX-02: database uniqueness/dedup is proven only by an integration test outside this
  package. Next step: integrator runs the full integration tier on the exact SHA.
- FIN-01: no event-sourced ledger-fold API; replay idempotency is the implemented behavior.
  Next step (owner decision): add a rebuild-balances-from-entries capability if the gate
  requires it.

No red/failing command remains in this change: the targeted tests, Java conventions test and
fast gate all pass. The above are production-scope gaps, not failures of the delivered tests.
