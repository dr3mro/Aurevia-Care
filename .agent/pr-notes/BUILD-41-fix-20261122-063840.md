# BUILD-41 (fix pass) — an explicitly expired export must never be downloadable

## Summary

Continuation of BUILD-41 / OPS-07 on `swarm/BUILD-41-495`. Earlier passes had already
built the tenant-export feature, closed an orphaned-manifest leak, removed unreferenced
snapshots and made expiry retriable by marking the durable row `EXPIRED` *before*
removing the object. This pass closes the disclosure window that the last reorder
introduced: `TenantExportService.download()` gated only on the retention instant, so a
job whose status was already `EXPIRED` (but whose 24-hour `expiresAt` had not passed)
could still be disclosed while the manifest was still present.

A failing test was written first at both boundaries (domain value and service), then
`ExportJob.expired(Instant)` was changed to treat an explicit `EXPIRED` status as
expired regardless of the clock. A simulated senior-backend review confirmed the
predicate is in the right layer and suggested one in-scope Javadoc correction, applied
below. No migration, contract, dependency, threshold, exclusion or protected file was
changed. All data is synthetic.

Evidence provenance: **tool** commands run by this worker (listed below), plus a
**simulated reviewer** report when it arrives. No human, clinical or patient-participant
evidence. No PHI or credential appears in any note, log or test.

## Findings

- **Fixed this pass:** an explicit `EXPIRED` status now ends disclosure immediately,
  even while the manifest object is still present between `markExpired` and
  `objects.expire`, and even when the 24-hour retention instant has not passed. The
  time-based check remains as the backstop for jobs nobody explicitly expired.
- **Why the domain type owns the rule:** `expired(Instant)` is the single predicate
  `TenantExportService.download` uses to decide disclosure. Putting the status check
  there keeps one source of truth and avoids duplicating the rule in the controller or
  service, where a second caller could forget it. Confirmed by the simulated reviewer.
- **Residual expiry-cleanup gap (F2, pre-existing, separate task requested):** a job
  whose row was marked `EXPIRED` but whose object removal failed cannot be cleaned by a
  retry, because `JdbcExportStore.markExpired` is a `status='COMPLETE'` compare-and-set
  and a second call returns false. Not a disclosure risk after this fix; a cleanup
  correctness gap. `TenantExportServiceTest.anInterruptedExpiryCanBeRetriedToCompletion`
  covers only the opposite interruption (object gone, row still COMPLETE).
- **Find→read TOCTOU (F3, pre-existing, deferred):** an expire landing between
  `findJob` and `getVerified` in `download()` can still disclose bytes. Requires a
  post-read status re-check or a shared transaction; out of scope for this fix.
- **Contract debt (out of scope):** the three export routes are baselined in
  `contracts/openapi/missing-routes.txt`, not published in `contracts/openapi.yaml` or
  the generated staff-web client. Route parity is green; generated clients still cannot
  call them. Publishing is outside BUILD-41's declared scope and was requested in
  earlier passes' notes. `missing-routes.txt` is also flagged by `worker_gate` as a
  scope deviation when `STORY_BODY` supplies the declared scope — an owner reconciliation.
- **No automatic expiry (out of scope):** nothing schedules `TenantExportService.expire`;
  after `expiresAt`, downloads are refused (410) but the object remains until the
  explicit expire endpoint is called. Retention automation belongs in BUILD-42.
- **Environment only (verified by tool, pre-existing on main):** the six

## Lessons for workers

- When a durability fix reorders two side effects (mark the row, then remove the
  object), re-check every read path for the new intermediate state. Here the mark-first
  ordering made expiry retriable but opened a disclosure window that the read gate did
  not cover.
- Put a disclosure predicate next to the value it guards: a single `expired(Instant)`
  on `ExportJob` prevents the controller, service and any future caller from disagreeing
  about what "expired" means.
- A test must assert the observable outcome, not just the exception type. The new
  service test also asserts the object is still present and that no `EXPORT_DOWNLOAD`
  audit was appended, so a false pass caused by a missing object cannot satisfy it.
- In this cloud worker `opencode.json` is a CI profile under `skip-worktree`; compare
  with `.github/opencode.ci.json` and `git show HEAD:opencode.json` before believing a
  check-pack failure. Never regenerate or commit that file.
- Verify a "failing" gate reproduces on a clean reports directory before treating it as
  caused by the current branch: the `test_worker_gate` errors disappear once Maven has
  written `apps/api/target/surefire-reports`.
