# SPEC-CLN-04-C01 — CLN-04 clause 1 API test

## Summary

Added one new integration test class and one clause-evidence document. No
production code, existing test, contract or migration was changed. CLN-04
clause 1 is already implemented in the `clinical.templates` domain, so the
test proves the clause against real PostgreSQL through the production JDBC
store and marks the status **Proven by tests** (no `@Disabled`). All fixtures
are synthetic; no patient data or credential is present.

## Findings

- `JdbcTemplateStore.addVersion` (apps/api/src/main/java/com/aurevia/smartclinic/clinical/templates/JdbcTemplateStore.java:178-188)
  with `V80__template_store.sql:28-34` allocates the first durable version as
  **2**, while `InMemoryTemplateStore.addVersion` (line 59-70) starts at **1**.
  A test that assumes version 1 passes with the in-memory fake but fails
  against the production store. This clause does not mandate a starting number,
  so the test is store-agnostic; a later task should decide whether the
  discrepancy is intentional (V87 baseline version 1 reserved) and align the
  fake or the sequence, plus a task to adopt the baseline catalog into tenant
  version one if that is the intended workflow.
- `InMemoryTemplateStore` lives in `src/main` even though AGENTS.md requires
  in-memory fakes under `src/test`. Pre-existing, out of scope here (would be a
  production/wiring change).
- No HTTP controller exposes `TemplateService.defineVersion`/`approveVersion`/
  `effective`/`history`; only CLN-05 `ClinicalNoteController` is an HTTP adapter
  in this area. The clause is proven at the domain-service boundary with the
  production JDBC store; publishing a definition API would be a separate story.
- `git grep -nE '^(<<<<<<<|>>>>>>>) '` reports 6 conflict-marker lines in three
  HL7 Javadoc files (`exchange/hl7/Hl7ParseException.java`, `Hl7Parser.java`,
  `Hl7Segment.java`) already committed in HEAD. They are inside comments, so
  compilation and the gates pass; they are pre-existing and outside this task's

- Environment-only: `check-pack.py` / six `test_check_pack` failures are the

  (OPS-CW-003-01). No protected file was edited.

## Lessons for workers

- Before asserting a version number against a durable store, take it from the
  command result: the in-memory fake and the JDBC sequence can start at
  different numbers. The clause rarely prescribes the number.
- Give each integration test its own random organization when the domain keeps
  per-tenant version histories; a fixed tenant makes test order change the
  result (history length, "no row left behind" assertions).
- A `@SpringBootTest` integration test on a shared module DB must drop and
  recreate its own database in `@BeforeAll` and seed fresh tenants in
  `@BeforeEach`; bind `TenantContext` and run through `TransactionTemplate` so
  forced RLS resolves the same organization as in production.
- When `scripts/check.sh` stops at the known `opencode.json` staleness, confirm
  once with `git ls-files -v opencode.json` and run the remaining stages
  individually; do not regenerate or edit that protected file.
