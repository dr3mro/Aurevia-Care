# BUILD-32 — Scheduling: recurrence templates and series booking

## Summary

CLN-01 recurrence templates and atomic series booking. `SeriesRequest` now accepts a
fixed occurrence count **or** an inclusive local `endDate`; occurrences are expanded
from the facility IANA zone as civil dates plus a local clock time, so a daylight-saving
change keeps the local appointment time instead of drifting by an hour. Before any row
is written, every occurrence is checked for overlap on its protected clinician/room
resources inside the one tenant-guarded transaction; the whole series is rejected with
the complete clash list (`409 SERIES_CONFLICT`, message lists every clashing occurrence).
A new V86 migration stores the template, series and immutable occurrence index; each
edited appointment still keeps its `appointment_event` history, including the original
planned start in `series_occurrence`.

## Affected requirements

- CLN-01 — facility time zone, protected resources, recurrence templates, transactional
  overlap, atomic reschedule with retained history.
- ARC-01/ARC-02/OPS-02 — tenant-owned tables with `(organization_id, id)` keys, forced
  RLS, append-only rows and audit in the same transaction (see V86 header).

Risk class: cross-boundary (domain service + JDBC repository + new migration); no new
external contract. Route: `aurevia-senior-backend`, `aurevia-senior-database`,
`aurevia-senior-java-build`, `aurevia-test-engineer` (all skills loaded).

## Data changes

`db/migrations/V86__recurrence_templates.sql` (`Change: expand`, reserved version V86):
three additive tables `recurrence_template`, `appointment_series`, `series_occurrence`.
Each has `organization_id`, composite PK, FORCE RLS + `app_org()` policy, append-only
UPDATE/DELETE/TRUNCATE triggers for every role, and SELECT/INSERT granted only to
`aurevia_app`. No backfill, no UPDATE of existing rows, no destructive DDL; locks are
bounded by table creation. Rollback is a forward-fix migration; no capability is removed.

## Authorization boundaries and audit events

Authorization is re-checked inside the transaction with `APPOINTMENT_BOOK` via the
existing `AppointmentService.authorize` (active membership + role). All identifiers come
from `Synthetic X-Synthetic-Subject` / `X-Active-Organization` (synthetic-auth profile)
and forced RLS; no caller-supplied organization, author or version. New audit event:
`SERIES_BOOK` on success (scope `SCHEDULING`, resource `APPOINTMENT`); denials reuse the
existing `APPOINTMENT_BOOK/DENIED` audit. History events are written by the existing
trigger-derived actor. All fixtures are synthetic (ORG A/B share local codes).

## Migration and rollout considerations

`db/check.sh` applied all migrations in version order and passed the general
FORCE-RLS/policy catalog checks on the new tables. Integration tests migrated a fresh
database with the `aurevia_migrate` role and exercised the runtime role through HTTP.

## Findings

- The worktree `opencode.json` is the CI profile copied under `skip-worktree`, so
  `scripts/check-pack.py` and three `scripts/tests/test_check_pack.py` cases fail with
  "opencode.json is stale" while `git show HEAD:opencode.json` differs from the worktree
  copy. This is the documented OPS-CW-003-01 measurement artifact, not a change from this
  story (no agent/skill file was touched). The integrator's clean checkout uses the
  committed local profile, so the gate is green there. I did not regenerate or edit it.
- `scripts/check-wiring.py` printed only stale-baseline notes for already-fixed files;
  no new `unreferenced-service`, `store-without-durable`, `inmemory-in-main`,
  `controller-builds`, `fb-suppression` or requirement-ID name was introduced. No new
  `*Service`/`*Store` class was added, so wiring stays inside the existing
  controller → injected service → JDBC repository chain.
- The two competing-series test uses half-open slot ranges deliberately: an overlapping
  start (13:15Z) clashes, an adjacent one (13:30Z) does not.

## Lessons for workers

- Integration tests in one class share a database; give each scenario distinct dates or
  an earlier successful series will make later ones fail with `SERIES_CONFLICT`.
- `AppointmentView` is nested (`{"appointment": {...}, "history": [...]}`); assert nested
  fields when checking reschedule history over HTTP.
- `scripts/check-pack.py`/`test_check_pack.py` staleness under `skip-worktree` is a known
  false positive in this worker environment — verify with `git ls-files -v opencode.json`
  and `git show HEAD:opencode.json` before treating it as your defect.
