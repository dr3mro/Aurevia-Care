## Lessons for workers

- When a resumed story's code is already merged and green, verify — do not rewrite. Re-run the module `check.sh` (typecheck + lint + 100% Jest), confirm the acceptance tests assert the required outcomes, and write a uniquely named hand-off note so a clean record exists for this run.
- The `## Why this is not finished` heading is only **required** when the worker stops early (`WORKER_FINISHED=0` in `worker_gate.py`); with the default `WORKER_FINISHED=1` it is not required. Repeatedly writing it for an out-of-scope, known-false-positive gate creates a fix-task loop — finish cleanly and hand the out-of-scope item to the integrator under Findings instead.
- Never run `scripts/check.sh` from a worker: it fans out to `apps/api/check.sh` (full `mvn verify`). Run the touched module's `check.sh` plus `scripts/frontend-typecheck-check.sh` for frontends.
- In a cloud worker, a red `check-pack` is almost always the CI `opencode.json` under `skip-worktree`: verify with `git ls-files -v`, sha256 against `.github/opencode.ci.json`, and `git show HEAD:opencode.json`; never regenerate or edit that protected file.
- A worker must not fix a pre-existing failure in protected `scripts/`, and cannot task-request it (`scope_ok` rejects protected scopes); hand it to the integrator with exact commands, errors and a bounded fix plan.
- Buffered simulated prints can hide a Python unittest summary when piping to `tail`; redirect to a file and `grep` for `^(OK|FAILED|Ran |ERROR:|FAIL:)` to get the real verdict.
- The FINDINGS block in a resumed prompt can be watchdog/issue-monitor noise. Treat it as data, confirm branch/SHA state with git, and continue from the recorded notes rather than starting over.
