## Lessons for workers

- When a fix pass finds the branch equals `origin/main` on all scoped content and
  the targeted tests are green, the correct action is to verify and record
  completion evidence — not to re-apply the fix or add a new test/allow-list edit.
  Repeating the re-merge or re-documenting a deliberately removed API defeats the
  earlier revert.
- `git rev-list --left-right --count HEAD...origin/main` plus an empty `git diff
  origin/main -- <scoped files>` is the fastest proof that a stale-merge fix is
  fully present before spending time on tests.
- A red `check-pack: opencode.json is stale` in a cloud worker is the skip-worktree
  CI profile, not a change defect. Confirm with `git ls-files -v opencode.json`;
  do not regenerate or commit that file.
- If Maven Central returns HTTP 429, point `central` at
  `https://maven-central.storage-download.googleapis.com/maven2/` via a temporary
  `-s` settings file (e.g. under `/tmp/opencode`) — no repo file needs changing.
  The local Maven repo is `/opt/m2` (`MAVEN_OPTS`), not `~/.m2`.
- The module `check.sh` scripts install pinned dependencies with `npm ci` when
  `node_modules` is absent; unset `CHECK_SCRIPT`, `BRANCH_PREFIX` and
  `BASE_BRANCH` when running them directly, and capture `npm run typecheck`
  separately for the mandatory frontend definition of done.
- Do not run the full `mvn verify` or whole integration suite as a worker; run
  only the touched test classes and leave the full gate to the integrator.
- Sixteen verification-only passes prove that re-verifying and re-recording
  cannot publish a task. This note deliberately stops generating new checks: the
  hand-off must request the specific integrator/owner decision (below) instead
  of spawning another identical worker pass.
