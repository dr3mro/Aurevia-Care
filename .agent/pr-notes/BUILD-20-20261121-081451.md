# BUILD-20 — Patient app: released reports with revision and per-download authorization

## Summary

PAT-02 already had the report list, correction context, OS-backed credential storage and
user-intent confirmation in `apps/patient-mobile/src/features/reports`. The missing property was
that a download authorization was only bound to the report id and revision. This change binds every
download to the authenticated patient and to a still-current release: the client is constructed for
one patient, and each server authorization must carry a matching `patientId` and a `releaseState` of
`current` before any document reference is produced. A withdrawn release or a wrong-patient
authorization now fails closed with `RELEASE_WITHDRAWN` / `WRONG_PATIENT`.

Scope kept to `apps/patient-mobile/src/features/reports`. No dependency, migration or file outside
scope was changed. Synthetic identifiers only (`report-1`, `patient-1`, `patient-2`, `Clinic A`).

## Affected requirements

- PAT-02 — Show released reports with revision, issuing organization, effective date and correction
  context. Authorize every download against the linked patient and current release. Protect local
  credentials with OS-backed storage. Avoid persistent clinical caches. Confirm user intent for
  saving a local copy.

Acceptance mapping:
- "revision, issuing organization, effective date and correction context" — already implemented in
  `ReleasedReportsScreen.tsx` / `presentation.ts`; proven by `reports-screen.test.tsx`
  `shows revision, issuer, effective date, correction context and language` and
  `report-core.test.ts` `shows correction context only when both parts exist`.
- "Every download checks the linked patient and the current release" — `ReleasedReportClient` is
  bound to one patient and `parseAuthorization` (the single choke point for every
  `authorizeDownload`) checks `patientId` and `releaseState`.
- "a withdrawn release stops access" — `releaseState === 'withdrawn'` throws `RELEASE_WITHDRAWN`;
  no `DownloadAuthorization` is returned.
- Tests "withdrawn release", "wrong patient", "corrected report shows its context" — all present
  (see Test evidence).

## Risk class

Safety-critical (docs/WORKFLOW.md): patient-link / access authorization on a clinical document
download. Defensive, fail-closed behavior; the server remains the authority for the release and
patient link. No real clinical or patient sign-off was obtained — simulated engineering review only.

## Review owner

Primary agent (integrator). Bounded specialist review requested from `smartclinic-senior-mobile`.
No human clinical or privacy reviewer participated.

## Data changes

None. No database migration, backfill, lock or volume impact; no rollback needed.

## Authorization boundaries and audit events

- Client-side defense in depth only: the server still owns the verified patient link and the
  current-release decision. The client refuses to emit a document reference unless the
  authorization names the patient this client is bound to and reports a current release.
- No new audit events. No patient data in logs, URLs or alert payloads: the native confirmation
  alert carries generic text only (unchanged). Token stays in `expo-secure-store`; no clinical
  cache was introduced.

## Migration and rollout considerations

None beyond the normal patient-app release. Callers composing `ReleasedReportClient` must now pass
the authenticated patient id as the third constructor argument; the only caller in this repository
is the test suite (app composition is outside this task's scope). Failing closed on an unset or
wrong patient id is intentional.

## Clinical and architecture review

A bounded simulated review by `smartclinic-senior-mobile` was completed on the diff (no edits by the
reviewer). It confirmed: every download path runs the new checks; the authorization trust boundary
is sound (all fields narrowed before semantic checks); no new branch is uncovered; TypeScript
strictness is clean. Two findings were raised and are dispositioned under Findings. No clinical
reviewer, privacy auditor or patient participant reviewed this slice. The server-side enforcement of
the patient link and release state is outside this story's scope.

## Findings

- The reports feature already satisfied the display portion of PAT-02; only the per-download
  authorization checks were absent. No production defect was found in existing report code.
- The client cannot independently prove the server's patient link; it can only require that the
  authorization it receives names the patient the client is bound to. This is defense in depth, not
  a replacement for the server's verification.
- **Reviewer Finding 1 (MEDIUM, scope-limited / follow-up required).** `ReleasedReportClient` and
  `confirmAndAuthorizeDownload` still have no production caller. Verified with `grep`: the only
  `new ReleasedReportClient` occurrences are in `report-core.test.ts`; `app/patientPages.tsx:104`
  passes `placeholderAction` as `onDownload` and `loadReports` parses reports directly, bypassing
  the client. Therefore the checks are correct and fully tested *within the feature*, but acceptance
  item #2 is not yet enforced at runtime in the assembled app. Wiring `ReleasedReportsPage` to the
  client with the verified authenticated patient id (and routing reads through it) lives in
  `apps/patient-mobile/src/app/`, outside BUILD-20's declared scope, so no change was made here.
  READY-48 deliberately left the download flow unwired. **Next step:** a separate wiring story in
  `app/` must connect the page before PAT-02 can be claimed runtime-complete; the integrator/owner
  should decide whether to accept this story as the feature-level slice only.
- **Reviewer Finding 2 (LOW, fixed).** `patientId` was an unvalidated free constructor argument, so
  a blank id would make the WRONG_PATIENT check meaningless. Added a non-blank guard that throws
  `INVALID_PATIENT`, with a covering test. Provenance from a verified session remains an
  app-composition concern (Finding 1).
- **Environment artifact (not caused by this change).** `python3 -I scripts/check-pack.py` and 3
  tests in `python3 -I -m unittest discover -s scripts/tests` fail with
  `opencode.json is stale / out of date`. Verified `git status` shows `opencode.json` unchanged at
  HEAD with the `S` (skip-worktree) flag — it is the CI profile copied by `agent-run.sh`. MEMORY.md
  records this as a known cloud-worker false positive. The protected file was not regenerated or
  edited (outside scope). The other safe policy checks passed: `check-docs.py`, `check-secrets.py`,
  `check-names.py`, `check-wiring.py`, `check-migrations.py --require-baseline`, and
  `bash scripts/frontend-check.sh` (prettier + vitest green). `scripts/check.sh` was not run because
  it invokes the full `mvn verify` (>10 min, explicitly forbidden for workers); the canonical
  `bash apps/patient-mobile/check.sh` gate was run instead and is green.

## Lessons for workers

- Reuse the established patient-app pattern (see `features/acknowledgments/client.ts`): bind the
  client to the authenticated patient id and fail closed on patient/release mismatch, rather than
  trusting a well-formed server payload.
- In this module `types.ts` files are type-only and show `0 | 0 | 0 | 0` in coverage; that is normal
  and does not affect the 100% global gate.
- Keep new authorization checks at a single parse choke point so every download path is covered by
  one branch table.
