# FIX-OPENAPI-01 (fix pass) — Gate controller routes against the OpenAPI contract

## Summary

Added a build-failing route-parity gate plus a shrinking baseline. One test utility and
one unit-test class prove the gate logic with synthetic handler sets; one Spring-context
test enumerates every real route from `RequestMappingHandlerMapping` and compares it to
the authoritative `contracts/openapi.yaml`. `contracts/openapi/missing-routes.txt`
records the 313 routes currently absent from the contract (one `METHOD /path` per line,
sorted, path variables normalised to `{}`). No production code, controller, contract,
migration, dependency, threshold or exclusion was changed. All evidence is from executed
tools and synthetic fixtures; no simulated user or human participant was involved.

**Contract choice (important deviation, with evidence).** The story's problem text names
`contracts/openapi/generated/openapi.yaml`; that file is the X-04 *command catalogue*
output. Parsing both documents with a method/path parser and comparing to the 340 live
Spring routes gave: `contracts/openapi.yaml` 27/27 routes backed by a controller, **0
ghosts**; the X-04 generated catalogue 24 routes, only 13 backed by a controller and
**11 intentionally virtual command routes with no controller** (its own README says
"This slice adds no route, controller, database table or migration" and that it does not
prove documented paths match deployed routes). Gating against the catalogue could never
be green because a contract route with no controller is a required failure. The gate
therefore reads the hand-authored staff-API contract `contracts/openapi.yaml`, confirmed
as authoritative by `apps/staff-web/scripts/gen-api-types.sh:7`
(`spec=../../contracts/openapi.yaml`) and by prior notes `START-09-fix-20261121-171839.md`
and `AUD-20261121-24-20261121-203628.md`. Integrator/owner should confirm this reading of
the story; it is the only option consistent with a green, shrinking baseline.

Baseline generation: 340 live routes − 27 documented = 313 missing. One of the 313 is
`ANY /error`, Spring's method-less `BasicErrorController` fallback; it is retained
explicitly rather than silently dropped. The contract regeneration command is
`cd apps/staff-web && npm run gen:api` (the generated `openapi.d.ts` is never hand-edited).

## Findings

1. **Story names the wrong contract file.** `contracts/openapi/generated/openapi.yaml` is
   the X-04 command catalogue (24 routes, 11 virtual, no controllers). The authoritative
   staff-API contract is `contracts/openapi.yaml` (27 routes, all with controllers). The
   gate uses the latter; evidence and rationale are in Summary. The next worker/integrator
   should confirm this interpretation before FIX-OPENAPI-02..04 proceed against the baseline.
2. **`worker-check.sh` could not complete (`check-pack: opencode.json is stale`).** Verified
   as the known cloud-worker artifact: `git ls-files -v opencode.json` → `S` (skip-worktree);
   `git show HEAD:opencode.json | sha256sum` = `0dc2ac8e…`, worktree = `50005c9c…`; 5 of the
   7 remaining Python failures are `test_check_pack` cases for the same reason. Out of scope
   (worker rules forbid editing `opencode.json`, `.opencode/` and `scripts/`); recorded as
   `OPS-CW-003-01` in MEMORY.md. Exact next step: integrator evaluates the committed HEAD
   profile, not the skip-worktree worktree copy, then re-runs the full gate.
3. **Pre-existing duplicate migration V91.** `V91__service_profiles.sql` and
   `V91__staff_messaging.sql` both exist; `check-migrations.py --require-baseline` and two
   Python tests fail. Parallel-worker artifact; no migration was touched here. The owning
   story must renumber one of them before the full gate is green.
4. **One pre-existing tracker-format Python failure** prints
   `{"violations": [{"file": "TODO.md", "rule": "tracker"}]}`; caused by concurrent tracker
   edits, outside this worker's allowed files.
5. **`@Tag("integration")` is mandatory for this test.** `scripts/tests/test_fast_tier.py`
   requires it for any `@SpringBootTest`; without it `python3 -I -m unittest discover -s
   scripts/tests` failed on `test_db_tests_carry_the_integration_tag`. Consequence: the gate
   runs in the integration/full tier (`worker-check.sh -Dgroups=integration`, `mvn verify`),
   not in the DB-less fast tier. The unit-level `OpenApiRouteCoverageTest` still runs fast.

## Lessons for workers

- Before gating routes, verify which OpenAPI file is authoritative: the X-04 generated
  catalogue is a command model with virtual routes, while `contracts/openapi.yaml` is the
  staff-API contract consumed by `gen-api-types.sh`. Comparing against the catalogue yields
  11 permanent ghost failures.
- Use `RequestMappingHandlerMapping.getHandlerMethods()` for route enumeration; a source
  grep misses inherited mappings and cannot express path templates.
- `scripts/tests/test_fast_tier.py` fails any test containing `@SpringBootTest` unless it
  carries `@Tag("integration")` — add the tag first, then run `-Dgroups=integration` for a
  single-class check.
- In a cloud worker, `opencode.json` is a CI profile under `skip-worktree`; `check-pack` and
  five `test_check_pack` cases fail on that artifact, not on your change. Check
  `git ls-files -v opencode.json` before investigating.
- Normalise `{variable}` names to `{}` before comparing controller templates with contract
  paths; controllers and contracts use different placeholder names for the same route.

the required whole-worker gate could not be taken to green in this environment:

  `check-pack: opencode.json is stale: run scripts/gen-opencode.py`. It stops before

  passed where runnable).

  `50005c9c…` differs from the committed HEAD SHA `0dc2ac8e…`, so `gen-opencode.py --check`
  and `check-pack.py` judge the wrong profile. Five of the seven remaining Python unit
  failures are the same artifact; the other two are a pre-existing duplicate migration
  version `V91` from parallel work. None is caused by this change.
- **What was tried:** verified the worktree is clean apart from the three intended new
  paths; compared HEAD and worktree hashes; ran every later gate step individually
  (`frontend-check.sh` exit 0, SpotBugs exit 0, full fast unit tier exit 0, `check-docs`,
  `check-secrets`, `check-names`, `check-wiring` exit 0, `test_fast_tier.py` 4/4 OK); added
  `@Tag("integration")` to clear the one policy failure caused by this change.
- **Exact next step:** in the integrator environment, evaluate `git show HEAD:opencode.json`
  rather than the skip-worktree worktree copy (or restore the committed profile) and re-run
