## Lessons for workers

- When a story is re-dispatched many times, one clean verification pass is enough — spend the next pass obtaining the *automation* evidence (PR title, labels, exact check-run verdicts, and the gate/tracker conditions in `scripts/swarm.py`). Here that evidence shows a stale `needs-fix` label, not a failing check.
- Trace who is supposed to remove a blocking label. If the success path that would clear it is gated behind the label itself — as `plan_integration` gating behind `needs-fix` is — it is a deadlock only a trusted integrator/owner can break.
- Recommitting the same notes cannot change a label and re-triggers the same wave. State the single exact trusted next step and stop; do not add another no-op re-verification beyond confirming current state.
- When two workers implement the same story, survey `main` and all prior notes first: keep what already landed, contribute only the missing slice (here the HTTP entry-point test), and on conflict adopt the base file when it already carries equivalent coverage.
- In cloud workers `opencode.json` is skip-worktree (`S`) with the CI profile; compare `git show HEAD:opencode.json` with the generator before treating `check-pack.py` "stale" failures as yours.
- Do not run `scripts/check.sh`, `scripts/coverage-check.sh` (full `mvn verify`), `apps/api/check.sh` or `scripts/docs.sh` as a worker; the full PostgreSQL/static-analysis/documentation gate is reserved for the integrator/Delivery.
