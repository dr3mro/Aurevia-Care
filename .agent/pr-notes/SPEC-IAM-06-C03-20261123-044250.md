## Summary

Test-only proof of SmartClinic V1 requirement IAM-06 clause 3, "It cannot unlock
other organizations’ data." One new real-PostgreSQL `synthetic-auth` acceptance
class drives the emergency-access HTTP routes with two synthetic tenants and reads
the authoritative organization back from the grant and review tables. A new clause
document records the exact sentence, status, evidence and gap. No production code,
existing test, contract, migration, tracker, script or workflow was changed.

## Affected requirements

IAM-06 — emergency access is limited to qualified clinicians, scoped inside their
own organization, alerted and reviewed; it cannot unlock another organization's data.

## Authorization boundaries and audit events

Boundary under test: the active organization from `X-Active-Organization` is bound
into `TenantContext` by `TenantContextInterceptor`; the grant command carries only
facility, reason and duration, so no client field can name an organization.
Assertions cover a qualified clinician in the owning organization, the same
clinician entitled in a second organization (RLS must conceal the foreign grant),
a wrong role (403), and malformed or out-of-organization input (422/404).
The test asserts a committed `EMERGENCY_GRANT` / `DENIED` / `EMERGENCY_ACCESS`
audit row carrying the request's unique correlation id for the wrong-role refusal.
No audit event was added or changed in production.

## Lessons for workers

- Under `synthetic-auth`, `TenantContextInterceptor` does not verify organization membership. To prove tenant isolation, seed the SAME subject as an active clinician in both tenants and read the authoritative grant/review rows under each `app.current_org`; a different foreign subject can make `NO_GRANT` pass even without RLS.
- The emergency grant HTTP projection has no organization field. Assert `organization_id` directly on `emergency_access_grant` and `emergency_access_review` with a NOBYPASSRLS role and an explicit `app.current_org`, and keep an owner-tenant positive control beside every cross-tenant zero count.
- For an ID-based clause-proof story, a test-only two-tenant proof is sufficient when the clause is already implemented; do not add production code or an `@Disabled` GAP test just to look thorough.
- In a cloud worker, `bash scripts/worker-check.sh` stops on the stale `opencode.json` profile before the Java stages. Run the targeted `-Dtest=...` suite, compiled SpotBugs, `check-docs.py` and the individual policy scripts yourself; leave the full gate to the integrator.
