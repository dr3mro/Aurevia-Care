# START-06 · Docs: data dictionary built from the migrations

## Summary

Added `docs/reference/data-dictionary.md`: a data dictionary derived from every table created by the 40 Flyway migration files present in `db/migrations` (V1 through V90). It covers 126 tables grouped into 12 business areas. For each table it records a one-line purpose, every column with its type and meaning, keys and constraints, tenant-isolation/write policy (append-only, bounded UPDATE or read-only) and the migration that created or last changed it. The newest covered version (V90) is stated at the top. Fifteen genuinely unclear columns are marked `UNCLEAR:` with a question rather than a guess. No other file was changed; `docs/reference/index.md` was left untouched as required (START-18 links this page).

## Lessons for workers

- Verify a data dictionary mechanically: extract `CREATE TABLE public.<name>` from every migration and diff against the `### \`<name>\`` section headings. A 126-table manual pass can silently miss one; the regex will not. Ignore "CREATE TABLE on ..." style comments.
- `bash scripts/check.sh` and `test_check_pack` fail in cloud workers on the skip-worktree CI-profile `opencode.json`. Confirm with `git ls-files -v opencode.json` and `git show HEAD:opencode.json`, record it as an environment artifact and do not regenerate or edit that file inside a scoped story.
- The offline `db/check.sh` glob apply order differs from Flyway numeric order; many two-digit migrations guard DDL with `to_regclass(...)` and `RAISE NOTICE … RETURN`. Mention this when documenting migrations so readers do not misread the guard as a skipped table.
- `scripts/check-docs.py` only validates prefixes defined in the spec; IDs such as PAT-01/UX-01 are not checked. Still cite only defined IDs in a new page.
