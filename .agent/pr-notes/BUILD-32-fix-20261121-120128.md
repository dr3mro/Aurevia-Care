# BUILD-32 (fix pass) — Scheduling: recurrence templates and series booking

## Summary

Second fix/verification pass for BUILD-32 (CLN-01), continuing from the prior fix pass
`.agent/pr-notes/BUILD-32-fix-20261121-114253.md`. The implementation is already committed
on this branch in `28ba333` ("CLN-01 recurrence templates and atomic series booking");
**no production defect was found in this pass and no production code was changed.**
`SeriesRequest` accepts a fixed occurrence count or an inclusive local `endDate`.
`RecurrenceTemplate` expands occurrences from the facility IANA zone as civil dates plus a
local clock time, so a daylight-saving change keeps the local appointment time.
`AppointmentService.bookSeries` checks every occurrence for overlap on its protected
clinician/room resources inside one tenant-guarded transaction and rejects the whole series
with the complete clash list (`409 SERIES_CONFLICT`) before any row is written. V86 stores the
template, series and immutable occurrence index; editing one occurrence keeps its
`appointment_event` history and the original planned start in `series_occurrence`.

## Data changes

`db/migrations/V86__recurrence_templates.sql` (reserved version V86, `Change: expand`):
three additive tables `recurrence_template`, `appointment_series`, `series_occurrence`.
Each has `organization_id`, a composite PK including it, `created_at`, ENABLE + FORCE RLS and
a policy `USING/WITH CHECK (organization_id = public.app_org())`. Append-only reject-mutation
triggers for `UPDATE`, `DELETE` and `TRUNCATE` cover every role including the migration owner;
SELECT/INSERT are granted only to `orevia_app` and UPDATE/DELETE/TRUNCATE revoked.
No backfill, no UPDATE of existing rows, no destructive DDL; brief ACCESS EXCLUSIVE locks are
bounded by table creation. Rollback is a forward-fix migration; no capability is removed.
No migration was added or edited in this pass.

## Lessons for workers

- To reach 100% on a large touched class, run the full unit suite plus every integration test
  that exercises its pre-existing paths. A 3-class or even a 130-class unit subset leaves
  `AppointmentService`/`AppointmentRepository` branches uncovered; adding
  `SeriesHttpIntegrationTest`, `AppointmentListIntegrationTest` and especially
  `it/SchedulingBookingTest` closes the gap. Always re-read the JaCoCo XML and confirm
  `missed == 0` on each changed class before claiming 100%.
- JaCoCo counters print as `missed/total`, not `covered/total`; a line like `1/4` is a MISSED
  branch, not 25% coverage. Parse `mi`/`ci`/`mb`/`cb` directly to avoid this trap.
- `scripts/check-pack.py`/`test_check_pack.py` staleness under `skip-worktree` is a known false
  positive in this worker environment — verify with `git ls-files -v opencode.json` and
  `git show HEAD:opencode.json` before treating it as your defect.
- Integration tests in one class share a database; give each scenario distinct dates or an
  earlier successful series will make later ones fail with `SERIES_CONFLICT`.
- `AppointmentView` is nested (`{"appointment": {...}, "history": [...]}`); assert nested fields
  when checking reschedule history over HTTP.
- The generic "frontend definition of done" block in the swarm prompt applies only when the
  story touches a frontend module; for a backend-only scope, state that explicitly rather than
  installing toolchains or fabricating typecheck evidence.
