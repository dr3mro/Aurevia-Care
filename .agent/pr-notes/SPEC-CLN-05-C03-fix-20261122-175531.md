## Lessons for workers

- When a fix pass is notes-only, the persisting gate failure can be solely the missing
  `## Review verdicts` section: `scripts/check-verdicts.py:75-77` fails closed when the section is
  absent and a non-docs file (here the scoped `.java` test) is in the diff against the base. Run the
  three required read-only reviewers and copy their exact `orevia-` prefixed GO lines into that
  section as the last `##` section of the notes.
- Before trusting a red integration run on a swarm branch, run the targeted `-Dtest=ClassName`
  command and read the first error. A `testCompile` failure in an unrelated class may be an
  inherited `main` break already fixed by a later upstream commit; check whether the fix commit is
  an ancestor of HEAD (`git merge-base --is-ancestor <sha> HEAD`) before re-filing a task request.
- Do not run full `mvn verify` in a swarm worker: run the targeted test plus individual policy
  scripts and standalone SpotBugs (`-DskipTests compile spotbugs:check`), and leave the full gate
  and JaCoCo 1.00 check to the integrator. A bare `spotbugs:check` without compile is vacuously green.
- In a cloud worker, `git ls-files -v opencode.json` showing `S` explains `check-pack.py` and
  `test_check_pack.py` failures: verify with `git show HEAD:opencode.json` and never regenerate or
  commit that protected file.
