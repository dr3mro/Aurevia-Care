# START-01 — Staff web: English and Arabic message parity test across every feature

## Summary

Added one new Vitest file, `apps/staff-web/tests/messageParity.test.ts`, that loads every
English/Arabic bundle in `apps/staff-web/src` and checks key parity, non-empty values,
placeholder parity in both directions, and an Arabic letter in every Arabic value (with a
justified allow list). A filesystem glob guard fails when a newly added bundle file is not
registered. Broken sample bundles written inside the test prove each rule fails with a
diagnostic naming the bundle and the key. No production file, bundle, threshold, config or
dependency was changed.

  placeholders; §9.9 requires a test that fails when a key is added to one bundle only.
  This story adds that executable check across all staff-web bundles.

## Findings

1. **Real gap, allow-listed:** `admin.utcLabel` is `UTC` in both bundles
   (`src/features/admin/messages.ts` lines 273 and 406). It has no Arabic letter, so the
   checker reports it. It is allow-listed as `admin.utcLabel` with
   `// TODO fix in a separate task` and a justification that UTC is an ISO time-zone code
   quoted verbatim in both locales. No bundle was changed.
2. **Bundles beyond the story's example list:** `src/app/navigation.ts` (`navigationLabels`)
   and `src/app/shellText.ts` (`shellLabels`) also hold `en`/`ar` records. They are included
   so the test really covers every bilingual bundle under `src`, not only the enumerated
   examples. No gaps were found in them.
3. **Bundles with private records:** `admin`, `chart` and `scheduling` do not export their
   locale records; the test uses their exported `keys` arrays and `*Text(locale, key)`
   accessors. A key present in only one internal record is therefore observed as an
   undefined value and reported as empty rather than by comparing exported key arrays.
4. **Pre-existing environment artifact:** repo-root `scripts/check.sh` and three
   `test_check_pack` cases fail on the skip-worktree `opencode.json` CI profile. Verified as
   unrelated by `git ls-files -v` and an empty tracked diff; left untouched because workers
   must not edit generated config.
5. **Specialist review (MEDIUM) — discovery test was tautological:** it compared two
   hardcoded lists in the same file. Replaced with a real `import.meta.glob` filesystem
   guard over `**/messages.ts`, `**/stateViewMessages.ts`, `app/navigation.ts` and
   `app/shellText.ts`; probe-verified to fail on a new bundle file. The repo's own
   `ImportMeta.glob` declaration in `src/app/routes.tsx` is used with `{ eager: true }`
   instead of adding a conflicting `vite/client` types reference.
6. **Specialist review (LOW) — Arabic-letter regex was too broad:** `/[\u0600-\u06FF]/`
   also accepts Arabic-Indic digits and punctuation. Narrowed to Arabic letter ranges and
   added a digits-only negative test. No real bundle value changed classification.
7. No production defect was found. No test was skipped, disabled or weakened.

## Lessons for workers

- Locate bundles by searching for `en:` / `ar:` records under `src`, not only by file name:
  `app/navigation.ts` and `app/shellText.ts` are real bundles that a name-based search misses.
- Three feature bundles keep their records private and expose only `keys` plus a `*Text`
  accessor; reconstruct the bundle from those exports instead of trying to import the record.
- Under `noUncheckedIndexedAccess`, prefer `match[0].slice(1, -1)` over `match[1]` plus an
  undefined guard when parsing regex placeholders: the guard is a branch no input can take.
- In a cloud worker, `git ls-files -v opencode.json` showing `S` explains a stale-pack check
  failure; record it as an environment artifact instead of regenerating protected config.
- A registry test that compares two hardcoded lists proves nothing; glob the filesystem and
  assert the discovered paths match the registry. This repo declares `ImportMeta.glob`
  itself in `src/app/routes.tsx`, so do not add a `vite/client` types reference (duplicate
  declaration errors); call `import.meta.glob(pattern, { eager: true })`.
- For "contains an Arabic letter", use explicit Arabic letter ranges, not the whole
  `0600–06FF` block, which also matches digits and punctuation.
