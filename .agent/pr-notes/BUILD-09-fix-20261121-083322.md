## Summary

Follow-up fix for the blocking clinical-safety finding from the physician reviewer: the market-approved route on the catalog item was returned by versioned search but was not enforced when a prescriber selected a medication. Selection now rejects a requested route that contradicts the catalog's declared route (`422 ROUTE_MISMATCH`). Legacy entries whose route is the V76 sentinel `unspecified` remain selectable under the existing clinical workflow.

Unchanged: same tenant/role fold, action keys and audit path. A route mismatch is a business validation failure raised in the existing transactional command, so no medication, override or audit success is recorded.

## Migration and rollout considerations

None beyond the original V76. Legacy rows carry `route='unspecified'` and are deliberately exempt from route checking; a real-market rollout must replace the sentinel with approved routes and gate the documented baseline-version fallback off (open item, owner decision).

## Lessons for workers

- A catalog attribute that is only returned to the client is not a control: enforce it at the command boundary (selection), not just in the search projection, when it is clinically safety-relevant.
- When a reviewer finding needs a guard on an existing command, add deterministic unit coverage for both sides of the guard plus one HTTP-level integration assertion that the rejected command persisted nothing.
