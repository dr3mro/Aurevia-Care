# ORDER-01 — API: orderable test and study catalog per facility (versioned)

## Summary

Adds a self-contained, pure domain slice for a per-facility, versioned catalog of orderable laboratory tests and imaging studies, and 26 tests over synthetic fixtures. The catalog is reference data a later order story consumes; it deliberately adds no Spring bean, store, migration or HTTP route because none of those are in this story's scope or reserved-version set.

What already existed (story step 1 survey, tool evidence):

- **G0 `com.aurevia.catalog`**: `CatalogService` (append-only drafts via `ConfigurationService`, effective-version fold, `CATALOG_READ`/`LIST` authorization and OPS-02 audit), `CatalogRepository` (tenant-scoped SQL, `audit_event` append), `CatalogEntry`. A separate versioned-medication fold already exists in the same package: `MedicationCatalog`, `MedicationCatalogItem`, `MedicationCatalogVersion`, `VersionedCatalogSearch` — a **pure class** built from items loaded by `PrescriptionRepository.loadMedicationCatalog()` and invoked by `PrescriptionService.searchCatalogWithVersion()`, exposed by `DrugCatalogController`. `MedicationCatalogVersion.BASELINE` and `DrugCatalog` own the effective-window and version rules. This story mirrors that pure-fold shape.
- **`exchange/order`**: `OrderController`, `OrderService`, `OrderRepository`, `OrderRequest` (already carries `orderCode`, `priority`, `destination`, `purpose`, `authorizationId`, `responsibleClinician`), `OrderInputs.priority()` (the canonical `routine|urgent|stat` 422 validator), `OrderView`, `WorkItemView`. No order currently binds a catalog item id/version; that is the follow-on place-order story (ORDER-02).
- **Lab packages**: `lab/accession` (`LabAccessionService`/`Controller`/`Repository`, `AccessionState`, `LabInputs.specimenType`, `LabAccession` with specimen type/site/collector/rejection/recollection), `lab/result` (`LabObservation`, `ReportRevision`, `LabConversionCatalog`, versioned reference ranges).
- **Imaging packages**: `radiology` (`ImagingService`, `ImagingOrder`, `ImagingController`, `RadTypes` with `Modality`, `Urgency`, `OrderState`, and `RadPolicyCatalog` for effective-dated, approved modality privileges).
- **`contracts/openapi.yaml`**: `/api/v1/catalogs/{family}` family/entry/approve routes exist; there is no orderable-catalog or place-order route yet.

No `orderentry` package existed before this change; all four production files are new.

## Affected requirements

- **LAB-01**: specimen-bearing orderable test definitions (specimen type, preparation, default priority, performing partner) available to a requisition.
- **RAD-01**: modality-bearing orderable study definitions and effective-dated versions.
- **XCH-01**: order code, priority, destination partner and immutable released-version snapshot semantics; a captured version stays renderable.
- Referenced, not claimed: ADM-01 (per-facility catalog administration), ARC-01/ARC-02 (tenant-owned keys and isolation; this fold filters supplied data but is not itself a DB isolation boundary), UX-01 (UTC instants; local presentation is the caller's concern).

## Risk class

Routine for the contained domain code; tenant-scoped query predicates were reviewed as cross-boundary because isolation is a hard gate. No clinical command, disclosure, release or patient data is involved.

## Review owner

Simulated reviews only (no human/clinical participant): `orevia-software-architect` and `orevia-test-engineer` returned bounded read-only findings; all actionable ones were applied (deterministic `resolve` tie-break, duplicate-version rejection, half-open window parity, resolve orderability, explicit scope guards, value-semantics test). The primary agent owns all edits.

## Data changes

None. No Flyway migration, no table, no backfill. No database or lock/volume impact. The catalog is folded over items supplied by the caller (the eventual Jdbc-backed consumer will supply tenant-scoped rows).

## Authorization boundaries and audit events

Every query method requires a non-blank organization id and facility id and an evaluation instant; it filters items by those exact keys. This class folds already tenant-scoped reference data and is **not** a `TenantContext` or RLS boundary — the caller must pass the active organization. No command writes are added, so no OPS-02 audit event is added. No patient data, credential or real identifier appears in code or fixtures.

## Migration and rollout considerations

None in this change. See **Findings** for the documented persistence follow-up.

## Findings

1. **Persistence/HTTP gap is a deliberate scope boundary, not a failed check.** Story scope grants only `orderentry/catalog` main and test paths: no `db/migrations`, no `reserved:` version, no `contracts/openapi.yaml`, no `it` package. The real `MedicationCatalog` is durable (V43 `drug_catalog_entry`, V76 `medication_catalog_version`, `PrescriptionRepository`, `PrescriptionService`, `DrugCatalogController`); this fold has no such backing. `scripts/check-wiring.py` would fail a new `@Service` with no caller or a `*Store` with no Jdbc implementation, and AGENTS.md forbids `InMemory*` in `src/main` — so a fake service/controller with synthetic items would be dishonest and gate-breaking. Keeping the fold pure mirrors the medication catalog and passes the wiring gate. **Follow-up needed (owner/integrator):** give the consuming order story (or a dedicated persistence story) `db/migrations` plus one reserved version for a tenant-owned forced-RLS table and a `JdbcOrderableCatalogStore`, then expose an HTTP entry and add the OpenAPI route and an HTTP-level integration test. Record that decision in PROJECT.md/MEMORY.md by the owning agent; swarm workers must not edit those trackers. The architect reviewer independently flagged this as the blocking DOD item.
2. **Priority and modality validation are shared rules, not new vocabularies.** Default priority reuses `OrderInputs.priority` (XCH-01). Imaging modality membership reuses `RadTypes.Modality.wire()`. Per `RadTypes.Modality` Javadoc, enum membership is structural validation, **not** facility approval; site approval remains ADM-01 configuration and is not claimed here. Lab specimen text is intentionally not run through `LabInputs.specimenType`: that validator guards accession commands, whereas this is bounded reference data and the real specimen is validated at accession (LAB-01); the catalog only requires a non-blank specimen code here.
3. **Effective dating** uses a half-open UTC `Instant` window (`from` inclusive, `to` exclusive), matching `DrugEntry.effectiveAt`. Facility-local "effective on a date" presentation (UX-01) is left to the caller; no IANA zone is stored because none is in scope.
4. **Determinism / integrity:** `resolve` breaks version ties with `effectiveFrom` then `itemId` (no input-order dependence); the constructor rejects duplicate `(org, facility, itemId, version)` and `(org, facility, code, version)` keys.
5. No defects were found in existing code; no existing test or threshold was changed. All reviews were simulated/static (tool-verified files, no reviewer-executed runtime and no human or clinical evidence).

## Lessons for workers

- Before adding a new `@Service` or `*Store`, check whether the task scope actually grants a migration version and an HTTP/OpenAPI entry; if not, mirror an existing pure domain fold (`MedicationCatalog`, `RadPolicyCatalog`) instead of wiring a store that cannot be durable.
- A test helper that hard-codes one local id for several items will trip a correct duplicate-key guard; derive the id from the fixture's business key.
- For JaCoCo 100%, cover the false side of the imaging-kind short-circuit with a lab item whose specimen is not a modality, and reach the `code.contains` branch with a code that is not a substring of the name (`CBC` / `Complete Blood Count`).
- Use a `requireText` helper for repeated null/blank guards: three cases cover every guarded field instead of two per field.
- In this worker image, `git ls-files -v opencode.json` = `S` and `check-pack.py` failure is a known environment artifact (OPS-CW-003-01); do not edit the protected config to "fix" it.
- Never split an integration test's role creation and `CREATE DATABASE ... OWNER` into two `@BeforeAll` methods: JUnit does not order multiple `@BeforeAll` methods, so `prepare()` can run before the roles exist on a fresh cluster. Create the roles inside the same single `@BeforeAll` before the database, as every other integration test does. When a coverage gate reports a test error rather than a missed branch, fix the test determinism rather than hunting for uncovered code.
