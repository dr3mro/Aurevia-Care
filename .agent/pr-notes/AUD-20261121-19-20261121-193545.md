# AUD-20261121-19 — Wire the unreachable document command APIs

## Summary

Chosen outcome: **wire, do not delete**. Added `DocumentArtifactController`, a thin tenant-owned HTTP adapter at `/api/v1/documents/artifacts` that exposes all twelve previously unreachable commands of `QuarantineService` and `PdfBindingService` through the injected domain services and the production `JdbcDocumentStore`. Added an HTTP-level integration test that drives every command through the real controller against a fresh PostgreSQL database with synthetic fixtures. No existing production file was modified; no migration, contract, script or tracker file was touched.

Deleting the services was rejected: it would orphan the 100% coverage of `DocumentContract`, `ArtifactInputs`, `DocumentActions`, `DocumentGuard` and the in-memory/JDBC stores, and would break the open `SPEC-ARC-06-C01/-C02` and `SPEC-CLN-07-*` clause tasks that construct these services. Wiring satisfies the AGENTS.md done bar (injected service → controller → durable store → HTTP test) without changing the domain rules.

## Affected requirements

- ARC-06 — upload validation, private quarantine, scan verdict, mediated download, immutable PDF binding and release gating are now reachable over HTTP.
- CLN-07, IAM-01, IAM-02, OPS-02 — tenant/role derivation and append-only audit facts are reused from `TenantContext`, `StaffRepository.activeRoles`, `DocumentGuard` and the existing V81 tables; no new rule.

## Authorization boundaries and audit events

- Organization and subject come only from `TenantContext` (bound by `TenantContextInterceptor`); roles are re-read on each request from `StaffRepository.activeRoles` inside the tenant-guarded `TransactionTemplate`. No tenant, role or patient binding is read from a request body.
- `actor()` fails closed with 403 `FORBIDDEN` for a `patient` role: `QuarantineService` treats a null `patientId` as "no ownership restriction", and this story has no independently verified subject→patient link source. Patient-facing HTTP self-service is a separate follow-up (task-request below).
- `SourceRevision.organizationId` and `contextId` in bodies remain untrusted: `QuarantineService.upload` re-checks grant activity/tenant/binding and `PdfBindingService.validateRevision` compares against the actor's organization (verified at service level; new routes do not weaken it).
- Audit facts are unchanged: existing `DocumentGuard` records `ACCESS_DENIED` before throwing, and the services emit `UPLOAD_ACCEPTED`, `SCAN_CLEAN`, `SCAN_FAILED`, `UPLOAD_COMPLETED`, `ARTIFACT_REMOVED`, `DOWNLOADED`, `RENDER_*`, `PDF_BOUND`, `RELEASED`/`RELEASE_BLOCKED`. No new event type or audit purpose.

## Migration and rollout considerations

No schema change, lock or volume impact. Rollout is a normal application deploy; deleting the controller removes the routes. Out-of-scope follow-up: publish the twelve routes in the authoritative OpenAPI source and regenerate clients (sequence after `FIX-OPENAPI-01`); there is currently no route/contract gate that fails on an undocumented route.

## Findings

1. **Resolved**: `QuarantineService` and `PdfBindingService` now have a real HTTP caller; `check-wiring.py` emits only "fixed; delete it from baseline" notes for them (baseline intentionally left to the maintainer).
2. **Defect — duplicate dispatch risk**: `TODO.md` also carries `AUD-20261121-24` with the same title and the identical scope (`docs/swarm`/task entry). Two workers wiring the same classes would collide. I did not edit `TODO.md`; the orchestrator should cancel or merge `-24` into `-19`.
3. **Out-of-scope gap**: the twelve new routes are not in `contracts/openapi`. No current gate fails on that, but clients cannot be generated until contract publication lands (task-request below).
4. **Deliberate limitation**: staff-mediated commands only; patient-role principals are refused because no verified subject→patient link source is available in this scope (task-request below).
5. **Environment artifact (not a change defect)**: worktree `opencode.json` is the CI profile under `skip-worktree`, so `check-pack.py` and five `test_check_pack` cases fail locally. Evidence in Test evidence item 6.

## Lessons for workers

- Wrap only `staff.activeRoles(...)` in the tenant-guarded `TransactionTemplate`; wrapping a whole command would join the inner store transactions and roll back the `ACCESS_DENIED` fact that `DocumentGuard` records before throwing.
- Call the tenant-context null guard before any transaction use — `TenantGuardTransactionManager.doBegin` throws when the ThreadLocal is empty, which would turn an unauthenticated direct call into a 500.
- `QuarantineService` treats a null `patientId` as "no ownership restriction"; when no independent subject→patient link is available, fail closed for `patient`-role principals instead of passing a null id.
- The 401 guard is unreachable over HTTP under `synthetic-auth` (the interceptor rejects first); cover it with a direct controller call after `TenantContext.clear()`.
- In the HTTP test, take `objectKey`/`objectVersion` from the `POST` response; `GET /{id}` returns a `View` (nested `artifact`), not the artifact itself.
- A `check-wiring` "note: ... is fixed" is a pass, not a failure — the baseline may only shrink, and this story was told to leave it to the maintainer.
- In cloud workers, `git ls-files -v opencode.json` showing `S` explains local `check-pack` failures; do not regenerate or commit that file.
