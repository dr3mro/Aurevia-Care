# BUILD-30 — Persist released reports and release history with JDBC

## Summary

Extracted `ReportReleaseStore` from the in-memory report-release adapter and added `JdbcReportReleaseStore`, a tenant-guarded Spring JDBC adapter backed by a new V84 migration. A release decision records the immutable revision, release policy version, effective time and optional hold reason/expiry, updates current access and appends an immutable history row in the same transaction. Withdrawal stops the next download while history stays queryable; two tenants with identical local identifiers remain isolated by forced row-level security. The synthetic adapter moved to `src/test`, and the controller now receives the service by injection (no `new ...Service(...)` in main). All fixtures are synthetic.

## Affected requirements

XCH-06 (separate patient release authorization, immutable revision, policy version, effective time, hold reason/expiry, withdrawal/correction keeps history), PAT-02 (released report download authorized against linked patient and current release). Supporting: ARC-01, ARC-02, OPS-02.

## Risk class

Cross-boundary (new persistence port, Spring wiring and a new Flyway migration on a patient-facing download path). No clinical sign-off or real-patient data in this slice.

## Review owner

Senior Java/Spring Boot and Senior PostgreSQL/Flyway (bounded reviews requested; results recorded under Findings when received).

## Data changes

New V84 migration (`db/migrations/V84__report_release_store.sql`, `Change: expand`, additive only) creates three tenant-owned tables:

- `report_chart_link` — current verified/active patient link per (organization, subject).
- `report_release_revision` — immutable revision identity and rendered artifact, current status and latest policy version; trigger `report_revision_identity_guard` rejects changes to identity columns.
- `report_release_history` — append-only release decisions (policy version, effective time, hold reason/expiry, status, recorded at); UPDATE/DELETE/TRUNCATE triggers cover every role including the migration owner.

Each table has ENABLE + FORCE RLS, a `tenant_isolation` policy using `public.app_org()` with `WITH CHECK`, and explicit grants/revokes for `smartclinic_app`. No backfill; lock/volume impact is DDL only on small new tables. Rollback is a forward-fix contract migration; no destructive DDL is needed. No dependency added.

## Authorization boundaries and audit events

Tenant comes only from `TenantContext` (bound to `app.current_org()` inside the guarded transaction and written on every insert). The verified, active chart link is re-read on every protected action; `ReleasedReportService` still denies unlinked/inactive subjects with 403 and checks status, effective date, supersession and current revision before a download. Existing audit outcomes (`REPORT_LIST`, `REPORT_DOWNLOAD`, purposes `PATIENT_REPORT_ACCESS`/`PATIENT_REPORT`) are unchanged. The audit sink remains the pre-existing in-memory implementation; a durable audit adapter is a separate follow-up and is not a regression from this change.

## Migration and rollout considerations

V84 is the reserved version and is additive. `db/check.sh` and Flyway both apply it in numeric order; the integration suite applied it as `84 - report release store`. No production table is altered, so rollout needs no data backfill. The append-only history table is protected by triggers, not grants alone.

## Findings

- Production audit events for patient report access still go to the pre-existing `InMemoryAuditSink`. It was promoted to a Spring `@Component` so the controller can inject the service, but it is not durable. OPS-02 durable audit for this path needs a separate adapter (it would require touching the `audit` module, outside this story's scope). No regression: the previous controller constructed the same sink.
- `recordRelease` and `withdraw` are persistence ports: the read/download paths are wired end-to-end, but the XCH-06 release/withdraw command workflow that calls these write ports is not part of this story's scope. `withdraw` is exercised through the HTTP integration test by invoking the store directly before the next request.
- `scripts/wiring-baseline.json` still lists the two now-fixed debt entries for this file; deleting baseline lines is owned by the orchestrator (protected file), so only a "fixed" note is printed and the gate passes.
- The append-only DB test initially produced a false pass: with FORCE RLS and no `app.current_org` in the migration-owner session, the UPDATE matched zero rows and no trigger fired. Fixed by setting the tenant GUC in that session before the mutation assertions; documented here so the next worker does not reintroduce the false positive.
- `python3 -I -m unittest discover -s scripts/tests -q` and `scripts/check.sh` fail for the pre-existing skip-worktree `opencode.json` CI profile, not for this change (details under Test evidence).

## Lessons for workers

- A FORCE RLS table's trigger test must set the tenant GUC in the same session and seed at least one visible row; otherwise zero rows match and "no exception" is a false pass (this is also in the senior-database skill).
- When a controller previously built its own service, extract one constructor taking the injected service: existing package-level tests keep working and the wiring baseline debt shrinks without touching the protected baseline file.
- In this cloud worker, a stale `opencode.json` is the CI profile under `skip-worktree`; verify with `git ls-files -v` and `git show HEAD:opencode.json` before treating it as a real regression. Never regenerate it from a story worker.
- Running a single test class at a time with JaCoCo and reading only the touched classes' counters is enough to prove 100% before the integrator runs the full `verify`; it avoids the ten-minute full gate.
