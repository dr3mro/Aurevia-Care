# BUILD-30 — Persist released reports and release history with JDBC

## Summary

Extracted `ReportReleaseStore` from the in-memory report-release adapter and added `JdbcReportReleaseStore`, a tenant-guarded Spring JDBC adapter backed by a new V84 migration. A release decision records the immutable revision, release policy version, effective time and optional hold reason/expiry, updates current access and appends an immutable history row in the same transaction. Withdrawal stops the next download while history stays queryable; a withdrawn revision is terminal and cannot be re-released. Two tenants with identical local identifiers remain isolated by forced row-level security. The synthetic adapter moved to `src/test`, and the controller now receives the service by injection (no `new ...Service(...)` in main). All fixtures are synthetic.

## Affected requirements

XCH-06 (separate patient release authorization, immutable revision, policy version, effective time, hold reason/expiry, withdrawal/correction keeps history, terminal withdrawal), PAT-02 (released report download authorized against linked patient and current release). Supporting: ARC-01, ARC-02, OPS-02.

## Risk class

Cross-boundary (new persistence port, Spring wiring and a new Flyway migration on a patient-facing download path). No clinical sign-off or real-patient data in this slice.

## Review owner

Senior Java/Spring Boot and Senior PostgreSQL/Flyway bounded reviews were run; their findings and dispositions are recorded under Findings. Reviewer evidence is simulated specialist review, not human or clinical acceptance.

## Data changes

New V84 migration (`db/migrations/V84__report_release_store.sql`, `Change: expand`, additive only) creates three tenant-owned tables:

- `report_chart_link` — current verified/active patient link per (organization, subject).
- `report_release_revision` — immutable revision identity and rendered artifact, current status and latest policy version; `guard_report_revision_update()` rejects identity changes and any `WITHDRAWN → RELEASED` transition.
- `report_release_history` — append-only release decisions (policy version, effective time, hold reason/expiry, status, recorded at); UPDATE/DELETE/TRUNCATE triggers cover every role including the migration owner.

Each table has ENABLE + FORCE RLS, a `tenant_isolation` policy using `public.app_org()` with `WITH CHECK`, and explicit grants/revokes for `orevia_app`. `report_release_revision` also has BEFORE DELETE and BEFORE TRUNCATE triggers; TRUNCATE is additionally blocked by the history foreign key. No backfill; lock/volume impact is DDL only on small new tables. Rollback is a forward-fix contract migration; no destructive DDL is needed. No dependency added.

## Authorization boundaries and audit events

Tenant comes only from `TenantContext` (bound to `app.current_org()` inside the guarded transaction and written on every insert). The verified, active chart link is re-read on every protected action; `ReleasedReportService` still denies unlinked/inactive subjects with 403 and checks status, effective date, supersession and current revision before a download. Existing audit outcomes (`REPORT_LIST`, `REPORT_DOWNLOAD`, purposes `PATIENT_REPORT_ACCESS`/`PATIENT_REPORT`) are unchanged. The audit sink remains the pre-existing in-memory implementation; a durable audit adapter is a separate follow-up and is not a regression from this change.

## Migration and rollout considerations

V84 is the reserved version and is additive. `db/check.sh` and Flyway both apply it in numeric order; the integration suite applied it as `84 - report release store`. No production table is altered, so rollout needs no data backfill. The append-only history and terminal-withdrawal invariants are protected by database constraints/triggers, not grants alone.

## Findings

- **Senior backend review — blocking F1 (reachability/OpenAPI):** the write methods (`putLink`, `putReport`, `recordRelease`, `withdraw`, `releaseHistory`) have no production caller; the read paths are wired end-to-end but release creation/withdrawal commands are not part of this story, and the patient report endpoints are absent from `contracts/openapi.yaml`. This is an explicit foundation-only boundary inherited from the story decomposition (the original in-memory adapter was also written only by tests). Scope forbids editing `contracts/`. Follow-up story needed with owner and acceptance: add a staff-authorized release/withdraw command endpoint, an HTTP integration test through it, and OpenAPI + regenerated client. BUILD-30 is complete against its four stated acceptance items but **not** against the full AGENTS.md entry-point/OpenAPI gate; the integrator/owner must decide whether to accept it as foundation-only.
- **Senior backend review — blocking F2 (withdrawn resurrection), fixed:** the `ON CONFLICT DO UPDATE` path could flip a withdrawn revision back to RELEASED. Fixed with `WHERE status <> 'WITHDRAWN'` in the upsert, a Java guard that aborts before appending a contradicting history row, a matching guard in the in-memory fake, a `WITHDRAWN → RELEASED` DB trigger guard (`23514`), and unit + integration tests asserting the download stays 410 after a re-release attempt.
- **Senior backend F3 (non-null correction branches), closed:** `recordReleaseWritesCorrectionContextIntoTheUpsert` and the non-null correction path in `historyRowMapperReadsRevisionAndReleaseColumns` take those branches; JaCoCo confirms zero missed branches.
- **Senior backend F4 (TOCTOU across separate store reads), documented not fixed:** `download()` makes several separate transaction-guarded reads, so a concurrent withdrawal between reads can affect an in-flight download. A single-transaction authorization port is a follow-up story. Sequential withdrawal stops the next download, which is the story's acceptance. Documented in `ReleasedReportService` Javadoc.
- **Senior backend F5 (mixed hold fact NPE), closed:** `dateTime` is now null-safe; the DB CHECK still rejects an invalid HELD row, and a unit test covers a reason without expiry.
- **Senior backend F6 (withdrawal policy version), documented:** `withdraw` inherits the revision's current policy version because it is a terminal state change, not a new authorization; stated in `ReportReleaseStore` Javadoc.
- **Senior database review — no blocking finding.** Its F1–F3 verification gaps were closed with SQLSTATE-specific assertions (`44000`, `42501`), non-zero seeded-row counts in the mutating session, revision identity/delete negative tests, and a cross-tenant `WITH CHECK` write-rejection test. Its F4 (revision DELETE/TRUNCATE protection) was closed by adding BEFORE DELETE/TRUNCATE triggers; TRUNCATE is also blocked by the history FK, and the test asserts rejection without assuming which guard fires.
- An initial append-only DB test produced a false pass: with FORCE RLS and no `app.current_org` in the migration-owner session, the UPDATE matched zero rows and no trigger fired. Fixed by setting the tenant GUC and asserting a non-zero row count in that session before the mutation assertions.

It was promoted to a Spring `@Component` so the controller can inject the service, but it is not durable. OPS-02 durable audit for this path needs a separate adapter (would require touching the `audit` module, outside this story's scope). No regression: the previous controller constructed the same sink.

## Lessons for workers

- A FORCE RLS table's trigger test must set the tenant GUC in the same session and assert a non-zero visible row count; otherwise zero rows match and "no exception" is a false pass. Assert the SQLSTATE, not just any `SQLException`.
- A guarded upsert must abort when its `WHERE` suppresses the update; otherwise a "decision" row can be appended that contradicts current access. Enforce terminal states in both SQL and the adapter.
- `TRUNCATE` on a table referenced by a foreign key fails with SQLSTATE `0A000` before BEFORE TRUNCATE triggers can run; a trigger there is unreachable, so rely on the FK and assert rejection generically.
- When a controller previously built its own service, extract one constructor taking the injected service: existing package-level tests keep working and the wiring baseline debt shrinks without touching the protected baseline file.
- In this cloud worker, a stale `opencode.json` is the CI profile under `skip-worktree`; verify with `git ls-files -v` and `git show HEAD:opencode.json` before treating it as a real regression. Never regenerate it from a story worker.
- Running a single test class at a time with JaCoCo and reading only the touched classes' counters is enough to prove 100% before the integrator runs the full `verify`; it avoids the ten-minute full gate.
