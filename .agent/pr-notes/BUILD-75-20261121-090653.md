# BUILD-75 — Staff web: care-team action tasks (owner, due date, status)

## Summary

Stopped at the story's step-5 contract gate before writing any code. The task API this
screen must call does not exist in `contracts/openapi.yaml` (or in the generated staff-web
client). The API domain model for a care-team task exists in Java but is deliberately
unwired — no controller, no HTTP route, no reassignment command, no per-patient/per-owner
list, no overdue concept, no Today count. Building the screen would require inventing an
API, which step 5 forbids. No files under `apps/staff-web/src/features/caretasks` were
created; no other files were changed.

## Affected requirements

| ID | Requirement | Acceptance in story | Status |
|---|---|---|---|
| CLN-06 | "Care-team action tasks track owner, due date and outcome." | Task list per patient and per owner with due date and status; creation from a chart or result; completion with a note; completed task keeps history | Blocked — no HTTP contract |
| ADM-02 | Operational queues; authorized operators assign/resolve with reason; "overdue" monitoring | Reassignment requires a reason; overdue task marked by word and colour; overdue task in owner's Today count | Blocked — no HTTP contract |
| WEB-09 | Resilient screens: loading/empty/error/offline/forbidden/conflict/session-expired states; conflict keeps typed work | Resilient states for the task screen (screen recipe sections 2 and 4) | Not started — depends on the API above |

Acceptance tests the story requires (reassignment needs a reason, an overdue task shows
the word "Overdue", a completed task keeps its history, English and Arabic) cannot be
written against a normal entry point until the contract exists. Screen-level message
parity and RTL rendering could be authored locally, but the data contract is a hard
prerequisite for the screen itself.

## Risk class

Cross-boundary blocker (docs/WORKFLOW.md): the story depends on an API contract and a

invented contract, it would also be a clinical-safety risk (ADM-02/CLN-06): wrong owner,
missed due date or a lost completion would affect care coordination.

## Findings

- **Hard blocker (decisive):** the task endpoints required by step 1 of the story are not
  in `contracts/openapi.yaml`. There is no `task` string, path or schema in any of the
  three OpenAPI files, nor in the generated staff-web client. Step 5 says to stop rather
  than invent the API; this note is that stop.
- **Two different "task" concepts exist in the backend.** `scheduling/followup/CareTeamTask`
  matches the story's fields (owner, due date, status, outcome) but is deliberately
  unwired and lacks reassignment/overdue/patient-owner listing. `exchange/task/ExchangeTask`
  is an XCH-02 workflow aggregate with real controller routes, but no owner/due date and
  no contract entry. Neither can be used from the staff web today.
- **Story dependency gap:** `BUILD-76` will register the caretasks routes, but nothing in
  the scheduled work creates the task API contract or backend endpoints. The owner should
  add that API story before re-dispatching BUILD-75.
- No defect was observed in existing code; the baseline staff-web check is green.

## Lessons for workers

- For any screen story with step 5 ("if the API is missing from `contracts/openapi.yaml`,
  stop"), run the contract/generated-client grep **before** scaffolding the feature
  folder. A domain model in `apps/api` is not an HTTP contract — check both the OpenAPI
  paths and the generated client.
- `grep -ic "task" contracts/openapi.yaml` is a fast, decisive gate. Do not build a typed
  `api.ts` wrapper or a mock endpoint to fill the gap; that is inventing the API and will
  fail `gen:api:check` and the wiring checks.
- Distinguish similarly named aggregates: `CareTeamTask` (care coordination) and
  `ExchangeTask` (XCH-02 workflow) are different records with different routes.

## Why this is not finished

The story's step-5 gate fired: **the API needed is missing from `contracts/openapi.yaml`**.

Missing contract operations, mapped to the story's acceptance points:

1. List tasks **per patient** and **per owner** with due date and status — no GET path in
   the contract. `FollowUpService.tasks(followUpId)` is the closest in-process method and
   is filtered by one follow-up id, not by patient or owner, and is not exposed over HTTP.
2. Create a task **from a chart or a result** — no POST path in the contract.
   `FollowUpService.createTask` requires a `followUpId` (a suggested follow-up), not a
   chart or a result reference, and is not exposed over HTTP.
3. **Reassignment with a reason** — no care-team task reassignment method or endpoint
   exists (`grep -rlin reassign apps/api/src/main --include='*.java'` finds only an
   unrelated `messaging/conversations/ConversationService.java`). This acceptance point
   cannot be met even by wiring the existing service.
4. **Completion with a note** — `FollowUpService.completeTask(taskId, outcome)` exists in
   process only; there is no POST endpoint, and the completed record is returned, not a
   history view. `CareTeamTask.complete` preserves the original fields on the same record,
   but no HTTP endpoint returns that data.
5. **Overdue marking by word and colour** and **overdue count in the owner's Today page** —
   there is no overdue flag/query, no due-date comparison endpoint, and no Today page or
   count endpoint in the contract or the API.
6. **English and Arabic, resilient states** — these are local to the screen, but the screen
   cannot render tasks without the data contract above.

What was tried: confirmed the absence in `contracts/openapi.yaml` (0 "task" matches, 19
paths listed), in `contracts/openapi/generated/openapi.yaml`, in `contracts/contract/openapi.yaml`
and in `apps/staff-web/src/api/generated/openapi.d.ts` (0 "task" matches); inspected the
only two backend "task" aggregates and their controllers/services; confirmed no existing
staff-web task wrapper. No code was written, so there is no failing test to attach.

Most likely cause: the care-team task backend slice (`FollowUpService`, `CareTeamTask`) is
explicitly documented as deliberately unwired — "a V16 migration and a web controller
belong to a follow-up story" — and that follow-up API/controller story was never scheduled
ahead of BUILD-75. The XCH-02 `exchange/task` routes were also never added to the OpenAPI
contract.

Exact next step for the owner / next worker: add an API story (outside this worker's scope)
that (a) adds the care-team task operations and schemas to `contracts/openapi.yaml` and
regenerates `apps/staff-web/src/api/generated/openapi.d.ts`, (b) exposes `FollowUpService`
through a controller with tenant/role authorization, an append-only Jdbc store and RLS
migration, (c) adds reassignment with a required reason, a per-patient/per-owner list with
due dates and derived overdue status, completion with a note, a history view and a Today
count endpoint, each with HTTP-level integration tests; then re-dispatch BUILD-75. Do not
proceed with a frontend-only implementation against an invented contract.
