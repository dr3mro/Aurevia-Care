## Findings

- **Blocking gap (observed, tool evidence):** the story names "the scheduling admin API in `contracts/openapi.yaml`", but that file contains no scheduling administration API. Its only scheduling path is the read-only `GET /api/v1/appointments` list. The generated client mirrors this (no `/api/v1/scheduling` operations).
- **Code/contract divergence:** a `SchedulingAdminController` exists in `apps/api/src/main/.../web/` with `POST /api/v1/scheduling/visit-types`, `POST /api/v1/scheduling/resources`, `GET /api/v1/scheduling/resources?facilityCode=`, and `POST /api/v1/scheduling/resources/{code}/availability`. None of these is published in `contracts/openapi.yaml`, `contracts/openapi/generated/openapi.yaml`, `contracts/contract/openapi.yaml` or the generated `openapi.d.ts`. `.agent/pr-notes/AUD-20261120-08.md` already documented this divergence; it is not a new defect and no contract file was edited.
- **Even the unpublished code endpoints are insufficient for this story.** Missing from both the contract and the code controller:

  | Story need | Contract (`contracts/openapi.yaml`) | Code controller | Verdict |
  |---|---|---|---|
  | Rooms and resources (kind clinician/room, per facility) | Absent | `POST`/`GET /resources` (unpublished) | Not in contract |
  | Clinician availability windows | Absent | `POST /resources/{code}/availability` (unpublished, no list) | Not in contract |
  | Visit types with duration | Absent | `POST /visit-types` (unpublished, no list) | Not in contract |
  | Recurrence templates | Absent | None (only an appointment-series booking command in `AppointmentService`, no admin endpoint) | Missing everywhere |
  | Holds (definition/management) | Absent | None (only transient `held` appointment state and `BookingRules.holdMinutes`) | Missing everywhere |
  | Booking rules (read/write) | Absent | `BookingRules` read from the approved configuration fold, no typed endpoint | Missing everywhere |
  | Effective date on each change + retained history | Absent | Request records have no effective date; no history endpoints | Missing everywhere |
  | Conflict message listing affected bookings | Absent | None (`GET /appointments` is a plain list, no what-if check) | Missing everywhere |

- **What the next worker must know:** do not build the screens by calling undocumented endpoints or by encoding visit types/holds/booking rules as opaque strings in the generic configuration/catalog API — that would be inventing the API and would not satisfy "list the affected bookings". The generic `configuration` and `catalogs` endpoints do provide effective dates, named approval and history, but they carry opaque `value` strings and no conflict semantics, so they cannot implement acceptance steps 2 and 3.
- No defect was filed in `BUGS.md` (worker trackers are not edited); the gap is recorded here for the integrator.

## Lessons for workers

- When a story names a specific contract file and adds a "stop if the API is missing" gate, enumerate that file's paths **before** designing screens. A `@RestController` in `src/main` is not a published contract endpoint; the two diverge in this repository (see `AUD-20261120-08`).
- Check the generated client (`apps/staff-web/src/api/generated/openapi.d.ts`) as the second authority: if it has no operations for a feature, a typed, contract-backed `api.ts` cannot be written without inventing the API.
- "The API exists in code" is not sufficient when acceptance also demands effective dates, history, recurrence templates, holds, booking rules and a conflict/affected-bookings check. Verify every acceptance noun against an actual path + schema.

## Why this is not finished

**Blocked by a missing API, per story step 5. No source change was made.**

- **What failed:** the contract lookup required by story step 1 did not find the scheduling administration API. `contracts/openapi.yaml` has 19 documented paths and only one scheduling path (`GET /api/v1/appointments`, line 340). `apps/staff-web/src/api/generated/openapi.d.ts` has no `/api/v1/scheduling` operations. The repository-wide grep over `contracts/` for `visit-types`, `booking-rules`, `recurrence`, `/resources` and `availability` returned no matches. Consequently acceptance steps 2–4 (effective-dated resources/availability/visit types/recurrence/holds/booking rules with history; conflict message listing affected bookings; and the tests for those) cannot be implemented against a published contract.
- **Most likely cause:** the backend scheduling work (S-G1-01, `docs/archive/TODO-DONE.md`) created the reference-data tables, `SchedulingAdminService` and a four-endpoint `SchedulingAdminController`, but those admin endpoints were never added to `contracts/openapi.yaml` (an existing, previously observed divergence in `AUD-20261120-08`). Several story requirements — recurrence templates, holds, booking rules, effective-date/history on changes and conflict/affected-bookings reporting — have no backend endpoint at all, published or otherwise.
- **What I tried:** read the full `contracts/openapi.yaml` and enumerated all 19 paths; enumerated the paths in `contracts/openapi/generated/openapi.yaml`, `contracts/contract/openapi.yaml` and the generated `openapi.d.ts`; grepped `contracts/` for all relevant nouns; read `SchedulingAdminController.java`, `SchedulingAdminService.java` and the scheduling domain package; checked `AUD-20261120-08.md`; ran the staff-web baseline check and typecheck (both green). I did not write any code, add an endpoint, or change a contract, per step 5 and TODO.md rule 9 ("if the spec and the task disagree, do not guess ... stop").
