# BUILD-33 — Templates: operative, OB/GYN, perinatal and pediatric development

## Summary

CLN-04 baseline completeness. `BaselineTemplates.java` already defined all five families, but there was no durable, versioned baseline artifact: the four story families were only in-process Java constants, and the two site dictionaries they reference (`obstetric_history`, `milestone_domain`) had no approved baseline seed. Added V87, a non-tenant, append-only baseline catalog holding the exact frozen field meanings and approved site dictionaries for all five families as version 1, plus fast-tier acceptance tests that bind the Java baselines to the migration and prove full/partial note validation, historical field meanings and the required-field save gate for each story family. All data is synthetic.

## Affected requirements

- CLN-04 — versioned SOAP/operative/OB-GYN/perinatal/pediatric-development templates; operative fields; LMP and structured obstetric history; birth/neonatal history; milestone domain/observation/date; governance-approved dictionaries and requiredness; free text with language; historical field meanings.
- ARC-02 — tenant isolation rationale for not seeding the tenant-owned V80 tables (no tenant exists at migration time; FORCE RLS).
- OPS-02 — append-only, immutable baseline configuration.

## Risk class

Cross-boundary (new database reference object plus domain acceptance evidence). Reviewed as bounded by the database and test specialists in simulated mode; no clinician or human evidence.

## Data changes

- New `db/migrations/V87__baseline_templates.sql` (reserved version V87 only; no other migration touched).
  - `public.clinical_template_baseline`: global reference table, PK `(kind, baseline_version)`, `fields` jsonb (serialized `FieldDefinition` records) and `dictionaries` jsonb (approved site codes). Five version-1 seed rows (SOAP plus the four story families), no backfill.
  - `public.current_clinical_template_baseline`: view of the highest version per family (adoption aid only).
  - `public.reject_baseline_catalog_mutation()`: dedicated immutability trigger function. The shared `reject_immutable_mutation()` reads `OLD.organization_id` and would fail misleadingly on a tenant-free table.
  - ENABLE + FORCE RLS with an explicit permissive policy (`USING (true) WITH CHECK (true)`): required because the table has no tenant key; append-only is bound by triggers for every role including the owner, and column access by GRANT/REVOKE.
  - Grants: `SELECT` on table and view plus `EXECUTE` on the function to `aurevia_app`; `INSERT/UPDATE/DELETE/TRUNCATE` on the table revoked; PUBLIC revoked.
  - Lock/volume: one small new table, one view, five rows; no existing row updated. Forward-fix: drop the table, view, triggers and function — nothing depends on them yet. No patient data.

## Authorization boundaries and audit events

No new role, command or audit event. The catalog is governance-approved reference configuration, not a tenant clinical payload; the migration deliberately does not fabricate a governance approval into V80's tenant tables. Per-tenant dictionary/version approval remains the existing role-gated `TemplateService` workflow (`tenant_admin` defines, `clinical_governance` approves), exercised by the new tests with synthetic actors.

## Migration and rollout considerations

The tenant-owned template tables (V80) cannot be seeded by a migration: they have `FORCE RLS` with `WITH CHECK (organization_id = public.app_org())` and an organization FK, while migrations run with the GUC unset and before any tenant exists. A global baseline catalog is the additive alternative and keeps governance ownership honest. `check-migrations.py --require-baseline` and `db/check.sh` both pass. The catalog needs a future adoption path (see `task-requests` below) before it changes tenant behavior; nothing auto-promotes on tenant creation.

## Findings

- Requiredness and dictionaries remain Java constants in `BaselineTemplates.fieldsFor`; V87 freezes the same values as approved configuration data and a parity test prevents drift. The Java class is still the in-process source for the acceptance tests; the DB catalog is not yet read by production code (tracking request below).
- Step 3 wording "Every field takes free text with a language" was read together with the existing `FieldType` design: structured DATE/CODE/TEXT fields keep their types, every FREE_TEXT field definition carries a canonical language and every authored FREE_TEXT value is required to carry one (`language:` violation). Converting all fields to FREE_TEXT would break date/dictionary validation and widen scope, so no production change was made.
- "A required field blocks signing" has no CLN-05 sign boundary in this module (`TemplateService` has no sign method). The in-scope equivalent is proven: a missing required field makes `validate` invalid and `saveNote` return 422 with nothing persisted. A true sign-level assertion needs the signing module.
- `worker-check.sh` red on the CI-profile `opencode.json` is a known cloud-worker measurement artifact (OPS-CW-003-01), not a change defect.

## Lessons for workers

- A global reference table with no `organization_id` cannot reuse `reject_immutable_mutation()` (it reads `OLD.organization_id`); give it a dedicated trigger function and an explicit permissive FORCE-RLS policy, then bind immutability with triggers and SELECT-only grants.
- Read the newest reconciled daily note before running the worker gate: the `opencode.json` skip-worktree profile makes `check-pack` fail; verify with `git ls-files -v` / `git show HEAD:opencode.json` and restore the CI bytes after any temporary swap instead of regenerating the file.
- When the story names a migration but the domain Java is already complete, make the migration the failing-test target (parse the SQL in a fast unit test) so the durable artifact has a reachable consumer in the test tier.
