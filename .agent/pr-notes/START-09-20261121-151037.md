# START-09 — API: OpenAPI error response rules as a unit test

## Summary

Added one test-only file, `apps/api/src/test/java/com/aurevia/contract/OpenApiErrorRulesTest.java`. It parses the committed staff-API contract `contracts/openapi.yaml` with SnakeYAML (already on the test classpath) and enforces three WEB-04/UX-01 rules: (1) every 4xx/5xx response that documents a body uses the single shared `Error` schema, and every operation documents that shared body at least once; (2) that schema declares a stable machine `code` (string, non-empty enum or schema `$ref`) and a string `correlationId`; (3) no error example exposes a person name, e-mail address, patient identifier or stack trace, and no error text exposes an e-mail address, patient identifier or stack trace. Twenty JUnit tests cover the real contract plus one isolated failing or edge fixture per rule/branch. No production code, contract, controller, dependency or threshold was changed.

## Affected requirements

- WEB-04 — API protection: machine-readable error bodies; never reveal stack traces, SQL, other tenants or internal class names; verify error-shape rules with tests. Acceptance: real contract passes all three rules; each rule fails on an isolated invalid fixture.
- UX-01 — English/Arabic presentation and safe clinical text: acceptance here is that error bodies carry no personal identifiers or stack traces, so the client can render a stable localized message from `code` plus `correlationId`.

Acceptance mapping: story step 2 → rules 1–3 and `committedContractSatisfiesEveryErrorRule`; step 3 → `PATIENT_IDENTIFIER_TEXT_ALLOW_LIST`; step 4 → 19 isolated failure/edge fixtures; step 5 → no missing resource (SnakeYAML 2.6 confirmed).

## Findings

- **Interpretation decision.** The committed contract documents a body (`schema`) on only one 4xx response shape (`403` → `Forbidden` → `Error`); 401/404/409/422 responses are bare `{ description }`. A literal reading of "every 4xx/5xx response uses one shared error schema" would make the real contract breach the rule on ~20 operations and require a long allow list, which the story forbids. The test therefore treats a response with no declared body as non-divergent — the contract simply leaves the body undocumented, and a 401 may be emitted by the security filter chain rather than the advice — and rejects any response that *does* declare a different body. It additionally requires every operation to document the shared body at least once so an empty contract cannot pass. This is stated in the class Javadoc.
- **Short allow list with TODO (story step 3):** `PATIENT_IDENTIFIER_TEXT_ALLOW_LIST` contains exactly one operation, `listFinanceInvoices`, with the inline comment `// TODO WEB-04: listFinanceInvoices echoes the "patientId" filter name in its 422 description; remove this entry when that response stops naming the request field.` The real contract's `listFinanceInvoices` 422 description is `Invalid cursor, limit, status, patientId or tenant selection`. The contract/controller were not edited.
- **Rule 3 scans `example`/`examples` for all four patterns and `description` for e-mail, patient identifier and stack trace.** The committed contract has zero `example` or `examples` keys, so restricting every pattern to examples would make the rule vacuously true. The person-name pattern is deliberately restricted to examples, because Title-Case prose such as "Not Found" or "Internal Server Error" is legitimate in a description; `aTitleCaseProseDescriptionIsNotAPersonName` pins that decision. The one real description hit is the allow-listed `patientId` above.
- **Bounded test-engineer review (simulated reviewer; static read, no shell).** Findings and dispositions: (1) the 5xx branch was untested → added `aFiveHundredWithADifferentBodyFailsTheSharedSchemaRule`; (2) the person-name regex was over-broad for descriptions → restricted to examples (above) with a regression test; (3) `Error.code` as an `enum` or `$ref` would fail a bare `type: string` assertion → `isStableMachineCode` now accepts a string, a non-empty enum or a `$ref`, with `anEnumeratedMachineCodeSatisfiesTheSchemaShapeRule` and `aReferencedMachineCodeSatisfiesTheSchemaShapeRule`. The reviewer also noted `examples` must be a map in OAS 3.0.3 → `withErrorExamplesList` now uses a named example whose `value` is an array, keeping the `List` branch covered in a valid document. Reviewer recommendation to keep the `documentsSharedBody` guard was adopted. No blocking finding remained.
- **Worker-environment artifact, not a change defect:** `scripts/check.sh` and `scripts/worker-check.sh` both stop at `check-pack: opencode.json is stale`, and three `test_check_pack` cases fail for the same reason. `opencode.json` is skip-worktree in this container and holds the CI profile copied by `agent-run.sh`; the committed HEAD file is the generator's local profile. Per MEMORY.md OPS-CW-003-01 this is a false positive of the worktree measurement, not a stale committed file. Nothing was edited to work around it, and the trusted integrator gate runs from a fresh checkout with the committed profile.

## Lessons for workers

- When a test fixture is a Java text block, count the closing-delimiter indentation: incidental whitespace is stripped from every content line. Three of the first fixtures silently did not apply because their `.replace(...)` literals still used source-column indentation, and the tests "passed" by finding no violation. Assert the violation message fragment, not just that an error was thrown, to catch this.
- A "parse the contract" lint must assert the fixture was actually mutated: if a supposed invalid fixture leaves the other rules green, check the fixture's parsed shape before blaming the rule.
- In a cloud worker, `check-pack`/`test_check_pack` staleness on `opencode.json` under `git ls-files -v` flag `S` is a CI-profile artifact; inspect `git show HEAD:opencode.json` and report which profile was measured instead of regenerating a protected file.
- Reading the production error handler before writing contract rules resolved the ambiguity about undocumented error bodies; do the same for pagination or authorization contract rules.
- **Root cause of repair attempt 1 (tool evidence, reproduced deterministically):** `JdbcPatientAccessStoreIntegrationTest` declares two `@BeforeAll` static methods with no ordering guarantee — `roles()` (lines 88–99, creates `orevia_migrate`/`orevia_app`) and `prepare()` (lines 102–119, runs `CREATE DATABASE ... OWNER orevia_migrate`). JUnit 5 runs `prepare()` first, so on a PostgreSQL cluster where the role does not yet exist the `CREATE DATABASE ... OWNER` fails. Reproduction, with the role dropped to emulate a fresh cluster and the exact gate env: `OREVIA_PG_ADMIN=postgres mvn -q -B -f apps/api/pom.xml -Pno-security -Dtest=JdbcPatientAccessStoreIntegrationTest test` → `Tests run: 1, Errors: 1`, `PSQLException: ERROR: role "orevia_migrate" does not exist` at `prepare(JdbcPatientAccessStoreIntegrationTest.java:108)`. When the role pre-exists (left by any earlier integration test) the class passes, which is why it was green on earlier full-suite runs and is environment/order dependent. Evidence source: executed tool commands only (no reviewer, simulated user or human participant).
