# READY-23 — Admin pages: /admin/facilities and /admin/staff on the real API

## Summary

Wire the two existing administration screens to the real API. Added a tenant-scoped
admin API client, a facilities page (list + create), a staff page (list + invite +
deactivate with confirmation and reason + immutable history), shared field-error
summary and page-accumulation helpers, bilingual messages, and the two routes.
All data is synthetic in tests; no patient data appears in URLs, logs, titles or
browser storage. No new dependency and no migration.

## Affected requirements

- IAM-01 — active-organization scope on every call; facility administration;
  tenant-local facility code and name; access denial shown as `ForbiddenState`.
- IAM-02 — staff invite/deactivate with a bounded role, immediate-effect
  deactivation, and the append-only history view with grantor/effective dates.

## Authorization boundaries and audit events

- Tenant comes only from `useActiveOrganization()` and is sent as
  `X-Active-Organization` by `buildRequestDescriptor`; no request body carries an
  organization, grantor or actor field.
- Writes carry a fresh `Idempotency-Key` per user action; no `If-Match` is sent
  because the facility/staff contracts have no version precondition.
- Roles are bounded client-side to `tenant_admin`, `reception`, `privacy_auditor`
  before invite; the API remains authoritative.
- Both routes are restricted in `src/app/navigation.ts` to `tenant_admin`; a
  direct visit still fails closed because a 403 renders `ForbiddenState`.
- Audit events are unchanged: deactivation auditing (`STAFF_ADMIN`) remains the
  server-side responsibility (PROJECT.md S-G0-02 decision).

## Migration and rollout considerations

None. Routes are code-split (`StaffPage` 2717 B gzip, `FacilitiesPage` chunk under
the 250 KB WEB-08 budget). `useRole()` still returns the synthetic `reception`
role until READY-11 supplies the authenticated role; this does not widen access
because the navigation model and the API are the gates.

  Reviewer follow-up: "Finding 3 resolved. No new correctness or coverage concern."
- **Open hand-off (medium, shared components out of this scope):** on a command
  409/412 the shared `ConflictState` still renders Compare / Reload / Copy with
  noop defaults, and list timeout/offline `ErrorState` Retry and
  `SessionExpiredState` Sign in are also noop because `ApiPage`/`StateView` accept

## Lessons for workers

- With `exactOptionalPropertyTypes: true`, a shared `error?: string` prop cannot
  be passed `string | undefined`; use `{...(error === undefined ? {} : { error })}`.
- A `mockResolvedValue` default must match the command's response shape, not just
  the list shape, or success-status assertions fail with an empty status region.
- Adding a route requires extending the exact array in
  `tests/app/AppShell.test.tsx`; the new page test alone does not keep the gate green.
- When `ApiPage` feeds an accumulating list, clear accumulated pages on a
  successful-command `reloadToken`, otherwise a reload duplicates every row.
- `??` and conditional error spreads count as V8 branches: cover the fallback
  with a facility whose `timeZone` is null and the no-error render with a valid form.
