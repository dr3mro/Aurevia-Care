# BUILD-52 — Staff web: register the new feature routes and navigation

## Summary

Make every shipped feature screen reachable from the role-scoped staff rail and show the forbidden state when a user without the required role opens a direct link. The route registry already self-registers feature routes through `import.meta.glob`; this change adds the missing navigation entries and a single, navigation-derived role resolver used by the application shell guard. No feature file or route registry file is edited.

## Affected requirements

- UX-01 — English/Arabic mirrored rail labels for every new item.
- WEB-09 — forbidden state on a direct link for a role without access.

## Risk class

Cross-boundary (staff-web application shell + shared navigation model). Role boundary only; no clinical data, no migration.

## Review owner

smartclinic-senior-react (staff web), with plan/code/coverage/security reviewers per the quality loop.

## Data changes

None. No migration, backfill, lock or volume impact, no rollback data work. Route parity is unchanged: `collectFeatureRoutes` already discovers every feature `routes.ts`; this work adds no route and edits no feature file.

## Authorization boundaries and audit events

Role comes only from `useRole()` (or the explicit `role` override used by isolated tests); never from the URL, query string or browser storage. The navigation model remains the single source of role-to-route truth. No audit event added or changed.

## Migration and rollout considerations

None. Front-end-only change; the lazy `/forbidden` chunk is reused rather than added as a new static import, so chunk count and the WEB-08 bundle budget are unchanged.

## Lessons for workers

- Derive direct-link role checks from the existing navigation model plus trailing-`:param` stripping; a second hard-coded route-to-role list in the shell duplicates rail policy and drifts. Check feature-level self-guards before writing an "allowed role" test: a page can show its own forbidden state from `useRole()` even when the shell guard allows it, so mock the shared `useRole` module for both.
- An exact-list rail test can conflict with a feature's own authorization table. A narrow, documented access override in the same module keeps both correct; add a named test for the override and one proving the rail is unchanged.
- In a cloud worker, `git grep` can surface conflict markers already committed in HEAD by another worker after a no-op merge. Confirm `git status` and `git merge` output before treating them as your own conflicts; they are out of scope and belong to their owning task.
