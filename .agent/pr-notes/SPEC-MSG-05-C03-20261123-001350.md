# SPEC-MSG-05-C03 — MSG-05 clause 3 API test evidence

## Summary

Adds a focused HTTP-level acceptance test proving MSG-05 clause 3 — "Track overdue requested
acknowledgments and route them to the owning unit for follow-up." — plus the companion
spec-clause evidence document. The clause is already implemented; this change adds proof only.
No production code, existing test, contract or migration was changed.

Claimed implementation locations found while proving the clause (step 1 of the task):
`InstructionFactService.overdueFollowUps` (lines 246-278), `InstructionFactController`
(`GET /api/v1/instructions/overdue-follow-ups`, publish/acknowledge/resolve routes),
`InstructionFactActions` (FOLLOW_UP_LIST matrix), `InstructionFactInputs` (unitId validation),
`InstructionFacts` records/enums, `JdbcInstructionFactStore.overdueCandidates`,
`db/migrations/V63__instruction_facts.sql` (nine tenant tables with RLS and FORCE RLS), and the
synthetic-auth tenant interceptor. The route is baselined in `contracts/openapi/missing-routes.txt:51`.

## Lessons for workers

- For `InstructionFactInputs.uuid(value, field)`, the error code is `INVALID_` + the field name
  upper-cased with no separator (`unitId` → `INVALID_UNITID`); assert the code actually emitted,
  not a guessed snake-case form. In Spring Boot 4.1.x the 422 constant is `UNPROCESSABLE_CONTENT`.
- To prove the defensive `requiresAcknowledgment` re-check in `overdueFollowUps`, seed a follow-up
  row directly with the migration-owner connection: `overdueCandidates` never creates one for a
  non-requested revision, so an HTTP-only test cannot reach that filter.
- Use a distinct peer-only unit UUID for the "peer tenant unit is denied" assertion. Sharing the
  unit UUID across tenants is correct for the RLS proof but makes a cross-unit 403 assertion
  ambiguous about which guard fired.
