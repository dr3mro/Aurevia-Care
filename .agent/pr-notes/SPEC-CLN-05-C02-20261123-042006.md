# SPEC-CLN-05-C02 — CLN-05 clause 2 (API test): sign permission, attestation, patient context, draft version, required fields

## Summary

Test-and-documentation-only story. Prove with ACTIVE real-HTTP integration tests that
clinical-note signing enforces the five CLN-05 clause-2 sub-rules, and record the evidence
in a clause note. No production code, no migration, no contract or client change, no
dependency, no existing test edited. Five new tests (1 positive + 4 negatives) exercise the
real `POST /api/v1/clinical-notes/{id}/sign` entry point against synthetic PostgreSQL.

## Affected requirements

CLN-05 (SMARTCLINIC_V1_SPEC.md line 55):
"Draft → signed, with separate amendment drafts and signed addenda. Require sign permission, signer attestation, correct patient context, draft version and required fields. Save signer, effective time, signed time, content checksum and template version. Signed revisions cannot be edited. Entered-in-error preserves the prior revision and records actor, reason and affected recipients. Signing differs from patient release and PDF rendering."

This story covers clause 2 only: "Require sign permission, signer attestation, correct patient context, draft version and required fields."

Supporting IDs mentioned only as context: CLN-03 (chart.record, no sign path), IAM-01/IAM-02
(membership/roles), ARC-02 (tenant context/RLS), OPS-02 (denial audit). No new requirement ID.

## Survey finding (step 1 of the story)

The package `apps/api/src/main/java/com/aurevia/smartclinic/chart` (chart.record, CLN-03)
has **no sign path**: `ChartController` exposes only
`POST /api/v1/chart/records/entries`, `POST /api/v1/chart/records/entries/{id}/verify`,
`GET /api/v1/chart/records/patients/{patientId}/entries` and
`GET /api/v1/chart/records/entries/{id}`. The CLN-05 signing rule is built in the
neighbour package `com.aurevia.smartclinic.clinical.notes`:
- `ClinicalNoteController` → `POST /api/v1/clinical-notes/{id}/sign` (and `/sign-addendum`,
  `/amend`, `/entered-in-error`) under `@RequestMapping("/api/v1/clinical-notes")`.
- `ClinicalNoteService.sign` → `authorize(SIGN)`, `requireVersion`, DRAFT state guard,
  `requireFields`, `requirePatient`, then append an immutable SIGNED revision.
- `NoteInputs.text`, `NoteState`, `NoteChecksum`, `IfMatch`, `ClinicalNoteRevision`,
  `NoteRepository`, `db/migrations/V15__clinical_note_signing.sql`.

The tests therefore drive `/api/v1/clinical-notes` over HTTP. The unpublished chart.record
routes are context only, not an ask. No production code was added. Confirmed independently
by smartclinic-context-optimizer.

## Findings

- **No sign path in chart.record (survey):** the story's boilerplate scope points at
  `.../chart/...` for a sign rule that lives in `com.aurevia.smartclinic.clinical.notes`.
  The test and doc files are placed at the required `chart/clauses` and `docs/spec/clauses/chart`
  paths, but the tests drive `/api/v1/clinical-notes` and say so in the Evidence section.
  No production code was added to satisfy a path convention.
- **Sign-time `requireFields` failure is not HTTP-reachable:** `createDraft` validates the
  same fields (and V15 CHECKs them), so a malformed draft cannot exist. The test proves the
  required-fields rule at the HTTP boundary where it is reachable (create rejection) and
  does not fabricate an unreachable case. The `requireFields` unit coverage already exists.
- **First red run was a fixture bug, not a production defect:** the first cross-tenant
  attempt used an author not seeded in ORG_B and hit an unrelated FK; corrected by
  parameterizing the author per tenant. Recorded above for the next worker.
- **Timestamp/null wire format:** `effectiveAt`/`signedAt` render as
  `yyyy-MM-dd HH:mm:ss.ffffff+00` and a null JSON field reads as `null` through the flat
  `field()` helper; assertions were written against the actual wire, not `Instant.parse`.
- Earlier note `BUILD-33-20261121-215402.md:65` claiming no CLN-05 sign boundary was about
  `TemplateService` and is stale; the boundary now exists in `ClinicalNoteService.requireFields`.
- Out-of-scope observation for the integrator: HEAD already contains committed Git conflict
  markers inside Javadoc in `apps/api/src/main/java/com/aurevia/smartclinic/exchange/hl7/`
  (`Hl7ParseException.java:6,10`, `Hl7Parser.java:14,18`, `Hl7Segment.java:10,14`). They are
  inside comments so compilation still passes. I did not touch them — outside this task's scope.

## Lessons for workers

- In cross-tenant HTTP fixtures, seed the clinical author in the tenant that creates the
  note and pass the author subject explicitly; a hard-coded author produces a misleading 500
  from the V15 foreign key before any authorization behavior is reached.
- `effectiveAt`/`signedAt` from `timestamptz` are not ISO `Instant` text in these HTTP
  responses; assert non-blank and UTC string ordering, and rely on the migration's
  `signed_at >= effective_at` CHECK for the invariant.
- With the flat `field()` JSON helper, a serialized `null` reads as the string `"null"`, not
  empty — assert on state/history rather than string emptiness for absent signer fields.
- Do not re-diagnose the `opencode.json is stale` cloud-worker false positive: confirm once
  with `git ls-files -v` = `S` and the committed profile, then run the other gate stages
  individually. Never regenerate that protected file in a worker.
