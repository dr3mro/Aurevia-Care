# SPEC-IAM-06-C04 — IAM-06 clause 4 API test

## Summary

Test-only story. Added an HTTP integration test that proves platform support access
to clinical data stays denied unless a separate privacy auditor approves an
unexpired incident, and recorded the evidence in a clause document. No production
code, existing test, contract or migration was changed. The clause is fully built,
so no test is disabled.

## Affected requirements

IAM-06 (clause 4, `SMARTCLINIC_V1_SPEC.md:32`), with supporting ARC-02 and OPS-02.

Acceptance mapping: story step 1 → production survey in the clause doc `## Evidence`;
step 2 → seven named tests in the new test class; step 3 → not applicable (clause
built, no `@Disabled`); step 4 → clause doc with the four required headings;
step 5 → no production/contract/migration edit and the checks below.

Risk class: safety-critical (tenant isolation and privileged access), verified with
synthetic subjects only.

## Review owner

SmartClinic integrator; read-only reviews from plan, code, coverage, security and

## Data changes

None. No migration, backfill, lock or volume impact. The tests create and drop a
dedicated synthetic database (`smartclinic_support_access_it`) and use only
synthetic incident references, reasons and staff subjects.

## Authorization boundaries and audit events

Tenant scope is set by `X-Active-Organization`; actor by `X-Synthetic-Subject`.
`tenant_admin` opens an incident, `privacy_auditor` approves it in a separate
command, and the decision is bound to the requesting subject and active tenant.
No new audit event type: the test asserts the existing `SUPPORT_INCIDENT_CREATE`,
`SUPPORT_INCIDENT_APPROVE` and `SUPPORT_ACCESS_CHECK` rows with purpose
`SUPPORT_ACCESS`, outcomes `SUCCESS`/`DENIED`, and the append-only chain in
`audit_event`. Cross-tenant denial is proved with the same subject active in both
tenants, so only forced RLS can explain it.

## Migration and rollout considerations

None. V11 already supplies `support_access_incident`, its separation-of-duties
CHECK, FORCE RLS and tenant policy; V3 supplies the audit chain.

## Findings

  across tenants while the seed helper filtered by subject only. Fixed by making
  the helper filter on `(organization_id, subject)`; the later deliberate same-subject
  seed in both tenants is safe for the same reason and makes the cross-tenant denial
  prove RLS rather than subject binding. The re-review returned VERDICT: GO.
- Pre-existing, out-of-scope baseline: the three support routes are in

## Lessons for workers

- `mvn -Pno-security,fast -Dgroups=integration` does not run integration tests;
  omit `fast` and confirm the Surefire report. With `-q`, read the report file for
  the test count.
- To prove cross-tenant RLS over HTTP, seed the identical subject in both tenants;
  otherwise a denial can be explained by subject binding. Seed helpers must filter
  on `(organization_id, subject)` when a subject is reused across tenants.
- In a cloud worker, six `test_check_pack` failures plus `check-pack.py` staleness
  are the skip-worktree CI profile, not a defect. Confirm once with
  `git ls-files -v opencode.json` and a HEAD-vs-generator comparison; never edit or
  regenerate that protected file.
- `git grep` for conflict markers at the start of a run: a parallel worker can merge
  markers into HEAD; record them instead of editing production files outside scope.
