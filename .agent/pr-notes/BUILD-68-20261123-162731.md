## Findings

- **Fixed in this segment — allergy verification label (code-reviewer Required).** `PatientBanner.tsx` had rendered a constant `chartText(locale, 'verified')` for the allergy chip, so an unverified/unknown allergy would be presented to the clinician as verified. The chip now uses the coded `verificationMessageKey[summary.allergy.verification]` map already used by `LongitudinalChart.tsx:108`, and a red-first test (`components.test.tsx › PatientBanner › shows the coded verification state of an allergy…`) proves an `'unverified'` fixture renders `Unverified` and not `Verified`; the `chart-screen.test.tsx` assertion was updated to the coded `verificationVerified` label. Evidence: targeted Vitest 3 files / 102 tests green. This is a clinical-safety label fix, not a coverage change.
- **Optional reviewer items deferred to the follow-up task (no gate impact).** The code reviewer marked four items Optional: the banner `<h3>` precedes the chart section `<h2>` in DOM order; `age`/`sex` fixture strings are shown verbatim under `locale="ar"` while `age`/`sex` message keys exist; `FollowUpCard`'s override-reason error is not bound via `aria-describedby`/`aria-invalid` and its input id is not revision-derived; and the results chip uses one phrase for both singular and plural counts. All are low-impact or need changes outside this story's scope; the coverage auditor's Optionals were style-only assertions and one doc line reference (the line reference was corrected).
- **Entry point and reachability.** `ChartScreen` is currently rendered only by tests; the routed staff chart is `ChartPage` (`src/features/chart/routes.ts`), which renders `LongitudinalChart` directly. This story was scoped by the brief to the synthetic chart screen inside `features/chart`, so the approved-design chrome is built there and the production route is unchanged. A separate task is needed to adopt the banner/tabs/cards in `ChartPage` (and in `app/AppShell.tsx` for the dark top bar) — neither is in this task's scope and neither was edited.
- **Status colour tokens are unavailable.** `src/theme/tokens.ts` exposes only background/foreground/border/accent/focusRing/spacing; `theme/` is out of scope. Allergy, language, results, High/Normal, required and stale states therefore carry a word, a shape-distinct glyph (`⚠`, `◍`, `!`) and a token boundary instead of literal red/blue/amber. No raw hex was added. If a reviewer requires a literal colour match to the PNG, that needs a status-colour-token task, not a local exception.
- **Focus order drove DOM placement.** The out-of-scope `tests/responsive/features-chart/ChartScreen.responsive.test.tsx:226-252` asserts that focusables inside the chart-labelled region before `documents` are exactly `[longitudinal, 3 table scrollers, 4 textareas, 2 buttons]` for the signed alpha fixture. Banner and tabs were placed outside that region and the follow-up card only renders for editable drafts, so the contract stays green with a logical DOM order.
- **Required-field gate is deliberately scoped.** `api.ts:399-401` maps the wire's single content string to `{subjective: content, objective:'', assessment:'', plan:''}`. An unconditional Plan gate would permanently disable Sign on `NotePage`; `planRequired` is passed only by the synthetic `ChartScreen`. The domain `signDraft` still rejects every incomplete draft, which keeps the existing `signError` announcement reachable (covered by a test that empties a non-Plan field).
- **Conflict recovery moved, not duplicated.** `ConflictState` now renders inside the note card from `NoteEditor` with callbacks supplied by `NotePage`; `NoteNotices` still maps every non-conflict `TransportError` through `StateView.forTransportError`. Existing Compare/Reload/Copy effects and the compare panel are unchanged.
- **Override reason is not persisted in this preview.** `FollowUpCard` requires a non-blank reason and calls `onOverride(reason)`; the synthetic `ChartScreen` only announces the outcome. A real booking/override workflow must persist the reason and actor for CLN-06 provenance. Likewise, `New order`/`Prescribe` announce that they are unavailable rather than fabricating an order.
- **Synthetic-only data.** All names, MRNs, issuers, signers and checksums are clearly synthetic (`Synthetic…`, `SYN-…`, `synthetic.*`); `PatientViewResponse` remains `{id, displayName}` and no demographic was fabricated on the wire.
- **Test-runner noise.** jsdom prints `Not implemented: navigation (except hash changes)` from pre-existing `UnsupportedBrowserPage` tests; all 2732 tests pass and no change was made to those tests.

## Lessons for workers

- Read the out-of-scope responsive tests before changing a screen: a strict focus-order assertion can dictate where new focusable elements may sit in the DOM.
- Check how the API maps wire data before gating a UI action on a field: `contentToSoap` fills only `subjective`, so a four-field requiredness rule belongs to the synthetic preview only.
- Strict ESLint `max-lines-per-function` (150) and `complexity` (12) fire quickly when JSX is added to an existing component; extract presentational subcomponents early instead of disabling rules.
- With `exactOptionalPropertyTypes`, declare new optional fields as `foo?: T | undefined` if tests (or callers) pass explicit `undefined`.
- Global 100% coverage can hide a single uncovered branch in a new component: run `npm run test:coverage`, read the per-file table, and name a test for every new branch in `## Coverage` before finishing.
