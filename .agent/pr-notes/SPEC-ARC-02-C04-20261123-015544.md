# SPEC-ARC-02-C04 — ARC-02 clause 4 (API test): Separate migration and runtime roles

## Summary

Adds a test-only, catalog/JDBC-level integration test proving that the Flyway
migration role (`orevia_migrate`) and the application runtime role
(`orevia_app`) are distinct and least privileged, that forced row level
security binds even the owning role, that a missing tenant context fails closed,
and that the runtime role cannot apply migration DDL. Adds the clause decision
document. No production code, migration, contract, existing test, script,
tracker, workflow or agent file was changed.

## Affected requirements

ARC-02 (Isolation) clause 4: "Separate migration and runtime roles." The whole
ARC-02 paragraph was read in `PROJECT_V1_SPEC.md:118`.

Acceptance mapping: one positive test for the rule being met and three negative
tests (wrong role / peer tenant, missing context, forbidden DDL), exactly as the
task requires; clause doc Status "Proven by tests" with `## Gap: None`.

## Risk class

Cross-boundary by subject (database roles, deployment configuration), but the
change itself is test-and-doc only. No production boundary moves.

## Review owner

Senior PostgreSQL/SQL/Flyway specialist for the SQL semantics; code reviewer,
coverage auditor and DevSecOps for the finished change (see `## Review verdicts`).

## Data changes

None. The test creates and drops a synthetic database
`orevia_separate_roles_it` (owner `orevia_migrate`) and seeds two
synthetic organizations with fixed UUIDs and facility codes. Roles are
cluster-wide: created with `IF NOT EXISTS` and force-altered to
`LOGIN NOBYPASSRLS NOCREATEDB NOCREATEROLE`, never dropped. No migration,
backfill, lock or volume impact; rollback is the database drop in `@AfterAll`.

## Authorization boundaries and audit events

The proof is about the database role boundary: `orevia_app` is a non-owner
without `BYPASSRLS` and without `CREATE` on `public`; tenant visibility depends
on transaction-local `app.current_org`. No new role, permission, route or audit
event is introduced, and no PHI, credential or token appears in fixtures, logs
or notes.

## Migration and rollout considerations

None. The clause is already implemented in `db/migrations/V2__rls_roles_policies.sql`
and `infra/app/start.sh`; this change only evidences it. Entry point to test
trace: `infra/app/start.sh:47-49,65,72` provisions the two roles, gives the DB to
`orevia_migrate`, applies migrations as that role and starts the API as
`orevia_app`; `application.yml:6,11-12` supplies the runtime user and
disables Spring Flyway; the test reproduces that setup with real Flyway on a
synthetic DB and asserts on `pg_roles`, `pg_class`, `pg_tables`,
`has_schema_privilege`, `current_user` and real tenant-scoped row counts.

## Lessons for workers

- A non-owner role is subject to RLS even if `FORCE` is removed: proving the
  runtime role's tenant filter does not prove FORCE RLS. Assert
  `pg_class.relforcerowsecurity` and check the owning role with no context.
- Catalog questions about schema objects must run inside the migrated test
  database; `public.facility::regclass` queried through the `postgres`
  maintenance database reports "relation does not exist".
- `-Pno-security` sets `spotbugs.skip=true`; pass `-Dspotbugs.skip=false`
  explicitly or `spotbugs:check` is vacuously green. Never combine
  `-Pfast` with `-Dgroups=integration` — `fast` excludes that tag.
- Database roles are cluster-wide: create with `IF NOT EXISTS`, then `ALTER ROLE`
  to force least-privilege attributes so a parallel suite cannot poison them.
- In this worker image `git ls-files -v opencode.json` = `S` explains all six
  `test_check_pack` failures and the worker-check stop; confirm once, record it,
  run the remaining stages individually, and never regenerate that file.
