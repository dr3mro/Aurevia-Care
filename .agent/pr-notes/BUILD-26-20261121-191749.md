# BUILD-26 — Persist field dictionaries and template versions with JDBC

## Summary

Replaced the process-local `InMemoryTemplateStore` as the production adapter for `TemplateService` with a tenant-owned JDBC store backed by a new Flyway migration. Template versions, field dictionaries, saved note revisions and audit facts now survive a restart and are forced-RLS isolated. `TemplateService` is now a Spring `@Service` that receives the store by injection. A saved note captures its exact field definitions and the entries of its referenced dictionaries at save time, so a later dictionary or template change cannot rewrite an old note's meanings.

## Affected requirements

- CLN-04: versioned templates, governed field dictionaries, immutable published versions, historical field meanings preserved per saved version.
- ARC-02: active-organization key on every statement plus forced RLS, non-owner grants, tenant-local version counters, tenant-isolated reads.

## Risk class

Cross-boundary (new persistence, migration, service bean) with clinical-safety aspects (immutable published template versions; historical note meanings). Reviewed against the engineering quality bar.

## Review owner

Senior Java and Spring Boot / Senior PostgreSQL and Flyway / Senior Java Build and Test Tooling (simulated specialist review). No human clinical evidence.

## Data changes

New `db/migrations/V80__template_store.sql` (`Change: expand`, additive, no backfill) creates five tables:
- `template_field_dictionary` — `(organization_id, dictionary_key)`, entries JSONB, approval state.
- `template_version_sequence` — one atomic per-tenant, per-family version counter.
- `template_version` — `(organization_id, kind, version)`, full field set as JSONB; a `BEFORE UPDATE OR DELETE` trigger rejects any rewrite of a published version.
- `template_note_revision` — append-only; authored values, exact field meanings and dictionary-entry snapshot as JSONB.
- `template_audit_event` — append-only with ordered `event_id`.

Every table has ENABLE + FORCE RLS, a `tenant_isolation` policy using `app_org()` with `WITH CHECK`, and explicit grants/revokes to `orevia_app`. A `guard_published_template_version()` trigger (granted only to the runtime role) enforces immutability for every role, including the owner. Rollback is forward-fix only: drop the V80 tables/triggers/functions in a later contract migration; no production data exists yet.

## Authorization boundaries and audit events

`TemplateService` keeps role checks from the freshly supplied `TemplateActor`: defining stays tenant_admin/clinical_governance, approving stays clinical_governance, reading stays open to active roles, audit review stays privacy_auditor/tenant_admin. New `saveNote` is clinician-only; `savedNote` is a tenant-scoped read. Every new command appends a `TemplateAuditEvent` through the store (`TEMPLATE_NOTE_SAVE` with SUCCESS/NOT_FOUND/INVALID outcomes; `TEMPLATE_READ` for saved-note reads). The organization is always taken from the actor and is part of every store key and SQL predicate; no body-supplied organization is trusted.

## Migration and rollout considerations

Applied by `orevia_migrate`; the runtime role has no DELETE/TRUNCATE and no BYPASSRLS. Version allocation uses the same atomic counter pattern as V85, so concurrent definers cannot collide. `bash db/check.sh` applied V80 and passed the generic forced-RLS/role-selection/isolation/append-only assertions.

## Findings

- The template domain still has no HTTP controller, so `TemplateService` remains in the `unreferenced-service` wiring baseline despite now being a real Spring bean with a durable JDBC store. The story scoped only the store and service bean; an HTTP/OpenAPI entry point needs its own story.
- `check-pack` (and therefore `scripts/check.sh`, `scripts/quick-check.sh` and `scripts/python-coverage.sh`) fails locally solely because the cloud worker's worktree `opencode.json` is the CI profile under `skip-worktree`; `git diff` shows no tracked change to it. This is the documented OPS-CW-003-01 measurement artifact, not a code defect.
- `coverage` (Python) is not installed in this worker, so the script-coverage numeric check was skipped locally; no scripts were changed.

## Lessons for workers

In a swarm worker, always check `git ls-files -v opencode.json` before treating a `check-pack`/`gen-opencode.py --check` failure as your own: flag `S` means the worktree holds the CI profile and those checks measure the wrong file. Run the remaining gate steps individually and record the artifact instead of editing the protected file.

What was tried: re-ran the check directly, compared HEAD and worktree bytes, and ran every other policy/test/coverage/DB gate individually (all passed; SpotBugs 0 findings, JaCoCo 100% on all touched classes, db/check.sh green).
