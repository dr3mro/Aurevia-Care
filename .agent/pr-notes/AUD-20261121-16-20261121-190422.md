# AUD-20261121-16 — Wire the CLN-04 dictionary services that no production code calls

## Decision (recorded this run)

**Outcome chosen: WIRE, not delete.** Deletion is infeasible inside the declared scope:
`it/catalog/ClinicalDictionaryTest.java` and `it/catalog/DiagnosisCatalogTest.java`
(outside the allowed `it/catalog/dictionary` test path) construct both services with
`new` and would fail to compile. A new migration is also impossible: `db/migrations`
is outside scope and this task has no `reserved:` version.

The two services are now Spring `@Service` beans called by a thin tenant-owned
`@RestController` inside `catalog/dictionary`, backed by the existing durable
`config_entry`/`config_approval` tables through `ConfigurationService`
(namespaced keys `cln_dictionary.*` and `cln_diagnosis.*`, no new schema, forced RLS
already present). The no-arg constructors remain for the unit-level domain tests.
The HTTP integration test proves the entry point, tenant isolation, distinct-reviewer
approval and restart durability.

Specialist review (both simulated, source/tool-based): `smartclinic-software-architect`
and `smartclinic-senior-backend` recommended this option and rejected the in-memory
controller (cross-tenant singleton state / fake durability). Their findings drove the
`DurableVersionStore` design, the `@Autowired` constructor, the actor-derived approver
and the Jackson 3 mapping.

## Findings

- `contracts/` is outside this task's scope, so the new `/api/v1/clinical-catalog/**` endpoints are not in the OpenAPI document or regenerated client. This is a required follow-up (task-request below), not a claim that the contract gate passed.
- `config_entry.value` is capped at 4000 characters by `ConfigurationService`; a very large dictionary version would be rejected with 422 `INVALID_VALUE`. No inflation/compression was added; this matches the existing catalog behavior.
- The distinct-reviewer check compares the stored defining subject with the approving subject. `ConfigurationService` separately derives the recorded approver id from the authenticated actor inside its tenant-guarded transaction, so a spoofed `Approval.approver` payload is ignored (asserted in `approveIgnoresPayloadApproverAndRecordsTheNamedApproval`).
- Deletion was rejected with tool evidence: the two out-of-scope `it/catalog/*Test.java` files compile against both services.
- No patient data, credentials or real identifiers appear in fixtures.

## Lessons for workers

- Before naming a new Spring adapter with an injected `ObjectMapper`, check the class-name suffix in `apps/api/spotbugs-exclude.xml`: only `Service|Repository|Controller|Store|Interceptor|Guard|Appender|Configuration` are exempt from `EI_EXPOSE_REP2`. A domain-appropriate `...Store` name avoided a new suppression.
- Mockito consecutive `when(...).thenThrow(a); when(...).thenThrow(b)` re-invokes the first stub during the second stubbing; use `thenThrow(a, b)` for sequential outcomes.
- `check-wiring.py` 'unreferenced-service' only needs another src/main class to *mention* the service; a thin injected controller clears it, but reachability without a durable store is cosmetic — prove persistence with a fresh service instance.
- In this checkout, `check-pack.py`/`test_check_pack` fail on the worktree `opencode.json` CI-profile artifact; compare `git show HEAD:opencode.json` before treating it as your own regression.
