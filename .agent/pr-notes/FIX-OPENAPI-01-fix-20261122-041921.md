## Lessons for workers

- When a fix pass finds that the branch equals `origin/main` on all scoped
  content and the targeted tests are green, the correct action is to verify and
  record completion evidence — not to re-apply the fix or add a new
  test/allow-list edit. Repeating the re-merge or re-documenting a deliberately
  removed API defeats the earlier revert.
- `git merge-base --is-ancestor origin/main HEAD` plus an empty `git diff
  origin/main -- <scoped files>` is the fastest proof that a stale-merge fix is
  fully present before spending time on tests.
- A red `check-pack: opencode.json is stale` in a cloud worker is the skip-worktree
  CI profile, not a change defect. Confirm with `git ls-files -v opencode.json`
  and by comparing worktree vs `git show HEAD:opencode.json`; do not regenerate or
  commit that file. If you run the generator to compare, restore the CI bytes
  from `.github/opencode.ci.json` afterwards.
- Unset `CHECK_SCRIPT`, `BRANCH_PREFIX` and `BASE_BRANCH` when running the module
  `check.sh` files directly so the root swarm gate does not override them.
- Do not run the full `mvn verify` or whole integration suite as a worker; run
  only the touched test classes and leave the full gate to the integrator.
- A global `git grep` for conflict markers can flag Javadoc text already
  committed on main; check `git show origin/main:<path>` and the branch diff
  before treating it as a merge defect.
