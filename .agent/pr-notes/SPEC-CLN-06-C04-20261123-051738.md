# SPEC-CLN-06-C04 — CLN-06 clause 4 API test

## Summary

Adds an HTTP-level integration test proving that a CLN-06 care-team action task
keeps its accountable owner and facility-local due date and records an outcome
only when an authorized clinician closes it. Test-only story: no production
code, contract or migration changes. Clause behaviour is already implemented in
`scheduling/followup`; `chart/clauses` is only the mandated clause-test home.

## Affected requirements

CLN-06 (clause 4 only: "Care-team action tasks track owner, due date and outcome.").
Clauses 1-3 (interval, override, booking) are deliberately not re-tested.

## Risk class

Routine (test-only, no product surface change). Boundary assertions cover role
authorization and tenant concealment, so read-only security and code review were
run.

## Review owner

Primary agent; read-only reviewers: plan-reviewer, test-engineer, code-reviewer,
coverage-auditor, devsecops.

## Data changes

None. No migration, backfill, lock or volume impact, rollback or forward-fix.
Synthetic fixtures only. The test seeds rows into `public.follow_up_suggestion`
and `public.care_team_task`, both already protected by `ENABLE`/`FORCE ROW LEVEL
SECURITY` and a tenant-isolation policy in `db/migrations/V74__build_05.sql`.

## Authorization boundaries and audit events

No audit event is added or changed. The test observes the existing boundaries:
`APPOINTMENT_BOOK` opens a task (reception), `APPOINTMENT_COMPLETE` records an
outcome (clinician), `APPOINTMENT_READ` lists tasks, and a peer tenant's read or
completion of another tenant's task is concealed as 404. Production audit events
`FOLLOWUP_TASK_CREATE`, `FOLLOWUP_TASK_COMPLETE` and `FOLLOWUP_TASK_READ` are
exercised through their real entry points, including their DENIED/CONFLICT and
NOT_FOUND paths.

## Migration and rollout considerations

None. No deployment or rollout action.

## Lessons for workers

- For a test-only clause story, seed one suggestion per test with a fresh UUID
  and scope every "no row" assertion on both `organization_id` and
  `follow_up_id`. A table-wide count in a shared database makes a suite fail
  nondeterministically with JUnit's non-source execution order.
- Use `-Pno-security -Dgroups=integration` with a `-Dtest=ClassName` filter and
  read the Surefire `.txt`; `-Pno-security,fast -Dgroups=integration` silently
  runs zero tests because `fast` sets `excludedGroups=integration`.
- A `git ls-files -v opencode.json` result of `S` explains `test_check_pack`
  failures in a cloud worker; record the final line once and run the remaining
  policy stages individually instead of regenerating a protected file.
