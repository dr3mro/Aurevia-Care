## Authorization boundaries and audit events

Tenant comes from `useActiveOrganization()` on every request descriptor (`X-Active-Organization`);
role from the session via `useRole()`, never from the URL, query string or browser storage.
`availableActions` offers responses only in the `requested` state and only to `clinician`,
`lab` or `radiology`, mirroring the screen map and the server's recipient role set. The API owns the
audit events for accept/reject/clarify. No patient name, clinical payload or reason is placed in a
URL, page title, log or browser storage; the opaque patient identifier is shown only as data
returned by the API. A `beforeunload` guard protects a typed reason from silent loss.

## Findings

1. **Scope note on `check.sh` (not a defect in this story).** The canonical gate's only failure is
   the two exact-match route-list tests in `src/app/routes.test.tsx` and
   `tests/app/AppShell.test.tsx`. The diff includes routes from three other in-flight features, so
   the failure predates and is independent of this story's correctness. FIX-ROUTES-01 (currently
   `[-]`, owner swarm-1) explicitly replaces those fixed lists with resilient checks and is the
   owner; the integrator is scheduled to merge it before this story. I did not edit either file.
   Next step: once FIX-ROUTES-01 lands, re-run `bash apps/staff-web/check.sh`; all steps should be
   green because every orders-specific check already passes here.
2. **Clinical-safety concern carried forward (reviewer finding 6, unresolved).**
   `OrderView.patientId` from `GET /api/v1/orders/{id}` is documented in `OrderView.java` as the
   *sending* organization's patient identifier, while `Xch03Service.accept` expects a locally
   verified receiver association (`localPatientId`). This client sends the sender's opaque id with
   bounded defaults `TREATMENT` / `STANDARD`. Verifying a local association needs
   `POST /api/v1/exchange/work-items/{id}/verify-patient`, which is outside this story's endpoint
   list and scope. Accept must not be used for real patients until a follow-up story sources
   `localPatientId` from the verified work item; no change was made here.
3. The generated OpenAPI client declares only `GET /api/v1/orders`. Detail, history and the three
   response paths use the same URL-substitution helper used by the scheduling and admin features;
   `buildRequestDescriptor` still owns tenant, correlation, version and idempotency headers. No
   contract or generated file was edited (outside scope).
4. `GET /api/v1/orders/{id}` returns no recipient state, so the current task state is derived from
   the newest XCH-03 history event (`toState`), defaulting to `requested` for empty history. The
   wire state set is bounded by the server; the cast is documented in `domain.ts`.

## Lessons for workers

- Read `.agent/pr-notes/<task>-<timestamp>.md` from earlier attempts first: READY-26's feature was
  already committed, so the correct move was verify-and-hand-off, not reimplementation.
- In this worker image run `npm ci` before any Vitest command; bare `npx vitest` resolves a
  different Vitest and fails to load `vitest/config`.
- When several parallel features self-register routes, prove 100% coverage of only your own area
  with `npx vitest run --coverage --coverage.include='src/features/<name>/**' src/features/<name>`
  instead of relying on the whole-suite gate, which can be red for another worker's route tests.
- Adding a feature route breaks the two exact-match route-list tests; that is FIX-ROUTES-01's job,
  not a reason to edit files outside your scope.
- An idempotency key must be bound to the command payload, not only the action name, or editing a
  reason turns the retry into an unrecoverable 409 (ARC-03).
