# AUD-20261121-04 — Deduplicate the catalog CODE validation regex

## Summary

The identical trust-boundary rule `Pattern.compile("[A-Za-z0-9][A-Za-z0-9_.:-]{1,63}")` was
declared three times (`catalog/CatalogService.java`, `catalog/dictionary/DiagnosisCode.java`,
`catalog/dictionary/DictionaryField.java`). Added one typed primitive
`com.aurevia.smartclinic.api.contract.CatalogCode` owning the single pattern, with a static
`code(String)` factory that returns a validated value and throws `IllegalArgumentException`
with a deterministic, non-sensitive message on invalid input. Removed all three declarations
and routed all three callers through the primitive. `CatalogService` translates the primitive's
`IllegalArgumentException` into its existing `ApiException(422, INVALID_CODE, ...)`; the two
dictionary records propagate the same `IllegalArgumentException` type they threw before.

Added valid, invalid, max-length (64), over-length (65) and Arabic/RTL acceptance tests at
all three callers, plus direct coverage of the new primitive's public API.

## Findings

- Only external detail change: malformed codes in the two dictionary records now carry the single
  deterministic message `code must be 2-64 letters, digits or _ . : -` instead of the caller-specific
  `invalid diagnosis or procedure code` / `invalid field code`. The exception **type** is unchanged.
  `grep -rn 'invalid diagnosis or procedure code\|invalid field code' apps/api/src` returned no hits,
  so no caller or test depended on the old text.
- `CatalogService.validateName` still dispatches on the string `name` (`"family"` vs `"code"`).
  This is pre-existing; it was kept to minimize the diff. A future cleanup could split it into
  `validateFamily` / `validateCode` methods.
- Other modules contain similarly shaped regex literals (`Xch03Inputs`, `PatientService`,
  `LabInputs`, etc.) with different alphabets/lengths; they are out of this story's declared scope
  and were left untouched.
- The three failing `test_check_pack` cases are the skip-worktree CI-profile artifact described in
  Test evidence, not a change defect.
- Senior-backend review returned three LOW findings, all fixed in the amended commit:
  1. The deterministic message was implemented but not asserted — `CatalogCodeValidationTest` now
     asserts `getMessage()` equals `CatalogCode.INVALID_MESSAGE` for an Arabic/RTL rejection (proving
     no input echo), and `CatalogServiceTest.codeValidationUsesTheSharedBoundedRule` now asserts the
     translated error code `INVALID_CODE` as well as status 422.
  2. The human-readable rule text was duplicated between `CatalogCode.INVALID_MESSAGE` and
     `CatalogService.validateName` — `INVALID_MESSAGE` is now public and reused by the service's
     code branch, so both the regex and its description are single-sourced.
  3. The deliberate `IllegalArgumentException` choice (vs sibling `ApiException` primitives) was
     undocumented — added a one-line Javadoc rationale preserving the records' contract and the
     service's translation.

## Lessons for workers

- When deduplicating a validation rule shared by a domain record and an API service, let the shared
  primitive throw plain `IllegalArgumentException` and have the API service translate it to its
  `ApiException`. That preserves both the record contract and the HTTP 422 behavior while removing
  the duplicated rule.
- A record primitive with a static `code(...)` factory reaches 100% METHOD coverage by exercising
  `value()`, `equals()`, `hashCode()` and `toString()` once from the owning caller's test; JaCoCo
  reported 100% on the new record.
- In a cloud worker, `git ls-files -v opencode.json` returning `S` means the worktree holds the CI
  profile. `check-pack.py` and `test_check_pack` then fail for that reason alone — verify with
  `git show HEAD:opencode.json` and do not regenerate the file.
- Compile first when running SpotBugs alone (`-DskipTests compile spotbugs:check`); a bare
  `spotbugs:check` is vacuously green.
