## Findings

1. **Advisor brief is internally inconsistent (recorded, not followed).** The brief's positive chain proposes a change and then calls `request-cancellation` on the same order without a recipient response. `ExchangeResponseService.requestCancellation` calls `requireState(ACCEPTED)` and `proposeChange` leaves the order in `CHANGE_PENDING`, so that chain would return 409, never `cancellation_pending`. The test uses two independent seeded accepted orders and records the reason here; the clause is proved by both branches independently.
2. **Known worker-environment false positive (tool evidence).** `git ls-files -v opencode.json` → `S opencode.json`. Worktree `opencode.json` sha `9d797518…` equals `.github/opencode.ci.json` and differs from the HEAD blob `69db5d8e…`: `agent-run.sh` installed the CI profile under skip-worktree. Therefore `check-pack.py` says "opencode.json is stale", `worker-check.sh` exits 1 at that stage, and the six `test_check_pack.py` cases fail. The committed local profile is the correct generated one. No file was regenerated or committed for this; the integrator owns the full gate.
3. **No task request.** The missing full OpenAPI entries for the XCH-03 routes are pre-existing and separately tracked in `contracts/openapi/missing-routes.txt:342-349` / FIX-OPENAPI-01; this slice cannot edit `contracts/` and does not need to.
4. **Pre-existing, out-of-scope observation.** Three committed `exchange/hl7/*.java` files contain conflict-marker lines inside Javadoc comments on HEAD. They do not affect compilation (javac exit 0 confirmed) or this clause; left untouched as out of scope.
5. **Optional reviewer suggestions not taken.** DevSecOps noted that `count(String sql)` accepts caller SQL (all current callers pass fixed literals through a tenant-bound connection) and that cross-tenant denial is not re-asserted here (already proven end to end in `ExchangeResponseExchangeTest.tenantsWithIdenticalOrderCodesStayIsolated`); both are out of this clause's scope.
6. **Optional code-reviewer findings addressed.** The class Javadoc now names the two non-accepted fixture orders explicitly and `seedTenant`'s Javadoc now says six orders. No Critical or Required finding was raised by any reviewer.

## Lessons for workers

- When a brief names an API sequence, verify it against the production state machine before writing the test: a post-acceptance cancellation must start from `accepted`, not from `change_pending`, so use two independent orders or respond to the change first.
- For clause-evidence stories where the rule is already built, prove the rule with outcome assertions (`/code`, ledger counts, revision links, checksum served while pending) rather than relying on a red-first production change; a skipped or assertion-free test proves nothing.
- In a cloud worker, confirm `git ls-files -v opencode.json` is `S` and compare the worktree sha with `.github/opencode.ci.json` before treating a stale-pack failure as a defect; never regenerate or commit that file.
- Give every integration fixture its own database name and one order per negative case: shared append-only ledgers leak versions and states between tests.
