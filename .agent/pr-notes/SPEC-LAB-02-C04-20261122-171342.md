# SPEC-LAB-02-C04 — Approved site reference ranges and critical policies are versioned

## Summary

LAB-02 clause 4 clause-proof task. Added one new test class and one new clause note. The tests prove
that the LAB-02 domain kernel selects, applies and stamps the newest approved effective version of a
reference range and a critical policy, and that future-dated, unapproved, expired and empty-catalog
inputs are refused. The clause is **not** reachable through the HTTP API today, so the note's status
is `Partly proven` and the missing HTTP chain is fully described as a gap. No production code,
existing test, migration or contract was changed.

## Findings

1. **Gap confirmed (not a defect of this change).** The versioning mechanism is built in the domain
   kernel but is not reachable through HTTP. `ResultConfiguration` injects
   `new LabPolicyCatalog(List.of(), List.of())`; `labflow.results.ResultEntryService.flag` hard-codes
   `DEFAULT_POLICY_VERSION = 1` from caller-submitted bounds; no controller approves, versions or
   effective-dates site ranges/critical policies; no migration persists them. V23 and V25 are
   adjacent mechanism only. Status is therefore `Partly proven`, never `Proven by tests`.
2. **Deviation from story step 3 (authorized by the brief's Risk #2).** The @Disabled HTTP gap test
   was deliberately NOT added: `scripts/check-constraints.py` rejects any new `@Disabled`/`@Ignore`
   Java line (probe exit 1) and AGENTS.md forbids skipped tests. The complete HTTP test (method name,
   fixture, assertions and negative cases) is written in the clause note's `## Gap` section, and the
   pull request stays green with four passing tests and zero skipped tests. A later task should add it
   once the HTTP approval/persistence chain exists.
3. **Brief inaccuracy.** The brief stated that `scripts/check-docs.py` requires the exact four clause
   headings and the clause sentence word for word. Reading `scripts/check-docs.py` shows it validates
   Markdown links, requirement IDs and structural faults, not clause-note headings. The four exact
   headings and the word-for-word sentence were included anyway, per the story.
4. **Pre-existing, out of scope.** HEAD contains committed conflict markers in
   `apps/api/src/main/java/com/aurevia/exchange/hl7/Hl7ParseException.java`, `Hl7Parser.java`
   and `Hl7Segment.java` from another worker's merge (`origin/swarm/BUILD-37-469`), inside Javadoc
   comments. Not touched by this change and outside its scope; flagged for the integrator.
5. Known false positives recorded under Test evidence items 6–7 (skip-worktree `opencode.json`).

## Lessons for workers

- A new `@Disabled("GAP: …")` test is rejected by `check-constraints.py` even though older GAP tests
  are grandfathered; keep the PR green with passing tests and put the full gap test in the clause
  note instead.
- `check-pack`/`test_check_pack`/`python-coverage.sh` failures in a cloud worker are usually the
  skip-worktree CI `opencode.json` profile; confirm with `git ls-files -v opencode.json` (`S`) and
  `git show HEAD:opencode.json` before changing anything. Never regenerate that protected file.
- `ReferenceRange`/`CriticalPolicy` require `low < high` even for versions you only add to prove they
  are ignored; build rejected fixtures with valid bounds (e.g. 1–10) and vary `approved`, `from` and
  `to` instead of inverting the bounds.
