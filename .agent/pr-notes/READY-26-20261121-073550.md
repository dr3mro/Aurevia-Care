# READY-26 — Orders list, detail and recipient responses

## Summary

Added the staff-web `orders` feature under `apps/staff-web/src/features/orders`: an API-backed
`/orders` worklist with work-item state filter and cursor paging, an API-backed `/orders/:id`
detail with released order fields and an append-only task-state timeline from XCH-03 history,
and the three recipient responses (accept, reject, clarify). Responses carry `If-Match` from
the XCH-03 history version and an `Idempotency-Key` bound to the exact action **and payload**, so
a byte-identical retry reuses it while a changed reason/question or a different action gets a
fresh key. Reject and clarify require a reason with a linked error summary; 409 and 412 show the
conflict state, keep the typed reason, and offer working Compare / Reload / Copy controls. A
browser-level guard warns before leaving with a typed reason. Timeline states and actions are
localized. Routes self-register through
`features/orders/routes.ts`; no shared router or navigation file was edited.

## Affected requirements

XCH-01 (released order fields), XCH-02 (workflow state timeline), XCH-03 (accept / reject with
reason / clarify with question), ARC-03 and ARC-04 (version precondition, idempotency, machine
readable failures), WEB-09 (all seven screen states), UX-01 (English and Arabic, RTL, logical
properties).

## Risk class

Cross-boundary: four real API reads and three guarded commands. No clinical decision is
automated (PRD-06); the API owns authorization, audit and state transitions. Synthetic data only.

## Review owner

Senior React and Vite / Senior TypeScript. A read-only bounded specialist review ran from the
`smartclinic-senior-react` subagent (evidence: static review of the checked-out files, no commands
run); its five in-scope findings were fixed and re-verified. QA and clinical feedback are
simulated, not human acceptance.

## Data changes

None. No Flyway migration, backfill, lock or volume impact; no reserved migration version used.

## Authorization boundaries and audit events

Tenant is taken from `useActiveOrganization()` on every descriptor (`X-Active-Organization`);
role from the session role via `useRole()` (with an explicit test override), never from URL, query
string or browser storage. `availableActions` offers responses only in the `requested` state and
only to `clinician`, `lab` or `radiology`, mirroring the screen map and the server's recipient
role set. The API owns the audit events for accept/reject/clarify. No patient name, clinical
payload or reason is put in a URL, page title, log or browser storage; the opaque local patient
identifier is displayed only as data returned by the API.

## Migration and rollout considerations

None. The two route chunks are 1.97 kB and 1.03 kB gzip, inside the WEB-08 250 kB budget.

## Clinical and architecture review

PRD-06: the screen only displays server state and forwards explicit user commands; it never
decides accept/reject/clarify. The API remains authoritative for transitions, authorization and
audit. No real clinician or patient participated; this is simulated review only. Per-site
clinical acceptance remains a G5 human gate.

Bounded senior-react review (static, reviewer evidence) raised six findings. Five were fixed and
re-verified by `bash apps/staff-web/check.sh`: (1) high — key reuse with a changed reason could
produce an unrecoverable 409; the key is now bound to the payload digest; (2) conflict Compare
and Copy were inert; both now work; (3) typed work had no navigation guard; a `beforeunload`
guard was added; (4) timeline tokens were raw English in Arabic; states and actions are now
localized; (5) a failed Load more was swallowed; it now shows a retryable banner while preserving
rows. Finding (6) is an unresolved clinical-safety concern recorded below.

## Findings

0. **Open clinical-safety concern (reviewer finding 6).** `OrderView.patientId` from
   `GET /api/v1/orders/{id}` is documented in `OrderView.java` as the *sending* organization's
   patient identifier, but `Xch03Service.accept` expects a locally verified receiver association
   (`localPatientId`). This client currently sends the sender's opaque id with the bounded
   purpose/retention defaults. Verifying a local association requires
   `POST /api/v1/exchange/work-items/{id}/verify-patient`, which is not in this story's endpoint
   list or scope. Accept must not be used for real patients until a follow-up story sources
   `localPatientId` from the verified work item; no change was made here.
1. Two shared exact-match route-list expectations needed the two new patterns:
   `apps/staff-web/src/app/routes.test.tsx` and `apps/staff-web/tests/app/AppShell.test.tsx`.
   These are outside the declared `scope` but are the direct consequence of READY-51's
   self-registering routes; git history shows READY-21/22/23 made the same minimal expectation
   updates for their own routes. Only the expected arrays were extended with `/orders` and
   `/orders/:id`; no other content changed. Flagged explicitly for the integrator's scope check.
2. The generated OpenAPI client declares only `GET /api/v1/orders`. Detail, history and the three
   response paths are built with the same URL-substitution helper used by the scheduling and
   admin features: `buildRequestDescriptor` still owns tenant, correlation, version and
   idempotency headers. No contract or generated file was edited (outside scope).
3. `GET /api/v1/orders/{id}` returns no recipient state, so the current task state is derived
   from the newest XCH-03 history event (`toState`), defaulting to `requested` for empty history.
   The wire state set is bounded by the server; the cast is documented in `domain.ts`.
4. The XCH-03 accept trust boundary requires `localPatientId`, `permittedPurpose` and
   `retentionPolicy`. The client sends the order's opaque patient id plus the bounded defaults
   `TREATMENT` / `STANDARD` (declared in `api.ts`), because no site configuration endpoint is in
   this story's scope. A future story should source these from approved site configuration.
5. `python3 -I scripts/check-pack.py` reports a stale `opencode.json` in this cloud worker; the
   file is skip-worktree with no diff from HEAD, so this is the known environment artifact, not a
   regression from this change.

## Lessons for workers

- In this worker image, `npm ci` is required before any Vitest command; `npx vitest` without it
  installs a different Vitest and fails to resolve `vitest/config`.
- The synthetic organization ids live in `features/scheduling/fixtures.ts`; importing them from
  `fixtures/synthetic` yields `undefined` at runtime without a typecheck error. Derive them from
  `syntheticOrganizations` instead.
- Vitest `mockRejectedValueOnce` for a command must be registered before the click, and a
  persistent conflict needs a `mockImplementation` router: a one-shot rejection is otherwise
  consumed by the initial loads or by the first retry, hiding the behavior under test.
- Adding a feature route breaks the two exact-match route-list tests in `src/app/routes.test.tsx`
  and `tests/app/AppShell.test.tsx`; extend both expected arrays in the same change.
- An idempotency key must be bound to the command payload, not only to the action name. Reusing a
  key after the clinician edits a reason turns the retry into a guaranteed 409 under ARC-03.
