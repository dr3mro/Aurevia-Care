## Summary

Adds a focused real-PostgreSQL HTTP-level acceptance test for IAM-06 clause 1
("Record business purpose, role, facility and user for sensitive actions") and the
required clause-evidence document. The clause is already built in the `authz.access`
and `audit` slices, so the test is active (not `@Disabled`) and green: one positive
proof that a sensitive grant records purpose, role, facility and user in both durable
stores, and two negative refusals (wrong role, cross-tenant). No production code,
migration, contract or existing test was changed. Synthetic data only.

## Affected requirements

- IAM-06 (clause 1 only). Related evidence generators: OPS-02 (append-only audit),
  IAM-01/ARC-02 (tenant and facility scope). No new requirement IDs introduced.

## Risk class

Routine (test + documentation evidence for an already-implemented clause; no behavior
change). Reviewed against the cross-boundary rules because it exercises HTTP, service,
repository and RLS schema boundaries through a normal entry point.

Senior Java and Spring Boot (`smartclinic-senior-backend`), Test Engineering

None. The test creates and drops its own isolated database

## Authorization boundaries and audit events

The test proves the rule under the `synthetic-auth` profile with two synthetic tenants
that share the local facility code `MAIN`:
- positive: `clinician-a` in Org A opens a reasoned grant; the durable grant row carries
  `purpose=EMERGENCY_ACCESS`, `role_key=clinician`, `facility_code=MAIN`,
  `subject=clinician-a`, and the `audit_event` row carries `purpose`, `scope=clinician:MAIN`,
  `actor_id` (trigger-derived user) and `outcome=SUCCESS`;
- wrong role: `admin-a` is refused with 403 and no grant is written; the committed
  `DENIED` audit still records purpose, scope and the acting user;
- cross-tenant: the Org A audit/grant rows are invisible under Org B's forced RLS.
No existing audit event definition was added or changed; only assertions were added.

## Findings

- Source survey (step 1) — where IAM-06 clause 1 is implemented today:
  - Schema: `db/migrations/V11__emergency_and_support_access.sql` defines
    `public.emergency_access_grant` with `purpose`, `role_key`, `facility_code` and
    `subject`; `db/migrations/V1__tenant_schema.sql` defines `audit_event` (`purpose`,
    `scope`, `actor_id`, `correlation_id`); `V2__rls_roles_policies.sql` forces RLS;
    `V3__audit_chain.sql` makes it append-only and derives `actor_id` from `app.actor`;
    `V93__membership_facility_scope.sql` supplies facility-scope checks.
  - Code: `com.aurevia.smartclinic.authz.access` (`AccessController`,
    `EmergencyAccessService`, `SupportAccessService`, `AccessRepository`,
    `AccessContracts`, `AccessRules`); `com.aurevia.smartclinic.audit`
    (`AuditAppender`, `AuditRepository`, `AuditService`, `AuditEvent`, `AuditPage`);
    `com.aurevia.smartclinic.web.TenantContextInterceptor`;
    `com.aurevia.smartclinic.tenant.TenantContext`.
  - Contract: `POST /api/v1/access/emergency` is declared in `contracts/openapi.yaml`
    and generated into the staff-web client.
  - Existing coverage: `it/authz/AccessIntegrationTest.sensitiveActionsAreAuditedWithPurposeRoleFacilityAndActor`
    and `it/authz/emergency/Iam06SensitiveActionAuditTest` already exercise the same

- One grant writes three audit rows sharing a correlation id (`EMERGENCY_GRANT`,

- Pre-existing, outside scope and not touched: conflict markers inside Javadoc comments

## Lessons for workers

- When asserting on `audit_event` rows for a sensitive action, filter by `action` as
  well as `correlation_id`: one command writes several audit rows under the same
  correlation id. The first red run here failed only on this counting assumption.
- Clause-evidence tests live under `apps/api/src/test/java/<domain>/clauses` with the
  matching doc under `docs/spec/clauses/<domain>/`; create the domain folder if absent
  and name it after the business domain (`audit`), never after the story or gate ID.
- Do not run `scripts/worker-check.sh`, `scripts/check.sh` or full `mvn verify` in a
  swarm worker — they run every integration test and time out the run. Run the targeted
  `-Dtest=...` suite, SpotBugs after a compile, and the individual policy scripts.
- Confirm the skip-worktree `opencode.json` profile with `git ls-files -v` before
  reporting any `check-pack.py`/`test_check_pack.py` failure; it is environmental.
