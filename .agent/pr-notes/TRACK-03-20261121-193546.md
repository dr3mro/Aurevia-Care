# TRACK-03 — Staff web: partner interface and outage board

## Summary

Adds a self-contained staff-web feature under `apps/staff-web/src/features/partnerboard`. It renders one board per partner kind (lab, imaging, pharmacy) with interface health, the last observation time, the number of orders/prescriptions waiting, how long each has waited, the three separate exchange state axes, and the approved manual fallback with an in-page link to its procedure. Every value is synthetic and the screen says so; no partner is connected. A feature route registers the board at `/operations/partner-board` through the existing self-registering route glob. No dependency was added and no file outside `apps/staff-web/src/features/partnerboard` was changed.

The waiting rule keeps transmission, workflow and clinical review separate (XCH-02): a delivered transmission never closes an unreviewed or action-pending clinical task, a stale pending or failed transmission is stuck, and a rejection or clarification request from the recipient is stuck (XCH-03). Each partner has a distinct manual fallback (lab: manual upload; imaging: call; pharmacy: print) paired with delivery/verification evidence wording (PRD-02).

## Findings

- The generated staff client contract has no partner-interface health, backlog or fallback endpoint (`apps/staff-web/src/api/generated/openapi.d.ts` contains no partner path). The board therefore renders labelled synthetic fixtures rather than pretending to be live. A read model and endpoint are requested below and are not part of this story's scope.
- The board route is registered by `routes.ts` but the navigation rail (`src/app/navigation.ts`) is outside this story's scope, so there is no new rail item; the board is reachable by URL. A separate navigation story is requested below. Route tests remain green because they derive feature patterns from the glob.
- The bilingual bundle is deliberately named `partnerMessages.ts`, not `messages.ts`: `tests/messageParity.test.ts` discovers every `src/**/messages.ts` and compares against a fixed registry that this story may not edit. `partnerMessages.test.ts` enforces its own en/ar key, placeholder, non-empty and Arabic-script parity over all 53 keys.
- No `messages.ts`, `navigation.ts`, `shellText.ts`, generated client, config, script, workflow or agent file was created or edited. No npm dependency was added (`package.json` / lockfile untouched).
- Simulated `orevia-senior-react` review returned **no material findings** on XCH-02/XCH-03 state separation, accessibility, Arabic/RTL or dead code. Two non-blocking observations: (1) the three fallback regions shared one accessible name — fixed in this change by adding `fallbackRegion` (`{partner}` placeholder) and passing the partner display name to `FallbackPanel`, with en/ar landmark assertions in `PartnerBoardScreen.test.tsx`; (2) the synthetic lab→manual-upload / imaging→call / pharmacy→print mapping must come from site configuration when live wiring lands, not be treated as an approved site decision — captured in the API task request below. Reviewer ran no commands; all tool evidence above came from the implementer.

## Lessons for workers

- `tests/messageParity.test.ts` globs `src/**/messages.ts` and `stateViewMessages.ts` into a fixed registry. A new feature bundle with either exact filename breaks that registry test even though the registry is outside your scope; choose a distinct filename and add a local parity test.
- An aria-label is not a text node: assert it with `getByRole('region', { name: ... })`, not `getByText(...)`. JSX `{label}: {value}` also splits text into separate nodes, so exact `getByText` fails; use a regex or one interpolated message.
- When a fixture legitimately has two stuck rows, `getByText('Stuck')` finds multiple elements — assert `getAllByText('Stuck')` with the expected count instead of weakening the data.
- `bash apps/staff-web/check.sh` runs `npm ci` when `node_modules` is absent; run it before targeted tests so you use the pinned local Vitest rather than an `npx` download.
- The `MARKER-NON-ERROR-VALUE` console lines in the suite come from an existing intentional ErrorBoundary fixture; rely on the command's exit code, not on a clean console, when judging that gate.
