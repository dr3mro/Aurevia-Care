# RADFLOW-02 — API: signed interpretation reaches the referrer, addenda notify and need acknowledgment

## Summary

Adds a bounded `radflow/report` domain kernel that delivers a signed interpretation to the referring clinician, links addenda as new revisions with independent referrer notifications, keeps each addendum open until the verified referrer acknowledges that exact revision, and ages open addenda into an overdue queue. A signed initial report carries technique, comparison, findings and impression. The signer is the authenticated subject and signing is reserved for credentialed interpreters. Every referrer-facing read and queue — including revision history — is scoped to the verified referrer. Unsigned or unattested interpretations are refused before any delivery fact is recorded. In-memory state follows the RADFLOW-01 sibling kernel; persistence, OpenAPI regeneration and clinical sign-off remain separate work.

## Authorization boundaries and audit events

- Tenant: every command, read, queue and event list is keyed by the active `organizationId`; another tenant gets 404 or an empty list.
- Role: delivering a report or addendum requires `radiology_interpreter` only, via `RadRules.mayInterpret`, re-derived from `StaffRepository` inside a tenant-guarded `TransactionTemplate` on each request. No role is taken from a request body.
- Signature binding: the signer is `context.subject()`, not a request field. A report cannot claim another clinician's signature; the HTTP response's `revisions[0].signer` is asserted against the authenticated subject.
- Referrer identity: reading a report, reading its revisions, acknowledging an addendum, and filtering queues/events require the authenticated subject to equal the verified referrer recorded on the report.
- Revision binding: an addendum must supersede the current version; an acknowledgment binds one exact addendum version and a duplicate is refused.
- Events (ARC-05/OPS-02): `INTERPRETATION_DELIVERED`, `ADDENDUM_DELIVERED`, `REFERRER_NOTIFIED`, `ADDENDUM_ACKNOWLEDGED`, `UNSIGNED_REPORT_REFUSED`. Events carry identifiers only — no clinical narrative or image data. A refusal fact records that an unsigned report was never delivered.
- Existing domain types reused rather than duplicated: `com.aurevia.radiology.Interpretation`, `RadTypes.InterpretationKind`, `RadRules`, `ApiException`.

## Migration and rollout considerations

None in this change. The configured acknowledgment window is a Spring property `radflow.report.acknowledgment-window` (default `PT24H`) injected into the service; no default properties file was changed.

## Clinical and architecture review

Simulated `aurevia-senior-backend` review completed with two HIGH findings, both fixed before commit, plus two MEDIUM caveats and one low-severity hardening note:

- HIGH — signature not bound to the authenticated actor and staff allowed to sign: fixed by deriving `signer` from `context.subject()`, removing the signer from both request DTOs, and delegating `ReportRules.mayDeliver` to `RadRules.mayInterpret`. Negative tests: staff role denied over HTTP and in the kernel.
- HIGH — `revisions` disclosed the clinical narrative to any tenant member: fixed by replacing the unscoped `revisions` method with `revisionsForReferrer` and adding a 403 test for another subject over HTTP and in the kernel. The unscoped method was deleted, not left unused.
- MEDIUM — referrer is caller-supplied at publish: accepted as deferred wiring, the same boundary RADFLOW-01 uses; a report is addressed to a subject from the imaging order and membership binding needs an integration story. Not claimed as production-ready.
- MEDIUM — end-to-end proven only in memory (no migration/JDBC/OpenAPI): documented under Findings, outside this scope.
- Low — addendum stored `current.version()+1` without checking the addendum's own version: fixed with a `409 INVALID_SUPERSEDES` guard and a test.

No real clinician, radiologist or patient participated, so RAD-01 release-to-referrer clinical acceptance and G5 sign-off are not claimed. The existing `radiology` package's `ImagingService` already signs interpretations; this story deliberately adds the separate `radflow/report` delivery kernel rather than editing that service, matching the RADFLOW-01 sibling boundary.

## Lessons for workers

- When reusing a domain record such as `Interpretation`, re-check which invariants it already enforces. Its constructor guarantees a named signer, so adding a `signer().isBlank()` check in `ReportRules.isSigned` created an unreachable JaCoCo branch; delete the duplicate guard instead of writing a test that cannot exist.
- Generate coverage for only your touched classes with `... -Dtest=YourTest test jacoco:report` and parse `target/site/jacoco/jacoco.xml`. Full `verify` is forbidden for workers, but per-class branches are still provable.
- A `record`'s derived method (e.g. `version()`) is not a JSON property. Add it as a component when the client needs it; a `jsonPath("$.version")` assertion against a derived accessor fails.
- Events endpoints filtered by referrer must be requested with the referrer's subject; an interpreter's subject legitimately sees no referrer events.
