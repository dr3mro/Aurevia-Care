# LABFLOW-05 — API: partner outage fallback with manual result upload linked to the order and an unmatched queue

## Summary

Implemented the partner-outage manual result fallback for lab results. When the partner result interface is down, an authorized laboratory user can attach the original report (evidence) and key observations in against an order, with a mandatory non-sensitive reason. Identifier matching repeats the accession label check: a match links the evidence to the order and records an outage history fact; no match places the entry in an unmatched queue with a named owner and records the same outage history fact. Every command writes a tenant-guarded OPS-02 audit event with identifiers only. All new production classes are business-domain named and live only in the declared `labflow/outage` scope.

## Affected requirements

LAB-02 (manual result entry against the order, verification evidence separation), XCH-03 (linked version / recipient response context for a manually keyed result), PRD-02 (manual workflows clearly identify delivery and verification evidence; partner-specific interfaces require approval). Supporting: ARC-01/ARC-02/ARC-03/ARC-04, OPS-02, OPS-05, BUILD-08 (unmatched reconciliation queue with owner).

## Risk class

Cross-boundary. It touches a clinical result workflow, patient/accession linkage, authorization and audit. Human partner-interface approval and G5 clinical acceptance remain separate gates; no live partner or real patient data is involved, and all fixtures are synthetic.

## Review owner

Senior Java and Spring Boot (bounded review dispatched), with Test Engineering and Java Build/Tooling guidance loaded. Clinical/PRD-02 acceptance remains with the site clinical lead and Product Owner at G5.

## Data changes

No Flyway migration, backfill or schema change: the task scope permits only `labflow/outage`, reserves no migration version, and forbids `db/migrations`. The linked order entry, unmatched queue and outage history are tenant-keyed in-memory projections, following the existing `exchange/result/ReconciliationService` precedent. No lock or volume impact today; a durability story is requested below for multi-replica use.

## Authorization boundaries and audit events

Authorization re-derives active membership and roles from `TenantContext` inside the tenant-guarded transaction via `LabAccessionRepository.hasActiveMembership` / `activeRoles`; `LabRules.mayCapture` or `mayVerify` is required (collector or verifier). Patient/accession/issuer are validated at the boundary and re-matched against the stored requisition before linkage; a mismatch is queued, never linked. All reads are keyed by the active organization. Added audit purpose `PARTNER_OUTAGE_FALLBACK`, action `LAB_OUTAGE_MANUAL_ENTRY`, resource `MANUAL_RESULT`, scope `LAB`, outcomes `SUCCESS`, `UNMATCHED`, `DENIED`. The append-only outage history stores the reason, actor, disposition and timestamp, never the clinical payload or a credential.

## Migration and rollout considerations

No migration to sequence; no expand/contract step. Rollout risk is limited to the (deliberately in-memory) queue being process-local. Feature is additive — no existing route or contract changed. Before multi-replica production use, move the three projections behind a tenant-owned forced-RLS store and publish the routes in OpenAPI (task request below).

## Findings

- The queue, order links and history are process-local by deliberate scope constraint (no `db/migrations`, no task `reserved:` version). This is the same limitation the existing XCH-04 reconciliation decisions carry; it is not durable across restarts or safe for multiple replicas. A follow-up task is requested below.
- The new routes are not published in `contracts/openapi` (outside scope), so generated clients cannot call them yet. Follow-up task requested below.
- Reused `LabAccessionRepository` for RLS-bounded order lookup and authorization, `LabRules` for role checks, `LabInputs` for identifier validation, `ObservationInput` from `labflow/results` for the keyed-in observations, and the shared `UploadValidation` for the path-free file name and checksum instead of duplicating those rules.
- Pre-existing, unrelated worker-environment failures observed (not caused by this Java-only change; worktree otherwise clean apart from the new scoped directories): `python3 -I scripts/check-pack.py` reports `opencode.json is stale` — confirmed `git ls-files -v opencode.json` → `S` and worktree byte-identical to `.github/opencode.ci.json`, the documented CI-profile `skip-worktree` artifact; `git show HEAD:opencode.json` is the committed local profile. File was not edited or committed. `bash scripts/python-coverage.sh` exits 1 on `{"violations": [{"file": "TODO.md", "rule": "tracker"}]}` from a live-tracker test. `bash scripts/frontend-check.sh` exits 1 on `src/features/domain-layout.test.ts` because patient-mobile already has a `tracker` feature directory not in that test's fixed list (1 failed / 606 tests). No frontend file was touched. The broader `python3 -I -m unittest discover -s scripts/tests -q` has 5 pre-existing `test_check_pack` failures for the same profile artifact.
- Bounded `orevia-senior-backend` review (source: subagent report, read-only static review; no gate re-run): no blocking findings. Three non-blocking points were resolved in this pass: (1) the tenant-keyed queue/history values were plain `ArrayList` mutated outside `computeIfAbsent`, risking lost updates on concurrent requests — changed to `CopyOnWriteArrayList` with a comment and an 8-thread regression test; (2) the read endpoints had no role gate — an explicit decision was recorded in the service Javadoc (tenant-scoped operational metadata readable by any authenticated member, writes still require a lab role, matching the XCH-04 reconciliation read precedent) with a regression test proving a reception subject reads but cannot write; (3) an invalid `@return` on the compact-constructor Javadoc was reworded. Coverage and all gates were re-proven after these edits.
- No defects in the new scoped code were found during implementation.

## Lessons for workers

- Confirm a `check-pack.py` "stale" verdict with `git ls-files -v opencode.json` (look for `S`) and `cmp` against `.github/opencode.ci.json` before regenerating anything; in a cloud worker that file is the CI profile under skip-worktree, not HEAD truth.
- `scripts/check.sh` runs `apps/api/check.sh` → `mvn verify` with every integration test and OWASP; under the 5-minute worker rule it cannot be run end to end. Run the policy steps directly and prove coverage with a targeted `-Dtest=... test jacoco:report` plus one scoped integration class.
- When a story's scope excludes `db/migrations` and `contracts`, follow the existing in-memory projection precedent, state the limitation plainly, and ask for a durability/contract task instead of silently widening the diff.
- Multi-line `assertThrows(..., () -> call(...)).code()` needs the closing parenthesis for `assertThrows` before `.code()`; a misplaced one compiles as a call on the returned value and fails at test compilation.
- A tenant-keyed `ConcurrentHashMap<String, List<...>>` is only thread-safe if its *values* are too: use `CopyOnWriteArrayList` for append-only queue/history projections, because `.add()` after `computeIfAbsent` is not atomic and concurrent readers can race `List.copyOf`.
- When a reviewer asks whether read endpoints should be role-gated, either apply the gate or record an explicit, Javadoc-backed policy decision with a test; do not leave the gap undocumented.
