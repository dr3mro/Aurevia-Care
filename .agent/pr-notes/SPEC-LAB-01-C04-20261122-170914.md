# SPEC-LAB-01-C04 — clause-4 API proof for rejected specimens

## Summary

Test-only story. Adds a clause-focused HTTP integration suite and its clause-evidence document for
PROJECT_V1_SPEC.md LAB-01 clause 4, "Rejected specimens retain reason and notification." The
suite proves the rule through `POST /api/v1/lab/accessions/{id}/reject` and refuses wrong role,
peer tenant, stale version, blank reason, blank notification, a non-positive version and a
forbidden source state. No production code, existing test, migration or contract was changed.

## Lessons for workers

- A directly SQL-seeded accession row has no history events. To prove append-only behavior without
  colliding with V26's `UNIQUE (organization_id, accession_id, accession_version)`, seed exactly one
  prior event at version 1 and let the reject append version `expectedVersion + 1 = 2`.
- Under FORCE RLS, a mis-bound direct DB read returns zero rows and makes `count(*) = 0` assertions
  pass vacuously. Bind `app.current_org`/`app.actor` with transaction-local `set_config`, and assert
  the seeded row is *visible* before asserting its values — crucial for the cross-tenant negative.
- A 403 can mean "no active membership" or "missing role". Assert `$.message` (or first prove the
  actor can read) so a wrong-role negative isolates the permission branch.
- For blank-input negatives use `""` or a single space: the `LabInputs` TEXT regex admits whitespace
  runs of length >= 2, so a longer blank string would validate and the expected 422 would not fire.
