## Summary

The five presentational enrollment screens (`EnrollmentScreen`, `RecoveryScreen`,
`LockoutScreen`, `StepUpPrompt`, `SupportRequestScreen`) now share one
presentational container style:

- content is capped at a readable `720` pt and centred on `large` windows;
  compact and regular windows fill the available width;
- each screen root is a core React Native `SafeAreaView`, so content stays
  clear of notches and cutouts;
- every `Pressable` keeps the existing `minHeight`/`minWidth: 44`;
- the `StepUpPrompt` action row uses `flexWrap: 'wrap'`, and no `Text` uses
  `numberOfLines`, `adjustsFontSizeToFit`, `maxFontSizeMultiplier` or a fixed
  `lineHeight`, so nothing is clipped at 200% text;
- RTL still uses the shared `getTextAlign` / `getRowDirection`, focus order and
  accessible names are untouched, and no storage, cache, API call, text,
  exported name or dependency was added.

No list-plus-detail screen exists in this component, so the two-pane rule
(inbox/thread, appointments/detail, reports/detail) does not apply here;
it belongs to the corresponding feature stories.

## Findings

1. **Shared safe-area Jest mock is unusable for named imports** —
   `apps/patient-mobile/jest.setup.ts` mocks `react-native-safe-area-context`
   with `jest.requireActual('react-native-safe-area-context/jest/mock')`, whose
   module exposes only a `default` export. Calling `useSafeAreaInsets`
   (therefore `useWindowClass`) from a screen crashes the pre-existing
   `screens.test.tsx` with `useSafeAreaInsets is not a function`. That file is
   outside this story's scope, so the screens use `useWindowDimensions` plus
   the shared `windowClassFor` classifier and a core `SafeAreaView` wrapper.
   A bounded read-only review by `orevia-senior-mobile` (subagent/tool
   evidence, no commands run) confirmed there is no mock-safe alternative
   inside these two files: the real library has no default export, so a
   default-import interop would break production. Consequence: core
   `SafeAreaView` is deprecated, iOS-only, and does not handle left/right
   landscape/RTL insets; on Android it is a plain `View`. This is a stopgap,
   not a complete inset implementation, and a task request is included below.
2. **Inset-derived layout is not asserted and vertical overflow is not proven** —
   the review also noted that the screens have no `ScrollView`, so a parent
   must provide scrolling for a dense error-plus-notice state at 2× text. I
   added a worst-case support-screen case asserting that the error, the
   submission notice, the radiogroup labels and the submit action all remain
   in the tree at 200% on a compact window; whether the parent scrolls is a
   parent/navigator concern outside this story's scope. The tablet test now
   drives real widths through `windowClassFor` (breakpoints 600/840) instead
   of mocking the classifier, so the window-class matrix is genuine; font
   scale and orientation remain invariant inputs because the component has no
   scale/orientation branch, and the tests assert that invariance.
3. **Specialist review outcome** — no behaviour, text, accessible-label,
   exported-name, API-call or dependency change was found, and no uncovered
   branch was found in `screens.tsx`. The review's platform-bound
   `root.type === 'SafeAreaView'` suggestion was removed in favour of
   platform-neutral base-style assertions.
4. **No two-pane candidate in this component** — all five screens are forms or
   prompts, not list-plus-detail; the two-pane requirement is satisfied by the
   inbox/thread, appointment/detail and report/detail stories, not by
   `screens.tsx`.
5. **Pre-existing conflict markers outside scope** — at start,
   `git grep -nE '^(<<<<<<<|>>>>>>>) '` listed committed markers in
   `apps/api/src/main/java/com/aurevia/exchange/hl7/Hl7ParseException.java`,
   `Hl7Parser.java` and `Hl7Segment.java`. `git merge --no-edit origin/main`
   was "Already up to date"; these markers predate this story and were not
   touched (scope restriction).

## Lessons for workers

- In `apps/patient-mobile` headless tests, the shared safe-area mock only has a
  `default` export. Do not call `useSafeAreaInsets` / `useWindowClass` from a
  component unless you also own the fix to `jest.setup.ts`.
- React 19 + RNTL: several `await render()` calls in one `it` leave later
  `toJSON()` calls returning `null`. Use one render per `it.each` case.
- `it.each` titles interpolate nested objects (`$window.windowClass`,
  `$testCase.name`), which keeps a large cross-product readable.
