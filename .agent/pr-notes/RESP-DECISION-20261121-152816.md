# RESP-DECISION — Responsive staff web decision record

## Summary

Added `docs/decisions/0004-responsive-staff-web.md` from `docs/decisions/template.md`. The record decides that the staff web is fully usable on phones (320-767 px), tablets (768-1279 px, both orientations) and desktop (1280 px+), replacing the current "use a larger screen" floor below 768 px in WEB-07 and `docs/design/screens-and-navigation.md`. Documentation-only; no code, dependency or tracker changed.

## Affected requirements

- WEB-07 (supported clients) — current spec text still states the 768 px floor; a person must amend it (recorded in Findings).
- UX-01 (bilingual accessibility, WCAG 2.2 AA) — grounds the 200% zoom, 320 px reflow, touch-target and RTL requirements.
- PRD-06 (no offline clinical editing) and PAT-02 (avoid persistent clinical caches) — ground the no-service-worker-cache decision.
- WEB-02 (`Cache-Control: no-store` on authenticated responses) and WEB-10 (end-to-end browser matrix) — referenced as the owning gates for later implementation.

## Findings

- **Spec drift (hand-off, not fixed here):** `PROJECT_V1_SPEC.md` WEB-07 and `docs/design/screens-and-navigation.md` section 1 still state the 768 px floor and the "use a larger screen" notice with no data below it. Per the story and AGENTS.md the swarm may not edit the specification; a person must amend WEB-07 (and the design doc) to align with this Proposed decision. Until then, the compact layout floor in code follows this decision (down to 320 px; width alone must not trigger the unsupported-browser page). The existing guard is `isSupportedBrowser(userAgent, width)` in `apps/staff-web/src/features/system/browserSupport.ts` (READY-32) — it currently returns false below 768 px and is the concrete code point a later implementation story must change.
- Browser matrix: desktop/tablet support is unchanged from WEB-07 (latest two majors of Chrome, Edge, Firefox, Safari); phone support is latest two majors of iOS Safari and Chrome on Android; Samsung Internet is explicitly out of scope.
- **Simulated UX/accessibility review (`orevia-ux-reviewer`)** confirmed all 10 acceptance criteria met and no blocking contradiction of the spec/design docs. It raised four findings, all resolved in the decision file before commit:
  1. [medium] "Labelled cards" as the primary phone table treatment was not authorized by `docs/design/accessibility-patterns.md` (reflow prescribes a labelled scroll region; a `div` grid is not valid clinical table semantics). Fixed: the labelled scroll region preserving `<table>`/`<caption>`/`<th scope>` is now the default; card rendering is allowed only if it preserves those semantics and the full column set.
  2. [low] Browser matrix was attributed to WEB-10 alone. Fixed: cites WEB-07 (browser matrix in the end-to-end suite) and WEB-10 (real-browser accessibility/visual verification).
  3. [low] "Fine-pointer" phrasing redefined `size.target.min`. Fixed: now says "general web floor"; the 44 x 44 coarse-pointer rule supersedes it for coarse pointers.
  4. [low] The sub-768 px "use a larger screen" notice was attributed to WEB-07. Fixed: attributed to `docs/design/screens-and-navigation.md` section 1; WEB-07 is cited only for the plain unsupported-browser message and layout floors.

## Lessons for workers

- A decision record may legitimately contradict the current specification when it is marked Proposed and names the exact spec text a person must amend; the hand-off should cite the concrete code guard and file that will need to change, not just the requirement ID.
- For documentation-only stories, the applicable gate is `python3 -I scripts/check-docs.py` (and `check-secrets.py`); record that a coverage gate does not apply rather than leaving `## Coverage` blank.
