# BUILD-49 — Staff web: care unit service hours, coverage and response targets

## Summary

Adds a tenant-scoped care-unit service profile editor under
`apps/staff-web/src/features/units`: published service hours, urgent and routine
response targets, supported topics, urgent contact instructions, named queue
owner and backup coverage, plus a change form carrying a named approver and a
future effective date. A unit with no named backup shows an operational
warning; a unit with no named owner cannot be enabled; a past effective date is
refused. Container, presentational screen, typed client, bilingual bundle,
synthetic fixtures and unit/component tests are included. No dependencies were
added and no file outside the scope was changed.

## Affected requirements

| Requirement | Where it is satisfied |
|---|---|
| MSG-06 | Published service details and the no-backup operational warning in `UnitsScreen.tsx`; named owner prerequisite in `domain.ts#canEnable`; change/approval/enable commands in `api.ts`. |
| ADM-01 | Named approver and effective date edited and validated in `domain.ts#validateProfile`; version precondition (`If-Match`) on every command; pending/approved state derived from `approvedAt`. |
| UX-01 (supporting) | en/ar message parity in `messages.ts`; `dir`/`lang` mirrored by `I18nProvider`; logical properties and `MixedScriptText` for isolated names; `formatCivilDate` for the effective date. |
| WEB-09 (supporting) | Loading, empty (`version === 0`), error, forbidden, conflict, stale-version and session-expired states mapped through `StateViews` in `UnitsPage.tsx`. |

## Risk class

Cross-boundary. The change introduces a typed client for a care-unit service
profile API family that is not yet published in the OpenAPI contract; it does
not change permissions, patient linkage, clinical records or any schema. No
patient data, credentials or real identifiers are used.

None. No migration, backfill, lock or volume impact; no rollback or forward-fix.

## Authorization boundaries and audit events

Tenant comes from `ActiveOrganizationProvider` via `useActiveOrganization()`,
never from a body. Writes carry `X-Active-Organization`, `If-Match` (profile
version) and a fresh `Idempotency-Key` per action, following ARC-02/ARC-03.
No patient data is stored in URLs, page titles or browser storage. No audit
event is added or changed; audit remains server-owned.

## Migration and rollout considerations

None for this change. Route registration and navigation are deliberately left
to BUILD-52 (see Findings); the proposed pattern is `/admin/units`. The
service-profile API and generated client types must be published before live
enablement.

## Findings

1. **No service-profile API in the contract.** `contracts/openapi.yaml` publishes
   no `/api/v1/units/...` path and no `ServiceProfile` schema (verified with
   `grep -nE '^  /' contracts/openapi.yaml`); the generated client
   (`src/api/generated/openapi.d.ts`) has no matching type. Story step 1 could
   not be satisfied as written. The client in `api.ts` follows
   `features/scheduling/api.ts`: it builds headers with the shared builder and
   substitutes the care-unit URL. The backend/contract owner must publish the
   family and generated types; `api.ts` paths and `ServiceProfileResponse` then
   need to be aligned with that contract. This is outside the story scope.
2. **No route registered.** `tests/app/AppShell.test.tsx` asserts an exact
   route-pattern list, and BUILD-52 owns route/navigation registration. Adding
   `features/units/routes.ts` here would break that out-of-scope test. Proposed
   pattern for BUILD-52: `/admin/units` (tenant admin), lazily loaded.
3. **Optimistic success text (resolved).** The first cut announced a success as
   soon as a callback fired. The page's `run` now returns `Promise<boolean>` and
   the screen's four handlers await it and announce only on `true`; a failed
   command leaves the status region empty while the page shows the typed error.
   Evidence: `units-screen.test.tsx` 'does not announce %s success when the page
   reports failure' and `UnitsPage.test.tsx` conflict tests assert an empty
   `units-status`.
4. **Named approver origin.** `validateProfile` requires a named approver and
   the propose body carries it, but ADM-01 says the server derives the approver
   from the authenticated actor. The API owner must validate or override this
   field; the client value is not an authorization decision.
5. `MARKER-NON-ERROR-VALUE` console output during the full coverage run is
   pre-existing (error-boundary test), not a failure introduced here.
6. **Missing-owner gate now also at the command boundary (resolved).** A bounded
   senior React review noted the view-only gate. `setUnitEnabled` now rechecks
   the named owner and rejects with `TransportError('invalid', OWNER_REQUIRED)`
   before any request is sent; the page passes the published owner to it, and
   the screen keeps its local refusal for feedback. Evidence:
   `api.test.ts` 'refuses to enable a unit with no named owner before sending a
   request'.
7. **Stale default "today" (resolved).** The first cut defaulted the effective
   date to a fixed fixture (`2026-03-09`), which would accept past dates in the
   running app on 2026-11-21. The page now derives the default from
   `new Date().toISOString().slice(0, 10)`; tests pin a civil date through the
   prop.
8. **Validation/a11y conformance (resolved).** The required hint is visible in
   both locales, the refusal reason is bound to the matching `FormField`
   (`aria-invalid`/`aria-describedby`), and focus moves to the error summary on
   a failed submit. Arabic-script owner/backup runs use a script-derived `lang`
   and `dir="auto"`. The shared `FormField` inline error still uses `role="alert"`
   and could double-announce with the summary; fixing that shared component is
   out of this story's scope.

## Lessons for workers

- Check `tests/app/AppShell.test.tsx` before adding any `features/*/routes.ts`:
  it asserts an exact route list, so a new feature route breaks it until the
  registration story updates the test.
- Run `npm run test:coverage` unfiltered. Vitest's `perFile: true` thresholds
  report every untouched file as failing when you pass only your own test
  files, which is misleading; the unfiltered run is the real gate.
- Verify a story's referenced API actually exists (`grep '^  /' contracts/openapi.yaml`)
  before designing a client against it; this snapshot has no care-unit service
  profile family yet.
- Never default a date gate to a fixture constant in production code: a civil
  "today" must come from an injected clock or `new Date()` at the page boundary,
  or the validation silently passes stale dates outside tests.
- When a view announces a command outcome, make the callback return the
  confirmed result: fire-and-forget callbacks make a failed command announce a
  false success in a `role="status"` region.
