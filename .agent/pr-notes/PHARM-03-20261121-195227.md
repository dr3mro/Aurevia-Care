# PHARM-03 — API: clarification thread between pharmacy and prescriber, tied to the prescription

## Summary

Added a tenant-scoped, append-only clarification thread API under `pharmacyflow/clarify`. A pharmacy staff member opens a request on a prescription; the prescriber address is resolved authoritatively from the prescription through `RxService.get(id)`, never from the request body. The prescriber answers with text, an amended prescription revision identifier, or both; the answer closes the request, is appended to the same trail and is readable by the pharmacy requester. Only the requester and the named prescriber in the same tenant may read a thread. Unanswered requests older than the configured limit (48 h domain default, injectable) are flagged overdue, with a strict `openedAt.isBefore(now - limit)` comparison.

## Affected requirements

RX-02 (track clarification separately; clarification answer distinct from acceptance/dispensing), MSG-04 (typed content tied to a prescription, versioned trail). Supporting: IAM-01/ARC-03 (tenant, role and precondition boundaries). Spec source: `PROJECT_V1_SPEC.md` lines 80 and 101; clause tasks `SPEC-RX-02-C01`..`C07` and `SPEC-MSG-04-C01`..`C06`.

Acceptance mapping:
1. Request opens a thread on the prescription addressed to the prescriber → `openCreatesThreadAddressedToAuthoritativePrescriber`, `openThreadThroughHttpAddressesThePrescriber`.
2. Prescriber answers with text or amended revision; answer closes and reaches pharmacy → `answerWithTextClosesRequestAndReachesPharmacy`, `answerWithAmendedRevisionLinksRevision`, `textAnswerThroughHttpClosesAndReachesPharmacy`, `amendedRevisionAnswerThroughHttpLinksRevision`.
3. Unanswered requests older than a configured limit appear overdue → `overdueBoundaryIsStrictlyOlderThanTheLimit`, `overdueListsOnlyOldOpenThreadsVisibleToTheCaller`, `defaultOverdueLimitIsConfiguredInTheDomain`, `overdueFlagSurfacesThroughHttp`.
4. Only the two parties and their tenant see the thread → `viewConcealsThreadFromThirdPartyAndWrongRole`, `viewConcealsThreadFromOtherTenantAndUnknownThread`, `answerConcealsThreadFromAnotherClinician`, `thirdPartyAndOtherTenantCannotViewThreadThroughHttp`.

## Authorization boundaries and audit events

Organization and subject come only from `TenantContext`, roles from freshly resolved `StaffRepository.activeRoles` at the controller; the prescriber subject comes from the tenant-bound `RxService.get(prescriptionId)`. Open requires `pharmacy_staff`; answer requires `clinician` AND subject equality with the thread addressee; read requires the requester or addressee subject with the matching role; overdue is scoped to those parties. Wrong role → 403; invisible thread, other tenant, third party → 404 (concealed), stale version → 412, re-answer → 409, bad input → 422. No new audit event was added; this slice mirrors PHARM-02, which also records none. Referrals to the OPS-02 audit trail are a follow-up consideration.

## Clinical and architecture review

Clinical safety: the answer never creates a signed prescription revision; it only links an opaque revision identifier, so no prescribing decision is automated here. Architecture: the prescriber identity is resolved from the authoritative prescription read, roles are re-derived per request, and the answer is a distinct append-only trail rather than a mutation of the PHARM-02 status facts. Advisory senior-backend and test-engineer reviews were received and their findings (strict overdue boundary, thread-scoped idempotency key, authoritative prescriber) were applied before green.

## Findings

1. Scope limitation (tool + reviewer): the task grants only the two `clarify` packages and no migration version, so this follows the in-memory kernel pattern of PHARM-02. AGENTS.md "Done means working end to end" (Flyway + Jdbc store + HTTP integration + OpenAPI) cannot be satisfied inside this scope; a durable-store/contract follow-up is requested below. The HTTP tests do prove the real controller entry point and tenant isolation.
2. Pre-existing gate drift (tool): `scripts/quick-check.sh` stops at `check-pack: opencode.json is stale`, with a clean `git diff` for that file and the same failure from `git show HEAD:opencode.json`. Not caused by and not fixable inside this scope.
3. Concealment choice (decision): a non-addressee clinician receives 404 rather than 403 on answer/read, so thread existence is not disclosed to a same-role third party. Re-answer of a closed thread by the addressee receives 409.
4. Answer shape (decision): "text or an amended revision" is treated as inclusive — at least one is required and both are stored when supplied (a note plus a linked revision). Strict XOR was considered and rejected as less useful clinically.
5. `overdue` uses a domain constant of 48 hours exposed as `ClarificationService.DEFAULT_OVERDUE_AFTER` and injectable via the 3-arg constructor; no external config file was touched because none is inside scope.
6. No new audit event is appended. This matches PHARM-02 but may need an OPS-02 audit follow-up for clinical accountability (see task-requests).

## Lessons for workers

- When using `overdue()` as a proxy for "list threads", remember it is time-relative: advance a single mutable test clock on the same service instance instead of constructing a second service (in-memory maps are per instance).
- A `ThreadView` JSON body nests projection fields under `thread`; MockMvc JSON paths must use `$.thread.<field>`, not `$.<field>`.
- The Java convention test requires two `List.copyOf(` occurrences in any file with a `List<`-bearing public record; keep both the compact constructor and the overridden accessor.
- `scripts/check-wiring.py` only flags `InMemory*` class names and `*Store` interfaces without a `Jdbc*` implementation; a private in-memory map inside a `*Service` is not flagged, but this is a deliberate temporary pattern.
