# RADFLOW-04 — Staff web: referrer view of imaging reports and addenda with acknowledgment

## Summary

Exports two reusable staff-web components under `apps/staff-web/src/features/radreferrer` for the chart: `ImagingReportCard` renders a signed interpretation with its five narrated sections always in clinical order, and `AddendumBanner` renders a banner with an explicit acknowledge action for every still-open addendum of that report. Domain helpers keep the clinical rules (section order, tenant/order scoping, open-only acknowledgment) pure and reused by the components, not test-only. A bounded senior React/TS review and a simulated referring-clinician review were applied: the acknowledge callback now carries the full tenant/order-scoped receipt, each action is uniquely named by revision, the version numeral is bidi-isolated, the live region is text-only, and an open→acknowledged transition test proves the banner closes. All data is synthetic; no dependency, tracker, workflow, shared component or protected file was changed.

Entry-point-to-test trace: the chart imports `ImagingReportCard`/`AddendumBanner` from this feature. `ImagingReportCard` → `reportSections` → canonical `REPORT_SECTION_KEYS` order asserted in `domain.test.ts` and by the ordered `[data-section]` nodes in `components.test.tsx`. `AddendumBanner` → `openAddenda` (tenant + order + open filter) → banner presence/absence, isolated version numeral, unique per-revision action name and the scoped `onAcknowledge(addendum)` callback asserted in `components.test.tsx`. The acknowledge click carries the exact tenant+order+version receipt; sending the command and flipping the receipt to `acknowledged` is the parent chart's responsibility (outside this scope), and the `rerender` transition test proves the banner disappears once the parent marks the receipt acknowledged.

## Affected requirements

- RAD-01 — signed interpretation with technique, comparison, findings, impression and follow-up; linked addenda that need referrer acknowledgment.
- WEB-09 — bilingual, right-to-left screen with explicit, observable acknowledge action and live banner state (loading/error/empty states remain owned by the consuming chart page).

Review evidence is simulated/tool-only — no human clinical or unit acceptance was performed.

None. No migration, backfill, lock or volume impact. No table, store, contract file or generated client was added or edited.

## Authorization boundaries and audit events

Tenant and order are explicit props on `AddendumBanner` and are re-checked by `openAddenda` as defence in depth over the API boundary; receipts from another tenant or order are never painted. The acknowledge callback receives only the exact revision number — no actor, tenant or patient data is placed in a URL, page title or browser storage. No audit event is added or changed here; the API's existing `ADDENDUM_ACKNOWLEDGED` fact remains the authoritative record. Clinical free text is rendered as stored inside `<bdi dir="auto">` runs; nothing is translated or re-spelled.

## Migration and rollout considerations

None. Both components are exported from the feature folder and imported by the chart; no route, navigation or registry entry is needed. The bilingual bundle is named `labels.ts`, not `messages.ts`, so the shared `tests/messageParity.test.ts` registry is untouched.

## Clinical and architecture review

A simulated `orevia-radiology-user` review and a bounded `orevia-senior-react` review were completed; all findings and dispositions are recorded under Findings. Section order comes from a fixed clinical vocabulary rather than object key order, so a scrambled interpretation cannot silently reorder the narrative. The signer, revision and UTC signing instant are shown as isolated runs. Addendum identity is bound to an exact tenant+order+version receipt, scoping drops receipts that do not belong to the active tenant/order, and the live region is text-only so the acknowledge control remains reachable. No real radiologist, referrer or patient participated, so RAD-01 release-to-referrer clinical acceptance and G5 sign-off are not claimed. One HIGH clinical gap remains open and requires an API change outside this scope (task-request below): the addendum receipt carries no clinical narrative, so the referrer cannot read what they are acknowledging.

The worktree `opencode.json` carries the skip-worktree CI profile (`git ls-files -v` shows `S`); `git diff -- opencode.json` is empty. Same environment artifact as RADFLOW-02/03; integrator/owner owns regeneration.
- **Simulated clinician Findings A/B (HIGH) — open, requires an API change outside this scope**: the `AddendumReceipt` in `apps/api/.../radflow/report/AddendumReceipt.java` carries only identifiers, `notifiedAt`, `state`, `acknowledgedAt` and `acknowledgedBy` — no narrative, signer or signed time. The banner therefore shows a version number, not what changed, and the card can display an older revision than the open addendum. A referrer cannot truly "read and accept" a revision. No client-only fix gives real assurance because the server would not enforce it. Recorded as a `task-requests` item below; not claimed as production-ready here. Fixture version numbers were made internally consistent (current report revision equals the open receipt revision) to remove local confusion.
- **Simulated clinician Finding C / senior-react Finding 2 (MODERATE) — resolved**: `onAcknowledge` now takes the full `AddendumAcknowledgment` (organizationId + orderId + version) instead of a bare integer, and each button has a unique bilingual `aria-label` containing its exact version (e.g. `Acknowledge version 3`). A two-open-addenda test asserts both names and that each click passes its own receipt.
- **Simulated clinician Finding D (MODERATE) — resolved in scope**: added an open→acknowledged `rerender` test proving the banner disappears when the parent flips the receipt. Real command dispatch, failure and duplicate-submit handling remain the consuming chart's responsibility (RADFLOW-05/out of scope); no local double-submit guard was added to a presentational component.
- **Simulated clinician Findings E/F and senior-react Finding 1 (LOW/MEDIUM) — resolved**: the Arabic RTL test now asserts every section body is a `BDI` with `dir="auto"` using mixed-script clinical text, asserts the signer run is also isolated, and asserts the addendum version numeral is an isolated `<bdi dir="ltr">` in both the body and the version-named action.
- **Senior-react Finding 3 (LOW) — resolved**: `role="status"` now wraps only the heading/body text; the acknowledge button sits outside the live region. Each receipt is a named `<section>` (`aria-labelledby` a unique heading id) with a semantic `<h3>` instead of `<strong>`.
- **Senior-react Finding 4 (LOW) — accepted with rationale**: the feature hand-rolls `<bdi dir="auto">` instead of the shared `MixedScriptText`, which requires a `lang` that neither `SignedReport` nor the API's `Interpretation` carries. Inventing a language from the interface locale would mis-tag clinical text; adding a stored language field is an API/model change outside this scope. The `labels.ts` dictionary duplication is the same explicit scope decision as the sibling `radworklist` feature (the shared message registry is protected).
- **Senior-react Finding 5 (informational)**: the exports have no production consumer in this checkout; the chart integration and end-to-end browser journey belong to RADFLOW-05. This is a deliberate slice boundary, not a claim of end-to-end acceptance.
- The components deliberately do not call the report API or flip receipt state: the consuming chart page (RADFLOW-05 / out of scope) owns the command and the state update. `AddendumBanner` hides the banner purely from its `addenda` prop, so a parent that does not refresh will keep showing an acknowledged addendum; this is the standard one-way-data-flow contract and is covered by the acknowledged-receipt and transition tests.

## Lessons for workers

- A new staff-web feature cannot use `messages.ts` for its bilingual bundle: `tests/messageParity.test.ts` hard-codes `BUNDLE_SOURCES` and glob-discovers `src/**/messages.ts`. Name the file `labels.ts` and add a parity test inside the feature.
- `bash apps/staff-web/check.sh` is the frontend definition of done; run it (not just Vitest) and paste the `tsc --noEmit` final lines into the notes. Per-file coverage is enforced by `vite.config.ts` with `perFile: true`, so every new source file must be fully covered.
- Vitest 5 `vi.fn` takes one procedure type parameter: `vi.fn<(version: number) => void>()`, not `vi.fn<[number], void>()`.
- `ThemeTokens` exposes `background`, `foreground`, `border`, `accent`, `focusRing` and `spacing` — there is no `surface` token; use `background`.
- In a cloud worker, a stale `opencode.json` report is the CI-profile/skip-worktree measurement artifact, not HEAD truth; verify with `git diff -- opencode.json` before touching anything protected.
