## Findings

- **Brief is wrong about two paths and one gate.** The brief pointed at `.../smartclinic/test/it/ConfigurationIsolationTest.java`; the real path is `.../smartclinic/it/ConfigurationIsolationTest.java`. It asked to confirm that `check-constraints.py` accepts the mandated GAP `@Disabled`; it does not (rule at `scripts/check-constraints.py:56`, no Java-test exemption in `EXEMPT` at 27-30, invoked by `scripts/quick-check.sh:20` and `scripts/integrator-gate.sh:8`). The story and AGENTS.md were followed: the test file was written as mandated and the conflict is reported instead of hidden.
- **The task cannot be gate-green with the mandated annotation.** `scripts/check-constraints.py` flags every newly added `@Disabled` in a `.java` file. Four earlier GAP tests in `origin/main` are grandfathered. `docs/gates/g0-isolation-surfaces.md:50` calls such a skip "an explicit gap marker, not a weakened gate", so the repository's practice sanctions the pattern but the check implementation is too blunt. Fixing it requires editing a protected `scripts/` file, which is outside this task's scope and belongs to the integrator or a person. No exemption list, env switch or waiver was found in `agent-run.sh`, `quality-gate.sh` or `integrator-gate.sh`.
- **Method-level `@Disabled` alone starts Spring and Flyway.** The first targeted run loaded the context and migrated a schema even though all four methods were skipped; a class-level `@Disabled` was added so the container is skipped before Spring's extension runs. The final run took 0.025 s with no Spring/Flyway output. A future task enabling the tests must remove both levels.
- **`opencode.json` false positive confirmed once.** `git ls-files -v opencode.json` is `S` and `git show HEAD:opencode.json` is a valid generated profile. Per AGENTS.md this is not re-diagnosed on later passes.
- **Survey correction from context-optimizer.** Channel columns also exist as `primary_channel`/`backup_channel` in `V23__critical_results.sql`, in addition to the V92 service-profile columns; no channel-test behaviour exists in either.

## Lessons for workers

- Before writing a not-built-clause test, run `python3 -I scripts/check-constraints.py` on a scratch copy: the mandated `@Disabled("GAP: ...")` is currently rejected as an added suppression, so the story and the gate disagree. Report the conflict; do not work around it with a qualified annotation, an assumption abort or a tag exclusion.
- Put `@Disabled` on the class as well as on each method when a would-prove test uses `@SpringBootTest`. Method-level skips still let Spring load the context and Flyway contact a database.
- In a cloud worker, `test_check_pack` failures and a stale `opencode.json` from `check-pack.py` are environmental: confirm once with `git ls-files -v opencode.json` (`S`) and `git show HEAD:opencode.json`, then run the remaining checks individually.
