# SPEC-CLN-03-C01 — CLN-03 clause 1 (API test): capture chief concern, history, exam, assessment/diagnoses, plan, vitals and the longitudinal chart

## Summary

Added one focused, synthetic-data-only HTTP-level test class for CLN-03 clause 1 and one spec-clause
evidence note. No production code, existing test, migration, contract or tracker was changed.

The structured half of the clause is built and now proven at the chart entry point: problems with a
versioned diagnosis-catalog mapping, allergies with an explicit "none" (ABSENT) assertion,
medications, and vitals with a value, unit and measurement time — captured with source, effective
dates and a clinical author kept distinct from the data-entry actor, and retrieved together as one
longitudinal chart. Negative proofs show the rule refuses an incomplete vital (422), a non-clinical
role (403) and a cross-tenant read (404).

The SOAP narrative half (chief concern, history, exam, assessment narrative and plan) is **not**
capturable by the CLN-03 chart domain — those fields exist only in the CLN-04 SOAP template slice.
A complete test for them is included but `@Disabled("GAP: …")`, so the pull request stays green; see
the `## Gap` section of the clause note and the `task-requests` block below. Status recorded as
**Partly proven**.

## Lessons for workers

- When seeding a patient with `app.actor`, seed that reception user in **every** tenant whose patient
  you insert: V7's `set_patient_created_by_from_actor()` raises "patient registration requires an
  authenticated user of the active tenant" if the actor is not an authenticated user of the active
  organization. My first run failed on the ORG_B patient until `reception-b` was seeded.
- For evidence-only API tasks, use the exact DB/Flyway/seed pattern from `ChartRecordIntegrationTest`,
  pick a DB name unique to the task (parallel workers share the PostgreSQL server), and run the
  targeted Surefire invocation (`-Dtest=Class`) rather than the whole integration suite; read the
  Surefire XML for the authoritative tests/errors/skipped counts.
- A `check-pack`/`opencode.json is stale` failure inside a cloud worker is almost always the CI
  profile under `skip-worktree` (OPS-CW-003-01). Prove it with `git ls-files -v` + `git diff --stat`,
  record it, run the remaining stages individually, and never edit `opencode.json` as a worker.
