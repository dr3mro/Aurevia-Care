## Summary

IAM-01 clause 4 ("Facility scope may further narrow access") is now built. The
`FacilityScopeFurtherNarrowAccessTest` was the only `@Disabled` test in the app; it is
enabled with `@Disabled` removed and extended with HTTP-level negative cases. Facility
scope is persisted on the membership at invitation acceptance and enforced at every
in-scope facility-aware authorization decision. The former red result (HTTP 200) is now
HTTP 403 for a reception member assigned to a sibling facility of the same tenant.

## Affected requirements

- IAM-01 — Maintain Organization, Facility, UserIdentity, Membership and RoleAssignment;
  facility scope may further narrow access; every write checks current scope.
- ARC-02 / OPS-02 — tenant-owned forced-RLS table, transaction-local scope fold,
  DENIED audit rows committed with the denial.
- (Adjacent, unchanged) CLN-02 / IAM-06 — check-in worklist and emergency access are
  the facility-aware boundaries narrowed here.

## Risk class

Safety-critical (authorization boundary): a tenant-owned RLS table and a new denial
path in check-in and emergency access. Negative and failure tests are included; no
clinical sign-off is claimed (synthetic fixtures only, simulated tests, no human
participant).

## Data changes

- New migration `db/migrations/V93__membership_facility_scope.sql` (reserved version
  V93; V92 is taken by the V91-duplicate fix on `origin/fix-duplicate-v91`).
  - Creates `public.membership_facility (organization_id, membership_id, facility_id,
    created_at)` with composite PK and composite FKs to `membership` and `facility`.
    ENABLE + FORCE RLS, own `tenant_isolation` policy, explicit REVOKE/GRANT to
    `smartclinic_app`, and append-only triggers reusing V4's
    `reject_immutable_mutation()`.
  - Forward-replaces V70's `accept_staff_invitation` so the invitation's `facility_id`
    is inserted onto the new membership row in the same guarded transaction. V70 is
    not edited.
  - Adds `public.is_facility_out_of_scope(subject, facility_code)`: true only when the
    member has assigned facilities but not the requested one; false for oversight
    roles (`tenant_admin`, `privacy_auditor`) and for members with no recorded
    assignment (legacy behaviour preserved, matching "may further narrow access").
  - Expand-only: no DROP/DELETE/TRUNCATE, no backfill, no table lock on existing
    tables. Rollback is a forward contract migration; no existing data is rewritten.

## Authorization boundaries and audit events

- Active tenant and subject still come only from `X-Active-Organization` and the
  synthetic subject header inside `TenantContext`; scope is re-read from the database
  fold inside the guarded transaction on every request.
- `CheckInService` now denies (403 FORBIDDEN, `facility is outside the assigned scope`)
  for identity verification, check-in, worklist read, assignment, handoff and intake
  before any read/write of out-of-scope data. Each denial writes a committed DENIED
  audit row using the existing action key and `CHECK_IN_WORKLIST` scope.
- `EmergencyAccessService` denies grant creation and treats an active grant as
  out-of-scope (403) when the grant's facility is outside the caller's assignment;
  both append DENIED audit rows with the existing `EMERGENCY_ACCESS` purpose.
- `WorklistRepository.outsideAssignedFacilities` and
  `AccessRepository.outsideAssignedFacilities` are the only new SQL entry points; both
  call the single database fold so the rule is not duplicated across layers.
- `ActionPolicy` remains role-only by design: facility narrowing is a service/DB
  decision, so no unrelated slice gains a facility input. Updating the OpenAPI scope
  claim and `AppointmentService`/`openEncounter` are outside this task's scope (see
  Findings).

## Lessons for workers

- When a story's scope excludes `staff`/`AppointmentService`/`contracts`, do not chase
  those callers: persist the rule in a database fold and call it from the repositories
  in scope, leaving the other boundaries for follow-up tasks.
- A predicate named as the denial (`outsideAssignedFacilities`) lets an unstubbed Mockito
  default keep legacy unit tests green while the real DB fold enforces the new rule.
  State this semantic explicitly in Javadoc so nobody inverts it later.
- In cloud workers the worktree `opencode.json` is the CI profile under `skip-worktree`:
  the five `test_check_pack` failures are a measurement artefact, not a regression.
  Check `git show HEAD:opencode.json` before touching generated config.
- A pre-existing duplicate Flyway version can make every integration test red before
  your code runs. Confirm the red cause, temporarily apply the known fix locally for
  verification, and restore it before committing so you do not steal another worker's
  change.
