## Requirement IDs

IAM-01, PRD-06, ARC-03, ARC-04, OPS-02 (as stated in the story and in the X-04 obligation map in `contracts/openapi/README.md`).

## Story summary

The X-04 server-side authorization control is inert in production. `CommandAuthorization` and its 24-command `CommandCatalog`, the generated OpenAPI contract and the generated TypeScript client are never invoked by a request. The story's **expected fix** has three parts:

1. Provide `CommandAuthorization` as a Spring bean wired to the durable `DecisionSink` from READY-41.
2. Call it from each owning write endpoint for all 24 catalog commands.
3. Add a build-failing parity test that fails CI when a catalog command has no production caller.

## Acceptance mapping — expected vs. achievable in this scope

| Expected deliverable | Files it requires | Inside my scope? | Outcome |
|---|---|---|---|
| `CommandAuthorization` as a Spring bean with durable sink | A bean config plus a `DecisionSink` bean, `MembershipResolver` bean and `Clock` bean; durable sink is READY-41 (`config`, `db/migrations/V65__authorization_decisions.sql`) | **No** — READY-41 is a separate, still-open story (`[ ]` in TODO.md); its `config`/`db/migrations` files are outside my scope and the class `JdbcDecisionSink` does not exist in this checkout, so any reference would not compile | Not done |

| Build-failing POST-mapping ↔ catalog parity test | A test under `apps/api/src/test/java/...` and/or wiring into `scripts/check.sh` / `.github/workflows` | **No** — `src/test`, `scripts/` and `.github/` are outside my scope | Not done |

There is no in-scope mechanism that makes the gate actually run: a Spring `@Component`/`@Bean` in `api/authorization` would need the `DecisionSink`/`MembershipResolver` beans that do not exist (registering it would break Spring context startup for every `@SpringBootTest`), and a bean that no controller calls remains inert. An interceptor in this package would still require those missing beans and would need to arbitrate 24 catalog commands against 143 unmapped POST routes (denying the rest would break the application; allowing them leaves the gate inert).

## Defects found

1. **Confirmed (story's premise):** the authorization gate has zero production callers; no command yields an authorization decision. Verified by the grep commands above.
2. **Additional finding:** the expected fix is a cross-boundary change spanning four areas outside the declared scope (controllers, `config`/migration for the durable sink, `src/test`, and `scripts/`/`.github/` for the build-failing gate). It cannot be completed by a worker confined to `api/authorization` + `contracts/openapi`.

## Decisions

- **Scope is authoritative.** Per the "Instructions for every agent" at the top of TODO.md (rules 3 and 9), I did not edit any file outside `api/authorization` and `contracts/openapi`, and I did not guess a design that would require unavailable classes. No controller, `config`, migration, script, workflow or shared tracker was touched.
- **READY-41 is a prerequisite, not a dependency I can create.** The durable sink is delivered by the separate, still-open READY-41 story in files outside my scope; referencing a not-yet-existing `JdbcDecisionSink` would not compile.
- **No test written.** A failing parity test cannot be made green without out-of-scope production changes, so committing a red test (which could break the build tier if it were wired) would be worse than documenting the blocker. A no-assertion or self-satisfying test would violate the coverage/test policy.

## Why this is not finished

- **What failed:** not a test failure — a scope/feasibility failure. Each of the three required deliverables needs files outside the declared scope (see acceptance mapping above). The closest executable check, the authorization test tier, is green at baseline (`mvn -B -f apps/api/pom.xml -Pno-security,fast test -Dtest=CommandAuthorizationTest,CommandClientGeneratorTest` → 27 tests, 0 failures; online mode required because offline `/opt/m2` lacks `surefire-junit-platform:3.5.6`).
- **Most likely cause:** the story was dispatched with a scope (`api/authorization`, `contracts/openapi`) that describes where the gate *lives*, not every place it must be *wired in*. The fix itself is intentionally cross-boundary, so the scope and the expected fix disagree.
- **What I tried:** verified the inert-gate premise and enumerated every required edit location with read-only grep/find commands; confirmed no production `DecisionSink`/`MembershipResolver` bean exists and that READY-41 is still open; confirmed the contract drift commands are not wired into any build script; established a green test baseline. I made no out-of-scope edits.
- **Exact next step (for the owner/integrator):** re-scope or split this story. One viable decomposition: (a) land READY-41 first for the durable sink (its `config` + `db/migrations/V65` + `it` scope); (b) a story with scope including the 33 controller packages to expose/inject a `CommandAuthorization` bean and call it for the 24 commands (or a single in-package interceptor plus explicit per-route mapping decisions); (c) a story with `apps/api/src/test` and `scripts/`/`.github/` scope for the build-failing POST-mapping ↔ catalog parity gate. Alternatively, if the gate is meant to stay a reusable choke point rather than a global enforcement point, close this story as "deferred — needs owner decision on enforcement boundary" and record that decision in `docs/decisions/`.
