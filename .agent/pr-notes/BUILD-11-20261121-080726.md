## Summary

RAD-01 study-link verification. An external Study Instance UID is linked only when the supplied patient **and** accession labels match the order. A mismatch now opens an item in a tenant-scoped study-link review queue, emits a review fact and leaves the order revision untouched; resolving the review does not itself link the study. A later correct `associateStudy` appends a new revision so the full order history is preserved. Modality, urgency and clinical question are recorded during the intake workflow; modality may be supplied at intake (only if approved) or at scheduling as before. All changes stay inside the two radiology paths in the story scope. Synthetic fixtures only.

## Affected requirements

- RAD-01 — imaging intake, patient/accession verification before study association, review of mismatches, modality/urgency/clinical question capture.
- ARC-01 / ARC-02 — immutable per-tenant revisions and events; review queue keyed by active tenant.
- OPS-02 — append-only review revisions and `STUDY_LINK_REVIEW_OPENED` / `STUDY_LINK_REVIEW_RESOLVED` facts.
- CLN-05 / XCH-05 — downstream signing and critical communication are unchanged; they still require a linked study.

## Authorization boundaries and audit events

Organization, actor and roles always come from `TenantContext` and freshly resolved membership; no identity is taken from the link/resolve request body. Linking and review resolution both require the existing `radiology_staff` role (`RadRules.mayAssociate`); a deactivated grant is denied on the next command. A mismatch is visible only in the active tenant's queue. Events carry only identifiers (no clinical narrative, no image pixels): `STUDY_LINK_REVIEW_OPENED` (destination = Study Instance UID, actor = caller) and `STUDY_LINK_REVIEW_RESOLVED` (same identifiers, resolution text is not put in the event). Resolved reviews are retained, not deleted.

## Clinical and architecture review

Simulated Senior Backend review raised five points: (1) keep `IntakeCommand` backward compatible — addressed with an overloaded 14-arg constructor; (2) avoid duplicate review facts with identical dedup keys — addressed by one queue item per (order, study) via `putIfAbsent`; (3) records are immutable — resolutions replace the OPEN revision and retain it; (4) no persistence/OpenAPI in scope — recorded as a release limitation; (5) explicit resolve before re-link — retained as the story-specified order. Simulated Test Engineer review supplied the branch/assertion matrix and the compatibility constraint; it was adopted where compatible with the chosen API. Neither reviewer executed commands. No human clinical or unit participant reviewed this change.

## Findings

- An approved modality may now be captured at intake (spec RAD-01 sequences it at scheduling); scheduling still records/confirms it, so the spec flow is unchanged for callers that omit it. The story's "record modality at intake" is satisfied literally for the new intake path, and no existing call signature was broken.
- A repeated mismatch for the same order and Study Instance UID is idempotent: it keeps the first queue item and emits only one `STUDY_LINK_REVIEW_OPENED` fact, avoiding the dedup-key collision the reviewer identified.
- Resolving a review intentionally does **not** link the study; a correct `associateStudy` call is still mandatory. A re-link performed without a prior resolve leaves an OPEN item; the story's review-then-relink sequence is the supported flow.
- The `@Autowired` controller constructor builds the same synthetic approved-modality catalog as before; only its covered test setup changed.
- Worker environment note: the worktree `opencode.json` is the CI profile copied under `skip-worktree`. Three `test_check_pack` assertions failed against that profile; `git show HEAD:opencode.json` equals the generator render, and all 436 Python tests pass when the committed profile is in place. The worktree profile was restored afterward; no config file was committed.

## Lessons for workers

- When adding a component to a widely used command record, keep the original arity as a delegating constructor — out-of-scope tests will still compile, and the overload needs its own coverage assertion.
- Before emitting a domain fact on repeated attempts, check the dedup key `(type, tenant, order, version)`; deduplicate the queue item at creation instead of emitting two facts with the same identity.
- In a cloud worker, a stale `opencode.json` failure is usually the CI profile under `skip-worktree`; compare `git show HEAD:opencode.json` with the generator render before editing any config.
