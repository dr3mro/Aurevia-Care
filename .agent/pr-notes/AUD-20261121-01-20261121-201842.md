# AUD-20261121-01 — Persist MSG-06 service profiles

## Summary

Production authorization state for MSG-06 lived in `@Repository InMemoryServiceProfileStore` (process-local `ConcurrentHashMap`s), so a restart lost it and two API replicas disagreed on who may act for a care unit. This change adds the tenant-owned, forced-RLS V91 migration, a `JdbcServiceProfileStore` behind `ServiceProfileStore`, moves the in-memory fake to `src/test` without any Spring stereotype, and adds an HTTP-level integration test through `ServiceProfileController`. Synthetic fixtures only; no patient or credential data.

## Affected requirements

MSG-06, ARC-01, ARC-02, OPS-02. V91 header names all four. Forced RLS and tenant-owned keys enforce ARC-01/ARC-02; the append-only `service_profile_audit` enforces OPS-02; versioned named approval and connected/assigned authorization enforce MSG-06.

## Risk class

Safety-critical / cross-boundary (authorization state, tenant policy, persistence schema, audit). Specialist reviews were simulated subagents; no human, clinical or patient-participant evidence is claimed.

## Review owner

smartclinic-senior-database (V91 migration) and smartclinic-senior-backend (JDBC store + wiring), both bounded read-only reviews in this session; smartclinic-test-engineer coverage matrix applied from AGENTS.md.

## Data changes

New `db/migrations/V91__service_profiles.sql` (V59 is rx02; V60-63 and V70-90 are used/reserved, V91 is free). Four tables: `service_profile` (durable versioned profiles, `UNIQUE(org,unit,version)`, one-way draft→approved guard), `service_profile_work_item` (ordered by identity `seq`), `service_profile_audit` (append-only, ordered by `seq`), `service_profile_unit_assignment` (reference for staff-unit assignment). Each table has `organization_id` FK, `ENABLE` + `FORCE ROW LEVEL SECURITY`, policy `organization_id = public.app_org()`, SELECT/INSERT grants to `smartclinic_app`, and reject-mutation triggers for every role including the owner. The profile table has a column-level UPDATE grant for the four approval fields plus a trigger that rejects any content rewrite, re-approval, same-approver or approval-field restamping. Additive only (`Change: expand`); no backfill; removal would be a later contract migration.

## Authorization boundaries and audit events

Organization comes only from `X-Active-Organization` via `TenantContext`; subject from `X-Synthetic-Subject` (gated on `synthetic-auth`). Membership/roles/chart links/connections are read from the authoritative V4/V10/V60 folds — never copied — so deactivation, unlink and revocation take effect on the next request. `hasConnectedChart` requires both `event='linked'` and `state='active'`. Every domain action still appends a `MessagingAudit` through the durable store, including denials.

## Lessons for workers

- `ON CONFLICT DO NOTHING` + a read-by-business-key avoids a `RETURNING` empty-result branch and makes a replay idempotent; assert the replay in the HTTP test.
- Bind `OffsetDateTime` (never raw `Instant`) to `timestamptz`, and keep `TransactionTemplate` in every JDBC store: reads under FORCE RLS are empty without the guarded transaction.
- A database approval trigger must enumerate every non-approval column with `IS DISTINCT FROM`; a `status='draft'→'approved'` check alone would let a caller rewrite hours or the effective date.
- `ResultSet.getStringArray` does not exist on the standard JDBC interface; use `getArray(...)` and cast as `JdbcMessagingStore` does.
- `version == null ? 0 : version` on an `Integer` triggers SpotBugs `BX_UNBOXING_IMMEDIATELY_REBOXED`; use `Integer.valueOf(0)`.
- Check for Markdown links to a file before moving it out of `src/main` — `check-docs.py` resolves relative links across the whole repository.
