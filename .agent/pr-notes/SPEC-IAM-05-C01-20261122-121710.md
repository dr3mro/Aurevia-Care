# SPEC-IAM-05-C01 — IAM-05 clause 1 acceptance evidence

## Summary

Adds a real-PostgreSQL clause acceptance test and the clause evidence document for
IAM-05 clause 1. The clause is already fully implemented in the patient identity
domain, so the tests are active (no `@Disabled`) and the PR stays green. No
production code, existing test, contract or migration was changed.

Source survey (step 1 of the story) found the clause implemented in:
`apps/api/src/main/java/com/aurevia/patient/identity/`
(`IdentityProofingController`, `IdentityProofingService`,
`IdentityProofingRepository`, `IdentityActionPolicy`, `PatientAccount`,
`InvitationIssue`, `InvitationRecord`, `ChartLink`); migration
`db/migrations/V10__patient_identity_proofing.sql`; and the HTTP contract is **not**
declared in `contracts/openapi.yaml` (no `/api/v1/patient-identity/**` paths —
survey result, left unchanged). Neighbouring evidence lives in
`apps/api/src/test/java/com/aurevia/it/patientidentity/` and
`.../it/patient/identity/`.

Acceptance mapping (clause sentence → proof):

| Clause property | Test method | Assertion |
|---|---|---|
| site-verified enrollment | `siteVerifiedEnrollmentSingleUseInvitationAndReverificationProveTheRule` | `reception` enrolls account → 201; one durable `patient_account` row |
| expiring invitation | `anExpiredInvitationCannotRestoreAccess` | invitation whose `expires_at` is moved into the past → claim 409, access `false` |
| single-use invitation | positive test | second claim of the same token → 409, access stays `true` |
| re-verification for lost access / disputed identity | positive test | unlink → access `false`; `tenant_admin` reverify → fresh token; stale token 409; fresh token → access `true` |
| wrong role / missing membership refused | `receptionAndUnverifiedCallersAreRefusedProtectedIdentityCommands` | reverify 403, cross-account access read 403, unauthenticated enroll 403 |
| tenant isolation of invitations | `anInvitationIssuedInAnotherTenantCannotBeClaimed` | other-tenant claim 404, access `false` in other tenant |

- OpenAPI contract gap (pre-existing, out of scope): `contracts/openapi.yaml`

## Lessons for workers

- When a clause is already implemented, write active HTTP-level acceptance
  tests and a "Proven by tests" clause document; reserve `@Disabled("GAP: …")`
  for clauses that genuinely do not exist.
- Verify the expected number of append-only events against the whole command
  flow: `reverify()` appends its own `unlinked` event before issuing the fresh
  invitation, so an earlier unlink produces two such rows.
- To test "expiring" deterministically, move `created_at` and `expires_at` of an
  unspent invitation into the past with an SQL update as the migration role
  (the `expires_at > created_at` check forbids moving `expires_at` alone); the
  database clock then refuses consumption without a timing-based test.
- Run the SpotBugs `compile spotbugs:check` command after compiling main classes;
  a bare `spotbugs:check` on empty output is vacuously green.
- In a cloud worker, confirm the `check-pack.py`/`quick-check.sh` "opencode.json
  is stale" failure against `git ls-files -v`, the worktree sha and
  `git show HEAD:opencode.json` once, then run the remaining gate stages
  individually; never regenerate or commit that protected file.
