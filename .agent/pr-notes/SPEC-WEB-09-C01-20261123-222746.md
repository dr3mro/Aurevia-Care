## Findings

- The pre-code plan review initially returned a blocking verdict with four
  Required items: remove the skipped-test contingency, assert loading/empty
  explicitly, prove the boundary is global at the app root, and filter React's
  own `console.error` before asserting the log line. The plan was revised and
  re-reviewed to a clean GO before any file was written; all four items are
  implemented in the spec.
- Two compile/lint issues appeared while writing the spec and were fixed without
  weakening any rule: `TS2769` from passing `children` as a `createElement` rest
  argument to a provider whose props require `children`, and
  `react/no-children-prop` from passing it inline in the props object. The fix
  follows the established repo pattern in
  `tests/spec/localization/support-english-arabic-rtl-direction-local-name.test.ts`:
  build the props in a variable first, then call `createElement(I18nProvider, props)`.
- The test-design reviewer raised three advisory points after the first green
  run. Two were fixed in the spec: the boundary test now also asserts that the
  plain-string log set is exactly the one boundary line (so a PHI-leaking line
  without a correlation ID is caught), and the AppShell wiring test now strips
  comments and asserts the `app-shell` region and `id="main"` are nested inside
  the boundary without depending on return-statement formatting. The third —
  red/green framing — was already recorded above: these are characterization
  guards for pre-existing behaviour, with no implied TDD red phase. A temporary
  diagnostic test was used to observe React's printf-formatted console call and
  was deleted; it is not part of the change.
- Senior React noted the spec does not itself render Arabic WEB-09 labels, and
  pointed to `tests/components/StateViews.responsive.test.tsx` as the existing
  Arabic proof; that is suite-wide coverage, not a new gap in this clause.
- No production defect, outage or drifted tracker was observed. No `task-requests`
  block is needed: every needed change was inside the two-file scope.
- Reviewer evidence: the three mandatory reviewers each read both new files and
  the named production sources and returned GO with no Critical or Required
  finding; the code reviewer verified the 11-kind mapping against
  `StateViews.tsx:225-247` and the AppShell regex anchors; the coverage auditor
  verified the config include/exclude paths and the absence of skips or pragmas;
  DevSecOps verified the log filter, the patient-token absence assertions and
  the absence of credentials or PHI-shaped strings.

## Lessons for workers

- In a plain `.ts` Vitest spec, a provider that requires `children` cannot be
  mounted with `createElement(Provider, props, view)` (TS2769) nor with
  `children` inline in the props object (`react/no-children-prop`). Build the
  props in a variable (`const i18nProps = { initialLocale, children: view }`)
  and call `createElement(I18nProvider, i18nProps)`, as the localization spec
  does.
- React 19's own caught-error log has a printf-style first argument (`%o…`),
  while an application line is a plain string. Filtering only by correlation ID
  proves the ID-bearing line is clean but misses a second PHI-leaking line; also
  assert the complete plain-string log set instead of mocking the boundary.
- A clause test that claims a "global" boundary must prove the app-root wiring,
  not only mount the component in isolation; a structural `readFileSync` regex
  against `AppShell.tsx` keeps the proof in a test-only scope.
- For a test-only proof story there is no red state to observe; say so plainly
  and prove non-vacuousness by asserting exact control sets, callback counts and
  negative cases instead of hunting for a production change.
