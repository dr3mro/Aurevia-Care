# PHARM-02 — API: pharmacy status events kept separate

## Summary

Added a bounded RX-02 pharmacy status kernel in `com.aurevia.pharmacyflow.status`
that records four **separate, append-only** facts: accept, reject (mandatory reason), ask
clarification, and dispensing evidence (who/when/what). Dispensing evidence never sets the
`accepted` flag — acceptance is derived only from a real `PHARMACY_ACCEPTED` fact. Every
write requires `If-Match` (optimistic version) and `Idempotency-Key` (a retried action
replays its original fact and records once). No inventory or stock concept was introduced.
The immutable fact types reuse the existing `RxContract.EventType` vocabulary and the shared
`SpecialtyRoles.PHARMACY_STAFF` role; the kernel mirrors the established `WorklistService`
pattern (domain kernel + thin injected controller).

## Affected requirements

RX-02 (primary). Supporting boundaries: ARC-01/ARC-03 (append-only facts, If-Match,
Idempotency-Key), IAM-01 (fresh `pharmacy_staff` role), OPS-02 (immutable fact trail).
Spec sentence: "Track submitted, delivery confirmed, pharmacy accepted/rejected,
clarification, renewal and cancellation events separately. Distinguish dispensing evidence
from acceptance."

## Risk class

Cross-boundary (new HTTP API + domain kernel). Safety-relevant facts (accept/reject/
dispensing evidence) are covered by synthetic tests only; no live clinical enablement and
no human participant evidence. Reviewed by tool evidence and simulated pharmacy workflow.

## Review owner

Senior Java and Spring Boot (backend kernel); pharmacy workflow specialist (simulated).
Independent QA review remains with the integrator.

## Data changes

None in scope. The kernel holds its append-only trails and idempotency ledger in process
memory, exactly like `radflow/worklist/WorklistService`. No migration, backfill or lock
impact. Persistence (RLS migration + Jdbc store + restart survival) is deferred to a
follow-up task requested below; the task scope forbids `db/migrations` and carries no
reserved migration version.

## Authorization boundaries and audit events

- Tenant, actor and roles come only from `TenantContext` (set by `TenantContextInterceptor`)
  and a fresh `StaffRepository.activeRoles(subject)` lookup; none is taken from a resource
  or body. Only `pharmacy_staff` may record a fact (403 otherwise).
- `If-Match` is parsed by `IfMatch.parse` (428 missing / 422 malformed); a stale version
  yields 412 `STALE_VERSION`. `Idempotency-Key` is parsed by `IdempotencyKey.parse`
  (428 missing / 422 malformed); a scoped retry returns the original fact once.
- Each emitted fact carries actor + `Clock` time. A dedicated `audit_event` row is **not**
  written by this slice (no `AuditAppender` in scope); the persistence follow-up should add
  it. The append-only fact trail itself is the attributable record in this slice.

## Migration and rollout considerations

No migration or rollout in scope. When the follow-up persists the kernel, it must add a
tenant-owned forced-RLS table for the fact trail and idempotency ledger, an HTTP integration
test proving restart survival and cross-tenant concealment, and the OpenAPI/client entries.

## Clinical and architecture review

Synthetic review only. No signed data, cross-organization sharing or real patient data.
Live clinical acceptance and enablement remain a G5 human gate. Architecture follows the
in-repo `WorklistService` kernel pattern: pure domain kernel, thin injected controller,
persistence/outbox deferred.

## Findings

1. **Persistence deferred (follow-up task requested below).** The kernel is process-local,
   like `WorklistService`; there is no RLS migration, Jdbc store, `audit_event` row or
   OpenAPI/client entry in scope. `scripts/check-wiring.py` passes because the service has a
   controller caller, but that does not make the facts durable. Downstream PHARM-03/05/07
   depend on this API and should be reviewed against the persistence gap.
2. **Pre-existing, unrelated gate failure.** `scripts/check.sh`, `bash scripts/python-coverage.sh`
   and `python3 -I -m unittest discover -s scripts/tests` all fail only in the five
   `test_check_pack` tests plus `check-pack.py`, reporting `opencode.json is stale`. The
   worktree `opencode.json` is a CI profile copied under `skip-worktree`; its SHA differs
   from the committed HEAD file. I did not touch `opencode.json`, agents, skills or
   `scripts/`, so this is the documented environmental artifact, not caused by this change.
   `python-coverage.sh` also warns that the Python `coverage` package is not installed here.
3. **If-Match header required=false.** Spring returns 400 for a missing required header, so
   both headers are bound with `required = false` and parsed explicitly to return the
   documented 428/422 (matching `InstructionController`).

## Lessons for workers

- A first write starts at version 1 with an empty trail (`events.size() + 1`), so an
  `If-Match` of 1 is valid for the first fact and the version advances per append. Keeping
  the first version at 1 avoids a conflict with `IfMatch.parse`, which rejects 0.
- When adding an HTTP success/failure test pair, check instruction coverage, not just line
  and branch: a method whose only test throws before `return` leaves the `areturn`
  instruction uncovered (`PharmacyStatusController.reject` initially showed 168/170).
- SpotBugs fails on `catch (NullPointerException)`; prefer an explicit null guard before a
  narrow `catch` of the specific parse exception.
