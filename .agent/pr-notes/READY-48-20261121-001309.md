## Summary

The three data-backed patient tabs now read through the READY-47 authenticated transport instead of returning placeholder lists. Appointment data comes from the patient endpoint `GET /api/v1/patient/appointments?patientId=…` (it **does** exist, so no appointment placeholder was kept), released reports from `GET /api/v1/patient/reports` and the conversation inbox from `GET /api/v1/conversations/inbox`. Untrusted JSON is validated at each loader boundary and mapped to the existing appointment/report/conversation domain types; no new domain type duplicates an existing one.

A shared `ScreenStateView` and a generic `PatientResource` give every screen loading, empty, error, offline and session-expired states. A 401 calls `onSessionExpired`, which clears the OS-backed credential via `clearToken()` and swaps the tab navigator for a signed-out screen whose text comes from `messages.ts` in English and Arabic. Commands (confirm, download, open thread) remain the existing no-op placeholders; this story replaces placeholder *reads* only.

## Authorization boundaries and audit events

The transport re-reads the credential for every request (READY-47), so revocation takes effect on the next load. The patient identifier is sent only to the patient appointment endpoint and the server re-verifies the link; the client never infers a patient from a response. `unitKey` is used as the inbox display label because the inbox projection carries no localized unit name; no directory lookup or cross-unit read was added. A closed thread is treated as read-only and a reply is never synthesized. No server-side audit event is added or changed; no patient data, token or error body is written to logs, URLs or local storage.

## Findings

1. **HIGH — the server serializes `AppointmentStatus` as its enum name, not the documented lower-case wire value (out-of-scope API defect, in-scope mitigation applied).** Verified with tool evidence: `messaging/appointments/AppointmentStatus.java` defines `wire()` but has no `@JsonValue`, and unlike every other wire-facing enum in `apps/api/src/main/java` it has no Jackson annotation; `PatientAppointmentControllerHttpTest.java:93` itself sends `"CHECKED_IN"`. Jackson therefore emits `"BOOKED"` while `contracts/openapi.yaml:612` documents `booked`. Left unhandled, `parseAppointment` would reject every real appointment and the tab would always show the generic error state. **In scope:** `appointmentStatusFromWire` in `providers.ts` now accepts both forms and returns the canonical lower-case domain value, so confirmation eligibility still works; two tests cover the exact server form at loader and screen level. **Out of scope for this worker:** adding `@JsonValue` to `AppointmentStatus.wire()` and aligning the API HTTP test / contract generation. The owning API story must do that; this worker did not edit `apps/api` or `contracts`.
2. **No state-component module existed in the patient app.** `docs/design/screen-recipe.md` and staff-web describe `StateViews`; patient-mobile had none. The five shared state views were therefore created in `src/app/screenStates.tsx` inside scope, rather than importing the out-of-scope staff-web components. This is the smallest honest way to satisfy the acceptance criterion and should be reconciled with the design docs by the owning tracker.
3. **The patient appointments endpoint exists.** `messaging/appointments/PatientAppointmentController` serves `GET /api/v1/patient/appointments`; the `GET /api/v1/appointments` staff route was not used and no placeholder was kept.
4. **Jest collects tests only under `src/**` in this module**, not under `apps/patient-mobile/tests`. Tests were accordingly colocated under the in-scope `src/app` and `src/features` directories, matching READY-47's precedent; `jest.config.ts` was not touched.
5. **Conversation payload mismatch:** the inbox projection supplies `unitKey`, `patientReadSequence` and an authoritative `unreadCount`, but no localized `unitName`, organization id, message trail or connection status. The loader uses `unitKey` as the display label, takes the organization id from app context, keeps `messages: []`, and adds an optional `unreadByConversation` prop to the existing inbox component so the server count is authoritative. A localized unit-name lookup and a real connection-status flag are follow-ups; no message content is fabricated.
6. **Malformed JSON maps to the offline state.** Loaders reject malformed payloads with `MALFORMED_*` errors, which `PatientResource` deliberately maps to offline (non-`TransportError` → network). This keeps the failure generic and non-clinical; distinguishing corrupt data from connectivity would need a new typed transport kind and is out of scope.
7. **Synthetic API origin and identity.** `PATIENT_API_BASE_URL = 'https://api.synthetic.example'` plus fixed synthetic organization/patient identifiers live in `providers.ts`/`RootNavigator` because no configuration source or login exists yet (READY-46). A deployment-backed origin and real identity must replace them before any real use; no URL, credential or patient datum is committed.
8. **Commands remain no-ops.** Confirm, details, download, open-thread and account actions still use `placeholderAction`; this story is explicitly a read-path change. Buttons may appear inert until the command stories land.
9. **Client-side confirmation policy is row-derived.** `deriveConfirmation` receives the server's `confirmationEnabled` flag for both site and row enablement. ADM-01 site-level enablement remains a gap for a later story.
10. `parseReleasedReport` was already a private, fully tested validator in `features/reports/reportClient.ts`; it was exported (one keyword) and reused rather than duplicating validation. The stale `/api/v1/released-reports` path inside that client is untouched and is not used by this story.

## Lessons for workers

- In `apps/patient-mobile`, put new tests under `src/**` — the Jest `testMatch` ignores a fresh `tests/` directory, so a correct test placed there would silently never run and would leave the new production file uncovered.
- Import `jest` from `@jest/globals` before `jest.fn`/`jest.mock`; bare `describe`/`it`/`expect` do not need it.
- Keep loader, emptiness and session callbacks referentially stable (module-level functions or `useCallback`). Inline arrows recreate the `useEffect` dependencies and reissue requests, which makes late-response tests flaky and can loop in the app.
- Do not call `setState` synchronously inside `useEffect` — the module's ESLint config rejects it with `react-hooks/set-state-in-effect`. Set the loading state in the retry event handler instead.
- React Testing Library's `toHaveTextContent` matches the exact whole string in this pinned version; use `getByText(...)` or a `RegExp` when a container has multiple text children, and render strings inside `<Text>` (RN test renderer rejects bare text at the root).
- The canonical gate is `bash apps/patient-mobile/check.sh`; it re-runs `npm ci`, so `npm run test:coverage -- --ci --runInBand` is the fast inner loop while iterating.
- Before trusting a fixture against a Java enum field, check the server type for `@JsonValue`: an unannotated enum serializes as its constant name, so a lower-case-only client parser will reject every real response even though all local fixtures pass.
