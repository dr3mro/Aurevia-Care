# SPEC-XCH-06-C03 — XCH-06 clause 3 API test

## Summary

Added a clause-focused, DB-backed HTTP integration test and the matching clause evidence doc. No
production code, existing test, migration, contract or dependency was changed. The test proves that
withdrawing or correcting a release immediately changes `GET /api/v1/patients/{patientId}/released-revisions`,
retains `GET /api/v1/releases/{id}/history`, and persists the policy-defined recipient scope in the
`release_notification` outbox (`prior-recipients` for a retraction, `linked-patient` for the fresh
authorization of a correction). The persisted `recipient_scope` assertion is the genuine increment:
existing HTTP tests assert only `event_type`, and unit tests stop at the repository boundary.

Files added (only these two, both in scope):

- `apps/api/src/test/java/com/aurevia/exchange/clauses/HandleCorrectedWithdrawnReleasesUpdatingCurrentAccessTest.java`
- `docs/spec/clauses/exchange/handle-corrected-withdrawn-releases-updating-current-access.md`

## Affected requirements

XCH-06 (clause 3, verbatim: "Handle corrected or withdrawn releases by updating current access,
retaining history and notifying affected recipients per policy."). Acceptance mapping:

- current access updated → `withdrawalUpdatesAccessRetainsHistoryAndNotifiesPriorRecipients`,
  `correctionMovesAccessToNewRevisionRetainingHistoryAndNotifyingPriorRecipients`;
- history retained → same two tests (`GET /{id}/history` plus row survival);
- notify affected recipients per policy → persisted `recipient_scope` assertions in both tests;
- refusals → five negative tests (wrong role, other tenant, stale version, forbidden state/duplicate,
  missing or invalid input).

the service re-derives membership and roles inside the guarded transaction. No PHI, token or

## Findings

- The advisor brief is incomplete: it did not mention `it/exchangerelease/PatientReleaseIsolationTest`,
  which already proves the withdraw/correct access, history, stale-version, terminal-state, duplicate,
  tenant-isolation and role-refusal cases at HTTP level. This test deliberately does not duplicate
  those exact assertions; it adds the persisted `recipient_scope` proof. Source: tool file reads.
- The advisor brief is wrong about one status: it says a stale `If-Match` returns 409; the code
  returns **412 `STALE_VERSION`** (`ReleaseService.java:199,386`; `ApiErrorCode.STALE_VERSION`),
  and the test asserts 412. 409 is reserved for illegal transitions and concurrent CAS conflicts.
  Source: tool file reads and the executed HTTP test log showing 412.
- The journey-loop and acceptance tests named in the brief exercise different release stacks
  (`labflow.release` and `messaging.reports`), not `exchange.release`; they are not evidence for this
  clause's package. Source: tool file reads.
- "Notifying" in this slice means appending a `release_notification` outbox row with a policy
  `recipient_scope`; no dispatcher consumes the outbox inside `src/main`. The doc records this
  boundary. Source: tool grep and context-optimizer report.
- The release routes are baselined in `contracts/openapi/missing-routes.txt` (lines 83, 103-104,
  310-313), so no OpenAPI or generated-client change was made; the doc notes the existing
  `FIX-OPENAPI-*` ownership. Source: tool grep.
- Environment artifact only: `opencode.json` is the CI profile under `skip-worktree`, so
  `worker-check.sh`, `check-pack.py` and six `test_check_pack` tests report staleness. The committed
  HEAD profile is correct; no file was edited. Source: tool commands.
- Pre-existing defect on `origin/main`, not introduced by this task (tool evidence, out of scope):
  `git grep -nE '^(<<<<<<<|>>>>>>>) '` finds conflict markers in three tracked files —
  `apps/api/src/main/java/com/aurevia/exchange/hl7/Hl7ParseException.java:6,10`,
  `Hl7Parser.java:14,18` and `Hl7Segment.java:10,14`. They exist identically at baseline `742855d4`
  and in `origin/main`, inside Javadoc comments, so Java compilation still succeeds and `check-docs.py`

## Lessons for workers

- When a clause test is requested, search for existing clause suites before designing new coverage —
  here `it/exchangerelease/PatientReleaseIsolationTest` already owned most assertions, and the real
  increment was a single persisted-column assertion (`recipient_scope`) that no HTTP test made.
- Trust the code over an advisor brief for exact statuses: this brief's stale-version 409 was wrong;
  `ApiErrorCode` and the executed HTTP log gave 412.
- Never combine `-Pfast` with `-Dgroups=integration`; `fast` sets `excludedGroups=integration` and
  silently runs zero integration tests. Confirm the Surefire count.
- For a proof-only story, a reverted expectation probe is the clean way to show fault detection
  without touching production code: change one expected value, observe the red assertion, restore,
  rerun green, and record both final lines.
- In a cloud worker, a red `worker-check.sh`/`check-pack.py` usually means the CI `opencode.json`
  under `skip-worktree` (`git ls-files -v` → `S`). Confirm with `git show HEAD:opencode.json`, run the
  remaining gate stages individually, and never regenerate or commit that file.
- Bind instants as `OffsetDateTime` (the repository already does) and end text-block SQL with a
  space before concatenated columns; both lessons came from earlier notes and were avoided here.
