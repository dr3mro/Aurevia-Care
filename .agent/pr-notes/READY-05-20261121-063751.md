# READY-05 — Structured JSON logs with correlation ID and a redaction test (WEB-06)

## Summary

Completes the WEB-06 wiring on the API side: switches the console to ECS structured
JSON, publishes the validated correlation id to SLF4J MDC from the tenant interceptor
and clears it at request completion, and adds an HTTP-level redaction acceptance test.
No logging library or dependency was added. No request/response body logging was
turned on, and no subject or organization is written to every log line. All data is
synthetic; no patient data, token or real identifier appears in code, tests or logs.

## Findings

1. **Known tooling artifact (both wrapper gates red).** `worker-check.sh` and `check.sh`
   exit 1 at `check-pack: opencode.json is stale` before reaching any Java check, and
   three `test_check_pack` cases in the Python suite fail for the same reason. In this
   cloud worker, `opencode.json` is the CI profile installed under `skip-worktree`
   (`git ls-files -v opencode.json` = `S`), so the pack check judges that file rather
   than HEAD. Verified via the generator that `git show HEAD:opencode.json` equals the
   generated local profile while the worktree copy does not. This is the documented
   OPS-CW-003-01 false positive, unrelated to this change; no protected file was edited.
   The underlying Java checks (targeted tests, JaCoCo, SpotBugs, check-names,
   check-wiring) all pass.
2. **Correlation ownership divergence (pre-existing, not introduced here).** READY-52's
   observability filter accepts `X-Correlation-Id` only as a UUID, while the tenant
   interceptor accepts the looser `[A-Za-z0-9._-]{1,128}` allowlist. The new `MDC.put`
   makes MDC follow the interceptor's value. With a valid UUID header (as in
   `LogRedactionTest`) the filter, MDC, response header, tenant context and error body
   all carry the same id; with a non-UUID header the filter logs its generated UUID
   while MDC/tenant context carry the header value. This behavior predates this story
   (the interceptor already echoed and audited that value) and needs a Product Owner /
   Architect decision to unify correlation ownership. No in-scope change was made; the
   story's literal acceptance is met for valid correlation ids.
3. **OWASP dependency scan not run locally.** No `NVD_API_KEY` is available in this
   worker; the integrator/CI runs the OWASP gate. SpotBugs, the other required static
   analysis, passed with no findings.
4. No new dependency, no `@SuppressFBWarnings`, no `.github/workflows`, `.opencode/`,
   `scripts/` or tracker edit. No push, tag or `gh` call.
5. **Review finding — MDC removed before the filter's completion log (not changed).** The
   review observed that `afterCompletion` runs inside the filter chain, so the filter's
   ECS completion line is emitted after the interceptor removed MDC; the correlation id
   still appears inside `RequestLogFormatter`'s fixed JSON message (the assertion in
   `LogRedactionTest` passes), but it is not additionally MDC-stamped on that one line.
   The story explicitly requires `MDC.remove` in `afterCompletion`, and the filter is
   outside this story's scope, so no change was made. If owner-approved, the fix belongs
   in a follow-up that gives MDC cleanup a single owner in the observability filter.
6. **Review finding — comment accuracy on direct `preHandle` throws (fixed).** MDC is put
   before the authentication/tenant/rate-limit checks, and Spring skips `afterCompletion`
   when `preHandle` throws; the filter's `finally` clears MDC in production, and both
   tests clear MDC in `@AfterEach`, so there is no cross-request leak. The original
   comment overstated that `afterCompletion` "covers direct interceptor use"; it was
   corrected to state that the filter owns cleanup on every path and `afterCompletion`
   clears the normal completion path. Review also suggested reusing
   `CorrelationIdFilter.MDC_KEY` instead of the literal; the literal was kept exactly as
   the story prescribes, avoiding a new cross-layer dependency in `src/main`.

## Repair attempt 1 — coverage-check failure (ECS log format)

**Failure (tool evidence, integrator coverage check).** Full `mvn verify` reported
`Tests run: 2535, Failures: 1, Errors: 3`, all in the two log-parsing tests:
`LogRedactionTest.errorRequestLogsCorrelationIdButNeitherBodyNorTokenMarker:96`
("a log line must carry the correlation id") and three `CorrelationIdFilterTest`
methods — `logsMethodMatchedRouteStatusAndLatency:113`,
`usesConstantRouteWhenNoHandlerPatternWasMatched:129`,
`clearsMdcAndLogsWhenTheChainThrows:177` — each with
`NullPointerException: JsonNode.get(String) ... is null`.

**Root cause (diagnosed from the captured lines in the failure output).** The `ecs`
console format from `application.yml` is applied globally once any of the 48
`@SpringBootTest` classes in the full suite initialises Spring Boot's logging
system in the shared surefire fork. The filter's completion line then becomes an
ECS envelope whose `message` field holds the escaped five-field JSON, while
Spring's own init lines carry a top-level MDC `correlationId`. The old parsers
selected a line by the plain `"correlationId"` substring (matching an MDC-stamped
init line) and read fields off the envelope, producing the NPEs; a second
assertion counted plain-quoted `"correlationId"` lines. Isolated worker runs
(`-Pno-security,fast`, no Spring context) kept logback's plain pattern and
passed, so the defect appeared only in the full verify. This is a test-harness
defect; no production behavior changed.

**Fix (test-only — no production code, threshold, exclusion or skip changed).**

- Added `src/test` helper `RequestLogCapture`: selects the line by logger name
  (`CorrelationIdFilter`), then returns the inner JSON when an ECS `message`
  field is present, otherwise the parsed line itself.
- `CorrelationIdFilterTest`: all eight field reads go through the helper; the
  "exactly one request log line" assertion now counts `CorrelationIdFilter`
  lines by logger name instead of the plain-quoted `"correlationId"` substring.
- `LogRedactionTest`: the correlation assertion compares the parsed request-log
  `correlationId` to the header value; the two redaction-marker assertions are
  unchanged.

## Lessons for workers

- Setting `logging.structured.format.console: ecs` turns every captured log line
  into an ECS envelope once any `@SpringBootTest` runs in the surefire fork, and
  MDC stamps a top-level `correlationId` on Spring's own init lines. Assert on
  request-log lines by logger name and unwrap the `message` field; never select
  by a plain-quoted field name or assume logback's default pattern.
- In a cloud worker the worktree `opencode.json` is a CI profile under `skip-worktree`.
  When `check-pack`/`test_check_pack` says it is stale, verify HEAD truth with
  `git show HEAD:opencode.json == gen_opencode.render(local)` instead of regenerating;
  do not edit the protected file.
- When proving JaCoCo coverage for a small change without the ten-minute full `verify`,
  run only the tests that touch the class, delete `target/jacoco.exec` first, then
  `mvn ... jacoco:report` and read the touched class's row in `jacoco.csv`.
