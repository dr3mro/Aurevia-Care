## Findings

1. **The Delivery blocker was pre-existing on `origin/main`, not introduced by this branch.**
   `905c23d0` widened `ExportRecord` to seven components; `20bbffe6` repaired the four fixture
   call sites in `OffboardingCommandTest.java`. This branch's diff for that file is empty. The
   branch's own new test and clause doc were correct and pass once compilation was repaired, as
   the debugger also found. The repair is already tracked in `BUGS.md` as `DELIVERY-1983`
   ("Four offboarding fixtures missed provenance …; local repair updates fixtures …; 13
   offboarding and 2542 staff tests passed locally. Full Delivery pending."), so no new defect
   entry or task request is needed from this worker.
2. **Scope decision.** The debugger's fix plan named an out-of-scope file, and the task says
   "Do not change production code, an existing test, the contract or a migration" and limits
   scope to the CLN-04 test and clause doc. Since the fix had already landed on main, this worker
   made no code change rather than editing or duplicating that repair. No `task-requests` block
   is needed because an existing repair already owns the file.
3. The debugger's optional strengthening assertion (`assertEquals("offboarding-proof",
   export().provenance().purpose())`) was not applied: it is out of scope, the current fixture
   uses purpose `"offboarding"`, and it is not required to clear the compile failure.
4. Pre-existing, out-of-scope defect: three files under
   `apps/api/src/main/java/com/aurevia/exchange/hl7/`
   (`Hl7ParseException.java`, `Hl7Parser.java`, `Hl7Segment.java`) contain committed
   conflict-marker lines inside Javadoc. They are in HEAD, harmless to compilation and untouched.
5. Environmental false positive OPS-CW-003-01: `git ls-files -v opencode.json` returns `S`
   (skip-worktree CI profile), so `check-pack.py`/`test_check_pack` judge the CI profile rather
   than the committed local profile. Not a defect of this change; the protected file was not
   edited.
6. `InMemoryTemplateStore` under `src/main` and the CLN-04 domain-service implementation are
   pre-existing; this branch only adds proof, so the senior-backend "reachable and durable"
   checklist (migration, Jdbc store, controller, HTTP integration test, OpenAPI entry) applies to
   the original implementation stories, not to this test-only proof.
7. Test-style deviation, disclosed rather than hidden: neighbouring `chart/clauses` tests that
   have an HTTP surface are `@Tag("integration")` `@SpringBootTest` tests against PostgreSQL with
   `RestClient`. This proof is deliberately an in-memory domain-service test using
   `InMemoryTemplateStore`, matching `TemplateVersioningTest` / `TemplateNoteAcceptanceTest`
   rather than the HTTP clause tests. No HTTP controller uses the clinical `TemplateService`, so
   an HTTP-level proof is not available inside this story's test-only scope. The clause doc's
   `## Evidence` states this openly; "Proven by tests" means proven at the domain-service entry
   point, not over HTTP or across a database restart.

## Lessons for workers

- Before editing a file a debugger report names, reconcile with `origin/main` and re-run the
  exact failing command. A parallel repair can land the fix on main between the debugger run and
  the fix worker; verify with `git diff origin/main..HEAD -- <file>` and a targeted `-Dtest=...`
  instead of trusting the report's age.
- When a debugger's proposed fix lies outside the declared task scope and the task forbids
  changing an existing test, re-verify first; if main already owns the repair, record it under
  `## Findings` and keep the diff scoped rather than duplicating the fix or widening scope.
- For a Java test-only proof, state explicitly that JaCoCo instruments `src/main` so there are no
  new production branches; name the targeted Surefire command and map each active negative test
  to the refusal path it covers, and let the integrator run the full gate.
- In cloud workers, `git ls-files -v opencode.json` showing `S` explains `check-pack.py` red;
  prove it once and run the remaining policy stages individually instead of editing the file.
