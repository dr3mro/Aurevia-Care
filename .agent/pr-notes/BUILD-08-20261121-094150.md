## Summary

Delivered the remaining XCH-04 gap: an operator reconciliation workflow for unmatched or conflicting results. The `exchange.result` package already implemented five-facet identifier matching, owner/coverage-queue routing, append-only revisions, correction lineage and queue creation (from S-G2-04). BUILD-08 adds a named disposition command — **match**, **reject** or **reassign** — each requiring a recorded reason, with reassignment requiring a new named owner. A repeated resolution of the same entry is rejected rather than overwriting the first decision.

The entry point is `POST /api/v1/xch04/reconciliations/{id}/resolve`; the recorded decision is read back with `GET /api/v1/xch04/reconciliations/{id}/resolution`. Authorization, validation and audit are enforced in one tenant-guarded transaction in `ReconciliationService`; `ReconciliationDecision` holds the pure guards.

## Affected requirements

- **XCH-04** — Route every final, corrected and critical result to a named owner and coverage queue; match patient, source, accession, destination and order before import; unmatched/conflicting reports enter a reconciliation queue.
- Supporting code references ARC-02 (tenant/RLS scope), ARC-03/ARC-04 (HTTP boundary), IAM-01/IAM-06 (role policy) and OPS-02 (append-only audit). No new requirement IDs were introduced into code names.

## Risk class

**Safety-critical** (docs/WORKFLOW.md): this is an operator override of patient/order identity matching and can change where a clinical result is routed. Negative-path tests (denial, concealment, invalid reason, already-resolved, unknown action, tenant isolation) are included. Simulated senior-backend and senior-integrations reviews were requested; no human clinical or unit participant reviewed this change.

## Review owner

Senior Java and Spring Boot / Senior Integrations (simulated, advisory). No human reviewer signed off.

## Data changes

- **No migration added or changed.** The task has no `reserved:` migration version and scope excludes `db/migrations`. No tables, columns, constraints or grants were changed.
- The reconciliation decision is held in an append-only, tenant-keyed in-domain projection (`ConcurrentHashMap` in `ReconciliationService`) and appended to the durable OPS-02 audit log. It is **not** a durable status column update.
- Reason: V22 grants `smartclinic_app` only `SELECT, INSERT` on `xch04_reconciliation` and explicitly `REVOKE UPDATE` (V22 lines 240-249). A `status = 'resolved'` UPDATE would fail at runtime with permission denied. This matches the accepted precedent in BUILD-11 (scoped review queue held in-domain, durable persistence deferred to a storage story).

## Authorization boundaries and audit events

- Tenant comes only from `TenantContext` (set by the request interceptor); the entry is read through the RLS-bounded `ResultRepository.findReconciliation`. Membership and roles are re-derived inside each transaction, so revocation takes effect on the next request.
- New action `XCH04_RECONCILIATION_RESOLVE` is allowed for `lab_verifier` and `tenant_admin` only; `clinician`, `privacy_auditor` and `reception` are denied (the auditor may *read* the queue but not resolve it).
- Audit: purpose `XCH04_RECONCILIATION_RESOLVE`, resource type `RECONCILIATION_ENTRY`; outcomes `SUCCESS`, `DENIED`, `CONFLICT`. `resourceId` is the queue entry id (the actor is derived by the V3 trigger), so no patient identifier, payload, reason or name is written to the audit event.

## Migration and rollout considerations

No migration, backfill, lock or volume impact; no rollback needed for schema. Operational limitation to carry into the follow-up storage story: a resolved entry still appears in the durable `open` queue because its status row cannot be updated without a bounded `GRANT UPDATE (status)` migration. The in-domain projection is per API instance and is lost on restart; the audit trail of the decision is durable.

## Findings

- The `exchange.result` package already satisfied most of XCH-04; the true gap was operator resolution. No duplicate matching/routing implementation was added.
- **Durable status limitation — HIGH (simulated senior-integrations finding F-1, confirmed by source inspection)**: V22 installs a `BEFORE UPDATE OR DELETE` immutability trigger on `xch04_reconciliation` (V22 lines 162-175) *and* revokes UPDATE (lines 245-249), so advancing `status` to `resolved` is impossible at runtime regardless of grants. No migration version is reserved and migrations are outside scope, so the resolved decision lives in an append-only in-domain projection plus the durable audit log. A resolved entry remains visible in the durable `open` queue; the decision is lost on restart and is invisible to other API instances. The POST returns the decision and the read-back endpoint exposes it, so this is a visible limitation, not a silent failure — but it does **not** meet AGENTS.md's "data survives a restart" done-criterion. The `ReconciliationDecision.decide` closed-entry guard is therefore a domain-precondition guard exercised by its unit test, not a production-reachable path today.
- **F-2 (MEDIUM)**: the new controller test is `MockMvc` standalone with a mocked service, not a DB-backed HTTP integration test; one cannot pass against durable state because no durable state is written. The integrator's database suite does not cover the new endpoint.
- **F-3 (LOW)**: the two new paths are not in `contracts/openapi.yaml`; the whole XCH-04 slice was already undocumented there and this change adds two more paths. Out of scope (no dependencies, no files outside `exchange`), so deferred.
- **F-4 (LOW, fixed)**: the controller conflict test originally stubbed `ENTRY_CHANGED`; it now stubs the real domain code `ENTRY_ALREADY_RESOLVED`.

**Simulated senior-backend review (static; no commands executed by the reviewer).** It reported a "critical compile blocker" — `authorize(context, id)` called with two arguments against a one-argument declaration — and a medium finding that the audit `resourceId` was the operator subject. ## Lessons for workers

- Before implementing a "new" capability, survey the domain package and `git log`: a requirement can already be largely present from an earlier gate story. Deliver the real remaining gap.
- Check the runtime SQL grants in `db/migrations` before writing an UPDATE. V22 gives `smartclinic_app` only SELECT/INSERT on `xch04_reconciliation`; an UPDATE there would fail at runtime even though unit tests with a mock JDBC template pass.
- In a cloud worker, a `check-pack`/`test_check_pack` failure with skip-worktree flag `S` on `opencode.json` is a CI-profile measurement artifact. Confirm with `git ls-files -v` and `cmp`, never edit the protected file.
- `scripts/check.sh` calls `mvn verify` (every integration suite). Under the worker time cap use targeted `-Dtest=...` runs plus `jacoco:report`, the fast profile and the individual policy scripts instead.
