# READY-11 — Staff web OIDC login with a session cookie and CSRF protection (WEB-03)

## Summary

Added the staff web browser OIDC authorization-code chain beside the existing stateless bearer chain. A new `@Order(1)` chain matches only requests without `Authorization: Bearer`, uses `oauth2Login`, an HTTP-only secure `SameSite=Lax` session cookie, CSRF with a readable `XSRF-TOKEN` cookie, a 12-hour absolute session guard driven by the injected `Clock`, and `POST /logout` that invalidates the server session and clears both cookies. The bearer chain is now `@Order(2)` and keeps its no-CSRF behaviour. The tenant interceptor now accepts the browser `OAuth2AuthenticationToken` with the same verified `sub`/`orgs` claim rules as the JWT path. Startup fails closed outside `synthetic-auth` when any OIDC environment value is missing. All fixtures are synthetic; no credential, token or patient data was committed. The `synthetic-auth` profile is unchanged.

## Affected requirements

WEB-03, WEB-02, IAM-01, ARC-02.

## Authorization boundaries and audit events

The browser chain requires an authenticated OIDC session for every non-bearer request. `TenantContextInterceptor` resolves the browser principal's user-info attributes through the existing `ClaimsTenantResolver`, so a session cannot widen its organization set and the tenant still comes only from `X-Active-Organization` intersected with verified claims. The bearer chain is unchanged: CSRF is ignored only for `Authorization: Bearer` requests. No new audit event was added; denial semantics (401/403) are unchanged.

## Migration and rollout considerations

`@ConditionalOnWebApplication(SERVLET)` keeps the non-web startup test green and prevents the browser chain from existing without an HTTP surface. The profile annotation keeps `synthetic-auth` untouched. In production all three `SMARTCLINIC_OIDC_*` values must be supplied; the issuer and client secret are never written to the repository. The identity provider must publish `/authorize`, `/token` and `/userinfo` under the issuer and return `sub` and `orgs` in user-info; this assumption is documented in the class Javadoc and should be confirmed with the real IdP before enablement (see Findings). The host must terminate TLS so the session and XSRF cookies carry `Secure`.

## Findings

1. **`TenantContextInterceptor` had to change.** It previously accepted only `JwtAuthenticationToken`, so an authenticated browser session would still receive 401 on `/api/v1/**`. The new `OAuth2AuthenticationToken` branch delegates to the existing `ClaimsTenantResolver`; no new claim rule was introduced. Identified by the Senior Spring Security specialist plan before implementation.
2. **Boot client registration properties cannot be placed in `application.yml` with empty defaults.** A first attempt put `spring.security.oauth2.client.registration.smartclinic.client-id: ${SMARTCLINIC_OIDC_CLIENT_ID:}` in the base document; `SmartClinicApiApplicationTest.startsTheApplicationEntryPoint` then failed with `IllegalStateException: Client id of registration 'smartclinic' must not be empty` even in a non-web context. The registration is now built in `StaffWebLoginConfiguration` from custom `smartclinic.oidc.*` placeholders, with no network discovery and an explicit fail-closed message.
3. **The XSRF cookie is not written by the default `XorCsrfTokenRequestAttributeHandler`.** It defers token resolution and sets a fixed `_csrf` request-attribute name, so a GET never materialised the `XSRF-TOKEN` cookie (verified: 302 to `/oauth2/authorization/smartclinic` with no `Set-Cookie`). Setting `CsrfTokenRequestAttributeHandler.setCsrfRequestAttributeName(null)` forces resolution on every response; the cookie is now asserted in `csrfCookie()`. This matters for the SPA reading `XSRF-TOKEN` from `document.cookie`.
4. **`bash scripts/worker-check.sh` fails before any API check** with `check-pack: opencode.json is stale: run scripts/gen-opencode.py`. Verified environmental cause: `git ls-files -v opencode.json` reports `S` (skip-worktree); its worktree SHA equals `.github/opencode.ci.json`, while `git show HEAD:opencode.json` is the generator's local profile — the documented CI-profile artifact (OPS-CW-003-01). No protected file was edited. The underlying gates were run individually and are green above.
5. `python3 -I -m unittest discover -s scripts/tests -q` → `Ran 436 tests … FAILED (failures=3)`; the three failures are all `test_check_pack` cases about the same opencode.json CI-profile drift, not this change. `bash scripts/frontend-check.sh` passes.
6. **WEB-03 limits deliberately out of scope:** listing and revoking a user's *other* sessions requires a session registry and needs a person to approve a follow-up task. Lockout and rate-limiting of the authentication endpoints is also not part of this slice. Neither is claimed as covered.
7. OWASP Dependency-Check was not run locally (no `NVD_API_KEY`; it times out without fresh NVD data). The new starter is managed by the Spring Boot parent with no version tag; the integrator's cached-NVD run owns this evidence.
8. Audience is still not fail-closed (`SMARTCLINIC_OIDC_AUDIENCE` defaults empty), an existing production-enablement risk recorded in the AUD-20261120-03 notes and not widened here.
9. **Health probes are not exempt in a non-synthetic profile (pre-existing, not introduced here).** Both chains use `anyRequest().authenticated()`, so `GET /health/live` and `/health/ready` need a credential outside `synthetic-auth`; the browser chain would redirect them to OIDC login. WEB-05 requires these routes to be unauthenticated. This belongs to a WEB-05/health-lifecycle story with its own tests — do not fix it inside READY-11.

## Lessons for workers

- In this Boot 4.1.2 / Spring Security 7 slice, `AntPathRequestMatcher` no longer exists — use `PathPatternRequestMatcher.pathPattern(HttpMethod.POST, "/logout")`, and `ClientRegistration.getProviderDetails().getAuthorizationUri()` instead of the removed top-level getters.
- With `CookieCsrfTokenRepository`, the default CSRF request handler will not write the `XSRF-TOKEN` cookie on a GET; set `CsrfTokenRequestAttributeHandler.setCsrfRequestAttributeName(null)` or the SPA has no token to send.
- Boot validates `spring.security.oauth2.client.registration.*.client-id` at startup even with empty defaults; keep custom env-backed properties and build the registration yourself when a profile must stay untouched.
- `MockHttpSession` has no `setCreationTime`; override `getCreationTime()` in an anonymous subclass for deterministic age tests.
- SpotBugs flags `OAuth2AuthenticationToken.getPrincipal()` dereference; `Objects.requireNonNull` satisfies it without adding a JaCoCo branch.
