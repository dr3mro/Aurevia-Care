## Findings

- The brief describes a single prescription exhibiting submitted, delivery
  confirmed, accepted, rejected, clarification, renewal and cancellation in one
  flow. `State.canTransitionTo` and the V59 DB guard make acceptance and
  rejection mutually exclusive and rejection terminal, so the positive test
  drives two synthetic prescriptions and asserts each ordered trail separately.
  No production gap and no `@Disabled` fallback: the clause is fully built.
- The brief states missing `If-Match` yields `400 PRECONDITION_REQUIRED`. The
  actual contract is `428` (`com.aurevia.api.IfMatch.parse` throws
  `ApiException(428, "PRECONDITION_REQUIRED", ...)`; `ApiErrorHandler` returns
  that status). The test asserts the real 428 and records `code` as
  `PRECONDITION_REQUIRED`. Brief guidance was inaccurate here; no rule changed.
- The task/story text permits `@Disabled("GAP: ...")` for an unbuilt clause, but
  `scripts/check-constraints.py:56` rejects `@Disabled`/`@Ignore` in Java and
  the quality gate would fail. Because the clause is implemented, no disabled
  test is committed. Had a positive assertion been red, the plan was to drop
  that method, set doc Status to `Partly proven`, describe the gap and add a
  `task-requests` block — never a skipped test.
- `coverage-check.sh` and the full integration stage of `worker-check.sh` are
  integrator-owned for this worker run (see Coverage); no protected file was
  edited to work around the known check-pack artifact.
- Pre-existing, unrelated defect observed while checking the post-merge tree:
  committed HEAD contains literal conflict markers inside Javadoc in

## Lessons for workers

- Before writing a clause test, check `git log --all --grep=<story>` and the
  remote branches: a prior attempt may already have a green, unmerged test you
  can learn from, and its notes may record brief inaccuracies and gate traps.
- `check-constraints.py` rejects `@Disabled`/`@Ignore` in Java even when the
  story text suggests a disabled GAP test; if the clause is built, keep every
  test green and enabled, otherwise drop the red method and use the doc Status
  plus a `task-requests` block.
- Assert HTTP error status via the numeric `getStatusCode().value()` for 422 and
  428 to avoid Spring `HttpStatus` alias mismatches (`UNPROCESSABLE_ENTITY` vs
  `UNPROCESSABLE_CONTENT`).
- A clause that includes mutually exclusive outcomes needs one synthetic
  prescription per outcome; a single trail cannot show both acceptance and
  rejection.
- In a cloud worker, `git ls-files -v opencode.json` showing `S` explains
  `check-pack`/`worker-check.sh` "opencode.json is stale" failures; confirm with
  `git show HEAD:opencode.json` and never regenerate or commit that file.
- Do not run `scripts/check.sh`, the full `mvn verify`, `coverage-check.sh` or
  the full `-Dgroups=integration` stage in a swarm worker; run the targeted
  `-Dtest=...` suite plus individual policy scripts and leave full gates to the
  integrator.
