# AUD-20261121-25 — Wire PatientAccessService to a real HTTP entry point

## Summary

`PatientAccessService` was a `@Service` with no HTTP caller: enrollment, invitation redemption and recovery were unreachable. Added a thin, tenant-scoped `PatientAccessController` under `/api/v1/patient/access` that injects the service plus `StaffRepository` and `TransactionTemplate`, derives the actor from `TenantContext` (organization + subject) and freshly resolved active roles, and delegates all 15 PAT-03 commands. No domain logic, store, migration or existing production class was changed. Added a MockMvc adapter test (drives the real service/in-memory store) and a real-PostgreSQL HTTP integration test covering the three named acceptance scenarios.

Evidence provenance: all test/coverage/policy results below came from executed tool commands; the bounded design reviews came from read-only `smartclinic-senior-backend` and `smartclinic-test-engineer` subagents (simulated review). No simulated-user, clinician or human-participant evidence is claimed. Synthetic fixtures only.

## Data changes

None. No Flyway migration was added or edited; V83 already owns the six `patient_access_*` tables with forced RLS. The HTTP integration test creates and drops its own synthetic database and seeds only synthetic organizations, identities, memberships, role assignments and one chart per tenant.

## Authorization boundaries and audit events

Organization comes only from `TenantContext.current()`; subject from the same context; roles are re-read every request from `active_roles(:subject)` inside the tenant-guarded transaction (same pattern as `AttachmentController.actor()`). No role or organization is accepted from request bodies, so a client cannot widen authority. Authorization, chart-link ownership, single-use CAS and lockout decisions remain entirely in `PatientAccessService`; the controller adds no decision and no new audit event. The service's existing append-only `patient_access_event` facts (invitation issued, enroll success, verification failed, account locked, etc.) are now produced by real HTTP requests.

## Migration and rollout considerations

No migration or backfill. `scripts/check-migrations.py --require-baseline` is green. Rollout is a normal controller addition; no data migration or rollback script is required. The wiring baseline now contains two stale entries (`PatientAccessService`, `PatientAccessStore`) that the integrator may delete from `scripts/wiring-baseline.json` (that file is outside this worker's scope).

## Findings

- OpenAPI: the committed client is generated from `CommandCatalog` (`contracts/openapi/README.md`), not from `@PostMapping` methods. My controller does not change that catalog, so no generated artifact changes and no regeneration is required for this slice; adding routes increases the documented route-coverage gap tracked by the open `FIX-OPENAPI-01`/`FIX-OPENAPI-02` tasks. `contracts/` is outside this task's scope, so no OpenAPI file was edited. The story's "regenerate the OpenAPI client" done-item therefore cannot be satisfied inside this scope — it belongs to those tasks.
- `check-pack.py` reports `opencode.json is stale`: `git ls-files -v opencode.json` → `S` (CI profile under `skip-worktree`, the known OPS-CW-003-01 artifact). HEAD truth was not changed and the protected file was not regenerated.
- `bash scripts/python-coverage.sh` exits 1 in this worker. Its output includes `{"file": "TODO.md", "rule": "tracker"}` printed by `scripts/tests/test_worker_gate.py` test cases (not a real violation) and other pre-existing Python-tooling environment noise recorded in `.agent/pr-notes/2026-11-20.md`. No `scripts/*.py` file was touched by this story.
- A first HTTP IT run exposed a real test-isolation constraint: `patient_access_account` has `UNIQUE (organization_id, subject)`, so reused subjects collided across tests (`409 CONFLICT`). Fixed by seeding a unique patient subject per test; no production change was needed.
- TOCTOU is unchanged from the established controller pattern: roles are snapshotted at request start and commands run in later store transactions, so a revocation between them can still authorize that one request. Accepted limitation, same as `AttachmentController`/`ImagingController`; no ownership claim beyond what the store provides.

## Lessons for workers

- Derive identity from `TenantContext` plus `StaffRepository.activeRoles` inside the tenant-guarded transaction for any kernel that takes an explicit actor; never read a role or organization from the body (`AttachmentController.actor()` is the reference implementation).
- Mockito here uses the subclass maker, so a `final @Service` cannot be mocked. A controller unit test can instead inject the real service with an in-memory store — stronger evidence and no production change.
- Mock a `TransactionTemplate` by answering `execute(any())` with `((TransactionCallback<?>) arg).doInTransaction(null)` so the actor-resolution lambda is actually exercised.
- When HTTP integration tests write per-subject rows, generate a fresh subject for every test; `UNIQUE (organization_id, subject)` on `patient_access_account` makes reused subjects collide across methods.
- `scripts/check-wiring.py` prints "is fixed; delete it from baseline" notes without failing; those baseline edits belong to an integrator, not a scoped worker.
- A "stale `opencode.json`" from `check-pack.py` inside a worker is usually the CI-profile `skip-worktree` artifact; verify with `git ls-files -v` and never regenerate the protected file.
