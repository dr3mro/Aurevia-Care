## Delivery failure diagnosis (debugger report)

**Root cause found: yes.**

### Failing commands

- CI: `bash scripts/frontend-check.sh` (Delivery job "Frontend standards", step 4), run
  `45044501435`, head `422de002260e488fbbb77e040dc50879096f3acd`, 16:33:36Z–16:36:41Z,
  conclusion `failure`. First actionable error (check-run annotation):
  `TestingLibraryElementError: Unable to find an accessible element with the role "rowheader" and
  name "MAIN"` at `apps/staff-web/tests/responsive/features-admin/FacilitiesPage.responsive.test.tsx:199`,
  test `responsive FacilitiesPage (WEB-07, UX-01) > renders one logical page with every facilities
  section at compact`. The printed DOM showed the table with its three `columnheader`s and an
  **empty `<tbody />`** — the facility row had not been committed yet.
- Aggregating job: "Delivery gate" step `Require every verification job to pass` failed solely
  because of that job. "Java and database verification" (`.github/actions/java-verify`) **succeeded**
  in the same run, as did "Policy and tooling", "Delivery tooling tests" and "Developer reference".

### Root cause

`FacilitiesPage` renders its `table` only after `useApi` resolves, but the rows come from
`PageSink`'s post-commit `useEffect` (`apps/staff-web/src/features/admin/PageSink.tsx:16-19`)
which calls `append` → `setAccumulated`. The test waits only for the table
(`await screen.findByRole('table', …)` at line 190) and then asserts the row **synchronously** with
`getByRole('rowheader', …)` at line 199. The table can therefore be present while `tbody` is still
empty; the assertion races the effect-driven re-render. Under a slower or differently scheduled
runner the row loses the race. Confidence: **high** — the printed DOM exactly matches the
pre-effect state, and the identical files pass on a later run. The test was introduced on `main`
by `a075fa01` (08:38:19 -0500, 2026-11-22), before this PR's first commit `bbc725ff` (16:12:47Z).
`git diff 422de002..HEAD -- apps/staff-web apps/patient-mobile` is empty, so this PR changed no
frontend file at all.

### Fix plan (out of scope for this worker)

1. In a **separate** staff-web task (owner: the integrator/Product Owner), make the four row
   assertions at `FacilitiesPage.responsive.test.tsx:199-201` wait for the committed row — e.g.
   `await within(table).findByRole('rowheader', { name: 'MAIN' })` — and apply the same pattern to
   any sibling responsive test that asserts a `PageSink`-appended row after `findByRole('table')`.
2. Prove it with `bash apps/staff-web/check.sh` (includes `tsc --noEmit`) and by running the flaky
   test repeatedly, then a green "Frontend standards" job on the exact SHA.

## Lessons for workers

- When the integrator says only `Delivery failed on the current head`, read the **public**
  check-run metadata for that SHA (`GET /repos/<owner>/<repo>/commits/<sha>/check-runs` and
  `/check-runs/<id>/annotations`) before assuming a Java cause: the failing job can be Frontend
  standards, and the annotation names the exact test and line. No `gh` or token is required.
- Compare the failed head with the current head (`git diff <failed>..HEAD -- <module>`) before
  changing code. If the failing module is unchanged and its CI job turns green on a later run of
  identical files, the cause is a flaky test, not the story.
- A test that `findByRole`s a container and then `getByRole`s a child appended by a post-commit
  `useEffect` (here `PageSink`) races the re-render; the child assertion must `findByRole`/`waitFor`.
- Do not "fix" an out-of-scope flaky test from a scoped worker: record the exact file, line, error,
  fix plan and command, and hand it to the owner as a separate task.
