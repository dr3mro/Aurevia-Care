# SPEC-CLN-05-C06 — CLN-05 clause 6 (API test)

## Summary

Test-only acceptance proof that signing a clinical note is a separate act from
patient release and PDF rendering. Adds one real-PostgreSQL HTTP integration
test class and one clause-evidence note. No production code, migration,
contract, existing test or tracker was changed.

Two new files only:

- `apps/api/src/test/java/com/aurevia/smartclinic/chart/clauses/SigningDiffersPatientReleasePdfRenderingTest.java`
- `docs/spec/clauses/chart/signing-differs-patient-release-pdf-rendering.md`

## Affected requirements

CLN-05, clause 6 — "Signing differs from patient release and PDF rendering."
(`SMARTCLINIC_V1_SPEC.md:55`.)

## Risk class

Routine (contained test and documentation addition). The subject clause is
clinical documentation, but this change does not alter any behavior, route,
permission, data model or release path.

## Review owner

Senior backend / test engineering; read-only plan, code, coverage and security
reviewers were consulted as recorded under `## Review verdicts`.

## Data changes

None. No migration, backfill, lock or volume impact, rollback or forward-fix.
The test creates a disposable database `smartclinic_cln05_signing_it` from the

No new boundary or audit event. The test asserts the existing behavior: sign

note. Audit events added or changed: none.

## Migration and rollout considerations

None. No rollout step; the change is test-only and carries no production

Entry-point-to-assertion trace:

1. `POST /api/v1/clinical-notes` → `ClinicalNoteController.create` →
   `ClinicalNoteService.createDraft` → one committed draft revision.
2. `POST /api/v1/clinical-notes/{id}/sign` with `If-Match: "1"` →
   `ClinicalNoteController.sign` → `ClinicalNoteService.sign` →
   `NoteRepository` appends one signed revision. HTTP 200 and `state=signed`
   are asserted.
3. A separate JDBC connection binds `app.current_org`, reads the control count
   from `clinical_note_revision` (2 revisions), then asserts zero rows in
   `patient_release`, `release_event`, `report_release_revision`,
   `document_pdf_job` and `rendered_document`.
4. Negative traces: `POST /{id}/release` and `POST /{id}/render` → 404;
   sign by a reception member → 403; sign by a clinician of another tenant →
   404 with both tenants' counts controlled; stale `If-Match: "1"` after an
   edit to version 2 → 412; empty attestation → 422. Each negative path also
   ends in the same zero-row assertions.

  triggered and no test was disabled.
- No mutation rehearsal was performed: temporarily adding a release side effect
  to production code would breach the two-file scope. The green tests are
  regression proofs; the repository's mutation tier remains the independent
  check that an assertion would notice a wrong result.
- Pre-existing observation in the base (not touched by this change):
  `apps/api/src/main/java/com/aurevia/smartclinic/exchange/hl7/*.java` contains
  committed conflict-marker text inside Javadoc comments. `mvn compile`,
  SpotBugs and check-constraints pass with it; it is unrelated to CLN-05.
- Optional hardening suggested by reviewers, not blocking and not in scope:
  replace the harness-style `field()` scanner with Jackson (which would also
  remove its unused missing-key and numeric-field branches), drop the always
  true null guards in `request`, and seed a sentinel row per ledger to prove
  each table itself is visible rather than relying on the shared tenant-bound
  connection. These are test-source helpers only, not JaCoCo-scoped production
  code, and none changes the clause verdict.

## Lessons for workers

- A zero-row count under FORCE RLS is vacuous unless the tenant is bound on
  that same connection and a positive control proves committed rows are
  visible; bind the tenant again for every tenant you check, not just the
  owning one.
- Assert numeric status codes (`.getStatusCode().value()`) for framework
  validation errors: the symbolic `HttpStatus` constant for 422 differs
  between Spring versions (`UNPROCESSABLE_CONTENT` vs
  `UNPROCESSABLE_ENTITY`), while the wire contract does not.
- In a cloud worker, `opencode.json` is a skip-worktree CI profile: confirm
  with `git ls-files -v` (S) once, record the failing commands and final lines,
  run the remaining gate stages individually, and never regenerate or edit the
  protected file.
- Read the task's read-first paths from the repository, not only from the
  advisor brief: a cited clause note lived under `docs/spec/clauses/product/`,
  not the brief's `chart/` path.
