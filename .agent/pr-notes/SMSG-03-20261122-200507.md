# SMSG-03 — API: instant conversations inside a facility

## Summary

Verify-and-close pass on the instant staff-chat slice at
`com.aurevia.staffmsg.instant`. The base implementation was already
merged in `ff19a818`; this run kept it, proved the gates from actual tool
execution, and closed three real in-scope gaps found by specialists:

1. `createGroup` accepted a non-empty peer list naming only the actor and
   created a group with zero peers — now rejected with 422 after normalization.
2. The `ConcurrentHashMap.merge(..., Math::max)` read-cursor monotonicity had
   no failing-capable test — now guarded end to end by a lower-after-higher
   `markRead` regression test.
3. Task acceptance #2 ("only staff of the same facility with an active role may
   take part") relied on a caller-supplied facility id. It now re-derives the
   authoritative membership-facility fold (V93 `public.is_facility_out_of_scope`)
   inside the tenant-guarded transaction for every actor, peer, new participant
   and caller, failing closed with 403.

No dependency, migration, contract, staff-web or tracker file was edited. No
push, tag or `gh` call was made. All fixtures are synthetic.

## Authorization boundaries and audit events

Tenant and actor come only from `TenantContext.current()` (`context()` fails
closed with 403 when unbound); request records carry no org or actor field.
Every command re-checks active staff membership/roles via
`store.activeStaff`, and now also `store.facilityWithinScope` against the V93
fold — for the actor and each peer at open/create, the new subject at add, the
caller in `requireAccess` (send/markRead/messages/add/remove) and in the two
list endpoints. The fold's facility argument is the tenant's DB `f.code`, not
request-body input; a facility absent from the tenant yields `false`. A former
member still sees history up to `left_at` but is refused on send/markRead.
Cross-organization access is concealed as 404 by forced RLS. The controller
passes the `Idempotency-Key` header only; sender/role are bound by DB triggers.
No audit event type was added or changed (MSG-07 audit remains a separate task).

## Lessons for workers

- A green JaCoCo number is not a behavioral proof: `Math::max`/`orElseGet` style
  JDK calls add no instrumented branch. Name the monotonicity/retry invariant
  and write a test that would fail under the naive implementation.
- `NamedParameterJdbcTemplate.queryForObject` throws `EmptyResultDataAccessException`
  on zero rows; for a fail-closed predicate use a scalar `COALESCE((SELECT ...),
  false)` so "absent" returns a value instead of throwing.
- Validate a collection *after* normalization: a non-empty input list can still
  normalize to an empty set once the actor is removed or peers are deduplicated.
- Prefer the tenant's existing authorization fold over a local reimplementation.
  `public.is_facility_out_of_scope` already encodes assignment, legacy scope and
  oversight-role exceptions; calling it with the DB facility code keeps the rule
  in one place and makes the request body untrusted for scope.
- In a cloud worker, confirm `git ls-files -v opencode.json` before treating a
  `check-pack`/`worker-check` staleness failure as a change defect; run the
  remaining gate stages individually and record the artifact once.
