# AUD-20261120-01 — Return HTTP 201 from patient registration and catalog entry creation

## Summary

`contracts/openapi/generated/openapi.yaml` declares `'201'` for `registerPatient` (POST `/api/v1/patients`) and `defineCatalogEntry` (POST `/api/v1/catalogs/{family}/entries`), but `PatientController.register` and `CatalogController.define` returned `ResponseEntity.ok(...)` (HTTP 200) with no `Location` header. Both now use `ResponseEntity.created(...)`, matching the convention already used by `StaffController`, `FacilityController`, `ConfigurationController` and `AppointmentController`. Tests that asserted 200 for these two POSTs were changed to assert 201, and the two primary HTTP tests now assert the `Location` header. No OpenAPI file, other controller, migration or shared tracker was changed.

## Findings

1. Real defect (the task): both POSTs answered 200 while the contract declares 201. Fixed as described. No `Location` header was present; now both include one.
2. `ConfigEntry` has no `code()` accessor — it carries `key` (`catalog.<family>.<code>`), `version`, `value`, etc. The story's suggested `created.code()` therefore does not compile. The `Location` is built from `request.code()`, the validated tenant-local code already passed to `CatalogService.define`; validation happens before the return, so the value is authoritative. `Patient` does have `id()`, so the patient `Location` uses `created.id()` as suggested.
3. Scope discrepancy: the declared scope lists test paths under `.../smartclinic/web`, but every assertion that expected 200 for these POSTs lives under `.../smartclinic/it/`. The story explicitly requires changing those assertions and defines "done" as "no test expects 200 for them", and `worker-check.sh` runs the integration tier, so leaving them unchanged would make the gate red. The six affected `it` test files were updated minimally (status expectation only, plus the two `Location` assertions). No other integration test was touched. The change is recorded here so the orchestrator can reconcile the scope if needed.
4. Environment findings (not repository defects): (a) worktree `opencode.json` is the CI profile under `skip-worktree`; (b) leaked swarm vars `CHECK_SCRIPT`, `BRANCH_PREFIX`, `BASE_BRANCH` break synthetic agent-run tests; (c) PyYAML missing in this image. All were handled in the environment only, as described above. No file outside the change was edited.
5. Simulated/human evidence: none. All evidence is tool-generated from synthetic fixtures. No real patient data, credential or clinical reviewer input was used.

## Lessons for workers

- When a worker prompt names a notes file and says "parallel worker", treat the scope field as a collision boundary but check where the assertions the story names actually live before declaring the task impossible: a narrow `web` test scope can still be contradicted by assertions in `it` packages that the same story requires to change. Record the deviation explicitly in Findings.
- In cloud workers, a red `check-pack`/`test_check_pack` with "opencode.json is stale" is usually the CI profile under `skip-worktree`, not a real staleness. Compare the worktree with `.github/opencode.ci.json` and use `git show HEAD:opencode.json` before regenerating anything; a protected-file edit would block the PR.
- Swarm job variables (`CHECK_SCRIPT`, `BRANCH_PREFIX`, `BASE_BRANCH`) leak into the synthetic unit tests of `scripts/agent-run.sh`; unset them with `env -u ...` when running `scripts/worker-check.sh` locally, otherwise unrelated tests report failures.
- `python3 -I` ignores `PYTHONPATH`; a missing `yaml` module cannot be fixed by exporting `PYTHONPATH`. Install the wheel into site-packages (environment only) instead of editing a protected script.
