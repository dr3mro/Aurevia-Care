## Affected requirements

XCH-06, clause 3, verbatim: "Handle corrected or withdrawn releases by updating current access,
retaining history and notifying affected recipients per policy."

Acceptance mapping:

- current access updated → `withdrawalUpdatesAccessRetainsHistoryAndNotifiesPriorRecipients`,
  `correctionMovesAccessToNewRevisionRetainingHistoryAndNotifyingPriorRecipients`;
- history retained → the same two tests (`GET /{id}/history` plus release-row survival);
- notify affected recipients per policy → persisted `recipient_scope` assertions in both tests;
- refusals → five negative tests (wrong role, other tenant, stale version, forbidden
  state or duplicate revision, missing or invalid input).

## Findings

- Root cause of the earlier stop (tool evidence): the first pass's `## Test evidence` section
  quoted a failed Maven assertion whose expected and actual values were each wrapped in angle
  brackets. The worker gate's placeholder detector — a regex matching a short non-whitespace
  token between angle brackets — matched both tokens and emitted
  `notes-placeholder`, so the whole run was recorded as not finished. This file writes those
  values in words and contains no angle-bracket token in either required section.
- The same earlier notes also quoted a conflict-marker grep pattern made of alternating
  angle-bracket runs; that text sat in a non-required section and did not trigger the gate,
  but this file avoids that form too. Source: tool inspection of
  `.agent/pr-notes/SPEC-XCH-06-C03-20261122-162651.md` and `scripts/worker_gate.py`.
- Optional, not adopted: the code reviewer suggested adding a release-id filter to the
  withdrawal notification query so both positive tests filter symmetrically. Correlation ids
  are unique per test (the two commands use distinct values), so the existing assertion is
  unambiguous; the test is left unchanged to keep the already-reviewed proof stable.
  Source: orevia-code-reviewer (simulated, read-only).
- The advisor brief is incomplete: it did not mention
  `it/exchangerelease/PatientReleaseIsolationTest`, which already proves the withdraw/correct
  access, history, stale-version, terminal-state, duplicate, tenant-isolation and role-refusal
  cases at HTTP level. This test deliberately does not duplicate those exact assertions; it
  adds the persisted `recipient_scope` proof. Source: tool file reads.

- Environment artifact only: `opencode.json` is the CI profile under `skip-worktree`, so

## Lessons for workers

- A hand-off notes file must keep its `## Test evidence` and `## Coverage` sections free of any
  short token enclosed in angle brackets. A Maven "expected versus was" diff, a generic type in
  prose, or a conflict-marker grep pattern all match the worker gate's placeholder detector and
  turn an otherwise green run into "not finished". Write such values without brackets or in
  words, then verify with the gate before committing.
- When a fix pass is only about the notes format, re-run the targeted test and the individual
  policy scripts on the already-committed change instead of rewriting the proof; re-ask the three
  post-code reviewers for fresh GO verdicts and carry forward the plan-reviewer GO.
- Never combine `-Pfast` with `-Dgroups=integration`; `fast` sets `excludedGroups=integration`
  and silently runs zero integration tests. Confirm the Surefire count.
- For a proof-only story, a reverted-expectation probe is the clean way to show fault detection
  without touching production code: change one expected value, observe the red assertion,
  restore, rerun green, and record both final lines.
- In a cloud worker, a red `worker-check.sh` or `check-pack.py` usually means the CI
  `opencode.json` under `skip-worktree`. Confirm with `git ls-files -v`, verify with
  `git show HEAD:opencode.json`, run the remaining gate stages individually, and never
  regenerate or commit that file.
