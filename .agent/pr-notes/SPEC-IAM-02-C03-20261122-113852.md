# SPEC-IAM-02-C03 — Permission changes take effect on the next protected request

## Summary

Added a single-purpose, real-PostgreSQL acceptance test for IAM-02 clause 3 and the
matching clause evidence document. The test proves that a permission change takes
effect on the very next protected request through the normal HTTP entry points: a
`tenant_admin` can read its own staff record while active, an administrator
deactivates that subject by appending a revoked membership event, and the next
request from the same subject (unchanged synthetic subject header, no session
change) is refused with HTTP 403 "no active membership". Three negative tests prove
a wrong role and another tenant cannot change the permission and that missing or
forbidden deactivation states are refused. No production code, existing test,
contract or migration was changed. All data is synthetic.

Files changed (only these two, inside the declared scope):

- `apps/api/src/test/java/com/aurevia/smartclinic/authz/clauses/PermissionChangesTakeEffectNextProtectedRequestTest.java`

## Findings

- The clause is already built. `com.aurevia.smartclinic.staff.StaffService.authorize`
  re-checks `hasActiveMembership`/`activeRoles` on every command; `deactivate` appends
  a `revoked` membership event; V4 SQL functions fold the latest effective event with
  `valid_from`/`valid_to` gating. Deactivation is the in-scope G0 permission change;
  arbitrary role reassignment/permission-matrix edits remain a later slice. No
  production change was needed, so no `@Disabled` gap test was written.
- Pre-existing, out-of-scope: three committed files contain literal merge-conflict
  markers inside Javadoc on `main` —
  `apps/api/src/main/java/com/aurevia/smartclinic/exchange/hl7/Hl7ParseException.java`,
  `Hl7Parser.java` and `Hl7Segment.java` (from `origin/swarm/BUILD-37-469`). They are
  inside comments, so the build still compiles. I did not touch them; a later worker
  or the integrator should decide whether to clean them up.
- Pre-existing environment noise (confirmed once, not re-diagnosed): `check-pack.py`
  and the `test_check_pack` unit tests fail because the worktree `opencode.json` is
  the CI profile installed under `skip-worktree` (OPS-CW-003-01). The committed
  HEAD profile is correct. No protected file was edited.
- Source survey for step 1 of the task: implementation lives in
  `apps/api/src/main/java/com/aurevia/smartclinic/authz` (`ActionPolicy`), its neighbours
  `staff/StaffService`, `staff/StaffRepository`, `tenancy/FacilityService` and
  `web/TenantContextInterceptor`, the `db/migrations/V1`, `V2`, `V4`, `V12` SQL, and the
  `contracts/openapi.yaml` staff routes. `authz.history.RoleHistoryIntegrationTest.permissionChangeDeniesTheNextProtectedRequest`
  already proves the same rule through the role-history route.

## Lessons for workers

- Before designing a new clause test, grep the existing `authz.clauses` and
  `authz.history` tests: the neighbouring fixtures (`seedStaff`, `RestClient`,
  `@Tag("integration")`, per-class database name) and an existing proof of the same
  rule can be reused, so spend the effort on distinct negative cases instead.
- Assert the authoritative fold (`SELECT public.has_active_membership(...)`) before
  and after the permission change, not just the HTTP status: it turns a before/after
  200→403 assertion into evidence that the change, not a session artifact, caused the denial.
