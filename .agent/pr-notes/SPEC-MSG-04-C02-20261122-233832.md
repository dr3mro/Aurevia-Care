# SPEC-MSG-04-C02 — tie instructions to a relevant care relationship

## Summary

One new service-level API test class and one clause document prove the part of
MSG-04 clause 2 that exists today: `InstructionService.send` binds every supported
`ContextType`/`contextId` to the published revision, preserves the binding on a
replacement, and refuses a mismatched template context, a malformed or null key and
a context-free send against a context-requiring template. The tests also show the
binding is tenant-scoped. No production code, existing test, contract or migration
was changed. The clause document records `Partly proven` because the referenced
domain object is never checked for existence or relevance and no durable store exists.

## Affected requirements

MSG-04, clause 2 — `SMARTCLINIC_V1_SPEC.md:101`: "Tie instructions to the relevant
appointment, order, referral, prescription or encounter when available."

| Acceptance item | Evidence |

| A template's required context is enforced | `sendWithTemplateRequiringADifferentContextIsRejected`, `sendWithoutContextIsRejectedWhenTemplateRequiresOne` |
| The key is validated at the boundary | `sendWithMalformedContextIdIsRejected` |
| The binding survives a revision change | `replacementKeepsTheOriginalContextBinding` |

## Findings

- Clause 2 is only partly implemented: `InstructionService.send` stamps and shape-validates the context but never checks that the referenced domain object exists or belongs to the same patient/unit. There is no `JdbcInstructionStore` or migration; `InstructionStore.java` is listed under `store-without-durable` in `scripts/wiring-baseline.json`. The routes are tracked in `contracts/openapi/missing-routes.txt` (lines 70-71, 257-260) but absent from `contracts/openapi.yaml`. All of this is recorded in the clause doc's `## Gap` with files-to-change and a three-task estimate.
- Pre-existing, unrelated defect on `origin/main` (HEAD `f12e4f43`): committed conflict markers inside Javadoc comments of `apps/api/src/main/java/com/aurevia/smartclinic/exchange/hl7/Hl7ParseException.java:6,10`, `Hl7Parser.java:14,18` and `Hl7Segment.java:10,14`, referencing `origin/swarm/BUILD-37-469`. They are inside comments so compilation succeeds. Out of this task's scope; not touched. The integrator should route a repair.
- The clock-injected `InstructionService(store, actions, clock)` constructor is package-private, so a test in `messaging.clauses` cannot use it. The public two-argument constructor is used instead; no assertion depends on a timestamp. This deviates from the advisor's fixture list and is recorded here.
- No `@Disabled("GAP: …")` test was added despite the task's step-3 suggestion: `scripts/check-constraints.py:56` rejects any newly added `@Disabled`, so a GAP-disabled test would fail the constraint gate. The gap is documented in prose and all tests are executable.

## Lessons for workers

- Check constructor visibility before copying fixtures into a new package: the clock-injected `InstructionService` constructor is package-private, so cross-package clause tests must use the public constructor and avoid time assertions.
- A new `@Disabled("GAP: …")` test is a gate failure here, not a way to keep a pull request green; record the missing behavior in the clause doc instead and keep every test executable.
- In this worker image `opencode.json` is the CI profile installed under skip-worktree (`git ls-files -v` → `S`), so `check-pack.py`, `test_check_pack` and `python-coverage.sh` fail on staleness. Confirm once, run the other gate stages individually, and never regenerate that file.
- `InstructionControllerTest` already covers the HTTP entry point; a service-level clause test should say so explicitly rather than claim to exercise the controller.
