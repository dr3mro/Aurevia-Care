# BUILD-41 (fix pass) — make export expiry retriable after an interrupted transition

## Summary

Fix pass for BUILD-41 / OPS-07 on `swarm/BUILD-41-495`, continuing from the earlier
findings instead of restarting them. The in-scope tenant-export implementation was
already complete, test-first and 100% covered. The prior pass closed one object-store
leak (`start()` on a refused insert); this pass closes the remaining in-scope
correctness defect recorded as **BUILD-41-QA-1**: `TenantExportService.expire()` removed
the manifest object *before* marking the job row `EXPIRED`. When `markExpired` then
returned false, the method threw with the object already gone, the row still `COMPLETE`
and no `EXPORT_EXPIRE` audit; every retry then failed at the object check, so the job
could never reach `EXPIRED` or be audited as expired.

A failing regression test was written first (RED: `EXPORT_OBJECT_MISSING` thrown on
retry, and the object gone after a refused transition), then `expire()` was changed so
the durable status transition is the gate: mark the row first, refuse without touching
the object when it is no longer `COMPLETE`, and treat an already-absent object as the
desired end state. One production branch was removed and none added. No migration,
contract, dependency, threshold, exclusion or protected file was changed.

Evidence provenance: **tool** commands run by this worker (all commands below), plus
earlier **simulated reviewer** reports (senior-backend and QA) read from the hand-off
findings. No human, clinical or patient-participant evidence. No PHI or credential in
any note, log or test.

## Affected requirements

- **OPS-07** — an export artifact must expire and leave a consistent, auditable end

## Findings

- **Fixed this pass (BUILD-41-QA-1):** expiry now marks the durable row before removing
  the object. A refused transition (row no longer COMPLETE) leaves the object intact and
  throws 409 `EXPORT_STATE_CONFLICT`; a retry after an interrupted object removal now
  reaches `markExpired` and the audit instead of failing forever at the object check.
  An already-absent promoted object is treated as the desired end state, not a conflict.
- **Intentional test change (documented):** `expireRefusesWhenTheObjectWasAlreadyRemoved`
  was rewritten as `anInterruptedExpiryCanBeRetriedToCompletion` because the behavior it
  asserted (object-gone ⇒ 409 `EXPORT_OBJECT_MISSING`) changed on purpose: an already-gone
  object with a COMPLETE row is now recoverable. `expireRefusesWhenTheJobWasNotMarked`
  was strengthened with an object-survival assertion (not weakened).
- **Contract debt (out of scope):** the three export routes are baselined in

## Lessons for workers

- When two side effects must both happen (durable status and object removal), make the
  durable transition the single gate and do it first; treat "already removed" as the
  desired end state so an interrupted operation is always retriable. The reverse order
  can leave a row that no retry can reach.
- A failure-path test must assert final observable state (object present / absent, audit
  appended), not just the thrown status code; the 409 alone looked correct while the job
  was permanently stuck.
- An independent reviewer found a defect all earlier verification passes missed because
  every expiry test only checked the happy path or a bare 409. Review failure branches and
  retry semantics, not just acceptance headlines.
- In this cloud worker `opencode.json` is a CI profile under `skip-worktree`; compare with
  `.github/opencode.ci.json` and `git show HEAD:opencode.json` before believing a
  check-pack failure. Never regenerate or commit that file.
