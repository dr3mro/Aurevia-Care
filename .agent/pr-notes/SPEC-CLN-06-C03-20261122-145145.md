# SPEC-CLN-06-C03 — Spec CLN-06 clause 3 (API test): Only explicit confirmation creates a booking

## Summary

Adds a self-contained HTTP-level API test and a clause evidence note for CLN-06 clause 3,
"Only explicit confirmation creates a booking." The clause is implemented today in the
`scheduling.followup` domain: `FollowUpService.confirm` is the only command that calls the booking
port. The new test proves that a single explicit, version-preconditioned, authorized confirmation
creates exactly one appointment with follow-up provenance, and that every other path (suggestion,
override, task commands, missing or stale precondition, repeated confirmation, wrong role, peer
tenant) creates none. No production code, existing test, contract or migration was changed.

## Affected requirements

CLN-06 (clause 3). Full requirement: "Suggest a follow-up date using configured visit type
intervals and applicable prior follow-up. Explain the rule and allow authorized override with
provenance. Only explicit confirmation creates a booking. Care-team action tasks track owner, due
date and outcome."

## Lessons for workers

- When an API clause test books through follow-up confirmation, give each confirming test a
  distinct encounter date: `FollowUpBookingService` always books the first clinician at 09:00 on
  the suggested civil date, so two confirmations on the same date fail with `SLOT_CONFLICT`
  instead of proving the intended refusal.
- `If-Match` is the precondition for confirmation: omitting it yields 428, a stale value 412, and a
  second confirmation 409; assert the appointment count in each case, not just the status code.
- In a cloud worker, treat `check-pack.py`/`test_check_pack` `opencode.json is stale` as a
  measurement artifact when `git ls-files -v opencode.json` is `S`; confirm with `git show
  HEAD:opencode.json`, record the evidence once, run the remaining gate stages individually and
  never regenerate or commit that file.
