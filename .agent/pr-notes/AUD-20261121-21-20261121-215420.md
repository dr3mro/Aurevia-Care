# AUD-20261121-21 — Unify the duplicated ISSUER/CODE boundary regex in patient and lab accession

## Summary

The exact rule `[A-Za-z0-9_.:-]{2,32}` was declared three times: `patient/PatientService.java:31`
(ISSUER), `lab/accession/LabInputs.java:19` (ISSUER) and `lab/accession/LabInputs.java:21`
(CODE, used by `specimenType`, `siteCode` and `quality`). Added one typed primitive
`com.aurevia.smartclinic.api.contract.IssuerCode` that owns the single pattern, with a static
`issuerCode(String)` factory that returns a validated value and throws `IllegalArgumentException`
with a deterministic, non-sensitive message on invalid input. Removed all three declarations and
routed all four call sites through the primitive; each caller keeps its own field-specific `422`
code and message. Added direct boundary tests plus valid, punctuation, max-length (32/33),
Arabic/RTL and null assertions proving the same accept/reject behavior at a patient endpoint and
a lab endpoint. Synthetic fixtures only; all existing HTTP behavior is preserved.

## Affected requirements

IAM-03 (issuer-scoped patient registration), LAB-01 (accession issuer, specimen type, site and
quality codes), ARC-03 (shared API boundary primitives). Audit story AUD-20261121-21; no new
requirement behavior — a maintainability/de-duplication refactor found by the daily audit.

Acceptance mapping:
- "add one canonical issuer/code primitive in api/contract" → `IssuerCode.java` (new).
- "replace all three declarations and their usages" → `PatientService.java`, `LabInputs.java`;
  grep confirms no remaining ISSUER/CODE declaration of the rule in scope.
- "valid, punctuation, max-length and Arabic/RTL assertions proving identical accept/reject
  behavior across a patient and a lab endpoint" → `IssuerCodeBoundaryTest.java` (6 tests).

## Findings

- The one remaining `[A-Za-z0-9_.:-]{2,32}` fragment in
  `patient/consolidation/ConsolidationService.java:35` belongs to a distinct compound rule
  `[A-Za-z0-9_.:-]{2,64}@[A-Za-z0-9_.:-]{2,32}` (a 2-64 identifier plus `@` plus a 2-32 part),
  not one of the three identical declarations named by this story. It was left untouched; the
  reviewer also confirmed other `INVALID_ISSUER` sites (`ImagingService:164`,
  `WorklistService:109`) use a different `requireText` rule.
- `api.contract.CatalogCode` keeps its different `[A-Za-z0-9][A-Za-z0-9_.:-]{1,63}` rule
  (owned by AUD-20261121-04). Merging that rule into this primitive would change HTTP behavior
  (2-64 with a leading alphanumeric vs 2-32 allowing leading punctuation) and break AUD-04's
  callers and tests, so this story unifies only the three copies it names.
- Cloud-worker pack artifact: `git ls-files -v opencode.json` → `S` (skip-worktree); the worktree
  holds the CI `gh *` profile while `gen-opencode.py` renders the local profile. `check-pack.py`
  and all 5 failing `test_check_pack` cases stem from this alone. No `.opencode/`, agent or
  `opencode.json` file was edited; `git show HEAD:opencode.json` is the authoritative profile.
- No new defects were found in the changed code.

## Lessons for workers

- Follow the `CatalogCode` / `FacilityCode` primitive shape: a record with a static factory, a
  public `INVALID_MESSAGE` (and `PATTERN` when callers/tests need it), and a compact constructor
  throwing `IllegalArgumentException`; let each API caller translate it to its own `422` code and
  message. Records are implicitly `final`, so SpotBugs CT_CONSTRUCTOR_THROW does not apply.
- `List.of(...)` throws `NullPointerException` on a `null` element; use `Arrays.asList(...)` for
  rejected-input tables that include `null`.
- The fast (unit) tier alone can leave pre-existing `PatientService` branches red in a per-class
  JaCoCo read. Append a targeted integration run (e.g. `-Dtest=PatientRegistrationTest`) before
  `jacoco:report` to see 100% on touched classes without running the full verify.
- Inside a cloud worker, `S` on `opencode.json` means check-pack failures are a measurement
  artifact; verify against `git show HEAD:opencode.json` and never regenerate the committed file.
