# BUILD-01 — Staff invitations: single-use expiring invitation, accept and revoke

## Summary

Implemented IAM-02 staff invitations inside the declared scope. A tenant administrator issues an invitation carrying bounded roles, a facility and an expiry; only the SHA-256 hash of a cryptographically random one-time token is persisted, and the raw token is returned once in the issue response. The invitee accepts inside an authenticated tenant context; one database function atomically consumes the token, creates the membership, appends one role assignment per invited role, and records the inviter as grantor with an effective date. Pending invitations can be listed and unused ones revoked. All unusable tokens (expired, reused, revoked, unknown, wrong tenant) return the same 409 outcome.

Delivered in `apps/api/src/main/java/com/aurevia/smartclinic/staff` (8 new classes, one one-line visibility change to reuse the canonical role set), matching tests under `apps/api/src/test/java/com/aurevia/smartclinic/staff`, and `db/migrations/V70__build_01.sql`. No dependency, no file outside scope, no tracker file, no push/tag/gh.

## Data changes

New migration `V70__build_01.sql` (reserved version, additive, `Change: expand`), one new table `public.staff_invitation` and four functions:
- `require_staff_invitation_admin()` — BEFORE INSERT guard requiring an active `tenant_admin` in the selected organization; derives `invited_by`/`created_by` from `app.actor`.
- `require_distinct_invitation_roles()` — BEFORE INSERT guard; PostgreSQL forbids a subquery in a CHECK.
- `revoke_staff_invitation(uuid)` — admin-guarded conditional timestamp update.
- `set_granted_by_from_actor()` — CREATE OR REPLACE of the V4 function so a dedicated transaction-local `app.grantor_subject` GUC can name the inviter without contaminating the actor used by the V3 audit trigger; existing grant paths fall back to `app.actor` unchanged.
- `accept_staff_invitation(text)` — SECURITY INVOKER, tenant-scoped by forced RLS; one conditional `UPDATE` consumes the token, then identity, membership and role assignments are inserted; a dedicated grantor GUC makes the inviter the grantor and `now()` the effective date; every unusable token returns NULL and no partial state survives.

RLS `ENABLE` + `FORCE` + `USING/WITH CHECK (organization_id = public.app_org())`, composite FKs to `organization` and `facility`, `REVOKE ALL` then scoped `GRANT SELECT, INSERT` and `GRANT UPDATE (used_at, revoked_at)` (the column grant must follow the table-level revoke). No existing migration edited. No backfill; table is empty at deploy. No lock/volume impact beyond DDL on one empty table.

## Authorization boundaries and audit events

Administration (`create`, `listPending`, `revoke`) re-derives membership and roles from the authoritative store and applies the existing `STAFF_INVITE` / `STAFF_READ` policy actions (tenant_admin only); no new action constant was needed. Acceptance is authorized by the one-time token plus the active tenant context from `X-Active-Organization` and an authenticated `X-Synthetic-Subject` (same model as IAM-05 patient invitation redemption); it is not an unauthenticated token-only endpoint. DB triggers independently enforce the admin guard on issue/revoke.

Audit actions appended in the same guarded transaction: `STAFF_INVITATION_CREATE`, `STAFF_INVITATION_LIST`, `STAFF_INVITATION_REVOKE`, `STAFF_INVITATION_ACCEPT` (purpose `STAFF_ADMIN`, scope `STAFF`, outcomes `SUCCESS`/`DENIED`/`CONFLICT`/`NOT_FOUND`). The raw token is never placed in an audit resource id, log, list projection or URL.

## Findings

- **Environmental gate failure:** `opencode.json` is flagged `S` (skip-worktree) in this worker and holds the CI profile, so `check-pack.py`, `check.sh` and three `test_check_pack.py` tests report staleness. With `git show HEAD:opencode.json` restored temporarily, `check-pack.py` passes. No `opencode.json` change was made or committed.
- **Unmet general definition-of-done element, outside this task's scope:** the generated OpenAPI contract/client (`contracts/openapi/generated`) is emitted from `CommandCatalog` in `api/authorization`, and `authz/ActionPolicy` owns action constants. Both packages and `contracts/` are outside BUILD-01's declared scope, so no catalog entries or regenerated client were added. The HTTP routes are exercised by controller/integration tests and follow the existing `/api/v1` convention. A follow-up cross-boundary story should add catalog commands and regenerate the contract/client; I reused `STAFF_INVITE`/`STAFF_READ` so no new action constant was needed.
- The existing staff HTTP controller lives in `web/StaffController`; the new invitation controller is deliberately in the `staff` package because the scope forbids `web/`. Paths do not collide and the controller only injects its service.
- Accept requires an authenticated tenant context and the token; it is not an unauthenticated token-only endpoint. This matches the interceptor and the IAM-05 identity-invitation precedent.
- Role-duplicate enforcement had to move from a CHECK (PostgreSQL forbids subqueries there) to a BEFORE INSERT trigger; the service also passes a bounded role set.
- `set_granted_by_from_actor` from V4 is replaced by a backward-compatible version that prefers `app.grantor_subject`. This touches a shared function; existing invite/grant behavior is unchanged and the full integration suite should confirm it at integrator stage.
- Maven Central returned HTTP 429 for the surefire provider; a GCS mirror settings file was used for local test commands. The file is outside the repo and not committed.

## Lessons for workers

- In a cloud worker, treat `opencode.json` staleness as a measurement artifact when `git ls-files -v opencode.json` starts with `S`; verify with HEAD content and never "fix" the file.
- When Maven Central returns 429 on this shared runner, a settings mirror `https://maven-central.storage-download.googleapis.com/maven2/` unblocks test runs without touching repo files.
- PostgreSQL forbids subqueries in CHECK constraints; use a BEFORE INSERT trigger for set-like invariants such as distinct array elements.
- `GRANT UPDATE (col)` must come *after* any table-level `REVOKE UPDATE`; the later revoke silently removes the column grant.
- For forced-RLS tables, a plain `SELECT` plus a conditional `UPDATE ... WHERE used_at IS NULL` gives atomic single-use consumption without needing row-lock privilege the runtime role does not have.
