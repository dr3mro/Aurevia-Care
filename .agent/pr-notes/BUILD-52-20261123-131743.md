# BUILD-52 — Staff web: register the new feature routes and navigation

## Summary

BUILD-52 makes every BUILD-45..51 feature screen reachable through the staff-web
shell, lazily code-split, with role-scoped rail entries and direct-link denial
(UX-01, WEB-09). The production change is already present and committed at
`HEAD` `deea5ca0ecdadb9fe63546c2f3f9fc103c85b248`, contained in
`apps/staff-web/src/app`:

- `routes.tsx` self-registers every `../features/*/routes.ts` module lazily via
  `import.meta.glob` (`RESERVED_PATTERNS`, `collectFeatureRoutes`, catch-all last);
  no route is hand-listed.
- `navigation.ts` is the single source for both the rail (`navigationFor`) and
  the direct-link guard (`routeAccessRoles` / `canAccessRoute`), so a link hidden
  from a role cannot be opened by URL. Adds the `exports`/`imports` rows and their
  paired en/ar labels.
- `AppShell.tsx` lazily loads `ForbiddenPage` and renders it when the matched
  route is denied (`accessDenied` at `:287`, render swap at `:389`).
- `navigation.test.tsx` and the new `routeAccess.test.tsx` cover rail visibility,
  direct-link denial, allowed rendering, the catch-all and the OPS-08 two-role
  import grant.

## Authorization boundaries and audit events

- Access is derived from the single `navigation` table, the same source that
  renders the rail: `canAccessRoute` mirrors `navigationFor`, so hiding a link and
  denying a URL cannot drift apart. The base `staff` role keeps the screen map's
  "all staff" rows available to every signed-in user.
- `/operations/imports` lists both roles OPS-08 authorizes, so the shell no longer
  denies a role the import screen and service allow.
- System pages, parameterised detail pages with no rail row (for example
  `/pharmacy/:id`) and the catch-all have no nav entry and stay unrestricted;
  their own screens own any further state.
- No new audit event; no tenant, patient identifier, name or free text enters a
  route, a label, a log or browser storage. No role is read from the URL. The
  `AppShell role` prop is an isolated-render test seam; production uses
  `useRole()`.
- The guard is advisory UI hygiene; server-side authorization remains
  authoritative.

## Findings

- **Brief premise correction.** The brief described "feature `routes.ts` role
  constants"; the `features/*/routes.ts` files export only `routes: AppRoute[]`
  (patterns + lazy components). Role decisions live as literals in
  `app/navigation.ts:101-268` and as `*PERMITTED_ROLES` in feature `domain.ts`
  files. The bounded reads were therefore `app/*` plus
  `features/dataexchange/domain.ts` (supplied in the brief). This did not change
  the plan or the outcome.
- **Optional (context-optimizer, plan-reviewer, code-reviewer):** role lists are
  duplicated between `app/navigation.ts` and feature `domain.ts` files; they
  agree today. OPS-08 imports correctly lists both roles in both places. A
  drift-check test belongs in a cross-boundary story, not this one.
- **Optional (code-reviewer):** the backend
  `ControlledImportService.AUTHORIZED_ROLES` also contains
  `clinical_safety_lead`, which is not in the frontend `Role` union or
  `IMPORT_PERMITTED_ROLES`. Pre-existing cross-layer difference outside this
  rail's scope; it neither over-exposes a screen nor drops either required role.
- **Out of scope, pre-existing, disposition accepted (devsecops Required, GO).**
  Registered routes with no navigation row — `/lab/release`,
  `/lab/results/entry`, `/lab/turnaround-board`, `/operations/partner-board`,

  BUILD-52 *added* the guard, so it reduces net exposure; it does not widen it.
  The owning features are outside this task's scope; closing the gap needs

  `task-requests` entry asks for that.

## Lessons for workers

- Verify ground truth before editing: a prior fix note's "already implemented and
  green" can still be true in scope while the repo-wide gate has drifted red for
  unrelated reasons. Separate in-scope results from main-level artifacts.
- Keep the shell's role table in sync with each feature's authoritative role
  constant. A rail row that grants fewer roles than the page/API authorize makes
  the new shell guard deny legitimate users on a direct link (OPS-08 imports).
- A branch is not covered just because it is evaluated: the named test must fail
  if the clause were removed. Short-circuit operands such as
  `|| roles.includes(ALL_STAFF_ROLE)` and `matched !== undefined &&` are easy to
  leave untested.
- Distinguish in-scope regressions from pre-existing out-of-scope gaps when a
  reviewer flags a security issue. File a `task-request` rather than inventing
  roles or editing feature files outside the declared scope.
- For the staff web, done is `bash apps/staff-web/check.sh` (typecheck, lint,
  build, gzip budget and per-file 100% coverage), not Vitest alone; when an
  earlier stage fails, run each later stage individually to prove your scope and
  paste the `npm run typecheck` final lines separately.
