## Summary

Closed the remaining MSG-07 acceptance gap: a scoped conversation export now keeps validated, non-sensitive source provenance (a tracked tenant source resource, exact source revision, allowlisted purpose code) through the HTTP entry point, the domain service, the JDBC store and a Flyway migration. Provenance is bound to a real resource in the active tenant, so a caller cannot attribute a copy to material that was never exported. All other MSG-07 behaviour (nine audited workflow actions, retention windows, legal holds that block retention, chart provenance, revocation effects, copy requests) already existed in `messaging/governance` from READY-38/V62 and was reused rather than duplicated. Tests prove that a held conversation survives the retention job and that an export carries its provenance.

## Affected requirements

MSG-07. Supporting: OPS-02 (append-only audit), ARC-02 (tenant isolation), OPS-07 (scoped expiring export).

Acceptance mapping:
- "Audit opening, viewing, sending, assigning, downloading, acknowledging, filing, correcting and restricting" — existing `AuditAction` values OPEN/VIEW/SEND/ASSIGN/DOWNLOAD/ACKNOWLEDGE/FILE/CORRECT/RESTRICT, proven by `MessagingGovernanceServiceTest.recordActionAuditsEveryConversationAndFileAction` (unchanged, reused).
- "Apply a retention period; a legal hold blocks deletion" — existing `applyRetention`/`retentionDecision` skip held resources; proven by `heldConversationSurvivesRetentionAndExportKeepsProvenance` and the existing `applyRetentionSkipsHeldAndRecentResources`.
- "An export keeps provenance" / "exports carry provenance" — new `ExportProvenance`, required, field-validated and bound to a tracked tenant resource in `createExport`, persisted in V78 and `JdbcMessagingGovernanceStore`, returned by `POST /api/v1/messaging-governance/exports`; proven by `createExportBoundsScopeAndTtl`, `createExportRejectsMissingProvenance`, `createExportRejectsBlankOrOverlongProvenanceFields`, `createExportBindsProvenanceToATrackedSourceResource`, `heldConversationSurvivesRetentionAndExportKeepsProvenance`, `MessagingGovernanceControllerHttpTest` and the JDBC round-trip assertion in `JdbcMessagingGovernanceStoreIntegrationTest`.

## Data changes

`db/migrations/V78__build_16.sql` (reserved version): additive `ALTER TABLE public.messaging_export ADD COLUMN source_reference text NOT NULL DEFAULT '', source_revision text NOT NULL DEFAULT '', export_purpose text NOT NULL DEFAULT ''`. No new table, so V62's forced RLS, tenant policy, append-only reject-mutation triggers and grants are inherited unchanged. Existing rows are backfilled with empty provenance; only newly created exports carry validated values. No lock or volume concern beyond the metadata-only default backfill on a small governance ledger. Forward fix: none needed (additive expand). Rollback is dropping the three columns in a later contract migration.

## Authorization boundaries and audit events

Unchanged: `createExport` derives organization and subject from `TenantContext`, re-checks active membership and the `EXPORT` action permission, and appends the `EXPORT` audit fact only after a successful store write. Order is now scope/TTL validation → context → authorization → provenance validation → source-resource binding → write → audit. Field-validation rejections write no audit fact (asserted by the two rejection tests); an untracked source resource is concealed as `404 NOT_FOUND` with a `NOT_FOUND` audit fact, consistent with other governance commands (asserted by `createExportBindsProvenanceToATrackedSourceResource`). `sourceReference` is a UUID bound to a resource in the active tenant, `purpose` is an allowlisted code and `sourceRevision` is a bounded identifier token, so no clinical free text or patient identifier can enter the immutable record. No new audit action was added.

## Migration and rollout considerations

The `messaging_export` table is append-only with reject-mutation triggers; `ADD COLUMN ... DEFAULT` is DDL and does not fire row triggers. `scripts/check-migrations.py --require-baseline` passes. The SELECT/INSERT in `JdbcMessagingGovernanceStore` were updated in the same change so old rows read empty provenance and new rows persist it.

## Findings

- DevSecOps simulated review (static file reads, no gates executed) returned F1–F4. F1 (provenance was self-asserted, not bound to a real resource) — fixed: `sourceReference` is now a UUID checked against `store.resources(org)`; untracked sources are concealed with `404`. F2 (free-text fields could carry PHI) — fixed: `purpose` is an allowlisted code and `sourceRevision` a bounded identifier token. F4 (legacy rows with empty provenance) — fixed by documenting the pre-V78 empty values on `ExportProvenance`. F3 (export write and audit fact are not in one transaction) — deferred: this is the inherited pattern of every governance command (`putExport` and `append` each use the tenant-guarded `TransactionTemplate`), so fixing it here alone would make `createExport` inconsistent and would be a cross-cutting change outside this story's scope; the integrator/owner can schedule it as one bounded transaction refactor for all governance commands.
- The MSG-07 governance implementation already existed at HEAD (READY-38, V62). Reusing it was deliberate; duplicating a second audit/hold/retention subsystem would have violated the reuse rule. The only unmet acceptance clause was export provenance.
- Retention in this codebase produces an explicit eligibility decision and audit fact; there is no physical delete command in the governance store. "Held conversations survive the retention job" is therefore proven as "not eligible for removal" plus `LEGAL_HOLD`, consistent with the existing design. No destructive DDL was introduced.
- Pre-existing, outside task scope and NOT modified: committed conflict markers in `apps/api/src/main/java/com/aurevia/smartclinic/exchange/hl7/{Hl7ParseException,Hl7Parser,Hl7Segment}.java` (from a prior BUILD-37 merge). They are inside Javadoc blocks, so javac and `check-docs.py` pass. The next worker/owner should remove them; this task must not edit files outside its scope.
- Worker-environment false positive confirmed once (see Test evidence): the six `test_check_pack` failures come from the skip-worktree CI `opencode.json`, not from this change.
- No defect was found in the new code; no `BUGS.md` entry is warranted (and workers do not edit trackers).

## Lessons for workers

- Before implementing a BUILD story, grep the domain package: several MSG-0x slices were already landed by earlier READY/SMSG stories. Close the specific missing clause instead of rebuilding the subsystem, and record which existing tests you are reusing as acceptance evidence.
- When adding a "provenance" or "origin" field to an audit/export record, bind it to a real, tenant-visible resource and allowlist its free-text codes. A client-supplied string that is only checked for length is not provenance and will be flagged by defensive review.
- When a cloud worker sees `opencode.json is stale`, check `git ls-files -v opencode.json` first; `S` means the CI profile is masking the committed profile and the pack failures are environmental. Do not regenerate or edit it.
- `scripts/check.sh` and `scripts/worker-check.sh` are not safe final gates for a parallel worker with a short budget: they fan out to the full `mvn verify` / all integration suites. Run the touched test classes, the single affected integration class, SpotBugs and the individual policy scripts, then let the integrator own the full gate.
