# SPEC-XCH-04-C02 — clause 2 (API test): match five identifiers before import

## Clause

Match patient, source, accession, destination and order identifiers before import.

## Status

In progress.

## Requirement and discovery

- Requirement XCH-04 (`PROJECT_V1_SPEC.md:66`): "Route every final, corrected and critical result to a named owner and coverage queue. Match patient, source, accession, destination and order identifiers before import. Unmatched or conflicting reports enter a reconciliation queue. ..."
- Clause implementation found (tool evidence, source reads):
  - `apps/api/src/main/java/com/aurevia/exchange/result/ResultRules.java` — pure `match(Optional<ExpectedOrder>, ResultIdentifiers)`: absent expectation → `UNMATCHED`; five exact comparisons → `CONFLICT` naming each disagreeing field; all equal → `MATCHED`.
  - `apps/api/src/main/java/com/aurevia/exchange/result/ResultRoutingService.java` — `importResult` validates, authorizes and calls `importGuarded`; `importGuarded` matches before any write and diverts a non-match to the reconciliation queue (`insertReconciliation`) without `insertReport`; `authorize` re-derives membership and roles inside the transaction.
  - `apps/api/src/main/java/com/aurevia/exchange/result/ResultController.java` — `POST /api/v1/xch04/results` thin adapter: 201 report, 202 reconciliation; `ApiErrorHandler` renders 403 domain denials.
  - Supporting: `ResultModel.java`, `ResultCommands.java`, `ResultActionPolicy.java`, `ResultRepository.java`, `AuditAppender.java`, `TenantContext.java`.
  - Persistence: `db/migrations` xch04 tables with RLS; real two-org isolation is exercised by `apps/api/src/test/java/com/aurevia/it/exchangeresult/ResultRoutingIntegrationTest.java`.
  - Contract: no xch04 route is published; all seven `/api/v1/xch04/*` routes are in `contracts/openapi/missing-routes.txt` (lines 122-124, 350-353). No contract change is in scope.
- Neighbouring evidence (not re-tested here): `it/exchangeresult/ResultRulesTest.java:43-49` covers each of the five field-level mismatches (including `orderId`) at rule level; `it/exchangeresult/ResultRoutingServiceTest.java` covers service branches; `acceptance/exchange/UnmatchedReportReviewAcceptanceTest.java` covers unmatched/conflicting at service level.

## Acceptance mapping

- One positive HTTP case: all five identifiers equal → 201 `ResultReport`, `insertReport` called, no reconciliation.
- Four HTTP CONFLICT cases: patientId, sourceId, accessionId, destinationId each wrong → 202 `ReconciliationEntry`, `reason=conflict`, exact mismatch name, `insertReport` never called.
- Order-identifier negative: an unregistered/wrong `orderRef` is not visible to `findOrder` and is refused as 202 `UNMATCHED` with no report write. The `orderId` field-comparison branch is proven at rule level by the existing `ResultRulesTest.eachMismatchedIdentifierIsReportedByName` (line 48), because the real repository always builds `ExpectedOrder.orderId` from the queried `order_ref`.
- Authorization negatives: missing result-import role and missing active membership → 403 `FORBIDDEN`, `DENIED` audit, no lookup or write.
- Tenant negative: an order not visible in the active tenant (RLS concealment modelled by `findOrder` returning empty) → 202 `UNMATCHED`, no report write, audit bound to the active tenant context. The mock does not prove database RLS; `ResultRoutingIntegrationTest.authorizationAndTenantIsolationFailClosed` is the real isolation evidence.

## Lessons for workers

- A standalone MockMvc clause test proves the service gate only when the real service and rules are wired behind the controller; assert `never()` on the write and the exact refusal status, not just the response code.
- Do not fabricate a repository state that the real store cannot produce (for example an `ExpectedOrder` whose `orderId` differs from the lookup key) just to hit a branch; cite the pure-rule test that owns that branch instead.
- In a mocked-repository tenant test, model RLS concealment with `findOrder → Optional.empty()` and say plainly that this does not prove PostgreSQL isolation; cite the real two-org integration test.
- `jsonPath("$.array").value(List.of(...))` can report a false mismatch in this Spring/Jackson version; assert `$.array[0]` or `isEmpty()` instead.
- Re-run the targeted suite after every reviewer-driven edit, even a one-line assertion addition.
