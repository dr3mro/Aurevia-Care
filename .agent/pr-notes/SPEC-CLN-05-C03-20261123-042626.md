# SPEC-CLN-05-C03 — CLN-05 clause 3 API evidence

## Summary

Test-only story. CLN-05 clause 3 ("Save signer, effective time, signed time,
content checksum and template version") is already implemented in the
`clinical.notes` slice. Added an HTTP-level integration test that proves all five
values are saved on a signed revision by reading the row back under tenant RLS,
plus seven negative/spoof cases; added the clause note. No production code,
migration, contract, existing test or tracker was changed.

## Findings

- The first red run exposed a fixture-format trap: `ClinicalNoteRevision`
  exposes `effective_at::text` / `signed_at::text`, which render as
  `2020-01-01 00:00:00+00`, not `Instant.toString()` output. Instants are now
  compared with PostgreSQL boolean expressions (`effective_at = CAST(... AS timestamptz)`,
  `signed_at >= effective_at`, `signed_at >= <instant captured before sign>`),
  so the test is deterministic across session time zones.
- Pre-existing at HEAD (not from this change): conflict-marker text inside
  Javadoc comments of
  `apps/api/src/main/java/com/aurevia/smartclinic/exchange/hl7/Hl7ParseException.java`,
  `Hl7Parser.java` and `Hl7Segment.java`. It compiles and is out of scope; no
  production file was touched.
- `contracts/openapi/missing-routes.txt` still lists the clinical-note routes:
  pre-existing, out of scope, documented in the clause note's `## Gap`.
- Reviewer Optional findings were adopted: the spoof case now guards an absent
  or JSON-null `signedAt` before its timestamp check, and `createId()` asserts
  that the create response carries a non-empty note id. The final targeted suite
  after those edits is the green run recorded above.
- No task outside the two-file scope was needed, so no `task-requests` block.

## Lessons for workers

- When a record maps `timestamptz::text` into JSON, compare instants with SQL
  booleans under the tenant context instead of `Instant.parse(...)` on the
  response string; the driver's text layout is not ISO-8601.
- A spoof test against a Java record request must use a raw JSON body with extra
  keys; the existing `RecordClinicalAuthorSeparatelyDataEntryActorTest`
  `recordWithSpoofedActor` proves Spring Boot ignores unknown `@RequestBody`
  properties.
- In a cloud worker, the `opencode.json is stale` pack failure is the CI profile
  under `skip-worktree`; verify with `git ls-files -v` and `git show HEAD:` once,
  then run the remaining gate stages individually instead of regenerating.
