## Findings

1. **Fix disposition:** no in-scope correctness defect. The grant/review transaction,
   outcome validation/closure, self-review depth (SQL guard + V88 CHECK), expiry on the
   next decision, cross-tenant RLS and support default-deny were each verified by both
   reviewers. `closeReview`'s ignored zero-row result is defensible: a service-created
   grant always has an open review row in the same transaction, and `reviewGrant` is
   single-shot; zero rows occur only for pre-V88 direct-SQL grants.
2. **Applied change (in scope):** hardened the cross-tenant negative HTTP test so a
   denied cross-tenant review is proven not to mutate the owner's review row.
3. **BLOCKER, pre-existing and out of scope:** `python3 -I scripts/check-docs.py` exits 1
   with `docs/reference/partner-api-guide.md:200: table row has 4 cells, expected 3`
   (the `?status=open|resolved` pipe inside a code span is read as a cell separator by
   `scripts/check-docs.py`, added in WFAUDIT-07). This also fails
   `test_check_docs.RepositoryTests.test_repository_docs_are_consistent` (the only
   failure in the 696-test Python suite, verified with the committed `opencode.json`
   restored). The file is unchanged on `origin/main`, predates BUILD-34's base, and is
   outside this task's scope — no task covers the fix. A task-request is filed below.
4. **Environment artifact, not a defect:** the worktree `opencode.json` is skip-worktree
   (`S`) and holds the CI profile, so `check-pack.py` / `gen-opencode.py --check` report
   staleness in the raw worktree (MEMORY OPS-CW-003-01). With the committed `HEAD` profile
   restored both checks exit 0; the original file was restored byte-for-byte afterwards.
5. **Out-of-scope follow-ups from the reviews:** no data-boundary consumer of the
   `active()` / `checkAccess()` decisions (expiry is proven only at the decision
   endpoint); no real-time delivery of the privacy-auditor alert; `checkAccess()` does
   not test a `platform_support` role; "never stacked" is app-level, not DB-enforced;
   `/api/v1/access` has no OpenAPI entry / regenerated client. None is caused by this
   change; each needs its own owner story.

## Lessons for workers

- Re-run the targeted JaCoCo command for every touched class before claiming 100%;
  `AccessRepository` in particular needs `AccessIntegrationTest` in the `-Dtest` list or
  its SQL methods show as uncovered.
- In a cloud worker, `git ls-files -v opencode.json` is `S`: temporarily restore the
  committed `HEAD` profile to run `check-pack.py` / the Python suite, then restore the
  CI profile byte-for-byte (BUILD-09-fix pattern). Mixing the two profiles up has
  produced false findings before.
- A reviewer-hardened negative HTTP test should re-assert the protected row's state
  after the denied request, not only the denial status.
