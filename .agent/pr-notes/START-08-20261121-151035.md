## Findings

- **Pre-existing contract gap (not fixed, allow-listed):** `listCatalogFamily`, `GET /api/v1/catalogs/{family}` (`contracts/openapi.yaml:151-165`), returns a bare `type: array` with no `cursor`, `limit` or `nextCursor`. It is the only detected list GET that fails the rules (proved by `theOnlyExemptionIsTheBareArrayCatalogFamilyList`). It sits on a short allow list with `// TODO`; a follow-up story should paginate catalog families and remove the exemption. No contract or controller was edited.
- **Environment artifact:** 3 local `test_check_pack` failures from the skip-worktree CI-profile `opencode.json` (OPS-CW-003-01). Not a change defect; no file regenerated.
- **Rule keys on `nextCursor`, not `items`:** `AuditPage` uses `events` while the other six page schemas use `items` (`contracts/openapi.yaml:596,469,494,640,705,712,772`), so the response rule must not assume an `items` field.
- The real contract's seven paginated list endpoints all use `cursor`, `limit` with `maximum: 200`, and a `nextCursor` page field; `queryAuditEvents` notably uses `events` instead of `items`.

## Lessons for workers

- SnakeYAML 2.6 is already on the API test classpath via Spring Boot; `new Yaml().load(String)` works and no new dependency is needed. Quote response-code keys (`'200'`) in hand-written YAML so SnakeYAML does not coerce them to integers.
- Surefire sets `basedir` to the module (`apps/api`), so the repo-root contract is `../../contracts/openapi.yaml` — two parent levels, not one.
- When a synthetic fixture is made by `String.replace`, assert the string actually changed; a no-op replacement gives a vacuous green.
- Test-only Java changes do not move JaCoCo (test classes are not instrumented). Say so explicitly instead of claiming an unrun coverage number.
- `git ls-files -v opencode.json` showing `S` plus three `test_check_pack` failures is the known skip-worktree CI-profile artifact; never regenerate `opencode.json` as a worker.
- Detect list responses from the response schema shape (array or `$ref` to a `*Page` schema), never from `cursor`/`limit`/`nextCursor` themselves, or a mutated fixture can disappear from the check and pass vacuously.

## Repair 1 — coverage gate failure (flaky integration-test setup, not a coverage gap)

The post-worker coverage gate (`scripts/coverage-check.sh` → `mvn -q -B -f apps/api/pom.xml -Pno-security verify`, PostgreSQL up, `AUREVIA_PG_ADMIN=postgres`) failed with `Tests run: 2799, Failures: 0, Errors: 1`, one error:

`JdbcPatientAccessStoreIntegrationTest.prepare:108 ? PSQL ERROR: role "aurevia_migrate" does not exist`

Root cause (tool evidence, surefire report `com.aurevia.messaging.enrollment.it.JdbcPatientAccessStoreIntegrationTest.txt`): the class had **two** `@BeforeAll` methods — `roles()` created the `aurevia_migrate` / `aurevia_app` roles, while `prepare()` created the database `OWNER aurevia_migrate`. JUnit does not guarantee the relative order of several `@BeforeAll` methods in one class; its deterministic method-hash ordering put `prepare()` first, so `CREATE DATABASE ... OWNER aurevia_migrate` (line 108) ran before the role existed. This was a pre-existing defect in another worker's test file, unrelated to this story's OpenAPI test; it surfaced because the gate runs the whole suite.

Deterministic reproduction: with the role dropped (`DROP ROLE IF EXISTS aurevia_migrate; DROP ROLE IF EXISTS aurevia_app;` and `DROP DATABASE IF EXISTS aurevia_patient_access_it WITH (FORCE)` as `postgres`), the targeted run fails red every time. An earlier run appeared green only because the failed gate's own `roles()` had left the role persisted in the cluster — confirming the dependency on leftover state.

Fix (test-only): merged the role-creation `DO $$ ... $$` block into the single `prepare()` `@BeforeAll` ahead of the `CREATE DATABASE` statement and deleted the separate `roles()` method. This matches the setup pattern used by every other `@Tag("integration")` test in `apps/api` (create roles with `IF NOT EXISTS`, then create the DB in the same method) and removes the ordering dependency rather than relying on `@Order`/method names. Added Javadoc explaining why role creation and DB creation must share one `@BeforeAll`. No production code, threshold, exclusion or other test was changed.
