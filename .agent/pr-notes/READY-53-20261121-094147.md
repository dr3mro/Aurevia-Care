# READY-53 — Public status, maintenance and support pages without patient data (WEB-13)

## Summary

Added a separately hosted, read-only set of six static public HTML pages plus one shared stylesheet, a hosting README and a Vitest suite that reads the files from disk. The pages carry a status notice, a maintenance notice, a support contact, and placeholder privacy, accessibility and terms documents. Legal placeholders are explicitly marked `Pending approval`; no legal claims are invented. Contacts use the reserved placeholder `support@example.invalid`. No JavaScript, external fonts, scripts, trackers or remote resources are used, and no personal or clinical data appears anywhere.

Entry point to test trace: `apps/staff-web/check.sh` → `npm run test:coverage` → Vitest `tests/publicPages.test.ts` reads each file under `apps/public-pages/` from disk and asserts its existence, legal links, shared stylesheet, absence of scripts/external resources, absence of patient/MRN/chart terms, accessibility structure and placeholder contact domain.

## Findings

- No approved wording for a privacy notice, accessibility statement or terms of use exists in `docs/` (searched `docs/`, `docs/design/approved/`, the launch checklist and the specification). Per the story, short neutral placeholders were written and each legal page is marked `Pending approval`; no legal claim was invented.
- `apps/staff-web/node_modules` was absent at the start; `check.sh` installs pinned dependencies with `npm ci` automatically. No dependency was added to `package.json`.
- No patient data was used in content, tests, logs or URLs. All contact addresses use the reserved `example.invalid` domain.
- Simulated UX/accessibility review (orevia-ux-reviewer subagent) raised two concrete findings, both fixed and covered with regression assertions:
  - **Medium, fixed:** `styles.css` used hardcoded `-1rem` full-bleed margins while the ≤360 px media query narrowed the body gutter to `0.75rem`, causing ~4 px horizontal overflow per side at 320 px (WCAG 1.4.10). Replaced with a single `--gutter` variable driving body padding and header/footer full-bleed margins via `calc(-1 * var(--gutter))`; the media query now changes only `--gutter`. Regression test: stylesheet must contain `--gutter: 1rem;` and must not contain `-1rem`.
  - **Low, fixed:** `<main id="main">` was not programmatically focusable, weakening the skip link. Added `tabindex="-1"` to all six pages. Regression test: each page contains `<main id="main" tabindex="-1">`.
  - The reviewer's other in-scope checks were clean (lang/dir, one h1, focus-visible outline, underlined links, contrast, no scripts/external resources, `Pending approval` legal placeholders, legal links on every page).
- `python3 -I scripts/check-pack.py` reported `opencode.json is stale`. This is the documented cloud-worker measurement artifact, not a defect: `git ls-files -v opencode.json` returns `S` (skip-worktree), so the worktree holds the CI profile copied by `agent-run.sh` and `git diff -- opencode.json` is empty. Per AGENTS.md the worker must not edit `opencode.json`; it was left untouched.

## Lessons for workers

- Mirror `tests/indexability.test.ts` when adding disk-reading Vitest tests: resolve from `import.meta.url`, use `existsSync` so a missing file becomes an assertion failure instead of an uncaught error, and compute `publicRoot` as two levels up from `tests/`.
- The verbose React "must be used inside Provider" stack traces in `apps/staff-web/check.sh` output are expected negative-path tests; judge the gate by its exit code and the final `Test Files`/`Tests`/coverage lines, not by stack-trace presence.
- Static content lives in `apps/public-pages/` and is validated from the staff-web test suite without adding production source, so it does not change the 100% V8 coverage denominator.
