## Summary

Replaced the process-local `@Repository` `InMemoryFlowPolicyStore` with a
PostgreSQL adapter. Added `db/migrations/V61__flow_policies.sql` with three
tenant-owned tables (`flow_policy`, `flow_approved_notice`, `flow_access_audit`),
each with forced row-level security, a `public.app_org()` policy and explicit
grants; the access-fact ledger is also protected by append-only triggers.
`JdbcFlowPolicyStore` implements every `FlowPolicyStore` method through the
tenant-guarded `TransactionTemplate` and parameterised SQL only, reusing the
authoritative `public.has_active_membership` fold instead of duplicating
membership state. `InMemoryFlowPolicyStore` lost its `@Repository` and moved to
test scope; the existing unit test constructs it directly with `new`, so no
`@Primary` test bean was needed.

## Data changes

`V61__flow_policies.sql` is additive (`-- Change: expand`) and creates three
tables:

- `flow_policy` — `(organization_id, id)` key plus
  `UNIQUE (organization_id, locale, platform)`, bounded `locale`/`platform`
  checks and integer `version`, `created_at`. Read-only to `smartclinic_app`.
- `flow_approved_notice` — `(organization_id, id)` key plus
  `UNIQUE (organization_id, notice_kind)`, bounded notice-kind check,
  `created_at`. Read-only to `smartclinic_app`.
- `flow_access_audit` — `(organization_id, id)` key, database-owned `seq` and
  `id`, non-sensitive fact fields, `occurred_at`, `created_at`; `UNIQUE (org,
  seq)`, no UPDATE/DELETE/TRUNCATE grant and `reject_immutable_mutation()`
  triggers for UPDATE, DELETE and TRUNCATE.

Every table carries `organization_id NOT NULL REFERENCES public.organization`,
`created_at timestamptz NOT NULL DEFAULT now()`, `ENABLE` + `FORCE ROW LEVEL
SECURITY`, a `tenant_isolation` policy with both `USING` and `WITH CHECK`, and
explicit grants/revokes to `smartclinic_app`. No existing migration was edited;
no backfill, lock or volume impact beyond three empty tables. Forward/rollback:
Flyway version 61 is new; a contract later removing a table must point at an
earlier `Change: expand` per `docs/decisions/0002`.

## Authorization boundaries and audit events

Every adapter method runs inside the shared tenant-guarded
`TransactionTemplate`, so `app.current_org()`, `app.actor`, `app.purpose` and
`app.correlation_id` are bound transaction-locally before any SQL. Reads carry
no manual organization predicate; forced RLS confines them. Inserts write the
method's `organizationId` so `WITH CHECK` fails closed on a mismatch —
`auditFactsAreOrderedTenantScopedAndFailClosedOnCrossTenantWrite` proves a
rejected cross-tenant write, and `auditFactsAreImmutableForTheMigrationOwnerToo`
proves the append-only trigger. The adapter changes no authorization decision:
`PatientFlowPresentationService` still re-derives membership on every request
through the authoritative fold. No audit event type was added or changed;
`FlowAudit` facts are stored durably with the same fields and insertion order
as before.

## Migration and rollout considerations

V61 was free (`ls db/migrations/ | grep ^V61` returned nothing). The migration
is applied last under both `sort -V` (`db/check.sh`) and Flyway's numeric order,
so `organization`, `app_org()` and `reject_immutable_mutation()` already exist.
The policy/notice tables are intentionally seed-free in the migration: a seed
would need `app.current_org` set in the same session or forced RLS `WITH CHECK`
would reject it. The tagged test sets that GUC before seeding. The production
bean change is immediate on deploy: the new adapter reads pre-existing folds,
so no data migration or dual-write is required. The tagged test creates and
drops its own `smartclinic_flow_policy_it` database.

## Findings

1. **V61 is free** (tool): no tracked V61 existed and the migration gate is
   green, so READY-35's stale V59 collision did not recur.
2. **AUD-20261120-04 is wired into `db/check.sh`** (tool): the catalog scan at
   lines 55–87 fails when a table with `organization_id` lacks FORCE RLS, and a
   second query fails when it has no policy. No separate script named after the
   finding exists; running `db/check.sh` exercises the gate.
3. **Zero-row `queryForObject` hazard avoided** (specialist reviewer B2): the
   interface requires `null` for an absent policy version, but
   `queryForObject(..., Integer.class)` throws `EmptyResultDataAccessException`
   on zero rows. `policyVersion` uses `SELECT MAX(version) ...`, which always
   returns one row whose SQL NULL maps to a null `Integer`; no catch branch was
   added.
4. **Two-bean ambiguity avoided** (specialist reviewer B1): before this change
   both the in-memory adapter and the new adapter would be `@Repository` beans
   for the single `FlowPolicyStore` injection point, causing
   `NoUniqueBeanDefinitionException`. Removing `@Repository` and moving the
   in-memory class to test scope leaves exactly one production bean;
   `productionBeanIsTheJdbcStore` asserts it.
5. **Outcome values not over-constrained** (database reviewer finding 1):
   `FLOW_PRESENTATION`, `FLOW_NOTICE` and outcomes `SUCCESS`, `DENIED`,
   `INVALID_INPUT`, `FORBIDDEN` are all stored by the service, so `action` and
   `outcome` remain unconstrained `text NOT NULL`, matching V60.
6. **Deterministic notice order** (database reviewer finding 2): reads use
   `ORDER BY notice_kind`, which matches the approved list order asserted by
   both the existing unit test and the new integration test.
7. **Defects found: none introduced.** No existing test was weakened, skipped
   or deleted. No threshold, exclusion or suppression was added beyond the
   standard Spring-collaborator SpotBugs annotation copied from
   `JdbcMessagingStore`.

## Lessons for workers

- `queryForObject` does not return `null` on zero rows — use an aggregate
  (`MAX`/`COUNT`) that always returns one row, or `query(...)`, before adding a
  `catch (EmptyResultDataAccessException)` branch you would then have to cover.
- When replacing a `@Repository` in-memory store, remove the annotation in the
  same change as adding the JDBC `@Repository`; two beans for one interface
  break every `@SpringBootTest` at context startup.
- New tables are not covered by V2's static RLS list: each migration must
  ENABLE/FORCE RLS, add its own `tenant_isolation` policy and grant/revoke
  explicitly. `db/check.sh` now enforces this for every table with an
  `organization_id` column.
- Forced RLS `WITH CHECK` rejects a seed insert when `app.current_org` is
  unset, even for the migration owner; set the GUC in the seeding session rather
  than disabling RLS.
