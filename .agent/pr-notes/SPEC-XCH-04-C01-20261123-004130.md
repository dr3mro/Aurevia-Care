# SPEC-XCH-04-C01 — API proof for XCH-04 clause 1

## Summary

Test-and-documentation-only story. Proves at the HTTP/API level that every FINAL, CORRECTED and CRITICAL
result is routed to the named owner and coverage queue registered on its matched order, and records that
evidence in a clause document. No production code, existing test, migration, contract or tracker changes.

## Findings

- Clause is implemented: `ResultRules.route` handles FINAL/CORRECTED/CRITICAL and `ResultRoutingService`
  persists the matched order's owner/queue onto every `ResultReport`. The new test adds the missing
  clause-focused HTTP proof for CORRECTED (and a single end-to-end proof for all three dispositions),
  not duplicate unit coverage.
- First targeted run was red at `assertEquals(1, lineage.size())` (`expected: <1> but was: <3>`): `GET
  /results/{id}` returns the whole order lineage for any requested revision. Assertions were corrected to
  three for every revision. No production defect and no production edit.
- No OpenAPI paths exist for the three xch04 routes (`contracts/openapi/missing-routes.txt:124,350,352`).
  Out of scope; recorded in the clause doc `## Gap`. One separate contract task would add the paths,
  regenerate the client and remove those lines.
- `Routing.critical` is in-memory only; neither `ResultReport` nor `xch04_report_revision` has a critical
  field. The test observes the marker through `kind` and `XCH04_CRITICAL_ROUTE`; a persisted column would
  need migration + DTO + OpenAPI work in a separate task and is not required by this clause sentence.
- The two-tenant test proves the security outcome but cannot attribute the refusal to RLS alone: the peer
  order references ORG_B's patient while the ORG_A caller must carry an ORG_A patient to satisfy the FK,
  so identifiers differ too. The clause doc was worded accordingly (devsecops Optional finding adopted).
- Environment artifacts, not change defects: worktree `opencode.json` is the CI profile under
  `skip-worktree` (`git ls-files -v` → `S`), so `check-pack.py`, `worker-check.sh` and six
  `test_check_pack` tests fail while `git show HEAD:opencode.json` is the valid committed local profile;
  `coverage` is not installed in this image. `git status --short` confirms only the three new files,
  with no `M` entry under `apps/api/src/main`, `db/migrations`, `contracts` or coverage config.
- Pre-existing base defect (NOT touched by this story): `git grep -nE '^(<<<<<<<|>>>>>>>) '` finds six

## Lessons for workers

- `GET /api/v1/xch04/results/{id}` returns `ResultDetail(current, review, lineage, notifications)` where
  `lineage` is the whole order lineage: assert `/current/owner` (not `/owner`) on GET, flat `/owner` on the
  POST response, and expect every revision's lineage to contain all revisions imported so far.
- A CORRECTED import must set `supersedesVersion` to the current tip; otherwise it diverts to 202
  reconciliation and the test fails for the wrong reason. FINAL and CRITICAL must omit it.
- A cross-tenant negative must use the caller's own patient: sending the peer tenant's patient violates the
  `(organization_id, patient_id)` foreign key and returns 500 instead of exercising concealment.
- The critical marker is not a field: assert `kind="critical"` plus the `XCH04_CRITICAL_ROUTE` audit, with
  final/corrected as zero controls. Do not assert a `/critical` JSON path.
- The plan reviewer caught the wrong detail JSON path and a would-be false `## Gap: None` before any code
  was written — a one-minute plan gate is cheaper than a debugging round.
- In a cloud worker, a `skip-worktree` `opencode.json` makes `check-pack.py` and `test_check_pack` fail;
  verify `git show HEAD:opencode.json` and run the remaining gate stages individually. Never regenerate it.
